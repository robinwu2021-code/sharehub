# 对比分析 · 简电云 vs ShareHub（我方）

> 对比基线：简电云 [01-运营端功能矩阵](01-运营端功能矩阵.md)（13 域/25 模块/**87 菜单项**，真实菜单导出）
> 我方基线：[运营端功能清单 §三](../../requirements/运营端功能清单.md)（7 域/14 模块/**73 菜单项** + 18 页内动作，与 `ops-web/lib/nav.ts` 1:1）
>
> ⚠️ **可比性边界**：对方是 **OCPP 充电桩线**，我方是**共享充电宝线**。凡涉及业务名词（桩/枪/车辆 ↔ 柜机/仓位/充电宝）不做等价映射，只比**经营结构与能力**。C 端对比用对方**充电宝线**原型（[02-C端信息架构](02-C端信息架构.md)），可比性高。
> 「我方状态」中的 ✅/◐/⬜ 指 **ops-web 前端实现度（均为 mock）**，后端另见 [实现状态总表](../../technical/实现状态总表.md)。

## 一、它有 · 我们没有（补齐候选）

| # | 简电云能力 | 菜单位置 | 对充电宝业态的意义 | 建议 |
|---|---|---|---|:---:|
| 1 | **告警规则引擎**：告警代码字典 + 通知规则 + 告警记录 + 告警通知 | 告警管理（独立域，4 项）| 我们只有监控 tab 里的"故障数"，**没有告警码字典、没有规则配置、没有通知触达**。这正好是我们 [§三·B G6](../../requirements/运营端功能清单.md) "故障→自动开工单未通"缺的上游 | **P1 强烈建议** |

| 7 | **应用版本管理** | 运营管理/基础管理 | C 端 App 版本/强更控制。我们 c-app 已是 Capacitor 打包 App，**迟早要** | P2 建议 |
| 8 | **问题管理（FAQ/问题库）** | 运营管理/基础管理 | C 端报障时的问题类型字典源。我们客服模块缺这个字典 | P2 建议 |
| 9 | **银行管理** | 运营管理/基础管理 | 提现银行字典。我们提现审核缺收款方字典 | P2 |
| 10 | **设备编码（出厂码/二维码批次）** | 设备管理 | 我们有机柜号但**无出厂编码/贴码批次**管理，量产投放会痛 | P2 |
| 11 | **密钥设置（自助 API Key）** | 平台设置/其他设置 | 我们 OpenAPI 应用在阶段 3 | 保持 |
| 12 | **发票设置（税率/税号配置）** | 平台设置/其他设置 | 我们有发票 tab(阶段3) 但无税率配置；MENA 有 VAT/TRN 硬需求 | P2 建议 |

| 14 | **登录设置 + 第三方登录配置** | 平台设置/服务设置 | 登录方式可配置化（哪些国家开哪些登录）。我们硬编码 | P2 |

| 17 | 车辆品牌/车辆管理、RFID 卡号、充电电量 | 会员/设备/基础 | 充电桩独有 | 不做 |

## 三、都有但形态不同（设计取舍）

| 维度 | 简电云 | ShareHub（我方） | 评判 |
|---|---|---|---|
| **分成建模** | 站场分成 + 商户分成（挂在站场下，按对象配）| 分润规则（维度 VENUE/AGENT + 模式 渠道分账/平台记账 + 优先级）+ 分润明细 + 结算单 | **我们更抽象可扩展**；对方更直观易上手 |
| **财务组织方式** | **按角色切**：平台/运营商/商户/会员 各一套收支流水，运营商与商户各有提现审核 | **按功能切**：规则/明细/结算/分录/提现/对账/发票 | 各有道理。对方的"按角色切"让**每个角色一眼看清自己的账**，值得在我们结算单里加角色视图 |
| **告警 → 运维** | 告警码字典 → 通知规则 → 告警记录 → 告警通知（配置化，**终点是通知人**）| 监控故障数 → （断裂）→ 工单看板/派单（**终点是工单闭环**）| **两边各缺一半**：把对方的规则引擎接上我们的工单，才是完整链路 |
| **设备台账层级** | 桩 → 枪（两级）+ 编码 + 库存 + 日志 + 配置 + 概览 | 机柜 → 仓位 + 充电宝（两级）+ 指令记录 + 库存调拨 + OTA | 结构对称。对方多「日志/编码」，我们多「远程指令/OTA」|
| **概览** | **分域概览**：站场概览 / 充电桩概览 / 订单概览 三个 | **统一经营看板**（KPI+趋势+告警+待办+榜单）| 我们更聚合；对方各域自带概览，深入某域时更顺手 |
| **会员/用户** | 会员列表 + 会员钱包（+账单）+ 车辆 | 用户列表 + 风控 + 黑名单 + 会员次卡 + 钱包 | 我们更全（多风控）；对方**运营端可直查会员钱包流水**，我们钱包在阶段 3 |
| **支付** | 6 个 PSP 各自配置页，渠道可插拔 | 委托 nearpay 单通道（ADR-005）| 对方为多国部署而生；我们为 MENA 单市场优化。**若将来出非洲/东南亚，需要对方那种渠道抽象** |
| **导航结构** | 13 域 / 25 模块 / 87 项 — 域切得碎（佣金、财务、充值、短信各自成域）| 7 域 / 14 模块 / 73 项 — 收敛进「交易与资金」「用户与服务」| 我们域更少更聚合；对方一级入口多、路径短。**无对错，但对方证明了 13 个一级图标也扛得住** |
| **C 端申诉链路** | 疑问反馈 → 问题详情 → 投诉商家，运营端「投诉订单」承接 | c-app 仅 toast 提示，运营端无投诉列表 | **对方完胜**，端到端闭环，建议照抄 |

## 三·B 字段级实证（2026-07-29 补采：直接读页面表头，非菜单名推断）

> 菜单名只能比"有没有"，表头才能比"模型怎么建的"。以下为实际抓取的列定义。

### 1. 告警三张表 → 一套完整的告警中台

| 页面 | 实际列 |
|---|---|
| 告警代码 | 告警代码 · 告警信息 · **告警等级** |
| 通知规则 | 告警代码 · **通知目标** · **通知渠道** · **通知方式** |
| 告警记录 | 充电桩 · 枪号 · 设备状态 · 站场 · 故障时间 · **设备类型** · **设备厂商** · **错误码** · **厂商错误码** · 状态 · 备注 |

**关键发现：`错误码` 与 `厂商错误码` 是两列。** 说明对方做了**多厂商错误码归一化**——厂商各自的错误码映射到平台统一告警码，再由统一告警码驱动等级判定与通知路由。
👉 我们有 vendor driver 插件化（ADR-003）**但没有错误码归一层**，各家 driver 上报什么就是什么。设备厂商一多，告警就无法统一治理。**这是我们 driver 抽象里缺的一块，且缺得不显眼。**

### 2. 订单表头 → 费用分项拆解

充电订单/异常订单/投诉订单共用一套宽表，费用相关列：
`电费` · `服务费` · **`占位费`** · `订单费用` · `支付金额` · `退款金额`；另有 `占位开始时间`/`占位结束时间`、`停止条件`、`结束类型`。

**关键发现：费用是分项存储的，不是一个总额。** 占位费（车充满不挪走）在充电宝业态的等价物就是**超时费/买断费**。
👉 我们订单目前只有单一金额字段，**租金/超时费/买断费/优惠减免没有拆开**。一旦要做分润（不同费项分成比例可能不同）、要做退款（只退某一项）、要做对账，这个模型会直接卡住。**这是数据模型层的欠债，越晚改越贵。**

### 3. 分成两张表 → 同一数据的双向视图

| 页面 | 列 |
|---|---|
| 站场分成 | 分成站场 · **分成商户与比例** |
| 商户分成 | 分成商户 · **分成站场与比例** |

同一份分成关系，一张按**场地**看"这个站分给谁"，一张按**商户**看"这个商户分了哪些站"。
👉 我们只有「分润规则」一个视角（按规则行看）。BD 谈商户时想看"这家商户手里有哪些点位、总共分多少"，现在得自己筛。**低成本、高体感的改进。**

### 4. 财务流水 → 账户流水模型（每笔带余额）

`收支类型 · 账单编号 · 所属商户 · 流水类型 · 金额 · `**`余额`**` · 状态 · 时间 · 订单编号 · 商户单号 · 备注`

**关键发现：每笔流水带 `余额` 快照。** 这是账户流水（account statement）模型，任意时点余额可直接读、对账时能二分定位差错点。
👉 我们做的是复式记账分录（更规范），但**没有账户余额快照**——查"某商户此刻余额"要现算。两者不冲突：**分录做账、流水快照做查询与对账**，建议都要。

### 5. 提现审核 → 审批留痕完整

`商户资料 · 提现到 · 银行卡号 · 申请金额 · `**`提现手续费`**` · 申请时间 · 审批状态 · 商户单号 · `**`审批人`**` · 审批时间 · `**`驳回原因`**

👉 我们提现审核（阶段 2）目前 mock 没有 **手续费、审批人、审批时间、驳回原因** —— 这四个是资金审批的合规底线，缺了没法追责。

### 6. 投诉订单 → 带证据链的申诉

`投诉问题 · 用户问题描述 · `**`投诉截图`**` · 投诉时间 · 投诉状态 · `**`投诉处理人`**` + 完整订单快照`

👉 用户上传截图 + 平台指派处理人 + 状态流转，且与订单强关联。我们 C 端只有 toast、运营端无此列表。**商户纠纷时这是唯一的取证材料。**

### 7. 充值套餐 / 会员钱包

- 充值套餐：`充值金额 · `**`赠送金额`**` · 支付金额 · 排序号 · 是否启用` → 储值+赠送的经典模型
- 会员钱包：`订单总数 · 订单总额 · `**`充值次数 · 充值总额`**` · 钱包余额` → **用户价值画像直接长在钱包页**，运营看一眼就知道谁是高价值用户

### 8. 计费方案挂在运营商下

收费方案列含 `所属运营商` → **计费方案是运营商级隔离的**，多运营商各管各的价。
👉 我们计费模板是平台级 + 计划中的点位差异化。若将来做多运营商/加盟，需要这一层归属。

## 四、结论：五条可执行的建议

按"对 P1 的影响 × 实现成本"排序：

> 排序依据：**改动成本随时间上升的排最前**（数据模型 > 功能 > 视图）。

| 优先级 | 建议 | 类型 | 理由 |
|:---:|---|:---:|---|
| **1** | **订单费用分项拆解**：租金 / 超时费 / 买断费 / 优惠减免 / 实收 / 退款 分列存储 | 🔴 数据模型 | 对方 `电费+服务费+占位费+订单费用+支付金额+退款金额` 是分项的。我们是单一金额 → **分项分润、部分退款、对账全部做不了**。这是唯一一条"现在不改，以后要迁数据"的建议，**排第一不是因为最重要，是因为最贵** |
| **2** | **设备错误码归一化**：厂商错误码 → 平台统一告警码（字典 + 映射） | 🔴 数据模型 | 对方告警记录里 `错误码` 与 `厂商错误码` 分列。我们多 driver 插件化却没有归一层，**厂商一多告警就治理不了**。属于我们 ADR-003 抽象里缺失且不显眼的一块 |
| **3** | **补告警规则引擎**（告警码字典 + 告警等级 + 通知规则）并**接上工单开单** | 🟡 功能 | 一举解决 G6 上游缺口。做完我们是"规则引擎 + 工单闭环"双全，对方只有前半——**这是我们能反超的点** |
| **4** | **补 C 端申诉链路 + 运营端投诉订单**（含**截图证据**与**处理人**） | 🟡 功能 | 对方端到端闭环，我们只有 toast。商户纠纷时这是唯一取证材料 |
| **5** | **P1 补站点/设备经营明细** | 🟢 视图 | 对方统计在订单域内 P1 可用；我们全压报表域（阶段 2/3）→ P1 上线运营方只有看板 Top5，**看不到按站点的经营数据**。交付体验问题，不是功能问题 |

**次一级（成本低、体感好，可顺手做）**：
- 提现审核补 **手续费 / 审批人 / 审批时间 / 驳回原因** 四列（资金合规底线，我们 mock 里缺）
- 分成加**双向视图**（按场地看 / 按商户看，同一份数据两个入口）
- 财务加**账户余额快照**（分录做账 + 流水带余额做查询对账，两者不冲突）
- 短信/通知**发送记录 + 拉黑**（OTP 是真钱，无记录不可追溯、无拉黑挡不住薅）
- 会员钱包页带**用户价值画像**（订单数/订单额/充值次数/充值额/余额）
