# 对比分析 · 简电云 vs ShareHub（我方）

> 对比基线：简电云 [01-运营端功能矩阵](01-运营端功能矩阵.md)（13 域/25 模块/**87 菜单项**，真实菜单导出）
> 我方基线：[运营端功能清单 §三](../../requirements/运营端功能清单.md)（7 域/14 模块/**73 菜单项** + 18 页内动作，与 `ops-web/lib/nav.ts` 1:1）
>
> ⚠️ **可比性边界**：对方是 **OCPP 充电桩线**，我方是**共享充电宝线**。凡涉及业务名词（桩/枪/车辆 ↔ 柜机/仓位/充电宝）不做等价映射，只比**经营结构与能力**。C 端对比用对方**充电宝线**原型（[02-C端信息架构](02-C端信息架构.md)），可比性高。
> 「我方状态」中的 ✅/◐/⬜ 指 **ops-web 前端实现度（均为 mock）**，后端另见 [实现状态总表](../../technical/实现状态总表.md)。

---

## 一、它有 · 我们没有（补齐候选）

| # | 简电云能力 | 菜单位置 | 对充电宝业态的意义 | 建议 |
|---|---|---|---|:---:|
| 1 | **告警规则引擎**：告警代码字典 + 通知规则 + 告警记录 + 告警通知 | 告警管理（独立域，4 项）| 我们只有监控 tab 里的"故障数"，**没有告警码字典、没有规则配置、没有通知触达**。这正好是我们 [§三·B G6](../../requirements/运营端功能清单.md) "故障→自动开工单未通"缺的上游 | **P1 强烈建议** |
| 2 | **发送治理**：短信记录 + 短信拉黑 | 短信管理（独立域）| 我们有「通知模板」但**无发送记录、无失败追溯、无号码拉黑**。OTP 短信是真金白银，海外尤甚，无治理=被薅 | **P1 建议** |
| 3 | **预约体系**：预约订单 + 预约调价 + 预约设置 | 订单/站场/设置 三处 | 充电宝可映射为"预约取宝/预约归还位"。高峰期热门点位的占位刚需 | P2 评估 |
| 4 | **免费用户白名单 + 免费订单** | 订单管理/免费充电 | 我们的免单是订单干预动作（一次性），对方是**白名单体系**（内测/VIP/BD 演示/商户自用）。运营早期非常实用 | P2 建议 |
| 5 | **充值套餐 + 充值订单 + 充值协议** | 充值管理（独立域）| 预充值/储值模式。我们钱包在阶段 3 且无套餐概念 | P3 保持 |
| 6 | **投诉订单独立列表** | 订单管理 | 我们只有"异常订单"（系统判定）。**用户主动投诉**是另一条流，且对方 C 端有完整申诉链路承接 | **P1 建议**（与 C 端反馈链路配套）|
| 7 | **应用版本管理** | 运营管理/基础管理 | C 端 App 版本/强更控制。我们 c-app 已是 Capacitor 打包 App，**迟早要** | P2 建议 |
| 8 | **问题管理（FAQ/问题库）** | 运营管理/基础管理 | C 端报障时的问题类型字典源。我们客服模块缺这个字典 | P2 建议 |
| 9 | **银行管理** | 运营管理/基础管理 | 提现银行字典。我们提现审核缺收款方字典 | P2 |
| 10 | **设备编码（出厂码/二维码批次）** | 设备管理 | 我们有机柜号但**无出厂编码/贴码批次**管理，量产投放会痛 | P2 |
| 11 | **密钥设置（自助 API Key）** | 平台设置/其他设置 | 我们 OpenAPI 应用在阶段 3 | 保持 |
| 12 | **发票设置（税率/税号配置）** | 平台设置/其他设置 | 我们有发票 tab(阶段3) 但无税率配置；MENA 有 VAT/TRN 硬需求 | P2 建议 |
| 13 | **多支付渠道各自配置页**（Stripe/Paypal/Braintree/Yedpay/ABA/Selcom）| 平台设置/支付设置（7 项）| 我们委托 nearpay 单一通道。对方是**渠道可插拔**，出海到新国家不改代码 | 观察（架构差异，见 §三）|
| 14 | **登录设置 + 第三方登录配置** | 平台设置/服务设置 | 登录方式可配置化（哪些国家开哪些登录）。我们硬编码 | P2 |
| 15 | **订单统计三件套**（设备统计/站场统计/站场明细）**放在订单域内** | 订单管理/订单统计 | 我们所有统计都在报表域且全是阶段 2/3 → **P1 上线时运营看不到任何按站点/设备的经营明细**（只有看板 Top5）| **P1 建议**（哪怕只做站点明细）|
| 16 | OCPI/EMSP 漫游对接 + POS/Kiosk 终端 | 平台对接（独立域，8 项）| 充电桩独有（第三方平台聚合、线下自助终端）。充电宝业态无直接对应 | 不做 |
| 17 | 车辆品牌/车辆管理、RFID 卡号、充电电量 | 会员/设备/基础 | 充电桩独有 | 不做 |

## 二、我们有 · 它没有（差异化）

| # | 我方能力 | 我方状态 | 说明 |
|---|---|:---:|---|
| 1 | **工单闭环**：列表/看板/派单/SLA/巡检 | ◐ | 对方**完全没有工单概念**，运维靠告警通知人工消化。这是我们最硬的差异化——但前提是把 [G6](../../requirements/运营端功能清单.md) 补完（目前只能派单，不能开单/关单）|
| 2 | **复式记账账务分录 + 对账** | ✅(mock) | 对方财务只有"流水 + 提现审核"，无分录、无三方对账。我们更规范 |
| 3 | **场地两层建模 + 进场合同** | ✅ | 场地方→站点→点位→设备 + 合同分成比例。对方只有"站场"单层 + 分成配置，**无场地方主体、无合同实体** |
| 4 | **门店 Onboarding + 门店生命周期** | ✅ | 商户自助进件与阶段管理，对方无 |
| 5 | **代理商体系**：档案/划拨/账号/绩效 | ✅ | 对方有"运营商/分佣商户"但**无设备点位划拨、无代理账号开通** |
| 6 | **按钮级 RBAC + 数据权限 + 操作审计 + 组织架构** | ✅/◐ | 对方权限域只有「用户管理 + 角色管理」两项。我们有 5 档数据范围（ALL/REGION/LOCATION/AGENT/SELF）——但注意 [G7](../../requirements/运营端功能清单.md)：数据权限抽屉目前**保存丢弃** |
| 7 | **营销体系**：券/活动/推送/裂变/广告位/广告活动/投放曝光 | ✅(mock) | 对方该角色菜单下**完全没有营销**（公开资料宣称的月卡/积分商城在此实例不可见）|
| 8 | **用户风控**：信用分/风险标记/黑名单 | ✅ | 对方只有短信拉黑，无用户信用体系 |
| 9 | **押金与欠费管理** | ✅ | 充电宝特有（对方预充值模式不需要押金）|
| 10 | **差异化定价 / 时段价** | ✅(mock) | 对方有收费方案 + 预约调价，但**无按点位/场景取价** |
| 11 | **客服模块**：报障受理 + 客服会话 | ✅(mock) | 对方只有 FAQ 式"问题管理"，无会话记录 |
| 12 | **多国家市场架构 + 消费者分析 + 实时大屏 + 自定义报表** | ✅(mock) | 对方无 |
| 13 | **阿拉伯语 + RTL** | ✅ | 对方菜单是 `name/name_en/name_tw`（简/英/繁）——**无阿语、无 RTL**。MENA 市场我们是碾压的 |
| 14 | **分期交付（phase gating）** | ✅ | 一次开发、按期解锁的产品化能力，对方无此概念 |

## 三、都有但形态不同（设计取舍）

| 维度 | 简电云 | ShareHub（我方） | 评判 |
|---|---|---|---|
| **分成建模** | 站场分成 + 商户分成（挂在站场下，按对象配）| 分润规则（维度 VENUE/AGENT + 模式 渠道分账/平台记账 + 优先级）+ 分润明细 + 结算单 | **我们更抽象可扩展**；对方更直观易上手 |
| **财务组织方式** | **按角色切**：平台/运营商/商户/会员 各一套收支流水，运营商与商户各有提现审核 | **按功能切**：规则/明细/结算/分录/提现/对账/发票 | 各有道理。对方的"按角色切"让**每个角色一眼看清自己的账**，值得在我们结算单里加角色视图 |
| **告警 → 运维** | 告警码字典 → 通知规则 → 告警记录 → 告警通知（配置化，**终点是通知人**）| 监控故障数 → （断裂）→ 工单看板/派单（**终点是工单闭环**）| **两边各缺一半**：把对方的规则引擎接上我们的工单，才是完整链路 |
| **设备台账层级** | 桩 → 枪（两级）+ 编码 + 库存 + 日志 + 配置 + 概览 | 机柜 → 仓位 + 充电宝（两级）+ 指令记录 + 库存调拨 + OTA | 结构对称。对方多「日志/编码」，我们多「远程指令/OTA」|
| **概览** | **分域概览**：站场概览 / 充电桩概览 / 订单概览 三个 | **统一经营看板**（KPI+趋势+告警+待办+榜单）| 我们更聚合；对方各域自带概览，深入某域时更顺手 |
| **会员/用户** | 会员列表 + 会员钱包（+账单）+ 车辆 | 用户列表 + 风控 + 黑名单 + 会员次卡 + 钱包 | 我们更全（多风控）；对方**运营端可直查会员钱包流水**，我们钱包在阶段 3 |
| **支付** | 6 个 PSP 各自配置页，渠道可插拔 | 委托 nearpay 单通道（ADR-005）| 对方为多国部署而生；我们为 MENA 单市场优化。**若将来出非洲/东南亚，需要对方那种渠道抽象** |
| **导航结构** | 13 域 / 25 模块 / 87 项 — 域切得碎（佣金、财务、充值、短信各自成域）| 7 域 / 14 模块 / 73 项 — 收敛进「交易与资金」「用户与服务」| 我们域更少更聚合；对方一级入口多、路径短。**无对错，但对方证明了 13 个一级图标也扛得住** |
| **C 端申诉链路** | 疑问反馈 → 问题详情 → 投诉商家，运营端「投诉订单」承接 | c-app 仅 toast 提示，运营端无投诉列表 | **对方完胜**，端到端闭环，建议照抄 |

## 四、结论：五条可执行的建议

按"对 P1 的影响 × 实现成本"排序：

| 优先级 | 建议 | 理由 |
|:---:|---|---|
| **1** | **补告警规则引擎**（告警码字典 + 通知规则），并**接上工单开单** | 一举解决我们 G6 的上游缺口；对方证明了这套配置化告警是充电运营的标配。做完我们就是"规则引擎 + 工单闭环"双全，而对方只有前半 |
| **2** | **P1 补一个站点/设备经营明细** | 对方把统计放在订单域内（P1 就能用），我们全压在报表域（阶段 2/3）→ P1 上线运营方**看不到按站点的经营数据**，只有看板 Top5。这是交付体验问题不是功能问题 |
| **3** | **补 C 端申诉链路 + 运营端投诉订单** | 对方端到端闭环，我们只有 toast。且这是**商户纠纷取证**的必需品 |
| **4** | **补短信/通知发送记录 + 拉黑** | OTP 短信是真钱，海外更贵；无记录无法追溯失败、无拉黑挡不住薅 |
| **5** | **结算单加"按角色视图"** | 借鉴对方"每个角色一眼看清自己的账"；成本低（现有数据换个筛选维度）|

**不建议跟进**：OCPI/EMSP 漫游、POS/Kiosk 终端、车辆/RFID（充电桩业态专属）；多 PSP 渠道抽象（等真要出第二个市场再说，现在做是过早抽象）。

**需要警惕的自满点**：我们在"它没有"那栏列了 14 项，但其中 **11 项是 mock 前端**、后端未落库。对方的 87 项是**跑在生产的真实系统**。功能矩阵上的领先不等于交付上的领先——参见 [实现状态总表](../../technical/实现状态总表.md)。
