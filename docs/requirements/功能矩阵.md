## 0. 全局定位与关键抽象

系统核心是**两层聚合适配**，这是区别于单一品牌自营系统的关键：

| 抽象层 | 目标 | 供应商/渠道差异被屏蔽的点 |
|--------|------|--------------------------|
| **硬件适配层**（Device Adapter / Driver）| 统一「借出/归还/查询/控制/升级」指令模型，每个硬件供应商实现一个 driver | 通信方式（TCP/MQTT 长连 vs HTTP 回调）、协议编码（二进制/JSON）、SN 规则、指令字、验签 |
| **支付适配层**（PaymentPort）| 统一「下单/预授权/请款/退款/查单」接口，**委托 neargo nearpay 实现**（不自建渠道，集成延后）| 渠道/PSP/合规差异全部收敛在 nearpay 侧 |

上层运营/订单/结算逻辑只依赖抽象接口，新增供应商/渠道 = 新增一个实现 + 配置注册，不改业务代码。

### 端与角色

| 端（Surface） | 使用者 | 形态 |
|--------------|--------|------|
| 运营管理后台（Admin）| 平台运营、财务、管理层 | Web |
| 运维 App（Ops）| 现场运维、地推 BD | 移动端 |
| 商户端（Merchant）| 点位商户 | 小程序 / H5 |
| 代理端（Agent）| 代理商 / 城市合伙人 | Web / 小程序 |
| 用户端（C端）| 终端消费者 | 微信/支付宝小程序、H5、App |
| 接入网关（Gateway）| 硬件设备、供应商平台 | TCP/MQTT/HTTP |
| 开放平台（API）| 第三方、供应商、代理系统 | OpenAPI |

优先级：**P0** = MVP 必备闭环 · **P1** = 规模化运营必备 · **P2** = 增强/差异化

## 15. MVP 建议范围（第一期闭环）

打通「设备可控 → 用户可借还 → 可收费 → 可运维」最小闭环：

- 硬件接入：单/双供应商 driver + 网关（模块 1 的 P0）
- 设备管理：台账、状态、远程弹出、生命周期（模块 2 的 P0）
- 点位：点位/商户/设备关联（模块 3 的 P0）
- 订单：租借全流程 + 计费 + 押金/免押 + 异常（模块 4 的 P0）
- 支付：`PaymentPort` **Stub** 跑通"借出→计费→归还"状态机；真实收费待 nearpay 对接（延后）
- 用户端：扫码借还 + 订单 + 报障（模块 10 的 P0）
- 工单：告警自动开单 + 派单 + 现场处理（模块 8 的 P0）
- 员工权限：组织 + RBAC + 审计（模块 9 的 P0）
- 数据：经营看板（模块 13 的 P0）
- 系统：通知 + 配置 + 调度（模块 14 的 P0）

## 关键决策（已确认 2026-07-11）

| 维度 | 决策 | 架构影响 |
|------|------|---------|
| 业务模式 | **单运营方自营为主**（ADR-011）；多租户为休眠口子 | 运营方体内含**代理商**（ADR-012，数据受限+分润）；租户仅后端 tenant_id 兼容列 |
| 场所本体 | **场地方→站点(网点)→点位→机柜** 层级（ADR/领域模型）| 站点归属代理/场地方/区域，决定分润与数据可见 |
| 广告（未来）| 设备投屏广告（P2）| `ad_` 域预留，广告收入可纳入分润 |
| 硬件接入 | **API 回调 + TCP/MQTT 协议直连，两者都要** | 网关需双栈；driver 插件化为核心设计 |
| 市场/区域 | **MENA 为主（UAE 起步）+ 少量海外微信中国用户**（ADR-009）| AED、ar/en RTL、PDPL/CBUAE 合规，强对齐 neargo |
| 支付 | **直接对接 neargo 支付 API（nearpay），集成延后**（ADR-005）；powerbank 不自建 PSP | 支付适配层外包 neargo；trade 只做 `PaymentPort` 编排 |
| C端载体 | **App 优先 → 小程序次要**（ADR-008，uni-app 一套）| 中东以 App 为主 |
| 分账模式 | **官方分账 + 平台内记账，两者都要** | 分账做成可配置双模式，按租户/场景切换 |
