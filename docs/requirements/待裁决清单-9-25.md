## ① 代理商档案要不要支持「按区域/站点切」

**问题**：`agt_account` / `agt_agent` / `agt_commission` 等 6 张表带 `agent_no`，
但没有 `site_no`/`region_id`。数据范围 handler 是 **fail-closed**（已用两向实验证实：
未注册时 SITE 员工看得到，只登记 AGENT 后**看到 0 行且不报错**）。
所以这 6 张一张都不能登记 —— 登记就等于让按站点收敛的员工在这些页面全瞎。

**我的建议**：只登记 AGENT，**同时禁止给能访问这些页面的角色配 SITE/REGION 范围**，
并为此加一条卡口。理由：代理商档案按站点切本来就没有业务含义。

**选错的后果**：
- 选「登记 AGENT 不加卡口」→ 将来有人配了 SITE 范围，那个人在代理商页面一行都看不到，**不报错**
- 选「补 site_no 列」→ 为了让机制通过而伪造业务语义，下一个人会以为分润规则真有站点维度
- 选「维持不登记」→ 代理端越权风险留着（`dev_alarm` 已经实际泄露过一次：AG002 看到 AG006 的柜机号）

**影响面**：6 张表；台账 `known-unscoped-owned-tables` 当前 **50 张**（其余 44 张是同一个问题的不同维度）
**证据**：`docs/technical/数据范围-51张表为什么注册不了.md`

## ② 权限码 B 类 22 条：补进真源表，角色怎么分

**问题**：后端在用这 22 个码鉴权，真源表里没有。症状是**管理员在角色勾选树上授不出这个能力，而端点按它拒人**。
形状高度一致：**真源表只登记了写的那一半**（如 `user:risk:update` 有、`user:risk:read` 没有，而后端 4 个端点在用）。

**我的建议**：与同资源已有码的角色分配保持一致。
只有三组没有参照，要单独定：`marketing:ad:*`（广告，L3）· `location:site:update` · `system:param:*`。

**选错的后果**：给宽了 = 越权；给窄了 = 功能对那个角色静默失效（端点 403，而按钮渲染着）。

**单独一条**：`workorder:wo:update` 的 2 个端点是**巡检计划**（`/api/ops/inspection-plans`），
而真源表另有 `workorder:inspection:update`。这是**用工单的码管巡检**，
与本轮修掉的「告警借工单只读码」同一个毛病 —— **该换码，不是补登记**。

**影响面**：22 条；台账 `known-perm-ssot-gaps` 当前 40 条里的一半以上
**证据**：`docs/requirements/权限码真源表-57条缺口分类.md` B 类

## ③ 权限码 C3 七条：授权粒度以谁为准

**问题**：真源表把能力拆得比实现细。管理员以为能单独授「只能回滚不能发布」
「只能催缴不能改押金」，**实际做不到** —— 授权粒度是表承诺的，实现给不出来。

| 表里声明 | 实现实际用的 |
|---|---|
| `device:ota:publish` / `:rollback` | `device:ota:manage` |
| `order:arrears:dun` | `order:deposit:update` |
| `order:reservation:cancel` | `order:order:update` |
| `device:command:batch` | `device:command:send` |
| `org:role:assign` | `org:role:update` |
| `device:slot:read` | 仓位无独立端点 |

**我的建议**：以实现为准合并表里的行（拆实现成本高、收益只是更细的授权，而目前没人要求）。
**例外**：`device:ota:publish` / `:rollback` 值得保留拆分 —— 发布和回滚的风险不对称，
「能回滚不能发布」是个真实的值班场景。

**选错的后果**：合并了将来又要拆 → 已授出去的权限要重新分配；
不合并也不拆 → 表继续说谎，下一个人继续被误导（我本轮就被误导过一次）。

**影响面**：7 条

## ④ 权限码 C4 十一条：这些功能到底做不做

**问题**：这些资源 create/read/update 都在，唯独声明的那个动作**没有端点** ——
台账导入/导出、库存盘点、报表导出、活动新建、OpenAPI 配置…

**我的建议**：逐条问「ops-web 上有没有按钮在等它」。
**有按钮就补端点，没按钮就删表里的行。** 删之前必须查这一步 ——
「台账导入/导出」如果已经画在界面上，删码等于承认按钮是假的。

**其中 `report:*:export` 是本轮新显形的**：真源表把「报表 导出」给了 OPS/FIN/BD/VIEW 四个角色，
而 13 个报表端点**全是 read**，一个导出都没有。

**影响面**：11 条

## ⑤ 运营端能不能手动把充电宝置为「报废 / 丢失」

**问题**：后端 `PowerbankStateMachine.eventFor()` 的注释写着「运营端『报废/丢失』等
直接改状态的入口用」；而 ops-web `devices/page.tsx` 写着「借出中 / 丢失 / 买断 / 报废
是业务流转出来的结果，**不给人在表单里直接选**」。**两边注释互相矛盾**，且都言之凿凿。

**我的建议**：以前端为准（不给手动选）。理由：这四个状态都有对应的业务事件
（超时、买断、上报故障），手动改会让资产状态与事件流水对不上。

**选错的后果**：若确认要给运营手动入口，`known-missing-ui-transitions` 里
Powerbank 相关的 14 条要从「B 类正常」转成「C 类债」，需要补迁移表与按钮。

**影响面**：14 条台账条目的定性

## ⑥ `agt_account.is_owner` 存量要不要回填

**问题**：V86 已把默认值从 1 改成 0（此前**运营端建的每个代理账号默认都是属主**，
而属主按 ADR-030 是「全站点全权限、不进授权表」）。但**存量没有回填** ——
测试库里 915 个账号全是 `is_owner=1`。

**我的建议**：**不做全量回填**。把一个真属主误降成普通账号，等于把人锁在自己的生意外面，
而「哪个才是真属主」这张表自己答不出来（全是 1 的时候无从区分）。
建议只在**同一 agent_no 下有多于一个属主**时人工核对：

```sql
SELECT agent_no, COUNT(*) accounts, SUM(is_owner) owners
  FROM agt_account GROUP BY agent_no HAVING SUM(is_owner) > 1;
```

**选错的后果**：盲目回填 → 有人登录后发现自己没权限了，且查不出为什么（属主不进授权表）；
完全不管 → 多账号的主体里每个人都是属主。

**影响面**：生产库的实际账号数（测试库 915 行不代表生产）
**证据**：V86 迁移注释里写了检出 SQL 与一种候选口径（标明勿直接跑）

## 排序建议

| | 事项 | 为什么这个顺序 |
|---|---|---|
| 1 | **⑥ is_owner 存量** | 唯一涉及**已经发生**的越权面，且一条 SQL 就能看清规模 |
| 2 | **② 权限码 B 类** | 影响面最大（22 条），且「授不出去而端点拒人」是每天都在发生的摩擦 |
| 3 | **① 数据范围** | 风险真实（已泄露过一次），但改动大，需要配套卡口 |
| 4 | **④ C4 做不做** | 要先去数按钮，属调研不属决策 |
| 5 | **③ C3 粒度** · **⑤ 充电宝手动改状态** | 纯口径，不卡任何人 |
