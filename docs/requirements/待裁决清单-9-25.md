## ① 代理商档案要不要支持「按区域/站点切」

**问题**：`agt_account` / `agt_agent` / `agt_commission` 等 6 张表带 `agent_no`，
但没有 `site_no`/`region_id`。数据范围 handler 是 **fail-closed**（已用两向实验证实：
未注册时 SITE 员工看得到，只登记 AGENT 后**看到 0 行且不报错**）。
所以这 6 张一张都不能登记 —— 登记就等于让按站点收敛的员工在这些页面全瞎。

**我的建议**：只登记 AGENT，**同时禁止给能访问这些页面的角色配 SITE/REGION 范围**，
并为此加一条卡口。理由：代理商档案按站点切本来就没有业务含义。

**选错的后果**：
- 选「登记 AGENT 不加卡口」→ 将来有人配了 SITE 范围，那个人在代理商页面一行都看不到，**不报错**
- 选「补 site_no 列」→ 为了让机制通过而伪造业务语义，下一个人会以为分润规则真有站点维度
- 选「维持不登记」→ 代理端越权风险留着（`dev_alarm` 已经实际泄露过一次：AG002 看到 AG006 的柜机号）

**影响面**：6 张表；台账 `known-unscoped-owned-tables` 当前 **50 张**（其余 44 张是同一个问题的不同维度）
**证据**：`docs/technical/数据范围-51张表为什么注册不了.md`

## ⑤ 运营端能不能手动把充电宝置为「报废 / 丢失」

**问题**：后端 `PowerbankStateMachine.eventFor()` 的注释写着「运营端『报废/丢失』等
直接改状态的入口用」；而 ops-web `devices/page.tsx` 写着「借出中 / 丢失 / 买断 / 报废
是业务流转出来的结果，**不给人在表单里直接选**」。**两边注释互相矛盾**，且都言之凿凿。

**⚠️ 查完发现两边其实不矛盾，是我先前没看全**：
前端表单给的是「在库 / 在仓 / 故障」三个（都是合法的手工态），
后端 `eventFor` 支持的正是这三者之间的迁移（DEPLOY / REPORT_FAULT / REPAIR）；
而「借出中 / 丢失 / 买断 / 报废」前端不给选、后端也只由事件驱动（RENT / OVERDUE / BUYOUT）。
两处注释各自描述了自己那一半，**没有冲突**。

**我的建议**：这条不用裁决，**台账里 Powerbank 那 14 条维持 B 类（正常）**。
把这个结论写进两边注释，免得下一个人再读出矛盾。

**选错的后果**：若确认要给运营手动入口，`known-missing-ui-transitions` 里
Powerbank 相关的 14 条要从「B 类正常」转成「C 类债」，需要补迁移表与按钮。

**影响面**：14 条台账条目的定性

## ⑥ `agt_account.is_owner` 存量要不要回填

**问题**：V86 已把默认值从 1 改成 0（此前**运营端建的每个代理账号默认都是属主**，
而属主按 ADR-030 是「全站点全权限、不进授权表」）。但**存量没有回填** ——
测试库里 915 个账号全是 `is_owner=1`。

**我的建议**：**不做全量回填**。把一个真属主误降成普通账号，等于把人锁在自己的生意外面，
而「哪个才是真属主」这张表自己答不出来（全是 1 的时候无从区分）。
建议只在**同一 agent_no 下有多于一个属主**时人工核对：

```sql
SELECT agent_no, COUNT(*) accounts, SUM(is_owner) owners
  FROM agt_account GROUP BY agent_no HAVING SUM(is_owner) > 1;
```

**选错的后果**：盲目回填 → 有人登录后发现自己没权限了，且查不出为什么（属主不进授权表）；
完全不管 → 多账号的主体里每个人都是属主。

**⚠️ 规模已实测**：测试库 **1189 个主体，只有 1 个有多属主**（AG001，测试用主体，75 账号 9 属主）。
也就是说「一个主体多个属主」几乎只出现在测试数据里。

**我的建议**：**不回填，只留检出 SQL**。生产上跑一次那条 SQL，
若同样只有个位数，人工核对即可，不值得为它写一条有误降风险的迁移。

**影响面**：生产库跑一次 SQL 即知（测试库 1189 主体 / 1 个命中）
**证据**：V86 迁移注释里写了检出 SQL 与一种候选口径（标明勿直接跑）

## ⑦ 代理账号的「数据范围」要不要做（2026-09-26 补）

**怎么发现的**：表单字段卡口（`check-form-fields`）报「`accountFieldsFor` 发出 `dataScope`，
后端不认」。查下来整块没有实现，而且不是漏了一次查询：

- `agt_account` **有意**没有 `data_scope` 列（实体注释写明），落点本该是 `iam_data_scope`；
- 但 `AGENT_ACCOUNT` **不在 `DataScopeSubject` 词表里**（只有 `ROLE` / `EMPLOYEE`），
  所以那张表里不会有这个主体的行，`DataScopeService.save()` 传它还会抛「非法 subjectType」；
- `AgentAccountServiceImpl.toVO` 里那条 TODO 给的理由（「iam 域 mapper 不在本分片边界内」）
  **不成立** —— `DataScopeService` 就在同一个 module，照它去补 port 会白做。已改正注释。
- 台账里原先那句「也没有单独的范围端点」也不准确：端点有
  （`PUT /api/platform/data-scopes/{subjectType}/{subjectNo}`），前端方法在 `org.ts` 不在 `agent.ts`。

**要定的是一个产品问题**：代理账号能不能看得**比它所属的代理更窄**？
代理会话本来就按 `agentNo` 收口，所以只有「一个代理下面按站点/区域再分人」才需要这一层。

| 选项 | 含义 | 代价 |
|---|---|---|
| A. 不做（建议） | 代理账号一律看本代理全量，撤掉这个字段与列 | 前端已撤表单项、列显示「未设置」；再进一步可把字段整个删掉 |
| B. 做 | `DataScopeSubject` 加 `AGENT_ACCOUNT`，照角色/员工那套独立抽屉（带 `scopeRefs`） | 一条迁移 + 一个抽屉；**注意不能用内联 select**：选「区域」却不给范围值是 fail-closed，那个账号会什么都看不到 |

与 ① 相关但不是同一件事：① 问的是「代理主体类的表能不能按区域/站点切」，
这里问的是「代理**账号**之间要不要再分权」。①=否 时这里仍可为是。

**现状（已落地，不预判裁决）**：运营端撤掉了那个选了不生效的表单项，
列在 `dataScope` 为 null 时显示「未设置」而不是空徽章，mock 也跟真后端一样给 null
—— 此前 mock 编了值，于是「这一格没实现」只有生产才看得见。
