# 核心最小可用清单（MVP）· 按经营链条

> 2026-09-23 · 口径：**能把一单真实的钱和一台真实的设备跑完整**所必需的功能，缺一环业务就停。
> 对齐对象：[运营端功能清单 §三](./运营端功能清单.md)（98 个菜单叶的全量矩阵）与
> [实现状态总表](../technical/实现状态总表.md)。本文只回答两件事：**最小要哪些**、**这些现在到哪一步了**。

---

## 一、主体与术语对齐（先统一叫法，否则清单会打架）

| 本文用词 | 系统里的实体 | 是什么 | 不是什么 |
|---|---|---|---|
| **场地方** | `loc_venue` | 提供场地的商场 / 机场 / 门店，按**进场合同**拿分成 | 不是租户，不登录运营端 |
| **加盟商 / 城市合伙人** | `agt_agent`（代理商） | 运营方**体内**的分润伙伴：出钱买设备、负责一片区域的铺设与运维，按**分润规则**拿分成（ADR-012） | 不是独立租户；「加盟商」「城市合伙人」是同一实体的不同叫法与层级，**不新增主体** |
| **站点** | `loc_site` | 一个物理经营场所（一个商场 = 一个站点），**归属与分成的单元**（ADR-013） | 不是点位 |
| **点位** | `loc_location` | 站点内的具体投放位（「L1 东门」） | 不承载归属，继承站点 |
| **设备** | `dev_cabinet` + `dev_powerbank` | 机柜与充电宝 | — |

**一句话**：场地方出场地、加盟商出钱和人、平台出系统和货，三方按站点分账。

---

## 二、最小闭环的七环

```
① 选址找场地 → ② 签约（场地方合同 / 加盟商协议）→ ③ 建站点与点位
      → ④ 上设备并绑定归属 → ⑤ 用户借还并付款 → ⑥ 出问题能发现能修（告警 + 工单）
      → ⑦ 按约定把钱分给场地方与加盟商（分润 + 结算 + 提现）
```

**判定标准**：某一环缺了，是「业务今天做不了」还是「做起来麻烦」。只有前者进 MVP。

## 四、三条硬阻塞（不解决，业务开不了张）

| # | 阻塞 | 影响范围 | 现状 | 性质 |
|---|---|---|---|---|
| **1** | **设备南向接入网关未建**（`access-gateway`） | 设备不上线、没有心跳、没有真实告警、远程弹出无效、借还指令下不到柜子 | 独立进程未建；驱动 SPI 已分族但无真实实现 | 需要第一家硬件厂商的协议文档与测试机，**有外部依赖** |
| **2** | **支付未接**（nearpay） | 收不到钱：押金、租金、充值全部走不通 | 回调路径已放行，处理器未实现 | 需要 nearpay 商户资料与联调 |
| **3** | **分润明细没有生成链路** | 订单产生了收入，但不会变成任何人的分成；结算单永远是空的 | 只有演示数据在写 `share_record`；订单结算后没有触发分账 | **纯内部开发**，无外部依赖，成本最低 |

另有两条会显著影响体验、但不至于开不了张：
- 站点经纬度为空 → C 端「找附近的柜」不可用（可先用固定站点列表过渡）
- 机柜建档端点缺失 → 只能靠数据库灌设备台账

## 五、与全量清单的对齐

| 分类 | 数量 | 说明 |
|---|:-:|---|
| 全量菜单叶（运营端 15 个一级菜单） | **98** | 实测自 `ops-web/lib/nav.ts`，与功能清单 §三 一致 |
| 新「运营管理」菜单 | 10 | **同一批功能的新入口**，不是新增功能（将来替换旧菜单对应项） |
| **进入 MVP** | **26** | 七环 21 个 + 跨环支撑 5 个 |
| 暂不进 MVP，但**已经做好了** | 约 60 | 页面与后端多数已具备，属于「有了更好」而非「没有就停」 |
| 暂不进 MVP，且**尚未做** | 约 12 | 主要是报表深度分析、OpenAPI / 多市场、营销玩法进阶 |

**明确排除在 MVP 之外的代表项与理由**

| 排除项 | 理由 |
|---|---|
| 门店自助 Onboarding、门店生命周期 | 起步阶段场地少，线下沟通 + 场地方档案够用 |
| 站点坪效、代理绩效、数据报表 6 叶 | 经营分析类；先有数据再谈分析 |
| 库存调拨、固件 OTA、设备编码、设备日志 | 设备规模上来之后才有意义 |
| 差异化定价、活动/时段价、优惠券、裂变、推送 | 增长玩法，MVP 先用一个默认计费方案 |
| 会员次卡、钱包充值、信用免押 | 支付通了之后的第二步 |
| 预约订单、免费订单、押金与欠费 | 边缘单据类型 |
| 对账、发票、账务分录 | 有真实流水后才需要 |
| OpenAPI、多国家市场、税率 | 单市场起步用不到 |

**结论：功能矩阵不是瓶颈，链路是。** 98 个菜单叶里 MVP 只要 26 个，而这 26 个里前端全部完成、后端大部分完成；
真正卡住的是上面三条链路级阻塞——它们都不在「菜单叶」的粒度上，所以看功能清单看不出来。

## 六、建议的落地顺序

| 里程碑 | 目标 | 内容 | 依赖 |
|---|---|---|---|
| **M1 内部可跑通** | 一单从借到分账在内部环境走完 | 修硬阻塞 3（分润生成）+ 补机柜建档端点 + 站点经纬度回填 | 无外部依赖，可立即开工 |
| **M2 能收钱** | 真实用户能付款 | 接 nearpay：收银 + 回调 + 退款 | nearpay 商户资料 |
| **M3 能上设备** | 真机联网、真实告警、远程弹出 | 建 access-gateway + 第一家厂商驱动 | 硬件厂商协议与测试机 |
| **M4 开第一个站点** | 一个真实商场跑起来 | 选址→签约→建站→上设备→跑单→分账 全流程实跑 | M1～M3 |

M1 **不依赖任何外部方**，是现在就能推进的部分；M2、M3 的排期取决于 nearpay 和硬件厂商。
