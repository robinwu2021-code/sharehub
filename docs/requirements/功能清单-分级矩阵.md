## 一、分级定义

### 1.1 四级

| 级 | 名字 | 判定标准（一句话） | 业务里程碑 |
|:-:|---|---|---|
| **L0** | **最小闭环** | **缺了今天业务就做不了**：一单真实的钱、一台真实的设备、一个真实的加盟商跑完整（选址→签约→建站→上设备→借还付款→告警工单→分钱） | 第一个站点开张（MVP M4） |
| **L1** | **首批站点运营** | 开站后**一个月内必然撞上**：用户投诉与欺诈、押金欠费、月底对账、多人协作留痕、App 上架强更 | 3–5 个站点、第一次月结 |
| **L2** | **规模化** | **多站点 / 多加盟商 / 多人**才出现的问题：资产流转、SLA、深度分析、会员钱包、优惠券、账务分录、发票；**第二种设备（按摩椅）试点** | 数十站点、多个加盟商、第二种设备 |
| **L3** | **增长与生态** | 有了规模之后的增长杠杆与外部连接：营销推送/裂变/广告、大屏与自定义分析、多国家市场、OpenAPI、充电桩、小程序 | 多城市 / 第二个国家 |

判定时问一个问题：**这个功能缺了，是「业务今天做不了」、「一个月内会出事」、「规模上来才有意义」，还是「有了才能增长」？** 四个答案对应四级。

### 1.2 与旧口径的映射

| 旧口径 | 定义在 | 与 L 的关系 |
|---|---|---|
| MVP 七环 26 项 | 核心最小可用清单-MVP | **= L0 的骨架**。本文把它展开到菜单叶与 C 端子功能，并补上支撑能力（网关 / 支付 / 认证 / 通知） |
| 阶段 1 / 2 / 3（= T1–T3 / T4–T6 / T7–T9） | PRD-分期路线图 · 运营端功能清单 | 阶段 1 ≈ L0 + L1；阶段 2 ≈ L2；阶段 3 ≈ L3。**阶段 1 内部分不出「开不了张」与「有了更好」**，这正是本文加 L1 的原因 |
| 建设 P0 / P1 / P2 | 运营端功能清单 · 功能矩阵 | 技术侧先后，与交付无关；**不再使用**，由 L 与实现状态总表共同替代 |

## 二、角色与主体（矩阵的列）

### 2.1 角色

以 [功能权限清单](./功能权限清单.md) 的 7 个系统角色为准，不新造岗位名；每个角色一句职责，数据范围按 v4/06 规划值。

| 代号 | 角色 | 一句话职责 | 数据范围（规划） | Realm |
|---|---|---|---|---|
| **ADM** | 管理员 / 负责人 | 建账号、配角色、定规则、看全局；资金类终审 | ALL | STAFF |
| **OPS** | 运营 / 现场运维 | 设备上线与维护、告警处置、工单执行、站点点位日常 | REGION（按区域） | STAFF |
| **CS** | 客服 | 用户报障与投诉受理、退款申请、风控拉黑、订单干预 | ALL | STAFF |
| **FIN** | 财务 | 计费方案、分润规则、结算与提现审核、对账、发票 | ALL | STAFF |
| **BD** | 拓展 / 招商 | 找场地、谈合同、建站点、招加盟商、划拨资产 | REGION | STAFF |
| **VIEW** | 只读 | 管理层看板与报表，不做任何写操作 | ALL | STAFF |
| **AGT** | 加盟商 / 代理商 | 看自己的设备、订单、收益、结算；申请提现；报修 | **强制 = 自己的 `agent_no`**（不可放宽） | AGENT |
| **C** | 消费者 | 找柜、借还、付款、报障 —— **没有角色，只有属主** | SELF | CONSUMER |

不在矩阵里的主体：**场地方**（`loc_venue`）今天没有账号体系，门店端形态未定（L3 候选，见 §八）。

> **没有「租户」这个概念**（[ADR-026](../technical/ADR/ADR-026-取消租户概念-唯一运营方.md)，2026-09-23 用户定：
> 「本平台只支持唯一的运营方，简化逻辑，没有租户概念」）。原 `PLATFORM_ADMIN` 角色与 `tenant:*` 权限码族**已取消**，
> 上表 7 个角色即全部。加盟商按[加盟商的逻辑](../technical/ADR/ADR-012-代理商模型.md)走 —— 用平台品牌、C 端无感知、
> 参与统一分润，隔离靠**数据范围 `AGENT`** 而非行级租户。

### 2.2 记法

角色列写作 `BD R · OPS U · VIEW V`：**R** = 主责（日常操作或审批的责任人）· **U** = 使用（可写但非主责）· **V** = 只读。
ADM 默认对所有运营端功能 R，不逐行重复。AGT 只在它能看到的行出现，且数据永远只是自己的。C 端行的角色就是 C。

**现状**列写作 `前/后/线`：前端页面 · 后端接口与落库 · 线上（powerbank.ichain.top）能否用；✅ 通 · 🟡 部分（mock / 内存 / 只读 / stub）· ⬜ 未建 · — 不适用。
运营端 98 叶前端**全部 ✅**（2026-07-29 收口），下文只在后端与线上有差异时标注。

### 9.2 结论一：21 项零缺失，但甲方清单自身有重复

**覆盖率 20/21 完全覆盖 + 1 项有真缺口**：18 项 ✅、3 项 ◐。
其中 #7 #8 是「形态不同」（报表类后置，见 9.3），**#3 商户管理是真缺口**（加盟商支付进件未建，见 9.4）。

甲方 21 项里有 **3 组实际重复**，去重后约 **18 个独立能力**：

| 重复组 | 我方落点 | 说明 |
|---|---|---|
| #13 充電站點廣告（設備屏） / #15 平台廣告管理 | 同一组三叶（广告位/广告活动/投放曝光） | 「设备屏」是广告位的一种载体，不是独立系统 |

**处理建议**：不按甲方的 21 项重排菜单。我方 98 叶的粒度更适合做菜单，21 项适合做**交付验收的checklist**。

### 9.3 结论二：两项「我方延后」要向甲方解释

只有 #7 財務數據 与 #8 基礎運營報表 是我方比甲方晚，两项都属于**报表/分析类**，延后的理由是同一条：

> **先有数据，再谈分析。** 支付未接通、分润明细刚打通、真实订单量为零的情况下，
> 财务报表与账务分录只能展示空表；等真实流水跑一段时间再做，口径才立得住。

缓解措施已在矩阵里：**经营看板（L0）**承载了甲方「基础运营报表」的日常诉求
（今日 GMV / 订单数 / 活跃设备 / 在线率 + 趋势 + 实时告警 + 待办 + 排名榜单），
**对账提到 L1**（第一次月结就要用）。所以甲方在第一期真正拿得到的经营数字并不缺。

反过来，我方主动提前的有 **6 项**（#4 #9 #10 #11 #12 #16），其中 #16 平台运营 Dashboard
从甲方 P3 提到 L0、#11 客服工单系统从 P2 提到 L0，都是「不提前就没法开门营业」。

### 9.4 结论三：#3「商戶管理」是真缺口 —— 加盟商支付进件未建

**甲方 2026-09-23 澄清：商户 = 加盟商，用途是「进件、收款」。** 这句话把本项从术语问题变成了能力问题。
「进件」在支付行业指把商户资质报给支付机构、开通它自己的收款（子商户）账户 —— 不是普通建档。

> 📌 **同日追加澄清**（[ADR-026](../technical/ADR/ADR-026-取消租户概念-唯一运营方.md)）：
> 「本平台只支持唯一的运营方，简化逻辑，**没有租户概念**」+「加盟商**用平台品牌，用户无感知**」。
> 这两条把下面的判断收窄了一大截，见 9.4.3。

#### 我方现状：建档与「平台代收再结算」齐备，「自己收款」缺位

| 加盟商要做的事 | 我方落点 | 状态 |
|---|---|:--:|
| 建档（主体/联系人/辖域/默认分润比例） | 代理商管理 › 代理商档案（L0） | ✅ |
| 开登录账号、看自己的数据 | 代理账号管理（L0）+ 代理门户 7 叶（全 L0） | ✅ |
| 约定分多少 | 分润配置 · 分润规则（L0） | ✅ |
| **平台代收 → 结算 → 打款给它** | 分润明细 · 结算单 · 提现审核 · 银行管理（全 L0） | ✅ |
| **报资质给支付机构、开它自己的收款账户** | **无** | ⬜ |
| **收款时钱直接进它的账户** | `share_rule.mode` 有 `CHANNEL_SPLIT` 档位，但无执行链路 | ⬜ |

实测：`agt_agent.settle_account` 是一个 `VARCHAR(128)` 自由文本（注释「结算账户(nearpay 收款方)」），
**不是**结构化的「子商户号 + 进件状态 + 生效时间」；没有资质材料上传、没有提交/审核/驳回状态机、
没有子商户号回写，运营端代理商管理 6 叶里也没有「进件」入口。

#### 这与 ADR-004 的既有决策直接相关

[ADR-004 分账双模式](../technical/ADR/ADR-004-分账双模式.md) 已经定义了两条路，缺的正是第一条：

| 模式 | 含义 | 需要进件？ | 我方现状 |
|---|---|:--:|---|
| `CHANNEL_SPLIT` 渠道分账 | PSP 支付时直接分账到分成方账户 | **需要** | ⬜ 仅有枚举值 |
| `LEDGER` 平台记账（默认，**ADR-004 写明「MENA 首期主用」**） | 平台统一收款 → 复式记账 → 结算单 → 提现打款 | 不需要 | ✅ 全链路 L0 |

ADR-004 当时还**否决过「仅官方分账」**，理由是「分成方必须有特约资质，覆盖不了长尾商户」。
甲方现在要求「进件、收款」，等于要求把 `CHANNEL_SPLIT` 从备选变成主路径 —— 这是对 ADR-004 的修订，不是补一个页面。

#### 要补的东西（若确认走 CHANNEL_SPLIT）

| 编号 | 能力 | 要点 | 建议级 |
|---|---|---|:--:|
| OPS-AGT-07 | **加盟商进件** | 资质材料上传（执照/身份证/银行账户证明）→ 提交 PSP → 进件状态机（待提交/审核中/已通过/已驳回+原因/已停用）→ **子商户号回写**；材料是敏感信息，入 `sharehub_pii`（PDPL） | 见下 |
| OPS-AGT-08 | 进件状态跟踪 | 列表 + 驳回重提；与代理商档案同页签 | 同上 |
| S-PAY-05 | 渠道分账执行 | 支付时按 `share_rule.mode=CHANNEL_SPLIT` 调 PSP split settlement，回执入账务；失败降级 `LEDGER` | 同上 |
| — | 代理门户「我的进件」 | 加盟商自助传材料、看进度 | 同上 |

**定级取决于一个问题**（见 §八 #9）：首批加盟商用哪条路拿钱？

- **走 LEDGER（ADR-004 原计划）** → 现有 L0 链路已完整，进件是 **L1**：第一批加盟商可以先由平台代收再结算。
- **走 CHANNEL_SPLIT（甲方字面要求）** → 进件是 **L0 阻塞项**：不进件就开不了第一个加盟商，
  且强依赖「PSP 支持 split settlement」这个外部条件（ADR-004 当时写的是「**若** nearpay/PSP 支持」，至今未验证）。

#### 9.4.3 「用平台品牌，用户无感知」基本排除了渠道分账

2026-09-23 的两条澄清让这件事几乎定了：

1. **品牌口径与加盟商自己收款直接冲突。** 走 `CHANNEL_SPLIT` 时，消费者刷卡后
   账单上出现的是**加盟商的商户名**（merchant descriptor）—— 用户立刻就知道这台机器归谁，
   与「用平台品牌、用户无感知」矛盾。这一条是硬的，不是排期问题。
2. **统一分润要求资金先归集再分配**，这正是 `LEDGER` 的形状；
   [ADR-004](../technical/ADR/ADR-004-分账双模式.md) 本就写明它是「通用兜底，MENA 首期主用」，
   并否决过「仅官方分账」（长尾商户没有特约资质）。
3. **没有租户概念**（ADR-026）意味着加盟商不是独立核算主体，更没有独立开户的必要。

**因此「进件」在本项目里应理解为「加盟商入驻平台的资质审核」**（平台侧的建档与审核流程），
**而不是支付进件**（向 PSP 报件开子商户号）。前者是运营流程，几天的事；后者要改 ADR-004 的主路径。

#### 9.4.4 按这个理解，要补的只剩一项

| 编号 | 能力 | 要点 | 级 |
|---|---|---|:--:|
| OPS-AGT-07 | **加盟商入驻审核** | 资质材料上传（执照/身份证/银行账户证明）→ 平台审核 → 通过即建档并开账号；状态机 待提交/审核中/已通过/已驳回+原因；材料入 `sharehub_pii`（PDPL） | **L1** |
| OPS-AGT-09 🆕 | **商家自助注册** | 免鉴权入口 `POST /api/agent/apply` + 手机号 OTP；与代建**同落 `agt_apply`、同状态机、同必填校验**；驳回可回填重提 | **L1** |
| OPS-AGT-10 🆕 | **入驻待办队列** | 运营端队列 + 历史检索（状态/关键词/时间区间）+ 受理/审核/驳回原因 + 审核留痕 | **L1** |

「收款」侧**已经齐了**：分润规则 → 分润明细 → 结算单 → 提现审核 → 银行字典，**全部 L0 且已实现**，
加盟商在门户里看得到自己的收益与结算，也能发起提现（AGT-06）。

原先列的另外三项（进件状态跟踪、渠道分账执行 `S-PAY-05`、门户「我的进件」）**按 LEDGER 路径不需要**；
若将来真要做渠道分账，它们随 ADR-004 的修订一起回来。

**定级 L1 而非 L0 的理由**：首批加盟商可以线下签约、后台代建档（代理商档案是 L0 且已实现），
自助进件是「人多了之后省事」，不是「没有就开不了张」。

#### 9.4.5 入驻入口：两条都要，条件相同（2026-09-23 用户定）

> 原话：「**商家可以注册，运营商也可以代建，条件相同，商家注册，也需要运营商审核通过。**」

这条把 OPS-AGT-07 从「后台建档」扩成**一条链两个写入点**，三处必须同：
**同一张申请单 `agt_apply` · 同一个状态机 · 同一套必填校验**（必填由 `operator_type` 决定，**不由入口决定**）。
差别只有 `source` 与 `submitted_by` 两个字段。详见 [ADR-030 §三](../technical/ADR/ADR-030-账号与主体-一个账号可属多个运营主体.md)。

**代建不是跳过审核**，是同一人立即完成审核——状态机照走、`reviewed_by` 照写。
录入码 `agent:apply:create` 与放行码 `agent:apply:approve` 分开，否则四眼原则以后没有落脚点。

**连带的一条硬约束**（照抄 ai-shop 的教训）：**审核通过 ≠ 能拿钱。**
`agt_agent.status=ENABLED` 只说明能经营；能不能提现要看 `stl_payout_account` 是否完整。
ai-shop 因为没分开，出现过「商家能卖、订单在来、结算单在生成，而收款号解析不到，账单留空钱欠着，
商家一路上没收到任何提示」——他们的结论是结算侧的兜底「保证了不出错，没保证有人知道」。
**我方今天同样是断的**（[ADR-029 §5.2](../technical/ADR/ADR-029-运营主体抽象.md)），代理门户必须显式提示「你还不能收款」。

### 9.5 结论四：我方有而甲方清单未列的（验收时要主动说明）

甲方 21 项没提、但运营离不开的，我方共 **约 40 叶**，主要是：

| 我方模块 | 叶数 | 为什么甲方没列 |
|---|:-:|---|
| **告警管理**（告警记录/通知/代码字典/通知规则） | 4（全 L0） | 甲方把它算进「硬件/IoT 系统 › 故障与告警」，但那是设备侧；运营侧的告警处置与转工单是另一回事 |
| **代理商管理 + 代理门户** | 6 + 7（12 个 L0） | 甲方 21 项完全没有代理/加盟商，但这是本项目的核心商业模式（ADR-012） |
| **员工与权限** | 5（2 个 L0） | 多人协作与资金操作的前提，甲方视为隐含能力 |
| **系统设置** | 16（8 个 L0） | 供应商接入/支付渠道/通知模板/字典/银行/问题类型等基础设施 |

这四块**不是超交付，是缺了就跑不起来**：没有告警就发现不了故障，没有员工权限就只能共用一个账号，
没有银行字典就选不了提现收款方。验收时建议主动列出，避免被当成「计划外工作」。
