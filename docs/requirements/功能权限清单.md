# 功能权限清单（RBAC SSOT）

> 状态：草稿（待确认）· 创建 2026-07-11
> 定位（[ADR-026](../technical/ADR/ADR-026-取消租户概念-唯一运营方.md)）：**唯一运营方，产品里没有租户概念**；本清单即全部内部角色（7 个）。
> 用途：前端按钮级鉴权 + 后端 `@PreAuthorize` 的**唯一权限码来源**。对齐 [功能清单-单运营方运营系统](./功能清单-单运营方运营系统.md)。

---

## 一、权限码规范
`<模块>:<资源>:<动作>`，小写点分。
- **通用动作**：`read` 查 · `create` 增 · `update` 改 · `delete` 删 · `export` 导出 · `import` 导入。
- **专用动作**：如 `command`(下发指令) · `dispatch`(派单) · `intervene`(干预) · `refund`(退款) · `audit`(审核) · `config`(配置) · `assign`(分配) 等，见各域。
- 通配：`<模块>:*` = 该模块全部；`*` = 超管全部。
- **没有 `delete` 动作**（2026-09-25 清理）。本仓库全站零 DELETE，软删语义一律用
  `archive` / `unarchive`，或各自的业务下线动作（合同 `terminate`、员工离职置
  `status=LEFT`、分润规则置状态）。实测 444 个端点里**零个**用 `:delete` 码鉴权。
  此前表里留着 10 条 `:delete`，它们不是「漏加闸」，是**能力已取消而表没删** ——
  而一份说着不存在能力的真源表，会让人以为那个能力只是还没做。

## 二、角色集（单运营方内部）
| 角色码 | 名称 | 职责范围 | 数据权限 |
|--------|------|---------|---------|
| `ADMIN` | 运营管理员 | 全部（`*`）| 全域 |
| `OPS` | 运维 | 设备 / 工单 / 库存 / OTA | 按**区域/点位**限定 |
| `CS` | 客服 | 订单干预 / 退款申请 / 用户风控 / 报障受理 | 全域只读 + 客服动作 |
| `FINANCE` | 财务 | 财务 / 分润 / 结算 / 提现 / 对账 / 发票 | 全域财务 |
| `BD` | 拓展 | 点位 / 场地方 / 合同 / CRM | 按**区域**限定 |
| `AGENT` | 代理商（代理端）| 自己设备/订单/收益 只读 + 提现申请 + 报修 | **限定自己 `agent_no`** |
| `VIEWER` | 只读分析 | 看板 / 列表 / 报表 只读 | 全域只读 |
| `WAREHOUSE` | 仓管（2026-10-29 新增，V186）| 到货质检 / 发货出库 / 盘点录入 / 期初导入 | 按**区域**限定 |

> `AGENT` 是运营方体内的受限外部伙伴（[ADR-012](../technical/ADR/ADR-012-代理商模型.md)），**数据范围强制 = 自己 `agent_no`**，只见/操作自己归属的设备/点位/订单/收益。下表凡代理有的权限均隐含此数据范围。

> **两类权限**：**功能权限**（本清单，能否执行某操作）+ **数据权限**（能看/操作哪些区域/点位的数据）。数据权限维度：`ALL` / `REGION` / `LOCATION` / `SELF`（自己经手）。OPS/BD 默认按区域或点位收敛（见各角色）。
> 下表 ✓=有该权限。`ADMIN` 拥有全部，表中省略其列（默认 ✓）。

> **收款账户（`finance:payout_account:*`）为 2026-09-23（B3）新增。** 在此之前这条链是断的：
> `loc_venue` 没有账户列、`agt_agent.settle_account` 全仓无代码读、提现单上只有收款**银行**没有账号 ——
> **提现审核页能点通过，审批完不知道往哪打钱**。
>
> **`:pay` 与 `:audit` 分开发码**（2026-09-23）：审批是「同意把钱打出去」，
> 打款回执是「钱确实出去了」—— 中间隔着一次真实资金动作，可能失败、可能延迟几天。
> 合成一个码，机构要做双人复核时就没有地方落。FINANCE 当前持 `finance:*` 通配、
> 两码都有，**但码分开了，将来收紧只是改角色配置；码没分开，收紧就得改代码**。
>
> ⚠️ **发码之后必须确认数据范围跟上了**（2026-09-24 实测教训）：给 AGENT 发
> `finance:payout_account:read` 时只想着「他要看自己的账户」，而 `stl_payout_account`
> 当时**没有数据范围锚点** —— 结果一个名下零条记录的新代理能读到全平台 150 行
> 户名与银行账号掩码。同期 `share_record` 泄露 108 行。V58 补锚点后堵住。
> **「给谁什么码」和「这个码能看到哪些行」是两个独立决策，清单只管前者。**
>
> 代理端也持 `:read`（代理门户要显示「你还不能收款」），但**不给 `:update`**：
> 账户一改，钱就换个地方进 —— 这个动作要留在运营侧，且与提现审核（`finance:withdrawal:audit`）
> 分开发码，免得「能审批」顺带变成「能改收款账号」。

> **`finance:invoice:void` 为 2026-07-30（S2）新增。** 原先只有 `:issue` 一个写权限码，作废被顺带覆盖。
> 作废比开具更危险——已开具的票一旦作废，账面凭空少一张票且不可撤销，而开具只是把草稿定型。
> 两者拆开后：`:issue` 给到能登记与开票的财务经办；`:void` 只给财务（FIN），不随开票权外扩。
> 运营端实现：开具/作废均为动作端点（`POST /api/trade/invoices/{no}/issue|void`），作废必填原因并留痕。

> **三个告警码为 2026-09-25 新增。** 此前**整个告警域挂在 `workorder:wo:read` 上** ——
> 三个菜单叶如此，**受理这个写动作也如此**。而 `workorder:wo:read` 的持有者含 `VIEWER`，
> 于是**只读角色能受理告警**。一个写动作挂在只读码上，代价就是这个。
>
> - **受理与关闭分成两个码**：受理是「我看到了、在处理」，关闭是「这事结了」——
>   关闭会把告警从「未处理」里抹掉，直接影响运营看的那个数。
>   合成一个码等于谁能受理谁就能抹数。
> - **CS 给受理不给关闭**：保持现状（CS 今天就能受理），且「用户报障 → 客服看告警」是真实路径；
>   但设备侧的「这事结了」该由运维判定。
> - **VIEWER 不给**：它现在就看不到告警（实现里 VIEWER 并不持有 `workorder:wo:read`），
>   本次只是把借用改成自有码，**不顺手扩大任何人的可见面**。
>
> ⚠️ **一处更正**：提案里写过「只读角色 VIEWER 现在能受理告警」，**那句不成立**。
> 依据是本表 §6「工单 查/看板」那一行给了 VIEW ✓，而 `RolePerms` 与
> `ops-web/lib/permissions.ts` 的 VIEWER 都**没有** `workorder:wo:read` ——
> 真源表与实现在这一格上本来就不一致（属 `known-perm-ssot-gaps` 的范围，不在本次处理）。
> 成立的部分是：**受理这个写动作确实挂在一个只读码上**，而 OPS / CS 持有它。
>
> 关闭必须带原因（已解决 / 误报 / 自愈 + 备注），与「验收关单必须给结论」同一口径。
> 实际理由：**「误报率」这个数只有在关闭时记了原因才算得出来**，否则告警质量永远无从评估。

> 工单状态机（前后端同一份）：`CREATED --dispatch--> DISPATCHED --accept--> PROCESSING --complete--> DONE --close--> CLOSED`；
> `DISPATCHED/PROCESSING --reject--> CREATED`（退回重派）；`PROCESSING --process--> PROCESSING`（提交处理进展，只留痕）。
> 非法迁移必须由服务端拒绝，前端按钮禁用只是体验层。
> 命名对齐记录（2026-07-29）：原 `workorder:wo:process` / `:audit` / `workorder:config` 从未被任何实现引用，
> 现统一为 `:handle` / `:close` 与三个具体配置码，与 ops-web `lib/permissions.ts` 一致。

### 16.1 在 OpsKit 里生效的是什么（2026-09-28，与 OpsKit 会话约定）

上表的 `flow:*` 管的是**运营台界面**（菜单、按钮、页面守卫）。真正放行 / 拒绝的是 OpsKit，它不认 `flow:*`，认两样：

- **产品权限**：由**角色**带来。OpsKit 里建与 ShareHub 同名的角色，按下表配产品权限；ShareHub 内省应答的 `roles[]` 即生效（OpsKit 引导配置，改了不用发版）。
- **范围**：内省应答的 `scopes[]`（数据范围 → `维度小写:编号`，全量范围发 `"*"`）。`*` 只放开范围这一个条件，能否看全部由产品权限决定。

宿主权限码（`perms[]`，如 `location:contract:audit`）在 OpsKit 里**只作任务候选条件**（审批步骤「按权限码」），不会变成产品权限。

| ShareHub 角色 | OpsKit 产品权限 | 依据（上表） |
|---|---|---|
| `ADMIN` | 全部：approval:submit · approval:decide · approval:view:all · ticket:create · ticket:view:all · ticket:work · ticket:assign · ticket:escalate · ticket:merge · ticket:comment:internal · process:manage · ticket-type:manage · sla:manage · report:view · directory:manage | 表中省略列 = ✓ |
| `OPS` | approval:submit · approval:decide · approval:view:all · ticket:create · ticket:view:scoped · ticket:work · ticket:assign · ticket:escalate · ticket:merge · ticket:comment:internal · sla:manage | 审批查 / 决定 · 工单查 / 办理 / 派单 · 运营配置 |
| `CS` | approval:submit · approval:decide · approval:view:all · ticket:create · ticket:view:scoped · ticket:work · ticket:comment:internal | 审批查 / 决定 · 工单查 / 办理（客服报障 = 手工建单的主要来源） |
| `FINANCE` | approval:submit · approval:decide · approval:view:all | 审批查 / 决定 |
| `BD` | approval:submit · approval:view:all | 审批查（自己提交的单另按「提交人始终可见」） |
| `VIEWER` | approval:view:all · ticket:view:scoped | 审批查 · 工单查 |
| `AGENT` | ticket:view:scoped · ticket:work | 工单查 / 办理；范围 = `agent:{代理号}`，只看自己片区 |

- 「审批查」一律给 approval:view:all（OpsKit 产品权限，不是本表的码；不加反引号，免得被当成声明）：审批列表是「全部审批单、按数据范围过滤」，可见范围由 `scopes` 收窄；不给它就只能看到自己参与的单。
- 发起审批（approval:submit，2026-09-28）给全体员工角色、不给 VIEWER / AGENT：运营台「发起审批」只能发起**审批模板**，按模板的发起表单填写；由宿主业务送审（如提现）走应用凭证，不需要这个权限。界面入口用 `flow:approval:submit`（2026-09-28 已在上表补，授予同上五个角色）。
- 工单一律按范围看（ticket:view:scoped），只有 `ADMIN` 是 `view:all`：全量范围的员工 `scopes=["*"]`，效果等同全部。
- 审核队列（`flow:queue:claim`）不对应产品权限：能不能领取看是否为队列组成员（OpsKit 目录），目录同步随 M5。
> - BD 给审批「查」不给「决定」：BD 是合同的提交方，看进度是刚需；决定权在运营 / 财务。
> - **AGENT 持码但暂无入口**（2026-09-28）：代理只看得到门户 section（`portalFor`），通用菜单一律不出。
>   入口等 OpsKit 范围标签（21/07 P2，「代理只看自己标签内的工单」）上线后再挂进代理门户 ——
>   在那之前挂上，演示出来的是「代理看得到所有人的工单」，比没有入口更糟。

3. 远程指令是否细分到每种（弹出/锁/重启单独授权）还是合并 `command:send`（本文合并，弹出对 CS 单放）。
4. 退款是否需二级审批（大额财务复核）。

### 库存统一审批补充（2026-10-30）

`device:inventory:audit`为统一审批模块的库存审核候选权限，V220登记。流程`inventory_count_audit`通过该权限选择审核人，并禁止申请人自审；宿主回写再核对提交人与审批号。默认仓管仍仅有盘点录入权，不新增审核或通用流程决定权；OPS已有库存通配及流程审核权限、ADMIN已有全权限。库存页面不提供直接批准／驳回；旧端点明确拒绝，过账仅可恢复已获统一审批结论的执行。
