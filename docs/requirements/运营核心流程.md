## 零、一句话

**场地方出位置，代理商出钱和人，平台出系统和货；合同定分成，站点是单元，设备是产能，
监控发现问题，工单解决问题，订单产生收入，分润把钱分回去。**

这门生意的利润不在「铺了多少台」，而在「**铺下去的每一台是不是一直可借、可还、在赚钱**」。
所以运营流程的重心是后半段 —— 布放之后的监控、调度、维修与汰换，而不是前半段的拓场。

## 一、角色与职责

| 角色 | 是谁 | 在流程里做什么 | 登录哪 |
|---|---|---|---|
| **平台运营** | 运营商员工（运营/财务/客服/仓管） | 定规则、审合同、审代理、管仓库、盯指标、处理升级工单、结算 | 运营端 |
| **BD** | 平台员工或代理商（`DEVELOP` 责任） | 找场地、谈判、推动签约 | 运营端 / 代理门户 |
| **代理商 / 城市合伙人** | 体内分润伙伴 | 出资买设备、包一片区域的铺设与运维，拿分润 | 代理门户 |
| **运维人员** | 平台运维或代理商的人 | 装机、补宝调宝、巡检、接工单修设备、撤机 | 运维端（H5/小程序） |
| **场地方** | 商场/酒店/餐饮/机场等 | 提供位置和电源，按合同拿分成；**不登录运营端** | 对账单（线下/门户，待定） |
| **用户** | C 端消费者 | 借、还、付款、报障 | C 端 |

> **行业经验**：直营城市和代理城市的流程应该是**同一套**，只是执行人不同。
> 为代理单独做一套流程，是后期数据口径打架的主要来源 —— 本系统用「数据范围 = 代理商」收敛可见性，而不是分叉流程。

## 二、全景：一个站点的一生

```
  ┌────────── 前期（拓） ──────────┐ ┌──── 中期（建） ────┐ ┌──────────── 长期（营） ────────────┐ ┌─ 末期（退）─┐
  P1 场地拓展 ─▶ P2 合同签约 ─▶ P3 建站点/点位 ─▶ P4 设备布放上线 ─▶ P6 日常运营 ◀─▶ P7 监控·告警·工单 ─▶ P9 撤场回收
     商机              审批/生效        勘测/建档          入库→调拨→安装       借还·调度·定价       发现→派单→修复→验收        设备回收
                        │                                   │                   │                                         站点关闭
                        │                    P5 代理商入驻与划拨（贯穿：谁出资、谁运维、谁拿钱）                          合同终止
                        └──────────────────────────── P8 结算分润（合同定比例，订单产生金额） ─────────────────────────────┘
```

**三条贯穿全程的主线**，任何一个流程都要回答它对这三条的影响：

| 主线 | 问题 | 载体 |
|---|---|---|
| **归属线** | 这个站点/设备归谁运维、收益分给谁 | 合同（场地方）· 划拨与责任（代理商） |
| **资产线** | 每一台柜、每一颗宝现在在哪、什么状态 | 设备台账 + 状态机 |
| **收入线** | 这个站点赚不赚钱、该不该留 | 订单 → 分润 → 站点效益 |

## 三、逐流程

每个流程按「**触发 → 步骤 → 产物 → 关键规则 → 异常**」写。
「关键规则」里标 🔒 的是**必须由系统强制**的（不能只靠人自觉）。

### P1 场地拓展（BD）

**触发**：城市开拓计划、代理商自拓、场地方主动来询、老站点周边加密。

```
线索 NEW ─▶ 已联系 CONTACTED ─▶ 洽谈中 NEGOTIATING ─▶ 已签约 SIGNED
   │              │                      │
   └──────────────┴──────────────────────┴──▶ 流失 LOST（必填原因，可重新激活）
```

| 步骤 | 做什么 | 行业要点 |
|---|---|---|
| 1. 录入线索 | 场地名、地址、类型、联系人、来源、负责 BD | **查重**：同一地址/同一场地方 90 天内只能一个 BD 跟进，否则撞单抢单 |
| 2. 选址评估 | 人流、停留时长、场景、竞品在不在、电源和网络条件、可摆放位置 | 停留时长比人流重要：**餐饮/KTV/酒吧/医院 > 商场通道 > 交通枢纽** |
| 3. 拜访跟进 | 每次记录跟进（时间/方式/结论/下一步） | 超 N 天无跟进自动提醒，超 M 天自动回收线索池 |
| 4. 商务谈判 | 分成模式、比例、进场费、期限、排他 | 谈判结果直接成为合同草稿，**不要再录一遍** |
| 5. 转化 | 签约 → 生成/关联场地方档案 → 进入 P2 | 🔒 签约后 BD 归因（`DEVELOP` 责任）写进站点，拓展佣金依此计算 |

**产物**：场地方档案（`loc_venue`）+ 合同草稿 + BD 归因。

**异常**：竞品排他（场地已签竞品独家）→ 记录到期时间、设提醒，到期前 60 天重新激活。

### P2 合同签约（进场合同）

合同是**场地方分成的唯一依据**，也是站点能否营业的前提。

```
草稿 DRAFT ─提交─▶ 待审批 PENDING ─通过─▶ 待生效 SIGNED ─到生效日─▶ 生效中 ACTIVE ─到期─▶ 已到期 EXPIRED
                      │驳回                                          │         │续签
                      ▼                                              │         └──▶ 新合同（旧合同到期当天无缝衔接）
                    草稿                                             └─提前终止─▶ 已终止 TERMINATED（必填原因）
```

| 要素 | 行业常见取值 | 说明 |
|---|---|---|
| 分成模式 | ① 纯分成（10%–40% 流水）② 固定进场费 ③ **保底 + 分成**（取高者）④ 免费入驻 | 高端场地多为③；②的风险全在运营方 |
| 分成基数 | 实收流水（扣退款）/ 应收流水 | 🔒 必须写清，否则对账必吵 |
| 结算周期 | 月结为主，T+N 日出对账单 | 场地方最在意「对账单能不能看懂」 |
| 期限 | 1–3 年，自动续约条款 | 到期前提醒：**60 / 30 / 7 天** |
| 排他 | 场内是否允许竞品 | 影响站点估值 |
| 设备数量与位置 | 几台柜、摆哪里 | 成为 P3 点位清单的依据 |
| 押金/进场费 | 金额、退还条件 | 撤场时要结清 |

**关键规则**

- 🔒 **无生效合同的站点不能上线营业**（P4 的上线校验要查）。行业里「先装机后补合同」是纠纷与白干的最大来源。
- 🔒 一个站点同一时刻**只有一份**生效合同；续签是新合同，不是改旧合同（旧合同上的历史分成比例要能追溯）。
- 🔒 合同改分成比例 = 新版本/补充协议，**只影响生效日之后的订单**（订单落快照）。
- 合同生效 → 若有牵线人（`REFER`），发一次性介绍费（ADR-027）。
- 合同到期未续 → 进入 P9 撤场评估，而不是让站点「无合同照常营业」。

### P3 站点与点位建立

**站点** = 一个场地 = 一份合同的标的 = 归属与分成的单元；**点位** = 场地内的具体摆放位置。

```
站点状态（唯一一套，2026-09-25 定：与「门店生命周期」合并，方案见 §十.2）：
筹备 PREPARING ─首台设备上线─▶ 营业 ACTIVE ⇄ 暂停 PAUSED ─撤场审批通过─▶ 撤场中 WITHDRAWING ─回收完成─▶ 关闭 CLOSED
     └──────────────────── 签约后放弃 / 合同终止 ───────────────────────────────────────────────▶ 关闭 CLOSED
                                  （暂停：装修/闭店/纠纷/整改，必填原因与预计恢复时间）
```

| 步骤 | 做什么 | 规则 |
|---|---|---|
| 1. 建站点 | 关联场地方、区域、经纬度、营业时间、品牌、运营主体 | 🔒 **上线必须有生效合同**（2026-09-25 定：合同要引用站点，建站时合同还不存在，所以校验放在上线门禁与恢复营业，而不是建站）；🔒 **营业时间必填** —— 它决定离线告警是否误报（见 P7） |
| 2. 现场勘测 | 确认点位：位置、电源、网络信号（4G/WiFi）、照片 | 信号差的点位装了也是长期离线，**勘测不过不装** |
| 3. 建点位 | 点位名（「L1 东门服务台」）、照片、电源类型 | 点位不承载归属，继承站点 |
| 4. 指定归属 | 运营主体（平台自营/代理商）+ 各责任人（出资/拓展/运维） | 🔒 必须有**运维责任人**，否则告警和工单没人接 |

**产物**：站点 + 点位清单 + 归属/责任 → 可以装机。

### P4 设备布放上线（资产线的起点）

```
采购到货 ─▶ 入库质检 ─▶ 在库 IN_STOCK ─调拨─▶ 城市仓/代理仓 ─领用─▶ 运输中 ─▶ 安装绑定点位
                                                                                   │
                                           激活联网 ─▶ 装宝 ─▶ 试借还验收 ─通过─▶ 已布放 DEPLOYED（上线营业）
                                                                  │不通过
                                                                  └──▶ 故障 FAULT ─▶ 维修工单 / 返仓
```

| 步骤 | 做什么 | 关键规则 |
|---|---|---|
| 1. 入库 | 按 SN 登记机柜与充电宝；质检（开机、仓位、宝电量与循环次数） | 🔒 SN 唯一；质检不过不入可用库存 |
| 2. 调拨 | 总仓 → 城市仓 / 代理仓；发货 → 在途 → 签收逐件核对 | 🔒 签收必须逐件核对，缺件要能挂差异 |
| 3. 划拨 | 出资方是代理商时，设备归属划给代理商（P5） | 🔒 划拨留痕，收益按划拨后订单计算 |
| 4. 安装 | 运维领装机工单 → 到场 → 扫码绑定点位 → 拍照 | **用工单驱动装机**，这样装机时效、谁装的、装在哪都有记录 |
| 5. 激活联网 | 设备首次心跳，平台确认在线 | 🔒 未收到心跳不能上线 |
| 6. 装宝 | 放入初始库存宝（一般装到仓位的 60%–70%，**留空仓给还宝**） | 满装是新手最常见错误：没地方还 = 用户投诉 + 订单超时 |
| 7. 试借还 | 运维扫码借一次、还一次，全链路走通 | 🔒 **上线门禁**：合同生效 + 在线 + 试借还通过 + 计费方案命中，缺一项不上线 |
| 8. 上线 | 设备状态 → 已布放；站点若是首台 → 筹备转营业；C 端地图可见 | |

### P5 代理商入驻与划拨（归属线）

入驻段（申请 → 审核 → 建号 → 登录 → 数据范围）已在 [必要功能清单](./必要功能清单-从入驻到到账.md) §二 写清，本文只补**运营侧**的后半段：

```
入驻通过 ─▶ 签代理协议（区域、责任、分润比例、保证金、考核）─▶ 划拨（区域/站点/点位/设备）─▶ 经营中 ENABLED
                                                                                           │
                           考核不达标 / 违约 ─▶ 暂停 SUSPENDED ─整改─▶ 恢复                  │
                                                  └─清退─▶ 资产收回 + 结清分润 + 退保证金 ─▶ 终止
```

| 环节 | 规则 |
|---|---|
| 划拨粒度 | 站点 → 连带其点位与设备；点位 → 连带其设备；设备 → 仅自身。🔒 **上级划拨必须级联下级**，否则同一站点里设备归属打架 |
| 责任 | 出资 / 拓展 / 运维 / 牵线四项原子责任，一个站点可以是 A 出资 B 运维（ADR-027） |
| 暂停的含义 | 🔒 暂停后：不能新划拨、分润**照常计提但冻结提现**、其名下工单要**改派**给平台运维（否则设备坏了没人修） |
| 清退 | 🔒 先收回资产（划回平台）、再结清分润、最后停账号 —— 顺序反了会出现「账号停了但还有钱没结」 |
| 考核 | 行业常用：设备在线率、工单 SLA 达成率、单柜日均收入、客诉率 |

> **行业经验**：代理模式最大的风险不是代理跑路，而是**代理不运维**。设备坏了代理不修，
> 用户骂的是品牌。所以代理的运维 SLA 必须和分润挂钩，超时的工单要能**被平台接管**。

### P6 日常运营

这是站点一生中最长、最赚钱也最容易被忽视的阶段。

#### P6.1 借还（交易主线）

```
扫码 ─▶ 免押/押金/预授权 ─▶ 下发弹宝指令 ─▶ 弹出成功（订单进行中）─▶ 任意柜归还 ─▶ 计费 ─▶ 扣款 ─▶ 订单完成 ─▶ 分润
            │                    │弹出失败                          │超时未还
            └ 失败：提示换方式    └──▶ 自动撤单退款 + 标记仓位异常    └──▶ 逾期 ─▶ 达到封顶 ─▶ 转买断（宝状态 → 已售）
```

| 规则 | 说明 |
|---|---|
| 🔒 站点暂停 / 设备离线 / 设备故障时**不可借** | 仍可还（用户手里的宝必须能还回来） |
| 🔒 弹出失败自动撤单 | 不能让用户为没拿到的宝付钱 |
| 🔒 还宝异常（机柜未识别）有人工补还通道 | 客服凭照片/视频补结束订单 |
| 计费方案按站点/设备类型命中恰好一个 | 见 [经营链条方案](../technical/经营链条方案-主体到分账.md) 第 6 环 |

#### P6.2 调度（补宝与调宝）—— 行业里最花人力的环节

柜子的健康不是「在线」，是**「有宝可借、有位可还」**。

| 状态 | 判定（行业常用阈值，可配置） | 动作 |
|---|---|---|
| **空柜/缺宝** | 可借宝数 ≤ 1，或可借率 < 20% | 生成补宝任务：从满柜/仓库调宝过来 |
| **满柜/无位** | 空仓数 ≤ 1 | 生成取宝任务：拿走一部分宝调给缺宝柜 |
| **低电宝堆积** | 电量 < 30% 的宝占比高 | 检查仓位充电故障，或宝电池老化 |
| **宝老化** | 循环次数/容量衰减超阈值 | 标记待报废，回收替换 |

调度任务本质是一类**工单**（类型 = 调度），用同一套派单与 SLA，按区域/路线合并派给运维，减少跑动。

#### P6.3 站点效益管理

| 周期 | 看什么 | 决策 |
|---|---|---|
| 每日 | 在线率、可借率、订单数、异常订单 | 触发调度、维修 |
| 每月 | **单柜日均收入**、周转率（订单数/宝数）、场地分成占比 | 低效站点预警 |
| 每季 | 连续 N 个月低于盈亏线的站点 | **迁机**（换点位/换站点）或**撤场**（P9） |

> **行业经验**：头部玩家的铺设策略是「铺 → 测 → 迁」。三个月跑不出来的点位要果断迁走，
> 设备闲置在低效点位上，比放在仓库里还亏（占着分成和运维成本）。

### P7 监控 · 告警 · 工单闭环（本文重点）

这是「出问题能发现能修」的全链路，**闭环的定义是：告警能自动产生、能转成工单、工单完成后告警能自动关闭，且整个过程有时限**。

```
          ┌─────────────── 监控（数据源）───────────────┐
          │ 设备心跳 · 状态上报 · 订单异常 · 用户报障 · 巡检 │
          └──────────────────────┬──────────────────────┘
                                 ▼
                    规则判定（阈值 + 持续时长 + 营业时间）
                                 ▼
    告警 OPEN ─(去重/收敛)─▶ 通知（按告警码：谁、什么渠道、静默窗口、升级）
       │  │
       │  ├─ 人工确认 ─▶ ACKED（有人在看）
       │  │
       │  └─ 自动/人工转工单 ─────────────────────────────┐
       │                                                  ▼
       │    工单 CREATED ─派单─▶ DISPATCHED ─接单─▶ ACCEPTED ─到场─▶ PROCESSING ─完工─▶ DONE ─验收─▶ CLOSED
       │                   ▲         │拒单                                              │验收不过
       │                   └─────────┘（退回待派）                                        └─▶ 返工 PROCESSING
       │                                                                                  │
       ▼                                                                                  ▼
    恢复 ◀── 设备恢复正常（心跳恢复/状态恢复）自动关闭 ◀──────── 工单完工后复核告警条件 ──┘
    CLOSED（记录恢复方式：自动恢复 / 工单修复 / 人工关闭+原因）
```

#### P7.1 监控项与告警分级

| 类别 | 监控项 | 判定（示例阈值） | 等级 | 默认处置 |
|---|---|---|---|---|
| 在线 | **机柜离线** | 心跳中断 > 10 分钟，且**在站点营业时间内** | 严重 | 转工单 |
| 在线 | 频繁掉线 | 24h 内掉线 > 5 次 | 警告 | 转工单（查网络/电源） |
| 硬件 | 仓位故障（卡宝、锁舌、充电） | 设备上报 | 严重 | 转工单，**该仓位自动禁用** |
| 硬件 | 弹出失败率高 | 同柜 1h 内弹出失败 ≥ 3 次 | 严重 | 转工单，柜子暂停借出 |
| 库存 | 缺宝 / 满柜 | 见 P6.2 | 提示 | 转调度任务 |
| 宝 | 宝电池异常（温度、鼓包、不充电） | 设备上报 | **严重 + 安全** | 立即锁仓 + 转工单（安全问题） |
| 订单 | 借出未拿到 / 还宝未识别 | 订单异常 | 警告 | 转客服单 |
| 资产 | 宝长期未归还 / 宝在非本区域出现 | 统计 | 提示 | 资产盘点 |

> 上表是**信号**视角的监控项。告警中心实际呈现的是按业务影响归纳的**业务告警**（站点借不到、用户还不了等），见 §十.3 与告警方案 v2。

**防误报三条**（行业里告警系统被运维「屏蔽」的主要原因就是误报太多）：

1. **结合营业时间**：商场闭店断电是最常见的「离线」，营业时间外的离线**不告警**，开门后 30 分钟仍离线才告警。
2. **持续时长**：瞬时抖动不算，满足条件持续 N 分钟才开告警。
3. **去重收敛**：同一设备同一告警码未关闭时，**不开新告警，只累加次数**；一个站点多台同时离线收敛为一条「站点级离线」（多半是场地断电/断网）。

#### P7.2 工单

| 维度 | 取值 |
|---|---|
| **来源** | 告警自动 · 告警人工转 · 用户报障（客服转）· 巡检计划 · 人工开单 · 调度任务 · 装机/撤机 |
| **类型** | 装机 · 维修 · 调度（补宝/取宝）· 巡检 · 撤机 · 其他 |
| **派单规则** | 🔒 按站点的**运维责任人**自动派；无责任人/责任人暂停 → 派平台区域运维；可抢单模式 |
| **SLA** | 响应时限（派单 → 接单）+ 解决时限（派单 → 完工），按工单优先级：P1（安全类）30min/4h、P2（严重）2h/24h、P3（警告）8h/48h、P4（提示/计划类）24h/72h（示例，可配置；与告警等级的映射见 §十.3） |
| **超时升级** | 响应超时 → 通知组长；解决超时 → 通知区域经理并**可由平台接管**（代理商的单） |
| **完工要求** | 🔒 必填处理结果、故障原因分类、更换配件、**现场照片**；关联设备状态随之更新 |
| **验收** | 完工后系统**自动复核**：关联告警是否已恢复、设备是否在线、仓位是否可用。自动复核通过即验收；不通过 → 返工 |
| **计费** | 配件与人工成本记到站点（算站点效益），代理商负责运维的记到代理商 |

#### P7.3 巡检

- 巡检计划：路线（站点列表）+ 周期（周/月）+ 检查项（外观、清洁、贴纸二维码、电源线、宝数量与外观）。
- 到期**自动**生成巡检工单并派给路线责任人。
- 巡检发现问题 → 从巡检工单**直接派生**维修工单（保留来源链）。

> **行业经验**：巡检最常被形式化（拍一张照片就完工）。有效做法是巡检项要可验证：
> 例如「清点宝数量」与系统读数比对，不一致即异常 —— 这同时是一次**资产盘点**。

### P8 结算分润

订单完成 → 按快照生成分润明细（场地方按合同、代理商按责任规则）→ 周期汇总结算单 → 场地方对账/代理商提现 → 打款。
已在 [必要功能清单](./必要功能清单-从入驻到到账.md) §三 与 [经营链条方案](../technical/经营链条方案-主体到分账.md) 第 8 环写清。

运营流程对结算的三个**输入约束**：

- 🔒 分润依据的是**成单时刻**的合同与归属（快照），划拨或换合同不追溯历史订单。
- 🔒 **保底 + 分成**的合同，保底差额在结算单层面补齐，不在逐单分润里体现。
- 撤场时的进场费/押金退还、代理保证金退还，走结算单的**调整项**，不走提现。

### P9 撤场与资产回收

**触发**：合同到期不续 · 合同提前终止 · 站点长期低效 · 场地装修/倒闭 · 代理清退后无人接手。

```
撤场决策（审批）─▶ 站点暂停借出（仍可还）─▶ 等待在借订单归还（或设宽限期）─▶ 撤机工单
     ─▶ 运维到场拆机、清点宝 ─▶ 调拨回仓（签收核对）─▶ 设备回到在库 ─▶ 站点关闭 ─▶ 结清分成与押金 ─▶ 合同终止/到期归档
```

| 规则 | 说明 |
|---|---|
| 🔒 撤场前先停借不停还 | 否则用户手里的宝还不回来 |
| 🔒 站点关闭前：点位下无设备、无进行中工单、无在借订单 | 否则资产和订单悬空 |
| 🔒 回收的宝**逐颗清点**，与系统在柜数比对 | 撤场是丢宝最集中的时刻 |
| 撤场也是一类工单 | 有时限、有责任人、有照片 |

## 四、跨对象联动（事件 → 影响）

流程之间靠这些联动咬合。**一条联动缺失 = 某个环节要靠人记得去做**，而人一定会忘。

| # | 事件 | 自动影响 | 为什么必须自动 |
|---|---|---|---|
| E1 | 商机签约 | 生成/关联场地方 + 合同草稿；写入拓展归因 | 否则 BD 佣金无法计算 |
| E2 | 合同生效 | 站点允许上线；牵线人发介绍费 | 无合同不营业 |
| E3 | 合同到期前 60/30/7 天 | 提醒 BD 与运营；进入续签跟进 | 最常见的「过期白干」 |
| E4 | 合同到期未续 / 终止 | 站点进入撤场评估（不自动撤机，但标红） | 无合同营业 = 场地方随时可以清场 |
| E5 | 站点暂停 | 该站点所有设备**停借保还**；C 端显示暂停 | 否则用户借到、场地却闭店 |
| E6 | 首台设备上线 | 站点 筹备 → 营业 | |
| E7 | 划拨站点/点位 | 级联下级点位与设备的归属；此后订单按新归属分润 | 同站点归属不一致 |
| E8 | 代理商暂停 | 冻结提现；名下待处理工单改派平台 | 设备没人修 |
| E9 | 心跳中断（营业时间内超阈值） | 开离线告警；设备不可借 | 让用户扫到离线柜是最差体验 |
| E10 | 心跳恢复 | 关闭离线告警（自动恢复）；关联工单若未开始可自动撤销 | 否则告警越积越多、没人再看 |
| E11 | 告警（码配置为自动开单） | 生成工单，按运维责任人派单 | |
| E12 | 工单完工 | 复核关联告警与设备状态；通过则告警关闭、设备恢复可用 | 闭环的最后一环 |
| E13 | 工单超 SLA | 升级通知；代理的单可由平台接管 | |
| E14 | 巡检计划到期 | 生成巡检工单 | |
| E15 | 调拨签收 | 设备进入目标仓在库；差异件挂异常 | 资产线断点 |
| E16 | 订单完成 | 生成分润明细 | |
| E17 | 订单逾期达封顶 | 转买断，宝状态 → 已售，从资产中移除 | 否则宝「永远在借」 |
| E18 | 站点效益连续 N 月低于阈值 | 预警，进入迁机/撤场评估 | |

## 十、裁决落地方案（2026-09-25）

### 10.1 合同走审批

**状态机**

```
DRAFT 草稿 ─提交─▶ PENDING 待审批 ─通过─▶ SIGNED 待生效 ─到生效日（定时）─▶ ACTIVE 生效中 ─到期（定时）─▶ EXPIRED
   ▲                  │驳回（必填意见）                        │                          │
   └──────────────────┘                                        │                          └─终止（走审批）─▶ TERMINATED
                         撤回（提交人，审批前）─▶ DRAFT          └─生效日已过则通过即 ACTIVE
```

| 规则 | 说明 |
|---|---|
| 可编辑范围 | 🔒 只有 DRAFT 可改条款；SIGNED 之后改条款 = 新建补充协议/新版本，旧版保留 |
| 审批人 | 单级：运营负责人。**条件加签财务**：分成比例高于阈值、有保底金额、进场费高于阈值（阈值走系统参数） |
| 审批与签字的关系 | 审批是**内部**批准条款；线下盖章后上传扫描件、填签署日期，才从 SIGNED 允许到 ACTIVE |
| 提前终止 | 也走审批（影响分成与撤场），终止生效日之后站点进入撤场评估（E4） |
| 与站点联动 | 🔒 站点上线门禁查「有 ACTIVE 合同」；🔒 同站点同时刻只能一份 ACTIVE（新合同生效 = 旧合同到期/终止） |
| 定时任务 | SIGNED → ACTIVE（生效日）、ACTIVE → EXPIRED（到期日）、到期前 60/30/7 天提醒 |
| 留痕 | 每次迁移记操作人、时间、意见；审批意见在合同详情时间线可见 |

**权限码**：现有 `location:contract:create/update` 覆盖起草与编辑；**提交、审批、终止**在
[功能权限清单](./功能权限清单.md) 中没有对应码。按惯例不自造，候选写法（待登记后再用）：
`location:contract:submit` · `location:contract:audit` · `location:contract:terminate`。

**分级**：单级审批 + 待生效/到期定时 = **L0**（合同本身是 L0，状态机不能晚于它）；条件加签、补充协议版本链 = L1。

### 10.2 站点状态与门店生命周期合并

**现状两套**：`loc_site.status`（ACTIVE/PAUSED + 归档）与 `loc_site_lifecycle` 的阶段
（PROSPECTING/SIGNED/LIVE/ACTIVE/CHURNED/CLOSED，自由跳转）。同一个站点可以同时是「ACTIVE」和「CHURNED」。

**合并口径**：阶段按**对象归属**拆开，站点只保留站点存在之后的状态。

| 原生命周期阶段 | 合并后去向 | 理由 |
|---|---|---|
| PROSPECTING 拓展中 | → **商机**阶段（NEW/CONTACTED/NEGOTIATING） | 签约前站点还不存在，被拓展的是**场地** |
| SIGNED 已签约 | → 站点 **PREPARING 筹备** | 合同生效、站点已建、设备未上线 |
| LIVE 已上线 | → 站点 **ACTIVE**，另记「首次上线时间」 | LIVE 与 ACTIVE 的区别是时间长短，不是状态；用属性表达 |
| ACTIVE 稳定运营 | → 站点 **ACTIVE** | 同上 |
| CHURNED 流失 | → 站点 **WITHDRAWING 撤场中** | 「决定撤」到「撤完」之间有一段需要跟踪的过程 |
| CLOSED 关闭 | → 站点 **CLOSED** | |
| （无）暂停 | 站点 **PAUSED** 保留 | 原生命周期没有这个态 |

**迁移规则（不再自由跳转）**

| 迁移 | 触发 | 前置条件 |
|---|---|---|
| PREPARING → ACTIVE | 首台设备上线（E6，自动） | 有 ACTIVE 合同 |
| ACTIVE → PAUSED | 手动 | 必填原因 + 预计恢复时间；联动停借保还（E5） |
| PAUSED → ACTIVE | 手动 / 到预计时间提醒 | 有 ACTIVE 合同 |
| ACTIVE/PAUSED → WITHDRAWING | 撤场审批通过 | 生成撤机工单；站点停借保还 |
| WITHDRAWING → CLOSED | 自动（条件满足时） | 🔒 点位下无设备 · 无进行中工单 · 无在借订单 |
| PREPARING → CLOSED | 手动 | 无设备；签约后放弃或合同终止 |

**归档**与状态正交：只有 CLOSED 的站点可以归档（从默认列表隐藏）。

**`loc_site_lifecycle` 的去留**：从「状态」降为**状态变更日志**（谁、何时、从哪到哪、原因），
为「门店生命周期」页提供时间线与各阶段停留时长。菜单「场地方与拓展 › 门店生命周期」改为**只读看板**：
商机阶段（签约前）+ 站点状态（签约后）拼成一条漏斗，不再提供「改阶段」按钮。

**分级**：站点状态机 = **L0**（站点本身是 L0）；门店生命周期看板维持 L3。

### 10.3 告警码：业务视角（2026-09-25 定）

用户定：**告警码应该是业务视角**。详细方案见 [方案-告警码与自动开工单（v2 · 业务告警体系）](../technical/方案-告警码与自动开工单.md)，要点：

- **三层**：设备与交易的**信号**（离线、卡宝、温度……）是证据，不直接给人看；告警中心里看到的是**业务告警**（站点借不到、用户还不了、付了款没拿到宝、合同过期仍营业）；再按根因路由到**处置**（系统自愈 / 运维工单 / 客服跟进 / 待办 / 通知 / 升级）。
- **九个业务域**：可借 · 可还 · 交易 · 安全 · 资产 · 经营 · 履约 · 合作 · 资金；域决定默认主责与处置。首版 30 个业务码，L0 10 个。
- **严重度由影响评估算出**：告警等级固定在码上（便于统计）；处置优先级 = 基准 + 影响加成（整站 / 高峰 / A 级站点 / 有在途用户），同一个「离线」在单柜站点午高峰是 URGENT、在五柜站点凌晨是 LOW。
- **保护动作与告警解耦**：卡宝仓位禁用、电池异常锁仓、弹出失败撤单由信号立即触发，不等业务判定。
- v1 的开单延迟、合并、自动恢复、完工复核机制原样保留。
