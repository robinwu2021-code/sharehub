## 本文做什么、不做什么

**做什么**：把原文按「可验收的单条需求」重新切分并编号，让每一条都能被追溯、被比对、被验收。
原文按章节叙述，同一要求常在三四处重复出现（例如「历史归属不覆盖」出现在 §2.2、§4.1、§6.4、§10.4）；本文每条只出现一次，并标出全部原文出处。

**不做什么**：

- **不新增需求**。原文没写的（注册登录、地图找柜、客服、会员、营销、多设备类型等）一律不进本文，哪怕项目里已经做了。
- **不替运营方拍板**。原文里互相矛盾或只是演示的数字，原样进 §十二「待确认」，不在需求条目里选边。
- **不写实现方案**。怎么做、用哪张表，见对齐文档与各 TDD。

## 编号与标记

编号格式 `RQ-<域>-<序号>`，共 12 个域。每条带三个标记：

| 标记 | 取值 | 含义 |
|---|---|---|
| 强度 | **M** 必须 | 原文用「要求 / 应 / 必须 / 不得」表述 |
| | **C** 有条件 | 原文写明「在接口/网关/Zoho 支持的前提下」，可行性须先验证 |
| | **D** 演示 | 仅出现在 [B] 的演示图示，数值未经确认 |
| 验收 | **AC-xx** | 对应原文 §15.2 的 11 条验收标准（见 §十一） |
| 出处 | `A§n` / `B p.n` / `原文§n` | 前两者是原始材料页码，后者是归并稿章节 |
