## 一、结论

**原始需求与项目现状的重合度不高，而且分歧主要不在「还没做」，而在「做成了另一个样子」。**

| 覆盖 | 条数 | 占比 | 含义 |
|---|---:|---:|---|
| ✅ 已覆盖 | 16 | 14% | 文档有、代码有、口径一致 |
| ◐ 部分 | 62 | 54% | 有骨架，缺字段、缺筛选、缺导出，或只到 mock |
| ❌ 缺失 | 22 | 19% | 文档与代码都没有 |
| ⚠️ 冲突 | 15 | 13% | 项目已做出**与原文相反**的决定，补功能解决不了，须先裁决 |

| 域 | ✅ | ◐ | ❌ | ⚠️ | 判断 |
|---|---:|---:|---:|---:|---|
| SCP 定位边界 | 3 | 1 | 0 | 2 | 项目范围远大于原文，且是新建不是升级 |
| APP 用户 App | 1 | 3 | 0 | 2 | 借还主链路可用；收费披露与发票不达标 |

| **合计** | **16** | **62** | **22** | **15** | |

**三句话读懂差距**：

1. 原文是一个**财务与资产管控系统**：每笔租赁要能出税务发票、每笔分成要能和 Zoho 对上、每台设备要能追到采购单。项目是一个**运营平台**：重心在借还、设备接入、工单告警、代理分润，并扩展到多设备与互联互通。
2. 原文最看重的三块，**Zoho 集成、自动发票、采购库存**，在项目里分别是空白、另一种模型、空白。
3. 项目有大量原文没要求的能力（多设备、OCPI、会员营销、竞品对标），而原文明确要求的报表与导出只做到了 CSV。

## 二、术语映射（评审前必读）

同一个词在两边指不同的东西。不先统一，评审会议上每一句话都可能被误读。

> ✅ **2026-10-28 已裁决**：原文的「商户」在本项目一律称**商家**，第一阶段以商家为结算单元；
> 「商户」只指商家在支付渠道侧的收款身份（[ADR-032 §一](../technical/ADR/ADR-032-第一阶段以商家为结算单元-会计系统架构预留.md)）。
> 下表前两行按此改写，原「原文商户 = 场地方」的映射作废。

| 原文用词 | 项目用词 | 映射说明 |
|---|---|---|
| **商户** Merchant（如 Hotel A，分成 15–50%） | **商家**（运营主体，代码 `agt_agent` / `agent_no`） | ✅ 已裁决。第一阶段唯一结算单元；经自助注册或运营代建、审核后产生 |
| （无对应） | **商户**（渠道侧） | 商家在支付渠道的子商户号与进件状态，商家 1:N 商户（ADR-029 §5.2 `pay_merchant`，未建） |
| （无对应） | **场地方** Venue | 场所档案与进场合同保留；第一阶段不作为独立结算对象 |
| 商户分支机构 | **站点** Site | ADR-013：场地方 → 站点 → 点位 |
| 安装地点 | **点位** Point / Location | |
| 代理（佣金对象） | **代理商 / 加盟商 / 城市合伙人** Agent | 项目语义更宽：带出资、拓展、运维责任，是运营体内的分润伙伴（ADR-012/027） |
| 机器 Machine | **机柜** Cabinet | |
| 最高租赁收费 | **总封顶 = 买断价** `capTotal` | ⚠️ 项目把它和遗失费合成一个数，见冲突 K5 |
| 最长租赁时限 | `overdueHours`（系统设置，默认 72） | ⚠️ 后端无人读取，见冲突 K4 |
| 供应商（采购对象） | **供应商** Vendor | ⚠️ 项目指**硬件厂商的驱动插件**（ADR-018），不是采购供应商 |
| 销售 Sales | **BD**（拓展/招商） | |
| 管理层 Management | **VIEWER**（只读） | 项目另有 CS（客服）、AGENT（代理）两个角色 |
| 支付网关 | nearpay → **ai-shop pay** | ADR-025（2026-09-23 已决）改为复用 ai-shop 在跑的支付服务；项目多处文档仍写 nearpay |

## 三、须先裁决的根本性冲突

以下八项都是**项目已经做了与原文相反的决定**。继续开发前必须由运营方拍板，否则补得越多返工越大。

### K1 · 项目定位：充电宝运营系统，还是多设备共享平台？

| | |
|---|---|
| **原文** | 「适用业务：共享充电宝租赁（**不是新能源汽车充电桩**）」；开发商先**评估现有 App、后台、数据库**，再决定升级或部分重建（RQ-SCP-01、04） |
| **项目** | 更名 ShareHub，定位「对充电宝/充电桩/储物柜一视同仁」，充电桩与储物柜列为首批三类，OCPI 互联互通在范围内（ADR-014/018、架构设计总纲 §〇 §1.6）。Flyway 从 V1 建库，**全仓没有对运营方现有系统的评估或数据迁移方案** |
| **另一个来源** | 项目当前需求主要来自 `ref/充電寶專案_V4(1).pdf`（甲方 V4，T1–T9 三期）与竞品简电云对标，和本次原文是**两套来源** |
| **要裁决** | ① 两套来源以谁为准，还是合并？② 运营方现有系统要不要评估、要不要迁移数据？③ 多设备扩展是否保留，若保留是否推迟到原文范围交付之后？ |

### K2 · 会计主账：Zoho Books，还是项目自建账本？

| | |
|---|---|
| **原文** | Zoho Books 是「**会计分录与已记录付款**」的记录来源；本系统只保留逐笔运营明细（RQ-ZOH-08） |
| **项目** | 自建复式账 `acct_account`/`acct_ledger`，支持手工记账凭证 `POST /api/trade/ledger/vouchers`；三方对账对的是「nearpay ↔ pay_order ↔ acct_ledger」（`ReconcileService`）。**Zoho 在项目文档与代码中零命中** |
| **要裁决** | 若 Zoho 是主账：内部账降级为运营子账，手工凭证入口应关闭，三方对账改为「应用 ↔ 网关 ↔ Zoho」。依赖待确认项 C14（科目映射） |
| ✅ **裁决** | **2026-10-28**：Zoho 暂时不做，架构上预留、编码上暂不处理。第一阶段内部复式账仍是账务来源；资金事件字段与应付台账的付款来源按「将来可切换」设计（ADR-032 §二） |

### K3 · 分成付款：Zoho 录入后读回，还是本系统提现打款？

| | |
|---|---|
| **原文** | 「商户和代理的实际付款**在 Zoho Books 录入，不在超级应用中重复手工录入**」；系统读回付款并自动更新未结余额（RQ-SHR-06、RQ-ZOH-02） |
| **项目** | ADR-004 定 `LEDGER` 模式：分润入账 → 结算单 → **受益方自助申请提现** → 审批 → 本系统登记打款（MANUAL / NEARPAY）。已实现（`WithdrawalServiceImpl`） |
| **连带问题** | 场地方「不登录」，提现只授给 AGENT 角色，结算单 CONFIRMED→PAID 无调用方 ⇒ **场地方（原文的商户）的「应得 / 已付 / 未结」在项目里出不来**，而这正是原文验收 AC-06 |
| **要裁决** | 是否改为「应付台账 + Zoho 付款读回」？若保留提现模型，至少要给场地方补一条应付闭环 |
| ✅ **裁决** | **2026-10-28**：第一阶段以**商家**为结算单元，场地方不单独结算。新增商家维度的应付台账；第一阶段由本系统登记付款，会计系统接入后改为读回（ADR-032）。场地方分成由谁承担仍待确认 |

### K4 · 超时扣款：按时间触发，还是按金额触顶买断？

| | 原文 | 项目 |
|---|---|---|
| 触发条件 | 到**最长租赁时限**（时间） | 累计费用达到 `capTotal`（金额）；未配 `capTotal` 则永不触发 |
| 触发后 | 发起最高收费，订单仍是「未归还」 | 订单直接 SETTLED，充电宝变 **SOLD**（转给用户） |
| 之后归还 | **更新归还状态**，不冲销收费 | 被**静默忽略**（`PowerbankTracker`「不在预期状态时静默跳过」） |
| 时限参数 | 可配置 | `overdueHours` 页面可存，**后端无任何代码读取** |
| 证据 | RQ-BIL-01/02/04/07 | `OrderOverdueBuyoutJob`、`RentOrderServiceImpl#buyoutIfCapped`、PRD-trade-rental 第 56 行 |

**要裁决**：采用哪种模型。原文模型要求「已扣款未归还」作为一个可见状态存在，项目目前没有这个状态。依赖 C04（封顶与时限规则）。

### K5 · 最高租赁收费与设备遗失费：独立，还是合一？

原文：遗失费如要实施，应作为「**独立于最高租赁收费的规则**」（RQ-APP-06）。
项目：`PricePlan.capTotal` 注释为「总封顶 = 买断价」，代码注释「买断那一刻收的是硬件钱」（`ChargeChain` 约束 3）。
**要裁决**：拆成两个参数，还是接受合一。合一在阿联酋的消费者披露上是否合规，需法务确认。

### K6 · 发票：每笔租赁自动出 B2C 税务发票，还是 B2B 结算发票加申请制？

| | 原文 | 项目 |
|---|---|---|
| 对象 | **每笔租赁**给租赁客户 | 运营端 `fin_invoice`：给**场地方/代理商**的结算发票；C 端 `UsrInvoice`：用户**手动申请**、财务开具 |
| 时点 | 法定时点；最高收费触发时也要开，**不能只等归还** | 「已结算订单可开」 |
| 生成 | 自动 | 人工登记草稿 |
| 模型 | TRN、VAT 税率/税额、租赁明细、支付信息 | 有 `invoiceCode/invoiceNumber`（**中国增值税发票的代码+号码模型**）、只有 vatTrn，无税率税额 |
| 更正 | 贷项通知单（Credit Note） | 只有整张作废 VOID |
| 排期 | M 级 | **L2**，MVP 明确排除 |
| 证据 | RQ-INV-01/02/03/10、RQ-APP-05 | 分级矩阵 C-IV-01、§八 #2；`FinInvoice`、`UsrInvoice` |

**要裁决**：发票是否升为首期；开票时点（C05）、开票主体（C01）必须同时确认。

### K7 · 设备采购：平台内跟踪，还是平台外处理？

原文：采购单 → **确认实际收货才入库** → 部分收货只增实收数 → 同一采购不重复入库（RQ-AST-04/05/06）。
项目：没有采购单、没有采购供应商模型；设备**建档即 `IN_STOCK`**；唯一的「确认收货」是**调拨单签收**。架构设计总纲 §1.5 明确把采购划到平台外：「供应商的资金关系只有设备采购/租赁（应付账）……线下或应付模块处理」。
**要裁决**：采购是否纳入平台。若纳入，资产档案还需补成本、附件、期初价值字段（`ReportServiceImpl` 自述「全站无资产成本表」）。

### K8 · 报表导出：Excel 与 PDF，还是前端 CSV？

原文：所有报表「下载 **Excel 和 PDF**」，验收 AC-09。
项目：只有前端 CSV（`ops-web/lib/export-csv.ts`：「无后端导出接口」），且 [待裁决清单-9-25](./待裁决清单-9-25.md) ④-1 **建议删除** `report:*:export` 等导出权限码。后端无任何 PDF 库。
**要裁决**：撤回 ④-1 的建议，补后端 Excel/PDF 导出能力。
