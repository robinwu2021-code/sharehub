## 〇、结论

| # | 结论 | 数据 |
|---|---|---|
| 1 | **现有接口层是齐的**：ops-web 在流程范围内调用的 135 个端点，后端**全部存在**（无 404 风险）；C 端流程相关 13 个调用也全部存在 | §1.1 |
| 2 | **ops-web 契约自身完整**：319 个 API 方法，每个都同时有 HTTP 实现与 mock 实现 | §1.1 |
| 3 | **设计新增的 46 个端点，只有 1 个已实现**（告警关闭，在途）；其余 45 个前后端都没有 —— 与 TDD 分批（P0–P4）一致，属「待建」而非「漂移」 | §二 |
| 4 | **3 个设计要删除的端点仍被页面使用**：阶段手改（门店生命周期页）、告警转工单（告警页）、批量自动开单（设备监控页） | §3.1 |
| 5 | **22 个设计要改的端点，前后端都在用旧形态**；改动集中在 5 个页面文件 | §3.2 |
| 6 | **功能层面，现有实现与功能说明的冲突有 11 处**，都是「状态可以手改 / 联动没接 / 桩代码」一类 —— 正是新增 L0 流程能力要消灭的 | §四 |
| 7 | 字段级不一致 2 处在流程范围内（告警记录、告警代码的后端字段前端未声明） | §1.2 |

**一句话**：接口「接得上」，但接上的是旧形态；流程要的状态机、门禁、联动在前后端都还没有。对齐的主要工作不是修补，而是按批次把设计落地，同时处理好旧形态的退场。

## 四、功能层对齐（功能说明 × ops-web × 后端）

逐条对照功能规划中的**规划要点**与现状。结论：✅ 一致 · 🟡 部分 · ❌ 冲突或缺失。

## 五、ops-web 内部与设计的差距（代码层）

| 类别 | 现状 | 设计要求 | 批次 |
|---|---|---|:-:|
| 状态类型 | `Contract.status` 为内联联合 `"ACTIVE" \| "EXPIRED"`；无 `ContractStatus` / `SiteStatus` 具名类型；`CabinetStatus` 无 `IN_TRANSIT` | 具名类型（两端词表比对只认具名） | P1–P3 |
| 迁移表 | 仅有工单、告警、调拨等；无 `CONTRACT_ / SITE_ / CABINET_ / POWERBANK_TRANSITIONS` | 每个后端状态机一张同名表 | P1–P3 |
| 共享部件 | 无状态步骤条、门禁清单、业务号链接、文件字段、实体选择器 | C1–C8 | P0 |
| 文件上传 | `uploadFile` 契约不存在；合同附件为原生 `<input type=file>` 假上传 | `FormDrawer` 的 `file` 字段 + `/api/platform/files` | P0 |
| 就绪门禁 | `PARTIAL_READY` 只登记了站点暂停与统计 | 每个新动作登记一项，真实后端未就绪时隐藏按钮 | 各批 |
| mock 一致性 | 划拨不级联；告警 mock 用设备码种子 | mock 与后端同规则；种子换业务码 | P3 / P4 |
