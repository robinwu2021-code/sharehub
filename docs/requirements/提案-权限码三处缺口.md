## 为什么是这三处

它们有一个共同形状：**C 端或后端已经在产生数据 / 已经留了状态，而运营端没有对应的动作面**。
不报错、不红、用户也不会投诉（他们不知道本该有），只有拿领域模型逐对象扫一遍才会露出来。

| | 功能 | 现状 | 缺什么 |
|---|---|---|---|
| ① | **关闭告警** | `AlarmStateMachine` 有 `OPEN→CLOSED` / `ACKED→CLOSED` 两条边，**主源码里没有任何一处发这个事件**（只有测试里有），`AlarmService` 六个方法里也没有 `close` | 告警只能 OPEN→ACKED 然后停住，`dev_alarm` 的 ACKED 行只增不减，「还有多少没处理」这个数从此说不清 |
| ② | **注销申请受理** | C 端 `POST /mp/user/logoff` 已开放（另一条线 2026-09-25 刚把 c-app 接上真接口），`usr_logoff` 有 PENDING 与冷静期 | 运营端零入口 ⇒ 冷静期内**没人能看到待注销队列，也没有撤销入口**。`UserLogoffService` 注释写明「冷静期已过此时数据可能已开始清除」——误操作的用户只能等数据被清掉 |
| ③ | **C 端开票受理** | C 端可提交开票申请（`usr_invoice` / `usr_invoice_title`） | 运营端「发票」叶子管的是 `fin_invoice`——**给场地方/代理商开的结算发票**，与 C 端开票是两个对象。消费者提交后无人受理 |

## ① 关闭告警

**为什么不能复用现有码。** 真源表里告警只有一个 `workorder:alarm:config`
（管告警代码 / 通知规则**配置**）。而运营端现在的「确认」按钮借的是
`workorder:wo:read` —— **一个只读码在管一个写动作**，本身就是将就。
关闭是有后果的动作（关掉就不再计入未处理），该有自己的码。

**提案**（放进 §6 运维工单 `workorder` 模块，与告警配置同域）：

| 子功能·操作 | 权限码 | OPS | CS | FIN | BD | VIEW |
|---|---|:--:|:--:|:--:|:--:|:--:|
| 告警 受理 | `workorder:alarm:ack` | ✓ | | | | |
| 告警 关闭 | `workorder:alarm:close` | ✓ | | | | |

**三个待裁决点**：

1. **受理与关闭要不要分成两个码？** 建议分。受理是「我看到了、我在处理」，
   关闭是「这事结了」。合成一个码，等于谁能受理谁就能把告警从未处理里抹掉。
2. **CS 要不要给？** 建议不给。告警是设备侧事实，客服不处理设备。
   但若「用户报障 → 客服看告警」是真实路径，则 CS 应给 `:ack` 不给 `:close`。
3. **关闭要不要填原因？** 建议必填（已解决 / 误报 / 自愈 三选 + 备注），
   与工单关单必须给验收结论同一口径 —— 否则「为什么关的」事后查不到。

> ⚠️ 顺带：`ack` 码定了之后，`alarms/page.tsx` 现在借用 `workorder:wo:read` 的地方要一并改掉。

## ② 注销申请受理

**为什么不能复用现有码。** 搜遍真源表，`logoff` / `注销` **一个码都没有**。
不能拿 `user:cuser:read` 顶 —— 看用户档案与处理注销队列不是一件事，
后者会**永久销毁数据**。

**提案**（放进 §8 用户运营 `user` 模块）：

| 子功能·操作 | 权限码 | OPS | CS | FIN | BD | VIEW |
|---|---|:--:|:--:|:--:|:--:|:--:|
| 注销申请 查 | `user:logoff:read` | | ✓ | | | ✓ |
| 注销申请 撤销 | `user:logoff:revoke` | | ✓ | | | |

**三个待裁决点**：

1. **谁能撤销？** 建议 CS（用户打电话说「我点错了」的入口就在客服）。
   若认为销毁类操作必须双人，则 `:revoke` 只给 ADMIN，CS 只给 `:read`。
2. **VIEWER 要不要能查？** 建议给 —— 注销量是个该被看见的经营指标。
   反对意见也成立：注销队列含个人信息，只读角色不该看。**请产品定**。
3. **要不要「立即执行」动作？** 建议**不要**。冷静期到点由任务执行，
   给一个手动提前销毁的按钮，等于给了一个不可逆的误操作入口。

## ③ C 端开票受理

**为什么不能复用现有码。** 现有 `finance:invoice:read` / `:issue` / `:void`
管的是**结算发票**（`fin_invoice`，给场地方 / 代理商开）。
拿它去管 C 端开票会把两个对象的权限混成一个：
**财务能开结算发票，不等于该能处理消费者的开票申请**——两者的金额口径、
抬头来源、作废后果都不一样。

**提案**（放进 §8 用户运营 `user` 模块，因为它属于消费者侧）：

| 子功能·操作 | 权限码 | OPS | CS | FIN | BD | VIEW |
|---|---|:--:|:--:|:--:|:--:|:--:|
| C 端开票申请 查 | `user:invoice:read` | | ✓ | ✓ | | ✓ |
| C 端开票申请 处理 | `user:invoice:handle` | | | ✓ | | |

**两个待裁决点**：

1. **归 `user` 还是 `finance` 模块？** 建议 `user` —— 对象是消费者的申请单，
   不是运营的账。但若财务认为「所有开票归财务」，改成
   `finance:cuser_invoice:*` 也自洽，**只要别和结算发票共用一个码**。
2. **CS 能不能处理？** 建议只给查。开票涉及税务凭据，出错要追回，
   与 CS 的日常处置不是一类风险。
