# 必要功能清单 · 从入驻到到账

本文接在 [`核心最小可用清单-MVP.md`](核心最小可用清单-MVP.md) **前面**。那份从「① 选址找场地」起步，
默认运营商**已经存在、已经登录**；本文把链条往前拉到入驻，往后拉到钱真正离开平台账户。

**判定「必要」的标准**：这一环缺了，**下一环拿不到它的产物**。不是「做了更好」，是「后面接不上」。
按这个尺子，好看的功能会掉出去，难看但承重的会留下。

## 一、主线

```
入驻段  ① 提交申请 → ② 审核 → ③ 激活建号 → ④ 登录 → ⑤ 选主体 → ⑥ 权限与数据域
经营段  ⑦…⑩ 选址 / 签约 / 建站点 / 上设备 / 借还付款      见 MVP 清单 ①–⑤
分钱段  ⑪ 分润明细 → ⑫ 结算单 → ⑬ 收款账户 → ⑭ 提现申请 → ⑮ 打款到账

（2026-09-23 后端已贯通；前端页面另计，见 §五）
```

**这张图原本最该看的不是绿色**：入驻段 ①–③ 做完时，两侧各有一个断点把它夹住 ——
①–③ 的产物是「一个能经营的账号」，而 ④ 读不到它；分钱段一路到 ⑭ 都通，⑮ 让钱停在「出款在途」。
两头任一不通，中间做多少都不变现。

**2026-09-23 下午：三个断点的后端已补齐**（④⑤⑮，20 条集成用例）。
下面各环保留当初的诊断原文 —— 它们记录的是**为什么会断**，比「现在通了」更值得留着。

|---|---|---|:-:|---|

| ⑤ | 一号多主体时选择当前主体 | `GET /api/auth/operators` · `POST /{agentNo}/switch` | ✅ 🆕 | 此前**整个缺失**，见下 |
| ⑥ | 登录后只看见自己的数据 | `PermissionService.resolveDataScope` + 锚点注册 | ✅ 🆕 | 机制一直在，但资金表未注册 —— ④ 通了之后实测出泄露，V58 补齐（见下） |

### ④ 当初为什么是断的 —— 不是「没做完」，是**两套身份互不相识**

```
grep -c "agt_account|AgtAccount" AuthController.java  →  0
```

生产路径上 `login()` 只认一个硬编码用户：

- 配了 `sharehub.admin.password` → 仅 `admin` + 该口令放行，角色由账号定；
- 没配且非 dev-mode → fail-closed 拒绝；
- dev-mode → 免密，且**角色和 `agentNo` 都由前端传**（`agentNo` 缺省还会兜底成 `AG001`）。

三条分支**没有一条查过 `agt_account`**。也就是说：入驻审核通过、`activate()` 老老实实写进库的那行账号，
**没有任何代码路径会在登录时读它**。①–③ 不是「做了一半」，是做完了但**接不上电**。

> 这一条与 D0（真实登录 / 凭据库，v4/06 A3）是同一件事。在 D0 落地前，入驻的产物只存在于数据库里。

### ⑤ 为什么必要 —— ADR-030 的承诺曾经只在库里、不在 API 上

ADR-030 定的是「一个手机号 = 一个 `agt_principal`，对多行 `agt_account`」。
数据结构支持了，`ops-web` 的 auth store 也留了 `memberships` / `currentOperatorNo` / `operatorGen`，
但**后端没有任何端点把「我属于哪几个主体」告诉前端**（全仓 `operators`/`principals` 的 Mapping → 0）。

结果：一个人给两家运营商干活时，登录后无从选择、也无从切换。
**单主体时可以不做；多主体时这是硬缺口**——而多主体正是 ADR-030 存在的理由。

## 三、分钱段

| # | 必要能力 | 端点 | 状态 | 备注 |
|---|---|---|:-:|---|
| ⑪ | 订单产生分润明细 | `finance:share_record:read` | ✅ | 生成链路 2026-09-23 已通 |
| ⑫ | 明细汇成结算单 | 6 个端点 | ✅ | |
| ⑬ | 维护收款账户（谁收钱、收到哪） | `GET/POST /api/trade/payout-accounts` | ✅ | |
| ⑭ | 提现申请 + 审批 | `POST /withdrawals`·`/audit` | ✅ | 审批前强校验有默认收款账户，快照户名与掩码 |
| ⑮ | 打款执行与回执 | `POST /api/trade/withdrawals/{no}/pay` | ✅ 🆕 | 此前状态机有 `PAY`/`FAIL` 迁移却**没有任何入口调用**；代付通道（nearpay）仍未接 |

### ⑮ 当初钱停在哪

状态机写着 `PAYING --PAY--> PAID`、`--FAIL--> FAILED`，但 `FinanceController` 的提现端点只有三个：
**建、查、审批**。审批把单子推到 `PAYING`（「出款在途」）之后，**再没有一条路通向 PAID**。

也就是：那时这套系统能把钱算清楚、能让人申请、能让人批准，**批准之后钱不会动，单子也永远不会变成已付**。
常见的误读是把它归给硬阻塞 2（nearpay 未接）—— 但**即使 nearpay 通了，也还缺一个回执入口**，
两件事，别当成一件。补上的入口先服务人工转账登记，通道接通后换个调用方调同一个方法即可。

## 四、两个小口子（不断链，但会让人白跑）

| 口子 | 现状 | 影响 |
|---|---|---|
| AGENT 缺 `finance:payout_account:read` | ✅ **本次已修** | 修之前：代理门户「你还不能收款」判据取不到数，提示**永不显示**，代理会一路提交到被驳回才知道 |
| 「申请提现」菜单叶 `soon: true` | 未改 | 代理在导航里点不进提现，只能靠运营代提 |

前者值得记一笔：文档（功能权限清单 §6 注）写了「代理端也持 `:read`」，`RolePerms.java` 没加。
D6d 的权限漂移守卫**抓不到**它——那个守卫比的是前后端两份镜像，两边都漏则一致。
**两份镜像一致 ≠ 权限正确**，按链路走一遍才查得出来。

## 五、已做与待做

### 2026-09-23 已落地（后端，20 条集成用例）

| 环 | 端点 | 承重设计 |
|---|---|---|
| ④ | `POST /api/auth/login`（手机号 + OTP）· `POST /api/auth/otp` | 只做 OTP 不做口令：全仓没有凭据存储，`cred_credential` 归属 `pb_auth`/auth-core，现在另起一张平行表将来要迁数据。查无此号也返回 ok，失败文案不区分「号不存在」与「码不对」—— 否则是一台手机号探测器 |
| ⑤ | `GET /api/auth/operators` · `POST /operators/{agentNo}/switch` | 切换**换发 token** 而非改会话字段：`agentNo` 是数据范围锚点，原地改会留下「旧 token 拿着旧范围继续跑」的窗口 |
| ⑮ | `POST /api/trade/withdrawals/{no}/pay` | 与 `:audit` 分开发码，便于将来做双人复核；成功必填渠道流水号（否则「已到账」无法在对账中证实），失败原因与审批驳回原因**分列**；`uk_stl_withdrawal_payref` 拦重复登记 |

顺带修掉的两处：**AGENT 缺 `finance:payout_account:read`**（代理门户「你还不能收款」提示永不显示）、
**`ApplyRateLimitFilter` 更名 `AnonymousRateLimitFilter`** 并覆盖登录发码（原本是个没人限速的刷短信口子）。

> 依赖倒置的落点：`AuthController` 直接依赖 `agent` 会闭合 `agent → loc → platform → agent`
> 的环。端口 `platform.iam.port.AgentIdentityPort` 由消费方声明、`agent` 实现 ——
> 这条是 ArchUnit 的 `noCyclesBetweenDomains` 当场抓出来的，不是事后想到的。

### 2026-09-24 前端接线（25 条 mock 测试）

| 环 | 落点 | 承重设计 |
|---|---|---|
| ④ | 登录页「合作伙伴」tab 改手机号 + 验证码 | 员工仍是邮箱 + 口令。不是两种风格并存，是两边凭据现实不同：代理端**全仓没有凭据存储** |
| ⑤ | 顶栏主体切换器 `components/layout/operator-switcher.tsx` | 切换**换发 token 并清 react-query 缓存**；只有一个主体时整个不渲染（永远只有一个选项的下拉框是噪音） |
| ⑮ | 提现审核页「登记打款」抽屉 + 「打款」列 | 「驳回原因」与「失败原因」分两列；种子里两种 FAILED 来源各占一半，否则分列这件事在界面上看不出来 |

过程中被守卫与实跑抓出来的三处，都是**光看代码看不出来**的：

| 抓到的 | 怎么抓到的 |
|---|---|
| `finance:withdrawal:pay` 没登记进 `UI_PERM_MAP` → 按钮对**任何人**都不渲染（`can()` 未登记一律拒，超管的 `*` 也不放行） | 跑起来看页面 + 运行时 `console.warn` 兜底 |
| 造了不存在的 `text-danger` / `--z-dropdown` | 反查 token 表；正确的是 `text-destructive` / `--z-popover` |
| 手搓下拉框，漏掉方向键 / typeahead / Esc / 焦点归还 | 组件库 `dropdown-menu.tsx` 的类注释原话「自绘必漏」—— 改用既有组件 |

> `store.switchOperator` 原本是**纯本地改字段**且无任何调用方。后端换发 token 之后它就错了：
> 旧 token 仍带着旧主体的数据范围，**界面显示已切换、拿回来的却是上一家的数据，且不报错**。
> 已改为接收服务端换发的新会话。

### 2026-09-24 代理自助提现（⑭ 的申请侧）

「申请提现」菜单叶此前挂着 `soon: true`：代理登录进来，却点不进去。去掉之后
暴露了一个**既有缺陷** —— 同一个 tab key 可以在多个 section 登记不同权限码
（`/finance?tab=withdrawals` 在「财务管理 › 提现审核」判 `:read`，
在「我的经营 › 申请提现」判 `:apply`），而 `resolveTabs` **只取评分最高的那一条**。
财务管理的 `/finance` 叶子多、评分高，于是代理拿到的是「提现审核」那条 ——
他没有 `:read`，整个 tab 被丢掉，**尽管他持有 `:apply`**。
表现是「菜单点得进来、页面上却没有这个 tab」，且不报任何错。
改为按 pool 顺序找**第一条该访问者进得去的**，顺带把「我的结算」也修好了。

| 落点 | 承重设计 |
|---|---|
| `POST /api/trade/withdrawals`（前端补齐） | 手续费 / 状态 / 申请人三者**入参里根本没有** —— 让前端传 fee，改一行请求体就能少交手续费 |
| 代理端列表按 `payeeNo` 收敛 | **展示过滤，不是安全边界**：真正管住的是服务端 AGENT 数据范围硬过滤 |
| 没有可用收款账户时按钮直接禁用 | 而不是让人填完金额提交、再在审批环节被退回 |
| 申请抽屉当场算手续费与实际到账 | 审批页早就这么做了，申请这一侧却没有 —— 申请人直到收到钱才知道扣了多少 |

`Withdrawal` 补上 `payeeType`/`payeeNo`（原本只有 `payeeName`）：按名字筛会把同名主体混进来，
且与 `settlements`/`shareRecords` 的 `(payeeType, payeeNo)` 口径对不上账。
mock 主体名改为取自 agents 种子 —— 否则切换器写着「示例代理商甲」、
自己的提现单却署名「North Hub」，看上去像筛错了数据。

### 2026-09-24 数据范围：门开了才发现门后是敞的

⑥ 这一环此前标 ✅「机制一直在，④ 通了之后才真正生效」—— **只说对了一半**。
机制在，但它只覆盖站点/点位/机柜/订单/工单，**四张资金表一张都没注册**。
代理端登录打通之前没人能触发；打通之后实测：

```
新代理 AG075（名下零条资金记录）能读到：
  分润明细 = 108 行     全平台每个人的分成流水
  收款账户 = 150 行     全平台的户名 + 银行账号掩码
```

收款账户这条是**本轮自找的**：为了代理门户那条「你还不能收款」提示，
给 AGENT 发了 `finance:payout_account:read` —— 码给了，范围没跟上。

`DataScopeRegistration` 原本卡在「registry 只能登记『维度 → 列』一对一，
表达不了 `payee_type='AGENT' AND payee_no IN (...)`，需 handler 支持带条件的锚点」。
**V58 把条件挪进列定义**：`agent_no` 是生成列
`CASE WHEN payee_type='AGENT' THEN payee_no END`，VENUE 行为 NULL，
而 `IN (...)` 天然不匹配 NULL —— 不必改共享框架，也不会误伤 VENUE 的行。
生成列而非普通列 + 同步逻辑：同步一旦漏一处就是静默泄露，生成列没有「忘了写」这种可能。

回归 `AgentDataScopeProbeTest` 三条，**缺任何一条都不够**：

| 用例 | 为什么不能省 |
|---|---|
| 代理看不到别人的 | 本体 |
| 代理**看得到自己的** | handler 是 fail-closed，一个把所有人都拒光的实现同样能让上一条变绿 |
| 运营侧仍看得到全部 | 注册锚点不该把 ALL 范围的角色也收窄 |

> 顺带确认了一处虚惊：`ShareGenerator` 的幂等走 **INSERT + 捕获唯一键冲突**，
> 不是 SELECT —— 数据范围不作用于 INSERT，分账链路不受影响。
> 若它当初用的是「先查后插」，注册 `share_record` 会让幂等查询恒空、**重复分账**。
