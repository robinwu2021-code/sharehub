# TDD-C端H5扫码

状态：**已实现**（2026-09-27）
关联需求：[`C端功能清单.md`](../requirements/C端功能清单.md) §3 扫码借出（C-SC，P0）
关联现状：[`C端对齐现状-17模块.md`](C端对齐现状-17模块.md) 模块 3

## 1. 为什么要做

扫码是借出的**主要方式**（需求 §3 的主路径）。而 `uni.scanCode` 是 App / 小程序能力，
H5 没有 —— 当前 Android 产物又是 Capacitor 壳（纯 WebView），同样没有。
于是「扫码」这个主入口在两个实际在用的形态上都不存在，主次颠倒成了「输入编号在前」。

## 2. 方案选型

| 方案 | 结论 |
|---|---|
| **A（采用）`BarcodeDetector` + `getUserMedia`** | 浏览器原生，**零依赖**。实测本机 Chromium 支持 `qr_code`。不支持时回落手输 |
| B 引 JS 解码库（jsQR / zxing-wasm） | 包体 +100KB～1MB，而 A 在目标浏览器已可用。真要覆盖 Safari 时再叠加，不是现在 |
| C H5 不做扫码，只手输 | 与「扫码是主要方式」直接冲突 —— 主入口在主力形态上不存在 |

**能力探测而非 UA 判断**：`'BarcodeDetector' in window` + `navigator.mediaDevices` +
`isSecureContext`。UA 判断会在每次浏览器更新后过期，而这三样是真正决定能不能跑的东西。

## 3. 设计

- `pb-scanner.vue`：全屏取景层（`<video>` + 取景框 + 取消），`requestAnimationFrame` 循环解码。
  扫到就 `emit('result', 柜机号)`；层内常驻一个「输入编号」出口 —— 扫不出来时不该只能退出重来。
- `ports/scan.ts` 补 `canScanHere()`：三端统一的能力探测，页面据此决定走哪条路。
- 首页：主按钮恒为**扫码**；`uni.scanCode` 有就用它，没有但浏览器能解码就开取景层，
  两者都不行才直接开手输框。手输始终是次要入口，不消失。

**相机权限被拒不是错误**：提示一句并落回手输，不弹红色报错 —— 用户拒绝授权是正当选择。

## 4. 测试

浏览器实测：能力探测三项为真 · 取景层打开后 `video.readyState>=2`（拿到画面）·
取消能关闭并停掉轨道（`track.readyState==='ended'`，不关就是相机灯一直亮）·
不支持时回落手输。解码本身依赖真实二维码，不在自动化里断言。

## 5. 风险

- **Safari 不支持 `BarcodeDetector`** → 自动回落手输，不报错。要覆盖 Safari 再议方案 B。
- 相机轨道必须在关闭/页面隐藏时停掉，否则相机指示灯不灭 —— 用户会认为 App 在偷拍。
