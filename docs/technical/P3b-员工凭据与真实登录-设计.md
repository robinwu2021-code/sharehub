# P3b · 员工凭据与真实登录 · 设计

> 创建 2026-09-24 · 数字取自当天的生产库与代码。
>
> **这份不重新设计。** [v4/06-认证与权限.md](./v4/06-认证与权限.md) §2.6 已经把员工登录
> 定死了：登录名、bcrypt cost 10、建号发一次性随机密码 + `must_change`、密码策略、
> 找回密码限流、改密踢会话。本文只回答三件它没回答的：
> **哪些已经有了 · 哪些是它假设而仓库里不存在的 · 按什么顺序做才不会把生产锁死**。
>
> 上游：[权限与菜单-用户角色资源统一方案.md](./权限与菜单-用户角色资源统一方案.md) P3。
> P3 的授权半已完成（`910cb39`）—— 会话角色来自员工档案；本文是认证那半。

---

## 1. 现状：生产只有一个共享口令

| 事实 | 值 |
|---|---|
| 生产登录 | 用户名**必须是** `admin`，口令来自配置 `sharehub.admin.password` |
| 员工档案 | 5 人，`iam_employee.user_id`（凭据引用）**全为 NULL** |
| 密码存储 | **不存在**。全仓库没有 `password_hash`、没有凭据表 |
| `pb_auth` / `cred_credential` | **只出现在注释与 javadoc 里**，从未建过 |

也就是说：**这个系统至今没有过一套密码凭据**。代理端走的是手机号 + OTP，
本来就没有密码；员工端走的是一个所有人共用的口令。

> ⚠️ 共享口令的三个后果，都不报错：审计里所有操作都署名 `admin`（`iam_audit_log`
> 的 actor 全是同一个人）· 无法按人停用 · 换人时要通知所有人改口令。
> 而 P3 的授权半刚打通「角色来自员工档案」——**档案认得出人了，登录还认不出**。

## 2. 已经有的（不用重建）

| 件 | 位置 | 说明 |
|---|---|---|
| **标识哈希** | `IdentifierHasher` + `sharehub.security.identity-pepper` | 生产已配（≥32 字符，缺了直接启动失败）。手机/邮箱 → `*_hash` 供等值查找 |
| **身份表的形状** | `agt_principal` | `phone_hash/mask/enc` · `email_hash/mask/enc` · `hash_ver` · `cred_ref` · `status`。**员工侧照抄这个形状即可**，不必另设计 |
| **会话与踢人** | `TokenStore.issue/revoke` · `StaffTokenAuthFilter` | 改密/停用后踢会话的底座已在 |
| **权限即时生效** | 口径 B（`PermVersion` + `PrincipalRefresher`） | 改角色不用重登，已有用例守 |
| **角色解析** | `EmployeeRoles`（P3 授权半） | 认得出员工就用档案上的角色 |
| **短信通道** | `NotifySendService` + 代理端 OTP 实跑 | 唯一**真的能送达**的通道 |
| **限流 / 不泄露存在性** | 代理端 `sendLoginOtp` | 查无此号也回成功，防手机号枚举。同一套思路直接复用 |

## 3. 缺的：三件，其中一件推翻了 v4/06 的假设

### 3.1 凭据表（要新建）

`cred_credential` 从来没建过。按 `agt_principal.cred_ref` 的既定引用关系建，
员工与代理**共用一张**（realm 区分），而不是各建一张 ——
两张表意味着两套密码策略、两套锁定逻辑，迟早只改了一边。

最小列：`cred_no` · `realm` · `subject_no` · `algo`(BCRYPT) · `hash` · `must_change` ·
`failed_count` · `locked_until` · `pwd_changed_at` · `status`。

### 3.2 员工身份列（要新建）

`iam_employee` 今天存的是**明文** `email` / `phone`，没有 hash。
登录要按 `email_hash` 等值查，所以要么加列、要么建 `staff_principal` 镜像 `agt_principal`。

**建议加列而不是建表**：员工与代理不同——代理的一个自然人可以属于多个主体
（ADR-030，所以需要 principal 这一层），而员工与档案是一对一。多一张表换不来东西。

> 生产的 5 个员工**邮箱和手机都有值**（`ali@sharehub.ae` 等），回填哈希不缺数据。

### 3.3 ⚠️ 邮件通道**不存在** —— 这条推翻了 v4/06 的两处流程

`EMAIL` 在仓库里只是 `NotifyTemplate` / `NotifyLog` 的一个枚举值，
**没有 SMTP、没有 MailSender、没有任何发件实现**。而 v4/06 §2.6 里两处依赖它：

| v4/06 写的 | 今天能不能做 |
|---|---|
| 建号「生成 12 位随机密码**一次性显示（或邮件）**」 | **能**（走「一次性显示」那一支，不需要邮件） |
| 找回密码 `/api/auth/password/forgot` → 重置码 | **不能** —— 重置码没有通道送达 |

所以找回密码三选一，**这是要拍板的第一件事**（见 §5）。

## 4. 实施顺序

每步能独立上线、独立回滚，且各配一条会红的测试。
**顺序的唯一约束：共享口令闸要活到最后一步之后**——
中间任何一步把它拿掉，生产就再也登不进去。

### B1 · 凭据底座（不改登录）
建 `cred_credential`；加 `iam_employee.email_hash/phone_hash/cred_ref`；回填 5 个员工的哈希。
`PasswordEncoder`（BCrypt cost 10）注册成 bean。**登录一行不改。**
- 卡口：回填后每个在职员工都有 `email_hash`；哈希与 `IdentifierHasher` 的结果一致。

### B2 · 建号与改密（还不能用来登录）
管理员在「员工」页建号：生成 12 位随机密码，**一次性显示**（不入日志、不入审计详情），
写 `must_change=1`。自助改密 `PUT /api/auth/password`。
- 卡口：随机密码不出现在任何日志/审计字段里；改密后该账号全部会话被踢
  （`TokenStore.revoke` 已有）；弱密码（<8 位 / 等于登录名）被拒。

### B3 · 员工密码登录（与共享口令闸**并存**）
`POST /api/auth/login` 增加一条分支：`identifier` 含 `@` 走 `email_hash`，
否则规范化后走 `phone_hash`；命中 → 校验 bcrypt → 角色走 `EmployeeRoles`（已完成）。
**共享口令闸保留**，两条路并行。
- 卡口：密码错 / 账号停用 / `must_change=1` 各自的响应可区分且**不泄露账号是否存在**；
  连续失败 N 次锁定；锁定期内即使密码正确也拒。
- 这一步之后，审计里的 actor 才第一次是真实的人。

### B4 · 找回密码（取决于 §5 的决策）

### B5 · 退役共享口令闸
全部员工都能用自己的账号登录之后，再把 `sharehub.admin.password` 那一支删掉。
- 卡口：删除后仍有至少一个 ADMIN 账号可登录（否则就是把自己锁在门外）。

## 5. 三个决策（2026-09-25 已拍板）

### 5.1 找回密码 → 短信 OTP，管理员重置作兜底

选 §3.3 的 (a)。(c) 先接邮件被否：`EMAIL` 在本仓库只是 `NotifyTemplate` /
`NotifyLog` 的一个枚举值，**没有 SMTP、没有 MailSender、没有任何发件实现**，
接它等于多一个外部依赖 + 一套模板 + 送达率问题；而短信通道代理端已在生产上跑。
(b) 只允许管理员重置被否为**唯一**通道（管理员不在时没人能自救），但保留为兜底 ——
换了手机号的人自救不了，而 B2「建号发一次性随机密码」那条路本就支持重置。

**复用现成参数，不新造一组**（`OtpService` 的构造参数，见
`sharehub-svc-core/.../user/consumer/OtpService.java`）：

```
sharehub.auth.otp.ttl=5m · resend-interval=60s · max-attempts=5
```

再加 v4/06 §2.6 已写死的「每账号每小时 5 次」。**查无此号也回成功**
（防账号枚举）—— 代理端 `sendLoginOtp` 已是这个思路，照抄。

### 5.2 登录名 → 邮箱与手机都能登

一个 `identifier` 字段：含 `@` 走 `email_hash`，否则规范化后走 `phone_hash`。

v4/06 写「员工必须邮箱」，但 5.1 选了短信找回就必须有手机。生产 5 个员工
**邮箱和手机都有值**（§3.2），回填哈希不缺数据。与代理端同一套判定，少一套心智。

### 5.3 锁定策略

| 项 | 取值 | 为什么这么定 |
|---|---|---|
| 账号连续失败 | **5 次 → 锁 15 分钟** | 与 `otp.max-attempts=5` 同口径，避免库里出现两套数字 |
| 锁定期内 | **密码正确也拒** | 否则锁了等于没锁 |
| IP 维度 | 每小时 **20 次**失败 | 单账号限流拦不住横向撞库 |
| 失败响应 | 密码错 / 账号不存在 / 已停用 **同一句话、同一状态码** | 区分了就是一台账号枚举器 |
| `must_change` | **登录成功后**才暴露 | 它泄露「这个账号存在且是新建的」 |

参数走 `sharehub.auth.staff.*`，**不写死** —— 上线后大概率要调。

> 这三条落进 B3 的卡口（§4）：密码错 / 停用 / `must_change` 各自的响应
> 可区分且不泄露账号是否存在 · 连续失败 N 次锁定 · 锁定期内密码正确也拒。

## 6. 风险

- **把自己锁在门外**是这件事唯一的严重风险。所以共享口令闸活到 B5，
  且 B5 的卡口就是「删掉之后还登得进去」。
- **一次性密码的显示**：只在建号响应里返回一次。
  要专门验它不进日志、不进审计详情 —— 审计记的是「谁给谁建了号」，不是密码。
- **pepper 不可轮换**：`identity-pepper` 一旦用于哈希真实邮箱/手机，换 pepper
  等于所有人登不进去（这条在腾讯云部署记录里已经记过）。B1 回填前要确认它不再变。
