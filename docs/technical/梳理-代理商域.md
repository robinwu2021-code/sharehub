> 2026-09-26 梳理。依据 [ADR-012](ADR/ADR-012-代理商模型.md)（体内经营伙伴，非租户）、
> [ADR-027](ADR/)（站点责任行）、[ADR-030](ADR/)（自然人 × 主体）。
>
> **§四那条已修**（2026-09-26，V123 + `POST /agents/{no}/login-account`）：
> 运营端建出来的代理商此前**没有人能登录**，两个入口都断在同一处。
> 下文保留了问题的原貌，因为它是这一族缺陷最典型的形态：**功能齐全、整条链不通、两处都不报错**。

## 〇、三层身份模型（理解其余部分的前提）

```
agt_principal（自然人 · 一个人一行 · 一套 cred_ref）
      ↕  N:M，关系行 = agt_account（is_owner / is_primary / display_name）
agt_agent（运营主体 · 一家公司一行）
```

`agt_account` **不是登录账号**，是「这个人是这家主体的成员」这条关系。
一个人可以是多家主体的成员（ADR-030），登录后在顶栏切换。

三列分工必须守住（V47 的注释）：

| 列 | 用途 |
|---|---|
| `*_hash` | HMAC(规范化值, pepper)，**登录查找 + 唯一约束** |
| `*_mask` | **只用于显示**，绝不进唯一键、绝不做等值条件 |
| `*_enc` | 需要还原时（发短信/邮件）；pepper 轮换时重算 hash 的唯一依据 |

> 为什么不是「给 `agt_account` 加两列」：掩码不可逆，`13800138000` 与 `13811138000`
> 的掩码都是 `138****8000` —— 拿它做唯一键会把两个人判成同一个。

## 一、表

| 表 | 用途 | 关键点 |

### 归属锚点链（自上而下回填）

```
loc_site.agent_no（权威，空 = 平台直营）
  → loc_location.agent_no
    → dev_cabinet.agent_no
      → ord_rent.agent_no / wo_order.agent_no
```

⚠️ **订单与工单的 `agent_no` 是下单/开单时刻的快照，不随划拨回溯**。
站点转手后历史单仍归老代理可见 —— 否则会与已生成的 `share_record` 对不上。

财务四张表（`share_record` / `stl_settlement` / `stl_withdrawal` / `stl_payout_account`）
的 `agent_no` 是**生成列**（`payee_type='AGENT'` 时取 `payee_no`）——
用生成列而不是同步逻辑，因为同步漏一处就是静默的越权可见。

## 三、依赖项（代理商要能工作，先得有什么）

### 建档两条路

| | 路径 | 产出 | 能登录吗 |
|---|---|---|---|
| A | 入驻申请（自助 / 代建录入）→ 受理 → 审核通过 → `activate()` | agent + principal + account **一个事务** | ✅ |
| ~~B~~ | ~~运营端直连建档~~ | **2026-09-26 收掉** —— 见 §八 | — |

档案行上的「开通登录」仍在：它补的是**存量**代理商（审核流之前建的那些）
与「同一个人再服务一家主体」的情形。

路 A 的前置：手机号 + 邮箱（都必填）· 自助还要过 OTP · 同手机号无在途申请。

### 划拨资产的前置
1. 代理**存在**（不存在 → 资产变孤儿：冗余列写进去了，没有任何账号的数据范围匹配得到）
2. ASSIGN 要求 `status = ENABLED`；REVOKE 不要求（停用的代理要能收回资产）
3. 目标对象在**当前操作者数据范围内可见** —— 这既是存在性检查也是授权闸

### 分润真正依赖什么（链条最长，也最容易配错）

```
loc_site_agent 责任行（INVEST/DEVELOP/OPERATE/REFER）   ← 优先
   ↓ 没配责任行才回落
share_rule(AGENT, agent_no, basis='OPERATE')          ← 再找不到退回通用规则
   ↓ OPERATE 份额还要乘
agt_ops_assessment.coefficient（上月考核，没考核按 1）
   ↓ 系数分档依赖
sys_param: agent.ops.coef.{full_rate,mid,mid_rate,low}
   ↓ 考核本身依赖
wo_order + wo_sla + dev_cabinet.online_status + cs_ticket
```

> ⚠️ **运营端「分润配置」tab 写的是 `agt_commission`，而分润生成读的是
> `share_rule` + `loc_site_agent`。配了不生效，且不报错。**
> 这是本域最值钱的一条待办。

### 清退的三步门禁（每步全为 0 才能推进，`advance()` 会重算不信前端）

| 步 | 要清空什么 |
|---|---|
| RECLAIMING | 未关闭的归属站点 · 生效中的责任行 · 未退役的归属机柜 · 未完结的代理工单 |
| SETTLING | PENDING 分润 · 未打款结算单 · 在途提现 |
| CLOSING | 无门禁，推进即终局（停用全部账号 + 归档主体） |

## 四、⚠️ 最要紧的缺口：建出来的代理商没人能登录

登录链是 `phone → agt_principal.phone_hash → agt_account.principal_no → agent_no`。
而**两个运营端入口都不产生 `principal_no`**：

- **「新增代理商」** 只写 `agt_agent`，principal 与 account 一行都不建；
- **「新增代理账号」** `beforeCreate` 只要求 `agentNo`，**从不设 `principal_no`** ——
  行建出来了、列表里看得见，登录时按 principal 查不到它。

于是运营能建代理商、能给它开账号、能划拨资产、能配分润，
**唯独那个代理商自己永远进不来**。两处都不报错。

正确的做法已经写在 `ApplyServiceImpl.activate()` 的 ②③ 步里
（按 `phone_hash` 查自然人、命中则复用且绝不动 `cred_ref`；
`is_primary` 只给这个人的第一个主体）。解法是**把那段抽出来复用**，
不是再写一份 —— 两份实现意味着「在哪个入口建的，决定他能不能登录」。

### 配套前置：主体档案上得有手机号

`agt_agent` 原先只有一个自由文本 `contact`，生产 9 条里**全是纯手机号**
（没有姓名、没有邮箱）。要从档案开通登录，就得有结构化的手机号与邮箱 ——
这是 V123 拆 `contact_name` / `phone` / `email` 的直接原因。

> **档案上的手机号 ≠ 登录身份**。前者是「找这家公司谈事、发对账单」用的业务联系方式，
> 后者是 `agt_principal` 的 hash。开通登录时把前者**灌进**后者，
> 之后两者各走各的：改档案电话不会改登录方式（改登录方式要走换绑，另一条流程）。

## 五、关联项（谁会因为代理商而变）

### 事件

| 事件 | 发布 | 订阅 → 后果 |
|---|---|---|
| `AgentStatusChangedEvent` | 档案改状态 · 发起清退 | 停用时**名下未完结工单改派平台**（落不到员工就按区域负载找运维），`REQUIRES_NEW` + 靠 outbox 重投 |
| `AssetAssignedEvent` | 划拨回写归属 | 回写 `dev_cabinet.agent_no`（跨模块，最终一致；有 `OwnershipReconciler` 扫 outbox 补投） |

> 机柜不在同一事务里：`dev_cabinet` 归 core，platform 的事务不该跨到 core 的表。
> 划拨是低频运营动作，秒级最终一致可接受。

### 非事件的实时联动

- **提现冻结**：按**实时状态**拦，不靠事件。挡申请/审批/确认打款，驳回照常。
  ⚠️ **清退 SETTLING 例外** —— 这一步就是要把钱结给它，冻着就永远结不清。
- **不许改回启用**（清退中）· **不许划入资产**（非 ENABLED）—— 两条都在服务端，
  前端按钮禁用只是体验层。
- **告警** `AGENT_SLA_BELOW`；**平台接管**记 `taken_over_from`，计入下月考核。

### 数据范围

`DataScopeRegistration` 为约 20 张表注册了 AGENT 维度。
`agent_no IS NULL` = 平台直营，`IN(...)` 天然不匹配 NULL —— 代理看不到直营资产。

⚠️ `agt_account` / `agt_agent` / `agt_agent_region` / `agt_assignment` / `agt_commission`
/ `loc_site_agent` **有 `agent_no` 列但未注册数据范围**（已登记在
`known-unscoped-owned-tables.txt`，理由是这些表业务上没有站点/区域归属，
只登记 AGENT 维度会让 SITE 收敛后归零）。

## 七、第 1 条的落地（2026-09-26）

| | |
|---|---|
| V123 | `agt_agent` 拆出 `contact_name` / `phone` / `email`；存量 9 条纯手机号搬进 `phone`，`contact` 退役（形状不明的留着待人工归位，**不删列**） |
| 服务 | `AgentMembershipService.grantOwner()` —— 自然人 + 成员关系的**唯一**建立点，从 `ApplyServiceImpl.activate()` 的 ②③ 步抽出来，入驻审核那条路与运营端复用同一份实现 |
| 端点 | `POST /api/agent/agents/{agentNo}/login-account`，判 `agent:account:manage`（实质是「开一个能登录的账号」，与改档案是两种授权） |
| 界面 | 档案行上的「开通登录」；缺手机或邮箱时**禁用并在 title 里说缺哪个** |

**手机号与邮箱两个都要**，不是二选一：`agt_principal` 的 `phone_hash` 与 `email_hash`
都是 NOT NULL + UNIQUE —— 自然人有两个登录标识，缺一个这行建不出来。
这与入驻申请一致（那边本来就两者必填）。

**幂等**：重复开通返回既有的成员关系号。库上有 `uk_agt_account_member` 兜底，
但撞唯一键是 500，而重复点「开通登录」是个正常操作。

**同一个人服务两家主体**：按 `phone_hash` 复用同一个自然人，**绝不动 `cred_ref`**
（一个人一套密码，在这里顺手重置等于改了他在别家主体的登录）；
`is_primary` 只给他的第一个主体 —— 两个 `is_primary=1` 时登录后进哪家是不确定的。

> ⚠️ **档案手机 ≠ 登录方式**。开通时把前者灌进后者一次，此后各走各的：
> 改档案电话不会改登录方式（改登录要走换绑，另一条流程，尚未建）。

## 八、建档一律走审核（2026-09-26 裁决）

**裁决**：不论代理商自助注册还是运营端代录，都要过审核。

### 收掉了什么

`POST /api/agent/agents`（直连建档）。它建出来就是 `ENABLED`、立刻能被划拨资产、
配分润，**全程零审核** —— 而同一个系统里入驻那条路刻意把「录入」
（`agent:apply:create`）与「放行」（`agent:apply:approve`）分成两个码来立四眼。

两条路的治理强度差这么多**不是设计**：直连那条先存在、审核流后补，
没人回头看过它们的关系。

### 补上了什么

**四眼真正生效**：审核时拦「审核人 = 录入人」。
此前只是分了码，而生产里 BD 持的是 `agent:*` 通配，两个码它都有 ——
**分码等于没分**，控制器注释里那句「四眼原则以后有落脚点」一直是许愿。
只拦代建（`submitted_by` 存员工号）；自助提交那一路 `submitted_by`
存的是手机号哈希前缀，不会与任何员工号相等，天然不受影响。

### 权限码的连带

`agent:agent:create` 随之**退役**（V125 从目录删除，真源表同步）。
留着的后果不是报错，是管理员勾了它却什么也没发生 —— 与 V116 收拾的三个工单码同一类。

> ⚠️ 这个码一天之内走完了「声明未强制 → 补上强制 → 补进目录 → 整条路撤掉 → 从目录删除」。
> 值得记一句：**先确认这条路该不该存在，再去补它的权限码**，
> 否则补得越完整，撤的时候要退的东西越多。

### 没有动的

**改档那条路仍可 upsert**：`POST /agents/{agentNo}` 打一个不存在的编号会建出来。
其它用例靠它建可读的夹具号（`AG-RBAC-ADMIN` / `AG-E2E-GULF`），本次沿用。
它需要 `agent:agent:update`，不是零门槛，但严格说这是审核流的一个旁路 ——
要堵得先把那些夹具改掉，属另一批。

## 九、取号撞唯一键（2026-09-26 生产实测）

§八 上线后跑真实流程，走到「他人放行」那一步**生产 500**：

```
Duplicate entry 'AG010' for key 'uk_agent_no'
```

而运营台的代理商列表里**完全看不到 AG010**。两件事撞在一起：

| | |
|---|---|
| `uk_agent_no` **不含 `deleted` 列** | 这是对的 —— 软删/归档掉的编号被合同、结算、划拨记录引用着，不能被重新发出去 |
| 取号用 MyBatis-Plus 的 `QueryWrapper` 取 `MAX` | `@TableLogic` 自动补上 `deleted = 0`，**取号看不见那些行** |

于是**只要有一个代理被归档，它的号就变成一个洞**，下一次取号必然走进去。
症状极具欺骗性：审核通过报 500，而列表看上去一切正常（那一行被逻辑删除藏起来了），
于是第一反应会往审核逻辑、往事务、往权限上找。

**修**：`BizNoSequence.next()` 改走**原生 SQL**，不经 mapper ——
要的就是「连软删的一起算」这个语义，而它必须是显式的、不可能被某个拦截器悄悄改掉。
用例 `AgentCreateTest#soft_deleted_numbers_still_occupy_the_unique_key` 钉住：
先造一个「软删掉的下一个号」，再走完整审核流，断言取到的号跳过了它。
负对照（把 `deleted = 0` 加回去）确认只有这一条红。

### 同一个洞还在别处

`AbstractCrudService#nextNo` 走的是同一条错路，而基类的 `remove()` 正是软删。
21 个实体覆盖它的 `keyPrefix()` 用前缀取号（员工、部门、券模板、价格方案、
告警规则、巡检计划…）—— **删掉一个员工，下一次新建员工就撞唯一键 500**。
同一个病，只是还没被点到。
