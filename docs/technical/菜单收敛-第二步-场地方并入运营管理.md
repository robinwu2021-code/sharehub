## 零、为什么现在必须做

第一步把「站点管理」并进了运营管理，于是：

```
站点与点位          ← 名字里的「站点」已经不在这里了
├ 场地资产   点位管理 · 站点坪效
└ 场地方机构 场地方 · 进场合同 · 门店 Onboarding · 门店生命周期 · BD 拓展 CRM
```

**一个叫「站点与点位」的菜单里没有站点**，这是第一步留下的欠账，不能放着。
收口只有两个方向：给它改个名继续独立，或者整个撤掉并进运营管理。

## 一、方案：撤销这个 L1，七项全并入运营管理

### 1.1 目标结构

```
运营管理
├ 场站管理    站点概览 · 站点管理 · 点位管理
├ 场地与合同  场地方 · 进场合同
├ 拓展        BD 拓展 CRM · 门店 Onboarding(L2) · 门店生命周期(L3)
├ 计费与调价  收费方案 · 预约调价
├ 基础管理    应用版本 · 银行管理 · 问题管理
├ 公告管理    公告管理
└ 场站报表    站点分成 · 分成方分成 · 站点坪效(L3)
```

17 个叶子 / 7 个分组。L1 从 16 个降到 **15** 个。

### 1.2 为什么不是拆一个「场地方管理」L1

原方案（本文之前的第 2 步）打算把场地方机构独立成 L1，与「代理商管理」对称 ——
两类合作主体，一个给地、一个出钱。**论实体分类它是对的，论走路它是错的**：

- **BD 已经住在运营管理里**。现在 BD 角色在运营管理能看到 站点概览 / 站点管理 /
  站点分成 / 分成方分成 / 公告管理 五项。它的完整动线是
  「线索 → 进件 → 签约 → 建站点 → 配收费方案 → 看分成」——
  独立成 L1 只会把这条动线从头切成两段。
- **站点与场地方本来就是一个抽屉里的事**。站点详情已经有「合同」页签，
  建站点时「场地方」是必选下拉。分成两个 L1，等于让人在两个一级菜单之间核对同一件事。
- 对称性是给**看结构的人**的，不是给**干活的人**的。代理商独立成 L1 的理由不是
  「它是一类主体」，而是它有自己的账号体系、划拨、结算、绩效 —— 一整套只属于它的操作。
  场地方没有这一套，它的全部操作都挂在站点上。

### 1.3 关键实现点：**只改菜单，不搬页面**

`/locations` 这个页面**一行不动**，URL 也不变。要改的只有三处：

| 改什么 | 怎么改 |
|---|---|
| `lib/nav.ts` | 删掉 `key: "location"` 这个 section；七条叶子按新分组挂到 `operation` 的 `children` 后面（保持 `/locations?tab=…` 原 href） |
| `operation` 的 `match` | `["/operation"]` → `["/operation", "/locations"]`，让 `/locations` 归属运营管理（面包屑、Rail 高亮按它走） |
| `children` 的构造 | 现在是 `opLeaves([...])`；改成 `[...opLeaves([...]), ...普通叶子]` —— 场地方那几条不是 `/operation/<page>`，不走 backend-ready 灰显 |

这三处都在 `nav.ts` 一个文件里。**页面代码零改动**，因为：

- `useNavTabs("/locations", TAB_KEYS)` 按「命中本页 tab 最多的 section」取名
  （`resolveTabs` 的评分规则），叶子挪到运营管理后它会自然找到那边；
- `findActiveSection` 按**最长前缀**匹配 `match`，加一个 `/locations` 前缀即可；
- 跨 section 深链本来就是既有能力（代理商 ↔ 财务两条就是）。

> 将来若要把这些页面真正搬到 `/operation/*` 下，是独立的一次重构，
> 与菜单收敛无关，**不要混在一起做** —— 那会把一次 nav 改动变成七个页面的大搬家。

### 1.4 连带影响

| 影响 | 说明 |
|---|---|
| L1 基线 16 → 15 | `nav.test.ts` 的 `L1_KEYS` 要显式改，`NAV.filter(!portalFor)` 的 16 改 15 |
| 叶子五元组 | 七条的 `group` 字段全变（`场地资产`/`场地方机构` → 新分组名），基线逐条更新 |
| 角色可见性 | 有 `location:*` 的角色（ADMIN / BD / OPS / VIEWER 按各自权限码）在运营管理多看到这七项；**没有任何角色因此多得到或少掉权限**，`perm` 一个不改 |
| 运营管理成为最大的 L1 | 17 叶，超过系统设置的 13。这是本方案唯一的实质代价，见下 |
| `sec("location")` 的用例 | `nav.test.ts` 里有几处直接按 key 取这个 section，要改成从 `operation` 取 |

## 二、唯一的实质代价：二级面板变长

17 叶 + 7 个分组标题 ≈ 24 行，按实测每行约 30px 算 ≈ 720px。
**在 800px 高的窗口上会需要滚动**（面板本身可滚，不是截断）。

三个可选的减负手段，按推荐顺序：

1. **把「公告管理」并进「基础管理」**（4 项：应用版本 · 银行 · 问题 · 公告）。
   少一个只有一条叶子、且名字与叶子完全相同的分组。7 组 → 6 组。
2. **「拓展」组的两条 L2/L3 叶子本来就是灰的**（门店 Onboarding / 门店生命周期），
   可以等它们真正就绪再挂出来，先只留 BD 拓展 CRM。17 叶 → 15 叶。
3. 不动。面板可滚，且运营管理本来就是这个产品的主场，重一点是合理的。

我建议 **1 + 3**：并掉那个单叶分组，其余不动。第 2 条会让「这个功能存不存在」变得不可见，
与 `soon`/`phase` 灰显机制想达到的效果相反。

> **落地后实测**：按 1+3 做完是 17 叶 / 6 组，在 648px 高的内容区里**一屏放得下**，
> 没有出现预估的滚动。前面 720px 的估算偏保守（按每行 30px 算，实际分组标题行更矮）。

## 六、落地结果（2026-09-23）

```
运营管理  match: ["/operation", "/locations"]
├ 场站管理    站点概览 · 站点管理 · 点位管理
├ 场地与合同  场地方 · 进场合同
├ 拓展        BD 拓展 CRM · 门店 Onboarding(L2) · 门店生命周期(L3)
├ 计费与调价  收费方案 · 预约调价
├ 基础管理    应用版本 · 银行管理 · 问题管理 · 公告管理
└ 场站报表    站点分成 · 分成方分成 · 站点坪效(L3)
```

17 叶 / 6 组，L1 16 → **15**。页面代码只动了一处：`/locations` 的 `TAB_KEYS` 顺序
调成与菜单分组一致（页内 tab 条和二级面板是同一批东西，两处顺序不同会让人以为少了一项）。

**顺带修掉一个越权可见**：「BD 拓展 CRM」此前**没有 perm**，靠跟随 section 可见。
在原来的「站点与点位」下这还说得过去，并进跨模块的运营管理后，
客服（凭 `system`/`marketing` 模块进得来）会看到 BD 的线索池。
已补 `location:lead:read`（功能权限清单 §BD CRM 有登记，BD 靠 `location:*` 命中），
同时 OPS / VIEWER / FINANCE 也不再看到它 —— 这是收紧，不是回归。

实测面包屑：
- `/locations` → 运营管理 › 场站管理 › 点位管理
- `/locations?tab=venues` → 运营管理 › 场地与合同 › 场地方
- `/locations?tab=crm` → 运营管理 › 拓展 › BD 拓展 CRM
- `/locations?tab=contracts` → 运营管理 › 场地与合同 › 进场合同
