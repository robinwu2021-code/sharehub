# 业务模块分层

> **本文件由脚本生成，不要手改** —— `python3 backend/scripts/module-graph.py`。
>
> 模块划分与语义分层是**人定的**（写在脚本的 `MODULES` / `NAMED_LAYERS` 里，每条都有理由）；依赖关系与校验结论是**算出来的**。

## 这份图凭什么可信

架构分层图最容易变成「画得很整齐但和代码没关系」的装饰品。这份图用三条硬约束顶住：

| 约束 | 怎么保证 | 当前结果 |
|---|---|---|
| 每张表都必须归属某个模块 | 脚本报落单表 | **144 张表全部归位，0 落单** |
| 依赖关系必须有证据 | 用列名引用推导（`ord_rent.cabinet_no` = 订单依赖设备），每条边都能追到具体列 | 49 条依赖边 |
| 分层不允许反向依赖 | 拓扑校验，下层依赖上层即报错 | **0 处违规**（见下） |

**局限**（否则会高估这份图）：本库无外键约束，依赖靠命名约定推断；JSON 里的软引用抓不到；快照字段（如 `payee_name`）不算依赖 —— 它是拷贝不是引用。

## 分层总览

```
L0 平台底座        租户  认证授权  审计  主数据  数据字典  系统参数  通知  开放平台  支付渠道  厂商目录
L1 主体与资源       组织架构  代理商  消费者  权益与营销  场地拓展  场地与点位  设备资产  固件  库存  资产归属
L2 运行管理        告警  工单  设备接入
L3 交易          计价  订单  支付
L4 资金          账务  分润  结算提现  发票  对账
L5 服务          客服
```

**层间规则**：模块只能依赖**同层或更低层**。层内可互相依赖（如「库存」依赖「设备资产」，同属 L1）。

- **L0 平台底座** — 与业务无关的能力与目录。被所有层依赖，不依赖任何业务模块。
- **L1 主体与资源** — 经营的「人」与「物」：谁在经营（组织/代理）、服务谁（消费者）、用什么经营（场地/设备/库存）。层内可互相依赖。
- **L2 运行管理** — 让资源转起来：设备联通、异常发现、人工处置。
- **L3 交易** — 一次租借的完整生命周期。
- **L4 资金** — 钱怎么记、怎么分、怎么结、怎么核。全部在交易之后。
- **L5 服务** — 售后与人工介入，跨交易与运行两层取数。

## ⚠️ 跨域重名的业务键（6 个）

同一个列名在不同域指向**不同实体**。这不只是文档问题：联表、排错、以及任何按列名做的自动化（包括本脚本）都会认错。

本脚本已把它们排除出依赖推导 —— 但代价是这些真实依赖**推不出来**，所以下面的依赖图在这几处是偏保守的。

| 列名 | 被哪些模块各自定义 |
|---|---|
| `account_no` | 代理商 / 账务 |
| `invoice_no` | 发票 / 消费者 |
| `order_no` | 支付 / 订单 |
| `plan_no` | 权益与营销 / 计价 |
| `refund_no` | 支付 / 订单 |
| `rule_no` | 分润 / 计价 |

## 模块清单


### L0 平台底座

#### 租户

多租户隔离的锚点；单运营方下休眠但不删（ADR-011）

依赖：无（底座模块）

表 2 张：`tenant` · `tenant_config`

#### 认证授权

RBAC 与数据范围。**不含 sys_token** —— 会话令牌是基础设施（见 INFRA_TABLES），归在这里会让「登录」凭空跨服务边界

依赖：无（底座模块）

表 5 张：`iam_data_scope` · `iam_menu` · `iam_permission` · `iam_role` · `iam_role_perm`

#### 审计

WORM 留痕，只写不改

依赖：无（底座模块）

表 1 张：`iam_audit_log`

#### 主数据

银行/地区/国家/问题目录 —— 全局共享，无租户列

依赖：无（底座模块）

表 5 张：`md_bank` · `md_device_type` · `md_market_country` · `md_problem` · `md_region`

#### 数据字典

可运营配置的枚举，避免硬编码发版

依赖：无（底座模块）

表 1 张：`dict_item`

#### 系统参数

业务规则/税率/登录策略/应用版本

依赖：无（底座模块）

表 6 张：`sys_app_version` · `sys_biz_rule` · `sys_login_setting` · `sys_outbox` · `sys_param` · `sys_tax_setting`

#### 通知

模板 · 发送日志 · 退订黑名单；被所有层调用

依赖：无（底座模块）

表 3 张：`notify_blacklist` · `notify_log` · `notify_template`

#### 开放平台

对外 API 应用与密钥

依赖：无（底座模块）

表 1 张：`openapi_app`

#### 支付渠道

支付渠道及其适用范围 —— 配置，不是流水。**与「支付」分开**：充值单引用渠道(`usr_recharge_order.channel_code`)、支付流水引用消费者(`pay_order.c_user_no`)，混在一个模块里就成了 消费者↔支付 的环。
这是本图第三次出现同一个模式：**目录/配置与运行时流水必须分模块**（另两处：厂商目录 vs 网关运行时、计价方案 vs 订单）

依赖：无（底座模块）

表 2 张：`pay_channel` · `pay_channel_scope`

#### 厂商目录

设备厂商及其接入配置。**与「设备接入」分开**：厂商是主数据（机柜的一个属性，`dev_cabinet.vendor_code` 引用它），报文日志是运行时产物（引用机柜）——混在一个模块里会让「设备资产」与「设备接入」互相依赖，算出一个真环

依赖：无（底座模块）

表 2 张：`gw_vendor` · `gw_vendor_config`


### L1 主体与资源

#### 组织架构

部门树与员工归属 —— 与「认证授权」分开：组织是业务概念（谁向谁汇报、按部门看数），RBAC 是基础设施
