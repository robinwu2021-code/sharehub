## 二、A 组 · 状态机闭合（先做，因为它是卡口）

### ✅ 已完成（2026-09-25）· A1 · 6 个状态机内部收敛到 enum —— **它现在正从棘轮盲区里漏过去**

**发现**：8 个状态机里只有 `Wo` / `Alarm` 用了 enum，其余 6 个
（`Powerbank` `InvTransfer` `Ord` `Campaign` `Settlement` `Withdrawal`）**状态仍是裸字符串**：

```java
// SettlementStateMachine —— SettlementStatus 这个 enum 早就存在，这里没用
"CONFIRM", Map.of("GEN", "CONFIRMED"),
```

**为什么棘轮没拦住**：`BareStatusLiteralRatchetTest` 锚在**用法**上
——「字段名以 `Status`/`Type`/`Level`/`Action`/`Mode` 结尾」。而
`Map.of("GEN", "CONFIRMED")` 里没有字段名，于是整类漏检。
**状态机是最不该漏的那一处**：它是这个对象合法状态的定义处。

**技术方案**：机械替换，6 个文件，`XxxStatus` 枚举全部已存在（`SettlementStatus`
`WithdrawalStatus` `PowerbankStatus` `PriceAdjustmentStatus` … 共 34 个）。
`InvTransfer` 需确认是否有对应 enum，没有则新建（照 `AlarmStatus` 的形状）。
出入参保持 `String`（`next(String from, String event)`），只把**字面量的来源**收敛
—— 与 §3.4 已落地的那一轮同一口径，不牵动 MyBatis 类型处理器。

**顺带**：给 `BareStatusLiteralRatchetTest` 加第二个锚点 —— `*StateMachine.java` 内的
所有大写字符串字面量一律计入。补完 A1 后该锚点基线为 0，**零容忍不设台账**。

**验收**：6 个文件内 `grep -E '"[A-Z_]{2,}"'` 只剩事件名（事件是动词，本就该是字符串
—— 见 `WoStateMachine` 注释「状态是名词、事件是动词，类型不同让两者无法被混为一谈」）。

**工作量**：半天。

### ✅ 已完成（2026-09-25）· A2 · 边的跨端卡口（第 6 个检查器）—— **词表卡住了，边没有**

**现状**：`StatusVocabularyAcrossEndsTest` 比的是**节点集**（这个对象有哪些状态），
两端已经一字不差。**没有任何检查比较边**（从哪能到哪）。

**代价是不对称的**：

| 分叉方向 | 症状 | 严重度 |
|---|---|---|
| 前端边**比后端宽** | 按钮亮着，点了报错 | 吵，但安全 |
| 前端边**比后端窄** | **按钮灰着，而接口放行** | 静默失能 |

后者已经发生过：前端把 `accept` 写成 `→PROCESSING`，后端落 `ACCEPTED`，
于是没有任何动作的 `from` 含 `ACCEPTED` —— **那张工单界面上一个按钮都没有**，
处理/完工/驳回全部消失，且不报错。是人肉发现的。

**技术方案** —— `StateMachineEdgeAcrossEndsTest`，照 `AcrossEnds` 同款（自动发现，不靠人登记）：

1. **后端侧**：扫 `*StateMachine.java` 的 `Map.of("EVENT", Map.of(FROM, TO, …))`
   → 边集 `{(from, to)}`。**A1 是前置条件**：状态是 enum 常量才能稳定解析。
2. **前端侧**：扫 `ops-web/lib/types/*.ts` 的
   `export const X_TRANSITIONS: Record<A, { from: readonly S[]; to: S }>`
   → 边集 `{(from, to)}`。
3. **配对靠状态类型名，不靠状态机名**（`WoStateMachine` vs `WO_TRANSITIONS` 机械对不上）：
   前端表的类型注解里写着 `from: readonly WorkOrderStatus[]`，后端状态机 A1 之后
   引用的是 `WorkOrderStatus` —— 而这两个同名词表 `AcrossEnds` 已经保证一字不差，
   **拿它当主键是安全的**。
4. **不比事件名**：后端 `"ACCEPT"`/`"DONE"`，前端 `accept`/`complete` —— 事件名是各端
   的词汇，不是契约。只比 `(from, to)`。

**两个方向分别断言**（严宽不同，这是设计要点）：

- **方向一（零容忍）**：前端每条边，后端必须**可达**。
  注意是**可达**不是**存在** —— 工单 `close` 前端是 `DONE→CLOSED`，后端是
  `DONE→AUDITED→CLOSED` 两跳，这是**合法的复合边**（AUDITED 是过程态，不单独出按钮）。
  要求存在就会误报，所以用后端边集的**传递闭包**判定。
- **方向二（带台账）**：后端每条 `from` 为**用户可见态**的边，前端应有对应动作；
  差异登记进 `known-missing-ui-transitions.txt`，只准变短。
  首批入账的就是 A3 那 5 个 —— 它们现在是"页面手写 if"，卡口一立就显形。

**验收**：两向对照 —— 先把 `WO_TRANSITIONS` 的 `accept` 改回 `→PROCESSING`，必须红；
改回来必须绿。

> **2026-09-25 实测修正**：红的是**方向二**，不是方向一。方向一用传递闭包，
> 而后端 `DISPATCHED→ACCEPTED→PROCESSING` 的闭包里就有 `DISPATCHED→PROCESSING`，
> 所以它"可达"、方向一照样绿；红的是后端 `DISPATCHED→ACCEPTED` 在运营端再也走不出来。
> **推论**：方向一宽容，所以更严重的那一类失效落在方向二的台账上 ——
> 台账不是"软的那一条"。

**工作量**：1–1.5 天（测试类约 300 行 + 台账）。

> **位置修正**：不接进 `check:drift`（那条链是纯 python 检查器）。边卡口与它的同类
> `StatusVocabularyAcrossEndsTest` 一样是 JUnit 架构测试，跑在 `mvn test` 里 ——
> 同一类东西放同一个地方，否则下一个人会问「为什么词表卡口在这边、边卡口在那边」。

#### A3-1 · 提现 `WITHDRAW_TRANSITIONS`（最值钱，且无阻塞）

**现状**：[`finance/page.tsx:785`](../../ops-web/app/finance/page.tsx#L785) 手写
`(w.status === "AUDIT" || w.status === "APPLY")` —— 正是 `WithdrawalStateMachine`
的 `APPROVE` from 集抄了一份；而 `canPayWithdrawal` 是**另一处**孤立的
`status === "PAYING"`，与那份抄件毫无关系。两处各自为政。

**一个坑，先说**：打款端点是**一个动作两条边** ——
[`WithdrawalServiceImpl:190`](../../backend/sharehub-svc-finance/src/main/java/ai/neargo/sharehub/finance/service/impl/WithdrawalServiceImpl.java#L190)
是 `stateMachine.next(status, ok ? "PAY" : "FAIL")`：登记回执时填成功就
`PAYING→PAID`，填失败就 `PAYING→FAILED`。
所以表的形状**不能**是 `{ from, to }` 一对一。审核端点同样如此（approve/reject）。

**方案**：拆成四个动作，一个动作一个 `to` —— 与 `RECON_TRANSITIONS` 同一套写法
（那张表四个动作各自带 `result`，正是为了这个）：

```ts
export type WithdrawAction = "approve" | "reject" | "pay" | "payFail";
export const WITHDRAW_TRANSITIONS: Record<WithdrawAction,
    { from: readonly WithdrawalStatus[]; to: WithdrawalStatus; label: string }> = {
  approve: { from: ["APPLY", "AUDIT"], to: "PAYING", label: "审核通过" },
  reject:  { from: ["APPLY", "AUDIT"], to: "FAILED", label: "驳回" },
  pay:     { from: ["PAYING"], to: "PAID",   label: "登记打款回执" },
  payFail: { from: ["PAYING"], to: "FAILED", label: "登记打款失败" },
};
```

`approve`/`reject` 共用 `auditWithdrawal(no, approve, …)` 一个端点，
`pay`/`payFail` 共用 `payWithdrawal(no, body)` —— **动作是 UI 概念、端点是传输概念**，
不必一一对应。页面按钮出不出由 `canWithdrawAction()` 决定，两处手写的 if 一起删掉。

**权限码**（已核，都在[真源表](../requirements/功能权限清单.md)里，不新造）：
`finance:withdrawal:audit` · `finance:withdrawal:pay`。

**台账**：删 6 条，**留 `APPLY->AUDIT`** —— 那是代理侧的 SUBMIT，运营端不该有动作。
删之前把它挪进 B 类分组并注明。

**工作量**：3 小时。

#### A3-2 · 告警 —— 不只是缺一张表：**告警永远关不掉**

查前端手写 if 时顺带查出来的：

- `AlarmStateMachine` 有 `CLOSE` 边（`OPEN→CLOSED`、`ACKED→CLOSED`）；
- **主源码里没有任何一处发 `"CLOSE"` 事件**（只有测试里有）；

告警记录页会无限堆积，而「还有多少没处理」这个数从此说不清。
不报错、不红 —— 又是一条「留了边没人走」，与 B1 的订单事件是同一种形状。

1. **补表（现在可做）**：`ALARM_TRANSITIONS` 只声明 `ack: OPEN→ACKED`，

2. **补关闭动作（阻塞：缺权限码）**：后端加 `AlarmService.close(alarmNo, reason)`
   走 `stateMachine.next(status, "CLOSE")` + 端点 + 前端按钮，台账再删 2 条。

> 🚧 **第二步卡在权限码上，不要自己造。** 真源表里告警只有一个

就是同一类读端点（干预留痕分页）：

```java
/** 订单状态流转留痕（审计视图，append-only 表 ord_event_log）。 */
@GetMapping("/order-events")
@PreAuthorize("@perm.can('order:order:read')")
public List<OrderDtos.OrderEvent> orderEvents(@RequestParam String orderNo) {
    return eventLogService.timeline(orderNo);
}
```

**两个决定，说清理由**：

1. **返回 `List` 而不是 `PageResult`**，与隔壁的干预分页不同。
   一张订单的事件是**有界的**（十几条封顶，不随时间增长），分页只会让前端
   多写一圈翻页代码去翻一页。干预分页之所以是 `PageResult`，是因为它还兼作
   **跨订单**的审计列表（带 `action` 筛选）；订单事件没有这个用法。
   —— 若将来要跨订单审计视图，那时另加一个分页端点，不要现在预支。
2. **不合并进订单详情 VO**。详情是常看的，事件是排障才看的；
   塞进详情会让每次开抽屉都多查一张 append 表。

**权限码**：`order:order:read`（已核，在真源表里，与干预留痕同一个码 —— 都是"看这张单"）。

**前端**：

- `lib/types/order.ts` 加 `OrderEvent`（字段照后端 record：
  `orderNo/fromStatus/toStatus/event/operator/createdAt`）；
- `contracts` / `https` / `mocks` 三件套；`contract.test.ts` 端点计数 **+1**；
- 详情抽屉加「状态流转」时间线，**与「干预历史」并列而非合并** ——
  一个是状态怎么走的，一个是人做了什么，合并会丢信息（干预里有 `to: null`
  的只留痕动作，它根本不产生状态流转）。
- ⚠️ **mock 要真写事件行**：`lib/mock/db/order.ts` 在每次状态迁移时 append 一条，
  否则 mock 下时间线永远是空的 —— 而「空时间线」与「功能没做」长得一模一样，
  下一个人会以为没接通。

**验收**：造一张走过 EXCEPTION 的订单，详情页能看到完整迁移链；
mock 与真后端都非空。

**🚧 阻塞（D1）**：`docs/api/contract.json` 要等 `IamAdminController` /

### ✅ 已完成（2026-09-25）· B3 · 停用的员工仍能继续用旧令牌（本轮查得最实的一个洞）

**结论先说**：员工停用后，其**已签发令牌继续有效**，而且现有的
`PermVersion` 机制**救不了** —— 这不是"少调一个撤销方法"，是重建逻辑本身不回查在职状态。

证据链：

1. `TokenStore` 只有 `revoke(String token)`，**没有按人撤销**；
   `sys_token` 有 `subject_no` 列但**没有索引**（PK 是 token，另一个只有 `idx_token_expire`）；
   `RedisTokenStore` 的键只有 `pb:auth:token:{token}`，**无二级索引**。
   ⇒ 现在根本无法"撤销某人的全部会话"。
2. 看起来有个现成机制 `PermVersion.bump()`（改数据范围时就在用，"在线生效"），
   `StaffTokenAuthFilter` 每请求比对会话戳，变了就
   `refresher.rebuild(d.user(), d.roleNos())` 重建会话。
3. **但 `PermissionService.rebuild()`（:136）是按 `old.realm()/old.userNo()` 与
   *会话里带来的* `roleCodes` 重算权限的，全程不读 `iam_employee`。**
   ⇒ 停用一个员工再 bump，他的会话只会"照原样重算一遍"然后放行。

**技术方案**（两步，第一步单独可上，成本小且用的是现成机械）：

- **第一步 —— 让重建回查在职状态。**
  `rebuild()` 增加一次主体有效性校验（`iam_employee.status == ACTIVE`），
  失效则让过滤器按未认证处理；`EmployeeServiceImpl` 的停用/删除路径调 `permVersion.bump()`。
  这样停用后**下一次请求**即失效，不需要新建任何索引。
  ⚠️ 注意 `rebuild()` 在 `sharehub-common`（infra 层）被调用，回查要走
  已有的 `PrincipalRefresher` 抽象，**不能让 infra 反向依赖 IAM**（ADR-015 分层）。
- **第二步（可后置）—— 真正的按人撤销**：`sys_token.subject_no` 加索引 +
  `TokenStore.revokeBySubject(realm, subjectNo)`；Redis 侧加
  `pb:auth:subject:{realm}:{no}` → token 集合的二级索引（**不能用 SCAN**）。
  会话列表 / 手动踢人界面建在它上面。

**顺带记一个已存在的限制**（不在本任务范围，但与 D4/多副本相关）：
`PermVersion` 是**进程内的 `AtomicLong`**。多副本部署时一个副本 bump
不会传到另一个副本 ⇒ "改权限即时生效"在多副本下**只对自己这台成立**。
切 `token-store: redis` 做水平扩展时，这一条必须一起解决。

**验收**（两向）：停用员工后，用他原来的 token 调任意接口必须 401；
停用前必须 200。配场景测试。

⚠️ `EmployeeServiceImpl` **当前在别的会话手里在途**（见 D3）—— 先沟通或等他们提交。

**工作量**：第一步 1 天（含分层与测试）；第二步 1.5 天。
