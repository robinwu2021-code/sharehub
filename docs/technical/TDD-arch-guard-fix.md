## 2. 当前架构分析（实测 2026-09-23）

修复前 `python3 scripts/arch-guard.py` 的输出是：

```
扫描：76 个类 · 0 个实体 · 11 个 mapper · 6 个接口有实现
✅ 四个卡口全部通过
```

**「0 个实体」就是破绽** —— 后端有 97 个类 `extends BaseEntity`。两处根因：

| # | 缺陷 | 证据 | 后果 |
|---|---|---|---|
| 1 | **`EXTRA_SRC` 算出来却从没被用过** | 三处 `os.walk(SRC)`，`SRC` 只有 `sharehub-app/src/main/java` | 只扫 62 个文件；业务代码所在的 5 个 svc 模块（`core` 259 · `platform` 167 · `ops` 57 · `finance` 43 · `gateway` 24 · `api` 17，共 567 个）**一个没扫** |
| 2 | **G4 的路径是早已改名的模块** | `root = ROOT + 'backend/powerbank-common/src/main/java'`，实际模块是 `sharehub-common`；`if not os.path.isdir(root): return []` | G4 从改名那天起**一次都没真正跑过**，永远返回「违规 0」 |

源码注释里其实留了警告：「本会话已四次遇到『报绿但没扫』，每次动模块结构都要回头查这里」——
但那是一句**提醒**，不是**卡口**，所以第五次照样发生。

---

## 3. 方案设计

### 3.1 扫描面

新增唯一入口 `walk_java()`，遍历 `ALL_SRC = [SRC] + EXTRA_SRC`，产出 `(绝对路径, 短路径)`；
短路径统一去掉 `ai/neargo/sharehub/` 前缀，使白名单与台账条目在哪个模块都是同一种形状。
三处 `os.walk(SRC)` 全部改走它 —— **新增模块只改 `EXTRA_SRC` 一处**。

### 3.2 G4 路径：从「静默跳过」改为「显式报错」

```python
if not os.path.isdir(root):
    raise SystemExit('arch-guard: 找不到 common 模块源码根 ... —— 模块改名后请同步此处')
```

`return []` 是这次事故的形状本身：**找不到就当作没问题**。改成报错后，下次再改名会立刻炸，而不是悄悄全绿。

### 3.3 G3 的两类豁免（扫全之后新出现的 13 处，逐一判定而非一律拉白名单）

扫描面修好后 G3 报 13 处违规。逐个看，它们属于两类**架构本就允许**的情况：

| 类别 | 条目 | 依据 |
|---|---|---|
| **app 层跨域只读编排** | `SharingQueryService`(1) · `OperationOverviewService`(3) | [v4/09 §九](./v4/09-后端代码架构.md) · [v4/12 §4.3](./v4/12-代码库与工程结构.md) 明确「跨域报表 / 看板是唯一允许跨域读的地方」。实测这两个类**零写操作**（6–7 处读） |
| **演示种子** | `DemoOpsFinanceSeeder`(9) | 职责就是把各域样例数据一次性灌进去；且 `@ConditionalOnProperty(sharehub.seed.enabled)` 默认不装配，不在任何生产路径上。B4 会物理移到 `support/sharehub-seed`，届时这 9 条整体删除 |

**关键是豁免的粒度**：不按类名拉白名单，而是按「包 + 只读」判定 ——
`G3_READONLY_ORCHESTRATION` 里的包**一旦出现写操作**（`insert/update/delete/save/remove`），仍判违规。
跨域**读**可以，跨域**写**必须经 Port，否则拆分时事务边界就断了（那正是 G2 守的东西）。

### 3.4 棘轮：台账外的新豁免一律失败

没有这一步，「豁免」就是一张无限额白条：下次谁跨域注入，只要把类放进 `operation/` 或 `seed/` 就自动免检。
新增 `backend/known-arch-exemptions.txt` 钉死当前 13 条；卡口比对，**台账外的豁免计入违规**。

## 5. 已知盲区（写进台账，不当作「已覆盖」）

| 盲区 | 说明 | 何时消失 |
|---|---|---|
| **纯编排类对 G3 隐形** | G3 靠「方法体里出现哪些实体名」反推类的服务归属。只调 Port / 别的 service、不直接碰实体的类拿不到归属 → 整类跳过，其跨域注入检测不到 | 拆成 svc-* 后改为按 Maven 模块判定归属（B4） |
| **卡口没进 CI** | 仓库无任何 CI 配置（无 `.github` / `Jenkinsfile` / `.gitlab-ci.yml`），`--strict` 只能手工跑 | B2 剩余项或部署流水线接入时 |
| G2 的 5 处「仅读跨界」 | 警告不计违规，按分层规则属允许的跨域读 | — |

## 6. B2 剩余三项（**改动面大，动手前单独确认**）

| 项 | 现状实测 | 要做什么 | 风险 |
|---|---|---|---|
| **H2 测试隔离** | `src/test/resources` 下**只有 `fixtures`，没有任何配置** → 138 个测试直接连本机开发库 `pb_core`（`jdbc:mysql://127.0.0.1:3306`）。刚跑的全量测试就是写的真库 | 照 ai-shop：由 Flyway 迁移生成 `schema-test.sql` + H2 MySQL 模式 + `application-test.yml` | **最大**：40 个迁移里的 MySQL 方言未必被 H2 接受；`SmokeTest` 等断言依赖种子数据 |
| **ArchUnit** | 无依赖、无测试 | 引 `archunit-junit5` 1.3.0 + `ArchitectureTest`（控制器位置、Port 位置、禁全限定名、公共层隔离） | 中：首次跑必然大量违例，要先建 `known-*.txt` 基线 |
| **enforcer 依赖规则** | 无 `bannedDependencies` / `dependencyConvergence` | 按 [v4/12 §5.2](./v4/12-代码库与工程结构.md) 每模块一条规则 | 低，但会暴露现存的依赖收敛问题 |

**建议顺序**：enforcer（最小）→ ArchUnit（中）→ H2 隔离（最大，且最好与 B4 目录重排同窗口做，避免两次搬测试）。
