# 业务系统改造与库存服务对接

> 状态：开发设计草案（未实施） · 2026-10-29
> 已确认边界：仓内库存、进出库、盘点；出库后不跟踪业务库存；通过出库池交接；独立部署并提供 API。其余具体规则为本轮建议设计。

## 1. powerbank 需要新增的能力

| ID | 模块/入口 | 改造 |
|---|---|---|
| PB-01 | 库存适配层 | InventoryClient、服务凭证、错误转换、幂等任务、结果查询 |
| PB-02 | 主数据同步 | 型号→item，站点/点位/人员→external-target；出库 SN→设备身份 |
| PB-03 | 设备建档与安装 | 从出库池领取，建立本地稳定设备身份和业务关联，不伪造仓内状态 |
| PB-04 | 检测执行器 | 接任务、真实检测、证据上传、幂等结果回传 |
| PB-05 | 撤机与退仓 | 发退仓申请，等实物入库事件再完成交接 |
| PB-06 | 状态与门禁 | 仓内归库存；已出库未安装用业务待安装状态，不继续叫 IN_STOCK |
| PB-07 | BFF 与页面 | 库存查询/作业代理、设备选择器、领取恢复提示 |
| PB-08 | 事件与对账 | inbox、资源版本投影、待处理任务、孤立关联对账 |

建议新增 `backend/sharehub-app/src/main/java/ai/neargo/sharehub/inventorybridge/`（宿主编排，不塞进通用库存）；业务领域通过 Port 获取凭证/交接结果，不跨库读 inv_*。

## 2. 本地数据与状态

建议本地映射：inventorySerialId、serialNo、itemId、deviceNo/powerbankNo、lastDispatchItemId、claimNo、inventoryVersion。SN 跨仓周期沿用同一业务设备身份，不因回仓再出库重复建设备；关联新池和新安装任务。

新增持久化任务 `inventory_bridge_task`：taskNo,operation,requestId,payloadHash,businessRef,status(PENDING/REMOTE_DONE/LOCAL_DONE/COMPENSATING/FAILED),retryAt,lastError。新增 `inventory_inbox`，eventId 唯一。两者迁移号查当前最新，不在本方案预占 V 号。

仓内库存状态与业务设备状态分开：库存 OPEN/PENDING/PASSED 不等于柜子 DEPLOYED/FAULT。建议增加业务 `PENDING_INSTALL`，仓内字段仅投影，不接受前端直接改写；转换旧 IN_STOCK 状态的所有读写点必须列出并迁移。已出库未安装的设备也不能参加现场营业。

## 3. 安装领取协议

1. BFF 校验员工可管理站点、工单可执行、站点允许安装，查询授权目标池候选。
2. 本地事务锁定工单，创建稳定设备身份/待关联占位和唯一任务（尚不准安装完成/上线）；业务引用使用已提交业务对象 ID。
3. worker 用固定 Idempotency-Key 调 claim，失败/超时先查 commands，不能换键重复试。
4. 远端成功后本地事务写 claimNo、dispatchItemId、激活业务关联并标 LOCAL_DONE；崩溃重启重试第 3/4 步。
5. 永久失败保持可见待处理；人工决定继续完成还是受控补偿。补偿前冻结工单和占位，确认未安装/无下游依赖，release 原 claim 后才清理本地占位。

领取没有自动 TTL，避免本地已经安装但远端租约到期后又能被别人领。网络断开不回写旧库存，不自动按 SN 建立“已经领了”的假关联。

## 4. 回仓协议

业务发起 `RETURN_REQUEST`，记录设备、原池和业务冻结检查；库存可创建 RETURN 草稿但不增加库存。仓管扫码实收过账，新建周期并将原池 RETURNED。业务 inbox 同事务更新“仓库已接收”投影，清理安装交接关系，不删除设备身份与历史。

发送退仓前，powerbank 必须按设备类型验证：柜子已停借保还并安全撤机，充电宝无有效借出订单或已完成专门异常处置，安装/维修工单无冲突。库存服务无法验证这些业务表；退仓申请携带已核验业务授权引用。实物异常已在仓时可隔离接收，但不得据此悄悄结束未处理订单，产生业务对账异常。

退仓实收与业务最终解除关联之间允许明确的同步中状态；该设备仓内 PENDING，不可再次出库，直到退仓业务确认（returnClearance）到达。业务完成本地解除关联事务后，通过持久化任务调用 `POST /inbounds/{no}/business-clearance`，附 businessRef/clearanceRef，固定幂等键重试；此门禁是独立仓内冻结原因，解除后仍需质检通过。未领取设备可直接走 RETURN，无需伪造 claim，库存验证确无有效领取后免除此业务确认等待。

## 5. 组合设备

柜子与随柜宝均属于 SERIAL 时，出库必须列全 SN，不能仅柜号+宝数量。通用库存仅保留该次包装/同批出库引用，不维护实时柜槽关系。业务在领用时验证整组一致，后续装拆宝归 powerbank。扫码包装码可展开已核验 SN 清单，最终过账仍逐件校验。

现场清点数不符仍走业务资产异常，不生成仓内盘亏。实际回仓的缺件按实收 SN 入库，未回件继续由业务追查；不能以“预计回 10”自动增加 10。

## 6. ai-shop 电商对接

继续使用原 `invbridge` 作为适配入口，`InventoryStockPort`/`DualWriteStockPort` 改远端客户端，但不通过普通 ISSUE 池处理销售。

- 下单先在本地持久化 PENDING 库存意图，固定 externalRef 调 reserve，确认成功才能进入相应订单状态；超时先查询预留结果。
- 支付完成推进库存提交任务，同一 externalRef 幂等 commit；库存服务在一个事务中预留→销售出库。预留到期与支付回调竞争必须原子裁决：已过期提交返回明确冲突，宿主退款/补库存策略不得默默超卖。
- 取消/超时持久化 release 意图；已 commit 后不能 release，应走订单/售后反向业务。
- RETURN_REFUND 产生一次退货入库，REFUND_ONLY 不回补；重复回调不重复加库存。
- SKU/门店更名事件不修改历史单据快照；门店共享发货源语义留在商城适配，不能让 powerbank 接收站点自动使用默认仓库存。

商城切流详见 07，旧 DUAL 是迁移观测机制，不是永久的双库存写权。

## 7. 现有 powerbank 写入口收口

`InventoryController`、`AssetOpsController` 的库存/仓内质检动作改库存 BFF；`InventoryTransferServiceImpl`、`TransferOpsServiceImpl` 停止成为库存权威。`RemovalCompletedListener` 改发退仓申请，不因撤机直接回仓。`QcServiceImpl` 仓内部分转库存质检任务；现场门禁与设备检测继续保留。

旧域 `inv_stock/inv_warehouse/inv_transfer/inv_transfer_item/inv_asset_diff` 按语义迁移：业务差异留业务域、仓内差异迁盘点/纠正；不能把站点清点记录全搬成仓库库存差异。

## 8. 必要对账

按批次核对 SN 身份、池领取与本地工单关联、RETURNED 与本地回仓投影、待完成远端命令、模板/质检版本。只报不一致并进入处置任务，不自动以任意一边覆盖另一边。库存不监控设备当前运行位置。
