# 独立进销存：需求边界与决策

> 状态：开发设计草案（未实施） · 2026-10-29
> 已确认边界：仓内库存、进出库、盘点；出库后不跟踪业务库存；通过出库池交接；独立部署并提供 API。其余具体规则为本轮建议设计。

## 1. 已确认的业务边界

1. 库存只覆盖受管仓库的进出库、仓内余额和盘点；出库之后停止跟踪业务位置与数量。
2. 出库前选择人员、门店或站点等接收对象；实际出库过账后生成交接池。
3. 业务系统按目的地或接收人查找设备，并通过领取命令建立业务关联。
4. 库存独立部署，业务通过独立 API 对接。

出库池是交接凭证，不是虚拟库存。领取不再次扣库存；设备换站点、安装、上线、借还、维修和业务丢失不调用库存改数。仓外资产巡检不生成仓内盘点单。仓内实存不包括池中未领取的设备。

## 2. 方案选择与依据

| 方案 | 取舍 | 结论 |
|---|---|---|
| 整个商城后端直接作为库存服务 | 带入商城身份、上下文、部署和商品假设 | 不采用 |
| 只抽本地 Java 库 | 降低初期调用成本，但不能满足独立 API/部署 | 不作为目标 |
| 提取通用库存内核、独立服务、各宿主适配 | 复用余额/流水/单据，补齐交接和 SN | 采用，独立服务方向由用户指定 |

服务代码先托管在 ai-shop 仓库，库存库与发布产物独立；这是建议落点，不等于用户已指定最终独立仓库。

## 4. 接收对象与库存业主

`ownerId` 是库存账隔离边界，`systemCode` 是调用系统身份；两者不互相替代。凭证绑定可访问业主及动作，服务端解析，不能相信请求体声明的租户身份。

目的地用 `targetSystem + targetType + targetRef` 唯一标识；人员接收另用 `receiverRef`。例如目的地是站点 S1，接收人 U1，两者可同时查询。一张出库单一个目的地，多个站点拆单。

代理代管不必等于跨业主：平台自有库存可由不同代理仓保管。真正跨所有权转移另行设计，本期禁止以一次普通仓库调拨实现跨业主搬账。出库也不自动改变设备法律归属或财务资产所有权。

## 5. 仓内/仓外场景分类

| 场景 | 库存动作 | 业务动作 |
|---|---|---|
| 采购到仓 | 入库、待检、质检放行 | 采购来源登记 |
| 仓发给站点/运维 | 出库、交接池 | 领取后安装/使用 |
| 已出库设备跨站调整 | 无 | 改绑定与责任 |
| 站点故障、外场维修 | 无 | 故障与维修状态机 |
| 维修设备实际回仓 | 退仓入库、重新质检 | 发起退仓并等待确认 |
| 仓内报损/盘亏 | 出库/盘点调整，无设备待选池 | 必要的损失审批 |
| 仓间调拨 | 保留可选内部能力，在途仍属于库存域 | 不生成业务待选池 |
| 用户借还充电宝 | 无 | 订单、信号、柜槽宝关系 |

仓间调拨如启用，必须作为显式扩展能力：来源出库、在途、目标实收及差异有账；不允许把“已出给业务的站点设备”放入仓间在途余额。首版 powerbank 接入不依赖该能力，ai-shop 旧能力迁移不得静默删除。

## 6. 本轮建议默认值

- 入库时计实存；需质检设备待检不可出库。SN 草稿不永久占用，过账强校验；若启用预占则有 TTL。
- 交接型出库（`ISSUE`）必须有目的地且生成池；销售、报损、盘亏、退供应商默认不生成池。
- 领取按请求全成全败；领取后不自动过期。只有未完成业务关联且业务系统证明确可释放时才解除领取。
- 首版仓内盘点冻结选中物料范围的库存变更与预留操作，详情见 01；不停仓盘点列为后续扩展。
- 仓内质检最终通过/不通过只由库存质检服务按冻结模板计算，业务执行器提供结果和证据。

## 7. 非目标与术语

不建设设备远程控制、资产折旧、现场工单引擎、完整采购审批与应付账款、售后维修平台。供应商和采购入库可复用，但采购订单、账期不是本次必做。

“过账”是唯一改变库存的确认动作；“领取”是唯一建立池业务关联的动作；“质检通过”是库存可放行条件；“上线验收通过”是业务侧条件。所有报表和页面必须沿用此区分。
