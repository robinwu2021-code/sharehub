## 〇、结论

**原则**：ai-shop 已经走过的路不再走一遍 —— **中性的代码下沉共享**（两项目依赖同一份），**约定照搬**，**ai-shop 业务特有的不碰**；
只有在 ai-shop 的做法有已知缺陷、或与 ShareHub 已定的底座（neargo 契约）冲突时才不同，并写明理由（§二.3）。

### 2.2 照搬约定（复制做法，不共享代码）

| 约定 | ai-shop 的做法 | ShareHub 落地 |
|---|---|---|
| 模块层序 | `base ← base-auth ← store-mybatis ← 各域 ← app`；判据是「进没进 classpath」 | `common ← auth ← store ← api ← svc-* ← app`（§三） |
| 模块数 | 「模块数 = 将来可能的部署单元数；域数 = 包数」 | 不为每个域建 Maven 模块；域是包 |
| 域包布局 | `<域>/{api/{mp,biz,ops,callback}, service, service/impl, entity, mapper/XxxMappers, dto, port, job}` + `package-info.java` 写边界 | §四 |
| 控制器位置 | 放在域的 `api/<端>` 子包（跨域编排的才放 app `portal`） | 同（拆服务时控制器随域走，契合 ADR-017 双形态） |
| DTO | Web 入参 `XxxReq`（嵌套在控制器，带校验注解）· 服务入参 `XxxCommand`（嵌套在服务接口）· 出参 `XxxVO`（独立文件） | 同 |
| Mapper | 每个域一个 `XxxMappers` final 类，内嵌各 `BaseMapper` 接口；`@MapperScan(markerInterface = BaseMapper)` | 同（ShareHub 现有的 `LocMappers` 等**就是这个形状，保留**） |
| 实体 | 一实体一文件，表前缀即域 | 同（拆掉 `IamEntities`） |
| 错误 | 服务层唯一的预期内失败出口 `BizException(ErrorCode, args)`；`ErrorCode` 按首位分段、`msgKey` 走三语 properties | §五.1 |
| 状态机 | 静态迁移表 + `assertTransit`，非法迁移抛 `BizException(CONFLICT)`；Service 里不许散写 `if (status == …)` | §五.3 |
| 跨域写 | 同步读走 Port；**跨域写推迟到提交后** `AfterCommit.run`；异步走 Outbox + 按事件号去重；每张表只有所属域能写 | 同（卡口 `CrossDomainWriteConventionTest`） |
| 对外标识 | 只暴露业务键 `xxxNo`，`id` 不进 URL 不进响应；删除一律逻辑删除 / 归档 | 同（ShareHub 已有此约定） |
| 权限 | `@PreAuthorize("@perm.can('" + Perms.X + "')")`，`Perms` 常量类；每个端点必须显式声明权限（测试守） | 同（`Perms` 放 `sharehub-auth`，由[功能权限清单](../../requirements/功能权限清单.md)校验） |
| 校验 | 类上 `@Validated`，`@RequestBody` 上 `@Valid`，约束写在 Req 上；未接线的记 `known-unwired-validation.txt` | 同 |
| 定时任务 | `JobHandler` + `@Bean JobDeclaration` | 同，但**不再写** ai-shop 过渡期的 `@Scheduled` + `JobSupport` 旧路径（[07](./07-定时任务.md)） |
| 事件消费 | `XxxConsumer implements OutboxConsumer`（ai-shop 10 个），`@EventListener` 几乎不用 | 同 |
| 架构测试 | ArchUnit 1.3.0，放 `shop-app/src/test/.../arch`；已知欠账写 `known-*.txt`，**只准变短**，新增违例直接红、修好未删行也红 | §七 |
| 测试 | H2（`MODE=MySQL`）+ 由迁移生成的 `schema-test.sql` + `SchemaParityTest` 防漂移；`e2e` profile 对真库跑；`TestLogin` 走真实登录 | §六 |

### 2.3 不用 / 有意不同

| 项 | ai-shop | ShareHub | 理由 |
|---|---|---|---|
| 响应信封 | 自有 `ApiResult{code,msg,data}` · `PageData{records,total,page,size}` | **neargo** `Result{code,message,data}` · `PageResult{list,total}`（现状，不变） | ShareHub 与 neargo 底座一致；ops-web 已按此对齐。故 ai-shop 的 `ApiResult` `PageData` `ApiResponseWrapper` `GlobalExceptionHandler` 只照搬写法，不共享代码 |
| 403 | HTTP 200 + `10403` | HTTP 403 + `10403` | ai-shop 运营端的 403 处理因此从未触发（[06 §七](./06-认证与权限.md)） |
| 金额 | `long xxxMinor` | `BigDecimal` + `DECIMAL(18,2)`（现状，不变） | 库表已定；**唯一换算点**在 `RemotePaymentPort`（共享支付模块用 minor），有测试 |
| 审计 | 显式 `auditLogPort.record(...)`（55 处） | 保留现有写操作审计拦截器（横切）**+** 高危操作显式 `AuditLogPort.record` | 横切兜底不漏，显式记录补业务语义 |
| 时间 | 业务直接 `LocalDateTime.now()` | 注入 `Clock` | 到期 / 超时 / 日切类逻辑多，需要可测 |
| 一个 jar 起多种进程 | `@Profile("api" / "ops" / "worker")`，每个控制器带 profile | 暂不做 | ShareHub 单个业务进程即可；保留为「运营端与 C 端分进程」的备选手段 |
| 业务特有 | `spi/*` 约 110 个 Port 的内容、`Perms` / `BizPerms` 的码、`BizContext`、门店 / 社区维度、`ErrorCode` 2–8 段内容、`BizKey` 前缀常量、支付专项 9 个架构测试、media / archive | 不用 | 电商业务 |
| 由前端 TS 生成 OpenAPI | 是（`gen-openapi.mjs`） | 契约方向与前端会话共同决定（§九 C5） | 前端另行整理 |

### 2.4 `common` / `auth` / `store` 三层能否直接共用 ai-shop 的成果

**结论：能共用大半，但不是整包依赖 `shop-base` / `shop-base-auth` / `shop-store-mybatis`** —— 这三个包都是「中性骨架 + ai-shop 业务内容」混装的。
做法是把中性的一半抽到 `neargo-framework`（2.x），两项目都依赖它；各自只保留一层很薄的产品层。

| ai-shop 包 | 能直接共用（抽到 neargo） | 改造后才能共用 | 不能共用（ai-shop 业务） | ShareHub 产品层保留 |
|---|---|---|---|---|
| `shop-base`（127 类） | `BizException` · `ErrorCode` 接口与 10xxx 通用段 · `Messages` · `IsoTime` · `Masks` · `Geo` · `AfterCommit` · `DomainEvent` · `JobHandlerRegistry` · `svc/InternalClient` 等 · `ratelimit` · `CaptchaService` | `Phones`（去掉大陆号码规则，改为按国家配）· `OtpStore`（内存 → SPI，ShareHub 落库实现）· `BizKey` 生成器（前缀常量拆出去） | `spi/*` 约 110 个 Port · `ErrorCode` 2–8 段 · 支付 / 物流 / 类目枚举 · `PlaceNames` 等 | 本产品 `ErrorCode` 分段、业务号前缀、`sharehub-api` 的 Port |
| `shop-base-auth`（31 类） | `PasswordHasher` · `LoginAuditor` · `OtpSendGuard` · `RealmRoutingTokenStore` 的路由逻辑 · `AbstractTokenAuthFilter` 的骨架 | **Realm**：现为固定枚举（CONSUMER / MERCHANT / OPERATOR）→ 改为可插拔的 `RealmSpec`（名称、令牌前缀、过滤器链路径、会话档位），各产品注册自己的一组；**401 / 403 响应**：现直接写 ai-shop 的 `ApiResult` → 改为 `ErrorResponseWriter` SPI，由产品按自己的信封写出 | `Perms`（720 行）· `BizPerms` · `BizContext`（门店上下文）· 数据范围维度值 | Realm 集合（CONSUMER / STAFF / AGENT）、`Perms`、信封与全局异常处理、数据范围登记 |
| `shop-store-mybatis`（36 类） | `IdempotencyService` · `EventIdempotency` · `OutboxEventBus` · `OutboxDispatcher` · `OutboxConsumer` · `MybatisPages` · `AuditMetaObjectHandler`（含 `updateFill` 坑的修法） | **实体基类**：ai-shop 的 `BaseEntity` 与 ShareHub 的只差租户列（`tenantNo` / `tenantId`）→ 共享一个**不含租户列**的 `AuditedEntity`（id · 创建 / 更新时间与人 · version · deleted），租户列留在产品子类 | media / archive（偏 ai-shop 业务） | `BaseEntity extends AuditedEntity` + `tenantId`；CRUD 基类（ShareHub 自有，ai-shop 无对应） |

**三个阻碍，以及不用两边统一就能绕开的办法**：

| 阻碍 | 实测 | 办法 |
|---|---|---|
| 响应信封不同 | ai-shop `{code, msg, data}` · `{records, total, page, size}`；ShareHub（neargo）`{code, message, data}` · `{list, total}` | 共享层**不拥有信封**：错误经 `ErrorResponseWriter` SPI、成功由产品自己的包裹器写；两边信封以后要不要统一，另议，不阻塞共享 |
| 实体基类不同 | 同上表 | 框架 2.x 提供四档基类（`IdEntity` → `CreatedEntity` → `AuditedEntity` → `StandardEntity`），租户列下放到产品基类；审计填充按字段类型填 `Instant` / `LocalDateTime`，ai-neargo 的实体也能用（框架 design/01 §5.1） |
| Realm 写死 | `enum Realm { CONSUMER, MERCHANT, OPERATOR }` | 可插拔 `RealmSpec`；ai-shop 注册自己的三个，ShareHub 注册自己的三个 |

**落到 neargo 的目标模块**（与已有 `neargo-common-*` 同一家族、同一发布线，[10](./10-共享构件与Nexus.md)）：

| 模块 | 内容 | 依赖 |
|---|---|---|
| `neargo-common-core`（扩充） | 上表 `shop-base` 列的中性件 | — |
| 🆕 `neargo-common-internal` | `InternalClient` · `ServiceLocator` · `ServiceName` | core |
| 🆕 `neargo-common-store` | `AuditedEntity` · 审计填充 · 幂等 · 事件去重 · Outbox · 分页 | core、MyBatis-Plus |
| 🆕 `neargo-common-auth` | `RealmSpec` · 令牌过滤器骨架 · 池路由 · 密码哈希 · 登录审计 · 验证码发送防护 · `ErrorResponseWriter` SPI | core、`neargo-common-security`（rbac / scope）、`neargo-auth-store` |
| `neargo-auth-store`（已提） | 会话 / 登录日志持久层 | spring-jdbc |

之后 ShareHub 的三层变成：`sharehub-common` ≈ 产品错误码 + 业务号前缀 + 工具补充；`sharehub-auth` ≈ Realm 集合 + `Perms` + 信封与异常处理 + 登录策略；
`sharehub-store` ≈ `BaseEntity`（带 `tenantId`）+ CRUD 基类 + 数据范围登记。ai-shop 的三层同理变薄 —— **这是 ai-shop 仓库的改动，需要与其并行会话排期**。

## 三、目标模块分层

```
                 neargo commons（core · data · security · …）＋ 下沉件（job · auth-store · internal · store-mybatis）
                                            ▲
sharehub-common   ≈ shop-base        内核：BizException / ErrorCode、业务号、事件接口、AfterCommit、状态机工具、内部调用、工具类
                                     —— 不依赖 MyBatis、不含任何业务名词
                                            ▲
sharehub-auth     ≈ shop-base-auth   令牌过滤器、Realm、@perm 与 Perms、响应包裹、全局异常处理、登录策略、OTP
                                            ▲
sharehub-store    ≈ shop-store-mybatis   BaseEntity、审计填充、CRUD 基类、分页、幂等、事件去重、Outbox 投递
                                            ▲
sharehub-api      ≈ shop-base/spi    跨模块 / 跨进程 Port、事件类、DTO、远程实现（Port 接口只许放这里）
                                            ▲
sharehub-svc-{platform, core, ops, finance}   业务域（含各域控制器）
                                            ▲
sharehub-app      启动与装配：配置、跨域编排（报表读模型、看板、桥接）、Flyway 主库
─────────────────────────────────────────────────────────────
sharehub-gateway-kernel ← -transport-* ← -driver-*  ←  sharehub-app-gateway      （独立进程）
sharehub-seed（demo 构建）· sharehub-test-support（test scope）
```

**为什么把 `store` 从 `common` 分出来**（照 ai-shop 的判据「进没进 classpath」）：内核要能被不需要 MyBatis 的地方依赖
（网关的传输层、将来的独立小进程），而 ShareHub 今天的 `common` 把 `AbstractCrudService`、`SysOutbox` 实体和 MyBatis 一起强加给了所有依赖方。

## 四、业务域的包布局（照 ai-shop）

```
ai.neargo.sharehub.<domain>
├─ package-info.java        边界说明：本域拥有哪些表、对外暴露哪些 Port
├─ api/
│  ├─ ops/                  XxxOpsController   /api/**   （内嵌 XxxReq record，带 @Valid 约束）
│  ├─ mp/                   XxxMpController    /mp/**
│  └─ internal/             XxxInternalEndpoint /internal/**（sharehub-api Port 的服务端，不套 Result 信封）
├─ service/                 XxxService（接口，内嵌 XxxCommand record）· XxxStateMachine
├─ service/impl/            XxxServiceImpl（+ 包内私有 helper）
├─ entity/                  一实体一文件
├─ mapper/                  XxxMappers（final 类内嵌各 BaseMapper 接口）
├─ dto/                     XxxVO（独立文件，`static of(entity)` 是实体 → VO 的唯一出口）
├─ port/                    XxxPortImpl（实现 sharehub-api 的 Port）
├─ event/                   XxxConsumer（OutboxConsumer）
└─ job/                     XxxJob（JobHandler）+ 声明
```

**写法约束**（全部进架构测试）：

1. 控制器只在 `..api..`（域内）或 `sharehub-app` 的 `portal..`（仅跨域编排：报表、看板）；控制器**不依赖 Mapper**、不写 `@Transactional`；
2. `XxxService` 是接口，实现名 `XxxServiceImpl` 且在 `impl` 子包；
3. 请求体只能是 `XxxReq`，响应只能是 `XxxVO` / `PageResult<XxxVO>` / 基础类型 —— **不许实体、不许 `Map`**；
4. Req → Command 的转换在控制器；Command → 实体的赋值在 `ServiceImpl`，**只赋白名单字段**；状态与归属不经 Command 修改，只经动作接口（`archive` / `stop` / 划拨）；
5. `*Port` 接口只在 `sharehub-api`；本域实现在 `port/`；
6. 跨域写用 `AfterCommit.run`，跨域读用 Port；
7. 服务层不碰 `HttpServletRequest` / `SecurityContextHolder`，身份只经 `SecurityUtils` / `StaffContext` / `ConsumerContext`。

## 五、统一件

### 5.1 错误码与 `BizException`（复用 ai-shop 骨架）

- 服务层**唯一**的预期内失败出口：`throw new BizException(ErrorCode.X, args)`；不再用 `IllegalArgumentException` / `ResponseStatusException` 表达业务失败；
- `ErrorCode` = `code` + `msgKey`，文案在 `messages{,_en,_ar}.properties`；**首位分段**决定 HTTP 状态映射与端上行为：

| 段 | 域 | 说明 |
|---|---|---|
| `10xxx` | 通用（**照搬 ai-shop 同码同义**） | `10400` 参数 · `10401` 未登录 · `10402` 会话失效 · `10403` 无权限 · `10404` 不存在（含越权）· `10409` 冲突 · `10429` 限流 · `10500` 内部；认证类 `1045x`（[06](./06-认证与权限.md)） |
| `20xxx` | 订单 · 计价 · 支付编排 | 如 `20001` 设备不可用 · `20002` 已有进行中订单 · `20003` 该类型不支持此付费模式 |
| `30xxx` | 设备 · 协议对接 · 库存 | 如 指令超时、设备离线 |
| `40xxx` | 营销 · 会员 · 券 | |
| `50xxx` | 账务 · 分润 · 结算 · 提现 · 发票 | |
| `60xxx` | 消费者 · 风控 · 钱包 | |
| `70xxx` | 场地 · 代理 · 划拨 | |
| `80xxx` | 平台 · IAM · 系统 | |
| `90xxx` | 告警 · 工单 · 客服 | |

- 各段一个枚举（`OrderError` `DeviceError` …）实现同一接口，放各自模块；**`ErrorCodeUniqueTest`** 保证全局唯一，**`BackendI18nParityTest`** 保证三语词条齐全（均照搬 ai-shop）；
- `GlobalExceptionHandler`（`sharehub-auth`）：`BizException` → HTTP 状态（按段与码）+ neargo `Result`；校验异常 → `10400` 并记被拒字段（ai-shop 做法）。

### 5.2 业务号

一个生成器（neargo `IdGenerator`），格式对齐 ai-shop `BizKey`：**前缀 + `yyMMddHHmmss` + 序号 + 随机**；
**前缀归各域**（`enum OrderBizKey implements BizPrefix { ORDER("OD"), … }`），启动时校验全局唯一（测试锁住）；
合并 `BizKey` · `PayBizKey` · `FinNos` · `BizNoAllocator` · `AbstractCrudService.nextNo` 五处。

### 5.3 状态机

照 ai-shop 的写法（静态迁移表 + `assertTransit`），把 8 份复制抽成 `sharehub-common` 里 20 行的工具：

```java
public final class StateTransitions<S extends Enum<S>, E extends Enum<E>> {
    public static <S extends Enum<S>, E extends Enum<E>> Builder<S, E> of(Class<S> s, Class<E> e) { … }
    public S next(S from, E event) { … }   // 非法迁移 → BizException(ErrorCode.CONFLICT, from, event)
}
// 各域：OrderStateMachine 持有一个 StateTransitions<OrderStatus, OrderEvent>，状态与事件改为枚举
```

ai-shop 本身没有这层抽象（每个状态机各写一遍），建议随 `neargo-common-core` 下沉时一并回馈。

### 5.4 持久与一致性（复用 ai-shop `shop-store-mybatis`）

| 件 | 用在哪 |
|---|---|
| `IdempotencyService.execute(key, endpoint, userNo, type, supplier)`（表 `sys_idempotent`，保留 24 小时） | 所有带 `Idempotency-Key` 的创建类接口：建单、充值、提现申请、下发指令 |
| `EventIdempotency.once(eventNo, handler, action)`（表 `sys_event_consumed`） | 所有事件消费者：设备事件、支付事件、Outbox 消费 |
| `OutboxEventBus` + `OutboxDispatcher`（`REQUIRES_NEW`，每批 200、最多 10 次、退避 10 秒起至 30 分钟）+ `OutboxConsumer` | 取代 ShareHub 现有的进程内投递与 `OwnershipReconciler` 专用重投；由任务 `outbox-dispatch` 驱动 |
| `AuditMetaObjectHandler`（更新用 `setFieldValByName`，否则 `updated_at` 永不变） | 替换 ShareHub 现有实现（核对是否踩了同一个坑） |
| CRUD 基类（ShareHub 自有 `AbstractCrudService`，ai-shop 无对应） | **保留**，但 `save(E)` 改为 `create(Command)` / `update(no, Command)`，租户取 `TenantContext` |

### 5.5 内部调用（复用 ai-shop `shop-base/svc`）

| 调用 | 客户端 |
|---|---|
| app → pay-svc / gateway；gateway / pay-svc → app 的事件回推 | `InternalClient` + `ServiceLocator`（`sharehub.services.targets.{PAY,GATEWAY,APP}` · `internal-token`）—— 服务凭证 |
| 将来拆分后的业务服务之间 | 现有 `RemoteCaller` / `RemotePorts` —— 透传用户 Bearer（[设计v3](../设计v3-工程骨架.md) 已定） |

服务端统一用 `InternalTokenFilter` 校验（ai-shop 是在各端点里各自校验，这里收成一个过滤器）。
