# 16 · 工作流与工单组件方案

> 所属：[v4 详细规划](./README.md) · 状态：**方案待确认**（2026-09-27）

> 形式：按 11 的约定**只用表格、不出图**。

> ⏸ **框架线冻结中**（ADR-025 决定 5）。本篇的落地路线因此是：**先在两个产品里用同一份中性代码跑通**，

## 〇、结论

| # | 结论 | 一句话理由 |
|:-:|---|---|
| 1 | 拆成**三个构件**，不是一个「工作流引擎」 | 状态机谁都要、不带表；审批与工单带表、采用节奏不同。捆在一起会让 ai-shop 为了用状态机被迫接受工单表 |
| 2 | 状态机统一为**事件驱动 + 双枚举**（`状态` 与 `事件` 都是枚举，两种类型） | 两个产品现在是两套互不兼容的模型；事件模型能**推导出** from→to 图，反过来推不出（§一 1.1） |
| 3 | 工单引擎的内建行为**绑定状态的「角色」，不绑定状态名** | 充电宝工单有 `AUDITED`、ai-shop 售后有 `ARBITRATING`/`REFUNDING`，名字不可能统一，但「这一态 SLA 停表」「这一态是终态」可以统一 |
| 4 | **嵌入式库，不做共用服务** | 状态迁移必须与业务行更新在**同一事务**提交；做成服务就只剩最终一致，「合同已获批但站点没生成」会成为常态 |
| 5 | **不引入 BPMN**（Flowable / Camunda） | 两个产品的流程都 ≤ 3 步；BPMN 带来 20+ 张运行时表、XML 建模和一个没人会运维的引擎，换来的能力我们用不上（§十） |
| 6 | 先在产品里跑通、再上移框架 | 框架线冻结；且 11 的「不猜测性抽取」要求两个产品都真用起来才抽 |

## 一、现状（两边实测，2026-09-27）

### 1.1 状态机：两个仓库、两套模型、零公共抽象

| 维度 | powerbank（ShareHub） | ai-shop |
|---|---|---|
| 数量 | **14 个**状态机类，各自手写 | **1 个**类（`OrderStateMachine`）里塞三张图：订单 / 子单 / 售后 |
| 模型 | 事件驱动：`event → (from → to)` | 纯图：`from → Set<to>`，**没有事件** |
| 状态类型 | 枚举（有卡口 `StateMachineUsesEnumTest`） | 裸字符串；`"AUDITING"` 字面量散在 **7 个**主代码文件，其中 **2 个类**各自定义了一遍同名常量 |
| 形态 | `@Component` 实例 | `static` 工具方法 `assertXxxTransit(from, to)` |
| 方法面 | **已分叉**：13 个叫 `next`、`LeadStateMachine` 叫 `check`；「由迁移反查事件」一个叫 `eventFor`、一个叫 `eventOf`；`isTerminal` 只有 1 个类有；`CampaignStateMachine.next` 是 static | 统一但贫乏：只有「能不能走」，没有「走哪条边、为什么」 |
| 前后端一致 | 有卡口 `StateMachineEdgeAcrossEndsTest`（按形状发现迁移表、传递闭包比对） | 无 |

**为什么选事件模型**：同一对 `from → to` 可以由不同事件触发、带不同语义 —— 充电宝工单的 `WITHDRAW`（告警自愈撤单）与 `MERGE`（并入上层工单）都是 `→ CLOSED`，但 `close_reason` 不同、统计口径不同。事件模型能机械地投影出 ai-shop 要的 `from → Set<to>`；纯图模型**丢掉了**「为什么走这条边」，补不回来。

### 1.2 审批：两边都在各自手写同样的四条规则

| 产品 | 手写审批的地方 | 各自重写了哪些规则 |
|---|---|---|
| powerbank | 进场合同（**两级**：运营审批 → 条件触发的财务会签）· 代理入驻审核 · 提现审批 · 退款 · 场地方入驻 | ① 提交人不能审自己 ② 驳回必须填原因 ③ 只有提交人能撤回、且只在待审时 ④ 「按原状态 + 原环节」条件更新，并发只一人赢 |
| ai-shop | 商品审核（`audit_status`：AUDITING/APPROVED/REJECTED + 审核队列）· 商户主体申请（REVIEWING）· 平台活动审批 | 同上四条，各写各的；「待我审核」队列各自拼查询 |

合同审批那段注释写着「运营通过、仍待财务：状态不动（PENDING），只推进审批环节 —— 按原状态 + 原环节条件更新，并发只一人赢」—— 这正是一个审批组件该内建、而不是每个域都重新推导一遍的东西。

### 1.3 工单：同一类东西，两个名字

| 产品 | 「工单」 | 规模 | 共有的形状 |
|---|---|---|---|
| powerbank | 运维工单 `wo_*` | **35 个**文件；`WorkOrderService`（旧）与 `WoOpsService`（新）**并存**，都有 `dispatch` 与 `page`，旧的仍被 3 处引用 | 编号 · 状态机 · 受理人 · 派单（人工 / 抢单池 / 接管）· 驳回 / 返工 · SLA 计时与超时扫描 · 复核 · 撤单 / 合并 · 时间线 · 附件 |
| powerbank | 客服报障 `cs_ticket`、业务告警 | 各自一套 | 同上的子集 |
| ai-shop | 售后单 `OrdAfterSale` | 申请 · 撤销 · 寄回 · 商家同意 / 驳回 · **申诉升级到平台仲裁** · 确认收货 · 系统自动退 · 商家待办计数 | 同上：在「用户 → 商家 → 平台」之间流转的事项，驳回后可升级 |

### 1.4 流转日志：7 张表，7 种写法

| 产品 | 表 |
|---|---|
| powerbank | `OrdEventLog` · `WoDispatch` · `WoHandle` · `LocContractLog` · `LocSiteStatusLog` · `LocSiteLifecycleLog` |
| ai-shop | `OrdStatusLog` |

字段大同小异（谁、何时、从哪到哪、为什么），但没有两张表能用同一段代码读。

## 三、`neargo-statemachine`（#17）

### 3.1 接口

| 能力 | 签名（示意） | 替换两边的什么 |
|---|---|---|
| 定义 | `StateMachine.of(S.class, E.class).on(E.DISPATCH).from(S.CREATED).to(S.DISPATCHED)…build()` | 14 个手写 `Map.of(…)` + ai-shop 三张 `Map<String, Set<String>>` |
| 推进 | `S next(S from, E event)`；非法抛 `IllegalTransition(from, event)`，带可本地化的错误键 | 13 个 `next` + 1 个 `check` |
| 反查事件 | `E eventFor(S from, S to)`；**不唯一时抛错而不是随便挑一个** | `eventFor` / `eventOf` 两个名字 |
| 可走事件 | `Set<E> events(S from)` —— 前端据此决定亮哪些按钮 | 6 个类各自的 `events` |
| 终态 | `boolean isTerminal(S s)` —— **由图推导**（无出边即终态），不手写 | 只有 1 个类有 |
| 守卫 | `.on(E.APPROVE).from(…).to(…).guard(ctx -> …)`，返回拒绝原因键 | 「提交人不能审自己」这类散在 service 里的判断 |
| 图导出 | `Graph graph()` → JSON：状态、事件、边、终态、状态角色 | 本项目 `StateMachineEdgeAcrossEndsTest` 靠正则解析 TS 与 Java 的做法 |
| ai-shop 兼容 | `Map<S, Set<S>> projection()` —— 投影出纯图 | ai-shop 现有 `canTransit(graph, from, to)` 调用点可先不动 |

### 3.2 状态角色（#19 工单引擎用，其他域可忽略）

| 角色 | 含义 | 本项目工单 | ai-shop 售后 |
|---|---|---|---|
| `INITIAL` | 新建落这里 | `CREATED` | `APPLIED` |
| `ASSIGNED` | 已有受理人，SLA 开始计 | `DISPATCHED` / `ACCEPTED` / `PROCESSING` | `APPLIED`（受理人 = 商家） |
| `WAITING_EXTERNAL` | 等外部，**SLA 暂停** | — | `REFUNDING`（等支付回执）· 等用户寄回 |
| `AWAITING_VERIFY` | 待复核 | `DONE` | — |
| `ESCALATED` | 已升级 | （接管后仍在 `PROCESSING`，另记升级标记） | `ARBITRATING` |
| `TERMINAL` | 终态 | `CLOSED` | `REFUNDED` / `CLOSED` / `REJECTED`* |

\* ai-shop 的 `REJECTED` 可以申诉转 `ARBITRATING`，所以**不是**终态 —— 它现有注释里把它列进终态是错的，接入时会被「终态由图推导」直接纠正。

### 3.3 持久化（#17a）

| 能力 | 做法 | 替换 |
|---|---|---|
| 条件更新 | `UPDATE … SET status = :to WHERE id = :id AND status = :from [AND step = :step]`；影响 0 行 → `StateChanged`（HTTP 409） | 合同审批、调拨、商机转化里各自写的「按原状态条件更新，并发只一人赢」 |

## 四、`neargo-approval`（#18）

### 4.1 模型

| 概念 | 说明 |
|---|---|
| 审批对象 subject | `(subject_type, subject_no)`，**不透明引用**：组件不认识合同、商品 |
| 流程定义 flow | **代码定义**（首版）：有序步骤。每步 = 审批人解析器 + 进入条件 + 或签 / 会签 |
| 审批人解析器 | SPI `ApproverResolver`：按权限码（本项目默认）、按角色、按指定人、按「对象归属的负责人」 |
| 进入条件 | `Predicate<Subject>`：合同的「是否需要财务会签」就是一个进入条件，不再是 service 里的 `if (needsCosign(c))` |
| 轮次 round | 驳回后再提交 = 新一轮，**每一轮的审批人与意见都是结构化的一行**。本项目合同现在重提时会把上一轮的 `auditedBy` / `auditNote` / `financeAuditedBy` / `financeAuditNote` **全部清空**，主行上只剩最新一轮；前几轮只剩 `loc_contract_log` 里的一句文字，查「上次是谁、因为什么驳回的」要去翻日志 |

### 4.2 表

| 表 | 关键列 |
|---|---|
| `wf_approval` | `approval_no` · `subject_type` · `subject_no` · `flow_code` · `round` · `status`（PENDING / APPROVED / REJECTED / WITHDRAWN）· `current_step` · `submitted_by` · `submitted_at` · `version` |
| `wf_approval_task` | `approval_no` · `round` · `step` · `assignee_type` · `assignee_no` · `result` · `reason` · `acted_by` · `acted_at` |

审批状态本身用 #17 状态机管；两张表按 `neargo-data` 隔离登记（租户 + 数据范围锚点，见 §九 #2）。

### 4.3 内建规则（两边都各写过一遍的四条）

| 规则 | 默认 | 可关 | 本项目出处 | ai-shop 出处 |
|---|---|:-:|---|---|
| 提交人不能审自己 | 开 | 按流程 | 合同审批「待我审批」过滤 | 商品审核 |
| 驳回必须填原因 | 开 | 否 | 合同 `error.common.reason_required` | 商品 / 商户申请驳回 |
| 只有提交人能撤回，且只在待审 | 开 | 否 | 合同 `withdraw_submitter_only` | — |
| 并发只一人赢 | 开 | 否 | 合同「按原状态 + 原环节条件更新」 | — |

### 4.4 与业务域的边界

| 组件做 | 业务域做 |
|---|---|
| 流转审批、记录每一步、算「待我审批」 | 自己的状态列（合同 `DRAFT/PENDING/SIGNED…`） |
| 审批结束发 `ApprovalCompleted(subjectType, subjectNo, APPROVED/REJECTED, round)` | 监听该事件，推进**自己的**状态机（合同 `PENDING → SIGNED`） |
| 不写任何业务表 | 不直接写 `wf_*` 表 |

## 十、不做

| 不做 | 为什么 |
|---|---|
| BPMN 引擎（Flowable / Camunda） | 两个产品的流程都 ≤ 3 步；引擎带 20+ 张运行时表与 XML 建模，团队里没人运维它；我们缺的是「状态机统一 + 短审批链 + 工单内核」，不是图形化流程 |
| 可视化流程设计器 | 同上；且流程由研发定义，运营只调 SLA |
| 共用服务形态 | 迁移必须与业务写同事务（§〇 #4） |
| 跨服务 Saga | 两个产品都是单体优先（ADR-020），没有跨服务长事务 |
| 一次性把 14 个状态机和 7 张日志表全换掉 | 逐个迁、每个都有「不改测试仍绿 + 负对照」才算完成 |
