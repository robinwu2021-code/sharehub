## 〇、先选要什么

| 你要什么 | 依赖 | 建表 | 要写的东西 | 目标耗时 |
|---|---|:-:|---|---|
| 只是让状态流转不再手写 | `workflow-api` | 否 | 一个状态机定义 | ≤ 30 分钟 |
| 再加并发保护与统一流转日志 | `workflow-core` | 自动 | 上面 + `ActorContextProvider` | ≤ 1 小时 |
| 审批 | `workflow-core` | 自动 | 流程定义 · 结果回调 · 两个 Provider | 第一个流程 ≤ 半天 |
| 工单 | `workorder-core` | 自动 | 状态机 · 类型定义 · 锚点解析 · 两个 Provider | 第一个类型 ≤ 2 天 |

ai-erp（jOOQ）、ai-neargo 只要第一行；ichain / tradeagent 要审批；powerbank / ai-shop 全要。

## 一、依赖

```xml
<!-- 只要状态机 -->
<dependency><groupId>ai.neargo.workflow</groupId><artifactId>workflow-api</artifactId><version>${workflow.version}</version></dependency>
<!-- 审批（含上面）-->
<dependency><groupId>ai.neargo.workflow</groupId><artifactId>workflow-core</artifactId><version>${workflow.version}</version></dependency>
<!-- 工单（含 workflow-api）-->
<dependency><groupId>ai.neargo.workorder</groupId><artifactId>workorder-core</artifactId><version>${workorder.version}</version></dependency>
<!-- 测试：契约测试与架构规则 -->
<dependency><groupId>ai.neargo.workflow</groupId><artifactId>workflow-core</artifactId><version>${workflow.version}</version><classifier>tests</classifier><scope>test</scope></dependency>
```

业务域模块（如 powerbank 的 `sharehub-svc-*`）只依赖 `*-api`；启动模块（`sharehub-app`）依赖 `*-core`。不要求父 POM。

Nexus 就绪之前的共用办法见 [07 落地计划](./07-落地计划.md) §二。

## 二、只要状态机

| 步 | 做什么 |
|:-:|---|
| 1 | 状态值改成枚举（已是则跳过）；再定义一个事件枚举 |
| 2 | 写 `StateMachine.builder(code, S.class, E.class)…build()`，放在状态枚举旁边的 `static final` 字段（05 §1.1） |
| 3 | 手写的 `if (status.equals(…))` 与迁移表换成 `SM.next(from, event)` |

从现有三种写法迁：

| 现在 | 怎么迁 |
|---|---|
| powerbank：`Map<事件, Map<起, 止>>` | 逐行照抄成 `.edge(事件, 起, 止)`；`check` / `eventOf` 改名 `next` / `eventFor` |
| ai-shop：`Map<起, Set<止>>` + `assertXxxTransit(from, to)` | **每条边补一个事件名**（要懂业务的人做）；旧调用点先改成对 `SM.projection()` 判断，行为不变，再逐个改为按事件 |
| ai-erp：`InvoiceFsm.legalTargets` / `assertLegal` | 同 ai-shop；状态已是枚举，只补事件枚举 |

证明没改行为：用 `StateMachineParityCheck`（tck）把旧表与 `projection()` 比一次；既有用例全绿；从定义里删一条边 → 至少一条用例变红。

## 三、审批

### 3.1 配置

```yaml
neargo:
  workflow:
    system-code: SHAREHUB          # 本产品在共用表里的代号
    mode: embedded                 # 形态 A；以后切服务改 remote
    store:
      tenant-column: tenant_id     # ai-shop 写 tenant_no；无租户项目不影响
```

建表由模块自己的 Flyway 实例完成，历史表 `flyway_schema_history_workflow`，**不占你的 V 号**，也不用改你的 `spring.flyway.locations`。

### 3.2 五步

| 步 | 做什么 | powerbank 的例 |
|:-:|---|---|
| 1 | 实现 `ActorContextProvider`：当前人 + 权限 + 角色 + 队列 + 租户 | 从 `StaffContext` 取工号与权限集合 |
| 2 | 有数据范围的项目实现 `ScopeConditionProvider` | 把员工的数据范围翻成「锚点 1 ∈ 站点集合」 |
| 3 | `@Bean ApprovalFlow`：步骤、条件（属性判定）、审批人规则 | 合同：运营步 + 条件会签步 |
| 4 | 业务的送审入口里：算好属性与锚点 → `workflow.submit(…)` | `needsCosign(c)` 算成属性 |
| 5 | 实现 `ApprovalOutcomeHandler`：**按轮次幂等地**推进业务状态 | `markSignedIfPending(no, round)` |

### 3.3 业务侧只改两处

| 原来 | 现在 |
|---|---|
| service 里 `approve / reject / withdraw / cosign` 各一段手写逻辑 | 删掉；决定、撤回、领取都走 `WorkflowClient` |
| 业务表上的审批人、意见、环节列 | 不再写；展示读 `workflow.detail(…)`。旧列保留只读 |

### 3.4 ichain / tradeagent 的 `AuditTask` 对照

| `AuditTask` | 模块 |
|---|---|
| `targetType` · `targetId` | `subject_type` · `subject_no` |
| `queue` | `ApproverRule.queue(…)`；成员由 `ActorContext.queues` 给 |
| `priority` | 送审属性 `priority`，`myTasks` 按它排序 |
| `status` PENDING / CLAIMED / APPROVED / REJECTED / CANCELLED | 任务 `OPEN / CLAIMED / DONE / CANCELLED` + 决定 `APPROVE / REJECT` |
| `assigneeId` · `claimedAt` · `decision` · `reason` · `decidedAt` | `claimed_by` · `claimed_at_ms` · `decision` · `reason` · `decided_at_ms` |
| `evidence` | `nwf_approval.evidence` |

## 四、工单

### 4.1 配置

```yaml
neargo:
  workorder:
    system-code: SHAREHUB
    mode: embedded
    store:
      tenant-column: tenant_id
```

### 4.2 七步

| 步 | 做什么 | 例 |
|:-:|---|---|
| 1 | 审批的第 1、2 步（两个 Provider 两个模块共用一份实现） | —— |
| 2 | 写该工单类型的状态机，并**给状态标角色**（02 §5.3） | 运维工单：`DONE` 标 `AWAITING_VERIFY` |
| 3 | `@Bean WorkOrderType`：图 · 编号前缀 · 受理方类型 · 派单方式 · SLA 规则组 · 锚点槽位含义 | 05 §3.1 |
| 4 | 实现 `ScopeAnchorResolver`：从对象算出三个锚点 | 设备 → 站点、代理 |
| 5 | 把原来每个动作一个的 service 方法改成 `workOrders.fire(no, event, cmd)` | 接单、处理、完工、驳回、返工、关闭 |
| 6 | 需要业务联动的实现 `WorkOrderTransitionHandler`（幂等） | 完工 → 回写设备状态 |
| 7 | 灌 SLA 规则与日历；把 `sweepSla` 挂进你的定时任务 | 见 4.3 |

### 4.3 定时任务壳

模块不依赖任何任务框架。在你自己的任务框架里：

```java
@Component
class WorkOrderSlaSweepJob implements JobHandler {             // 你项目自己的任务接口
    private final WorkOrderClient workOrders;
    public void run() { while (workOrders.sweepSla(500) == 500) { } }
}
```

形态 B 下服务自己调度 SLA 扫描与领取超时，产品不用挂。

### 4.4 业务侧怎么改

| 原来 | 现在 |
|---|---|
| 自己的派单、抢单、接管、SLA 表与扫描 | `WorkOrderClient` + `nwo_sla_rule` |
| 自己的时间线表 | `workOrders.detail(no).timeline()` |
| 业务专有字段（设备号、站点名、寄回单号…） | 只展示的放 `ext`；要按它查或控权限的放 `subject` 或锚点 |
| 受理方停用时的改派逻辑 | 停用处调一次 `workOrders.reassignFrom(assignee, reason)` |

## 五、暴露接口

| 你的项目 | 做法 |
|---|---|
| 控制器返回平铺对象、切面包信封（powerbank） | `neargo.workflow.web.enabled: true`（工单同理），设 `base-path` |
| 其他（`ApiResult` / `Result` / `PageData` …） | 写薄控制器，如下 |

```java
@RestController
@RequestMapping("/admin/approvals")
class AdminApprovalController {
    private final WorkflowClient workflow;

    @GetMapping("/tasks/mine")
    ApiResult<PageResult<TaskView>> mine(TaskQuery q) { return ApiResult.ok(workflow.myTasks(q)); }

    @PostMapping("/tasks/{taskNo}/claim")
    ApiResult<TaskView> claim(@PathVariable String taskNo) { return ApiResult.ok(workflow.claim(taskNo)); }

    @PostMapping("/{approvalNo}/decide")
    ApiResult<ApprovalView> decide(@PathVariable String approvalNo, @RequestBody DecideReq r) {
        return ApiResult.ok(workflow.decide(approvalNo, r.decision(), r.reason()));
    }
    record DecideReq(Decision decision, String reason) { }     // 请求体一律 record 白名单
}
```

前端：按钮用出参里的 `actions`（当前状态可走事件 ∩ 当前用户有权限的）；状态图用 `GET …/graphs/{code}`；**前端不再自己维护迁移表**。

## 六、切到独立服务（形态 B）

| 步 | 做什么 |
|:-:|---|
| 1 | 部署 `workflow-svc` / `workorder-svc`，独立库；在服务的系统登记里加本产品的 `system_code`、凭证、回调地址 |
| 2 | 迁数据：把本产品库里 `nwf_*` / `nwo_*` 的行按 `system_code` 导入服务库（表结构相同） |
| 3 | 产品配置改 `mode: remote`，填 `remote.base-url` 与 `remote.credential` |
| 4 | 业务代码不改 —— 前提是满足 03 §四的 R1 ~ R4；上线前跑一遍契约测试 |
| 5 | 撤掉产品侧挂的 SLA 扫描与领取超时任务（服务自己调度） |

## 七、上线前检查

| # | 检查 |
|:-:|---|
| 1 | `ActorContextProvider` 在定时任务线程里返回 `SYSTEM`，不抛异常 |
| 2 | 用只有单站点 / 单商家范围的账号查列表：**看不到别人的** |
| 3 | 形态 A：结果回调里抛异常 → 审批决定一起回滚（写一条用例） |
| 4 | 结果回调交付两次 → 业务状态只变一次（契约测试 `OutcomeHandlerContract`） |
| 5 | 结果回调里没有调用 `WorkflowClient` / `WorkOrderClient`（契约测试） |
| 6 | 表前缀、租户列名定稿后才首次启动（建表后再改要迁移） |
| 7 | 旧的迁移表 / 审批列 / 日志表：保留只读，不物理删除 |

## 八、常见坑

| 坑 | 表现 | 做法 |
|---|---|---|
| 在提交后的事件里推进业务状态 | 审批已通过，业务单还在待审 | 用 `ApprovalOutcomeHandler`（形态 A 在事务内） |
| 结果回调不幂等 | 切到形态 B 后同一审批把业务推了两次 | 以 `(subjectNo, round)` / `(orderNo, seq)` 为键，条件更新 |
| 流程条件里想写 lambda | 编译不过 | 在提交前算成属性，条件写 `attr(…).isTrue()` |
| 把 `ext` 当查询条件 | 列表慢、数据范围失效 | 放 `subject` 或锚点 |
| 给有出边的状态标 `TERMINAL` | 启动失败 | 终态由图推导 |
| 同一对「起 → 止」有两个事件还用 `eventFor` | `AmbiguousEventException` | 明确传事件 |
| 表前缀配成空 | 启动失败 | `order` / `case` 在 MySQL 与 PostgreSQL 都是保留字 |
| 队列任务没领取就决定 | `not_claimed` | 先 `claim` |
