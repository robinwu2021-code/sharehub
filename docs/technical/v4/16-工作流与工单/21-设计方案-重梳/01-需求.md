# 01 · 需求

> 所属：[21 OpsKit 设计方案](./README.md) · 状态：**已定**（2026-09-27）
> 原则：需求按**产品**写，不按某个现有系统写。现有系统的诉求只作为「这个通用能力是否覆盖得到」的检验样本，放在附录 A。

---

## 一、问题与机会

| 观察 | 含义 |
|---|---|
| 组织内五个后端各自手写状态流转、审批、工单：三种互不兼容的状态机、七张流转日志表、四份同样的审批规则（实测，见 [旧 01 §一](../01-需求.md)） | 这是**每个运营系统都要做一遍**的通用能力，不是某个业务的特有逻辑 |
| 做法相同的地方远多于不同的地方：谁来办、办到哪、超没超时、谁能看见、全程留痕 | 可以产品化 |
| 市面产品（Jira Service Management · Zendesk · ServiceNow · 钉钉 / 飞书审批）各覆盖一块，嵌入其他平台的能力弱、按席位收费不适合平台转售 | 「**可嵌入、可转售的运营基础能力**」有空间 |

## 二、产品定位

| 项 | 定 |
|---|---|
| 一句话 | 给运营系统的「事情找人」基础能力：流程、审批、工单、时限，以 API、嵌入组件和独立控制台三种方式交付 |
| 不是什么 | 不是 BPM 建模平台（不画 BPMN）· 不是低代码（不生成业务应用）· 不是项目管理工具 · 不替业务管业务对象 |
| 差异 | ① **平台伙伴模式**：伙伴一次定义、给自己的每个客户开空间，客户数据互相隔离 ② **嵌入优先**：界面组件继承宿主皮肤与身份 ③ **业务解耦**：服务从不回调业务、从不读业务库，业务只收事件 |

## 三、客户与使用方式

| 客户类型 | 例子 | 怎么用 | 身份从哪来 |
|---|---|---|---|
| **平台伙伴** | ShareHub（其运营商各一个空间）、ai-shop（其商户各一个空间） | API 接入 + 嵌入组件进自己的控制台 | 伙伴平台的令牌（联邦） |
| **直接客户** | 没有自有运营平台的企业 | OpsKit 独立控制台 | 客户自己的 IdP（OIDC）；内置账号二期 |
| **内部系统** | ichain · tradeagent · ai-erp 的审核与流转 | 只用 API（及纯 Java 状态机库） | 应用凭证代成员操作 |

| 使用方式 | 说明 |
|---|---|
| API | 全部能力可经 HTTP 使用；OpenAPI 为契约真源 |
| 嵌入组件 | 页面级组件嵌进宿主控制台，继承宿主身份与皮肤（前端工程见 [15](../15-前端方案-独立可嵌入与皮肤.md) / [17](../17-前端模块化集成.md) / [22](../22-前端方案/README.md)） |
| 独立控制台 | 没有宿主的客户直接使用 |
| 事件 | webhook 推送一切状态变化，业务据此推进自己的状态 |
| 状态机库 | 纯 Java 库，业务进程内用，不经服务（只要「合法迁移校验」时） |

## 四、通用概念（产品词汇表）

| 概念 | 定义 |
|---|---|
| **账户** Account | 签约主体：一个伙伴平台或一家直接客户；计费、套餐、配额的单位 |
| **空间** Workspace | 数据隔离单位；一个账户下 1..N 个（伙伴给自己的每个客户开一个）|
| **应用** App | 接入 OpsKit 的外部系统，持有凭证；可代空间内成员操作 |
| **成员** Member | 空间里的一个人；带外部引用号（宿主里的用户编号）与**属性**（如 `partyType=AGENT`）|
| **组** Group | 成员的集合；可作为团队、队列（可领取）、审批组、派单池 |
| **角色** Role | 产品权限的组合，由租户定义；绑定到成员或组 |
| **外部联系人** Contact | 不登录的相关方（如报障的最终用户），可作为发起人 / 关注人 |
| **流程定义** Process | 状态 + 迁移 + 状态上的门（审批 / 外部确认 / 定时）|
| **流程实例** Instance | 一件事按某流程的一次运行；带数据、参与者、范围标签、时限 |
| **任务** Task | 需要人做的一步：办理或审批；有候选人、办理人、到期 |
| **工单类型** Ticket Type | 租户定义：用哪个流程、有哪些字段、优先级与解决结果选项、派单策略、SLA 策略 |
| **工单** Ticket | 某类型的一条记录；状态来自其流程实例 |
| **范围标签** Scope Tag | `维度:值`，多值；决定谁能看见 |
| **SLA 策略** | 指标（首次响应 · 解决 · 自定义）× 起算 / 暂停 / 停止条件 × 目标矩阵 × 工作日历 |
| **选项集** Option Set | 优先级、解决结果、来源等可枚举值，租户定义 |

## 五、角色（产品角色，不是某个客户的岗位）

| 产品角色 | 能做什么 | 在某客户那里可能是 |
|---|---|---|
| 发起人 Requester | 提交工单 / 发起审批，查看自己的进度，撤回 | 用户、BD、商户 |
| 办理人 Agent | 领取、处理、流转、备注 | 运维员工、代理、商家客服 |
| 审批人 Approver | 通过 / 驳回 | 运营、财务 |
| 负责人 Owner | 对一件事的结果负责，可改派、升级 | 班组长、区域经理 |
| 关注人 Watcher | 只接收进展 | 相关方 |
| 空间管理员 | 管理流程、工单类型、字段、SLA、组、角色 | 客户的运营负责人 |
| 账户管理员 | 管理空间、应用、模板、计费 | 伙伴平台的运维 |
| 平台运维（我们） | 管理账户与系统级配置 | —— |

「员工 / 代理 / 商家」「运营 / 财务」这类岗位**不进产品概念**：客户用组、属性和角色去表达。

## 六、能力需求

### 6.1 平台（PLT）

| 编号 | 需求 | 级 |
|---|---|:-:|
| PLT-01 | 账户 → 空间两级；一切运行时数据按空间隔离，跨空间访问 = 不存在 | P0 |
| PLT-02 | 定义（流程、工单类型、SLA 策略、选项集）可在**账户级**作为模板被所有空间继承，空间可覆盖 | P0 |
| PLT-03 | 应用凭证：一个应用可被授权访问账户下全部或部分空间；凭证只显示一次、可轮换 | P0 |
| PLT-04 | 令牌联邦：按签发方识别账户 / 空间，按声明映射取成员、组、角色、范围标签；首次出现的成员**即时开通** | P0 |
| PLT-05 | 成员目录：成员 · 组 · 组成员 · 角色 · 角色绑定；提供同步 API（批量 upsert） | P0 |
| PLT-06 | 产品权限目录固定（§九）；角色由租户组合 | P0 |
| PLT-07 | 工作日历：时区 · 每周时段 · 节假日；空间级 | P0 |
| PLT-08 | 事件订阅与 webhook：签名 · 至少一次 · 退避重试 · 投递记录 · 手工重投 | P0 |
| PLT-09 | 审计日志：配置变更、权限变更、凭证操作 | P1 |
| PLT-10 | 套餐与配额：空间数、记录数、API 速率 | P2 |

### 6.2 流程（PRC）

| 编号 | 需求 | 级 |
|---|---|:-:|
| PRC-01 | 流程定义 = 状态（带类别）+ 迁移；定义是数据，版本 = 内容哈希，在途实例按启动时版本走完 | P0 |
| PRC-02 | 状态类别固定五种：`NEW` · `IN_PROGRESS` · `WAITING` · `DONE` · `CANCELLED`；通用行为（时限暂停 / 停止、统计口径、关闭）只看类别，不看状态名 | P0 |
| PRC-03 | 迁移可配置：谁能走（参与者角色 / 角色 / 组 / 权限）· 条件（字段比较）· 必填（字段、评论）· 后置动作（派单、设字段、加关注人） | P0 |
| PRC-04 | 条件只支持字段比较（= ≠ ∈ > ≥ < ≤ 存在 为空），至多两层 all / any 组合；**不支持表达式** | P0 |
| PRC-05 | 迁移为条件更新，并发只一人成功，其余 409 | P0 |
| PRC-06 | 每次变化写流转日志，与变化同事务 | P0 |
| PRC-07 | **审批门**：进入状态即发起审批；结果自动触发配置好的迁移 | P0 |
| PRC-08 | **外部确认门**：进入状态即发事件，等外部系统回复「确认 / 驳回」（带超时）后自动迁移 | P0 |
| PRC-09 | **定时门**：在状态停留满时长后自动迁移（如「已解决 7 天后自动关闭」） | P1 |
| PRC-10 | 参与者：发起人 · 负责人 · 办理人 · 关注人 + 租户自定义参与者角色 | P0 |
| PRC-11 | 纯 Java 状态机库：同一套定义模型的进程内版本（校验 · 可走事件 · 反查 · 投影） | P1 |

### 6.3 任务与审批（TSK / APV）

| 编号 | 需求 | 级 |
|---|---|:-:|
| TSK-01 | 任务两类：办理、审批；统一候选模型（成员 · 组 · 角色 · 权限 · 按字段取人） | P0 |
| TSK-02 | 领取 / 放回；领取超时自动放回并留痕；并发领取只一人成功 | P0 |
| TSK-03 | 指派 · 转派（必填原因）；已领取 / 已指派只能由当前办理人完成 | P0 |
| APV-01 | 审批步骤有序；每步可设进入条件；或签 / 会签（会签要求审批人可枚举：成员列表、组、按字段取人） | P0 |
| APV-02 | 内建规则：① 不能审自己提交的（可关）② 驳回必填原因（不可关）③ 只有发起人能在待审时撤回 ④ 并发只一人赢 ⑤ 同一轮同一人不能审两步（可关） | P0 |
| APV-03 | 轮次：驳回 / 撤回后再提交为新一轮，每轮每步决定结构化保留 | P0 |

### 6.4 工单（TKT）

| 编号 | 需求 | 级 |
|---|---|:-:|
| TKT-01 | 租户定义工单类型：流程 · 字段集 · 优先级选项集 · 解决结果选项集 · 编号前缀 · 派单策略 · SLA 策略 · 范围标签的来源字段 | P0 |
| TKT-02 | 字段类型：文本 · 长文本 · 数字 · 金额 · 日期时间 · 单选 · 多选 · 成员 · 组 · 附件 · 外部引用（类型 + 编号 + 快照）；必填 / 创建时可填 / 可筛选 | P0 |
| TKT-03 | 可筛选字段支持按值筛选与排序（列表页每个筛选控件对应一个查询参数） | P0 |
| TKT-04 | 派单策略：手工 · 队列领取 · 轮询 · 最少负载 · 按字段 · 外部指定（发事件等外部回填） | P0 |
| TKT-05 | 去重：同一去重键已有未结单时附加到该单；并发下也只有一张 | P1 |
| TKT-06 | 升级 / 接管 · 合并 · 批量改派（某人不可用时） | P1 |
| TKT-07 | 评论（公开 / 内部）· 附件 · 时间线（迁移、派单、评论、SLA、审批一条流水） | P0 |
| TKT-08 | 可见性：有「全部可见」权限 ∪ 是参与者 ∪ 范围标签与自己相交 | P0 |
| TKT-09 | 统计：按类型 / 组 / 办理人 / 时间段 / 范围标签的数量、达标率、平均时长；看板卡片可点进同口径列表 | P1 |

### 6.5 时限（SLA）

| 编号 | 需求 | 级 |
|---|---|:-:|
| SLA-01 | 策略含多个指标；每个指标有起算、暂停、停止条件（按状态类别、状态、迁移、首次公开评论） | P0 |
| SLA-02 | 目标按条件矩阵取（如 优先级 = 高 且 类型 = 维修 → 响应 30 分钟 / 解决 4 小时），可指定工作日历 | P0 |
| SLA-03 | 预警（达到目标的 N%）· 超时 · 达标，各发事件 | P0 |
| SLA-04 | 条件变化（如改优先级）按新目标重算，扣除已暂停时长 | P1 |

### 6.6 集成（INT）

| 编号 | 需求 | 级 |
|---|---|:-:|
| INT-01 | 写请求带幂等键；同键同内容返回首次结果，不同内容 409 | P0 |
| INT-02 | 应用代成员操作：请求体给成员外部引用号，不存在即开通 | P0 |
| INT-03 | 对账：按外部引用（业务对象）查全部实例、工单、审批历史 | P0 |
| INT-04 | 服务**从不同步调用业务、从不读业务库**（唯一例外：令牌校验的 JWKS / 内省） | P0 |

## 十、不做（本期）

| 不做 | 为什么 |

## 附录 A · 现有系统如何适配（它们适应产品，不是产品适应它们）

| 现有系统的做法 | 用 OpsKit 的通用概念表达 | 现有系统要改什么 |
|---|---|---|
| ShareHub：多运营商租户 | 一个**账户**（伙伴），每个运营商一个**空间**；定义放账户级作模板 | 开通空间的时机接到运营商开户流程 |
| ShareHub：员工 / 代理两类受理方 | 都是**成员**；代理加属性 `partyType=AGENT`，按代理公司建**组** | 令牌里带成员号与组；或调同步 API |
| ShareHub：站点 / 代理数据范围（`DataScope`） | **范围标签** `site:{站点号}` · `agent:{代理号}`；成员的可见标签由令牌声明给出 | 把 `DataScope` 翻译成声明；工单类型把「站点」「代理」字段登记为标签来源 |
| ShareHub：权限码（`location:contract:audit` …） | 宿主权限经声明映射到 OpsKit **角色**；审批步骤候选写「角色：合同审批」 | 建一份权限 → 角色映射 |
| ShareHub：合同审批（运营 → 条件触发财务会签；通过前查时间段不重叠） | 流程：`草稿 → 待运营审 → [需要会签? 待财务签] → 生效确认中 → 已生效 / 已驳回`；两级审批门；「时间段不重叠」用**外部确认门** | 提交时算好 `needsCosign` 字段；收 `awaiting_confirmation` 事件后校验并回复 |
