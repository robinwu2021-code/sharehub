# 22 · 多区集成方案（Multi-Zones 模式，自托管）

> 所属：[16 工作流与工单](./README.md) · 状态**待确认**（2026-09-27）· 调研依据：[19](./19-前端模块化-业界方案调研.md) §三 B 类
> 用户定：「可以考虑这个方案，只需要能各自开发，并集成到一起即可」。
> 目标因此收敛为两条：**① 各系统各自开发、各自发布；② 在同一个域名、同一个外壳下呈现为一个产品。** 不要求同屏组合，不要求跨技术栈嵌入。
> 下文「实测」均为 2026-09-27 从仓库核出。

---

## 〇、一页结论

| 项 | 定 |
|---|---|
| 形态 | **同域、按路径分区**：每个系统是一个「区」（zone），独立仓库、独立构建、独立发布；nginx 按路径前缀把请求交给对应的区 |
| 为什么不用 `@vercel/microfrontends` | 它的生产路由由 Vercel 平台托管；我们在腾讯云，且各区都是静态导出（不支持 rewrites / middleware）→ 路由层用 **nginx**，其余照 Multi-Zones 的约定 |
| 外壳 | 抽成共享包 **`@neargo/ops-shell`**，每个区都用它渲染顶栏与菜单 → 跨区看起来是同一个产品 |
| 身份 | **同源** → 登录一次各区通用，不需要跨域 SSO |
| 代价 | 跨区导航是整页加载；外壳包要各区对齐版本 |
| 先例 | 生产 nginx 已在同域 `/c/` 下挂着 C 端 H5，这个方案是把同一手法用到运营端 |

---

## 一、分区

| 区 | 路径前缀 | 产物 | 拥有者 | 后端 |
|---|---|---|---|---|
| 运营台（宿主区） | `/` | ops-web 静态导出 | ShareHub | `/api/**` → sharehub:8082 |
| **流程与工单** | **`/flow/`** | **flow-console 静态导出** | 平台 | **`/api/flow/**` → flow-svc** |
| C 端 H5（已有） | `/c/` | c-app 静态 | ShareHub | 同上 |

登录页、首页、个人设置属于宿主区；各区只拥有自己前缀下的页面。

---

## 二、先例：`/c/` 已经这样跑了（实测 `deploy/tencent/nginx/powerbank.ichain.top`）

```nginx
root /data/app/powerbank/web/ops-web;          # 运营端出在 /

location ^~ /c/ {                               # C 端 H5 出在 /c/
    alias /data/app/powerbank/web/c-app/;
    try_files $uri $uri/ /c/index.html;
    location ~* \.(js|css|woff2?|svg|png|jpg|jpeg|webp)$ { expires 30d; access_log off; }
}
```

flow 区照抄，只多一段 API 反代：

```nginx
location ^~ /flow/ {
    alias /data/app/powerbank/web/flow-console/;
    try_files $uri $uri/ $uri.html /flow/index.html;
    location ~* \.(js|css|woff2?|svg|png|jpg|jpeg|webp)$ { expires 30d; access_log off; }
}
location ^~ /api/flow/ { proxy_pass http://127.0.0.1:<flow-port>; include /etc/nginx/proxy_params; }
```

`^~` 前缀匹配取**最长前缀**，所以 `/api/flow/` 自然优先于既有的 `/api/`，与书写顺序无关。

## 三、区契约：每个区必须遵守的五条

| # | 约定 | 为什么 | 怎么守 |
|:-:|---|---|---|
| 1 | **`basePath` = 自己的前缀**（flow 区为 `/flow`） | 静态资源与路由都挂在前缀下，不与别区撞 | ops-web 的 `next.config.ts` **已支持** `NEXT_PUBLIC_BASE_PATH` → basePath/assetPrefix（实测），flow-console 同模板 |
| 2 | **外壳一律用 `@neargo/ops-shell`** | 跨区视觉一致、菜单一致 | 区内不得自写顶栏 / 侧栏；架构测试禁止 |
| 3 | **会话、主题、语言只经外壳包读写** | 同源下 `localStorage` 天然共享，但各区若各自读写就会各写各的 key | 外壳包导出 `getSession()` / 主题 / 语言三个入口，区内禁止直接碰这些 key |
| 4 | **跨区链接用 `<a href>`，区内链接用 `<Link>`** | Next 的 `<Link>` 会**自动加 basePath**：在 flow 区里写 `<Link href="/sites">` 会变成 `/flow/sites`，打到 404 | 外壳包的菜单按「目标是否在本区前缀内」自动选 `<Link>` 或 `<a>`；页面内跨区跳转用外壳包导出的 `zoneHref()` |
| 5 | **401 统一跳宿主区** `/login?next=<当前完整路径>` | 登录只在宿主区有 | 外壳包统一处理；现有 `lib/api/session.ts` 的 `window.location.replace(LOGIN_PATH)` 需补 `next` 参数（现在登录后回不到原页） |

## 四、外壳：抽成共享包

### 4.1 现状（实测）

| 事实 | 含义 |
|---|---|
| 外壳在 `ops-web/components/layout/`：`app-shell` · `header` · `rail` · `secondary-nav` · `theme-switcher` · `lang-switcher` · `operator-switcher` · `phase-guard` 共 8 个文件 | 抽包的边界现成，不用重新划 |
| 菜单是代码里的静态常量 `lib/nav.ts` 的 `NAV`，不是从接口拉取 | flow 区拿不到宿主的菜单，必须把菜单变成可共享的数据 |
| ai-shop 的 ops-web 有同名外壳文件，但**已经分叉**：7 个同名文件各差 19～101 行，还多了 `command-palette` · `notify-bell` · `scroll-hint` | 同一模板 fork 后各自演化；ai-shop 接入时要先合并分叉 |

### 4.2 包的内容

| 导出 | 说明 |
|---|---|
| `<OpsShell zone nav>` | 顶栏 + Rail + 二级菜单 + 内容区；`zone` 是本区前缀，决定链接用 `<Link>` 还是 `<a>` |
| `getSession()` · `useSession()` | 读宿主的登录态（同源共享）；401 处理 |
| 主题 · 语言 | 与现在 `lib/stores/theme.ts` · `locale.ts` 同一套持久化 key |
| `zoneHref(path)` | 页面内跨区跳转 |
| 设计 token | 外壳与各区共用的 CSS 变量；包内同样跑 `design-tokens` 卡口 |

### 4.3 菜单归谁

| 阶段 | 做法 |
|---|---|
| **首版** | **菜单仍归宿主**：宿主在 `lib/nav.ts` 加 `/flow/...` 的叶子（放组末尾），沿用既有的菜单迁移 SQL → 三语 → 快照与 `nav-seed` 卡口；宿主构建时额外导出一份 `/shell/nav.json`，flow 区运行时拉取渲染同一棵菜单 |
| 区多了以后 | 各区各自导出 `nav.json`，外壳按清单（manifest）合并 —— 业界门户的通行做法（19 §4.3）；等第三个区出现再做 |

首版这样选的理由：权限码、菜单种子、三语与卡口都已经围着 `lib/nav.ts` 建好了，菜单改由别处定义会绕开这些卡口。

## 五、身份与权限

| 项 | 做法 |
|---|---|
| 登录 | 只在宿主区；同源 → 令牌在 `localStorage` 里各区共享 → **登录一次各区通用，无需跨域 SSO** |
| flow 区调接口 | 带宿主令牌请求 `/api/flow/**` → flow-svc 回源 ShareHub 内省（令牌是不透明的 `stk_` + UUID、会话在 Redis，无法离线验签），短缓存 |
| 权限 | 菜单与按钮按登录下发的 `perms` 过滤（外壳包负责菜单）；真正的闸在 flow-svc；flow 的权限码进 ShareHub 权限真源表（16 的 X1） |
| 与 21 的接口面对齐 | flow 区页面调的是 [21](./21-设计方案-重梳/README.md) 定的**界面面** `/api/flow/ui/v1/**`（nginx 的 `/api/flow/` 前缀已覆盖）；21 的 C5 规定「带业务前置校验的动作」要转给宿主后端 —— 多区下宿主后端与 flow 区**同源**，页面直接调宿主 `/api/**` 即可，不需要额外代理 |
| 以后 | 按 RFC 10017 改 BFF：会话改为 `Path=/` 的 HttpOnly cookie，同样全区共享、且令牌离开浏览器 —— 分区方案不用改 |

## 六、本地开发

| 项 | 做法 |
|---|---|
| 各自开发 | 每个区单独 `pnpm dev`，互不依赖；单独开发 flow 区时可用外壳包的 mock 会话 |
| 联调 | 一个本地代理把各 dev server 拼成同域：`/` → ops-web、`/flow/` → flow-console、`/api/**` → 后端；**要放行 WebSocket 升级**，否则 HMR 断 |
| 为什么不用 Next 的 rewrites | 静态导出模式不支持 rewrites（Next 文档），dev 里也不能靠它 |

---

## 七、发布

| 项 | 做法 |
|---|---|
| 独立发布 | 每个区独立流水线，产物落各自目录（`web/ops-web/` · `web/flow-console/`），互不覆盖 |
| 缓存 | `index.html` 不缓存；带 hash 的资源长缓存（`/c/` 已是此配置） |
| 外壳包版本 | 两区的外壳包版本不一致，界面会看出差异 → 发布前卡口：各区锁定的 `@neargo/ops-shell` 次版本号一致 |

## 八、代价与边界

| 代价 | 说明 | 缓解 |
|---|---|---|
| 跨区整页加载 | 在运营菜单与工单菜单之间切换会整页刷新 | 状态都在 URL 上（页内 tab 已由 `use-page-tab` 同步到 URL），不丢状态；对另一区入口做 `prefetch` |
| 外壳抽包的一次性成本 | 8 个文件 + 菜单数据化 + 会话入口 | 边界现成 |
| ai-shop 接入 | 外壳已分叉，要先合并 | 放在 ai-shop 接入时做，不阻塞 powerbank |
| 只适合「同一产品域」 | 各区要共用外壳与登录；跨组织、跨栈嵌入不在本方案范围 | 真有需要时再按 19 引入 wujie，与本方案不冲突 |

## 九、与上一轮 wujie 方案的对比

| 维度 | 多区（本方案） | wujie |
|---|---|---|
| 各自开发发布 | ✅ | ✅ |
| 新运行时依赖 | **无**（nginx + 一个共享包） | wujie 框架 |
| 外壳 | 共享包，各区自己渲染 | 宿主渲染，子应用只占内容区 |
| 跨区切换 | 整页加载 | 无刷新 |
| 跨技术栈 | 否（各区同模板） | 是 |
| 隔离 | 天然（不同页面） | 沙箱 |
| 风险点 | 外壳包版本对齐 | 沙箱边角（弹层、`:root`、内存） |

在「各自开发 + 集成到一起」这个目标下，多区方案更简单，也没有引入新的运行时依赖。
