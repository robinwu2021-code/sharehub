## 一、构件划分

| 1 | `neargo-statemachine` | 状态机：定义、推进、守卫、终态推导、角色、图导出与投影 | **无**（纯 Java） | — | SM-01 ~ 10、13 |
| 2 | `neargo-workflow-store` | 持久化：条件更新、流转日志、审批与工单的仓储实现（`JdbcClient`）；两种方言的 DDL | 1 · Spring JDBC | `wf_transition_log` 等（§五） | SM-11、12；NFR-D3、D4 |

| 4 | `neargo-case` | 工单领域：内核、受理方、派单、抢单池、SLA、升级、合并、复核、时间线 | 1 · 仓储接口 | — | CS-01 ~ 13 |
| 5 | `neargo-workflow-web` | **可选**通用控制器（返回平铺 DTO，靠项目的切面包信封） | 3 · 4 · Spring Web | — | NFR-I5 |
| 6 | `neargo-starter-workflow` | 自动装配：扫描定义、装仓储、建表、挂指标 | 2 · 3 · 4 | — | NFR-I2 ~ I4 |
| 7 | `neargo-workflow-test` | TCK（SPI 契约测试）· 测试夹具 · 架构规则（状态必须枚举、禁止手写迁移判断、前后端边一致） | 1 ~ 4 · JUnit | — | AC-4 |

**为什么这样拆**：

| 拆法 | 理由 |
|---|---|
| 状态机单独、零依赖 | 所有项目都要；ai-erp（jOOQ）、ai-neargo（KDS）只要它；让它带 Spring 或表会逼这些项目接受用不上的东西（NFR-I1） |
| 领域层（3、4）与持久化（2）分开 | 领域层只认仓储接口：单测不用库；将来谁要 jOOQ 原生仓储也只换 2 |
| 审批与工单分开 | ichain / tradeagent 只要审批；采用节奏不同 |
| 控制器可选 | 六个项目四种响应信封、各自的 URL 与权限码约定（01 §2.1），强塞控制器反而拖慢集成 |

## 三、领域模型

### 3.1 状态机

| 概念 | 定义 | 说明 |
|---|---|---|
| 状态 `S` | 枚举 | 名词 |
| 事件 `E` | 枚举 | 动词。与状态**类型不同**，编译期就混不了 |
| 边 `Edge<S,E>` | `(event, from, to, guard?)` | 同一对 `(from, to)` 允许多个事件 |
| 角色 `StateRole` | `INITIAL` · `ACTIVE` · `WAITING_EXTERNAL` · `AWAITING_VERIFY` · `ESCALATED` · `TERMINAL` | 只供工单引擎用；`TERMINAL` 由图推导，手写会被定义期校验拒绝 |
| 守卫 `Guard<C>` | `(context) → 通过 / 拒绝(错误键)` | 例：提交人不能审自己 |
| 定义 `StateMachine<S,E>` | 边的集合 + 角色映射 | **不可变**；构建时做完全部校验（SM-08） |
| 迁移 `Transition<S,E>` | `(subjectType, subjectNo, event, from, to, actor, reason, payload, at)` | 写进流转日志的那一行 |

### 3.2 审批

| 概念 | 说明 |
|---|---|
| 审批对象 `Subject` | `(subjectType, subjectNo)` 不透明引用 + 用于解析审批人的属性（如金额、归属站点） |
| 流程 `ApprovalFlow` | `flowCode` + 有序步骤；**代码定义** |
| 步骤 `Step` | `stepCode` · 进入条件 · 审批人解析器 · 模式（或签 / 会签）· 是否允许提交人自审 |
| 审批人解析器 `ApproverResolver` | 返回「审批人集合」或「队列编号」二者之一 |
| 审批单 `Approval` | 一次提交 = 一个审批单；带轮次；自身状态由状态机管 |
| 任务 `ApprovalTask` | 某轮某步某审批人（或某队列）的一件待办；队列任务有「领取人」 |
| 结果回调 `ApprovalOutcomeHandler` | 事务内同步：`(subjectType, subjectNo, flowCode, round, APPROVED / REJECTED / WITHDRAWN)`；业务域在这里推进自己的状态 |
| 结果事件 `ApprovalCompletedEvent` | 同样的字段，**提交后**发，只用于通知等副作用 |

审批单状态机（组件内置）：

| 事件 | 起 → 止 |
|---|---|
| `SUBMIT` | —（新建）→ `PENDING` |
| `APPROVE_STEP` | `PENDING` → `PENDING`（进下一步）或 `APPROVED`（最后一步） |
| `REJECT` | `PENDING` → `REJECTED` |
| `WITHDRAW` | `PENDING` → `WITHDRAWN` |
| `RESUBMIT` | `REJECTED` / `WITHDRAWN` → `PENDING`（轮次 +1） |

任务状态机（组件内置，队列模式才有 `CLAIMED`）：

| 事件 | 起 → 止 |
|---|---|
| `CLAIM` | `OPEN` → `CLAIMED` |
| `RELEASE` / 领取超时 | `CLAIMED` → `OPEN` |
| `DECIDE` | `OPEN`（非队列）/ `CLAIMED`（队列）→ `DONE` |
| `CANCEL` | `OPEN` / `CLAIMED` → `CANCELLED`（同步其余或签任务、撤回、驳回时） |

### 3.3 工单

| 概念 | 说明 |
|---|---|
| 工单类型 `CaseType` | 项目登记：`typeCode` · 状态机 · 角色映射 · 编号前缀 · 默认派单策略 · SLA 规则组 |
| 工单 `Case` | 内核字段（03 §五 `wf_case`）+ 扩展（JSON，不参与查询与权限） |
| 受理方 `Assignee` | `(assigneeType, assigneeNo)`；类型由项目登记（员工 / 代理 / 商家 / 平台 / 用户） |
| 派单策略 `DispatchStrategy` | `MANUAL` · `POOL` · 项目自定义 |
| SLA 规则 `SlaRule` | `(typeCode, priority) → 响应分钟 · 解决分钟 · 是否只算营业时间` |
| 工作日历 `BusinessCalendar` | 项目实现；缺省为 7×24 |
| 时间线 `CaseEvent` | 迁移 · 备注 · 附件 · 派单 · 升级，同一张流水 |

## 四、工单引擎怎么做到「一套引擎，各项目各自的状态」

引擎不认识任何状态名，只认角色。每个工单类型登记状态机时把自己的状态映射到角色：

| 引擎行为 | 触发条件（角色） | powerbank 运维工单 | ai-shop 售后 |
|---|---|---|---|
| 新建落点 | `INITIAL` | `CREATED` | `APPLIED` |
| SLA 开始计时 | 进入任一 `ACTIVE` | `DISPATCHED` | `APPLIED` |
| SLA 暂停 | 进入 `WAITING_EXTERNAL` | — | `REFUNDING`、等寄回 |
| SLA 恢复 | 离开 `WAITING_EXTERNAL` | — | 同上 |
| 进入复核 | `AWAITING_VERIFY` | `DONE` | — |
| 升级标记 | `ESCALATED` 或调用 `escalate` | 接管 | `ARBITRATING` |
| SLA 停表、从待办移除 | `TERMINAL`（图推导） | `CLOSED` | `REFUNDED`、`CLOSED` |
| 抢单池可见 | `in_pool = true` 且角色 `INITIAL` | `CREATED` 且放池 | — |

同理，工单的全部动作都是「对当前工单发一个事件」，引擎只做：守卫 → 条件更新 → 写时间线 → 按角色做 SLA / 待办 → 提交后发事件。**不再每个动作一个方法**（powerbank 现在是 `accept` / `handle` / `complete` / `reject` / `rework` / `close` / `withdraw` 各一个）。

## 五、事务与事件

| 时机 | 做什么 | 在不在业务事务里 |
|---|---|:-:|
| 迁移前 | 守卫校验（可读库） | ✓ |
| 迁移 | 条件更新状态列；0 行 → 冲突 | ✓ |
| 迁移后同步 | 写流转日志 / 时间线；算 SLA；同步任务状态 | ✓ |
| **结果回调** | 审批结束调 `ApprovalOutcomeHandler`、工单迁移调 `CaseTransitionHandler` —— **业务域在这里推进自己的状态** | ✓ |
| 提交后 | 发 `Transitioned` · `ApprovalCompleted` · `CaseEscalated` · `SlaBreached`；**只用于**通知、统计、跨域联动 | ✗（`AfterCommit`） |

**推进业务状态为什么必须在事务内**：若合同在审批提交之后才由事件监听改成「已签」，中途任何失败都会留下「审批已通过、合同还在待审」—— 两张表各说各的，而没有东西会去补。所以业务状态走事务内的同步回调，事务外的事件只做失败了也不影响一致性的事。

业务域与组件的写入边界：

| 组件写 | 业务域写 | 谁都不写对方的表 |
|---|---|---|
| `wf_*` 表 | 自己的业务表（在结果回调里） | 组件不碰业务表；业务域不直接写 `wf_*` |

**唯一例外**：只用状态机（构件 1 + 2）、不用审批与工单时，条件更新作用在**业务表自己的状态列**上 —— 这是给 SM-11「各处手写并发只一人赢」的统一实现，表名、主键列、状态列由调用方传入。

## 六、多项目适配

| 差异点（01 §2.1 实测） | 适配方式 | 缺省 |
|---|---|---|
| 租户：`tenant_id` / `tenant_no` / 无 | 配置 `neargo.workflow.tenant.column`；取值由 SPI `TenantProvider` 给 | 不带租户列 |
| 数据范围 | 工单表带三个通用锚点列 `scope_anchor_1..3`；项目登记每一列代表什么（站点 / 代理 / 商家…）并实现 `ScopeFilter` 把当前用户的范围翻成条件 | 不过滤（**只在未配置数据范围的项目**；配了就 fail-closed） |
| 当前操作人 | SPI `ActorProvider`：`(actorType, actorNo, actorName)` | 必须实现 |
| 权限 | SPI `PermissionChecker`：「此人能否对此对象做此事件」 | 放行（项目通常在控制器上已经 `@PreAuthorize`） |
| 响应信封 | 组件只返回平铺 DTO；可选控制器靠项目已有的 `ResponseBodyAdvice` 包信封 | 不装控制器 |
| 数据库方言 | Flyway `{vendor}` 占位，自动选 `mysql` / `postgresql` / `h2` 目录 | 按数据源自动识别 |
| 迁移版本号 | 组件用**独立的 Flyway 实例和历史表**（`flyway_schema_history_neargo_workflow`） | 开 |
| 表名前缀 | `neargo.workflow.table-prefix` | `wf_` |
| 业务号 | SPI `BizNoGenerator`（powerbank 已有 `BizNoSequence`、ai-shop 有自己的） | 前缀 + 雪花 |
| 错误码与文案 | 组件抛 `WorkflowException(errorKey, args)`；项目的全局异常处理映射成自己的错误码 | 冲突 409，其余 400 |
| 时区 | 全部 UTC 存；`neargo.workflow.business-zone` 用于营业时间 | `UTC` |

## 七、关键决定

| # | 决定 | 放弃的方案 | 为什么 |
|:-:|---|---|---|
| D1 | 事件驱动状态机、状态与事件双枚举 | 纯图（ai-shop / ai-erp 现行） | 纯图丢掉「为什么走这条边」；事件模型能投影出纯图（SM-10），反过来补不回 |
| D2 | 工单引擎按**角色**触发行为 | 规定统一状态名 | 各项目状态名不可能统一，也不该统一 |
| D3 | 嵌入式库 | 共用服务 | 同一事务（NFR-C1） |
| D4 | 持久化用 `JdbcClient` | 用 MyBatis-Plus 实体 | ai-erp 是 jOOQ；MP 会逼所有项目带 MP |
| D5 | 组件用独立 Flyway 历史表 | 并入项目的迁移目录 | 各项目 V 号独立增长，共用目录必然撞号；独立历史也让组件自己升级 |
| D6 | 工单数据范围用三个通用锚点列 | 各项目 ALTER 加列 / 扩展表 JOIN | 数据范围 fail-closed：锚点不在被查的表上等于看不到；ALTER 让组件与表不一致；JOIN 拖慢每次列表 |
| D7 | 流程**代码定义**，SLA 规则**入库** | 全部入库可配 | 流程变更要研发评审；SLA 运营要调（powerbank 已有 `wo_sla_rule`） |
| D8 | 不带控制器（可选开启） | 默认装一套 REST | 四种信封、各自 URL 与权限码约定 |
| D9 | 不引入 BPMN | Flowable / Camunda | 01 §六 |
