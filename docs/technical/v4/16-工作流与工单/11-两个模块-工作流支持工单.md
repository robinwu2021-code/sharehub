# 11 · 两个独立模块：工作流是引擎，工单建在它之上

> 所属：[16 工作流与工单](./README.md) · 状态：**待确认**（2026-09-27）· 依据：[08](./08-纯脱耦服务-场景分析.md) · [09](./09-集成方案-powerbank与ai-shop.md) · [10](./10-微服务设计.md)
> 用户定（2026-09-27）：「工作流和工单应该是作为两个独立的模块，同时工作流要支持工单」。
> 本篇**取代** 00 §四 与 10 §一 / §二 里「一个服务六个领域」的切法；10 的表、接口、引擎选型不变，只按本篇重新归属（§六）。

---

## 一、结论

| 项 | 定 |
|---|---|
| 模块 | **工作流 `workflow`**（引擎）· **工单 `workorder`**（应用），各自独立发布、独立表前缀、独立接口前缀 |
| 依赖方向 | **工单 → 工作流**，只经工作流的客户端接口，不碰工作流的表；工作流**不知道**工单 |
| 「工作流支持工单」的含义 | 工作流提供工单所需的全部通用能力：**流程实例**（跑状态图）· **人工任务**（办理 / 审批，含指派、候选池、领取、转派）· **时限**（按状态角色计时）· **待办** · **流转日志** · **接入与回调**。工单只写自己特有的东西：业务字段、类型登记、派单策略、去重、合并、统计 |
| 只要审批的业务 | 只接工作流，不装工单 |
| 部署 | 现在一个进程 `flow-svc` 同时装两个模块，模块间走进程内的客户端实现；将来可拆成 `workflow-svc` + `workorder-svc`，工单把客户端切成远程，代码不改 |

## 二、能力归属

| 能力 | 归属 | 说明 |
|---|:-:|---|
| 状态图定义与执行（状态、事件、边、角色、终态推导） | 工作流 | 图是数据；执行主体是**流程实例** |
| 流程实例 ProcessInstance | 工作流 | 任何业务对象的一次生命周期；工单是它的一种用法 |
| 人工任务 HumanTask（两类：`ASSIGNMENT` 办理、`APPROVAL` 审批） | 工作流 | 指派 · 候选池 · 领取 / 放回 · 转派 · 完成 · 到期；资格模型（人 / 权限码 / 角色 / 队列 / 池） |
| 审批（流程、步骤、条件步、或签 / 会签、轮次、五条规则） | 工作流 | 建在 `APPROVAL` 任务之上 |
| 时限 / SLA（起算 · 暂停 · 恢复 · 超时 · 营业时间） | 工作流 | 挂在流程实例上，按状态角色触发；审批步骤的到期也用它 |
| 待办 | 工作流 | 所有人工任务的投影，办理与审批同一张 |
| 流转日志 | 工作流 | 实例 / 任务 / 审批单的每次变化 |
| 接入系统 · 凭证 · webhook · 发件箱 · 幂等 · 对账 | 工作流 | 平台层；工单经它对外发事件 |
| 队列 · 日历 | 工作流 | 定义类数据 |
| 工单类型登记（引用哪张图、受理方类型、派单方式、锚点含义、关闭原因、内嵌审批） | 工单 | —— |
| 工单实体（来源、对象、标题、优先级、受理方快照、升级标记、去重键、合并关系、扩展） | 工单 | 持有 `instanceNo` 与当前办理任务号 |
| 派单策略、抢单、升级 / 接管、改派、改优先级 | 工单 | 落到工作流的任务操作 |
| 去重开单、合并、撤单 | 工单 | 合并关系存工单侧；状态变化仍经流程实例 |
| 工单时间线（视图） | 工单 | = 工作流流转日志 + 任务事件 + 工单侧备注与附件 |
| 工单统计（按受理方 / 时间段 / 锚点） | 工单 | 清退门禁、月度考核、看板 |

一句话：**「谁来办、办到哪、超没超时、谁能看见」是工作流；「办的是什么事」是工单。**

## 三、工单怎么用工作流（动作映射）

| 工单动作 | 工单模块做 | 调工作流 |
|---|---|---|
| 开单 | 校验类型；算去重键；写工单行 | `instances.start(graph, subject, anchors, slaGroup)` → `instanceNo`；`tasks.create(ASSIGNMENT, instanceNo, 候选 = 受理方 或 池, title, priority, anchors)` |
| 去重开单 | 同键有未结单 → 只加一条备注，返回既有单 | `instances.note(instanceNo, …)` |
| 指派 / 放池 / 抢单 | 记受理方快照 | `tasks.assign` / `tasks.pool` / `tasks.claim` |
| 接单 · 处理 · 完工 · 驳回 · 返工 · 关闭 · 撤单 | 校验是不是当前受理方；关闭时记关闭原因 | `instances.fire(instanceNo, event, actor)`；工作流按角色处理时限、写日志、发 `instance.transitioned` |
| 升级 / 接管 | 打升级标记 | `tasks.reassign(taskNo, 新受理方, reason)` |
| 受理方不可用批量改派 | 找出该受理方名下未结单 | 逐单 `tasks.reassign` 或 `tasks.pool` |
| 合并 | 记 `mergedInto` | 被并单 `instances.fire(MERGE)` |
| 改优先级 | 写工单行 | `instances.resla(instanceNo, priority)`（时限按新规则重算） |
| 内嵌审批（如费用超额） | 类型里登记「事件 → 审批流程」；收到实例进入 `WAITING_EXTERNAL` 后发起审批，结果回来再发事件 | `approvals.submit(flow, subject = 工单, actor)`；`instances.fire(实例, APPROVED_EVENT / REJECTED_EVENT)` |
| 待办 | 不自己做 | 工作流 `todos.query`（办理任务带工单标题、优先级、锚点） |
| 时间线 | 拼视图 | `instances.history` + `tasks.history` + 工单侧备注 |
| 对业务的回调 | 把 `instance.transitioned` 加工成 `work_order.transitioned`（补上工单号、类型、序号） | 经工作流的 webhook 投递发出 |

工单模块**不直接改状态列**：它没有自己的状态字段，`status` 从流程实例读（或冗余一份只读快照供列表查询，由 `instance.transitioned` 事件同步）。

## 四、两个模块的领域对象

### 4.1 工作流

| 聚合 / 实体 | 关键字段 | 说明 |
|---|---|---|
| **System** | 系统代号 · 凭证 · 回调地址 · 签名密钥 · 时区 | 平台层 |
| **Definition** | kind（GRAPH · FLOW）· code · version · body | 只增不改 |
| **ProcessInstance** | `instanceNo` · `graphCode/version` · `subject{type, no, display}` · `status` · `open` · `anchors` · `sla{ruleId, startedAt, dueAt, pausedMs, pausedSince, state}` · `version` | 取代 10 里工单表上的状态与 SLA 列 |
| **HumanTask** | `taskNo` · `kind`(ASSIGNMENT · APPROVAL) · `instanceNo` · `approvalNo?` · `title` · `priority` · `eligibility[]{kind, ref}` · `assignee?{type, no, name}` · `status`(OPEN · CLAIMED · ASSIGNED · DONE · CANCELLED) · `dueAt` · `anchors` · `payload` | 办理任务与审批任务同一实体，行为按 `kind` 分 |
| **Approval** · **Round** | 同 10 §2.4 | 建在 `APPROVAL` 任务上 |
| **TodoItem** | 同 10 §2.6 | 投影自 HumanTask |
| **Queue** · **SlaRule** · **Calendar** · **OutboxMessage** · **IdempotencyRecord** · **WebhookDelivery** | 同 10 | —— |

### 4.2 工单

| 聚合 / 实体 | 关键字段 | 说明 |
|---|---|---|
| **WorkOrderType** | `code` · `version` · `graphCode` · `noPrefix` · `assigneeTypes[]` · `dispatch` · `slaGroup` · `anchorSlots[3]` · `embeddedFlows[]{event, flowCode, approvedEvent, rejectedEvent}` · `closeReasons[]` | 登记时把 `graphCode` 交给工作流校验存在 |
| **WorkOrder** | `orderNo` · `typeCode/version` · `instanceNo` · `currentTaskNo?` · `source{kind, ref}` · `subject` · `title` · `description` · `priority` · `statusSnapshot`（只读冗余）· `assignee?`（快照）· `escalated` · `closeReason?` · `mergedInto?` · `dedupeKey?` · `anchors` · `ext` · `createdBy/At` · `closedAt?` | 没有自己的状态机 |
| **Note** | `orderNo` · `seq` · `actor` · `content` · `attachments[]` · `at` | 工单侧备注与附件 |

## 五、目录（重排 10 §一）

```
backend/flow/                              # 聚合 ai.neargo.flow:flow-parent
├── workflow/                              # 引擎模块  ai.neargo.flow:workflow-*
│   ├── workflow-api/      状态机库 · ProcessInstance / HumanTask / Approval / Todo 的 DTO · WorkflowClient 接口 · webhook 载荷 · WorkflowPaths
│   ├── workflow-client/   HttpWorkflowClient · EmbeddedWorkflowClient（测试 / 同进程）· 回调接收骨架 · 发件箱 · Provider SPI
│   ├── workflow-core/     platform(access · integration) · definition · instance · task · approval · sla · todo · app
│   └── workflow-store/    wf_* DAO · 两套 DDL
├── workorder/                             # 应用模块  ai.neargo.flow:workorder-*   只依赖 workflow-api + workflow-client
│   ├── workorder-api/     WorkOrderType / WorkOrder / Note 的 DTO · WorkOrderClient 接口 · WorkOrderPaths
│   ├── workorder-client/  HttpWorkOrderClient · EmbeddedWorkOrderClient
│   ├── workorder-core/    type · order · dispatch · dedupe · merge · timeline · stats · app
│   └── workorder-store/   wo_* DAO · 两套 DDL
└── flow-svc/                              # 进程：默认同时装两个模块；profile `workflow-only` / `workorder-only` 可各自单独起
```

| 规则 | 守法 |
|---|---|
| `workorder-*` 只依赖 `workflow-api` · `workflow-client`，**不依赖 `workflow-core` / `workflow-store`** | 架构测试 |
| `workflow-*` 不依赖任何 `workorder-*`；代码里不出现「工单」 | 架构测试 |
| 两个模块各自的 Flyway 实例与历史表（`flyway_schema_history_workflow` / `_workorder`），同库不同前缀，**不跨前缀 JOIN** | 代码评审 + 架构测试扫 SQL |
| 同进程时工单调工作流走 `EmbeddedWorkflowClient`（进程内、同事务可选）；拆进程后切 `HttpWorkflowClient` | 配置 |

## 六、表与接口的归属（10 的内容按此重排）

### 6.1 表

| 前缀 `wf_`（工作流） | 前缀 `wo_`（工单） |
|---|---|
| `wf_system` · `wf_webhook_subscription` · `wf_definition` · `wf_queue` · `wf_sla_rule` · `wf_calendar` | `wo_type_definition` |
| **`wf_process_instance`**（新：`instanceNo · graph · subject · status · is_open · anchors · sla_*`） | **`wo_work_order`**（去掉 `status / sla_* / in_pool`，加 `instance_no · current_task_no · status_snapshot`） |
| **`wf_task`**（取代 10 的 `flw_approval_task`，加 `kind · instance_no · title · priority · assignee_* · anchors · payload`） | `wo_note`（取代 10 的 `flw_work_order_event` 里备注 / 附件那部分） |
| `wf_approval` · `wf_approval_round` | —— |
| `wf_todo` · `wf_transition_log` · `wf_outbox` · `wf_webhook_delivery` · `wf_idempotency` | —— |

> 前缀说明：服务有自己的库，`wo_` 不会与 powerbank 业务库里的 `wo_order` 相撞；嵌入模式只用于测试且跑 H2。

### 6.2 接口

| 基路径 `/api/workflow/v1`（工作流） | 基路径 `/api/workorder/v1`（工单） |
|---|---|
| `definitions/graphs` · `definitions/flows` · `queues` · `sla-rules` · `calendars` | `types` |
| `instances`（start · fire · resla · note · history · query） | `work-orders`（open · events/{event} · assign · pool · grab · escalate · merge · notes · priority · reassign · query · timeline） |
| `tasks`（create · assign · pool · claim · release · reassign · complete · query） | `stats`（open-count · by-assignee · summary） |
| `approvals` · `approval-tasks` | —— |
| `todos`（query · count） | —— |
| `stats/instances` · `subjects/{type}/{no}/history` | —— |
| `webhooks`（订阅 · 投递记录 · 重投） | —— |

业务系统：只要审批 → 只接 `/api/workflow/v1`；要工单 → 接 `/api/workorder/v1`，待办与 webhook 仍从工作流拿。
工单模块内部调的也是 `/api/workflow/v1` 这套契约（进程内实现），没有私有通道。

### 6.3 Webhook 事件

| 工作流发 | 工单发（经工作流的投递通道） |
|---|---|
| `instance.transitioned` · `instance.sla.breached` · `task.created` · `task.assigned` · `task.due` · `approval.completed` | `work_order.opened` · `work_order.transitioned`（在 `instance.transitioned` 上补工单号、类型、序号）· `work_order.assigned` · `work_order.escalated` · `work_order.closed` |

接了工单的业务系统订阅 `work_order.*` 即可；`instance.*` 是给直接用流程实例的业务。

## 八、待确认

| # | 问题 | 建议 |
|:-:|---|---|
| 1 | 工单是否**完全**不持有状态机（状态只从流程实例来） | 是；工单表上的 `status_snapshot` 只读、由事件同步，便于列表查询 |
| 2 | 办理任务与审批任务用同一个实体 `HumanTask` | 是；待办才能是一张表、一套资格模型 |
| 3 | 时限挂在流程实例（工作流）而不是工单 | 是；审批步骤到期也复用，且拆进程后工单不必自己扫 |
| 4 | 首版一个进程装两个模块 | 是；拆分靠配置 |
| 5 | 基路径分成 `/api/workflow/v1` 与 `/api/workorder/v1` | 是；只要审批的业务不必知道工单 |
