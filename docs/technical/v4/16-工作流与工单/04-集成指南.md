## 〇、先选档位

| 你要什么 | 档位 | 依赖 | 要建表吗 | 要写的东西 | 目标耗时 |
|---|---|---|:-:|---|---|
| 只是让状态流转不再手写 | **A · 状态机** | `neargo-statemachine` | 否 | 一个定义 | ≤ 30 分钟 |
| 再加并发保护与统一流转日志 | **A+ · 状态机 + 持久化** | `neargo-workflow-store` | 自动 | 上面 + 3 行配置 | ≤ 1 小时 |
| 审批 | **B · 审批** | `neargo-starter-workflow` | 自动 | 流程定义 · 结果回调 · 2 ~ 3 个 SPI | 第一个流程 ≤ 半天 |
| 工单 | **C · 工单** | `neargo-starter-workflow` | 自动 | 类型登记 · 受理方目录 · 数据范围 | 第一个类型 ≤ 2 天 |

ai-erp（jOOQ）、ai-neargo（KDS）只要 A；ichain / tradeagent 要 B；powerbank / ai-shop 三档都要。

## 二、档 A · 只要状态机

### 2.1 三步

| 步 | 做什么 |
|:-:|---|
| 1 | 把状态值改成枚举（已经是的跳过）；再定义一个事件枚举 |
| 2 | 写定义（03 §1.1），放在领域包里一个 `static final` 字段 |
| 3 | 把手写的 `if (status.equals(…))` 与迁移表换成 `SM.next(from, event)` |

### 2.2 从现有三种写法迁过来

| 你现在的写法 | 怎么迁 |
|---|---|
| powerbank：`Map<事件, Map<起, 止>>` | 逐行照抄成 `.edge(事件, 起, 止)`；`next` 调用点不变；`check` / `eventOf` 改名为 `next` / `eventFor` |
| ai-shop：`Map<起, Set<止>>` + `assertXxxTransit(from, to)` | **每条边补一个事件名**（这一步要懂业务的人做）；旧调用点先改成 `SM.projection()` 上的判断，保持行为不变，再逐个改为按事件 |
| ai-erp：`InvoiceFsm.legalTargets(from)` / `assertLegal(from, to)` | 同 ai-shop；状态已是枚举，只补事件枚举 |

### 2.3 迁完怎么证明没改行为

| 检查 | 做法 |
|---|---|
| 边一条没少 | 用旧表与 `projection()` 做集合比对的一次性测试，通过后删掉旧表 |
| 既有用例不改仍绿 | 跑全量 |
| 负对照 | 从定义里删一条边 → 至少一条既有用例变红；恢复 → 绿 |

## 三、档 A+ · 加持久化

### 3.1 配置

```yaml
neargo:
  workflow:
    approval.enabled: false     # 只要持久化与日志时关掉
    case.enabled: false
    tenant:
      enabled: true             # 有租户的项目
      column: tenant_id         # ai-shop 写 tenant_no；无租户项目不配
```

Flyway 用组件自己的实例与历史表（`flyway_schema_history_neargo_workflow`），**不需要**往你的 `spring.flyway.locations` 里加东西，也**不占你的 V 号**。

### 3.2 调用

```java
@Transactional
public void dispatch(String woNo, String assignee) {
    WoStatus from = mapper.statusOf(woNo);
    transitions.fire(WO, Target.of("wo_order", "wo_no", woNo, "status"), from, WoEvent.DISPATCH,
                     Meta.of("派单给 " + assignee).set("assignee_name", assignee));
    // 并发冲突 → StateChangedException（409）；日志已在同一事务里写好
}
```

你的 ORM 不受影响：组件用 `JdbcClient` 走同一个 `DataSource` 与事务管理器，MyBatis-Plus / jOOQ 的写入和它在同一事务里。

## 四、档 B · 审批

### 4.1 五步

| 步 | 做什么 | 例 |
|:-:|---|---|
| 1 | 加 starter，配租户（同 3.1） | — |
| 2 | 实现 `ActorProvider` | powerbank 从 `StaffContext` 取；ichain 从自己的登录上下文取 |
| 3 | 按审批人方式实现 `PermissionDirectory` 或 `QueueMembership` | powerbank 用权限码；ichain 用队列 |
| 4 | 写流程定义 `@Bean ApprovalFlow` | 03 §2.1 |
| 5 | 写结果回调 `ApprovalOutcomeHandler` —— **在这里推进你的业务状态** | 03 §2.3 |

### 4.2 业务侧只改两处

| 原来 | 现在 |
|---|---|
| 业务 service 里的 `submit / approve / reject / withdraw` 各一段手写逻辑 | 业务 `submit` 只做「校验业务数据 → `approvals.submit(…)`」；决定、撤回全部由组件接口完成 |
| 业务表上的审批人、意见、环节列 | 不再写；要展示时读 `approvals.detail(…)`。**旧列保留只读**，历史数据不迁 |

### 4.3 ichain / tradeagent 的 `AuditTask` 对照

| `AuditTask` 字段 | 组件 |
|---|---|
| `targetType` · `targetId` | `subject_type` · `subject_no` |
| `queue` | `Approvers.queue(queueCode)` |
| `priority` | 任务优先级（`myTasks` 按它排序） |
| `status` PENDING / CLAIMED / APPROVED / REJECTED / CANCELLED | 任务 `OPEN / CLAIMED / DONE / CANCELLED` + 决定 `APPROVE / REJECT` |
| `assigneeId` · `claimedAt` | `claimed_by` · `claimed_at_ms` |
| `decision` · `reason` · `decidedAt` | 同名 |
| `evidence`（JSON） | `wf_approval.evidence` |

## 五、档 C · 工单

### 5.1 七步

| 步 | 做什么 | 例 |
|:-:|---|---|
| 1 | 档 B 的 1 ~ 2 | — |
| 2 | 定义该工单类型的状态机，并**给状态标角色** | 03 §1.1；角色见 02 §四 |
| 3 | `@Bean CaseType` 登记：状态机 · 编号前缀 · 受理方类型 · 派单策略 · SLA 规则组 · 锚点 | 03 §3.1 |
| 4 | 实现 `AssigneeDirectory`（名字、是否可用） | powerbank：员工 + 代理；ai-shop：商家 + 平台 |
| 5 | 有数据范围的项目：登记锚点 + 实现 `ScopeFilter` | powerbank：锚点 1 = 站点、2 = 代理；ai-shop：1 = 商家 |
| 6 | 往 `wf_sla_rule` 灌 SLA 规则（运营之后可在后台调） | — |
| 7 | 把 SLA 扫描登记成你的定时任务（三行，见 5.3） | — |

### 5.2 业务侧怎么改

| 原来 | 现在 |
|---|---|
| 每个动作一个 service 方法（接单、处理、完工、驳回、返工、关闭…） | 一个 `cases.fire(caseNo, eventCode, cmd)`；业务特有的联动写在 `CaseTransitionHandler` |
| 自己的派单、抢单、接管、SLA 表与扫描 | 组件接口 + `wf_sla_rule` |
| 自己的时间线表 | `detail(caseNo).timeline()` |
| 业务专有字段（设备号、站点名、寄回单号…） | `ext`（JSON，只展示）；要按它查 / 控权限的，放进 `subject` 或锚点 |

### 5.3 SLA 扫描登记

组件不依赖任何任务框架（NFR-D5）。在你的任务框架里写一个壳：

```java
@Component
class CaseSlaSweepJob implements JobHandler {             // 你项目自己的任务接口
    private final CaseService cases;
    public void run() { while (cases.sweepSla(500) == 500) { } }   // 分批直到扫完
}
```

## 六、暴露接口

### 6.1 控制器返回平铺对象、由切面包信封的项目（powerbank）

开启可选控制器即可：

```yaml
neargo.workflow.web:
  enabled: true
  base-path: /api/ops/workflow
```

### 6.2 其他项目：写一个薄控制器

以 ichain 的 `ApiResult` 为例，其他信封同理替换返回类型：

```java
@RestController
@RequestMapping("/admin/approvals")
class AdminApprovalController {
    private final ApprovalService approvals;

    @GetMapping("/tasks/mine")
    ApiResult<PageResult<ApprovalTaskView>> mine(TaskQuery q) { return ApiResult.ok(approvals.myTasks(q)); }

    @PostMapping("/tasks/{taskNo}/claim")
    ApiResult<ApprovalTaskView> claim(@PathVariable String taskNo) { return ApiResult.ok(approvals.claim(taskNo)); }

    @PostMapping("/{approvalNo}/decide")
    ApiResult<ApprovalView> decide(@PathVariable String approvalNo, @RequestBody DecideReq r) {
        return ApiResult.ok(approvals.decide(approvalNo, r.decision(), r.reason()));
    }
    record DecideReq(Decision decision, String reason) { }     // 请求体一律 record 白名单
}
```

### 6.3 前端

| 需要 | 从哪拿 |
|---|---|
| 当前能点哪些按钮 | 出参 `actions` = 当前状态可走事件 ∩ 当前用户有权限的 |
| 状态图（画流程、做前后端一致卡口） | `GET …/graphs/{subjectType}` |
| 时间线 | `detail(…).timeline()` |

前端**不再自己维护**迁移表。

## 七、上线前检查清单

| # | 检查 |
|:-:|---|
| 1 | `ActorProvider` 在定时任务线程里返回 `SYSTEM` 而不是抛异常 |
| 2 | 开了数据范围的项目：用一个只有单站点 / 单商家范围的账号查列表，**看不到别人的** |
| 3 | 结果回调里抛异常时，审批决定一起回滚（写一条用例） |
| 4 | 表前缀、租户列名定稿后才首次启动（建表后再改需要迁移） |
| 5 | 生产连接串里没有依赖时区的假设（组件时间都是毫秒整数，不受影响；但你自己的表仍要注意） |
| 6 | 跑 `neargo-workflow-test` 的 TCK：你实现的每个 SPI 都过 |
| 7 | 旧的迁移表 / 审批列 / 日志表：**保留只读**，不物理删除 |

## 八、常见坑

| 坑 | 表现 | 做法 |
|---|---|---|
| 在事务外推进业务状态 | 审批已通过，业务单还在待审 | 用 `ApprovalOutcomeHandler`（事务内），不要用 `ApprovalCompletedEvent` 推状态 |
| 把 `ext` 当查询条件 | 列表慢、数据范围失效 | 要查的放 `subject` 或锚点 |
| 给有出边的状态标 `TERMINAL` | 启动失败 | 这是故意的 —— 终态由图推导 |
| 同一对「起 → 止」两个事件，用 `eventFor` 反查 | `AmbiguousEventException` | 调用方明确传事件，不要反查 |
| 表前缀配成空 | 启动失败 | `case` 在 MySQL 与 PostgreSQL 都是保留字 |
| 队列任务没领取就决定 | `workflow.approval.not_claimed` | 先 `claim` |
