## 一、一句话

**一个服务，管「需要有人来办、有时限、要留痕」的事：审批与工单。** 业务系统把事交给它，它负责派给谁、谁能办、办到哪一步、超没超时、全过程记录；办完了回头告诉业务系统结果。它不认识合同、订单、设备，只认识「一个业务对象」。

## 二、定位与边界

| 管 | 不管 | 那归谁 |
|---|---|---|
| 审批：多步、条件步、或签 / 会签、队列领取、驳回重提、转交 | 业务对象自身的状态（订单是否已支付、机柜是否在线） | 业务系统，用本模块附带的**状态机库**在自己进程里管 |
| 工单：开单、去重、派单、抢单、受理、处理、复核、升级、合并、撤单 | 通知怎么发出去（短信、推送） | 通知组件 / 将来的消息中心；本服务只发事件 |
| SLA：时限、营业时间、暂停、超时 | 定时调度 | 共用任务服务；本服务提供「扫一批」的方法 |
| 待办：一个人名下所有要办的审批与工单 | 权限与登录 | 业务系统；本服务只收它给的「操作人上下文」 |
| 全过程的时间线 | 业务数据本身 | 业务系统；本服务只存引用和展示用的快照 |

**和业务解耦的三条硬约束**：

| # | 约束 | 含义 |
|:-:|---|---|
| C1 | 服务里没有任何业务代码、业务名词 | 模块代码里出现「合同」「机柜」「订单」即被架构测试拦下 |
| C2 | 业务对象是**不透明引用** | `(对象类型, 对象编号)`，外加业务给的属性与锚点；服务从不回查业务库 |
| C3 | 所有「业务相关的判断」在业务侧做完，只把**结果数据**交给服务 | 例：「这份合同要不要财务会签」由业务算成属性 `needsCosign=true`，服务只按属性走分支 |

## 三、总体结构

### 3.1 一个模块，五个子模块

| 子模块 | 放什么 | 谁依赖 |
|---|---|---|
| `flow-api` | **状态机库**（零依赖，业务在自己进程里用）· 服务契约：领域 DTO、客户端接口、回调接口、事件、错误键 | 所有业务模块 |
| `flow-client` | 业务侧客户端：本地实现（形态 A）· 远程实现（形态 B）· 回调接收 · 发件箱与对账 | 业务的启动模块 |
| `flow-core` | 引擎：定义、审批、工单、SLA、待办、时间线 | 形态 A 下由业务启动模块在运行期带入；形态 B 下只有服务依赖 |
| `flow-store` | 持久化（`JdbcClient` 手写 SQL）· MySQL / PostgreSQL 两套建表脚本 | core |
| `flow-svc` | 独立服务进程；只暴露 `/internal` 与回调 | 部署用 |

照 ai-shop 任务模块（`job-api · job-store · job-core · job-worker`）与支付（`pay-svc`、规划中的 `pay-client`）的分法。

### 3.2 放在哪、叫什么

| 项 | 取值 |
|---|---|
| 位置 | powerbank `backend/flow/`（聚合模块，与 `sharehub-*` 平级） |
| 坐标 / 包名 | `ai.neargo.flow` / `ai.neargo.flow.*` —— 中性，不带 `sharehub`，将来独立时不改名 |
| 表前缀 | `flw_`（powerbank 已有 `wo_order`，迁移期必须不撞） |
| 名字 | `flow`（流程与工单服务）为暂定；按 ADR-023 的约定避开「Ops」 |

### 3.3 两种形态

| | 形态 A · 嵌入（**现在**） | 形态 B · 独立服务（**将来**） |
|---|---|---|
| 引擎 | 跑在 powerbank 进程里 | 跑在 `flow-svc` |
| 表 | powerbank 库里的 `flw_*` | 服务自己的库 |
| 结果回调 | 同一事务内同步调用 → 强一致 | 服务提交后 HTTP 回调 → 最终一致（幂等 + 重试 + 对账） |
| 多个业务系统 | —— | 每张表带 `system_code`，按接入系统隔离 |
| 切换 | —— | 只改配置；前提是 §八 的四条规则从第一天就遵守 |

## 四、领域划分

服务内部分六个领域，彼此只通过领域事件协作。

| 领域 | 职责 | 核心对象 |
|---|---|---|
| **接入** | 谁在用这个服务、怎么回调它 | 接入系统 |
| **定义** | 规则：状态图、审批流程、工单类型、SLA、日历、队列 | 状态图 · 审批流程 · 工单类型 · SLA 规则 · 工作日历 · 队列 |
| **审批** | 一个业务对象要经过若干人同意 | 审批单（含轮次、任务） |
| **工单** | 一件事派给人或组织去处理 | 工单（含时间线、SLA 计时） |
| **待办** | 某人现在能办哪些事 | 待办项（读模型） |
| **集成** | 与业务系统之间可靠地收发 | 发件箱消息 · 幂等记录 |

审批与工单是**两个聚合**，不强行合成一种「任务」：审批的核心是「决定」，工单的核心是「处理」，状态、规则、统计口径都不同。合并的收益来自它们**共用**定义、SLA、待办、时间线、集成这些基础设施（§七）。

## 五、领域对象

### 5.1 共用的值对象

| 对象 | 属性 | 说明 |
|---|---|---|
| **业务对象** Subject | 对象类型 · 对象编号 · 属性（键值）· 锚点（最多 3 个） | 不透明引用。属性供审批条件与审批人规则使用；锚点供数据范围过滤（如站点、代理、商家） |
| **操作人上下文** ActorContext | 类型（员工 / 代理 / 商家 / 用户 / 系统）· 编号 · 姓名 · 权限集合 · 角色集合 · 队列集合 · 租户 | 业务每次调用时组装。服务据此判断「是不是我的待办」「能不能做这个动作」 |
| **数据范围条件** ScopeCondition | 槽位 1 ~ 3 → 允许值集合或「全部」 | 业务把当前用户的数据范围翻译过来；**给了就只返回范围内的行**（fail-closed） |
| **受理方** Assignee | 类型 · 编号 · 名称快照 | 类型由业务登记（员工、代理、商家、平台…） |
| **附件引用** AttachmentRef | 媒体编号 · 名称 · 类型 | 文件本身在媒体组件，服务只存引用 |

### 5.2 接入领域

| 对象 | 关键属性 | 状态 | 不变式 |
|---|---|---|---|
| **接入系统** System | 系统代号 `system_code` · 名称 · 回调地址 · 凭证 · 默认时区 | 启用 / 停用 | 所有数据都带系统代号；系统之间互不可见。形态 A 下只有一个（本产品） |

### 5.3 定义领域（全部是数据，带版本）

| 对象 | 关键属性 | 不变式 |
|---|---|---|
| **状态图** StateGraph | 代号 · 版本 · 状态（各带角色）· 事件 · 边（事件, 起, 止） | 有且只有一个初始状态；终态由图推导（无出边）；同一「起 + 事件」只能到一个「止」。版本 = 内容哈希，不可修改只可新增 |
| **审批流程** ApprovalFlow | 代号 · 版本 · 有序步骤 | 至少一步 |
| └ 步骤 Step | 代号 · 进入条件 · 审批人规则 · 模式（或签 / 会签）· 是否允许自审 · 时限 | 进入条件只能是对属性的简单判定（等于 / 为真 / 属于）；审批人规则只能是四种之一：**权限码 · 角色 · 属性里给的人 · 队列** |
| **工单类型** WorkOrderType | 代号 · 版本 · 状态图 · 编号前缀 · 受理方类型 · 派单方式（指派 / 抢单池 / 规则）· SLA 规则组 · 锚点槽位含义 · 可发起的审批流程 | 状态图里的每个状态都有角色 |
| **SLA 规则** SlaRule | 规则组 · 适用对象（工单类型或审批流程）· 优先级 · 响应时限 · 解决时限 · 只算营业时间 · 日历 | 同一「组 + 对象 + 优先级」唯一；`*` 表示通配 |
| **工作日历** Calendar | 代号 · 时区 · 每周营业时段 · 节假日 | —— |
| **队列** Queue | 代号 · 名称 · 排序规则 | 成员不在服务里维护：由操作人上下文里的「队列集合」给出 |

**状态角色**（工单引擎只认角色，不认状态名 —— 这是一套引擎能服务不同业务的关键）：

| 角色 | 含义 | 引擎做什么 |
|---|---|---|
| `INITIAL` | 新建 | 开单落点；抢单池模式下进池 |
| `ACTIVE` | 处理中 | 首次进入时 SLA 起算 |
| `WAITING_EXTERNAL` | 等外部（等用户、等支付回执、等配件） | SLA 暂停 |
| `AWAITING_VERIFY` | 待复核 | 进入复核环节 |
| `ESCALATED` | 已升级 | 打升级标记 |
| `TERMINAL` | 终态 | 停表、移出待办、记关闭原因 |

### 5.4 审批领域（聚合根：审批单）

| 对象 | 关键属性 | 状态 | 不变式 |
|---|---|---|---|
| **审批单** Approval | 编号 · 流程代号 + 版本 · 业务对象 · 当前轮次 · 当前步 · 本轮计划 · 属性快照 · 提交人 · 证据 · 时限 | 待审 · 通过 · 驳回 · 撤回 | 同一业务对象同一时刻**至多一张待审**；进行中的审批按提交时的流程版本走完 |
| └ **轮次** Round | 轮次号 · 计划（本轮实际要走的步骤）· 提交时间 · 结果 | —— | 驳回或撤回后再提交 = 新一轮；**旧轮次的一切永不覆盖** |
| └ **审批任务** ApprovalTask | 编号 · 轮次 · 步骤 · 审批人规则 · 领取人 · 决定 · 原因 · 决定人 · 到期 | 待办 · 已领取 · 已完成 · 已取消 | 队列任务只能由领取人决定；领取超时自动放回；或签一人决定后同步取消其余 |
| **审批结果** ApprovalOutcome（事件） | 业务对象 · 流程 · 轮次 · 结果 · 原因 · 决定人 | —— | 交给业务的结果回调；可能重复交付（形态 B），业务必须幂等 |

**五条内建规则**（前四条两边业务都各手写过一遍，统一收进来）：

| # | 规则 | 缺省 | 出处 |
|:-:|---|---|---|
| 1 | 提交人不能审自己 | 开（流程可关） | powerbank 合同、ai-shop 商品审核 |
| 2 | 驳回必须填原因 | 开 | 同上 |
| 3 | 只有提交人能在待审时撤回 | 开 | powerbank 合同 |
| 4 | 并发下同一决定只有一个成功 | 开 | powerbank 合同「按原状态 + 原环节条件更新」 |
| 5 | **跨步互斥**：同一轮里，后一步不能由前面某步的决定人来做 | 关（流程可开） | powerbank 权限真源表：财务会签「不能与运营审批人同一人」 |

### 5.5 工单领域（聚合根：工单）

| 对象 | 关键属性 | 状态 | 不变式 |
|---|---|---|---|
| **工单** WorkOrder | 编号 · 类型 + 版本 · 来源（告警 / 巡检 / 用户 / 手工…）+ 来源编号 · 业务对象 · 标题 · 描述 · 优先级 · 状态 · 是否未结 · 受理方 · 是否在抢单池 · 升级标记 · 关闭原因 · 并入单号 · 去重键 · 锚点 · 扩展（仅展示） | 由其类型的状态图决定 | 每次状态变化都是图上的一条边；同一去重键**至多一张未结单**；终态后不可再变 |
| └ **SLA 计时** SlaClock | 规则 · 起算时间 · 到期时间 · 已暂停时长 · 暂停起点 · 计时状态 | 正常 · 暂停 · 超时 · 按时完成 | 暂停期间不计时；改优先级从起算点按新规则重算；进终态停表 |
| └ **时间线条目** TimelineEntry | 序号 · 种类（迁移 / 派单 / 升级 / 备注 / 附件 / SLA / 合并 / 审批）· 事件 · 起止状态 · 操作人 · 内容 · 附件 · 时间 | —— | 只增不改；序号单调递增（也是结果回调的幂等键） |
| **工单迁移** WorkOrderTransition（事件） | 工单 · 类型 · 事件 · 起止 · 序号 · 操作人 | —— | 交给业务的迁移回调；幂等 |

**关闭原因**（通用 + 业务可扩展）：`RESOLVED` 已解决 · `WITHDRAWN` 起因消失撤单 · `DUPLICATE` 并入他单（均为 powerbank 现行词表），业务可登记更多。

### 5.6 待办领域（读模型）

| 对象 | 关键属性 | 说明 |
|---|---|---|
| **待办项** TodoItem | 来源（审批任务 / 工单）· 来源编号 · 标题 · 业务对象 · 优先级 · 到期 · **谁能办**（指定人 / 权限码 / 角色 / 队列 / 受理方）· 锚点 · 状态 | 由审批任务与工单的变化投影而来，**不是**独立的业务事实。「我的待办」= 用操作人上下文匹配「谁能办」+ 数据范围过滤 |

### 5.7 集成领域

| 对象 | 关键属性 | 说明 |
|---|---|---|
| **发件箱消息** OutboxMessage | 方向（请求 / 回调）· 幂等键 · 目标 · 内容 · 尝试次数 · 下次时间 · 完成时间 | 与业务写在同一事务；投递失败按退避重试 |

## 六、核心流程

表中「业务」指接入的业务系统（如 powerbank），「客户端」指装在业务进程里的 `flow-client`，「服务」指引擎（形态 A 同进程，形态 B 在 `flow-svc`）。

### 6.1 接入与定义登记（业务启动时）

| 步 | 谁 | 做什么 |
|:-:|---|---|
| 1 | 业务 | 用状态机库写出状态图；声明审批流程、工单类型（代码里的定义） |
| 2 | 客户端 | 把定义编译成数据，算出版本（内容哈希） |
| 3 | 客户端 → 服务 | 登记定义；版本已存在则跳过 |
| 4 | 服务 | 校验（初始状态唯一、终态由图推导、审批人规则合法…），不合法则**启动失败** |

### 6.2 业务对象自身的状态迁移（不经过服务）

| 步 | 谁 | 做什么 |
|:-:|---|---|
| 1 | 业务 | `状态机.next(当前状态, 事件)`；非法迁移直接报错 |
| 2 | 业务 | 条件更新自己的表：`WHERE status = 原状态`，0 行即并发冲突 |
| 3 | 客户端 | 在业务库写一条流转日志（同事务） |

订单、机柜、合同状态这类「业务对象自己的状态」**永远在业务进程里**：如果每次改订单状态都要调远程服务，延迟与故障面都不可接受。服务只管「要有人来办」的那部分。

### 6.3 审批

**主流程**（以 powerbank 进场合同为例：运营审批 → 需要时财务会签）：

| 步 | 谁 | 做什么 | 结果 |
|:-:|---|---|---|
| 1 | 业务 | 校验合同数据；算属性 `needsCosign`；算锚点（站点、代理） | —— |
| 2 | 业务 | 合同状态 → 「审批中」；调 `提交(流程 LOC_CONTRACT, 对象, 属性)` | —— |
| 3 | 服务 | 检查该合同无待审审批单；按属性求**本轮计划**：`needsCosign=true` → [运营, 财务]，否则 [运营] | 审批单：待审，第 1 轮 |
| 4 | 服务 | 为第一步建任务（审批人规则 = 权限码 `location:contract:audit`）；投影待办 | 待办出现在所有持有该权限、且数据范围覆盖该站点的人名下 |
| 5 | 审批人 | 在待办里看到 → 决定「通过」 | —— |
| 6 | 服务 | 校验：不是提交人本人 · 任务仍待办 · 并发只一人赢 | 任务：已完成 |
| 7 | 服务 | 有下一步 → 为财务步建任务（该流程开启了规则 5：运营步的决定人**不能**再做财务会签）；没有 → 审批单：通过 | —— |
| 8 | 服务 → 业务 | 交付结果「通过」 | —— |
| 9 | 业务 | 结果回调里**幂等地**把合同改为「已签」 | 形态 A：与第 6 ~ 7 步同一事务 |

**分支**：

| 分支 | 触发 | 服务做什么 | 业务做什么 |
|---|---|---|---|
| 驳回 | 任一步决定「驳回」（必须填原因） | 审批单：驳回；取消本轮其余任务 | 回调里把合同改回草稿并记原因 |
| 撤回 | 提交人在待审时撤回 | 审批单：撤回；取消所有未完成任务 | 回调里改回草稿 |
| 再提交 | 驳回 / 撤回后修改再送审 | **新一轮**：重新求计划、建任务；旧轮次原样保留 | 重新算属性后调「再提交」 |
| 或签 | 一步多个审批人，一人决定即可 | 一人决定后取消同步其余任务 | —— |
| 会签 | 一步多个审批人，都通过才算 | 全部通过才进下一步；任一驳回即整单驳回 | —— |
| 队列领取 | 审批人规则 = 队列（ichain 审核队列形态） | 任务先「领取」才能决定；领取超时自动放回 | —— |
| 审批超时 | 步骤设了时限且到期 | 标记超时、发事件（催办交给通知） | —— |

### 6.4 工单

**主流程**（以 powerbank 运维工单为例：告警 → 派运维 → 维修 → 复核 → 关闭）：

| 步 | 谁 | 做什么 | 工单状态（角色） |
|:-:|---|---|---|
| 1 | 业务 | 告警触发；算锚点（站点、代理）；去重键 = `告警码 + 设备` | —— |
| 2 | 服务 | **去重开单**：同一去重键已有未结单 → 附加一条时间线、返回那张单；否则新建 | 新建（`INITIAL`） |
| 3 | 服务 | 按类型的派单方式：**指派**（业务给受理方）/ **抢单池**（进池等人抢）/ **规则**（业务算好受理方后指派） | 已派单（`ACTIVE`）→ **SLA 起算** |
| 4 | 受理方 | 接单 → 开始处理（每一步都是对工单「发一个事件」） | 处理中（`ACTIVE`） |
| 5 | 受理方 | 需要等配件 → 发「等待」事件 | 等外部（`WAITING_EXTERNAL`）→ **SLA 暂停** |
| 6 | 受理方 | 配件到了 → 发「恢复」事件 | 处理中 → **SLA 恢复**，到期顺延 |
| 7 | 受理方 | 完工 | 待复核（`AWAITING_VERIFY`） |
| 8 | 复核人 | 复核通过 → 关闭 | 已关闭（`TERMINAL`），关闭原因 `RESOLVED` → **停表**、移出待办 |
| 9 | 服务 → 业务 | 每次迁移交付回调 | 业务在「完工」回调里幂等地回写设备状态 |

**分支**：

| 分支 | 触发 | 服务做什么 |
|---|---|---|
| 复核不过 | 复核人驳回 | 按状态图退回处理中（**不回新建** —— 返工是同一人再修，不是重新派单） |
| 驳回派单 | 受理方拒接 | 退回新建，清空受理方，可重新派 |
| 升级 / 接管 | 超时未处理、或运营手动接管 | 换受理方、打升级标记、写时间线 |
| 受理方不可用 | 代理被停用、商家停业（业务通知服务） | 名下所有未结单改派或回池 |
| 撤单 | 起因消失（告警自愈且尚未接单） | 关闭，原因 `WITHDRAWN` |
| 合并 | 被上层工单取代 | 关闭，原因 `DUPLICATE`，记「并入」单号 |
| 改优先级 | 运营调整 | SLA 从起算点按新规则重算，已暂停时长照扣 |
| SLA 超时 | 定时扫描发现到期 | 计时状态「超时」、写时间线、发事件（催办 / 自动升级由订阅方决定） |

### 6.5 工单内嵌审批（合并后才有的流程）

以「维修费用超过额度需审批」为例：

| 步 | 谁 | 做什么 |
|:-:|---|---|
| 1 | 受理方 | 提交维修费用 |
| 2 | 业务 | 判断超额 → 对工单发「申请费用」事件，附属性 `amount` |
| 3 | 服务 | 工单进入「等审批」（`WAITING_EXTERNAL`，SLA 暂停）；**在服务内部**以该工单为业务对象发起审批（工单类型里登记了可发起的流程） |
| 4 | 服务 | 审批结束 → **在服务内部**推进工单：通过 → 回到处理中；驳回 → 回到处理中并在时间线记驳回原因 |
| 5 | 服务 → 业务 | 只交付工单迁移回调；业务不需要知道中间有过一次审批 |

分成两个服务时，这一段需要业务在两个回调之间来回编排；合成一个服务后在服务内部闭环。

### 6.6 待办

| 步 | 做什么 |
|:-:|---|
| 1 | 审批任务创建 / 领取 / 完成 / 取消、工单派单 / 进池 / 抢单 / 关闭时，同步更新待办项 |
| 2 | 查「我的待办」：用操作人上下文匹配「谁能办」—— 指定人、持有权限码、属于角色、属于队列、是当前受理方、能抢该池 —— 再按数据范围过滤 |
| 3 | 按到期时间、优先级排序；返回数量角标 |

审批与工单在同一张待办里，这是合并后给用户最直接的变化：一个人不用去两个地方看。

### 6.7 SLA 与超时

| 步 | 做什么 |
|:-:|---|
| 1 | 工单首次进入 `ACTIVE`、或审批步骤开始时：按「规则组 + 对象 + 优先级」找规则，按日历算出到期时间 |
| 2 | 进出 `WAITING_EXTERNAL`：累计暂停时长、顺延到期 |
| 3 | 定时扫描（形态 A 由 powerbank 的定时任务调；形态 B 服务自调）：分批取「未结且到期」的，标超时、写时间线、发事件 |
| 4 | 进终态：停表，按时完成记「按时」 |

### 6.8 结果回调与对账（形态 B 才有）

| 步 | 业务 | 服务 |
|:-:|---|---|
| 1 | 业务状态先改为「审批中 / 已开单」，同事务写请求发件箱（带幂等键） | —— |
| 2 | 发件箱投递；失败退避重试 | 按幂等键去重；重复请求返回首次结果 |
| 3 | —— | 引擎推进；同事务写回调发件箱 |
| 4 | 收到回调，按幂等键处理；返回成功 | 失败退避重试 |
| 5 | 对账：本地「审批中」超过阈值的，向服务查一次，按结果补推 | 提供查询 |

## 七、为什么合成一个服务

| 收益 | 说明 |
|---|---|
| 统一待办 | 审批任务与工单在同一张待办里（§6.6） |
| 工单内嵌审批在服务内闭环 | 不用业务在两个回调间编排（§6.5） |
| 审批也有时限与催办 | 审批步骤复用工单的 SLA 规则与工作日历 |
| 一套基础设施 | 定义登记、接入系统、发件箱、幂等、回调、对账、数据范围只做一遍；部署、库、凭证也只有一套 |

| 代价 | 应对 |
|---|---|
| 服务变大 | 六个领域各自独立的包与表，只通过事件协作；将来真要拆可按领域拆 |
| 只用状态机的业务（ai-erp、ai-neargo）也要面对整个服务 | 不会：状态机库在 `flow-api` 里零依赖，只依赖它即可，服务都不用接 |

## 八、与业务解耦的四条规则（从第一天遵守）

| # | 规则 | 为什么 | 谁守 |
|:-:|---|---|---|
| R1 | 业务只调 `flow-client` 的接口，不直接用引擎类 | 形态 A / B 是同一接口的两种实现 | 架构测试 |
| R2 | 业务相关的判断在业务侧做完，只交数据 | 独立服务里没有业务代码，函数传不过去 | 定义对象本身不接受函数 |
| R3 | 结果回调从第一天起**幂等** | 形态 B 下可能重复交付；形态 A 下写成幂等没有代价 | 契约测试：交付两次，业务只变一次 |
| R4 | 结果回调只推进业务自己的状态，不回头调服务 | 形态 A 会重入；形态 B 会形成环 | 契约测试 |

业务侧只需提供三样：**操作人上下文**（我是谁、有什么权限角色队列）· **数据范围条件**（我能看哪些）· **锚点**（这个对象属于哪个站点 / 代理 / 商家）。
