# 04 · 项目代码结构

> 所属：[16 工作流与工单](./README.md) · 状态：**待确认**（2026-09-27）· 依据：[03 设计方案](./03-设计方案.md)
> 命名与分包照 ai-shop 任务模块的现行写法（`job-api` 放契约与 `JobHttpPaths`；`job-store` 用 `XxxDao` + `XxxRow`、自带自动装配与 `db/job/V*.sql`；`job-worker` 用 `@HttpExchange` 调业务），让两边的人看着眼熟。
> 下面的类名是**骨架**：定职责与归属，实现时可以增补，但不跨子模块挪动。

---

## 一、在 powerbank 里的位置

```
powerbank/backend/
├── pom.xml                      # 加两个 <module>：workflow · workorder
├── workflow/                    # 工作流模块（聚合）
├── workorder/                   # 工单模块（聚合）
├── sharehub-common/
├── sharehub-api/
├── sharehub-svc-*/
└── sharehub-app/                # 形态 A：依赖 workflow-core · workorder-core
```

| 项 | 取值 |
|---|---|
| 聚合 POM | `ai.neargo.workflow:workflow-parent` · `ai.neargo.workorder:workorder-parent`，父为 `neargo-parent`（与 `sharehub-parent` 平级） |
| 版本线 | 各自独立，从 `0.1.0-SNAPSHOT` 起；发布后与产品版本解耦 |
| 产品依赖 | `sharehub-app` 依赖 `workflow-core` · `workorder-core`；各业务 `sharehub-svc-*` 只依赖 `workflow-api` · `workorder-api` |

## 六、产品侧的代码放哪（以 powerbank 为例）

| 放什么 | 放哪 | 例 |
|---|---|---|
| 状态机定义 | 各业务域，与状态枚举同包 | `sharehub-svc-ops/…/wo/WoStateMachine.java` 改为持有一个 `StateMachine<WoStatus, WoEvent>` |

| 结果回调 | 业务域 | `ContractApprovalOutcome implements ApprovalOutcomeHandler` · `MaintenanceTransition implements WorkOrderTransitionHandler` |
| 三个 Provider | 产品的公共层（只写一次） | `sharehub-common/…/workflow/StaffActorContextProvider.java`（从 `StaffContext` 取）· `DataScopeConditionProvider.java`（从数据范围翻译）· `SiteAnchorResolver.java` |

其他项目同理：Provider 各写一次，定义与回调跟着业务域走。

## 七、构建

| 项 | 做法 |
|---|---|
| 模块顺序 | `workflow` → `workorder` → 产品模块（在 `backend/pom.xml` 的 `<modules>` 里排在 `sharehub-*` 之前） |
| 独立构建 | 每个聚合都能单独 `mvn -pl workflow -am verify`；不依赖任何 `sharehub-*` |
| `*-svc` | 不进产品的默认构建；打包服务时单独 `mvn -pl workflow/workflow-svc -am package` |
| 数据库测试 | `*-store` 用 H2（MySQL 模式）跑单测；CI 另跑一轮 MySQL 与 PostgreSQL（Testcontainers） |
| 架构测试 | 每个子模块带 ArchUnit：api 不依赖 Spring；产品构件一律禁入；engine 包只许本模块与 svc 引用 |
| 副本防漂移（Nexus 就绪前） | 见 [07 落地计划](./07-落地计划.md) §二 |
