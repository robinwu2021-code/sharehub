## 二、工作流引擎：Flowable 8.0.0

### 2.1 决定与理由（10 §4.3 的结论，此处给可执行版本）

| 问题 | 答 |
|---|---|
| 为什么不自研引擎 | 用户已定「工作流引擎不用自研」 |
| 为什么是 Flowable | 候选里唯一同时满足「Apache 2.0 · 可嵌入（不用运维集群）· 仍在维护」：Camunda 7 社区版 2025-10 停维 · Camunda 8 非 OSI 许可且要 broker 集群 · Temporal 要集群且"流程是代码"（外部系统登不了记）· Conductor 已归档 · Activiti 活跃度低于 Flowable |
| 为什么是 8.0.0 而不是 7.2.0 | 8.0.0 的基线是 **Spring Boot 4.0.2 · Spring Framework 7.0.3 · JDK 17**，与我们的 Boot 4.0.7 同代；7.2.0 还停在 Boot 3.5.4 线，装不进来 |
| 引擎会不会漏到业务 | 不会。对外契约是「定义是数据」：业务登记状态图 / 流程 JSON，**工作流模块生成 BPMN** 再喂 Flowable；API、webhook 与 10 §五 一致 |

### 2.2 装什么、不装什么

| 坐标 | 装不装 | 理由 |
|---|:-:|---|
| `org.flowable:flowable-spring-boot-starter-process:8.0.0` | ✅ | **只要 BPMN 流程引擎** |
| `org.flowable:flowable-spring-boot-starter` | ❌ | 伞形 starter，核出来它同时拉 `starter-app` · `starter-cmmn` · `starter-dmn` 三套 configurator —— 白装二十多张表 |
| `flowable-spring-boot-starter-cmmn` / `-dmn` | ❌ | 我们不用 Case / 决策表 |
| `flowable-spring-boot-starter-rest` · Flowable UI / Modeler | ❌ | 不开引擎自己的 REST 与建模器；对外只走我们自己的 `/api/flow/v1`。**建模器一旦开，就出现第二条定义入口，"定义是数据"当场破功** |
| `flowable-image-generator`（传递进来） | ⚠️ 排除 | 我们不出流程图 PNG，白带 batik 依赖 |
| IDM | ❌ 关 | 候选人不同步身份目录，用 candidateGroups 编码（§2.3） |

### 2.3 概念怎么映射（决定了哪些能力白拿、哪些还得自己写）

| 我们的概念 | Flowable 的 | 说明 |
|---|---|---|
| `system_code`（多系统隔离） | `tenantId` | 每张 `ACT_*` 表自带，直接映射；验收用「A 系统凭证查 B 数据 → 404」 |
| 人工任务 | UserTask | 白拿 |
| 资格 / 队列 | `candidateGroups` | 编码成 `PERMISSION:x` · `ROLE:x` · `QUEUE:x`，不同步用户目录 |
| 领取 / 放回 | `claim` / `unclaim` | 白拿；领取**超时**自动放回要自己扫（Flowable 没有这个语义） |
| 到期 | `dueDate` + 定时器 | 白拿计时；**营业时间 / 暂停 / 恢复 要自己算**（§2.4） |
| 流程版本 | 定义版本 | 白拿；我们另存内容哈希版本对外 |
| 审批轮次 / 或签 / 会签 / 五条内建规则 | —— | **自己写**（`workflow-core`） |
| 待办投影（跨 kind 合并 + 锚点 fail-closed 过滤） | —— | **自己写** |
| 工单全套（派单 · 抢单 · 升级 · 合并 · 时间线） | —— | **自己写**（`workorder-*`） |

**一句话**：Flowable 承担"流程实例推进 + 人工任务 + 租户隔离 + 定时器"，其余全在我们的薄层里。引擎换掉的是最容易写错的那部分（并发推进与持久化），而不是业务语义。

### 2.4 顺带被否掉的两个

| 方案 | 否 | 理由 |
|---|:-:|---|
| Spring Statemachine 做状态机 | ❌ | 配置是代码 / 枚举，不是可由外部系统登记的数据（形态 B 的服务里没有产品枚举）；比需求重。状态机继续用自研薄门面：它只做"图的校验 + 投影"，几百行 |
| 用 Flowable 跑工单生命周期 | ❌ | 工单是**角色驱动**（D2），且工单模块必须能脱离工作流单独部署（D6）。让工单依赖 BPMN 引擎等于把这两条都作废 |

## 三、已核出的三处咬合点（落地前就会撞）

### 3.1 Boot 版本差：Flowable 基线 4.0.2 vs 我们 4.0.7

| 事实 | 处理 |
|---|---|
| `flowable-dependencies:8.0.0` 里 `spring.boot.version=4.0.2` | 我们的 `spring-boot-dependencies:4.0.7` BOM **先导入**，Spring 构件统一到 4.0.7，`dependencyConvergence` 不会红 |
| 同为 4.0.x 补丁线，但 Flowable 未针对 4.0.7 认证 | 由 **B1 打通性实测**作为放行前置，不靠推断 |

### 3.2 MyBatis：Flowable 自带 vs MyBatis-Plus

| 事实 | 结论 |
|---|---|
| `flowable-dependencies:8.0.0` → `mybatis 3.5.19` | **同版本，不撞** |
| `mybatis-plus-core:3.5.16` → `org.mybatis:mybatis:3.5.19` | 同上（已逐字核 pom） |
| 但 Flowable 与 MyBatis-Plus 各自装配 `SqlSessionFactory` | 形态 A（嵌入业务进程）下**必须给 Flowable 独立的 SqlSessionFactory / 事务管理器配置**，否则两边的拦截器（MP 的分页、租户插件）会串到 `ACT_*` 查询上 —— 这是嵌入式引擎最经典的事故，列为 B1 的必测项 |

### 3.3 Jackson：两条线共存

| 事实 | 处理 |
|---|---|
| Boot 4 走 Jackson 3（`tools.jackson`） | 我们的 DTO、API、webhook 一律 Jackson 3 |
| `flowable-engine:8.0.0` 依赖 `jackson-databind`（2.20.1 线） | 留着，作为 Flowable 内部实现细节；**不在我们代码里 import `com.fasterxml.jackson`** |
| 风险 | 类路径上两套 Jackson 会让"为什么这个注解不生效"极难查。加一条 ArchUnit 规则：`ai.neargo.workflow..*` / `ai.neargo.workorder..*` 不得引用 `com.fasterxml.jackson..*` |

## 四、其余选型与理由

| 项 | 选 | 放弃 | 为什么 |
|---|---|---|---|
| 业务表持久化 | Spring JDBC `JdbcClient` | MyBatis-Plus 实体 | 模块要能装进 jOOQ 的 ai-erp、也要装进 MP 的 powerbank；`job-store` 已是同样做法（D7） |
| 迁移 | 每模块独立 Flyway 实例 + 独立 `*_schema_history` | 并入项目 `db/migration` | 各项目 V 号各自增长，共用必撞号（D8）。powerbank 已到 V99+，撞号是当天就会发生的事 |
| 表前缀 | `wf_` / `wo_`（**待 D5 确认**；03 写的是 `nwf_` / `nwo_`） | 无前缀 | powerbank 已有 `wo_order`，迁移期两套并存必须不撞；`case` / `order` 在两种库都是保留字。**这处两份文档不一致，需拍板** |
| 定时互斥 | ShedLock 7.10.1（DB 锁表） | Quartz / 纯 `@Scheduled` | 已有 `known-inprocess-schedules.txt` 卡口在管进程内调度；Flowable 的 async executor 只锁它自己的 job |
| 缓存 / 幂等 | 数据库表（幂等键 · 发件箱） | Redis | 强一致优先；形态 A 下与业务同事务（03 §五）。Redis 只做可丢的热点缓存 |
| 服务间调用（形态 B） | `svc-client`（`@HttpExchange` + `RestClient`） | Feign | ai-shop 已在用且零业务依赖；下沉前两个 core 各带最小实现 |
| 契约 | springdoc-openapi **3.0.3** 生成 `openapi.yaml` 入库 | 手写 | 前端类型、其他语言 SDK 都从它生成（17 §一）。3.0.3 的 parent 是 Boot **4.0.5**（同 4.0 线）；3.1.1 已跟到 Boot 4.1，等我们升 Boot 再跟 |
| 架构守卫 | ArchUnit | 评审 | 模块依赖方向、`*-api` 不依赖 Spring、不得出现产品名词、不得引 Jackson 2 —— 每条配一个负对照（S0-2） |
| 双库测试 | Testcontainers | 只测 H2 | H2 测不出 MySQL / PG 的锁与保留字差异；引擎又要在两库上跑 `ACT_*` |

## 六、放行前置：B1 打通性实测（1 人日）

版本能核，行为不能核。下面每条都要有实据才算 Flowable 定稿：

| # | 测什么 | 通过标准 |
|:-:|---|---|
| 1 | Boot 4.0.7 + Flowable 8.0.0 起得来 | 应用启动、`ACT_*` 建表完成、无版本冲突告警 |
| 2 | MySQL 与 PostgreSQL 各一遍 | 同一条三步流程两库都跑通 |
| 3 | `ACT_*` 与 `wf_*` 共库不同前缀 | 两套 Flyway 历史表互不干扰 |
| 4 | **tenantId 隔离** | A 系统凭证查 B 的实例 → 404（**负对照：故意去掉 tenantId 条件必须变红**） |
| 5 | **SqlSessionFactory 隔离**（§3.2） | MP 的分页 / 租户插件不作用于 `ACT_*` 查询 |
| 6 | 定义 JSON → BPMN 生成 → 部署 → 跑通 | 一条三步审批流走完，含条件步 |
| 7 | 依赖收敛 | `mvn -pl flow -am verify` 在 `dependencyConvergence` 开着的情况下通过 |

**任一条不过就回到 §二 重评**——10 §4.2 的候选表原样保留，不是摆设。

### 6.1 B1-N：GraalVM native 打通性实测（追加 1.5 人日）

只在 T5 拍板要 native 时做，且**上面七条在 JVM 上全绿之后**才开始 —— 否则分不清是 native 的锅还是 Flowable 的锅。

| # | 测什么 | 通过标准 |
|:-:|---|---|
| N1 | `flow-svc` 编得出原生镜像 | `mvn -Pnative native:compile` 成功；**记下编译耗时与峰值内存**（决定 Jenkins agent 规格） |
| N2 | 起得来 + 建表 | 原生镜像连 MySQL 启动，Flyway 跑完 `ACT_*` 与 `wf_*` |
| N3 | **运行期生成 BPMN → 部署 → 跑通**（native 最大未知数，§9.3） | 一条三步审批流走完 |
| N4 | Flyway 多 vendor 目录资源可见（§9.5 B1） | MySQL 与 PG 各一遍，**核对历史表行数**，不看日志 |
| N5 | 定时器与 async executor | SLA 到期、领取超时在原生镜像里真的触发 |
| N6 | 上面 1–7 条在原生镜像上重跑 | 全绿，尤其 tenantId 隔离 |
| N7 | 收益量化 | 启动耗时、常驻内存 vs JVM 版。**拿不出明显收益就不做**（§9.6） |

| T3 | 形态 A 下 Flowable 是否与业务**共用数据源**（共用则 §3.2 的隔离必须做；独立库则简单但失去同事务） | 一致性模型 |
| T4 | 前端 Tailwind 分叉（17 §二）：包内预编译 CSS，还是要求宿主把包加进扫描源 | F1–F3 |
| **T5** | **GraalVM native 的范围**：建议**只 `flow-svc`（形态 B）**，不含 `sharehub-app`。若要 `sharehub-app` 也原生化，那是另一个项目（多个业务 svc + MyBatis-Plus），不该塞进本方案 | §九 · B1-N · 发布流水线 |
| **T6** | 接受形态顺序倒置：native 的收益只在独立进程上成立，而 03 §三 的缺省是形态 A（嵌入）。**要 native，等于要先做形态 B** | 03 §三 · 16 任务清单的 S 顺序 |

## 九、GraalVM 与 AOT

> 2026-09-27 用户提出「期望用 GraalVM、AOT」。本节回答：**方案要不要改**。
> 一句话：**架构不用改，五处要调**；并且先把「AOT」拆成两件风险差很多的事。

### 9.1 先拆词

| | **Spring AOT（JVM 上）** | **GraalVM native-image** |
|---|---|---|
| 做什么 | 构建期把 Bean 定义、代理、配置解析算好，生成源码 | 构建期把整个程序编成本地可执行文件 |
| 收益 | 启动加快、反射与配置解析开销下降 | 启动进入百毫秒级、常驻内存显著下降 |
| 代价 | 几乎为零 | 编译慢且吃内存 · 反射要穷举登记 · 排障难 · 测试要另起一套 |
| 运行期能动态加载类吗 | 能 | **不能**（封闭世界假设） |
| 建议 | **立刻开**（§9.2） | **限定 `flow-svc`，以 B1-N 放行**（§六 6.1） |

如果真正的诉求只是「启动快、少吃内存」，先开 Spring AOT、量一下，未必需要 native。下文按「两个都要」写。

### 9.2 Spring AOT：不用调整，直接开

| 事实（已核） | 结论 |
|---|---|
| Boot 4 自带 AOT（`spring-boot-maven-plugin` 的 `process-aot`） | `flow-svc` 打包时开，方案零改动 |
| **Flowable 8.0.0 自带 Spring AOT 提示**：`FlowableProcessRuntimeHints` 注册了 `org/flowable/db/mapping`（引擎的 MyBatis XML）、`org/flowable/impl/bpmn/parser/*.xsd`、`ScriptEngineFactory` 服务发现、`QueryVariableValue` 反射 | Flowable 官方把 native 当支持目标在维护 —— 选型时未知、现在核实的**加分项** |
| 7.2.0 也带 | AOT 不构成「必须 8.0.0」的新理由；§二 2.1 的理由（Boot 4 同代）不变 |

### 9.3 native 下最大的未知数：我们是**运行期**生成并部署 BPMN

这是本方案与 Flowable 官方 native 路径的**唯一实质分歧**：

| 事实 | 影响 |
|---|---|
| Flowable 的 AOT 处理器 `FlowableProcessAutoDeployBeanFactoryInitializationAotProcessor` 做的是**构建期**预部署 classpath 上的 `.bpmn20.xml` | 对我们**用不上**：BPMN 由登记的 JSON 在运行期生成（03 §六「定义是数据」），classpath 上一个 BPMN 文件也没有 |
| 所以我们走的是 Flowable native 支持里验证较少的那条路 | 列为 **N3**，是 B1-N 里最可能红的一条 |
| BPMN 解析是 StAX + 解析器直接 `new` 行为类，并非按名字反射；xsd 与 mapping 资源 Flowable 已登记 | 理论上可行。**理论上可行不是证据**，所以要测 |

### 9.4 五处调整

| # | 调整 | 为什么 |
|:-:|---|---|
| **A1** | **native 只做 `flow-svc`（形态 B），不做 `sharehub-app`** | `sharehub-app` 重度依赖 MyBatis-Plus：jar 内**零** native 元数据，只能靠外部维护的社区元数据（覆盖到 3.5.17，够用但不在我们手里）。而 `flow-*` 按 D7 用 `JdbcClient`，**完全不碰 MP** —— 它是本仓库**最适合原生化的模块** |
| **A2** | **生成的 BPMN 里禁止任何表达式与脚本**（JUEL `${…}` / Groovy / Nashorn），条件一律由我们的薄层求值后以流程变量写入 | 表达式求值靠反射解析属性，是 native 的头号杀手。**03 §六 本来就规定条件只支持「属性 = 值 / 为真 / ∈ 集合」** —— 设计本来就绕开了它。现在从「设计偏好」升为**硬约束**，并由 BPMN 生成器的校验与一条单测守住 |
| **A3** | **springdoc 只在构建期用，不进原生镜像** | 它靠运行期扫描控制器，native 下慢且易缺元数据。改为 JVM profile 生成 `openapi.yaml` 入库（本来就是契约真源），native profile 不打包它 |
| **A4** | **测试分两层**：Testcontainers 双库全量用例留在 JVM；原生镜像只跑 N1–N7 冒烟 | native 测试编译一次就是分钟级，把 S0-3 全量搬过去 CI 会不可用。负对照留在 JVM 层 |
| **A5** | **ShedLock 自补 hints**，或改用我们已有的幂等表做互斥 | 已核：社区元数据库里 Flyway / MyBatis / MP / springdoc 都有，**唯独 ShedLock 没有** |

### 9.5 另外四个会咬人的点

| # | 点 | 处理 |
|:-:|---|---|
| B1 | **Flyway 的 `{vendor}` 目录**：没登记为资源的 SQL 在原生镜像里读不到，表现是**迁移一条没跑、也不报错** | 显式把 mysql / postgresql / h2 三个目录登记为资源；N4 核历史表行数。与 CLAUDE.md 已记的「Boot 4 只加 flyway-core 不生效」同一形状：**都是静默不执行** |
| B2 | **两条 Jackson 线**（§3.3） | 我们的 DTO 走 Jackson 3 的具名类；Flowable 内部的 Jackson 2 由它自己的 hints 覆盖。ArchUnit「不得 import Jackson 2」在 native 下从可读性问题变成正确性问题 |
| B3 | **JDK 锁 21** | GraalVM for JDK 21 有 native-image，可用。Boot 另有基于新版 JDK 的 AOT cache 路线，若将来想走需先解 `neargo-parent` 的 enforcer 锁 —— 本次未核，需要时单独核 |
| B4 | **发布流水线** | N1 量出编译内存后定 Jenkins agent 规格；现有 buildah/docker 链路加多阶段构建（builder 编译 → 精简运行镜像） |

### 9.6 收益与代价

| 收益 | 代价 |
|---|---|
| `flow-svc` 冷启动与内存显著改善 —— 它要被多个系统共用、将来可能多实例，这是真收益 | 编译分钟级且吃内存；本地开发仍走 JVM |
| 镜像小、扩缩快，便于以后上容器编排 | 排障从「看栈」变成「找哪个反射没登记」 |
| 与「定义是数据、不跑脚本」的设计天然契合（A2） | 多一条构建与测试路径要长期维护 |

**建议**：Spring AOT 立刻开；GraalVM native 定为 `flow-svc` 的**目标而非前提** —— 先按 §六 把 JVM 版打通，再做 1.5 人日的 B1-N，**N7 拿不出明显收益就不做**。
