## 〇、先说一处需要你拍板的冲突

「把原型的颜色风格做成一套皮肤」与 ops-web 现行规范**有冲突**，必须先对齐：

| 事实 | 出处 |
|---|---|
| ops-web 的皮肤**只换主色**（`--primary` 五档派生）；中性灰 12 档与语义色（绿 / 黄 / 红 / 蓝）在四套皮肤下**完全相同** | `globals.css:127`「换肤不该动摇整个界面的观感」 |
| 「状态的含义不能随皮肤漂移，所以语义色四套皮肤下完全相同」 | 设计规范 §2.2 |
| 「三级灰阶梯」「简电青主色」等曾被明确**否决**，附了原因 | 设计规范 README 的被否决清单 |

而原型主界面的观感，主要来自它自带的语义色与灰阶。所以本方案的处理是（§三详述）：

| 原型要素 | 处理 | 理由 |
|---|---|---|
| 主色墨绿 `#0f7173` | ✅ 新增第五套皮肤 `teal` | 皮肤机制本就是换主色，零冲突 |
| SLA 四色条 · 状态徽章 · 时间线 · 步骤条 · 可点统计卡 · 表单化步骤编辑器 | ✅ 做成**通用组件**进 ops-web 组件库 | 这些是布局与组件，与皮肤无关，且能反哺现有页面 |
| 原型自带的灰阶与圆角 | ❌ 不搬，改用 ops-web 的 12 档灰与五档圆角 | 规范硬约束 + 已有卡口（`design-tokens.test.ts`） |
| 原型的语义色 | ⚠️ 只在**明显更好**时提议改 ops-web 的语义色本身（全站生效、四套皮肤一起变），不做成「一套皮肤」 | 语义色随皮肤漂移会让「红＝超时」在不同皮肤下不成立 |

**要你定**：若你要的确实是「连语义色和灰阶一起换的整套皮肤」，那要先修订设计规范 §2.2 并解释为什么状态色可以漂移 —— 我不会绕过规范自行放宽。下文按「主色成皮肤 + 其余成组件」推进。

## 一、前端形态：独立仓库 + 可嵌入包 + 可跳转

### 1.1 结论

**一套代码，三种用法**：独立站（自己的域名）· 嵌入宿主运营台（ops-web 里的菜单叶）· 从宿主跳转（带上下文的深链）。

| # | 决定 |
|:-:|---|
| 1 | 前端**独立**：独立仓库 / 独立构建，与 `flow` 服务同版本线，不住在 ops-web 里 |
| 2 | 产物两个：`@neargo/flow-ui`（React 组件包，给宿主嵌入）· `flow-console`（独立站，装同一个包 + 最小外壳） |
| 3 | 嵌入 ops-web 用 **npm 包 + 路由挂载**，不用 iframe（§1.3 给了理由） |
| 4 | 跳转用**深链**：`/flow/work-orders/WO26092701`，带 `?from=`，回跳用宿主提供的返回地址 |
| 5 | 身份与权限**全部来自宿主**，平台前端不做登录（PRD 已定） |

### 1.2 三种用法

| 用法 | 谁在用 | 怎么接 |
|---|---|---|
| **嵌入**（首选） | ShareHub ops-web、ai-shop 运营台 | 宿主装 `@neargo/flow-ui`，在自己的路由下挂 `<FlowRoutes>`，传入 `FlowProvider`（身份、权限、数据范围、主题、跳转函数） |
| **跳转** | 宿主里不便嵌入的位置（如告警详情「查看工单」） | 深链到宿主自己的 `/flow/...` 路由（仍是嵌入页），不跳出站 |
| **独立站** | 没有运营台的接入方（ichain / tradeagent）；平台管理员的接入管理 | `flow-console` 部署一份，用宿主的 OIDC / 令牌换取身份（§二 2.4） |

### 1.3 为什么是 npm 包而不是 iframe / 微前端

| 方案 | 否决理由 |
|---|---|
| iframe | 身份与权限要跨 frame 传；主题无法继承（你要的「皮肤赋能」直接落空）；弹窗、键盘焦点、返回键都要额外桥接；高度自适应长期不稳 |
| 微前端（Module Federation 等） | 为一个包引入一整套运行时与构建耦合，收益不抵成本；ops-web 是 Next.js，宿主构建差异大 |
| **npm 包** ✅ | 主题天然继承宿主 CSS 变量（这正是「皮肤赋能」成立的前提）；类型与契约随包走；版本可控 |

### 1.4 包边界

```
@neargo/flow-ui
├── pages/        九个页面组件（TodoCenter · ApprovalList · ApprovalDetail · ReviewQueue
│                  WorkOrderBoard · WorkOrderDetail · FlowConfig · OpsConfig · AccessAdmin）
├── components/   平台专有：SlaBar · Timeline · StepFlow · ApproverRuleField · DefinitionVersionList
├── client/       契约客户端（按 14 的接口）+ 类型（由 openapi.yaml 生成）
├── provider/     FlowProvider：身份 · 权限 · 数据范围 · 主题 · 导航 · i18n · 时区
└── routes/       <FlowRoutes basePath> —— 宿主挂载点
```

**不含**：登录页、侧边导航外壳、全局布局、菜单。这些是宿主的。

## 二、统一权限管理

### 2.1 原则

**权限码在平台定义，判定在宿主与服务两端执行。** 平台不建自己的用户体系（PRD 已定：身份来自宿主）。

| 层 | 谁判 | 判什么 |
|---|---|---|
| 菜单可见 | 宿主前端 | 宿主自己的菜单权限码（ops-web 现有机制：登录下发 `perms`，按码判） |
| 页面内按钮 | `@neargo/flow-ui` | 用 `FlowProvider` 传入的 `perms` 判：有没有这个码 |
| 数据可见 | flow 服务 | 按请求带的 `ScopeCondition` 过滤，fail-closed |
| 能不能做这个动作 | flow 服务 | 资格匹配（是不是这条任务的合法办理人 / 领取人 / 受理方） |

三层缺一不可：**前端判权只是体验，闸在服务端**（延续 ops-web 既有口径）。

### 2.2 平台权限码（建议，需进真源表）

平台定义一套中性权限码，各宿主把它们纳入自己的角色体系：

| 权限码 | 含义 | 对应页面 |
|---|---|---|
| `flow:todo:read` | 看自己的待办 | P1 |
| `flow:approval:read` | 查审批单（全部，非仅待我审） | P2a · P2 |
| `flow:approval:decide` | 做审批决定 | P2 |
| `flow:queue:claim` | 队列领取与决定 | P3 |
| `flow:workorder:read` | 查工单 | P4 · P5 |
| `flow:workorder:handle` | 办理工单（接单 / 处理 / 完工 / 备注） | P5 |
| `flow:workorder:dispatch` | 派单 / 改派 / 升级 / 合并 / 改优先级 | P4 · P5 |
| `flow:definition:manage` | 流程配置（发布新版本 / 停用） | P5a |
| `flow:config:manage` | SLA / 日历 / 队列配置 | P6 |
| `flow:access:manage` | 接入管理（系统 · 凭证 · webhook） | P7 |

> ⚠️ 按本仓库纪律，**用权限码前先确认它在真源表中存在**。上表是提案，需先进 `docs/requirements/功能权限清单.md` 并走 `perm-ssot-align` 卡口，再写进代码。

### 2.3 宿主怎么把权限交给平台

```tsx
// ops-web 里（示意）
<FlowProvider
  actor={{ actorType: "STAFF", actorNo: me.employeeNo, actorName: me.name,
           permissions: me.perms, roles: me.roles, queues: me.queues }}
  scope={toScopeCondition(me.dataScope)}     // 宿主把自己的数据范围翻成锚点条件
  api={{ baseUrl: "/api/flow-proxy", fetch: opsWebFetch }}  // 走宿主的鉴权代理
  theme={{ mode: "inherit" }}                 // 继承 ops-web 的 CSS 变量
  nav={{ push: router.push, back: () => router.back() }}
  locale={locale} timeZone={bizZone}
/>
```

**请求不直连 flow 服务**：经宿主的后端代理（`/api/flow-proxy`），由宿主用**服务凭证**调平台。好处：浏览器里不出现平台凭证；`system_code` 由凭证决定，前端伪造不了；宿主可在代理层再做一次权限校验。

### 2.4 独立站的身份

独立站没有宿主页面，但仍不自建账号体系：用宿主的 OIDC / 令牌换取一次性会话（谁接入谁提供），拿到同样的 `actor` 与 `scope` 后走同一套组件。首版只给平台管理员与没有运营台的接入方用。

## 三、UI 整合：布局照 ops-web，组件与主色来自原型

### 3.1 皮肤：新增第五套 `teal`

```css
/* globals.css 皮肤块新增一行 —— 与现有四套同构，只换主色 */
[data-theme="teal"] { --primary: #0f7173; --primary-foreground: #ffffff; }
.dark[data-theme="teal"] { --primary: #2aa7a8; --primary-foreground: #06201f; }
```

| 项 | 说明 |
|---|---|
| 为什么能加 | 皮肤机制本就是「只换主色」，加一套与既有四套同构，不动语义色与灰阶 |
| 暗色为什么要单列 | 与 `mono` 同理：`#0f7173` 在深底上对比不足，暗色下提亮 |
| 验收 | 五档派生（`--primary-{1..5}`）在两种色彩模式下都过对比度；切到 teal 后语义色不变 |

### 3.2 从原型提炼、进 ops-web 组件库的六个组件

这些是「原型的可取之处」的真正载体，**全部用 ops-web 现有 token 实现**（语义色、12 档灰、五档圆角、七档类型阶）：

| 组件 | 来自原型 | 进组件库后谁还能用 |
|---|---|---|
| `<SlaBar value state>` | 工作台 SLA 四色条（绿 / 黄 / 红 / 灰暂停） | 任何有时限的列表：提现审批时效、合同到期 |
| `<Timeline items>` | 工单详情时间线（迁移 / 派单 / 备注 / SLA 事件同一条流水） | 订单事件、合同审批历史、设备生命周期 |
| `<StepFlow steps current>` | 审批进度条（含条件步标记） | 站点五态、合同状态、入驻流程 |
| `<StatCard clickable queryParams>` | 工作台可点统计卡 | 统一「卡片数字 ↔ 列表筛选」的口径；PRD 把「统计卡必须可点」写进验收，正是因为不可点的卡出现过（§5.8 #12 记过一次） |
| `<RuleToggleGroup>` | 流程配置的三条规则开关（含「不可关」态） | 任何「规则开关 + 说明」的配置块 |
| `<VersionHistory>` | 流程配置版本历史 | 定义版本、价格方案版本 |

**反哺是这件事的主要收益**：ops-web 现有页面正因为缺这些组件，才出现「内联 `Badge tone={}` 58 处」「手写『仅可查看』17 处」这类棘轮基线。新组件落地后，那些数字才可能往下降。

### 3.3 布局：一律照 ops-web

| 项 | 照谁 |
|---|---|
| 外壳（rail / content / 表面与分隔 / 滚动归属 / RTL） | ops-web 设计规范「布局与外壳」，平台前端**不自带外壳** |
| 页面骨架（列表 = `PagedTable`、筛选 = 既有 chips / 下拉、抽屉 = `FormDrawer`） | ops-web 现有组件，平台页面直接用 |
| 密度、间距、类型阶 | ops-web token（注意：**类型阶不与 `font-*` / `leading-*` 共存**，CLAUDE.md 明确记过） |
| 空态、错误态、409 提示 | ops-web 既有约定 + PRD 的解释性空态要求 |

### 3.4 原型怎么改

原型现在是独立色板，与上述不一致。**建议改一版**，把颜色换成 ops-web token 的实际值、圆角换成五档，这样它从「设计稿」变成「真实预览」。改完后原型仍可单文件打开，但看到的就是将来 ops-web 里的样子。

## 四、落地顺序

| 阶段 | 做什么 | 卡口影响 |
|:-:|---|---|
| **U1** | ops-web 加 `teal` 皮肤 + 六个组件进组件库（`/dev/ui` 组件总览页可自查） | 零：纯新增，现有页面不动 |
| **U2** | 原型改成 ops-web token 版 | 零 |
| **U3** | 权限码提案进真源表，过 `perm-ssot-align` | 按既有流程 |
| **U4** | 建 `@neargo/flow-ui` 骨架 + `FlowProvider`；用 mock 在 ops-web `/dev/flow` 下渲染两页（待办中心 · 工单详情） | 零：不进菜单、不挂 https 契约 |
| **U5** | flow 服务的只读端点可用后，接真接口；页面进菜单（需菜单迁移 + `nav.ts` + 快照卡口） | 正常流程 |
| **U6** | `flow-console` 独立站外壳；ai-shop 接入适配层 | —— |

U1 ~ U4 全部零卡口风险，且 U1 的组件立刻能反哺现有页面 —— 这是先做它的理由。
