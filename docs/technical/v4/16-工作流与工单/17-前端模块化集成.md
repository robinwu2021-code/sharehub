> 本篇回答：一套源码怎么嵌进栈各不相同的宿主。下面每条「实测」都是 2026-09-27 从各仓源码核出来的。

## 一、先看清宿主有几种栈（实测 36 个仓）

| 组 | 栈 | 前端数 | 例 |
|:-:|---|:-:|---|
| **H1** | Next 16 · React 19 · **Tailwind 4**（ops-web 同一模板） | **8** | powerbank · ai-shop · ai-agent · ai-boss ×3 · soukmind · ai-kb |
| **H2** | React 19 · **Vite 8** · Tailwind 4 | 4 | ai-admin · ai-erp · ai-Recs · ai-glow |
| **H3** | **React 18** · Vite 5（Tailwind 3 或无） | 5 | boss-web ×4 · merchant-web · ai-whatsapp |
| **H4** | **Vue 3 · UnoCSS**（uni-app） | 3 | powerbank/c-app · ai-shop/b-app · ai-shop/c-app |
| **H5** | 无 JS 前端 | 2 | ichain · tradeagent |

两个结论直接落在方案上：

1. **H1+H2 共 12 个宿主是同一代栈**（React 19 + Tailwind 4）—— npm 包对它们是最优解。
2. **H3/H4/H5 共 10 个宿主吃不下 React 19 的包** —— 必须有第二种出口，否则「共用」只是对一半人共用。

还有一条与栈无关但同样致命：**H1 全是 `output: "export"` 静态导出**。npm 包是编译期依赖，平台每发一次 UI，**12 个宿主各自重新构建 + 部署**。这是 npm-包-唯一方案的真实成本，也是必须有运行时出口的理由。

## 二、方案：一套源码，四个出口

| 出口 | 形态 | 装配时机 | 适用 | 覆盖 |
|:-:|---|---|---|:-:|
| **E1** | npm 包 `@neargo/flow-ui`（React 组件） | 编译期 | H1 · H2 | 12 |
| **E2** | **Web Component** `flow-embed.js` → `<flow-console>` | **运行时** | H3 · H4 · 任何栈，含纯 HTML | 10 |
| **E3** | 独立站 `flow-console` + SSO 跳转 | 无 | H5 · 外部单位 · 平台管理员 | 2 |
| **E4** | `@neargo/flow-client`（纯 TS，零 UI） | 编译期 | 只要数据、自己画（uni-app 小部件） | 3 |

四个出口**共用同一份页面组件**。能做到的前提是页面组件本来就不碰宿主：不 import `next/*`、不读宿主 store、导航与身份全经 `FlowProvider` 注入（架构测试守住：禁止 import 任何宿主路径）。E2 因此只是 ~50 行 wrapper，不是第二套界面。

### 2.1 E1 · npm 包（深集成）

```tsx
// ops-web: app/flow/page.tsx
"use client";
import { FlowRoutes } from "@neargo/flow-ui";
export default function Page() { return <FlowRoutes basePath="/flow" />; }
```

能力：组件用宿主的类名与 token；可以只取单个组件嵌进宿主已有页面（把「审批卡」放进站点详情页）；类型安全；无外域脚本。
代价：宿主须同代栈；平台发版要宿主重新构建。

### 2.2 E2 · Web Component（跨栈、运行时）

```html
<script type="module" src="/flow-embed/v1/flow.js"></script>
<flow-console view="todo"></flow-console>
```

```js
// 身份不进 DOM 属性 —— 用 property 传宿主自己的 fetch，令牌不出宿主存储
document.querySelector("flow-console").flowContext = {
  actor, scope, fetch: hostFetch, locale, timeZone,
};
```

能力：宿主是什么栈都行；平台发版宿主零动作（URL 带主版本，补丁自动生效）；皮肤仍然跟随宿主，因为**CSS 自定义属性会继承**，`--flow-*` 自动取到宿主的值。
代价：样式自带一份（见 §三）；宿主不能用自己的类改内部；要么允许外域脚本，要么像 API 一样 nginx 反代到同源。

### 2.3 为什么不是 iframe / 微前端

| 方案 | 否决理由 |
|---|---|
| iframe | 皮肤与字体不继承；双滚动条；弹层与下拉被 iframe 边界裁掉；键盘焦点与深链、返回键都要另造桥。**唯一优点是样式绝对隔离**，而这点 E2 用前缀 + 不引 preflight 已经够（§三） |
| Module Federation | 它的收益就是「运行时远程」，E2 已经给了，且跨栈还能用；而 Next 16 + Turbopack 对 MF 支持薄，12 个宿主各配一遍构建插件不划算 |
| single-spa 之类 | 为「多个应用抢一个页面」而生；这里是「一个平台嵌进多个宿主」，方向相反 |

## 三、样式：两个必须先定的技术前提（都已实测）

### 3.1 Tailwind 4 不扫 `node_modules`（影响 E1）

实测：ops-web 的 `globals.css` 第一行只有 `@import "tailwindcss";`，无 `@source`，无 `tailwind.config.*`。Tailwind 4 默认不扫 `node_modules`，所以包里的类名**根本不会被生成 —— 页面完全没样式**。这种失败不报错，容易被当成组件写错去查。

解法：宿主加一行

```css
@source "../node_modules/@neargo/flow-ui/dist";
```

12 个宿主各一行，写进接入清单。

### 3.2 E2 的 CSS 必须去掉 preflight（影响 E2）

实测 `node_modules/tailwindcss/` 下 `preflight.css` · `theme.css` · `utilities.css` **可以分开引**。这很要紧：preflight 会 reset `*` 的 margin/padding/border、把 `ul/ol` 的 `list-style` 清成 `none`、把 `img/svg` 改成 `display:block` —— 整块注进 Vue + UnoCSS 宿主会把宿主样式冲掉。

所以 E2 的构建：

```css
/* 只要 theme 与 utilities，不要 preflight；再加前缀避免与宿主类名相撞 */
@import "tailwindcss/theme.css" layer(theme);
@import "tailwindcss/utilities.css" layer(utilities);
```

加上元素级的最小 reset（只作用于 `flow-console` 内部），以及类名前缀（Tailwind 4 的 `prefix(...)` 写法要在实做时验证，别照抄 v3 的 `prefix` 配置项）。

### 3.3 颜色一律走变量，包内不写死色值

```css
/* @neargo/flow-tokens —— 契约：平台需要这些槽位，值由宿主给 */
:root, flow-console {
  --flow-primary: var(--primary);      /* 回落到宿主主色 */
  --flow-ok:  var(--green-solid);
  --flow-warn: var(--amber-solid);
  --flow-bad: var(--red-solid);
  --flow-surface: var(--surface);
  --flow-line: var(--gray-6);
}
```

宿主什么都不做就继承自己的语义色；要单独调只覆盖 `--flow-*`，**不影响宿主自身**。这也是 E2 跨栈还能保持皮肤一致的机制，也是 iframe 被否的根本原因。

另外两条硬约束（CLAUDE.md 与设计规范）在包内同样生效，`flow-ui` 的 CI 跑 ops-web 同一套 `design-tokens` 检查：只用 `rounded-control/field/card/sheet/chip` 五档；**类型阶不与 `font-*` / `leading-*` 共存**（`.txt-*` 在非 layer 区永远胜出，共存的字重行高是死代码）。

## 四、包怎么切

| 包 | 内容 | 依赖 | 谁装 |
|---|---|---|---|
| `@neargo/flow-client` | 契约客户端 + 类型（由 `openapi.yaml` 生成）。**零 UI、零框架** | 无 | 任何前端，含 uni-app |
| `@neargo/flow-tokens` | CSS 变量契约（只定槽位，不定色值） | 无 | 宿主（或由 flow-ui 带入） |
| `@neargo/flow-ui` | 九个页面 + `FlowProvider` + `FlowRoutes` | React · 上两个 | H1 · H2 |
| `flow-embed`（产物 `flow.js`） | E2 的自定义元素壳，把 React 打进单文件 | — | H3 · H4（`<script>` 引） |
| `flow-console` | 独立站外壳 + 最小登录桥 | flow-ui | 独立部署 |

`flow-client` 单独切出来，是因为 c-app / b-app 是 uni-app，用不了 React 组件但要同一套类型 —— 类型只有一份，两端才不会分叉。

## 五、Provider 契约：宿主要注入什么（E1 传 props，E2 传 property）

```ts
interface FlowContext {
  actor: { actorType; actorNo; actorName; permissions: string[]; roles: string[]; queues: string[] };
  scope: ScopeCondition;                 // 宿主把自己的数据范围翻成锚点条件
  api:   { baseUrl; prefix; fetch };     // fetch 由宿主提供 → 令牌不出宿主存储
  nav:   { push(href): void; back(): void };
  i18n:  { locale: "zh" | "en" | "ar"; t?(key, args?): string };
  timeZone: string;                      // 业务时区，显示用
  theme?: { vars?: Record<string, string> };
  features?: { flowConfig?: boolean; accessAdmin?: boolean };
}
```

ops-web 侧适配层约 30 行，集中在 `lib/flow/provider.tsx`。

## 六、请求与鉴权（**更正 15 §2.3**）

15 §2.3 写「请求经宿主的后端代理 `/api/flow-proxy`，浏览器里不出现平台凭证」。**ops-web 做不到**：

| 实测 | 出处 |
|---|---|
| `output: "export"` 静态导出，无 Node 运行时 | `ops-web/next.config.ts` |
| 全仓 **0 个** `app/**/route.ts` | 查证 |
| 浏览器直接带 `Authorization: Bearer <宿主令牌>` 调后端，同源经 nginx 反代 | `lib/api/http-client.ts:51,58` |

改为 **nginx 反代 + 宿主令牌**：浏览器带宿主自己的令牌调同源 `/api/flow/**` → nginx 反代到 flow 服务 → 服务校验令牌，**自行解析** `system_code` 与操作人，不信任请求体里的自称值。前端因此同样拿不到平台凭证，还少一跳。

> ⚠️ **由此新增的服务端要求**：flow 服务要能校验各宿主的令牌。做法是每个接入系统登记自己的校验方式（JWKS 或内省端点），服务按路由前缀 / `Host` 选用。要补进 [10](./10-微服务设计.md) §五 认证小节与 [16](./16-任务清单.md) 的 S1-9。

判权仍是两端：页面按钮看 `actor.permissions`，真正的闸在服务端（资格 + 数据范围）。

## 七、路由与菜单

| 项 | 做法 |
|---|---|
| E1 路由 | 宿主给一个路由，`FlowRoutes` 自行分发。**首版用固定路由 + 查询参数**（`/flow?view=todo&no=WO…`）——`output: "export"` 下 catch-all 要 `generateStaticParams` 枚举，枚举不全就漏页 |
| E2 路由 | `view` / `no` 走 attribute；内部跳转 `dispatchEvent` 出来由宿主决定 |
| 跳转 | 一律经 `FlowProvider.nav`，包内不直接用 `next/navigation` |
| 菜单 | **菜单是宿主的**，包不提供。ops-web 按既有流程：`nav.ts` 加叶子（放组**末尾**）→ 菜单迁移 SQL → 三语 → 快照与 `nav-seed` 卡口 |

## 八、mock 与本地开发

| 项 | 做法 |
|---|---|
| 包内 mock | `flow-client` 导出 `createMockClient()`，**状态机在 mock 层强制**（非法迁移抛错，与 ops-web 既有 mock 纪律一致） |
| ops-web 预览 | `/dev/flow` 用 mock 渲染，不进菜单、不挂 https 契约 → **零卡口影响**（16 的 F7） |
| 切真接口 | 只换 `api.fetch`，页面代码不动 |
| 契约一致 | mock 与真实客户端由同一份 `openapi.yaml` 生成；CI 校验两者签名一致 |

## 九、版本与发布

| 项 | 做法 |
|---|---|
| 版本线 | 与 flow 服务 API 版本对齐：`1.x` ↔ `/api/flow/v1`；补丁号独立 |
| E1 发布 | 私仓 `nexus.neargo.ai`（与后端构件同处） |
| E2 发布 | URL 带主版本 `/flow-embed/v1/flow.js`；**主版本内只加不改**，宿主不动就吃到补丁；破坏性变更起 `v2` 并行至少一个季度 |
| 版本校验 | `FlowProvider` 启动时比对「客户端 ↔ 服务 API 版本」，不匹配在控制台告警而非静默 |
