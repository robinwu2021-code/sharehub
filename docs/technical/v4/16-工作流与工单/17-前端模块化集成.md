# 17 · 前端怎么模块化集成

> 所属：[16 工作流与工单](./README.md) · 状态：**待确认**（2026-09-27）· 依据：[15 前端方案](./15-前端方案-独立可嵌入与皮肤.md)
> 15 只给了结论（npm 包、非 iframe）。本篇讲**具体怎么做**：包怎么切、样式怎么过 Tailwind 4、请求怎么带令牌、路由与菜单怎么挂、mock 怎么共用、版本怎么管。
> 下面每条「现状」都是 2026-09-27 从 ops-web 源码核出来的。

---

## 〇、先更正 15 的一处错误

15 §2.3 写「请求经宿主的后端代理 `/api/flow-proxy`，浏览器里不出现平台凭证」。**在 ops-web 上做不到**：

| 核出来的事实 | 出处 |
|---|---|
| ops-web 是**静态导出**（`output: "export"`），没有 Node 运行时 | `next.config.ts` |
| 全仓**没有一个** `app/**/route.ts`，不存在可用的 API 路由层 | 查证为 0 |
| 浏览器直接带 `Authorization: Bearer <宿主令牌>` 调后端，同源经 nginx 反代 | `lib/api/http-client.ts:51,58` |

所以正确做法是 **nginx 反代 + 宿主令牌**（§四）：平台服务信任宿主令牌、自己解析出操作人与系统，而不是让前端去拿平台凭证。这比原方案还少一跳，但要求平台服务接受宿主的令牌格式 —— 这是新增的服务端要求，记在 §四 与 §八。

## 一、包怎么切（四个包，各自独立发布）

| 包 | 内容 | 依赖 | 谁装 |
|---|---|---|---|
| `@neargo/flow-client` | 契约客户端 + 类型（由 `openapi.yaml` 生成）。**零 UI、零框架** | 无 | 任何前端，含 c-app |
| `@neargo/flow-ui` | 九个页面 + 平台专有组件 + `FlowProvider` | React · `flow-client` · `flow-tokens` | 宿主运营台 |
| `@neargo/flow-tokens` | CSS 变量契约：平台用到的语义槽位（**不含具体色值**） | 无 | 宿主（或由 `flow-ui` 带入） |
| `flow-console` | 独立站外壳（路由 + 最小登录桥） | `flow-ui` | 独立部署 |

**为什么把 `flow-client` 单独切出来**：c-app（uni-app）将来可能要展示「我的工单进度」，它用不了 React 组件，但要用同一套类型与请求。类型只有一份，两端就不会分叉。

## 二、样式怎么办 —— Tailwind 4 的坑先说

### 2.1 现状与坑

| 事实 | 后果 |
|---|---|
| ops-web 用 Tailwind 4，配置在 CSS（`@import "tailwindcss"`，无 `tailwind.config.*`） | 类名扫描由 Tailwind 自动发现源码 |
| **Tailwind 4 默认不扫 `node_modules`** | 如果 `flow-ui` 用 Tailwind 类名写样式，装进 ops-web 后**类名不会被生成，页面完全没样式** |

这是必须提前决定的分叉点。两条路：

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A · 宿主声明扫描源**（建议） | 宿主在 `globals.css` 加一行 `@source "../node_modules/@neargo/flow-ui/dist";` | 组件直接用 Tailwind 类名写，与 ops-web 现有组件完全同构；代价是宿主多一行声明，且要求宿主也用 Tailwind 4 |
| B · 包内自带编译好的 CSS | `flow-ui` 构建时产出 `dist/style.css`，宿主 `import` | 宿主不限技术栈（ai-shop 若不用 Tailwind 也能装）；代价是样式隔离、难以被宿主主题完全覆盖，且两套 CSS 体积重复 |

**建议 A**，因为你要的「皮肤赋能」恰恰依赖组件跟宿主用同一套 token 与类名。若将来 ai-shop 不是 Tailwind 4，再为它单独产一份 B 形态的构建。

### 2.2 颜色一律走变量，包内不写死

`flow-ui` 只消费 CSS 变量，**不定义色值**：

```css
/* @neargo/flow-tokens —— 契约：平台需要这些槽位，值由宿主给 */
:root {
  --flow-primary: var(--primary);           /* 回落到宿主的主色 */
  --flow-ok: var(--green-solid);
  --flow-warn: var(--amber-solid);
  --flow-bad: var(--red-solid);
  --flow-paused: var(--gray-9);
  --flow-surface: var(--surface);
  --flow-line: var(--gray-6);
}
```

宿主什么都不做就继承 ops-web 的语义色；要单独调时覆盖 `--flow-*` 即可，**不会影响宿主自身**。这也让 ai-shop 能注入自己的色板。

### 2.3 圆角与类型阶

包内只用宿主的五档圆角类与七档类型阶。**两条硬约束**（CLAUDE.md 与设计规范）：

- 不用废弃圆角类，只用 `rounded-control/field/card/sheet/chip`；
- **类型阶不与 `font-*` / `leading-*` 共存**（`.txt-*` 定义在非 layer 区，永远胜出，共存的字重行高是死代码）。

`flow-ui` 的 CI 里跑与 ops-web 同一套 `design-tokens` 检查，防止包里写出违规样式。

## 三、挂载：路由与菜单

### 3.1 路由

`flow-ui` 导出一个受控的路由组件，**不自带 router**：

```tsx
// ops-web: app/flow/[[...slug]]/page.tsx
"use client";
import { FlowRoutes } from "@neargo/flow-ui";

export default function FlowPage() {
  return <FlowRoutes basePath="/flow" />;   // 内部按 slug 决定渲染哪一页
}
```

| 项 | 做法 |
|---|---|
| 路由形态 | 宿主给一个 catch-all 路由，`FlowRoutes` 按 `basePath` 之后的段自行分发 |
| 静态导出兼容 | ops-web 是 `output: "export"`，catch-all 需要 `generateStaticParams` 兜底；**或**改用一个固定路由 + 查询参数（`/flow?view=todo&no=WO…`）。首版按后者更稳，避免导出期枚举不全 |
| 跳转 | 由 `FlowProvider.nav` 注入宿主的 `router.push` / `back`，包内不直接用 `next/navigation` |
| 深链 | `/flow?view=work-order&no=WO26092701`，从告警详情等处跳入 |

### 3.2 菜单

菜单是**宿主的**，包不提供。ops-web 侧按既有流程：`nav.ts` 加叶子（放组**末尾**，避免整表重灌）→ 菜单迁移 SQL → 三语 → 快照与 `nav-seed` 卡口。

## 四、请求：令牌与鉴权（更正后的方案）

```tsx
<FlowProvider
  api={{
    baseUrl: process.env.NEXT_PUBLIC_API_BASE ?? "",   // 同源，nginx 反代 /api/flow → flow-svc
    prefix: "/api/flow",
    fetch: opsWebFetch,        // 复用 ops-web 的 http-client：自动带 Authorization + Accept-Language + Result 拆包
  }}
  …
/>
```

| 层 | 谁做 |
|---|---|
| 带令牌 | 复用宿主的 fetch 封装（ops-web 的 `http-client` 已带 `Authorization` 与语言头），**包内不碰令牌存储** |
| 路由到平台 | nginx：`location /api/flow/ → flow-svc`（同源，无 CORS） |
| 识别是哪个系统 | flow 服务校验宿主令牌 → 解析出 `system_code` 与操作人；**不信任请求体里的自称值** |
| 判权 | 页面按钮看 `FlowProvider.perms`；真正的闸在服务端（资格 + 数据范围） |

> ⚠️ **新增的服务端要求**：flow 服务要能校验各宿主的令牌（ShareHub 的 staff token、ai-shop 的 token…）。做法是每个接入系统登记自己的令牌校验方式（JWKS 或内省端点），服务按 `Host`/路由前缀选用。这一条要补进 [10](./10-微服务设计.md) §五 的认证小节与 [16](./16-任务清单.md) 的 S1-9。

## 五、Provider 契约：宿主要注入什么

```ts
interface FlowContext {
  actor: { actorType; actorNo; actorName; permissions: string[]; roles: string[]; queues: string[] };
  scope: ScopeCondition;                 // 宿主把自己的数据范围翻成锚点条件
  api:   { baseUrl; prefix; fetch };
  nav:   { push(href): void; back(): void };
  i18n:  { locale: "zh" | "en" | "ar"; t?(key, args?): string };  // 缺省用包内文案
  timeZone: string;                      // 业务时区，显示用
  theme?: { vars?: Record<string, string> };                      // 覆盖 --flow-* 槽位
  features?: { flowConfig?: boolean; accessAdmin?: boolean };      // 宿主可关掉某些页
}
```

**包不读宿主的全局状态**（不 import ops-web 的 store / auth）——全部经 Provider 传入。这是包能同时服务两个宿主的前提，也由 `flow-ui` 的架构测试守住：禁止 import 任何宿主路径。

ops-web 侧的适配层约 30 行，集中在一个文件 `lib/flow/provider.tsx`。

## 六、mock 与本地开发

| 项 | 做法 |
|---|---|
| 包内 mock | `@neargo/flow-client` 导出 `createMockClient()`，实现同一套契约、**状态机在 mock 层强制**（非法迁移抛错，与 ops-web 既有 mock 纪律一致） |
| ops-web 预览 | `/dev/flow` 下用 mock client 渲染，不进菜单、不挂 https 契约 → **零卡口影响**（16 的 F7） |
| 切真接口 | Provider 换一个 `api.fetch` 即可，页面代码不动 |
| 契约一致 | mock 与真实客户端由同一份 `openapi.yaml` 生成类型；CI 校验两者方法签名一致 |

## 七、版本与发布

| 项 | 做法 |
|---|---|
| 版本线 | `flow-client` / `flow-ui` 与 **flow 服务 API 版本对齐**：`1.x` 对 `/api/flow/v1`；补丁号独立 |
| 发布 | 私仓 `nexus.neargo.ai`（与后端构件同一处） |
| 兼容 | `v1` 内只加字段不删改；破坏性变更起 `v2` 并行至少一个季度 |
| 宿主升级 | 宿主自行选择版本；`FlowProvider` 启动时校验「客户端版本 ↔ 服务 API 版本」，不匹配在控制台告警而非静默 |
