# 08 · 能不能做成纯脱耦的服务 —— 基于场景的分析

> 所属：[16 工作流与工单](./README.md) · 状态：**分析结论，待确认**（2026-09-27）
> 用户问：「工单和工作流可以作为一个纯粹脱耦的服务、独立的数据库和独立的服务、其他业务系统通过调用 API 集成吗？需要基于场景进行分析。」
> 下面每个场景的「今天怎么耦合」都是 2026-09-27 从 powerbank 与 ai-shop 源码里查出来的，注明了文件；「纯服务下」是把耦合点搬走之后的做法。

---

## 一、结论

**可以，而且建议这么做。** 但「纯脱耦」不是把现有代码搬进一个进程就成立的 —— 今天业务与工单 / 审批之间有 **六类咬合点**（§二），每一类都要有明确的去处。去处定下来之后，服务本身可以做到：**独立库、独立进程、只有 API 和回调、代码里没有任何业务名词、从不读业务库**。

代价是三件事的语义会变（§五），其中最重的一件是「审批通过那一刻在一个事务里生成下游对象」变成「通过之后最终生成」。这需要你确认接受。

---

## 二、六类咬合点（从代码里数出来的）

| 类 | 咬合点 | 例子（文件） |
|:-:|---|---|
| A | **决定那一刻要重查业务数据** | 合同审批通过前再查一次「有没有别的合同已获批、时间段重叠」（`ContractServiceImpl:352`，注释：「提交之后可能已有别的合同获批」）；提现审批通过前再查「代理是否已停用」（`WithdrawalServiceImpl:146`） |
| B | **决定的结果要在同一事务里触发业务重动作** | 代理入驻审核通过 → 同一事务里造出主体 + 账号 + 属主关系（`ApplyServiceImpl:activate`，注释：「中途失败会留下有主体没账号的半成品，所以整块必须在事务里」）；ai-shop 售后商家同意 → 立即退款 `doRefund`（`AfterSaleServiceImpl:395`） |
| C | **派单要读业务目录** | 运维工单候选人 = 站点归属的代理（且启用）+ 站点运维员工（`WoOpsServiceImpl:candidates`）；整个工单服务注入了 7 个业务端口：设备、站点、代理、员工、文件、通知、参数 |
| D | **别的业务域直接连查工单表** | 代理清退门禁：`COUNT(*) FROM wo_order WHERE assignee = 代理 AND status IN (未结)`（`AgentExitServiceImpl:116`）；代理月度考核：按工单完成数、SLA 达标数、被接管数算分（`AgentOpsAssessmentServiceImpl:48-57`，含 `JOIN wo_sla`） |
| E | **展示需要业务上下文** | 工单列表要显示点位名、设备在线状态；售后要显示商品与金额 |
| F | **横切能力** | 数据范围（代理只看自己的）、权限码、附件、通知、用户身份 |

## 三、逐场景分析

「判定」列：✅ 纯服务下**无损**；⚠️ 可做但**语义有变**（见 §五）；❌ 纯服务做不到（本次没有）。

### 3.1 审批类

| 场景 | 今天怎么耦合 | 纯服务下谁做什么 | 一致性 | 判定 |
|---|---|---|---|:-:|
| **S1 进场合同审批**（运营审批 → 条件财务会签） | 业务 service 里：提交时算「是否需会签」；**通过那一刻重查时间段重叠**；通过后合同置「已签」；驳回后重提会覆盖上一轮审批人 | ① 提交：业务算好 `needsCosign` 与锚点，调服务 `submit`。② **决定入口在业务**：审批人点「通过」→ 业务接口先重查重叠 → 再调服务 `decide`；重叠则业务直接拒绝，服务里什么都没发生。③ 服务回调「通过」→ 业务置「已签」（幂等）。④ 轮次由服务保存，业务不再覆盖 | 决定与置「已签」跨两个事务，中间合同处于「审批中」。回调丢失由对账补 | ✅ 决定时重查的问题**用「决定入口在业务」解掉**；比今天多的只是「审批中」这个中间态，而合同本来就有 `PENDING` |
| **S2 代理入驻审核**（通过即激活） | 通过那一刻**同一事务**造出主体 + 账号 + 属主关系；失败整体回滚 | 服务回调「通过」→ 业务在自己的事务里做 `activate`（幂等键 = 申请号 + 轮次）；失败重试；重试仍失败告警 | **「通过即激活」变成「通过后最终激活」**。会出现短暂的「审批已通过、账号还没建」，且需要一个可重试的激活任务 | ⚠️ 语义变化最大的一个场景。补救：申请单增加「激活中」状态，激活失败在运营台可见可重试 |
| **S3 提现审批 → 打款** | 通过前查代理未停用；通过后进入出款（支付服务，本来就是异步） | 同 S1：决定入口在业务，先查停用再调服务；通过回调 → 业务发起打款 | 打款本来就是最终一致 | ✅ |
| **S4 ai-shop 售后**（商家同意 → 退款 / 待寄回） | 同一 service：置状态 → 立即 `doRefund`（退款走支付，异步） | 商家同意 → 业务接口先校验（子单状态、金额）→ 调服务对售后工单发「同意」事件；回调 → 业务 `doRefund`（幂等） | 退款本就异步；多一跳回调 | ✅ |
| **S5 ai-shop 商品审核**（队列 · 通过可上架 · 免审分支） | `audit_status` 列 + 审核队列；有「免审」直接置通过的分支 | 需审的：业务提交到服务队列，审核员领取 / 决定，回调置 `audit_status`。免审的：业务直接置通过，**不经服务** | 通过与可上架跨两个事务；上架本就是另一个动作 | ✅ 免审分支说明：不是所有状态变化都要经服务，服务只管「要有人审」的那部分 |
| **S6 ichain / tradeagent 审核队列**（领取 · 决定 · 证据） | 自己的 `AuditTask` 表 | 整体映射到服务的队列模式；证据作附件引用 | 无变化（今天也是独立表） | ✅ |

### 3.2 工单类

| 场景 | 今天怎么耦合 | 纯服务下谁做什么 | 一致性 | 判定 |
|---|---|---|---|:-:|
| **S7 运维工单派单**（候选人来自站点归属） | 工单 service 注入站点、代理、员工三个端口算候选 | **候选人在业务算**：业务的「派单」接口先算候选（读自己的站点、代理、员工），选定后调服务 `assign(工单, 受理方 + 名称快照)`。自动派单规则同理：业务订阅服务的「已开单」事件 → 算受理方 → 调 `assign` | 开单与自动派单跨两步；中间工单短暂无受理方 | ✅ 与 00 的原则一致：判断在业务侧，服务只记录 |
| **S8 告警去重开单 · 自愈撤单** | 告警引擎直接调工单 service：`openOrAttach(去重键)`；告警恢复且未接单 → `withdraw` | 告警引擎调服务 API：`openOrAttach` / `fire(WITHDRAW)`；去重键由业务拼（告警码 + 设备） | 无变化 —— 这两个动作今天也是单向调用 | ✅ |
| **S9 客服报障 → 转退款 / 转工单** | 报障 service 幂等地建退款单、建运维工单 | 报障本身是服务里的一类工单；「转退款」是业务动作（业务读报障详情 → 建退款单 → 在报障工单上记一条时间线）；「转运维工单」= 服务内开第二张单并关联 | 无变化 | ✅ |
| **S10 受理方不可用改派**（代理停用） | 业务事件 → 工单 service `reassignFromAgent` | 业务在停用代理时调服务 `reassignFrom(受理方)`；服务回池或按业务给的新受理方改派 | 无变化 | ✅ |
| **S11 巡检计划定时开单** | 业务定时任务按计划建工单 | 不变：业务定时任务调服务开单 | 无变化 | ✅ |
| **S12 工单完工回写设备** | 工单 service 里直接改设备状态（或发事件） | 服务回调「完工」→ 业务回写设备（幂等键 = 工单号 + 序号） | 跨两个事务 | ✅ |

### 3.3 跨域读取类（最容易被忽略的一类）

| 场景 | 今天怎么耦合 | 纯服务下谁做什么 | 判定 |
|---|---|---|:-:|
| **S13 代理清退门禁**：「名下没有未结工单才能清退」 | 业务 SQL 直接 `COUNT(*) FROM wo_order` | 服务提供 **`countOpen(受理方)`** 查询接口；业务在清退检查时调用 | ✅ 前提是接口存在（§六） |
| **S14 代理月度考核**：按完成数、SLA 达标数、被接管数算分 | 业务 SQL 直接查 `wo_order JOIN wo_sla` | 服务提供 **按受理方 + 时间段的统计接口**（完成数、达标数、被接管数）；业务月结时调用 | ✅ 同上；统计口径由服务定义一次，两个产品共用 |
| **S15 运营台列表要显示点位名、设备状态** | 工单表冗余 `location_name`；设备状态实时查 | 开单时把展示用的名称作**快照**放进 `ext`（本仓库既有约定：「写入时快照，不回溯」）；实时状态由业务页面另查设备接口后拼装 | ✅ |
| **S16 报表 / BI 跨库关联**（工单 × 订单 × 设备） | 同一个库里 JOIN | 独立库后**不能 JOIN**。两条路：服务提供统计接口；或两边都同步到数据仓库 | ⚠️ 需要数仓或接口，不能靠库 |

### 3.4 横切类

| 场景 | 纯服务下怎么做 | 判定 |
|---|---|:-:|
| **S17 数据范围**（代理只看自己的工单） | 业务把当前用户的数据范围翻成锚点条件随请求传给服务；服务只按锚点列过滤，不解释锚点含义 | ✅ 00 已设计 |
| **S18 权限**（谁能决定、谁能派单） | 人的每个动作都经业务接口（S1 的「决定入口在业务」），业务用自己的权限码拦；服务只校验「这个操作人是不是任务的合法办理人」 | ✅ |
| **S19 用户身份 / 待办中心 UI** | 服务**不做登录**，没有用户表；待办页面放在各业务的运营台里调服务 API。如果将来要一个跨系统的待办门户，那是一个新的前端 + 单点登录，不属于本服务 | ✅ 前提是首版不做自己的 UI |
| **S20 附件** | 服务只存媒体引用；文件在媒体组件 | ✅ |
| **S21 通知（催办、超时预警）** | 服务发 webhook 事件；业务或通知组件订阅后发送 | ✅ |
| **S22 非 Java 业务**（soukmind 等 Python） | 只能走 HTTP + webhook；所以接口以 HTTP 规格为准，Java 客户端是其上一层封装 | ✅ 这是「纯服务」相对「代码集成」的独有收益 |

## 四、让「纯脱耦」成立的五条规则

| # | 规则 | 解掉哪类咬合 |
|:-:|---|---|
| R1 | **人的所有动作都经业务系统的接口进入**，业务先做自己的校验，再调服务；服务不对外提供给人直接操作的接口（只给系统调） | A（决定时重查） |
| R2 | **服务从不同步回调业务、从不读业务库**；业务数据只以「引用 + 属性 + 快照」进服务 | C、E |
| R3 | **结果只经 webhook 回推，业务处理必须幂等**；服务侧发件箱 + 重试，业务侧对账 | B |
| R4 | **派单、候选、自动分配的判断在业务侧**；服务只记录「派给了谁」 | C |
| R5 | **业务需要工单 / 审批的数据时只调服务的查询与统计接口**，不连表 | D、S16 |

R1 值得单独强调：它是唯一能把「决定那一刻重查业务数据」解掉、而**不**让服务回调业务的办法。代价是服务不能自带一个让人直接点「通过」的界面 —— 首版本来也不做。

## 五、语义上会变的三件事（需要确认接受）

| # | 今天 | 纯服务后 | 影响到 |
|:-:|---|---|---|
| 1 | 审批通过**那一刻**在一个事务里生成下游对象 | 通过**之后最终**生成；中间有「激活中」状态；失败可重试、可见 | 代理入驻（S2）；将来任何「通过即生效」的流程 |
| 2 | 业务表上直接有审批人、意见、环节列，同库可查 | 审批全过程在服务里；业务表只留「审批中 / 已通过」这种粗状态；细节调服务 | 合同、提现、入驻的列表与详情页要改成调服务 |
| 3 | 报表在一个库里 JOIN 工单与业务表 | 要么调服务的统计接口，要么两边同步到数仓 | 代理考核（S14）、任何含工单维度的报表 |

第 1 件是真正的取舍。如果不能接受「通过后最终激活」，S2 这一类流程就只能留在业务里自己写审批，不进服务 —— 这不影响其余场景进服务。

## 六、服务必须提供、否则业务会被逼回去连表的接口

| 接口 | 谁需要 | 场景 |
|---|---|---|
| `countOpen(受理方)` · `listOpen(受理方)` | powerbank 代理清退 | S13 |
| `stats(受理方, 时间段)` → 完成数 · SLA 达标数 · 被接管数 · 平均时长 | powerbank 代理考核；ai-shop 商家考核 | S14 |
| `summary(锚点条件)` → 待办数 · 超时数 · 达标率 | 各运营台看板 | —— |
| `history(业务对象)` → 审批与工单全过程 | 合同 / 提现 / 入驻详情页 | 变化 2 |
| `export(条件)` 或数仓同步 | BI | S16 |
| webhook：审批结果 · 工单迁移 · SLA 超时 · 任务创建 | 全部 | R3 |
