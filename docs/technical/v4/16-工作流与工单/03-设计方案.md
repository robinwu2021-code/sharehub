# 03 · 设计方案

## 一、两个模块

照 ai-shop 任务模块（`job-api · job-store · job-core · job-worker`）与支付模块（`pay-channel · pay-domain · pay-svc`）：**一个模块 = 一个 Maven 聚合 + 四个子模块**，同一套 core 既能嵌进业务进程（形态 A），也能单独部署（形态 B）。

| 模块 | 管什么 | 子模块 |
|---|---|---|
| **工作流** `workflow/` | 状态机 · 审批 · 统一流转日志 | `workflow-api` · `workflow-store` · `workflow-core` · `workflow-svc` |
| **工单** `workorder/` | 工单内核 · 受理方与派单 · 抢单池 · 升级 · SLA · 撤单 / 合并 / 去重开单 · 复核 · 时间线 | `workorder-api` · `workorder-store` · `workorder-core` · `workorder-svc` |

### 1.1 子模块职责

| 子模块 | 对照 ai-shop | 内容 | 依赖 | 产物 |
|---|---|---|---|---|
| `workflow-api` | `job-api`（零依赖契约） | 类型化状态机门面 · 状态图（数据）· 审批定义与 DTO · `WorkflowClient` · 产品侧接口（`ApprovalOutcomeHandler` · `ActorContextProvider` · `ScopeConditionProvider`）· 事件 · 错误键 | **无**（不引 Spring） | 库 |
| `workflow-store` | `job-store`（`JdbcClient` 手写 SQL） | 仓储实现 · 两套 DDL（MySQL / PostgreSQL，另 H2 供测试） | api · Spring JDBC · Flyway | 库 |
| `workflow-core` | `job-core`（两个宿主共用） | 引擎（迁移执行、审批推进、领取超时）· 定义注册表 · **本地客户端**（形态 A）· **远程客户端**（形态 B）· 回调交付 · 发件箱 · 可选控制器（默认关）· 自动装配 · 契约测试（test-jar） | api · store · `svc-client` | 库 |
| `workflow-svc` | `job-worker` / `pay-svc` | 独立进程：只暴露 `/internal`（业务调用）与向业务回调；不接前端流量；不含业务代码 | core | 可执行 |
| `workorder-api` | 同上 | 工单 DTO · 类型定义 · `WorkOrderClient` · `WorkOrderTransitionHandler` · `ScopeAnchorResolver` · 事件 · 错误键 | `workflow-api`（**只为状态机**） | 库 |
| `workorder-store` | 同上 | 仓储实现 · 两套 DDL | workorder-api | 库 |
| `workorder-core` | 同上 | 工单引擎（派单、抢单、升级、合并、SLA 计时与扫描、时间线）· 类型注册表 · 本地 / 远程客户端 · 回调交付 · 发件箱 · 可选控制器 · 自动装配 · 契约测试 | workorder-api · workorder-store · `svc-client` | 库 |
| `workorder-svc` | 同上 | 独立进程 | workorder-core | 可执行 |

**接入方只面对两个坐标**：只要状态机依赖 `workflow-api`；要审批依赖 `workflow-core`；要工单依赖 `workorder-core`。`*-store` 由 core 带入，产品不直接依赖；`*-svc` 只在要独立部署时构建。

### 1.2 两个模块的关系

| 关系 | 说明 |
|---|---|
| 工单 → 工作流 | 只依赖 `workflow-api`（状态机门面与状态图是纯数据契约）；不依赖审批引擎、不依赖工作流的表 |
| 工作流 → 工单 | 无 |
| 单独部署 | 两个都能；工单服务不需要工作流服务在线 |
| 工单里要审批 | 产品编排：工单进入某状态 → `WorkOrderTransitionHandler` 里调 `WorkflowClient.submit` → `ApprovalOutcomeHandler` 里再对工单发事件。两个模块互不知道对方 |
| 流转日志 | 工单的状态变化记在**工单自己的时间线**，不写工作流的流转日志 —— 否则工单服务就得依赖工作流服务 |

### 1.3 托管与命名

| 项 | 做法 | 依据 |
|---|---|---|
| 托管 | **暂由 powerbank 托管**：`backend/workflow/`、`backend/workorder/` 两个聚合模块，与 `sharehub-*` 平级 | 同「支付与任务暂由 ai-shop 托管」（ADR-024 / 025）；框架线冻结中 |
| groupId | `ai.neargo.workflow` · `ai.neargo.workorder` | 中性，不带 `sharehub` |
| 包名 | `ai.neargo.workflow.*` · `ai.neargo.workorder.*` | 同上 |
| 表前缀 | `nwf_`（工作流）· `nwo_`（工单），可配、不可为空 | powerbank 已有 `wo_order`，迁移期两套并存，前缀必须不撞；`case` / `order` 在 MySQL 与 PostgreSQL 都是保留字，不能无前缀 |
| 发布 | 随托管仓库发布到 Nexus；未就绪前按 07 §二 的副本 + 校验和办法共用 | v4/10 |
| 将来 | 独立仓库，或解冻后并入 `neargo-framework` 能力组件 | v4/11 |

## 二、依赖方向

| 从 | 可以依赖 | 不可以依赖 |
|---|---|---|
| `*-api` | JDK；`workorder-api` 另可依赖 `workflow-api` | Spring、ORM、任何产品构件 |
| `*-store` | 本模块 api · Spring JDBC · Flyway | MyBatis-Plus、jOOQ、任何产品构件 |
| `*-core` | 本模块 api / store · Spring Boot · `svc-client` | 任何产品构件 |
| `*-svc` | 本模块 core | 任何产品构件 |
| 产品 | `workflow-api` · `workflow-core` · `workorder-core` | `*-store`、`*-svc` |

由模块自带的架构测试守住：不得依赖 `ai.neargo.shop..*`、`ai.neargo.sharehub..*`、`top.ichain..*`；`*-api` 不得依赖 `org.springframework..*`。

> `svc-client` 现为 ai-shop 的传输零件（`@HttpExchange` + `RestClient`、令牌头、五种失败分类），已零业务依赖；v4/11 规划它下沉为 `neargo-web` 的内部调用。下沉之前两个 core 各带一份最小实现。

## 三、两种形态

| | **形态 A · 嵌入**（缺省） | **形态 B · 独立服务** |
|---|---|---|
| 引擎在哪 | 业务进程内 | `*-svc` 进程 |
| 表在哪 | 业务库，`nwf_*` / `nwo_*` | 服务自己的库 `neargo_workflow` / `neargo_workorder` |
| 客户端实现 | 本地：直接调引擎 | 远程：`/internal/*`，服务凭证 |
| 定义怎么到引擎 | 启动时注册到进程内注册表 | 启动时推送到服务（带版本号，幂等；版本不变不重推） |
| 结果回调 | 引擎在**同一事务**内同步调 `…Handler` | 服务提交后写回调发件箱，HTTP 回调业务的 `/callback`；业务幂等处理 |
| 一致性 | 强一致 | 最终一致：请求发件箱 + 服务端幂等 + 回调重试 + 对账（§五） |
| 多产品共用 | —— | 所有表带 `system_code`，按系统隔离（同支付 / 任务的 `system` 维度） |
| 切换 | —— | `neargo.workflow.mode: remote`（工单同理）；**业务代码不改**（§四） |
| 何时切 | 默认 | 出现信号再切：多个产品要共看同一批审批 / 工单；工单量或 SLA 扫描拖累业务进程；要给外部系统开放工单 |

## 四、让「只改配置就能切」成立

| # | 规则 | 为什么 | 谁守 |
|:-:|---|---|---|
| R1 | 产品只调 `WorkflowClient` / `WorkOrderClient`，不直接用引擎类 | 两种形态是同一接口的两个实现 | 架构测试：产品代码不得引用 `ai.neargo.*.core.engine..*` |
| R2 | 所有产品相关的判断在产品侧做完，只把**数据**交给引擎（02 §一） | 形态 B 的服务里没有产品代码，lambda 传不过去 | 定义类型本身就不接受 lambda（除产品侧守卫） |
| R3 | 结果回调**从第一天起就幂等**：以 `(subjectType, subjectNo, round)` 或 `(orderNo, eventSeq)` 为键 | 形态 B 下回调可能重复交付；形态 A 下写成幂等没有代价 | core 的契约测试：同一回调交付两次，业务状态只变一次 |
| R4 | 结果回调只推进业务自己的状态，**不回头调引擎** | 形态 A 下会重入引擎事务；形态 B 下形成跨进程环 | 契约测试：回调中调用客户端即失败 |

## 五、一致性

### 5.1 形态 A

| 时机 | 做什么 | 在业务事务里 |
|---|---|:-:|
| 调用前（产品侧） | 守卫、组装操作人上下文、算属性与锚点 | ✓ |
| 迁移 | 条件更新（`WHERE status = 原状态`）；0 行 → 冲突 | ✓ |
| 迁移后 | 写流转日志 / 时间线；算 SLA；同步任务 | ✓ |
| 结果回调 | `ApprovalOutcomeHandler` / `WorkOrderTransitionHandler` 推进业务状态 | ✓ |
| 提交后 | 发事件：只做通知、统计、跨域联动 | ✗ |

### 5.2 形态 B

| 步 | 业务侧 | 服务侧 |
|:-:|---|---|
| 1 | 业务状态先改为「审批中 / 已开单」，同事务写请求发件箱（带幂等号） | —— |
| 2 | 投递 `/internal/*`；失败退避重试 | 按 `(system_code, 幂等号)` 去重；重复请求返回上次结果 |
| 3 | —— | 引擎推进；同事务写回调发件箱 |
| 4 | `/callback` 收到后按 R3 幂等处理 | 回调失败退避重试 |
| 5 | 对账：本地「审批中」超过阈值的，查 `/internal/*/{no}`，按结果补推 | 提供查询 |

请求发件箱、回调发件箱、幂等去重用 v4/11 规划的 `neargo-store`（接口幂等 · 事件去重 · Outbox）；它就绪前两个 core 各带最小实现。

## 六、定义是数据

| 定义 | 产品怎么写 | 引擎收到的是 |
|---|---|---|
| 状态机 | `StateMachine.builder(S.class, E.class)…` 类型化门面 | `Graph`：状态名 · 事件名 · 边 · 角色（字符串） |
| 审批流程 | `ApprovalFlow.code(…).step(…).when(attr("needsCosign").isTrue()).approvers(byPermission(…))` | `FlowDef`：步骤 · 条件（属性 = 值 / 属性为真）· 审批人规则（种类 + 引用）· 模式 |
| 工单类型 | `WorkOrderType.code(…).graph(…).roles(…).slaGroup(…)` | `WorkOrderTypeDef` |
| SLA 规则 | 运营后台维护 | `nwo_sla_rule` 行 |
| 工作日历 | 运营后台维护 | `nwo_calendar` 行（时区 · 每周时段 · 节假日） |

| 规则 | 说明 |
|---|---|
| 条件只支持「属性 = 值」「属性为真」「属性 ∈ 集合」 | 复杂条件由产品在提交前算成一个布尔属性（合同的「是否需要会签」即此） |
| 审批人不接受函数 | 「对象负责人」由产品在提交时放进属性，规则写 `fromAttr("ownerNos")` |
| 守卫只在产品侧 | 门面在调用客户端之前执行；引擎只校验「图上有没有这条边」 |
| 每个定义带版本号 | 定义内容的哈希；形态 B 下版本不变不重推；进行中的审批按提交时的版本走完 |

## 七、多项目适配

| 差异（01 §2.1 实测） | 适配 | 缺省 |
|---|---|---|
| 租户列 `tenant_id` / `tenant_no` / 无 | 表内租户列名取建表占位，可配；取值来自操作人上下文 | 不启用 |
| 多产品共用服务 | 表带 `system_code` | 形态 A：配置常量 |
| 数据范围 | 工单与审批表各三个通用锚点列 `scope_anchor_1..3`；产品登记各代表什么；`ScopeConditionProvider` 产出条件 | 未提供条件则不过滤；**提供了即 fail-closed** |
| 响应信封（四种） | 模块只返回平铺 DTO；可选控制器默认关 | 不装 |
| 数据库方言 | Flyway `{vendor}` 自动选 MySQL / PostgreSQL / H2 脚本 | 按数据源 |
| 迁移版本号 | 每个模块独立 Flyway 实例与历史表 | 开 |
| 业务号 | 产品可提供 `BizNoGenerator` | 前缀 + 雪花 |
| 时间 | `BIGINT` 毫秒（UTC）；营业时间按日历时区 | —— |

## 八、关键决定

| # | 决定 | 放弃 | 为什么 |
|:-:|---|---|---|
| D1 | 事件驱动、状态与事件双枚举（产品侧）；引擎以字符串图运行 | 纯图（ai-shop / ai-erp 现行）；引擎直接持有枚举 | 事件模型能投影出纯图，反过来补不回；形态 B 的服务里没有产品枚举 |
| D2 | 工单引擎按角色触发行为 | 统一状态名 | 各项目状态名不可能也不该统一 |
| D3 | **两个模块、各四个子模块** | 七个细粒度构件（上一版） | 接入方只面对两个模块；与支付、任务同构，团队已在运维 |
| D4 | 同一套 core、两种形态，默认嵌入 | 只嵌入 / 只服务 | 嵌入拿强一致与零运维；服务化是出现信号后的选项 |
| D5 | 产品侧判断、引擎只收数据 | 引擎回调产品做判断 | 否则形态 B 每次判断都要跨进程回调，延迟与失败面都翻倍 |
| D6 | 工单只依赖 `workflow-api`；工单状态记在自己的时间线 | 工单依赖工作流引擎与流转日志 | 两个模块能各自单独部署 |
| D7 | 持久化 `JdbcClient` 手写 SQL | MyBatis-Plus 实体 | ai-erp 是 jOOQ；`job-store` 已是同样做法 |
| D8 | 每个模块独立 Flyway 历史表 | 并入项目迁移目录 | 各项目 V 号各自增长，共用必撞号；形态 B 下本来就是独立库 |
| D9 | 数据范围用通用锚点列 | 各项目加列 / 扩展表 JOIN | fail-closed；形态 B 下服务只能认通用列 |
| D10 | 流程代码定义，SLA 与日历入库 | 全部入库 | 流程变更要研发评审；SLA 与日历运营要调 |
| D11 | 不引入 BPMN | Flowable / Camunda | 01 §六 |

## 九、对现有代码的替换关系

| 现有 | 替换为 | 旧的怎么办 |
|---|---|---|
| powerbank 14 个 `*StateMachine` | `workflow-api` 状态机门面 | 逐个换实现；类名可暂留为薄包装 |
| ai-shop `OrderStateMachine` 三张图 · ai-erp `InvoiceFsm` | 同上 + `projection()` 兼容旧调用点 | 调用点逐步改为按事件 |
| 7 张流转日志表 | 非工单的 5 张（`OrdEventLog` · `LocContractLog` · `LocSiteStatusLog` · `LocSiteLifecycleLog` · ai-shop `OrdStatusLog`）→ `nwf_transition_log`；powerbank 工单的 `wo_dispatch` · `wo_handle` → 工单模块的 `nwo_event`（工单不依赖工作流，§1.2） | 双写 → 读侧切换 → 停写；旧表保留只读 |
| powerbank 合同审批、代理入驻、提现 · ai-shop 商品审核 · ichain / tradeagent `AuditTask` | 工作流 · 审批（后两者用队列模式） | 业务状态列保留，由结果回调推进 |
| powerbank `wo_*` + `WorkOrderService` + `WoOpsService` · 客服报障 · 告警开单 · ai-shop 售后 | 工单模块（各为一个工单类型） | `wo_*` 经双写过渡；两套 service 并为一层 |
