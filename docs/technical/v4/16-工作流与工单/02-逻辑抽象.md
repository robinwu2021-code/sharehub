## 一、一条总原则：产品侧判断，引擎只收数据

用户要求工作流与工单都能从「嵌进业务进程」（形态 A）切到「独立服务」（形态 B）。形态 B 的服务进程里**没有任何业务代码**，所以：

| 放在产品侧（客户端库里执行） | 放在引擎侧（形态 A 在本进程，形态 B 在服务里） |
|---|---|
| 类型化的状态 / 事件枚举 | 以字符串为键的**状态图**（由枚举编译而来） |
| 守卫：「提交人不能审自己」之外的业务条件 | 图上的合法性：这条边存不存在、起点对不对 |
| 条件步是否成立（如「要不要财务会签」）→ 算成一个属性 | 按属性决定走哪几步 |
| 当前用户是谁、持有哪些权限 / 角色 / 队列 → 装进 `ActorContext` | 按 `ActorContext` 判定「是不是我的待办」 |
| 当前用户的数据范围 → 翻成 `ScopeCondition` | 按 `ScopeCondition` 过滤 |
| 受理方的名字、是否可用 | 存名字快照；收到「不可用」通知时改派 |
| 结果到了以后推进自己的业务状态（回调） | 算出结果、按形态交付回调 |

**判断在产品侧、事实在引擎侧**。满足这条，形态 A 与形态 B 的差别就只剩「调用是本地还是远程、回调是同步还是异步」，业务代码不用改。

## 二、三层概念

| 层 | 管什么 | 属于哪个模块 |
|---|---|---|
| **流转** | 一个对象的状态按合法路径变化，并留下记录 | 工作流 |
| **审批** | 一个对象需要一个或多个人「同意 / 驳回」之后才能继续 | 工作流 |
| **工单** | 一件事需要派给某个人或组织去处理，有时限、可升级、要留痕 | 工单 |

审批与工单都**建在流转之上**：审批单与审批任务自身的状态、工单的状态，都是一张状态图。

## 三、概念清单

### 3.1 通用

| 概念 | 是什么 | 不是什么 |
|---|---|---|
| **业务对象** Subject | `(subjectType, subjectNo)` —— 一个不透明引用，如 `(LOC_CONTRACT, CT0042)` | 不是业务实体本身；引擎不认识合同、商品、设备 |
| **操作人上下文** ActorContext | `(actorType, actorNo, actorName, permissions, roles, queues)`，由产品侧组装 | 不是登录会话；引擎不做认证 |
| **数据范围条件** ScopeCondition | `{槽位 → 允许的锚点值集合 或 全部}`，由产品侧把当前用户的数据范围翻译而来 | 不是权限码；只管「看得见哪些行」 |
| **定义** Definition | 状态图、审批流程、工单类型、SLA 规则、工作日历 —— **全部是数据**，可序列化 | 不含 lambda；不含业务代码 |
| **结果回调** Handler | 产品实现的接口：结果出来后，推进产品自己的业务状态 | 不是事件监听；形态 A 在同一事务内同步调用 |

### 3.2 流转

| 概念 | 定义 |
|---|---|
| 状态 State | 对象此刻所处的阶段（名词） |
| 事件 Event | 让对象换阶段的动作（动词）。**与状态是两种类型**，不能互相替代 |
| 边 Edge | `(事件, 起, 止)`。同一对「起 → 止」允许多个事件（撤单与合并都 → 关闭，但原因与统计口径不同） |
| 状态图 Graph | 边的集合 + 每个状态的角色。**不可变**；构建时校验 |
| 角色 Role | 状态在引擎眼里的含义：`INITIAL` 初始 · `ACTIVE` 进行中 · `WAITING_EXTERNAL` 等外部 · `AWAITING_VERIFY` 待复核 · `ESCALATED` 已升级 · `TERMINAL` 终态 |
| 守卫 Guard | 边上的附加条件；产品侧执行 |
| 迁移 Transition | 一次状态变化的事实：`(对象, 事件, 起, 止, 操作人, 原因, 附加数据, 时间)` |
| 流转日志 | 全部迁移的流水；只增不改 |

### 3.3 审批

| 概念 | 定义 |
|---|---|
| 流程 Flow | `flowCode` + 有序步骤。是数据 |
| 步骤 Step | `stepCode` · 进入条件（对属性的简单判定，如 `needsCosign = true`）· 审批人规则 · 或签 / 会签 · 是否允许自审 |
| 审批人规则 ApproverRule | 按权限码 · 按角色 · 按属性里给出的人 · 按队列 —— 四选一，都是数据 |
| 审批单 Approval | 某对象的一次送审；带**轮次**；有自己的状态图 |
| 轮次 Round | 驳回或撤回后再提交，轮次加一；**每一轮每一步的决定都保留** |
| 计划 Plan | 提交时按属性求值后，本轮实际要走的步骤序列（条件步已定） |
| 任务 Task | 某轮某步分给某条审批人规则的一件待办；有自己的状态图 |
| 领取 Claim | 队列任务的独占：领了之后只有领取人能决定；超时自动放回 |
| 结果 Outcome | `APPROVED` · `REJECTED` · `WITHDRAWN`，连同对象、流程、轮次交给结果回调 |

### 3.4 工单

| 概念 | 定义 |
|---|---|
| 工单类型 WorkOrderType | 产品登记：状态图 · 编号前缀 · 受理方类型 · 派单方式 · SLA 规则组 · 数据范围锚点的含义 |
| 工单 WorkOrder | 一件要处理的事：通用内核字段 + 扩展（只展示，不参与查询与权限） |
| 来源 Source | 为什么开这张单（告警、巡检、用户申请、手工…）+ 来源编号 |
| 受理方 Assignee | `(assigneeType, assigneeNo, assigneeName 快照)`；类型由产品登记（员工 / 代理 / 商家 / 平台 / 用户） |
| 派单 Dispatch | 指派 · 放入抢单池 · 产品规则算出受理方后指派 |
| 抢单池 Pool | 未指派、谁有资格谁可以抢的单 |
| 升级 Escalation | 换受理方到更高一级（接管、仲裁），并打升级标记 |
| 去重键 DedupeKey | 同一对象同一原因只允许一张未结单；再开则附加到那张 |
| 合并 Merge | 一张单被另一张取代，以「并入」原因关闭 |
| SLA | 按（类型, 优先级）定的响应 / 解决时限；可只算营业时间；等外部时暂停 |
| 工作日历 Calendar | 营业时段、节假日、时区 —— 数据 |
| 时间线 Timeline | 这张单上发生过的一切：迁移、派单、升级、备注、附件、SLA 事件 |

## 四、概念之间的关系

| 关系 | 基数 | 说明 |
|---|---|---|
| 业务对象 — 审批单 | 1 : N | 同一时刻**至多一张**待审（`PENDING`） |
| 审批单 — 轮次 — 任务 | 1 : N : N | 或签一步一张共享任务；会签一步每人一张 |
| 流程 — 步骤 | 1 : N（有序） | 计划 = 步骤按属性筛选后的子序列 |
| 工单类型 — 状态图 | 1 : 1 | 不同类型可以用不同的图（运维工单与售后单） |
| 工单 — 时间线条目 | 1 : N | 只增不改 |
| 工单 — 受理方 | N : 1（当前） | 历次受理方在时间线里 |
| 状态图 — 迁移 | 1 : N | 每次迁移都必须是图上的一条边 |
| 审批 / 工单 — 流转日志 | 1 : N | 审批单、任务、工单的每次状态变化都进同一本流转日志 |

## 五、生命周期

### 5.1 审批单

| 事件 | 起 → 止 |
|---|---|
| `SUBMIT` | （新建）→ `PENDING` |
| `STEP_APPROVED` | `PENDING` → `PENDING`（进下一步） |
| `APPROVE` | `PENDING` → `APPROVED`（最后一步通过） |
| `REJECT` | `PENDING` → `REJECTED` |
| `WITHDRAW` | `PENDING` → `WITHDRAWN` |
| `RESUBMIT` | `REJECTED` / `WITHDRAWN` → `PENDING`（轮次 + 1） |

### 5.2 审批任务

| 事件 | 起 → 止 |
|---|---|
| `CLAIM` | `OPEN` → `CLAIMED`（队列任务） |
| `RELEASE` · 领取超时 | `CLAIMED` → `OPEN` |
| `DECIDE` | `OPEN`（非队列）· `CLAIMED`（队列）→ `DONE` |
| `CANCEL` | `OPEN` / `CLAIMED` → `CANCELLED`（或签已有人决定、撤回、驳回） |

### 5.3 工单

工单**没有**统一的状态图 —— 每个类型用自己的。引擎只按角色做事：

| 角色 | 引擎做什么 |
|---|---|
| 进入 `INITIAL` | 新建落点；若派单方式为抢单池则进池 |
| 首次进入 `ACTIVE` | SLA 起算 |
| 进入 / 离开 `WAITING_EXTERNAL` | SLA 暂停 / 恢复（暂停时长不计） |
| 进入 `AWAITING_VERIFY` | 进入复核；复核不过由产品的图决定退回哪一态 |
| 进入 `ESCALATED` 或调用升级 | 打升级标记、换受理方 |
| 进入 `TERMINAL` | 停表、移出待办、记关闭原因 |

## 六、对外的接口（抽象）

| 接口 | 谁实现 | 谁调用 | 作用 |
|---|---|---|---|
| `WorkflowClient` | 模块（本地 / 远程两种实现） | 产品 | 登记定义 · 执行迁移 · 送审 / 决定 / 撤回 / 重提 / 领取 / 放回 · 查待办 / 详情 / 流转历史 |
| `WorkOrderClient` | 模块（本地 / 远程） | 产品 | 登记类型 · 开单 / 去重开单 · 发事件 · 派单 / 抢单 / 升级 / 合并 / 备注 / 改优先级 · 改派 · 查询 |
| `ApprovalOutcomeHandler` | 产品 | 模块 | 审批结果到达，推进业务状态 |
| `WorkOrderTransitionHandler` | 产品 | 模块 | 工单迁移到达，做业务联动（如完工回写设备状态） |
| `ActorContextProvider` | 产品 | 模块的客户端库 | 组装当前操作人上下文 |
| `ScopeConditionProvider` | 产品 | 模块的客户端库 | 把当前用户的数据范围翻成锚点条件 |
| `ScopeAnchorResolver` | 产品 | 模块的客户端库 | 开单时从对象算出锚点值（快照） |

四个「产品实现」的接口全在产品侧执行；引擎侧只收它们产出的数据。

## 七、不变式

引擎在任何形态下都保证：

| # | 不变式 |
|:-:|---|
| I-1 | 每一次状态变化都是状态图上的一条边，且都有一条流转日志 |
| I-2 | 终态没有出边；终态由图推导，不能手写 |
| I-3 | 同一对象同一时刻至多一张 `PENDING` 审批单 |
| I-4 | 队列任务只能由领取人决定；领取超时自动放回 |
| I-5 | 驳回必须有原因；撤回只能由提交人、只在待审时 |
| I-6 | 历次轮次的决定永不被覆盖 |
| I-7 | 同一去重键至多一张未结工单 |
| I-8 | SLA 暂停期间不计时；进入终态停表 |
| I-9 | 并发下同一次迁移只有一个成功，其余得到可识别的冲突 |
| I-10 | 数据范围 fail-closed：带了范围条件就只返回范围内的行 |
| I-11 | 同一个结果回调可能被交付多次（形态 B），产品处理必须幂等；形态 A 下只交付一次 |
