## 一页结论

| 问题 | 结论 |
|---|---|
| 做成什么 | 三个构件：**状态机**（零依赖）· **审批** · **工单**，外加持久化、可选控制器、starter、TCK |
| 谁用 | powerbank · ai-shop（三档都要）· ichain · tradeagent（审批）· ai-erp · ai-neargo（状态机） |
| 为什么现在做 | 六个项目里五个在手写同样的东西：3 种状态机模型、7 张流转日志表、4 条重复的审批规则、2 份同形的 `AuditTask` |
| 状态机模型 | 事件驱动、状态与事件双枚举；能投影出 ai-shop / ai-erp 现行的「起 → 止集合」，所以旧调用点可以先不动 |
| 一套工单引擎怎么适配各项目 | 引擎按状态**角色**（初始 / 进行中 / 等外部 / 待复核 / 已升级 / 终态）触发行为，不认状态名 |
| 怎么做到快速集成 | 只要状态机：一个依赖一个定义，≤ 30 分钟，不要 Spring、不建表；审批 / 工单：一个 starter，自动建表（独立迁移历史，不占项目 V 号），项目只写定义和几个 SPI |
| 怎么兼容各项目差异 | 持久化用 `JdbcClient`（MyBatis-Plus / jOOQ / JDBC 都能用）；MySQL 与 PostgreSQL 两套 DDL；租户列名可配；不强加响应信封 |
| 形态 | **嵌入式库**，不做共用服务 —— 状态迁移必须与业务写同一事务 |
| 不做 | BPMN 引擎、流程设计器、跨服务 Saga |
| 框架冻结期 | 在 powerbank 写、其他项目逐字复制 + 校验和防漂移；解冻后进 `neargo-framework`，调用方零改动 |
| 需要你拍板 | 05 §五 的 8 项，最关键：**#1 各项目是否排期**、**#2 工单数据范围锚点落法** |

## 与上一版的关系

2026-09-27 上午的单篇《16 工作流与工单组件方案》只覆盖 powerbank 与 ai-shop、只有设计。本目录取代它：扩到六个项目，补齐需求、详细设计、集成指南与落地计划，并修正了两处：

| 修正 | 说明 |
|---|---|
| 业务状态在事务内推进 | 上一版写「审批结束发事件、业务域监听后推进」，与「同一事务」矛盾 —— 会出现「审批已通过、合同还在待审」。现在业务状态走事务内的结果回调，事件只做通知等副作用（02 §五） |
| 构件粒度 | 上一版的「状态机数据适配」单列为 `neargo-workflow-store`，并把 starter、可选控制器、TCK 独立出来，对应「快速集成」的三档 |
