## 一、背景与目标

### 1.1 问题

六个 Java 后端里，**五个**都在各自手写同样的三样东西 —— 状态流转、审批、工单 —— 而且手写出了三种互不兼容的状态机模型、七张流转日志表、四份一模一样的审批规则。

| 症状 | 实测证据 |
|---|---|
| 同一个概念三种写法 | 状态机：powerbank「事件 → (起 → 止)」· ai-shop「起 → 止集合（字符串）」· ai-erp「起 → 止集合（枚举）」 |
| 同一个项目内部已经分叉 | powerbank 14 个状态机：13 个叫 `next`、1 个叫 `check`；「由迁移反查事件」一处叫 `eventFor`、一处叫 `eventOf`；「是否终态」只有 1 个类有 |
| 状态值是散落的字面量 | ai-shop 的 `"AUDITING"` 在 7 个主代码文件里各写一遍，其中 2 个类各自定义了同名常量 |
| 规则重复且各有漏洞 | 「提交人不能审自己 / 驳回必填原因 / 只有提交人能撤回 / 并发只一人赢」在 powerbank 合同审批、ai-shop 商品审核里各写一遍 |
| 历史丢失 | powerbank 合同重提审批时把上一轮审批人与意见**全部清空**，前几轮只剩日志里一句文字 |
| 注释与实现矛盾 | ai-shop 售后状态机注释说 `REJECTED` 是终态，图里它却有 `→ ARBITRATING` 的出边 |
| 新项目从零再写一遍 | ichain 与 tradeagent 各有一个 `AuditTask`（审核任务队列 + 领取），两份代码几乎相同 |

### 1.2 目标

| # | 目标 | 可度量的验收 |
|:-:|---|---|
| G1 | **一套**状态机、审批、工单能力，所有 Java 后端共用 | 六个仓库里不再出现手写的迁移表 |
| G2 | **快速集成**：新项目接入以「分钟 / 小时」计，不以「天」计 | 见 §五 NFR-I1 ~ I4 的目标值 |
| G3 | **不改变任何现有行为**：迁移是换实现，不是改需求 | 每个项目接入时，既有场景测试**一条不改**仍全绿 |
| G4 | 消掉 §1.1 里每一条症状 | 每条症状对应一条卡口或内建规则（§四） |

### 1.3 范围

| 在范围内 | 不在范围内（§六） |
|---|---|
| 状态机（定义、推进、守卫、日志、导出） | BPMN / 图形化流程设计器 |
| 审批（多步、条件步、或签 / 会签、队列领取、轮次） | 表单设计器、低代码 |
| 工单（受理、派单、抢单、SLA、升级、合并、复核、时间线） | 跨服务 Saga / 分布式事务 |
| 与各项目已有的租户、数据权限、权限码、响应信封、迁移工具对接 | 通知发送（交给 `neargo-notify`）、定时调度（交给共用任务服务） |

## 四、功能需求

### 4.1 状态机（SM）

| 编号 | 需求 | 优先级 | 消掉的症状 |
|---|---|:-:|---|
| SM-01 | 状态与事件都是**枚举**，两种类型不可混用 | P0 | 字面量散落；事件与状态混写（powerbank 告警域出过这个缺陷） |
| SM-02 | 定义时声明「事件 × 起 → 止」；同一对「起 → 止」允许多个事件 | P0 | 三种模型不兼容 |
| SM-03 | `next(from, event)`：非法迁移抛带错误键的异常 | P0 | `next` / `check` 分叉 |
| SM-04 | `events(from)`：当前可走的事件 | P0 | 前端各自维护一份迁移表 |
| SM-05 | `eventFor(from, to)`：由迁移反查事件，**不唯一时报错**，不随便挑一个 | P1 | `eventFor` / `eventOf` 分叉 |
| SM-06 | 终态**由图推导**（无出边），不允许手写 | P0 | 注释与实现矛盾（ai-shop `REJECTED`） |
| SM-07 | 守卫：迁移前的条件校验，拒绝时给错误键 | P1 | 「提交人不能审自己」散在 service |
| SM-08 | 定义期校验：不可达状态、重复边、事件无边 → 启动即失败 | P1 | — |
| SM-09 | 导出图（JSON）：状态、事件、边、终态、状态角色 | P0 | 前后端一致卡口靠正则解析源码 |
| SM-10 | 投影为「起 → 止集合」，兼容 ai-shop / ai-erp 现有调用点 | P0 | 接入期不能一次改完所有调用点 |
| SM-11 | 条件更新：`WHERE status = 原状态`，0 行即冲突（409） | P0 | 各处手写「并发只一人赢」 |
| SM-12 | 统一流转日志：谁、何时、事件、起止、原因、附加数据；与业务写同一事务 | P0 | 7 张日志表 |
| SM-13 | 状态可打「角色」标签（初始 / 已受理 / 等外部 / 待复核 / 已升级 / 终态），供工单引擎使用 | P1 | 工单行为绑状态名导致无法共用 |

### 4.2 审批（AP）

| 编号 | 需求 | 优先级 | 出处 |
|---|---|:-:|---|
| AP-01 | 审批对象是不透明引用（类型 + 编号），组件不认识业务 | P0 | 全部 |
| AP-02 | 流程由有序步骤组成；每步可设**进入条件**（不满足则跳过） | P0 | powerbank 合同条件会签 |
| AP-03 | 每步的审批人解析：按权限码 / 角色 / 指定人 / 对象负责人 / **队列** | P0 | powerbank 权限码；ichain 队列 |
| AP-04 | 或签（一人通过即过）与会签（全部通过才过） | P1 | powerbank 财务会签 |
| AP-05 | 队列模式：领取、放回、领取超时自动回收；已领取的只能由领取人决定 | P0 | ichain `CLAIMED` |
| AP-06 | 内建规则：提交人不能审自己（按流程可关）· 驳回必填原因 · 只有提交人能在待审时撤回 · 并发只一人赢 | P0 | powerbank、ai-shop |
| AP-07 | 轮次：驳回后再提交是新一轮，**每轮每步的决定都结构化保留** | P0 | powerbank 合同丢历史 |
| AP-08 | 「待我审批」查询：按审批人解析结果 + 数据范围 | P0 | 全部 |
| AP-09 | 审批结束发事件，业务域据此推进**自己的**状态；组件不写业务表 | P0 | 解耦 |
| AP-10 | 审批附带证据（附件引用、JSON） | P1 | ichain `evidence` |
| AP-11 | 转交：审批人把任务转给他人（留痕） | P2 | — |
| AP-12 | 审批超时提醒 | P2 | — |

### 4.3 工单（CS）

| 编号 | 需求 | 优先级 | 出处 |
|---|---|:-:|---|
| CS-01 | 工单内核字段通用（编号、类型、来源、对象、优先级、状态、受理方、SLA、升级、关闭原因），业务扩展放扩展字段 | P0 | 全部 |
| CS-02 | 每种工单类型可以有**自己的状态机**；引擎行为按状态**角色**触发 | P0 | powerbank `AUDITED` 与 ai-shop `ARBITRATING` 无法同名 |
| CS-03 | 受理方类型由项目登记（员工 / 代理 / 商家 / 平台 / 用户） | P0 | 全部 |
| CS-04 | 派单策略：指派 · 抢单池 · 规则（项目实现） | P0 | powerbank |
| CS-05 | 受理方不可用 → 名下未结单自动改派（由项目发事件触发） | P1 | powerbank 代理停用 |
| CS-06 | 去重开单：同一去重键已有未结单时附加到该单 | P1 | powerbank 告警 |
| CS-07 | 升级 / 接管：换受理方、打升级标记、留痕 | P0 | powerbank 接管；ai-shop 仲裁 |
| CS-08 | 合并 / 撤单，带关闭原因 | P1 | powerbank |
| CS-09 | SLA：按（类型，优先级）配置响应 / 解决时限；工作日历；「等外部」角色自动暂停；超时扫描 | P0 | powerbank；ai-shop 商家处理时限 |
| CS-10 | 复核：完成后进入待复核，不过则返工（不回初始） | P1 | powerbank |
| CS-11 | 时间线：每次迁移、备注、附件统一成一条流水 | P0 | powerbank `wo_dispatch` + `wo_handle` |
| CS-12 | 待办数、超时数、SLA 达标率 | P1 | powerbank 看板；ai-shop 商家待办数 |
| CS-13 | 列表按数据范围过滤（代理只看自己的、商家只看自己的） | P0 | powerbank、ai-shop |

## 五、非功能需求

### 5.1 快速集成（I）

| 编号 | 需求 | 目标值 |
|---|---|---|
| NFR-I1 | 只接状态机：加一个依赖、写一个定义类，**不需要 Spring、不需要建表** | ≤ 30 分钟 |
| NFR-I2 | 接审批：加一个 starter、配 ≤ 5 个属性、写一个流程定义和一个结果监听 | 第一个流程 ≤ 半天 |
| NFR-I3 | 接工单：加一个 starter、登记类型与受理方、实现数据范围锚点 | 第一个类型 ≤ 2 天 |
| NFR-I4 | 建表自动完成，**不占用项目自己的迁移版本号** | 零手工 DDL |
| NFR-I5 | 不强加响应信封、URL 前缀、权限码格式；项目用自己的控制器暴露，或开启可选的通用控制器 | — |

### 5.2 兼容与依赖（D）

| 编号 | 需求 |
|---|---|
| NFR-D1 | Java 21；Spring Boot 4.0.x 与 4.1.x 都要跑通 |
| NFR-D2 | 状态机核心**零依赖**（纯 Java），审批与工单的领域层不依赖任何 ORM |
| NFR-D3 | 持久化用 Spring `JdbcClient`，走项目自己的 `DataSource` 与事务 —— MyBatis-Plus、jOOQ、裸 JDBC 的项目都能用 |
| NFR-D4 | DDL 同时提供 MySQL / MariaDB 与 PostgreSQL 两种方言；H2（MySQL 模式）能跑测试 |
| NFR-D5 | 不依赖任何产品的构件（`ai.neargo.shop:*`、`sharehub-*`、`top.ichain:*`） —— 同 11 §一 |
| NFR-D6 | 表名前缀、租户列名可配置，租户列可以不要 |

### 5.3 正确性（C）

| 编号 | 需求 |
|---|---|
| NFR-C1 | 状态迁移、流转日志、业务行更新在**同一事务**；跨域副作用在提交之后发 |
| NFR-C2 | 并发冲突一律乐观检测，只有一个成功，其余返回可识别的冲突（HTTP 409） |
| NFR-C3 | 所有时间以 **UTC** 存；SLA 的「营业时间」按项目配置的业务时区算（powerbank 已踩过三个时区的坑） |
| NFR-C4 | 数据范围 **fail-closed**：查不到锚点时看不到，而不是全看得到 |
| NFR-C5 | 请求体一律 DTO 白名单，状态、受理方、审计字段不可经请求体改（powerbank 批量赋值加固的同一教训） |

### 5.4 可运维（O）

| 编号 | 需求 |
|---|---|
| NFR-O1 | 指标（Micrometer）：迁移次数与冲突率、待办数、SLA 超时数 |
| NFR-O2 | 日志遵循各项目日志规范：带业务键、不打敏感信息、WARN/ERROR 必须说明谁该做什么 |
| NFR-O3 | 错误键可本地化（zh / en / ar） |

### 5.5 性能（P，目标值）

| 编号 | 场景 | 目标 |
|---|---|---|
| NFR-P1 | 单次迁移（含日志） | 额外开销 < 5 ms |
| NFR-P2 | 待办列表（100 万工单、按受理方 + 状态） | P95 < 100 ms（靠索引，§03） |
| NFR-P3 | SLA 超时扫描 | 每批 ≤ 500 行、可分批续扫，不锁表 |

## 六、不做

| 不做 | 为什么 |
|---|---|
| BPMN 引擎（Flowable / Camunda） | 六个项目的流程都 ≤ 3 步；引擎带 20+ 张运行时表与 XML 建模，没人运维；我们缺的是「统一 + 规则内建」，不是图形化 |
| 流程 / 表单设计器 | 流程由研发定义；运营只调 SLA 与队列 |
| 共用服务形态 | 迁移必须与业务写**同一事务**（NFR-C1），服务化只能最终一致 |
| 跨服务 Saga | 各项目单体优先 |
| 替项目发通知、做调度 | 组件发事件；通知交 `neargo-notify`，定时交共用任务服务 |
