# 19 · 前端模块化：业界方案调研（多系统页面集成）

> 所属：[16 工作流与工单](./README.md)，但内容是**通用的**：任何「把多个系统的前端页面集成到一起」的场景都适用。
> 状态：调研稿（2026-09-27）。用户要求：「不用过分参考目前的方案，要调研业界的通用前端模块化方案，用来集成多系统的前端页面」，包含微前端与统一认证的跳转。
> 写法：前七节只讲业界，**不以 15 / 17 为锚**；§八 才对照本组织的实际情况。活跃度数据取自 GitHub API（2026-09-27），其余出处见文末。

## 〇、一页结论

| 问题 | 业界共识 |
|---|---|
| 有没有「一种方案」 | **没有**。业界按「组合发生在哪一层」分六类，成熟平台通常**组合使用两到三类** |
| 决定选哪类的三个问题 | ① 信任边界（同一组织 vs 第三方）② 技术栈是否统一 ③ 要不要**同屏组合**（一个页面里拼多个系统的块），还是**整页切换**就够 |
| 微前端框架的位置 | 适合「同组织、多技术栈、要同屏或同外壳」；不是默认选项 —— 业界普遍提醒它有复杂度税 |
| 统一认证 | 与前端组合方式**正交**：无论选哪类，底座都是**集中身份提供方（IdP）+ OIDC**；浏览器侧令牌处理以 **RFC 10017（2026-08 发布）** 为准，推荐 BFF |
| 最稳的基线 | **统一 IdP + 门户导航 + 链接跳转** —— 零耦合、任何栈都能接，其余方案都是在它之上加「更紧的组合」 |

## 一、多系统前端集成要解决的八件事

任何方案都要逐条回答，比较方案时也按这八条比：

| # | 关注点 | 问题 |
|:-:|---|---|
| 1 | **组合** | 各系统的界面在哪里、何时拼到一起（构建期 / 服务端 / 浏览器运行时 / 不拼只跳转） |
| 2 | **隔离** | JS 全局变量、CSS、路由、存储会不会互相污染 |
| 3 | **身份与会话** | 用户登录一次，能不能在所有系统里都被认出；登出能不能一起登出 |
| 4 | **权限** | 谁决定某人能不能看某块；权限数据从哪来 |
| 5 | **外壳与导航** | 统一的顶栏、菜单、通知、搜索由谁提供；菜单怎么注册 |
| 6 | **视觉一致** | 各系统看起来是不是同一个产品；主题切换能不能联动 |
| 7 | **通信与路由** | 系统间怎么传事件；深链、刷新、浏览器前进后退是否正常 |
| 8 | **版本与发布** | 能不能各自独立发布；共享依赖（React 等）版本冲突怎么办 |

## 二、方案谱系：按「组合发生的位置」分六类

| 类 | 组合位置 | 代表 | 一句话 |
|:-:|---|---|---|
| **A** | 构建期 | monorepo + 共享包、私有 npm 包 | 编译成一个应用；最紧、最简单，但要同栈、要一起发布 |
| **B** | 服务端 / 边缘 | SSI / ESI、Podium、Tailor、**Next.js Multi-Zones**、反向代理按路径分流 | 服务器把片段或整页拼好再给浏览器；浏览器端零框架 |
| **C** | 浏览器运行时 · 模块级 | **Module Federation 2.0**、import maps + SystemJS、**Web Components** | 运行时加载别的系统的模块或组件，拼进同一个页面 |
| **D** | 浏览器运行时 · 应用级（「微前端框架」） | single-spa、**qiankun**、**micro-app**、**wujie**、Garfish | 主应用在运行时装载整个子应用，负责生命周期与沙箱 |
| **E** | 浏览器运行时 · 框架隔离 | **iframe + 通信桥**：SAP Luigi、Shopify App Bridge、Atlassian Connect、各大云控制台 | 每个子系统在自己的 iframe 里，经 postMessage 桥与外壳对话 |
| **F** | 链接级 | 门户 / 应用启动器 + **SSO 跳转** | 不拼，只跳；靠统一登录做到「无感切换」 |

越往上耦合越紧、体验越一体；越往下隔离越强、接入越容易。

## 三、逐类详评

### A · 构建期组合（monorepo / npm 包）

| 项 | 内容 |
|---|---|
| 机制 | 各系统的模块作为包发布，宿主编译时装进来，最终是一个应用 |
| 优势 | 最简单；类型安全；共享依赖只有一份；无运行时开销；调试体验最好 |
| 代价 | **强制同技术栈**（同一框架、通常同一大版本）；被嵌方每次发版，**所有宿主都要重新构建发布**；样式工具链要对齐（例如 Tailwind 4 要求宿主把包加进扫描源） |
| 适用 | 同一团队或同栈的一组产品；嵌入的是「组件」而非「整个系统」 |

### B · 服务端 / 边缘组合

| 方案 | 机制 | 现状 |
|---|---|---|
| SSI / ESI | nginx、Varnish、CDN 按标记把 HTML 片段拼进页面 | 老牌、稳定；适合内容型页面，不适合重交互后台 |
| Podium · Tailor | 源站把各团队的 HTML 片段（podlet / fragment）组合成页面 | 电商门户用得多（Finn.no、Zalando） |
| **Next.js Multi-Zones** / `@vercel/microfrontends` | 多个独立 Next 应用挂在同一域名的不同路径下，边缘按路径路由；有跨区 Link 与预取 | Vercel 一方方案，**支持 App Router**；业界把它视为 Next 生态替代 Module Federation 的主路径 |
| 反向代理按路径分流 | `/a/**` → 系统 A、`/b/**` → 系统 B，同域 | 最朴素的「微前端」；本质是 F 类跳转 + 同域（共享 cookie、无跨域） |

优势：浏览器端零框架、首屏快、同域无跨域问题。代价：整页切换（跨区导航会重新加载）；外壳要么各自实现要么服务端注入。

### C · 浏览器运行时 · 模块级

| 方案 | 机制 | 现状（2026-09） | 注意 |
|---|---|---|---|
| **Module Federation 2.0** | 运行时从远程加载模块，共享依赖按版本协商（singleton） | 2.0 已稳定，运行时与打包器解耦；支持 webpack · **Rspack** · Rollup · Rolldown · **Vite** · Metro；带类型共享与 manifest 动态发现。`module-federation/core` 最新 v2.9.2（2026-09-26）| **Next.js 是例外**：`@module-federation/nextjs-mf` 已进维护模式、预计 2026 年底移出 CI，**App Router 从未被支持**；Vite 侧成熟度不如 Rspack |
| import maps + SystemJS | 浏览器按映射表加载各系统的 ES 模块，共享 React 等依赖 | 标准能力（import maps 已被主流浏览器原生支持）；single-spa 官方推荐搭配 | 共享依赖版本要人为治理 |
| **Web Components** | 各系统把界面封成自定义元素（custom element），宿主当 HTML 标签用 | 浏览器标准，不依赖任何框架；Salesforce LWC、SAP UI5 Web Components 都走这条 | 属性只能传字符串，对象与函数要走 property；Shadow DOM 与弹层、表单、焦点有已知坑；各元素自带一份框架运行时 |

优势：可以**同屏组合**（一个页面里放多个系统的组件）；被嵌方独立发布，宿主不用重建。代价：共享依赖版本治理；样式与全局污染要靠纪律。

### D · 浏览器运行时 · 应用级（微前端框架）

| 框架 | 机制 | 活跃度（GitHub，2026-09-27） | 评价 |
|---|---|---|---|
| single-spa | 主应用管各子应用的挂载 / 卸载生命周期；推荐 import maps | ★13.9k；v7 仍是 **beta.13（2025-09）**，最近推送 2026-02 | 思想是业界源头，但核心已近一年无推进，维护风险高 |
| **qiankun**（蚂蚁） | 基于 single-spa + JS 沙箱（Proxy）+ 样式隔离，HTML entry | ★16.7k；**v3.0.0-rc.22（2026-08-30）**，活跃 | 国内最普及；2.x **不原生支持 Vite 的 ESM**（需插件）；3.0 迟迟未正式发布 |
| **micro-app**（京东） | 类 Web Component 容器 + 沙箱，可选 iframe 沙箱模式 | ★6.3k；**v1.0.0-rc.32（2026-06）**，活跃 | 接入改造少；1.0 长期处于 rc |
| **wujie**（腾讯） | 子应用 **JS 跑在 iframe 沙箱**、**DOM 渲染在 Web Component（Shadow DOM）**；支持保活、预加载、多应用同屏 | ★5.0k；**v2.1.0（2026-06-15）** | 隔离最彻底、对 Vite 友好、子应用几乎零改造；代价是每个子应用一个 iframe 的内存开销 |
| Garfish（字节） | 沙箱 + 路由驱动加载，Modern.js 体系 | ★2.9k；v1.19.12（2026-08），活跃 | 与字节系工具链绑定较深 |

共同优势：**跨技术栈**（主应用 React、子应用 Vue 都行）；子应用独立开发发布；有统一外壳。
共同代价：沙箱不是银弹（第三方库依赖 `window.top`、全局弹层、`position: fixed`、字体加载等总有边角问题）；调试链路长；性能开销；**框架本身成了新的依赖与单点**。业界 2026 年的普遍态度是「真有多团队多栈独立发布需求再上，否则复杂度税不值」。

### E · iframe + 通信桥

| 代表 | 做法 |
|---|---|
| **SAP Luigi** | Luigi Core 提供外壳（导航、权限、顶栏），各子应用在 iframe 里，Luigi Client 经 postMessage 与外壳交互；另有 Luigi Container 可以脱离 Core 单独嵌 | 
| **Shopify App Bridge** | 第三方应用嵌在 Shopify 后台的 iframe 里；App Bridge 提供导航、弹窗、Toast 等外壳能力，并**发放 60 秒有效的会话令牌**给嵌入应用调自己的后端，过期返回 401 + 特定头，桥自动换新重试 |
| Atlassian Connect · Salesforce Canvas · 各大云控制台 | 同一思路：外壳是宿主的，嵌入方在 iframe 里，经桥获得身份与外壳能力 |

优势：**隔离绝对**，适合**跨组织 / 第三方**（信任边界不同）；任何栈都能接。
代价：视觉只能靠嵌入方自觉遵守设计规范（样式不继承）；弹层出不了 iframe（所以桥要提供「请外壳替我弹窗」）；双滚动条、高度自适应、深链同步都要桥来补。

### F · 链接跳转 + SSO（门户模式）

| 项 | 内容 |
|---|---|
| 机制 | 统一门户 / 应用启动器列出各系统入口；点击跳转到对应系统；靠统一登录实现无感切换 |
| 代表 | Google Workspace、Microsoft 365 的应用启动器；多数企业内部「工作台 / 门户」 |
| 优势 | **零耦合**：各系统完全独立，任何栈、任何部署方式都能接；成本最低 |
| 代价 | 整页切换、各系统外壳各异（除非共享设计系统）；没有同屏组合 |

## 四、横切关注点的业界做法

### 4.1 统一认证（含跳转）

**底座：集中身份提供方（IdP）+ 标准协议。**

| 层 | 业界做法 |
|---|---|
| 协议 | 新建系统一律 **OIDC**（OAuth 2.0 之上）；对接老企业系统用 SAML；CAS 已少见 |
| 集中 IdP（自托管，2026-08 版本） | **Keycloak 26.7**（协议覆盖最广、SAML 中转与细粒度授权最强，Java 系）· **Zitadel v4.16**（Go、原生多租户、API 优先、事件溯源审计）· **Authentik 2026.5**（最灵活，可做前置认证代理，给不会 SSO 的老应用套一层）· **Casdoor**（Go，带 Casbin 策略引擎，国内用得多）|
| 浏览器侧令牌 | **RFC 10017《OAuth 2.0 for Browser-Based Applications》（2026-08 发布）**：一律授权码 + PKCE，禁用隐式流；**推荐 BFF**：由后端作为机密客户端持有令牌，浏览器只拿 HttpOnly 会话 cookie，令牌永不进浏览器 |
| 跨系统跳转 | 系统 B 发现未登录 → 重定向到 IdP → IdP 已有会话 → 直接带授权码回 B（用户无感）；B 用 `prompt=none` 做**静默续期** |
| 嵌入场景 | 被嵌方不自己走登录，而是向外壳要**短期会话令牌**（Shopify：60 秒 JWT，过期由桥自动换新）；或由外壳经 BFF 代为调用 |
| 服务间换票 | **RFC 8693 Token Exchange**：A 服务拿用户令牌换一张给 B 服务用的、受众收窄的令牌，而不是把用户令牌原样转发 |
| 单点登出 | OIDC **Back-Channel Logout**（IdP 服务端直接通知各系统，不受第三方 cookie 拦截影响，推荐）与 Front-Channel Logout（浏览器里挨个加载各系统登出页，易被拦） |
| 没有 IdP 时的过渡 | 由某个既有系统扮演 IdP（开出 authorize / token 两个端点），协议形状照 OIDC，将来换真 IdP 只改配置 |

安全要点（业界通行）：令牌不放 URL 与 DOM 属性；授权码单次有效、秒级过期、绑定 `redirect_uri`；`state` 防 CSRF；`redirect_uri` 白名单精确匹配；不信任前端自称的身份字段。

### 4.2 统一权限

| 做法 | 说明 | 取舍 |
|---|---|---|
| IdP 只管「你是谁」，各系统自判「你能做什么」 | 最常见；角色可作为令牌 claim 下发 | 简单；跨系统的权限视图要另做 |
| 集中授权服务（策略即代码：OPA、Casbin、Keycloak Authorization、Zanzibar 系如 SpiceDB / OpenFGA） | 各系统调它判权 | 一致性最好；引入新的关键依赖 |
| 外壳按权限过滤菜单，服务端做真正的闸 | 所有方案都应如此 | 前端判权只是体验，**不是安全边界** |

### 4.3 外壳与导航

业界几乎都有一个「外壳」（shell / 主应用 / 门户）：统一顶栏、菜单、通知、全局搜索、用户菜单。菜单通常由各子系统**以清单（manifest）注册**：路径、标题、图标、所需权限、入口地址；外壳汇总渲染。Luigi 的导航配置、Backstage 的插件注册、qiankun 的 `registerMicroApps` 都是这个模式。

### 4.4 视觉一致

| 手段 | 说明 |
|---|---|
| **设计 token**（CSS 变量；W3C Design Tokens 格式作为交换格式） | 最关键的一条：**CSS 自定义属性会穿透 Shadow DOM 继承**，所以 C / D 类方案下外壳换主题，子系统自动跟随；E 类（iframe）不继承，要经桥下发 |
| 共享组件库 / 设计系统 | 同栈发 npm 包；跨栈发 Web Components 版本（Salesforce、SAP 都这么做） |
| 样式隔离 | Shadow DOM（最彻底）· CSS 前缀 / CSS Modules（纪律型）· iframe（绝对）；**全局 reset（如 Tailwind preflight）绝不能注入宿主** |

### 4.5 通信与路由

| 项 | 业界做法 |
|---|---|
| 通信 | **URL 是第一契约**（深链、刷新、分享都靠它）；其次是事件（CustomEvent / 框架事件总线 / postMessage）；尽量不共享全局状态 |
| 路由 | 外壳按路径前缀分配给子系统；子系统内部路由同步回外壳 URL（wujie 的 `sync`、Luigi 的路由桥） |

### 4.6 版本与发布

独立发布是 B–F 类的核心卖点。关键实践：用 **manifest 做运行时发现**（外壳读取「当前各子系统版本的入口地址」，不写死）；共享依赖在 MF 里声明 singleton 并协商版本；主版本入 URL 或入 manifest，破坏性变更并行一段时间。

## 五、选型决策

| 条件 | 倾向 |
|---|---|
| 跨组织 / 第三方接入（信任边界不同） | **E**（iframe + 桥 + 短期会话令牌） |
| 同组织、**多技术栈**、要统一外壳或同屏 | **D**（wujie / qiankun / micro-app）或 **C**（Web Components） |
| 同组织、**同栈**、要同屏组合 | **A**（npm 包）或 **C**（Module Federation 2.0，Next 除外） |
| Next.js 为主、要多团队独立部署 | **B**（Multi-Zones） |
| 各系统松耦合、整页切换可接受 | **F**（门户 + SSO） |
| 任何情况 | 底座都是 **统一 IdP + OIDC**；前端判权只做体验 |

业界典型组合：

| 形态 | 组合 | 例 |
|---|---|---|
| 大型同栈平台 | A + C（MF） | 电商 / SaaS 单体拆团队 |
| 国内企业多系统后台 | D（qiankun / wujie 主应用）+ 统一登录 | 各类「中台 / 工作台」 |
| 平台开放给第三方 | E + 短期令牌 | Shopify、Atlassian、Salesforce |
| 多产品套件 | F + 统一 IdP + 共享设计系统，局部 A / C | Google、Microsoft |

## 六、微前端的常见误区（业界复盘里反复出现的）

| 误区 | 实际 |
|---|---|
| 「上了微前端就解耦了」 | 解耦的是**构建与部署**；业务耦合（共享数据、跨系统流程）一点没少，还多了运行时耦合 |
| 「沙箱能兜住一切」 | 弹层、全局样式、第三方脚本、`window.top`、字体与 Service Worker 总有漏网，必须有 PoC 清单逐项验 |
| 「按系统拆就是按团队拆」 | 微前端的边界应当跟**团队与发布节奏**走；同一团队的多个系统硬拆只会增加成本 |
| 「统一认证靠前端传令牌」 | 令牌在浏览器里多一处存放就多一处泄露面；RFC 10017 的方向是**让令牌离开浏览器**（BFF） |

## 七、PoC 该验什么（任何 C / D / E 类方案通用）

| # | 项 | 通过标准 |
|:-:|---|---|
| 1 | 样式双向不污染 | 宿主与子系统各一个「故意冲突」的样式，双方都不受影响 |
| 2 | 主题联动 | 宿主换主题，子系统同帧跟随 |
| 3 | 弹层与焦点 | 下拉、对话框、Toast 位置正确、层级正确、Esc 与焦点回归正常 |
| 4 | 深链 | 子系统内部任一页面 URL 可复制、刷新、分享、前进后退 |
| 5 | 身份 | 子系统拿不到宿主令牌原文也能正确识别用户；宿主登出后子系统下一次请求即失效 |
| 6 | 性能 | 首次加载、切换、保活的耗时与内存有数 |
| 7 | 失败降级 | 子系统加载失败时外壳给出可用的跳转入口，而不是白屏 |

## 八、对照本组织（事实均为 2026-09-27 实测）

| 事实 | 对选型的含义 |
|---|---|
| 36 个仓里的前端分五组栈：Next 16 + React 19 + Tailwind 4（8 个运营台，同模板）· React 19 + Vite 8（4）· React 18 + Vite 5（5）· Vue 3 + UnoCSS（uni-app，3）· 无 JS 前端（2） | **多栈是事实** → 纯 A 类只能覆盖一半；需要 D 或 C（Web Components）承接跨栈 |
| 主力宿主是 **Next.js（App Router）** | **Module Federation 基本出局**（nextjs-mf 维护模式、App Router 从未支持）；若要同栈多团队独立部署，B 类 Multi-Zones 是 Next 生态的正路 |
| 运营台均为 `output: "export"` 静态导出 | 无 Node 层 → BFF 若要做，只能放在各系统 Java 后端或独立网关里，不能放在 Next 里 |
| **没有统一认证中心**；ShareHub 与 ai-shop 各自发**不透明令牌**（ShareHub 为 `stk_` + UUID，会话在 Redis），前端存 `localStorage`、以 Bearer 头发送 | 跨系统跳转必须重新登录；且不透明令牌无法离线验签，只能回源内省。这是**最该先补的一块**，与选哪种前端组合无关 |
| 所有系统同一组织、同一设计规范体系 | 不需要 E 类的绝对隔离；D 类或 C 类足够 |

**据此的建议组合**（供拍板，不是结论）：

| 层 | 选择 | 理由 |
|---|---|---|
| 底座 | **统一 IdP（Keycloak 或 Zitadel）+ OIDC**；各系统后端作为机密客户端，保留现有会话机制（本质上就是 RFC 10017 的 BFF 形态） | 现有「后端持会话、前端持不透明句柄」离 BFF 只差一步；IdP 上线前可让一个系统按 OIDC 形状临时充当 IdP |
| 基线 | **F · 门户 + SSO 跳转** | 22 个前端任何栈都能接，零改造 |
| 整块嵌入（跨栈） | **D · wujie**（首选，隔离最彻底、Vite 友好）或 micro-app | 同组织多栈；Shadow DOM 渲染使 CSS 变量主题可继承 |
| 组件级嵌入（同栈） | **A · npm 包**；跨栈时发 **Web Components** 版本 | 只在确有「同屏放一张别系统的卡片」需求时做 |
| 不做 | Module Federation（Next 为主）、single-spa（维护停滞）、qiankun 2.x（Vite ESM 不原生） | 见 §三 |

与 [15](./15-前端方案-独立可嵌入与皮肤.md) / [17](./17-前端模块化集成.md) 的差异：那两篇以「flow 平台嵌进 ops-web」为中心、否决了微前端；本篇从业界出发，**微前端（wujie）进入候选**，且把**统一 IdP** 提为所有方案的共同前置。15 / 17 是否据此修订，待拍板后再改。另一会话在写的 18《技术栈》§五 沿用了「否决微前端」的旧结论，需其作者同步。
