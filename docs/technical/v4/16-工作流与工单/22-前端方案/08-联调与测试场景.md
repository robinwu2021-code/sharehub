## 二、运营端场景（S1–S6）

| 编号 | 场景 | 断言 | 对应服务口径 |
|---|---|---|---|

**场景已抓到的缺陷**（都在 9-28 修掉并补了单元回归）：

- 「仅可查看」句式的 key 落错分组，全站约 30 处显示原始 key。三语 key 齐平，所以 i18n 单测是绿的。
- mock 返回审批视图时是浅拷贝，写操作会「穿透」进页面缓存，界面一半新一半旧。

## 三、对真实 OpsKit 跑（O4-0 到位后）

1. 后端起服务，本地 profile，端口 8090。用 `opskit/scripts/dev-token.sh` 签成员令牌，参数为 sub、perms、`ws=ext:{租户号}`。
2. 把种子里的单号与令牌填进 `ops-web/scripts/flow-e2e/fixtures.opskit.json`。**令牌不要提交**。
3. `OPSKIT=http://localhost:8090 OPSKIT_WS=ext:{租户号} OPSKIT_ACCOUNT={账户} ops-web/scripts/flow-e2e.sh`
4. 首轮先跑读侧 `--only S1-1,S5`，再跑写侧 S2、S3、S4；S6 等 O3-8。

**种子要满足场景**（已发后端会话）：

| 场景 | 种子要求 |
|---|---|
| S2-1 | 一张两步单，第二步是条件会签，且条件成立；令牌成员是第一步候选、不是提交人 |
| S2-2 | 一张提交人就是令牌成员的待审单 |
| S3 | 一个队列组有 ≥ 2 条未领任务、1 条被别人领着 |
| S5 | 另签一个只有 `flow:todo:read · flow:approval:read · flow:ticket:read` 的只读令牌 |

**首次联调要核对的「待对齐」项**：已在 `lib/flow/client.ts` 标注。

- `tasks/query` 的参数名。
- 批量改派的请求体：契约是按原受理人 `{from, to, reason}`，界面是勾选若干单。
- 成员、工单类型、成员属性这三个选项接口：目前仍用 mock 的选项，接真服务前要换成异步查询。
- 页面上显示的 whyNot 文案：服务端按语言给出，场景 S2-1 目前匹配的是 mock 的原文。

## 四、跨端场景（M5 接入后补自动化）

| 编号 | 端 | 场景 | 断言 |
|---|---|---|---|
| X1 | C 端 → ShareHub → OpsKit → 运营端 | 用户在 C 端报障 | 工作台出现一张来源为「C 端」的工单，SLA 起算 |
| X2 | 柜机告警 → ShareHub → OpsKit | 同一柜机重复告警 | 并入同一单（去重键），时间线记「重复告警并入」 |
| X3 | 运营端 → OpsKit → ShareHub | 进场合同审批通过 | ShareHub 收到 webhook，合同状态随之变化；重投幂等 |
| X4 | ShareHub 登录 → OpsKit | 员工权限变更 | 下一次调用 OpsKit 即按新权限判（内省不缓存过期权限） |
| X5 | 代理门户 → OpsKit | 代理只看到自己片区的工单 | 范围标签过滤；负对照：换片区看不到 |
