## 一、一页结论

| 问题 | 结论 |
|---|---|
| 形态 | **同域、按路径分区**：运营台在 `/`，流程与工单平台（`flow-console`）在 `/flow/`；各自仓库、各自构建、各自发布；nginx 按前缀分流 |
| 为什么是这个 | 用户定的目标是「各自开发、集成到一起」，不要求同屏组合与跨栈嵌入；在这个目标下它最简单，且不引入任何运行时框架（对比见 [19](../19-前端模块化-业界方案调研.md)） |
| 看起来是一个产品 | 靠两个共享包：**`@neargo/ops-shell`**（外壳、会话、主题、语言）与 **`@neargo/ops-ui`**（设计 token + 基础组件），都从 ops-web 抽出 |
| 登录 | 只在运营台；同源，登录一次两区通用；无需跨域 SSO |
| 技术栈 | 与 ops-web 同模板：Next 16 静态导出 · React 19 · Tailwind 4 · Radix · TanStack Query/Table · zustand |
| 视觉 | 布局与组件照 ops-web；原型的可取之处落为 `teal` 皮肤 + 六个通用组件 |

## 二、与后端的边界（2026-09-27 与后端会话逐条对齐）

前端**不定义**接口、权限判定与数据范围；这些在 21。前端对后端只有下面这些**要求**，由 21 落实。
前端契约类型见 `ops-web/lib/flow/types.ts`（与 21/06 §七 同形），唯一取数入口 `ops-web/lib/flow/client.ts`。

| # | 前端需要 | 21 中的对应 | 状态 |
|:-:|---|---|---|
| R1 | 同源经宿主反代：基址 **`/api/opskit/v1`**，运行时资源在 `/workspaces/{ws}/` 下，ShareHub 场景 `ws = ext:{租户号}` | 21/06 §二 | ✅ 定稿（原 `/api/flow/ui/v1` 已废止） |
| R2 | 服务从**宿主令牌**解析操作人与权限，前端不传操作人、数据范围 | 21/06 §一「成员」 | ✅ 定稿；ShareHub 登记为 INTROSPECT 类 IdP，需 ShareHub 新增内省端点（21/07 P2，未做） |
| R3 | 带业务前置校验的动作由页面直接调**宿主后端** | 21 README C5 | ✅ |
| R4 | 列表每个筛选控件都有对应查询参数 | 21/06 §二「查询」 | ✅ |
| R5 | 统计卡数字附 queryParams；详情出参带 `actions[]` | 21/06 §五 | ✅ |

**成员属性显示名**（后端 21/07 O1-12）未实现前只给原值，前端没有 name 就显示原值。

**不写死业务词**（后端要求，前端已照做）：办理人类型取 `assignee.attrs.partyType`、来源取 `fields.source`、
优先级色调按 `priority.ordinal`、类型与状态名用服务给的 `name`。
