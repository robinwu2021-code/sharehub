# 02 · 前端架构设计

> 所属：[22 前端方案](./README.md)。本篇只讲前端；服务端（界面面、令牌解析、数据范围）见 [21](../21-设计方案-重梳/README.md)。

## 一、形态：同域、按路径分区（Multi-Zones 模式，自托管）

| 区 | 前缀 | 产物 | 仓库 | 拥有者 |
|---|---|---|---|---|
| 运营台（宿主区） | `/` | ops-web 静态导出 | powerbank/ops-web | ShareHub |
| **流程与工单** | **`/flow/`** | **flow-console 静态导出** | 平台（独立仓库） | 平台 |
| C 端 H5（已有） | `/c/` | c-app 静态 | powerbank/c-app | ShareHub |

每个区是一个完整的静态站点，各自构建、各自发布；nginx 按路径前缀分流。登录、首页、个人设置属于宿主区；各区只拥有自己前缀下的页面。

**为什么不用 `@vercel/microfrontends`**：它的生产路由由 Vercel 平台托管，而我们部署在腾讯云；并且各区都是 `output: "export"` 静态导出，Next 在此模式下**不支持 rewrites / redirects / middleware**。所以路由层用 nginx，其余照 Multi-Zones 的约定（`basePath`、跨区链接、共享布局包）。

## 二、先例与 nginx

生产 nginx（实测 `deploy/tencent/nginx/powerbank.ichain.top`）已经在同域 `/c/` 下挂着 C 端 H5：

```nginx
root /data/app/powerbank/web/ops-web;          # 运营端出在 /

location ^~ /c/ {
    alias /data/app/powerbank/web/c-app/;
    try_files $uri $uri/ /c/index.html;
    location ~* \.(js|css|woff2?|svg|png|jpg|jpeg|webp)$ { expires 30d; access_log off; }
}
```

flow 区照抄：

```nginx
location ^~ /flow/ {
    alias /data/app/powerbank/web/flow-console/;
    try_files $uri $uri/ $uri.html /flow/index.html;   # trailingSlash: true 的静态导出需要 $uri.html
    location ~* \.(js|css|woff2?|svg|png|jpg|jpeg|webp)$ { expires 30d; access_log off; }
}
```

接口反代 `location ^~ /api/flow/` 属于后端部署项（21）；`^~` 取最长前缀，自然优先于既有的 `/api/`，与书写顺序无关。

## 三、两个共享包

两区看起来是一个产品，靠的是两个从 ops-web 抽出的包：

| 包 | 内容 | 实测来源 | 变化频率 |
|---|---|---|---|
| **`@neargo/ops-shell`** | `<OpsShell>`（顶栏 · Rail · 二级菜单 · 内容区）· 会话读写与 401 处理 · 主题 · 语言 · 操作人切换 · 菜单来源切换 · `zoneHref()` | `components/layout/` 的 8 个文件 · `lib/auth.ts` · `lib/stores/{theme,locale,nav-prefs}.ts` · `lib/api/session.ts` · `lib/menu-source.ts` | 跟宿主演化，较快 |
| **`@neargo/ops-ui`** | 设计 token（`globals.css` 的 token 部分）· 基础组件 · 六个新组件（04） | `components/ui/` 的 41 个组件 | 稳定，较慢 |

拆成两个而非一个，是因为两者的发版节奏不同：外壳常随菜单与宿主功能变，基础组件很少变；合成一个包，每次外壳小改都会逼 flow 区跟着升基础组件。

抽包的两处要改（实测）：

| 处 | 现状 | 改法 |
|---|---|---|
| `components/ui/file-field.tsx` | 直接 `import { api } from "@/lib/api"` 上传文件 | 改为由调用方传入 `upload` 函数 |
| `components/ui/` 里 9 处 `@/lib/i18n` | 读宿主的 i18n 模块 | 包内自带基础组件文案（三语）+ 允许调用方覆盖 |

## 四、区契约（每个区必须遵守）

| # | 约定 | 为什么 | 怎么守 |
|:-:|---|---|---|
| 1 | `basePath` = 自己的前缀（flow 区为 `/flow`） | 路由与静态资源挂在前缀下，不与别区撞 | ops-web 的 `next.config.ts` **已支持** `NEXT_PUBLIC_BASE_PATH` → `basePath`/`assetPrefix`（实测），flow-console 同模板 |
| 2 | 外壳一律用 `@neargo/ops-shell` | 视觉与菜单一致 | 架构测试：区内禁止自写顶栏 / 侧栏 |
| 3 | 会话、主题、语言只经 `ops-shell` 读写 | 同源下 `localStorage` 天然共享，但各区自己读写就会写出两套 key | 架构测试：区内禁止直接访问这些存储 key |
| 4 | **跨区链接用 `<a href>`，区内用 `<Link>`** | Next 的 `<Link>` **会自动加 basePath**：在 flow 区写 `<Link href="/sites">` 会变成 `/flow/sites`，打到 404 | 菜单由 `ops-shell` 按「目标是否在本区前缀内」自动选；页面内跨区用 `zoneHref()`；架构测试拦截 flow 区里 `<Link>` 指向非 `/flow` 的字面量 |
| 5 | 401 一律跳宿主区 `/login?next=<当前完整路径>` | 登录只在宿主区 | `ops-shell` 统一处理 |

## 五、菜单

实测：菜单已经有两个来源，由 `lib/menu-source.ts` 切换 —— 本地 `lib/nav.ts` 的 `NAV`（默认），或服务端 `GET /api/auth/menus`（构建期 `NEXT_PUBLIC_DYNAMIC_MENU=1` 或浏览器开关打开时）；**拉取失败、空树、字段缺失一律回落本地**，理由写在该文件里：「菜单拿不到就整站没有入口」。

flow 区照搬这套逻辑，只是「本地那份」换成宿主导出的静态文件：

| 顺序 | 来源 | 说明 |
|:-:|---|---|
| 1 | `GET /api/auth/menus`（同源，带宿主令牌） | 与宿主区开关同一个判定；服务端菜单天然已按权限裁剪 |
| 2 | `/shell/nav.json`（宿主构建时由 `NAV` 生成） | 兜底，保证 flow 区永远有菜单 |

| 项 | 定 |
|---|---|
| 菜单归谁 | **归宿主**：flow 的叶子加在宿主的 `lib/nav.ts`（放组末尾）与菜单种子里，沿用既有的菜单迁移 SQL → 三语 → 快照与 `nav-seed` 卡口 |
| `menu-source` 放哪 | 随外壳一起进 `ops-shell`，两区共用同一份切换与兜底逻辑 |
| 区多了以后 | 各区各自登记菜单，外壳按清单合并；等第三个区出现再做 |

## 六、登录、会话与权限（前端侧）

| 项 | 做法 |
|---|---|
| 登录 | 只在宿主区；令牌存在同源 `localStorage`（现 key `pb-ops-auth-v2`，由 `ops-shell` 独占），两区共享 → 登录一次两区通用 |
| 调接口 | flow 区带宿主令牌调同源 `/api/flow/ui/v1/**`；**不传操作人、不传数据范围**（服务从令牌解析，21 K4） |
| 按钮权限 | 从会话读 `perms`，按 `flow:*` 权限码控制（码表见 04 §四）；前端判权只是体验，闸在服务端 |
| 登出 | 宿主区登出清会话；flow 区下一次请求得 401 → 跳登录页 |
| 以后 | 按 RFC 10017 改 BFF：会话改为 `Path=/` 的 HttpOnly cookie，两区照样共享、令牌离开浏览器；本方案不用改 |

## 七、本地开发

| 项 | 做法 |
|---|---|
| 单独开发 | 每个区自己 `pnpm dev`；flow 区可用 `ops-shell` 的 mock 会话 + 接口 mock，不依赖运营台与后端 |
| 联调 | 一个本地代理把各 dev server 拼成同域：`/` → ops-web、`/flow/` → flow-console、`/api/**` → 后端；**必须放行 WebSocket 升级**，否则 HMR 断 |
| 为什么不用 Next 的 rewrites | 静态导出模式不支持 rewrites，dev 里也不能指望它 |
| 共享包联调 | pnpm workspace 链接本地包；Tailwind 4 默认不扫 `node_modules`，两区的 `globals.css` 都要为两个包声明 `@source`，否则包里的类名不生成、组件完全没样式（且不报错） |

## 八、发布

| 项 | 做法 |
|---|---|
| 独立发布 | 各区独立流水线，产物落各自目录（`web/ops-web/` · `web/flow-console/`），互不覆盖 |
| 缓存 | `index.html` 不缓存；带 hash 的资源长缓存（与 `/c/` 同配置） |
| 共享包 | 发私仓 `nexus.neargo.ai`；**发布前卡口**：两区锁定的 `ops-shell` 与 `ops-ui` 次版本号必须一致，否则两区外壳会看出差异 |
| 菜单变更 | 宿主发布即更新 `/shell/nav.json`，flow 区无需发布 |

## 九、代价与边界

| 代价 | 说明 | 缓解 |
|---|---|---|
| 跨区整页加载 | 运营菜单与工单菜单之间切换会整页刷新 | 状态在 URL 上（页内 tab 已由 `use-page-tab` 同步到 URL）；对另一区入口预取 |
| 抽包的一次性成本 | 外壳 8 个文件 + 基础组件 41 个 + 两处去耦 | 边界现成 |
| ai-shop 接入 | 它的同名外壳文件已分叉（7 个文件各差 19～101 行，另有 3 个独有组件） | 放到 ai-shop 接入时合并，不阻塞 powerbank |
| 只适合同一产品域 | 各区共用外壳与登录 | 跨组织、跨栈嵌入不在范围 |
