## 一、状态机（`workflow-api`）

### 1.1 定义（产品侧，类型化）

```java
enum WoStatus { CREATED, DISPATCHED, ACCEPTED, PROCESSING, DONE, AUDITED, CLOSED }
enum WoEvent  { DISPATCH, ACCEPT, PROCESS, COMPLETE, AUDIT, CLOSE, REJECT, REWORK, WITHDRAW, MERGE }

static final StateMachine<WoStatus, WoEvent> WO = StateMachine.builder("PB_WORK_ORDER", WoStatus.class, WoEvent.class)
    .edge(DISPATCH, CREATED, DISPATCHED)
    .edge(ACCEPT,   DISPATCHED, ACCEPTED)
    .edge(PROCESS,  ACCEPTED, PROCESSING)
    .edge(COMPLETE, PROCESSING, DONE)
    .edge(AUDIT,    DONE, AUDITED)
    .edge(CLOSE,    AUDITED, CLOSED)
    .edge(REJECT,   Set.of(DISPATCHED, ACCEPTED, PROCESSING), CREATED)
    .edge(REWORK,   DONE, PROCESSING)
    .edge(WITHDRAW, Set.of(CREATED, DISPATCHED), CLOSED)
    .edge(MERGE,    Set.of(CREATED, DISPATCHED, ACCEPTED, PROCESSING), CLOSED)
    .role(CREATED, StateRole.INITIAL)
    .role(Set.of(DISPATCHED, ACCEPTED, PROCESSING), StateRole.ACTIVE)
    .role(DONE, StateRole.AWAITING_VERIFY)
    .build();   // 构建期完成全部校验（§1.3）；CLOSED 无出边 → 自动 TERMINAL
```

### 1.2 接口

| 方法 | 语义 | 失败 |
|---|---|---|
| `S next(S from, E event)` | 推进（不跑守卫） | `IllegalTransitionException` · 键 `workflow.transition.illegal` |
| `S next(S from, E event, GuardContext ctx)` | 推进并跑守卫 | `GuardRejectedException(errorKey, args)` |
| `Set<E> events(S from)` | 可走事件 | —— |
| `Optional<E> eventFor(S from, S to)` | 反查事件 | 多个 → `AmbiguousEventException`（不随便挑） |
| `boolean isTerminal(S)` · `Set<S> terminals()` · `StateRole roleOf(S)` | 由图推导 | —— |
| `Map<S, Set<S>> projection()` | 投影成「起 → 止集合」，兼容 ai-shop / ai-erp 旧调用点 | —— |
| `Graph graph()` | 数据形态（字符串），交给引擎与前端 | —— |

守卫只在产品侧执行（02 §一）：

```java
.edge(CLOSE, AUDITED, CLOSED).guard(ctx ->
    ctx.attr("hasOpenRefund", Boolean.class) ? Guard.reject("wo.close.refund_pending") : Guard.pass())
```

### 1.3 构建期校验

| 校验 | 例 |
|---|---|
| 有且只有一个 `INITIAL` | 没标或标了两个 |
| 每个状态都从 `INITIAL` 可达 | 孤立状态 |
| 每个事件至少一条边 | 定义了没用的事件 |
| 同一 `(event, from)` 不得有两个 `to` | 歧义 |
| 不得手工标 `TERMINAL` | ai-shop 售后 `REJECTED`（有 → `ARBITRATING` 的出边）会在这里被拦下 |

### 1.4 只用状态机也要并发保护与流转日志时

```java
WoStatus to = workflow.fire(
    WO.graph(),
    TransitionTarget.of("wo_order", "wo_no", woNo, "status"),   // 业务表自己的状态列；标识符按 ^[a-z_][a-z0-9_]{0,63}$ 校验
    expectedFrom.name(), WoEvent.DISPATCH.name(),
    TransitionMeta.reason("派单给 " + name).set("assignee_name", name));
// UPDATE wo_order SET status=?, assignee_name=? WHERE wo_no=? AND status=?   → 0 行 → StateChangedException（409）
// 同一事务写 nwf_transition_log
```

**只在形态 A 可用**：它改的是业务表，服务进程碰不到业务库。形态 B 下这一个方法仍在本进程执行（`workflow-core` 的本地部分），只有审批走远程。

## 二、审批（`workflow-api` 定义 · `workflow-core` 引擎）

### 2.1 流程定义（数据，不含 lambda）

```java
@Bean
ApprovalFlow locContractFlow() {
    return ApprovalFlow.code("LOC_CONTRACT")
        .step("OPS").approvers(ApproverRule.byPermission("location:contract:approve")).mode(ANY)
        .step("FINANCE")
            .when(Condition.attr("needsCosign").isTrue())          // 条件由产品在提交前算好
            .approvers(ApproverRule.byPermission("finance:contract:cosign")).mode(ANY)
        .build();
}

@Bean
ApprovalFlow merchantQualificationFlow() {                          // ichain 队列形态
    return ApprovalFlow.code("MERCHANT_QUALIFICATION")
        .step("REVIEW").approvers(ApproverRule.queue("audit-queue-qualified"))
        .build();
}
```

提交时产品算属性：

```java
workflow.submit(SubmitCommand.of("LOC_CONTRACT",
        Subject.of("LOC_CONTRACT", c.getContractNo())
               .attr("needsCosign", needsCosign(c))           // 原来的 if (needsCosign(c)) 挪到这里
               .anchors(c.getSiteNo(), c.getAgentNo(), null)),
    note);
```

### 2.2 审批人规则

| 规则 | 待办判定（`TodoResolver`） | 用在 |
|---|---|---|
| `byPermission(code)` | `ActorContext.permissions` 含该码（含通配） | powerbank |
| `byRole(role)` | `ActorContext.roles` 含该角色 | ai-shop 平台运营 |
| `fromAttr(name)` | 提交时属性里给出的人员编号集合含 `actorNo` | 对象负责人 |
| `queue(code)` | `ActorContext.queues` 含该队列 | ichain、ai-shop 商品审核 |

任务**不展开成具体人**：人员变动（离职、调岗）无需迁移任务；判定在查询时按 `ActorContext` 实时做。

### 2.3 `WorkflowClient`（审批部分）

| 方法 | 语义 | 内建规则 |
|---|---|---|
| `submit(SubmitCommand, note)` | 求计划、建第一步任务 | 同一对象已有 `PENDING` → `already_pending` |
| `decide(approvalNo, APPROVE / REJECT, reason)` | 当前步决定 | 驳回必填原因；不能审自己（流程可关）；队列任务须已领取且为领取人 |
| `withdraw(approvalNo, reason)` | 撤回 | 只有提交人、只在 `PENDING` |
| `resubmit(approvalNo, SubmitCommand)` | 再提交 | 轮次 + 1；属性可更新；旧轮次原样保留 |
| `claim(taskNo)` · `release(taskNo)` | 领取 / 放回 | 已被他人领取 → `claimed_by_other` |
| `myTasks(TaskQuery)` | 待我审批 | `ActorContext` + `ScopeCondition` |
| `detail(approvalNo)` | 全部轮次、每步每人的决定 | —— |
| `current(subjectType, subjectNo)` | 对象当前审批 | —— |
| `history(subjectType, subjectNo)` | 流转历史 | —— |

### 2.4 结果回调（必须幂等）

```java
@Component
class ContractApprovalOutcome implements ApprovalOutcomeHandler {
    public String flowCode() { return "LOC_CONTRACT"; }

    public void onOutcome(ApprovalOutcome o) {
        // 幂等：同一 (subjectNo, round) 已处理过就跳过（形态 B 可能重复交付）
        int n = switch (o.result()) {
            case APPROVED  -> contracts.markSignedIfPending(o.subjectNo(), o.round());
            case REJECTED  -> contracts.markRejectedIfPending(o.subjectNo(), o.round(), o.reason());
            case WITHDRAWN -> contracts.markDraftIfPending(o.subjectNo(), o.round());
        };
        // n == 0：已处理过或状态已变，直接返回 —— 不抛异常，不回调 workflow（R4）
    }
}
```

| 形态 | 何时调 | 异常怎么办 |
|---|---|---|
| A | 最后一步决定的**同一事务**内 | 抛异常 → 审批决定一起回滚 |
| B | 服务提交后经 `/callback` | 返回非 2xx → 服务退避重试；超过上限告警、等对账 |

### 2.5 领取超时

`ClaimTimeoutSweeper.sweep(batch)`：`CLAIMED` 且 `claimed_at + claim-timeout < now` → 放回 `OPEN`，写流转日志。形态 A 由产品定时任务调用；形态 B 由服务自己调度。

## 三、工单（`workorder-api` 定义 · `workorder-core` 引擎）

### 3.1 类型定义

```java
@Bean
WorkOrderType maintenance() {
    return WorkOrderType.code("PB_MAINTENANCE")
        .graph(WoStateMachine.WO.graph())
        .noPrefix("WO")
        .assigneeTypes("EMPLOYEE", "AGENT")
        .dispatch(DispatchMode.MANUAL)
        .slaGroup("PB_WO")
        .anchorSlots("SITE", "AGENT", null)            // 槽位 1、2 的含义；数据范围按此翻译
        .build();
}
```

开单时产品给锚点（快照语义，同 powerbank 数据范围锚点的既定口径）：

```java
workOrders.open(OpenCommand.of("PB_MAINTENANCE")
    .source("ALARM", alarmNo)
    .subject("CABINET", cabinetNo)
    .priority("P2").title(title)
    .anchors(anchorResolver.resolve("CABINET", cabinetNo))     // → [siteNo, agentNo, null]
    .dedupeKey("ALARM:" + cabinetNo + ":" + code)
    .ext(Map.of("locationName", locName)));
```

### 3.2 `WorkOrderClient`

| 方法 | 语义 |
|---|---|
| `registerType(WorkOrderTypeDef)` | 自动装配时对所有 `@Bean WorkOrderType` 调用 |
| `open(OpenCommand)` | 开单；有受理方则直接派 |
| `openOrAttach(OpenCommand)` | 同 `dedupeKey` 已有未结单 → 附加一条时间线，返回该单 |
| `fire(orderNo, eventCode, ActionCommand)` | **所有状态动作的唯一入口**；按该类型的图校验 |
| `assign(orderNo, Assignee, reason)` · `pool(orderNo)` · `grab(orderNo)` | 指派 / 放池 / 抢单 |
| `escalate(orderNo, Assignee, reason)` | 升级 / 接管 |
| `merge(fromNo, intoNo, reason)` | 合并；被并单以 `MERGED` 关闭 |
| `note(orderNo, text, mediaIds)` | 备注与附件 |
| `setPriority(orderNo, priority, reason)` | 改优先级，SLA 重算 |
| `reassignFrom(Assignee, reason)` | 受理方不可用 → 名下未结单改派（产品在代理停用、商家停业时调用） |
| `sweepSla(batch)` | 扫一批超时 |
| `page(WorkOrderQuery)` · `detail(orderNo)` · `summary(SummaryQuery)` | 查询；全部带 `ScopeCondition` |

### 3.3 SLA

| 项 | 规则 |
|---|---|
| 规则来源 | `nwo_sla_rule(rule_group, type_code, priority)` → `respond_minutes` · `resolve_minutes` · `business_hours_only` · `calendar_code` |
| 起算 | 首次进入 `ACTIVE` |
| 暂停 / 恢复 | 进 / 出 `WAITING_EXTERNAL`；暂停时长累加进 `sla_paused_ms` 并顺延 `sla_due_at_ms` |
| 营业时间 | `business_hours_only = 1` 时按 `nwo_calendar` 计算（时区 · 每周时段 · 节假日） |
| 超时 | 扫描置 `BREACHED`、写时间线、提交后发 `SlaBreached` |
| 停表 | 进入 `TERMINAL`：按时完成置 `MET` |
| 改优先级 | 从起算点按新规则重算，已暂停时长照扣 |

### 3.4 结果回调（必须幂等）

```java
@Component
class MaintenanceTransition implements WorkOrderTransitionHandler {
    public String typeCode() { return "PB_MAINTENANCE"; }
    public void onTransition(WorkOrderTransition t) {
        if (!processed.markIfAbsent(t.orderNo(), t.seq())) return;          // 幂等键 (orderNo, seq)
        if ("COMPLETE".equals(t.event())) cabinets.markRepaired(t.subjectNo());
    }
}
```

`seq` 是该工单时间线的序号，单调递增。

## 四、产品侧接口汇总

| 接口 | 必需 | 产出 | 说明 |
|---|:-:|---|---|
| `ActorContextProvider` | ✓ | `ActorContext` | 当前操作人与其权限、角色、队列、租户；定时任务线程里返回 `SYSTEM` |
| `ScopeConditionProvider` | 有数据范围时 ✓ | `ScopeCondition` | 把当前用户的数据范围翻成锚点条件；返回 `ALL` 表示不限 |
| `ScopeAnchorResolver` | 工单有数据范围时 ✓ | 三个锚点值 | 开单 / 送审时从对象算出 |
| `ApprovalOutcomeHandler` | 用审批时 ✓ | —— | 每个流程一个 |
| `WorkOrderTransitionHandler` | 可选 | —— | 需要业务联动的工单类型 |
| `BizNoGenerator` | 可选 | 业务号 | 缺省前缀 + 雪花 |

原先设想的 `PermissionChecker` · `PermissionDirectory` · `QueueMembership` · `AssigneeDirectory` · `BusinessCalendar` 都不要了：权限 / 角色 / 队列装进 `ActorContext`；受理方名字在指派时作为快照传入、可用性由产品调 `reassignFrom` 通知；日历改为数据表。原因见 02 §一 —— 形态 B 的服务无法回调产品做这些判断。

## 五、数据模型

### 5.1 约定

| 项 | 约定 |
|---|---|
| 公共列 | 每张表都有 `system_code VARCHAR(32) NOT NULL`（形态 A 填本产品常量）与租户列（名取建表占位 `${tenantColumn}`，缺省 `tenant_id`）。业务表上租户列可空；**参与唯一键的配置表（SLA 规则、日历）不可空、缺省空串** —— 唯一键里的 NULL 互不冲突，可空会让同一条规则插两遍 |
| 时间 | `BIGINT` 毫秒（UTC）—— 不受 JDBC 连接时区影响；三种数据库同一类型 |
| JSON | MySQL `JSON` / PostgreSQL `JSONB` |
| 表前缀 | 取建表占位 `${prefix}`；工作流缺省 `nwf_`、工单缺省 `nwo_`；**不允许为空** |
| 软删除 | 不做 |

### 5.4 PostgreSQL 差异

| MySQL | PostgreSQL |
|---|---|
| `BIGINT AUTO_INCREMENT PRIMARY KEY` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
| `JSON` | `JSONB` |
| `TINYINT` | `SMALLINT` |
| 表内 `KEY` / `UNIQUE KEY` | 表外 `CREATE [UNIQUE] INDEX` |
| 前缀索引 `rule_ref(128)` | 不需要（B-tree 支持 `VARCHAR(512)`） |

脚本：`classpath:db/workflow/{vendor}/`、`classpath:db/workorder/{vendor}/`（`mysql` · `postgresql` · `h2`），由各模块自己的 Flyway 实例按数据源选择。

| 方向 | 路径（`*HttpPaths` 常量） | 说明 |
|---|---|---|
| 产品 → 服务 | `POST /internal/workflow/definitions` | 推送状态图与流程（带版本；已存在即跳过） |
| | `POST /internal/workflow/approvals` · `/{no}/decide` · `/withdraw` · `/resubmit` | 请求头带 `Idempotency-Key` |
| | `POST /internal/workflow/tasks/{no}/claim` · `/release` | 同上 |
| | `POST /internal/workflow/tasks/query` · `GET /internal/workflow/approvals/{no}` | 请求体带 `ActorContext` · `ScopeCondition` |
| 服务 → 产品 | `POST /callback/workflow/outcome` | 载荷 `ApprovalOutcome`；产品返回 2xx 视为已接收 |
| 产品 → 服务 | `POST /internal/workorder/types` · `/orders` · `/orders/{no}/events/{event}` · `/assign` · `/grab` · `/escalate` · `/merge` · `/notes` | 同上 |
| 服务 → 产品 | `POST /callback/workorder/transition` | 载荷 `WorkOrderTransition` |

鉴权：服务凭证（与支付服务的内部调用同一套）；`system_code` 由凭证决定，请求体里的不采信。

## 七、错误键

| 键 | HTTP | 含义 |
|---|:-:|---|
| `workflow.transition.illegal` | 409 | 当前状态不能走这个事件 |
| `workflow.transition.state_changed` | 409 | 并发：状态已被他人改变 |
| `workflow.transition.ambiguous` | 500 | `eventFor` 歧义（定义缺陷） |
| `workflow.approval.self_review` | 409 | 提交人不能审自己 |
| `workflow.approval.reason_required` | 400 | 驳回必须填原因 |
| `workflow.approval.withdraw_submitter_only` | 409 | 只有提交人能撤回 |
| `workflow.approval.already_pending` | 409 | 已有待审 |
| `workflow.approval.not_claimed` · `claimed_by_other` | 409 | 领取相关 |
| `workflow.definition.unknown` | 400 | 流程 / 状态图未登记 |
| `workorder.not_assignee` | 403 | 不是当前受理方 |
| `workorder.not_in_pool` | 409 | 已被抢 |
| `workorder.merge_self` | 400 | 不能并入自己 |
| `workorder.type.unknown` | 400 | 工单类型未登记 |

文案随模块带 zh / en / ar；产品的全局异常处理把 `WorkflowException` / `WorkOrderException` 映射到自己的错误码分段。
