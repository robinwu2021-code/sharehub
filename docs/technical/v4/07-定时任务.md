## 〇、现状（实测）

**ShareHub 后端没有任何定时调度**：代码与 pom 里没有 `@Scheduled` / `@EnableScheduling` / Quartz / XXL-Job（XXL 只在旧文档里）。
周期性逻辑要么只有手动端点（巡检生成工单、周期出账、重发通知），要么只有一个方法没人调用（`OwnershipReconciler.redeliverPending`），
要么还没写（超时未归还、预授权到期、预约过期、券 / 会员过期、SLA 升级、告警规则评估、离线扫描、指令超时、会话清理、事件重投）。

## 一、决策

1. **不自建**：用 ai-shop 的任务服务，**代码共享一份**，任务服务是共用服务、**暂留 ai-shop**（[ADR-024](../ADR/ADR-024-共用服务暂由ai-shop托管-组件并入框架.md)），本项目只依赖 `shop-job-api` · `shop-job-target`，需要的改动提给 ai-shop 统一改；
2. **不部署自己的实例**：直接用 ai-shop 已在跑的 `ai-shop-job`（同机内网），由它改造为多系统后按 `system=SHAREHUB` 隔离（[ADR-025](../ADR/ADR-025-直接复用ai-shop在跑的支付与任务服务-多系统改造.md)，2026-09-23 用户定）；
3. **一个调度器、三个任务目标**：`SHAREHUB`（业务单体）· `GATEWAY`（协议对接）· `PAY`（pay-svc）—— 正好用上 ai-shop 已设计的多目标（`target` 列 + `targets` 映射）；
4. 业务代码只实现 `JobHandler` + 声明 `JobDeclaration`，**不写 `@Scheduled`**（卡口禁止）。

**共用实例的前提**（调研实测的三处缺口，[ADR-025](../ADR/ADR-025-直接复用ai-shop在跑的支付与任务服务-多系统改造.md) 决定补齐，见 [15 MJ1–MJ5](./15-多系统多平台改造需求.md)）：
`job_name` 全局唯一 → 改为 `(system, job_name)`；只有一把全局令牌 → 每系统每目标一把；运营端不区分系统 → 按登录人所属系统过滤。
**补齐前不许共用**。将来若 MENA 生产要求数据本地化，再按 [ADR-025](../ADR/ADR-025-直接复用ai-shop在跑的支付与任务服务-多系统改造.md) 决定 6 拆成两套实例，只改地址。

## 二、它怎么工作（ai-shop 现有机制）

```
ai-shop-job 共用调度器（无端口，服务自有库；ShareHub 的行 system=SHAREHUB）
   ├─ 每 30 秒同步：GET {目标}/internal/job/declarations → 写 job_definition → 对齐成 ScheduledFuture
   ├─ 到点：写 job_run(running=1) → POST {目标}/internal/job/{handler}/run  （X-Job-Token，同步等结果）
   └─ 结果：SUCCESS / FAILED / SKIPPED / TIMEOUT / UNREACHABLE → job_run · job_log

任务目标（sharehub-app / sharehub-gateway / pay-svc）
   └─ JobHandlerEndpoint：校验令牌 → ShedLock 抢锁（锁名 = handler 名）→ 调 JobHandler.run() → 返回结果
                            抢不到锁 → 409 → 记 SKIPPED（多副本只有一个真正执行）
```

| 语义 | 规则 |
|---|---|
| 调度表达式 | 6 段 Spring cron（到秒），调度器 JVM 时区 |
| 不重叠 | 同一任务上一轮结束才排下一轮 |
| 漏跑 | 不补跑（`BACKFILL` 是占位） |
| 重试 | **只对 UNREACHABLE**（目标不通）重试，退避 5 / 15 / 45 秒；业务失败不自动重试 |
| TIMEOUT | 表示「结果未知」，**不计入连续失败** —— 超时值设太短会让失败被吞掉 |
| 入参 | `JobInvocation(runId, type, bizDate, params)`；`bizDate` 固定为「昨天」（调度器时区） |
| 幂等 | 由业务侧负责（ShareHub 任务全部按业务键幂等） |
| 新任务 | `start-disabled = true`：首次登记一律停用，运营核对后逐个开启 |
| 手动触发 | 运营端写 `trigger_requested_at`，调度器下一轮（≤30 秒）执行 |

## 三、共享方式

### 3.1 需要 ai-shop 做的改动（服务留在 ai-shop）

ai-shop 的任务模块**本来就与业务无关**：包名已是 `ai.neargo.job.*`，`shop-job-api` 零依赖，`store` 只依赖 spring-jdbc + flyway，
有测试守着「classpath 上没有 MyBatis、没有任何业务模块」。服务留在 ai-shop，本项目需要 ai-shop 做的只有：

| 改什么 | 从 → 到 |
|---|---|
| 坐标 | **不变**：`ai.neargo.shop:shop-job-*`；ai-shop 的 CI 把 `shop-job-api` · `shop-job-target` · `shop-job`（可执行）发布到 Nexus |
| 配置前缀 | `shop.job.*` 改为可配（本项目实例沿用或自定，由 ai-shop 定） |
| 默认值 | DDL 的 `target DEFAULT 'PLATFORM'` 去掉默认；默认库名 / 端口改为参数 |
| 🆕 `shop-job-target` | 把 ai-shop 散在 `shop-base` / `shop-app` 的目标侧小类收进来：`JobHandlerRegistry` · `JobHandlerEndpoint`（`/internal/job/**`）· `JobTargetAutoConfiguration` · ShedLock 自动配置 · 进程内模式 `InProcessJobConfig` |

### 3.2 建议一并回馈上游的改进（ShareHub 三目标会用到）

| 改进 | 原因 | 是否阻塞 ShareHub |
|---|---|---|
| 令牌按目标配置（`targets.<T>.token`） | 三个目标三把令牌，泄露一把不波及其他 | 否（先共用一把） |
| `target` 列 16 → 32 字符 | 目标名留余量 | 否 |
| 运营端 API / 页面按目标筛选 | 三目标的任务混在一起难看 | 否 |
| 调度线程池默认 4 → 8；长任务改异步回执 | 同步 HTTP + 长任务（45 分钟对账）会挤住 5 秒级任务 | 否（ShareHub 的长任务少） |
| worker 与 core 统一 Jackson 版本 | 现在 core 用 Jackson 2、worker 用 Jackson 3 两套并存 | 否 |

## 四、ShareHub 集成

### 4.1 写一个任务

```java
@Component
class OrderOverdueScanJob implements JobHandler {
    private final OrderTimeoutService timeouts;
    public String name() { return "order-overdue-scan"; }
    public JobResult run(JobInvocation inv) {
        int n = timeouts.scanOverdue(Instant.now());              // 业务方法自身幂等（按订单号 + 状态条件更新）
        return JobResult.success("handled=" + n);
    }
}

@Configuration
class TradeJobs {
    @Bean JobDeclaration orderOverdueScan() {
        return JobDeclaration.builder("order-overdue-scan", "超时订单扫描")
            .ownerModule("trade.order").defaultCron("10 * * * * *")
            .timeoutSec(50).lockAtMostSec(60).manualTrigger(true).logEveryRun(false).build();
    }
}
```

示意代码，构造方法名以 `shop-job-api` 为准（ai-shop 现有写法是 `JobDeclaration.daily(...)` 等静态工厂 + `JobResult(status, detail, error)`）。
放在所属模块的 `job/` 包（[02 §3.1](./02-服务与模块.md)）。`timeout ≤ lock ≤ 4 × timeout`（声明构造时校验）。

### 4.2 各目标进程的接线

| 项 | sharehub-app | sharehub-gateway | pay-svc |
|---|---|---|---|
| 依赖 | `shop-job-api` · `shop-job-target` | 同左 | 支付服务自带 |
| 端点 | `GET /internal/job/declarations` · `POST /internal/job/{handler}/run` | 同左 | 同左 |
| 安全链 | `/internal/job/**` 走 `X-Job-Token` 过滤器，不走员工令牌 | 同左 | — |
| 出参 | **不套 `Result` 信封**（端点在 `ai.neargo.job` 包，不在 ShareHub 的 `ApiResponseWrapper` 扫描范围 —— 接线后用测试锁住） | 同左 | — |
| 锁表 | `sharehub_core.shedlock` | `sharehub_gw.shedlock` | 支付服务自有库（服务自带） |
| 配置 | `neargo.job.enabled=true` · `neargo.job.internal-token=${JOB_TOKEN}` | 同左 | 同左 |

**开发形态**：`neargo.job.in-process.enabled=true` 时，调度引擎直接跑在 sharehub-app 进程内（调用本地 `JobHandlerRegistry`，不走 HTTP），
本机不必起调度器。**生产禁止**进程内模式（多副本会各跑一份，只靠 ShedLock 兜底）。

### 4.3 运营端（照 ai-shop 移植）

- 后端：`/api/platform/jobs`（列表）· `/jobs/{name}`（详情）· `/jobs/{name}/logs?page&size` · `POST /jobs/{name}/enable|disable` ·
  `PUT /jobs/{name}/cron`（先用 `CronExpression` 校验）· `POST /jobs/{name}/trigger`；
  直接读写共用任务服务的库（sharehub-app 配第二数据源，**非 `@Primary`**，注入带 `@Qualifier`）；**查询一律带 `system='SHAREHUB'`**，由服务侧的数据范围再兜一层（[15 MJ5](./15-多系统多平台改造需求.md)）；
- 权限码：`system:job:read` · `system:job:manage`（登记进[功能权限清单](../../requirements/功能权限清单.md)）；
- 页面：ops-web「系统设置 → 定时任务」，从 ai-shop `ops-web/app/jobs/page.tsx` 移植：按目标分组、状态、下次执行、连续失败、最近日志、启停、改 cron、手动触发；
- 告警：连续失败 ≥ 3 次或 UNREACHABLE 持续 10 分钟 → 经告警模块通知值班。

## 六、部署与配置

### 6.1 在共用调度器里登记 ShareHub

调度器进程与库都是 ai-shop 的，ShareHub **只提供目标地址与令牌**，由 ai-shop 加进它的配置（[15 MJ3](./15-多系统多平台改造需求.md) 的分组形式）：

```yaml
# ai-shop-job 的配置（ai-shop 侧维护）
shop.job.worker.systems.SHAREHUB.targets:
  SHAREHUB: { url: http://app.svc.internal:8082, token: *** }
  GATEWAY:  { url: http://gw.svc.internal:8091,  token: *** }
  PAY:      { url: http://pay.svc.internal:8083, token: *** }   # 支付服务自带，登记在本系统下
```

- **时区**：调度器 JVM 只有一个时区，两系统共用。ShareHub 的 cron 按调度器时区书写；跨时区的业务口径（日结、账期）在任务内部按 `Asia/Dubai` 换算，**不依赖调度器时区**；
- ShareHub 侧只需在各目标进程配 `neargo.job.internal-token`（每目标一把，与上表一致）。

- systemd 单元照 ai-shop `ai-shop-job.service`：`Restart=always` · `TimeoutStopSec=45` · 依赖数据库、**不依赖**业务进程（目标不通时记 UNREACHABLE，不影响调度器）；
- 发布脚本照 `deploy-job.sh`：传新 jar → 切软链 → 重启 → 日志里等「调度器已启动」→ 检查有无「取任务声明失败」（多半是令牌不一致）；
- **时区**：`bizDate`（昨天）与所有 cron 按调度器 JVM 时区算，MENA 生产必须设 `Asia/Dubai`，否则日切类任务错一天。

### 6.2 各目标

```yaml
neargo:
  job:
    enabled: true
    internal-token: ${JOB_TOKEN}
    in-process:
      enabled: false          # 仅本机开发为 true
```

## 七、ai-shop 踩过的坑（接入时逐条对照）

| 坑 | 对策 |
|---|---|
| 第二数据源被设成 `@Primary` / 注入没带 `@Qualifier` → `job_*` 表悄悄建进业务库 | 共用任务库的数据源非 Primary，注入一律 `@Qualifier`；ShareHub 侧**只读** |
| 注册了 `Flyway` 类型的 bean → 业务库自己的迁移悄悄不跑 | 共享模块用自己的 Flyway 实例，不注册为 bean |
| 全局 `ResponseBodyAdvice` 给 `/internal/job` 套了信封 → 调度器读到的字段全是 null | 端点不在 ShareHub 包下；测试断言返回体是裸的 `{status,detail,error}` |
| `JobHandlerRegistry` 挂在某个 profile 下 → 生产拿不到 → 业务进程起不来 | 注册表无条件装配，只有端点受 `neargo.job.enabled` 控制 |
| `start-disabled` 环境变量写错 → 新任务带着启用状态入库 | 发布脚本校验该变量；首发后在运营端核对全部为停用 |
| 两个调度器实例抢同一个目标 | 一个目标只配一个调度器实例（需要高可用时再加 `job_lock`）；共用实例下更要确认 ShareHub 的目标只被登记一次 |
| 有先后依赖的任务只靠 cron 间隔错开 | ShareHub 的依赖链（出账 → 对账）在任务内部检查前置完成标记，不靠时间差 |
| 超时设太短 → 一直记 TIMEOUT，没人告警 | 超时按实测 P99 的 3 倍设；TIMEOUT 连续出现也纳入告警 |
