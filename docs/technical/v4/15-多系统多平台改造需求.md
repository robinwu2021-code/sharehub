# 15 · 支付与任务服务的多系统多平台改造需求

> 所属：[v4 详细规划](./README.md) · 决策：[ADR-025](../ADR/ADR-025-直接复用ai-shop在跑的支付与任务服务-多系统改造.md) · 前序：[ADR-024](../ADR/ADR-024-共用服务暂由ai-shop托管-组件并入框架.md)
> 状态：**需求已定，待 ai-shop 排期**（2026-09-23）
> **这份文档是 ShareHub 提给 ai-shop 的需求规格**：改动全部发生在 ai-shop 仓库的 `backend/pay/` 与 `backend/job/`，由 ai-shop 统一实施；ShareHub 负责对接与验收。
> 现状实测见 ADR-025 §背景。

---

## 〇、目标与范围

| 项 | 内容 |
|---|---|
| 目标 | 一套支付服务、一套任务服务，**同时服务多个业务系统**；ShareHub 直接接入已在跑的 `ai-shop-pay` 与 `ai-shop-job`，不另起实例 |
| 首批系统 | `SHOP`（ai-shop 电商）· `SHAREHUB`（共享设备） |
| 不在本次范围 | 把两个服务搬出 ai-shop 仓库（ADR-024：暂留）· 框架重排（ADR-025 决定 5：暂缓）· 新支付通道的业务谈判 |
| 兼容底线 | **ai-shop 现有行为不回归**。所有新列带默认值 `SHOP`，存量数据与现有调用方不改也能跑 |

### 四个维度（不要混为一谈）

| 维度 | 含义 | 例 | 今天有没有 |
|---|---|---|---|
| **系统 system** | 哪个业务产品在用这个服务 | `SHOP` · `SHAREHUB` | ❌ 两个服务都没有 |
| **市场 market** | 国家 / 币种 / 时区 / 结算规则 | `CN` · `AE` | ✅ 支付有（`sys_market`）；任务不需要 |
| **平台 platform** | 终端与支付场景 | App · 小程序 · H5 · Web | ✅ 支付有（`pay_scene` / `pay_method`） |
| **目标 target** | 同一系统里被调度的进程 | `SHAREHUB` 单体 · `GATEWAY` 协议对接 | ✅ 任务有（`targets` 映射） |

「多系统」= 新增第一个维度；「多平台」= 让后三个维度在每个系统下**各自成立**（ShareHub 用 `AE` 市场、自己的通道、自己的目标进程）。

## 一、任务服务（`backend/job/`）

| # | 项 | 今天 | 要改成 | 为什么 |
|---|---|---|---|---|
| **MJ1** | `job_definition` | `uk_job_def_name(job_name)`，无系统列 | 加 `system VARCHAR(16) NOT NULL DEFAULT 'SHOP'`；唯一键改 `uk(system, job_name)` | 两个系统都会有 `outbox-dispatch` 这样的通用任务名，全局唯一必撞 |
| **MJ2** | `job_run` · `job_log` | 无系统列 | 同样加 `system`（不靠 join 反查） | 运营端列表、日志清理、失败告警都要按系统过滤；join 反查在清理大表时代价高 |
| **MJ3** | worker 配置 | `worker.targets: {PLATFORM: url}` + **一把** `worker.token` | 改为按系统分组：<br>`worker.systems.<SYS>.targets.<TARGET>.url`<br>`worker.systems.<SYS>.targets.<TARGET>.token` | 一个系统多个目标进程；**每个目标一把令牌**，泄露一把不波及其他系统 |
| **MJ4** | 声明同步 | 按 target 拉 `/internal/job/declarations` | 按 `(system, target)` 拉取并落 `system`；某系统不可达时**只把该系统的任务标 `missing`**，不影响其他系统 | 一个系统停机不该让另一个系统的任务定义被标记成失踪 |
| **MJ5** | 运营端接口 | `OpsJobController` 直读 job 库、无系统过滤 | 接口按**登录人所属系统**过滤（不是按请求参数）；ShareHub 运营台只取 `system=SHAREHUB` | 否则 ShareHub 运营能看到并触发 ai-shop 的任务 |
| **MJ6** | 配置前缀 | `shop.job.*` | 保留 `shop.job.*`（改名不值得，服务留在 ai-shop）；库名 `ai_shop_job` 保留 | 改前缀要动两边配置与部署脚本，收益只是名字好看 |
| **MJ7** | 目标侧构件 | 目标侧小类散在 `shop-base/job` 与 `shop-app` | 收成 `shop-job-target`（注册表 · `/internal/job/**` 端点 · ShedLock 装配 · 进程内模式），发布到 Nexus | ShareHub 的三个目标进程要装配同一套 |
| **MJ8** | 发布 | 不发布 | CI 发布 `shop-job-api` · `shop-job-target` · `shop-job`（可执行 jar） | ShareHub 要依赖前两个 |

**迁移**：一条 `ALTER` 加列（默认 `SHOP`）+ 一条改唯一键；存量数据不动。

## 二、支付服务（`backend/pay/`）

### 2.1 三个硬前提（不做完不许上多系统）

| # | 项 | 今天 | 要改成 | 不做会怎样 |
|---|---|---|---|---|
| **MP1** | **独立库** | `pay-svc` 连主库 `ai_shop`，Flyway 由主应用跑 | 自己的库 + 自己的 Flyway（`classpath:db/pay`）；主应用不再管 pay 的迁移 | **ShareHub 的支付与用户数据会落进 ai-shop 的业务库** —— 越权与合规上都不可接受 |
| **MP2** | **回调入口** | 在 `shop-core` 的 `ChannelPayCallbackController`（`/pay/callback/{channel}`） | 移进 `pay-svc`；路径带系统：`/pay/callback/{system}/{channel}`（或由商户号反查系统，二选一但要固定） | ShareHub 的支付回调会流经 ai-shop 的业务进程 |
| **MP3** | **收款 API** | 独立形态下 11 个远程 Port 是「调用即抛」的桩 | 收款 / 查单 / 退款等入口在 `pay-svc` 内可用 | ShareHub 根本付不了款 |

### 2.2 多系统改造

| # | 项 | 今天 | 要改成 | 为什么 |
|---|---|---|---|---|
| **MP4** | 核心表加系统列 | `stl_payment` · `stl_bill` · `stl_settle_*` · `stl_recon_*` · `stl_withdraw` · `pay_setting` · `pts_*` 都无系统列 | 一律加 `system VARCHAR(16) NOT NULL DEFAULT 'SHOP'`；唯一键与常用索引前置 `system` | 两系统的流水、账单、对账、结算必须分得开 |
| **MP5** | **通道凭据进库** | 在配置项里（`shop.pay.wechat.mchid/appid/private-key…`），一个进程一套 | 新表 `pay_channel_account(system, market, channel, mch_id, app_id, key_ref, enabled…)`，按 `(system, market, channel)` 取；**密钥本身不落库**，库里存引用（环境变量名 / KMS 键），进程启动时解析 | 一个进程要同时持有 ai-shop 的微信商户与 ShareHub 的 AE 通道商户；这是「多系统 + 多市场」的核心 |
| **MP6** | 业务字段泛化 | `stl_payment` 带 `order_no` / `sub_order_no` / `after_sale_no` / `entity_no`；另有 41 处对 ai-shop 业务口的反向引用（`MerchantQueryPort` 27 · `SettleSourcePort` 14） | 增加 `biz_type` + `biz_no` 作为通用关联；旧列保留供 ai-shop 过渡；反向引用泛化为 SPI，按系统装配，ShareHub 不用的能力不装配 | ShareHub 没有「电商订单」「商户」这些概念，实例里也没有对应数据 |
| **MP7** | 商户单号 | `out_trade_no` 全局生成 | 带系统前缀；唯一键含 `system` | 两个系统各自生成，不加前缀迟早相撞 |
| **MP8** | 内部接口带系统 | 无系统概念 | 请求带 `X-System`；**令牌决定系统**，过滤器解析后强制覆盖请求里的值；DAO 层按 `system` 过滤，不信任调用方传参 | 防止一个系统读写另一个系统的数据 |
| **MP9** | 对账与结算按系统 | 全局出账 | 按 `system` 分别下载账单、对账、出结算单与发票 | 两个系统的资金流完全不相干，混在一起无法核账 |
| **MP10** | 预授权族（ShareHub 必需） | 无 | 冻结 / 请款 / 撤销 / 到期处理；作为通道能力位（不支持的通道要能明确拒绝） | 免押借还的前提 |
| **MP11** | 首个 AE 通道 | N-Genius / Tap / PayTabs 仅预置未实现 | 选定一家并实现（含回调验签、退款、对账下载） | ShareHub 在阿联酋收款（需用户先定签约方） |
| **MP12** | 客户端构件 | `payclient` 22 个类在 `shop-app` 内 | 整理为 `pay-client` 独立模块，**不依赖任何 `shop-*`**，发布到 Nexus | ShareHub 只依赖这一个支付构件 |

**迁移**：MP1 是唯一不可轻易回退的一步（建库 + 搬数据 + 切连接串），建议单独一个窗口做，并保留回退脚本。

## 三、安全与隔离（两个服务统一）

| 规则 | 实现 | 验收用例 |
|---|---|---|
| 令牌即系统身份 | 每个系统一把内部令牌；过滤器解析出 `system` 后**覆盖**请求参数里的任何 `system` | 拿 `SHAREHUB` 令牌查 `SHOP` 的支付流水 → `404`（不是 403，不泄露存在性） |
| 数据层兜底 | DAO / Mapper 统一追加 `system = :current`，不依赖调用方 | 故意在 service 层漏传 `system`，查询仍只返回本系统数据 |
| 凭据隔离 | `pay_channel_account` 只按当前系统取；密钥引用解析失败即拒绝装配该通道 | `SHAREHUB` 的请求拿不到 `SHOP` 的微信商户号 |
| 运营隔离 | 任务与支付的运营接口按登录人所属系统过滤 | ShareHub 运营台的任务列表里没有任何 `SHOP` 的任务 |
| 回调隔离 | 回调路径 / 商户号能唯一确定系统；跨系统的回调直接拒绝 | 用 `SHOP` 的商户号向 `SHAREHUB` 的回调地址发通知 → 拒绝并留痕 |
| 审计 | 两个服务的关键操作日志带 `system` | 日志可按系统检索 |

|---|---|---|
| H1 | 实现三个目标进程的任务端点（装 `shop-job-target`）：`SHAREHUB`（单体）· `GATEWAY`（协议对接）· `PAY` 由服务自带 | MJ7 · MJ8 |

## 五、验收清单

**任务服务**

1. 同一个调度器里同时存在两个系统的任务，`job_name` 相同也不冲突；
2. ShareHub 的任务到点回调到 ShareHub 的目标进程，ai-shop 的任务不受影响；
3. 停掉 ShareHub 的目标进程，只有 `system=SHAREHUB` 的任务被标 `missing`；
4. ShareHub 运营台看不到任何 ai-shop 的任务；手动触发只能触发自己系统的；
5. ai-shop 现有任务测试（`JobRegistrySyncTest` 等）全绿。

**支付服务**

6. `pay-svc` 连的是自己的库，主应用不再跑 pay 的迁移；
7. 两个系统各自的通道凭据同时装配，互不可见；
8. ShareHub 的收款 / 预授权 / 请款 / 退款在通道沙箱闭环；
9. 回调按系统正确路由，跨系统回调被拒绝并留痕；
10. 两个系统的对账与结算分别出账，金额可核；
11. ai-shop 支付全量测试不回归，`known-pay-reverse-deps.txt` 只降不升。

## 六、批次与顺序

| 批 | 内容 | 谁 | 解锁 |
|---|---|---|---|
| **M0** | MJ1–MJ2（加系统列）· MJ3–MJ5（配置 / 同步 / 运营过滤）· MJ7–MJ8（目标件与发布） | ai-shop | ShareHub 的定时任务（[08](./08-落地路线.md) S4） |
| **M1** | MP1 独立库（单独窗口，可回退） | ai-shop | 后续全部支付改造 |
| **M2** | MP2–MP3 回调与收款入口进 pay-svc | ai-shop | ShareHub 能付款 |
| **M3** | MP4–MP9 系统维度 + 凭据进库 + 业务字段泛化 + 分系统对账 | ai-shop | 两系统共用一个支付服务 |
| **M4** | MP10 预授权族 · MP11 首个 AE 通道 · MP12 `pay-client` | ai-shop（需用户定签约方） | ShareHub 免押借还（S6） |

M0 与 M1 可并行（一个在 job、一个在 pay）。**M0 最小、解锁最快，建议先做。**
