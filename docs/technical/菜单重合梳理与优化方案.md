新菜单建好了，旧入口一个没撤。于是同一份数据现在有两个页面、两处要改。

`/operation/sites` 和 `/locations?tab=sites` 各改了一遍 —— 两个文件、两套写法、同一个 `saveSite`。

| 问题管理 | 运营管理 › 基础管理 | 系统设置 › 基础字典 | `listProblems` / `saveProblem` / `archiveProblem` |

| 对 | 保留 | 撤销 | 为什么留它 |
|---|---|---|---|
| 银行 / 问题 / 应用版本 | 系统设置 | 运营管理的 4 个页面文件 | 主语是系统字典，不是站点 |

叶子 114 → 107；`app/operation/` 下删 4 个页面目录，`app/locations` 与 `app/pricing` 各瘦一半。
「计费定价」现在只剩「差异化定价」一个 P2 叶子，已是空壳 —— 按第 3 步随 P1 整体撤销，
在替代品（收费方案的适用范围）建好前不删，那是目前唯一的差异化取价入口。

### B 类 · 名字撞车、职责不同 → **改名或换位，不要删**

| 撞车的几项 | 实际职责 | 问题 |

| 计费定价 › 活动 / 时段价 | **周期性倍率**（工作日 / 节假日 / 时段） | 同上 |

### C 类 · 有意的跨 section 深链 → **不是重合，别动**

| 叶子 | 指向 | 说明 |
|---|---|---|

## 二、方向：不是「二选一」，是逐项判「它到底属于谁」

判据一句话：**这一项的主语是什么。**

按这条判，「运营管理」今天装了四类东西，只有前两类是它的：

| 现有分组 | 主语 | 判定 |
|---|---|---|
| 场站管理（站点概览 / 站点管理 / 收费方案 / 预约调价） | 站点 | ✅ 留下 |
| 站点分成 / 分成方分成 | 站点 | ✅ 留下，但要改名点明是**报表** |
| 基础管理（应用版本 / 银行 / 问题） | 系统字典 | ❌ 还给系统设置 |
| 公告管理 | 触达内容 | ❌ 还给营销 |

> 这三项是照搬简电云的菜单形状搬过来的。而我们自己的约定（`nav.ts` 系统设置那段注释）
> 早就写过：对方把提现/预约/充电设置拆三个菜单、7 个支付渠道各占一个菜单，
> **我们合并成一页，少菜单噪音即「信息更清晰」**。这里等于把已经拒绝过的做法又请了回来。

反过来，「站点与点位」把两件不同的事捆在一起：

| 现有分组 | 主语 | 判定 |
|---|---|---|
| 场地资产（站点 / 点位 / 坪效） | 站点 | → 并入运营管理（点位已是站点详情的页签） |
| 场地方机构（场地方 / 合同 / Onboarding / 生命周期 / CRM） | **场地方这个机构** | → 独立成 L1 |

**为什么场地方要独立**：场地方与代理商是链条上对等的两类合作主体 ——
一个给地拿进场分成，一个出钱拿代理分润，站点上是两个正交归属（`venue_no` / `agent_no`）。
代理商已经是独立 L1，场地方却藏在「站点与点位」下面当一个分组，
这是目前菜单与领域模型最不对齐的一处。

## 三、优化后的结构

### 3.1 运营管理（主语：站点）

```
运营管理
├ 场站管理    站点概览 · 站点管理
├ 计费与调价  收费方案 · 预约调价 · 活动/时段价
└ 场站报表    站点分成情况 · 分成方分成情况 · 站点坪效
```

- 「站点管理」= 今天的 `/operation/sites`，它是旧页的**超集**：
  详情抽屉已有 8 个页签（基本信息 / 点位 / 机柜 / 合同 / 计费 / 分成 / 统计 / 操作记录），
  点位、合同、分成都能就地看，不必再跳菜单。
- 分成两项改名加「情况」二字，与财务的「分润规则」（配置）区分开。

### 3.2 场地方管理（新 L1，主语：场地方机构）

```
场地方管理
├ 机构档案  场地方 · 进场合同
├ 进件      门店 Onboarding · 门店生命周期
└ 拓展      BD 拓展 CRM
```

与「代理商管理」形成对称：两类合作主体各有自己的档案、合同/协议、生命周期。

### 3.3 代理商管理（结构不动，补两处字段）

```
代理商管理
├ 机构档案  代理商档案（+类型：代理商/城市合伙人） · 代理账号 · 设备·点位划拨
├ 机构收益  分润配置 · 代理收益结算 →/finance
└ 机构经营  代理绩效
```

只加「类型」字段（差距 A1），**不加「城市合伙人」菜单** —— 它是 `agt_agent` 上的一个枚举值，
分润/结算/提现/门户全套复用，单开菜单会让人以为是两套数据。

### 3.4 被撤销的 L1

| L1 | 去向 |
|---|---|
| 站点与点位 | 场地资产 → 运营管理；场地方机构 → 新的「场地方管理」 |
| 计费定价 | 计费模板 → 运营管理 › 收费方案（同一份数据）；活动/时段价 → 运营管理 › 计费与调价；**差异化定价整页下线**（内容并入收费方案的「适用范围」，见经营链条方案 P1） |

L1 数量：16 → 15（撤 2 加 1）。

### 3.5 品牌与设备类型（用户点名的两项）

沿用 [经营链条方案 §3.2](./经营链条方案-主体到分账.md) 的结论，这里不改：

| | 位置 | 理由 |
|---|---|---|
| **品牌管理** | 系统设置 › 基础字典（与银行、问题同级） | 是一等对象，但一个运营方通常只有一两个品牌，**低频维护**，不值一个 L1 |
| **设备类型** | **不给菜单** | `md_device_type` 是开发期登记（新增一种设备要同时写一个 SPI 实现），不是运营可配的。给它按钮等于邀请人去点一个点了会坏的东西 |

但两个页面的筛选、归档开关、空态文案都不一样，用户会以为是两份数据。

## 五、护栏建议

✅ **已加**（2026-09-23，`lib/design-tokens.test.ts`）：

> **同一个写操作 API（`save*` / `archive*` / `unarchive*` / `create*` / `update*` / `delete*` / `remove*`）
> 不允许被两个 `app/**/page.tsx` 同时调用。**

判据取写操作而不是 `list*`：同一份数据在两处**只读展示**是合理的（概览页、报表页），
但**两个地方都能改**必然出现「在哪个入口改的，决定别人看不看得见」。

这条如果当初就有，运营管理菜单建起来的那天就会红，而不是拖到有人去改站点表单、
在两个文件里各改一遍才暴露。落地时它当场抓出两处残留（`archiveSite` / `unarchiveSite`
的 mutation 在旧页删了表格后还留着），已一并清掉。

## 六、本方案没有回答的

| 问题 | 为什么留着 |
|---|---|
| 「站点概览」与「经营看板」要不要合 | 两者都是首页型聚合页，但前者按站点、后者按全局。合并要先定「运营人员每天第一眼看什么」，不是菜单问题 |
| 场地方管理独立后，AGENT 门户要不要对应加「我的场地方」 | 代理商看不看得到场地方合同，是数据权限问题（ADR-012），先定权限再定菜单 |
| 「站点坪效」归运营管理还是数据报表 | 它同时是场站运营的日常指标和一张分析报表。目前建议放运营管理（贴着站点），若报表体系成型再议 |
