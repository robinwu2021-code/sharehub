# 方案 · 业务时区可配置（管理员改）

> 2026-09-28 裁决：**业务时区取 UTC+4（阿联酋）**，并且**可配置** ——
> 在 ops-web 加时区设置，改动需管理员权限。
>
> 背景见 [`known-localdate-now.txt`](../../backend/known-localdate-now.txt) 与
> `BizClock` 类注释：生产服务器跑在 `Asia/Shanghai`，业务在阿联酋，
> 每天有 4 小时（迪拜 20:00–24:00，租借高峰）各模块对「今天」的答案不一致。

---

## 〇、先说清楚：这不是「换个配置项」

现在 `sharehub.biz-zone` 是 **`@Value` 注入的启动期常量**（默认 `Asia/Dubai`），
`BizClock` 在构造时 `ZoneId.of(zone)` 一次。改成运行时可配，会动到三件事：

1. **值从哪读** —— 启动期属性 → 运行时可改的存储；
2. **谁能改** —— 需要权限码与审计；
3. **改了之后已经落库的数据怎么算** —— 这是最容易被跳过、代价最大的一条。

第 3 条下面单列一节。**不先回答它就动手，等于给未来埋一个比现在更难查的坑。**

---

## 一、值从哪读：用 `sys_param`，不要新建表

仓库里已有运行时参数机制，直接用：

| | |
|---|---|
| 存储 | `sys_param`（`param_key` 是自然键，`SysParamServiceImpl` 走 `AbstractCrudService`）|
| 读取 | `SysParamPort#textOf(key, default)`（在 `sharehub-api`，跨域只读面）|
| 权限 | 已有 `system:param:read` / `system:param:update` |
| 端点 | 已有 `SysConfigController`（`/api/platform/sys-params`）|

**新增一个参数键**：

```
biz.timezone = Asia/Dubai        # IANA 时区 ID，默认值与现在的 @Value 一致
```

### `BizClock` 怎么改

```java
public LocalDate today() {
    return LocalDate.ofInstant(clock.instant(), zone());
}

/** 每次都问一次参数 —— 见下「为什么不缓存」。 */
public ZoneId zone() { ... }
```

- 构造器里的 `@Value("${sharehub.biz-zone:Asia/Dubai}")` **保留**，作为
  「参数表里没配」时的兜底，也是**启动期 fail-fast 的地方**（值非法则启动失败）；
- 运行时优先读 `SysParamPort.textOf("biz.timezone", 兜底值)`。

**为什么不缓存**：`sys_param` 的读是一次主键查询，而业务日期不在热路径上
（不是每笔订单都算）。加缓存就要回答「改完多久生效」，而那个问题没有好答案 ——
运营在界面上点了保存，期待的是立刻生效，不是「大约一分钟后」。
若实测有性能问题，再加**带失效事件**的缓存，不要加 TTL 缓存：
TTL 会制造「改了但还没生效」的窗口，而那正是时区缺陷最擅长藏身的地方。

⚠️ **非法值要在写入时拦**，不是在读取时兜底：
`ZoneId.of()` 抛异常时若在读取处吞掉回落默认值，界面上会显示「已保存」而实际没生效。
写入校验 → 400 + 人话（「不是合法的 IANA 时区 ID，如 `Asia/Dubai`」）。

---

## 二、谁能改：复用 `system:param:update`，不新发码

**不要为时区单发一个 `system:timezone:update`。** 理由：

- 它就是一条系统参数，与「订单最长时长」「OTP 有效期」同类；
- 多一个码就多一处要在 `iam_permission` / `UI_PERM_MAP` / 角色分配里同步，
  而 2026-09-28 刚踩过 `agent:apply:create` 漏登记导致**按钮对所有人不可见**、
  四天没人发现的坑（那次连超管都被挡，因为查映射在判通配之前）。

**审计**：`sys_param` 走 `AbstractCrudService`，`updated_by` 由审计切面回填。
但时区这条值得再进一步 —— 见 §四。

---

## 三、⚠️ 改了之后，已经落库的数据怎么算

**这是本方案的核心，不是附注。**

改时区**不会**、也**不应该**重算任何历史数据：

| 数据 | 存的是什么 | 改时区后 |
|---|---|---|
| `created_at` / `closed_at` / `endedAt` | 服务器时区的墙上时间 | **不动**。它们是「事情发生的那一刻」，时区只影响怎么解释它 |
| `rent_start_at` / `rent_end_at` | UTC 字符串 | **不动**。UTC 是绝对时刻，本来就与业务时区无关 |
| 合同 `start_at` / `end_at` | 人填的**业务日期** | **不动**。人填 2026-09-30 指的就是那天，不随时区漂移 |
| 分润 `period`（`YYYY-MM`）| 结算时按当时的业务时区定格 | **不重算**。历史归属月是既成事实，重算会让对过账的月份变动 |

**所以「改时区」的准确语义是：从此刻起，新算出来的业务日期按新时区。**
过去的记录保持它当时的口径。

这听起来像妥协，其实是唯一正确的选择 —— 另一种做法（追溯重算）会让
**已经发出去的结算单金额变化**，那是比时区偏差严重得多的问题。

### 由此推出两条硬要求

1. **改动必须留痕，且要记下生效时刻**。否则半年后查「这笔为什么记在 9 月」时，
   没有任何东西能回答「当时的业务时区是什么」。
   建议：`sys_param` 的审计列之外，另写一条 `iam_audit_log`
   （`action=BIZ_TIMEZONE_CHANGED`，带 from/to）。
2. **界面上要把这句话写给操作的人看**，而不是只写在这份文档里。
   保存前的确认弹窗应当明说：「改后只影响新产生的业务日期，已有记录不重算」。

## 四、ops-web 的落点

放在**系统设置 › 系统参数**下（已有页面），不新建菜单：

| 要素 | 做法 |
|---|---|
| 控件 | 下拉选，**不是自由文本**。候选列表从后端给（见下），避免手打出 `Asia/Dubay` |
| 候选 | 后端出一个 `GET /api/platform/sys-params/timezones`，返回常用集合 + 当前值。**不要在前端写死列表** —— 写死就会与后端的 `ZoneId` 可解析集合漂移 |
| 当前值展示 | 同时显示「现在业务日历是哪天、几点」，让人一眼看出选对没有 |
| 权限 | `system:param:update`；只读者见值不见保存按钮（用 `<ReadOnlyNotice>`）|
| 确认 | 二次确认弹窗，写明 §三 那句「不重算历史」|

⚠️ **前端也有一处要跟着改**：`ops-web/lib/nav.ts` 与测试里的
`ApiTestSupport.bizToday()` / `FixedBizClock` 目前把 `Asia/Dubai` **写死**。
改成可配后，这些地方要么跟着读配置，要么在注释里写明
「这是测试固定口径，与运行时配置无关」。后者更好 —— 测试要的是确定性，
不该跟着生产配置漂。`FixedBizClock` 的类注释已经有类似说明，照它写。

## 七、不做什么

- **不做按租户/按市场分时区**。ADR-011 说明本仓是单运营方（`tenant_id` 恒 `MAIN`），
  多市场是 L3 的事。现在做等于为一个还不存在的需求把每个取日期的地方都加一个参数。
- **不追溯重算历史业务日期**（§三）。
- **不把报表的 UTC 口径一起改**。`ReportConfig` 用 `Clock.systemUTC()` 有它的理由
  （`rent_start_at` 存的是 UTC 字符串）。概览与运维指标那 3 处待定口径
  （见台账）**是另一个决定**，与本方案分开做 —— 一起动会让「概览与报表对同一天
  给出不同数字」这类问题更难定位。
