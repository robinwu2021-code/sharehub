## 〇、一页结论

| 维度 | 第一阶段 |
|---|---|
| **端** | C 端 App（含小程序、H5）· 平台运营台 · 商家视图 · 管理看板；后三者同属 ops-web 一个工程，按角色渲染 |
| **部署单元** | 与 v4 相同：自有 2 个进程（业务单体 `sharehub-app`、协议对接 `sharehub-gateway`）+ 共用 2 个服务（ai-shop 支付、ai-shop 任务调度） |
| **逻辑服务** | 7 个：平台 · 交易 · 运维 · 财务 · 报表 · 集成 · 设备网关。前 6 个第一阶段都在单体内，只有设备网关独立进程 |
| **新增的逻辑服务** | **报表**（读模型 + 导出中心，承接 Excel/PDF 与 15 张报表）· **集成**（外部会计系统接缝，第一阶段只有契约、不编码） |
| **结算** | 只有**商家**一支：订单 → 分润 → 结算单 → **应付台账** → 付款登记；会计系统接入后改为读回 |
| **第一阶段新增的业务能力** | 应付台账 · 自动开票与 PDF · 采购收货入库 · 设备移动履历 · 报表与导出中心 · 逾期与最高收费监控 |
| **刻意不做** | Zoho 代码 · 多设备新类型接入 · OCPI 互联互通 · 独立商家 App |

## 一、输入与边界

### 1.1 已定的口径

| 来源 | 口径 | 对架构的影响 |
|---|---|---|
| ADR-032 | 第一阶段以**商家**为结算单元；商家 1:N 渠道侧**商户** | 结算链路只有一支受益方；应付台账按商家建 |
| ADR-032 | 会计系统架构预留、不编码 | 新增「集成」逻辑服务，只有契约；资金事件字段按会计同步要求设计 |
| ADR-020/025 | 单体优先；支付与任务共用 ai-shop 实例 | 部署单元不变 |
| ADR-026 | 唯一运营方，无租户 | 无平台超管端 |
| ADR-012 | 商家（代理商）不建独立前端 | 商家视图在 ops-web 内 |

### 1.2 本文对未决项的处理

对齐文档里 K1、K4–K8 仍待运营方裁决。架构上的原则是：**把差异做成规则或配置，不在代码里预设答案**。

| 未决项 | 本文的默认假设 | 架构上怎么留余地 |
|---|---|---|
| K1 项目范围 | 第一阶段只上充电宝；多设备抽象保留、不扩新类型；不评估迁移运营方旧系统 | 设备类型仍是数据维度，不影响本期 |
| K4 超时扣款模型 | 按运营方原文：**到最长时限触发最高收费**，订单进入「已扣款未归还」，之后归还只更新归还状态 | 触发条件做成计费规则（时间 / 金额 / 二者先到），现有「触顶买断」作为一种规则保留 |
| K5 最高收费与遗失费 | 拆成两个参数 | 计费方案增加独立的遗失费项，可为空 |
| K6 发票 | 首期做**每笔租赁自动出票据**；开票时点可配 | 开票规则引擎：触发事件 × 单据类型 × 时点 |
| K7 采购 | 纳入平台 | 采购与收货放在交易服务的资产库存模块 |
| K8 导出 | 后端导出 Excel 与 PDF | 报表服务的导出中心 |

假设被推翻时，受影响的只是对应模块的规则与界面，服务边界不变。

## 二、端

### 2.1 端的清单

| 端 | 使用者 | 载体与技术 | 接入前缀 | 会话 Realm | 现状 |
|---|---|---|---|---|---|
| **C 端** | 租赁客户 | uni-app 一套代码：Android/iOS App（离线打包，ADR-031）· 微信小程序 · H5 | `/mp/**` | CONSUMER `ctk_` | ✅ 借还主链路可用 |
| **平台运营台** | 管理员 · 运营 · 财务 · 客服 · BD（销售）· 管理层（只读） | ops-web：Next.js 静态导出 + React + Tailwind | `/api/**` 六前缀 | STAFF `stk_` | ✅ 98 菜单叶，部分为 mock |
| **商家视图** | 商家（运营主体）的账号 | ops-web 同一工程，按角色与数据范围渲染 | `/api/**` | AGENT `atk_`，数据范围强制为自己 | ◐ 代理门户 7 叶 |
| **管理看板** | 上述员工角色 | ops-web 首页，按角色给不同卡片组 | `/api/ops/dashboard` 等 | 同运营台 | ◐ 单一看板 |

## 三、后端服务（部署单元）

第一阶段**不新增进程**。新能力全部以模块形式进入 `sharehub-app`。

| 部署单元 | 包含的逻辑服务 | 端口 | 库 | 第一阶段变化 |
|---|---|---|---|---|
| `sharehub-app` | 平台 · 交易 · 运维 · 财务 · **报表** · **集成（仅契约）** | 8082 | `sharehub_core` · `sharehub_auth` · `sharehub_pii` | 新增两个逻辑服务的模块；会话切库实现后才能多副本 |
| `sharehub-gateway` | 设备网关 | 8091 | `sharehub_gw` | 接首家真实厂商驱动（v4 P1） |
| `ai-shop-pay`（共用） | 支付 | 8083 | 服务自有库，按 `system` 隔离 | 多系统改造、预授权、首个 AE 通道（v4 P2，跨仓） |
| `ai-shop-job`（共用） | 任务调度 | 无 | 服务自有库 | 接入后替换进程内调度（见下） |

**第一阶段的定时任务**（全部写成 `JobHandler`，由共用调度器回调，禁止 `@Scheduled`）：

| 任务 | 所在服务 | 频率 | 承接需求 |
|---|---|---|---|
| 最长时限扫描 → 触发最高收费 | 交易 | 每 5 分钟 | BIL-02 |
| 扣款失败重试（可配次数与间隔） | 交易 | 每 15 分钟 | BIL-05 |
| 封顶 / 临近时限提醒 | 交易 → 平台通知 | 每 15 分钟 | APP-04 |
| 合同到期提醒（提前量可配，默认 2 个月） | 运维告警 | 每日 | MER-07 |
| 账期结算单生成 | 财务 | 按账期 | SHR-05 |
| 票据补开（事件丢失兜底） | 财务 | 每小时 | INV-01 |
| 导出任务执行与过期清理 | 报表 | 队列触发 / 每日 | RPT-03 |
| Outbox 跨进程投递 | 公共 | 每 30 秒 | — |

**不在第一阶段链路上的工程**：仓库根目录的 `opskit/` 是孵化中的通用运营套件，不依赖本项目任何构件，第一阶段不接入。

## 四、逻辑服务与模块

### 4.1 七个逻辑服务

逻辑服务 = 单体里的一组 Maven 模块 = 将来可独立部署的微服务。划分依据沿用总纲：**按变化的原因拆，不按业务名词拆**。

| 逻辑服务 | Maven 模块 | 变化的原因 | 承接的需求域 |
|---|---|---|---|
| **platform 平台** | `sharehub-svc-platform` | 运营配置，按运营节奏变 | MER（商家、场地、合同）· SEC（权限、审计）· 通知 · 系统参数 |
| **trade 交易** | `sharehub-svc-core` | 借还主链路，要本地事务 | APP · RNT · BIL · MON · PAY 编排 · AST（资产库存采购） |
| **ops 运维** | `sharehub-svc-ops` | 异步处置，节奏与主链路无关 | 告警（含合同到期、逾期）· 工单 · 客服 |
| **finance 财务** | `sharehub-svc-finance` | 批处理与记账一致性；合规可能要求独立 | SHR · INV · 对账 · 应付台账 |
| **report 报表** 🆕 | 新建 `sharehub-svc-report` | 读多、跨域、查询重；不能拖慢交易库 | RPT 全部 · 各域的导出 |
| **integration 集成** 🆕 | 第一阶段是单体内的集成适配层 `sharehub-app/integration`（OpsKit 客户端已有，会计端口只放契约）；接入外部 SaaS 时拆出 | 跟着外部 SaaS 的接口、限流、凭据变 | ZOH 全部（预留） |
| **gateway 设备网关** | `sharehub-svc-gateway` + `sharehub-app-gateway` | 每接一家厂商变一次；长连接 | AST-09 在线、故障、可用数 |

### 4.2 各服务第一阶段的模块变化

**platform 平台**

| 模块 | 变化 | 承接 |
|---|---|---|
| 商家（运营主体） | 界面统一叫「商家」；补营业执照号、TRN 等结构化字段 | MER-01、INV-03 |
| 商户（渠道侧） | `pay_merchant`：商家 × 渠道 × 市场 → 子商户号、进件状态。第一阶段走平台代收时可延后 | ADR-029、ADR-032 |
| 合同 | 到期提醒提前量改为可配（日历月或天数） | MER-07、C12 |
| 协议与披露 | 租借协议版本化，C 端借出前取当前版本 | APP-03 |
| 税务设置 | 开票主体、地址、TRN、VAT 税率 | INV-03、C01 |

**trade 交易**

| 模块 | 变化 | 承接 |
|---|---|---|
| 计价 | 计费方案增加**最长时限**、**遗失费**两个独立参数；触发规则可配（时间 / 金额 / 先到者） | BIL-01、APP-06、K4、K5 |
| 订单 | 新增「已扣最高收费、未归还」状态；最高收费作为**独立事件**记录，不再占用归还时间列；归还状态与支付状态分列 | BIL-03/04/07 |
| 支付编排 | 支付状态补「待处理」「已退款」；记录支付方式；退款审批后真正出款 | PAY-01/02/04 |
| 防重 | 订单更新检查影响行数，失败即中止扣款；支付请求带唯一业务键 | BIL-06、D2、D3 |
| 资产 | 设备状态补「维修中」「损坏」「已撤出」并与「故障」区分 | AST-07 |
| **采购** 🆕 | 采购单、收货单；**确认收货才入库**，部分收货只入实收数；同一采购不重复入库 | AST-04/05/06 |
| **供应商** 🆕 | 采购供应商档案，与网关的「硬件厂商」分开 | AST-04 |
| **设备履历** 🆕 | 统一移动记录：日期、原位置、新位置、负责人、原因 | AST-08、MER-06 |
| 盘点 🆕 | 仓库盘点单与差异 | AST-10 |

**finance 财务**

| 模块 | 变化 | 承接 |
|---|---|---|
| 分润 | 第一阶段受益方只有商家；场地方分润规则保留、不进结算单 | SHR-01~03、ADR-032 |
| **应付台账** 🆕 | 商家 × 账期：应得、调整、已付、未结；「已付」来源经 `PayoutSource` 可切换 | SHR-04/05/06 |
| 结算 | 结算单确认后进入应付台账；付款登记关联结算单；提现申请校验余额 | SHR-05、D6 |
| **票据** 🆕 | 区分两类：**租赁票据**（给租赁客户，每笔自动）与**结算票据**（给商家）；开票规则引擎；贷项通知单；已开具不可改（修 D1） | INV-01~11 |
| **票据渲染** 🆕 | 模板化 PDF 生成，写对象存储，单张与批量 | INV-06/07 |
| 账务 | 内部复式账保持为第一阶段的账务来源；关闭或审批手工凭证 | SEC-03、ADR-032 |
| 对账 | 订单 ↔ 支付事件 ↔ 分录；补网关手续费与结算到账 | PAY-05/06 |

**report 报表**（新逻辑服务）

| 模块 | 内容 | 承接 |
|---|---|---|
| 读模型 | 订阅各域事件落宽表：租赁明细、支付、票据、分润应付、库存变动、设备履历；单体期允许 `ReportMappers` 直接 JOIN | RPT-R01~R15 |
| 报表目录 | 15 张报表的定义：维度、指标、筛选（日期区间、商家、设备、状态、供应商） | RPT-03 |
| **导出中心** | 异步导出任务：提交 → 排队 → 生成 Excel 或 PDF → 存对象存储 → 下载链接；按权限码控制谁能导出什么 | RPT-03、INV-08、K8 |
| 看板聚合 | 按角色的卡片数据 | RPT-01/02 |

**integration 集成**（新逻辑服务，第一阶段只有契约）：见 §七。

**ops 运维**：基本不变；新增两类告警来源：逾期租赁、扣款失败超过重试次数。

## 五、微服务形态

### 5.1 目标服务目录

双形态机制（ADR-017）不变：同一套代码，classpath 决定是单体还是微服务。下表是**可以独立部署**的完整目录，不是第一阶段要部署的数量。

| # | 微服务 | 库 schema | 对外前缀 | 发布的事件 | 订阅的事件 |
|---|---|---|---|---|---|
| 1 | platform | `pb_platform` | `/api/platform` `/api/auth` `/api/agent` | 商家变更、合同变更 | — |
| 2 | trade | `pb_trade` | `/mp/**` `/api/trade`（订单部分） | 订单已结算、最高收费已触发、收货入库、设备移动 | 支付事件、设备事件 |
| 3 | ops | `pb_ops` | `/api/ops` | 工单关闭 | 设备事件、订单异常、合同到期 |
| 4 | finance | `pb_fin` | `/api/trade`（财务部分） | 票据已开具、贷项通知单、结算单已确认、付款已登记 | 订单已结算、退款成功 |
| 5 | report 🆕 | `pb_report`（读模型） | `/api/ops/reports` 等 | — | 几乎全部 |
| 6 | integration 🆕 | `pb_intg` | 无对外前缀 | 外部付款已读回 | 票据、付款、结算、退款 |
| 7 | gateway | `sharehub_gw` | `/gw/**` `/ocpp/**` | 设备事件、指令结果 | — |
| 共用 | pay（ai-shop） | 服务自有 | `/pay/callback/**` | 支付事件 | — |
| 共用 | job（ai-shop） | 服务自有 | 无 | — | — |

总纲定的上限是 **7 个业务服务**。本文新增报表与集成后正好到上限；再加服务必须先回答「哪两个变化原因真的不同」。

![合理微服务：现在拆什么，将来按信号拆什么](./diagrams/22-microservice-split.svg)

拆分顺序、信号与前置条件的完整说明见 [服务端架构-模块与服务 §八](./服务端架构-模块与服务.md)。

### 5.2 第一阶段拆哪几个

| 服务 | 第一阶段 | 理由 |
|---|---|---|
| gateway | **独立进程** | v4 已定；厂商接入是唯一的线性膨胀点 |
| pay · job | **共用 ai-shop 实例** | ADR-025 |
| platform · trade · ops · finance · report · integration | **单体内模块** | 单运营方、未规模化；拆开只换来运维成本 |

### 5.3 拆分信号与顺序

| 顺序 | 服务 | 拆分信号 |
|---|---|---|
| 1 | integration | 会计系统真正接入时。外部 SaaS 有限流、超时、凭据轮换，故障不应拖累交易 |
| 2 | report | 报表或导出查询开始影响交易库的响应时间；或需要独立只读副本 |
| 3 | finance | 合规要求财务数据独立部署；或批处理窗口与交易高峰冲突 |
| 4 | ops | 告警事件量大到需要独立扩容 |
| — | platform · trade | 不预期拆；trade 是借还主链路，拆开就要分布式事务 |

拆分前的硬门槛（v4 已列，此处强调）：跨进程 traceparent 透传、Outbox 跨进程投递与消费去重、会话库实现、`arch-guard.py --strict` 进 CI。

## 六、关键链路（第一阶段）

### 6.1 借出、计费与最长时限

```
扫码 ─▶ trade 建单 + 计价快照（含最长时限、最高收费、遗失费）─▶ pay 预授权 ─▶ gateway 弹仓
                                                                         │
                                ┌────────────── 使用中，计费累计 ──────────────┤
                                ▼                                          ▼
                         设备报告插回                        job：最长时限扫描（按规则判定触发）
                                │                                          │
                     trade 判定归还 → 计价                    trade 记「最高收费事件」→ pay 请款
                                │                          订单 →「已扣最高收费、未归还」
                     pay 请款 → 订单已结算                               │
                                │                          之后若归还：只更新归还状态，不冲销
                                └────────────┬─────────────────────────┘
                                             ▼
                              事件：订单已结算 / 最高收费已触发
                                             │
                          finance 分润（商家）· 票据（按规则开具） · report 读模型
```

要点：

- 触发判定与扣款分两步：先写「最高收费事件」并把订单状态改掉，**更新影响行数为 1 才发起请款**（D2 的修法）；
- 请款带业务唯一键 `MAXCHARGE-<orderNo>`，支付侧按此幂等；
- 失败进入重试队列，重试次数与间隔可配，用尽后转运维告警与人工跟进。

### 6.2 商家结算与应付

```
订单已结算 ─▶ 分润记录（受益方 = 商家，比例快照）
                     │
           job：账期到 ─▶ 结算单（商家 × 账期）─▶ 财务确认 ─▶ 应付台账：应得 +
                                                            │
                    调整单（须审批）─────────────────────────▶ 应付台账：调整 ±
                                                            │
     第一阶段：财务在本系统登记付款（关联结算单、外部单号唯一）─▶ 应付台账：已付 +
     会计系统接入后：integration 读回付款 ─────────────────────▶ （同一入口，按来源切换）
                                                            │
                                                      未结 = 应得 + 调整 − 已付
```

商家在商家视图里看到同一份台账与对账单。

### 6.3 自动开票

```
事件（订单已结算 / 最高收费已触发 / 退款成功 / 结算单已确认）
        │
finance 开票规则引擎：事件类型 × 单据类型（税务发票 / 收据 / 贷项通知单 / 结算票据）× 时点
        │
生成票据号（规则可配）→ 写票据与行项目（VAT 税率、税额、租赁明细、支付信息）→ 状态 已开具（不可改）
        │
票据渲染 → PDF 存对象存储 → C 端「我的发票」可下载 · 运营台发票中心 · 事件：票据已开具
        │
更正只能开贷项通知单关联原票，不得改原票
```

### 6.4 采购收货入库

```
采购单（供应商、型号、订购数、单价、VAT、附件）─▶ 收货单（实收数、序列号清单）
        │                                                    │
        │                                   确认收货 ─▶ 设备建档，状态「库存可用」
        │                                                    │  同一收货单只能确认一次
        └── 未收数量 = 订购 − 累计实收（在途，不计库存）            ▼
                                                     设备履历：入库（日期、仓库、负责人）
```

既有设备走「期初登记」：无采购单，标记来源与依据，可附文件。

### 6.5 报表导出

```
运营台选报表与筛选 ─▶ report 建导出任务（权限码校验）─▶ job 执行
        ─▶ 读模型查询 ─▶ 生成 Excel / PDF ─▶ 对象存储 ─▶ 任务完成通知 ─▶ 下载（链接带有效期）
```

导出任务表记录谁、何时、导出了什么，满足审计要求（SEC-04）。

## 七、外部会计系统接缝（Zoho Books，预留）

第一阶段**不写任何 Zoho 代码**（ADR-032）。本节定义接入时的形态，用来约束现在要做的资金域设计。

### 7.1 接入时的结构

```
finance / trade ──资金事件──▶ sys_outbox ──▶ integration
                                               ├─ AccountingPort（接口）
                                               │    └─ ZohoAccountingPort（接入时实现）
                                               ├─ 映射：科目、税码、客户与供应商对应（接入时建表）
                                               ├─ 同步日志与重试、失败告警
                                               └─ 付款读回 ─▶ finance 应付台账（PayoutSource 读回实现）
```

### 7.2 现在就要遵守的三条约束

| 约束 | 落在哪 | 为什么 |
|---|---|---|
| 资金事件自带会计同步所需字段：业务键、发生时间、金额、币种、**税额与税率**、对方（商家或客户参考号）、关联原单 | 财务与交易的事件定义 | 接入时消费者不必回查业务库 |
| 应付台账的「已付」只经 `PayoutSource` 写入，外部单号唯一 | 财务应付台账 | 来源切换时不改表结构，读回天然幂等 |
| 每笔业务明细永久保留在本系统，不因汇总入账而丢失 | 交易与财务 | 原文 RQ-ZOH-08 |

### 7.3 接入时要事先确认的

科目与税码映射、同步方向与周期、付款关联键（对齐文档待确认 C14），以及内部账是否降级为运营子账（ADR-032 待确认 3）。

## 十一、风险与待确认

| 风险 | 缓解 |
|---|---|
| 报表读模型在单体期直接 JOIN 交易库，查询拖慢借还 | 导出一律异步；大查询走只读副本；出现信号即按 §5.3 拆 report |
| 应付台账与现有「提现」模型并存，口径打架 | 第一阶段以应付台账为唯一真值，提现单只作为付款登记的一种来源 |
| 两类票据混用一张表 | 结算票据沿用 `fin_invoice`，租赁票据新建，界面分 Tab |
| 共用支付服务排期在 ai-shop | 本期功能全部经 `PaymentPort`，桩实现可先联调；资金类验收等 P2 完成 |
| 「商家」与代码中的 `agent` 命名不一致，新人误读 | 本文 §九 与 ADR-032 §1.3 写明映射；S1 改名窗口统一 |

**待确认**（除对齐文档 K1、K4–K8 与整理稿 🔴 项外，本文新增）：

1. 报表与集成两个新逻辑服务是否接受（达到总纲 7 个上限）；
2. 场地方分成第一阶段由谁承担（ADR-032 待确认 1）；
3. 商家收款走平台代收还是渠道分账（ADR-032 待确认 2）；
4. 对象存储的区域与驻留要求（票据 PDF、导出文件含个人数据，受 PDPL 约束）。
