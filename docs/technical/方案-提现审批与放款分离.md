# 方案 · 提现的审批与放款分离（管理员配）

> 2026-09-28 裁决：**审批与放款是两个动作**，按权限与流程配置，由管理员配置 ——
> 不硬拦「同一人既审批又放款」。

---

## 〇、先说一件好消息：一半已经做完了

查证后，现状比预想好得多：

| 已有 | 证据 |
|---|---|
| **两个动作是两个端点** | `POST /withdrawals/{no}/audit` · `POST /withdrawals/{no}/pay` |
| **两个动作判两个码** | `finance:withdrawal:audit` · `finance:withdrawal:pay` |
| **两个人分列存** | `auditor_no`/`auditor_name` 与 `payer_no`/`payer_name` |
| **都由服务端按会话回填，不信前端** | 两处都走 `SecurityUtils.currentUser()`；实体注释写死了这条 |

`StlWithdrawal` 上那句注释说得很准：

> `payerNo` —— 登记回执的人。与 `auditorNo` 分开存，**才查得出**「审批人是否自己给自己放款」。

**「才查得出」= 能事后查，但没有拦。** 本方案要补的就是这最后一步 ——
而且按裁决，补的不是「硬拦」，是**一个管理员能配的开关**。

---

## 一、为什么不硬拦

这条在本仓库已经栽过一次，值得引用：

> 合同双人复核的两道闸（不能自批、会签人≠审批人）写得全对，
> 但生产只有一个账号时**任何合同都进不了 ACTIVE**；
> 而这类故障只能靠改库自救。
> —— `powerbank-staff-credential-login` 记下的教训

提现比合同更要命：拦错了的后果是**钱打不出去**。而小团队只有一个财务是常态。

所以：**默认拦，但可配**。让部署方自己决定，而不是替他们决定。

---

## 二、配什么：一个参数，三态

新增系统参数（同 `sys_param` 机制，与时区方案共用）：

```
finance.withdrawal.separation = REQUIRE      # 默认
```

| 值 | 语义 | 适用 |
|---|---|---|
| `REQUIRE` | 放款人**不得**是审批人。违反 → 409 + 人话 | 有两个及以上财务（默认，合规口径） |
| `WARN` | 允许，但写一条 WARN 日志 + 在单据上标记「同一人经办」 | 过渡期：知道不合规，但暂时只有一个人 |
| `OFF` | 不判 | 单人运营，且明确接受 |

**为什么不是布尔开关**：布尔只有「拦」和「不拦」，而真实处境常是第三种 ——
**知道它不合规，但现在没有第二个人，同时希望这件事被记录下来**。
只给两态会逼人选 `OFF`，于是那条信息永远丢失。`WARN` 让「谁在什么时候自己给自己放的款」
留在日志与单据上，将来补人手时能查回来。

---

## 三、判在哪：`pay()` 里，不是 `audit()` 里

```java
// WithdrawalServiceImpl#pay，在回填 payerNo 之后、更新之前
String me = currentUserNo();
if (me != null && me.equals(e.getAuditorNo())) {
    switch (separationMode()) {
        case REQUIRE -> throw BizException.conflict("error.withdrawal.self_payout", withdrawNo);
        case WARN -> {
            log.warn("同一人既审批又放款 withdrawNo={} operator={} —— 当前配置为 WARN，已放行", withdrawNo, me);
            e.setSameOperator(1);           // 单据上标记，见 §四
        }
        case OFF -> { }
    }
}
```

**判在 `pay()` 而不是 `audit()`**：审批发生在前，那时还不知道谁会去放款。
放在 `audit()` 里判等于要求「审批时就锁定放款人」，那是另一种流程，不是本裁决的意思。

⚠️ **比的是 `userNo` 不是 `username`**：后者是展示名，可能重名、可能改。
实体上两个都存了，判定只能用前者。

## 四、单据上要看得见

只写日志不够 —— 日志不会出现在对账单和审计导出里。

`stl_withdrawal` 加一列：

```sql
same_operator TINYINT(1) NOT NULL DEFAULT 0
  COMMENT '审批人与放款人是否同一人（1=是）；REQUIRE 模式下不会出现 1'
```

- 列表与详情出参带上它，运营端用 `<StatusBadge>` 标一个 warning 调的「同一人经办」；
- 财务导出/对账单带上这一列。

**为什么要落列而不是每次比一下**：`auditor_no` 与 `payer_no` 将来可能被归档清理，
而「当时是不是同一人」是个**事实**，该在发生那一刻定格 ——
与分润 `period` 按结算时刻定格是同一个道理（那处刚因为用「今天」而错过一次，见
`RentOrderServiceImpl#publishSettled` 的注释）。

## 五、ops-web 的落点

**配置**放在系统设置 › 系统参数（与时区同页，同 `system:param:update`）：
三选一 + 每一档的后果说明，不要只给一个开关名。

**单据**：提现列表与详情加「经办」信息 —— 审批人 / 放款人两栏并排。
现在详情里只有审批人，放款人要翻数据库才看得到，而这恰恰是这条规则的观察面。

## 六、卡口

| 卡口 | 守什么 | 负对照 |
|---|---|---|
| `REQUIRE` 下同一人放款 → 409 | 默认口径真的拦得住 | 把判定去掉 → 变绿即失效 |
| `WARN` 下放行且 `same_operator=1` | 允许不等于不留痕 | 去掉落列 → 断言 1 的那条红 |
| `OFF` 下放行且 `same_operator` 仍为 1 | **关掉的是拦截，不是记录** | 同上 |
| 两个不同的人 → 三种配置下都放行且 `same_operator=0` | 反向断言，防止把判定写反 | 把 `equals` 改成 `!equals` → 红 |

最后一条容易被省掉，但正是它防住「判反了还全绿」——
今天在 `LocalCouponUse` 那条用例上就靠反向断言才分清「过期」与「最后一天仍可用」。

⚠️ 这四条用例都要**能在任何时刻跑**，不依赖当前有几个员工账号。
用 `jdbc` 直接造两个不同 `userNo` 的会话，别依赖种子数据里恰好有两个财务。

## 八、不做什么

- **不做「审批时指定放款人」**。那是另一种流程（指派制），本裁决说的是
  「两个动作、按权限配」，不是「审批人决定谁放款」。
- **不把这条推广到别的审批流**。合同的四眼、代理入驻的四眼各有各的处境
  （合同那两道闸是硬拦且已生效）。统一成一套「审批引擎」的提案在
  2026-09-26 评估过并**否决**了 —— 领域各自的门禁配不进一个引擎里。
- **不改 `audit()`**。它现在的四眼（审批人 ≠ 申请人）在提现这条路上**天然成立**：
  申请人是代理/场地方（`applicantNo`，运营端无创建入口），审批人是员工，
  两个身份体系不会相等。不需要也不该加判定。
