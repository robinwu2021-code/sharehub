> 状态：活文档 · 2026-07-12 · 以**代码现状**为准（非计划）
> 配套：[代码结构](./代码结构.md) · [分层设计 TDD](./TDD-backend-layered-design.md)（每层类/方法设计）· [实现状态总表](./实现状态总表.md)（功能进度）

## 一、三层职责契约（不可越界）

| 层 | 职责 | 禁止 |
|---|---|---|
| **Controller**（薄） | 路由映射；`@PreAuthorize("@perm.can('码')")` 授权；`@Valid` 校验；调 Service 编排；返 `ApiResult/PageData`（`ApiResponseWrapper` 自动包裹） | 不写业务；不 `stream/selectPage/new Entity`；不判数据范围 |
| **Service**（`interface`+`impl`） | 全部业务规则；状态机；经 `SecurityUtils/StaffContext/ConsumerContext` 取**上下文**（谁/租户/数据范围/属主）；发领域事件；实体↔DTO | 不碰 HTTP/`HttpServletRequest`；不判**功能**权限；不写 `SecurityContextHolder` |
| **Mapper**（`BaseMapper<E>`） | MyBatis-Plus 单表 CRUD；`LambdaQueryWrapper` 组合查询；`DataScopeHandler` 横切自动拼数据范围条件 | 不写业务分支；跨表聚合走 Service 组合或 XML |

授权只在 Controller；数据范围是 MyBatis 横切拦截器（Service 零 `where agent_no`）；上下文经门面工具，三层都不直连 Spring Security。

## 三、梳理发现（三个待收敛项）

1. **Service 形态不统一**：`agent/dev/wo` 用 `interface + impl`（可测、可替换、符合分层设计 §2），但 `loc/LocService` 与 `ConsumerAuthService` 是**具体类**。→ 收敛：统一抽 `interface + impl`（loc 是早期模板，回填时一并规整）。

2. **`OpsController` 跨域聚合**：一个 controller 同时承 loc(场所)+dev(设备)+wo(工单)+dashboard 四组端点。前三组已薄化转对应 Service（正确的聚合门面）；但 **dashboard 仍直连 `SeedData`**。→ 收敛：抽 `DashboardService`（跨域统计聚合），OpsController 彻底薄化。端点归属可保持不变（对前端 `/api/ops/*` 契约无影响）。

3. **五处 Controller 仍直连内存（🟡），待补三层**：`trade`(最大，含订单/计费/支付/分账/结算/提现/账本)、`platform/iam`(员工/角色落库→替换静态 RolePerms)、`gateway/gw`(厂商/驱动配置)、`user`(运营端用户/优惠券/风控)、`ops` dashboard。均按 loc/agt/dev/wo 已验证的"四件套"（entity/mapper/service+impl/controller 薄化 + seeder 幂等落库 + 独立状态机）复制。

## 四、收敛顺序（依赖驱动）

`trade`（C端借还闭环最大缺口，ord 状态机+price+pay 端口） → `platform/iam`（角色落库，鉴权唯一权威从静态转 DB） → `gateway/gw`（厂商/KMS 占位） → `user`（运营端用户/风控） → `dashboard`（依赖各域聚合，放最后）。每域完成的 DoD 见 [分层设计 §五](./TDD-backend-layered-design.md)；完成后回填 [实现状态总表](./实现状态总表.md)。
