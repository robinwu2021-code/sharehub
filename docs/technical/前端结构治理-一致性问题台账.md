## 三、API 层（拆 `lib/api/*` 发现，4 项）

> 契约一致性测试结果：**mock/http 双侧 161 个方法名完全对齐，零漏实现、零重复、零签名不一致**。
> 这次是「测试通过」而非「测试抓虫」，但锚数组从此把这个不变量固定住了——后续任何一侧漏实现会当场红。
>
> 方法按域分布：system 34 · device 14 · location 14 · order 14 · user 14 · marketing 14 · finance 12 · agent 8 · org 8 · alarm 7 · workorder 6 · pricing 6 · report 5 · cs 3 · dashboard 2 = **161**

| # | 问题 | 严重度 | 决策 |
|---|---|:---:|---|
| A1 | ⚠️ **同一订单域被切成两个后端前缀**：订单主链路 `/api/trade/**`，而押金/投诉/退款在 `/api/order/**` | **高** | **后端定稿前必须统一**。像是两个 agent 各选前缀。倾向统一到 `/api/trade/**`（与后端已有 `trade` 域模块名一致），`/api/order/**` 全部迁移 |
| A2 | ⚠️ **系统设置前缀双轨**：老字典类在 `/api/platform/**`，B2/B3/B5 新增 8 项在 `/api/system/**`，同属「系统设置」菜单 | **高** | 同上，**后端定稿前统一**。倾向 `/api/system/**`（语义更准，`platform` 是历史包袱） |
| A3 | **跨域挂靠 3 处**：`listConsumerSegments`(user 域)→`/api/report/**` · `listRechargeOrders`(finance 域)→`/api/user/**` · `listAdSlots`(marketing 域)→`/api/ops/**` | 中 | 这 3 处**挂靠是对的**（按数据归属而非菜单归属选前缀），但要在契约里加注释说明理由，避免后人"顺手改回去" |
| A4 | `saveVendor` 是 31 个 `save*` 里唯一 `vendorCode` 必填（非可选）的，签名风格不一致 | 低 | 统一为可选 + 运行时校验，与其余 save 一致 |
| A5 | `ReservationQ` 与 `WoQ` 结构等价已合并为 `StatusTypeQ`，但两者 `type` 语义不同（工单类型 vs 预约取宝/还位）| 低 | 保持合并。**但若预约 type 将来收窄为字面量联合，必须拆回去**——已在 query.ts 注释标注 |

### ⚠️ 端点前缀问题为什么必须在后端开工前解决

按既定路线（前端全量完成 → 再整体开发后端），**这 161 个方法的 http 端点就是后端要实现的接口清单**。
现在 `/api/trade` 与 `/api/order`、`/api/platform` 与 `/api/system` 双轨并存，后端照着建会直接把混乱固化成线上契约。
**A1/A2 必须在后端阶段开工前定稿**，且改动只在 `lib/api/https/*.ts`（页面零感知），成本极低。
