> 状态：**设计定稿，未重构**（2026-07-30）

## 一、Maven 结构

```
sharehub-parent/                        pom 聚合 + 依赖版本收敛 + enforcer 规则
├─ sharehub-common/                     Result · 分页 · 异常 · 受信头 · 数据范围 · 事件总线抽象 · BizKey
│
├─ sharehub-api-platform/               ┐
├─ sharehub-api-core/                   │ 只有 接口 + DTO + 事件类
├─ sharehub-api-gateway/                │ 谁都能依赖，自己谁都不依赖（除 common）
├─ sharehub-api-ops/                    │
├─ sharehub-api-finance/                ┘
│
├─ sharehub-svc-platform/               ┐
├─ sharehub-svc-core/                   │ 业务实现（jar，无 main，不可独立启动）
├─ sharehub-svc-gateway/                │ 依赖 common + 任意 api-*
├─ sharehub-svc-ops/                    │ **不许依赖任何 svc-***
├─ sharehub-svc-finance/                ┘
│
├─ sharehub-app-mono/                   单体：聚合 5 个 svc（**默认交付物**）
├─ sharehub-app-platform/               ┐
├─ sharehub-app-core/                   │ 微服务：各含 1 个 svc + 他人 api-*
├─ sharehub-app-gateway/                │ 只有 main + 配置 + 装配，无业务代码
├─ sharehub-app-ops/                    │
└─ sharehub-app-finance/                ┘
```

**16 个 Maven 模块**。看起来多，但 `api-*` 与 `app-*` 都很薄（前者只有接口，后者只有启动类）。

### 依赖规则（enforcer 卡死，违反即编译失败）

| 规则 | 理由 |
|---|---|
| `api-*` 只能依赖 `common` | api 依赖 svc 会形成环，且拆分时把实现拖进调用方 |
| `svc-X` 只能依赖 `common` + 任意 `api-*` | **`svc-X` 依赖 `svc-Y` 就是拆不动的根源** |
| `app-*` 不含业务代码 | 保证「换个 app 就换形态」 |
| 第三方依赖版本只在 parent 声明 | 5 个服务版本漂移会在拆分后爆发 |

前两条是 ADR-017「四条纪律」的第 3 条（只经接口调用）的**编译期落实**。
纪律靠自觉守不住，靠 enforcer 才守得住。

## 三、跨服务调用

### 接口定义（`api-core`）

```java
public interface DeviceQueryPort {
    CabinetView cabinet(String cabinetNo);
    List<SlotView> slots(String cabinetNo);
}
```

### 本地实现（`svc-core`，单体与 core 服务里都存在）

```java
@Service
class LocalDeviceQuery implements DeviceQueryPort { /* 直接调 mapper */ }
```

### 远程实现（`api-core/remote`，仅当本地实现不在 classpath 时装配）

```java
@ConditionalOnMissingBean(DeviceQueryPort.class)
@Service
class RemoteDeviceQuery implements DeviceQueryPort { /* HTTP */ }
```

**classpath 决定形态，配置只补地址**：

```yaml
sharehub:
  deploy:
    mode: mono            # mono | micro（仅用于日志与健康检查自述，不影响装配）
    remotes:
      core: http://svc-core:8080
      platform: http://svc-platform:8080
```

装配由 `@ConditionalOnMissingBean` 决定而非读 `mode` —— **配置写错不会导致装配错误**，
最坏是地址缺失时启动即失败（fail-fast），而不是运行到一半才发现调错了对象。

### 调用方无感

```java
@Service
public class WorkOrderService {
    private final DeviceQueryPort devices;   // 单体=方法调用，微服务=HTTP，代码相同
}
```

## 四、事件

```java
// common/event
public interface DomainEventBus { void publish(DomainEvent e); }

// svc-core：与业务同事务写 outbox
@Transactional
public void settle(String orderNo) {
    orderMapper.updateById(order);
    eventBus.publish(new OrderSettledEvent(orderNo, amount, currency, agentNo, siteNo, deviceType));
}
```

- **单体**：`MonoEventBus` 写 `sys_outbox` + 事务提交后转 `ApplicationEventPublisher`；
- **微服务**：`MqEventBus` 写 `sys_outbox`，独立轮询器投递到 MQ。

**两种形态都写 outbox** —— 它是拆分的前置条件，不是拆分时才加。
「落库」与「发消息」不原子的后果是：订单结算了但分润事件丢了，账永远对不上。

**事件必须自带消费方所需的全部字段**（上例带了 `agentNo`/`siteNo`/`deviceType`），
否则消费方要回调查询 —— 那等于把同步调用藏在事件里，拆分后依然是强耦合。

### 双形态实证（2026-07-30）

`sharehub-app-gateway` **独立启动成功**（6.6 秒），`/actuator/health` 返回 401
—— 不是连接失败而是被安全链拒绝，说明进程真在服务。同时单体形态 104 测试全绿。
**「一套代码两种部署」从设计变成了可运行的事实。**

启动过程暴露了三处「单体里被掩盖、微服务下才现形」的装配问题，逐一记下：

| 问题 | 为什么单体没事 | 修法 |
|---|---|---|
| `auditMetaObjectHandler` 与 neargo 自动配置**同名 bean 冲突** | 单体 `application.yml` 排除了三个 neargo autoconfig | 每个 `app-*` 都要重复这段排除 |
| Mapper 扫不到 | 单体 `@MapperScan("ai.neargo.sharehub")` 一网打尽 | **必须限定到本服务的包** —— 照抄单体会扫到别的服务的 mapper，拆库后运行期报表不存在 |
| `SysOutboxMapper` 扫不到 | 同上 | outbox 是基础设施，每个 app 都要显式加 `common.event.mapper` |

**这三处都不是编译期能发现的** —— 只有真正启动微服务形态才会暴露。
这就是为什么 S4 必须做到「能启动」而不是「能编译」。

⚠️ 第一处正是 ADR-017 §七开放问题 1（「app-mono 与 app-* 如何避免两套配置」）所指，
应抽成共享的 `application-shared.yml` 片段各自 import，当前是复制。

### Port 远程实现（2026-07-30）

三个 Port 的 HTTP 实现已落地，**跨进程调用链路打通**：
`RemoteProperties`（地址配置）· `RemoteCaller`（拼址 + 拆 `Result` 信封 + 统一失败语义）·
`RemotePorts`（三个远程实现）· 各 svc 的 `/internal/**` 服务端。

**一个决定正确性的实现细节**：远程实现放在 `@AutoConfiguration` 里，
**不是**给它们打 `@Component`。`@ConditionalOnMissingBean` 作用在被组件扫描的
`@Component` 上是**不可靠的** —— 条件在该类被扫到的那一刻求值，而扫描顺序无保证。
若远程实现恰好先被扫到，**单体形态会静默走 HTTP**：功能正常、测试全绿、没有任何报错，
只是每次调用绕一圈网络。自动配置在全部用户 bean 之后处理，条件判断才确定。

`PortWiringTest` 锁死这个不变式（单体下三个 Port 必须是 `Local*`）——
**这类错误不会自己暴露，只能靠断言锁住**。

#### 凭证透传：传 token，不传身份声明

跨服务调用的身份传递有两种做法，**选错一种就把安全模型毁了**：

| 做法 | 后果 |
|---|---|
| 传 `X-User-Id` / `X-Roles` | **能访问 `/internal/**` 的任何人可冒充任意身份** —— 与本项目「只认 token 反查权限，绝不信客户端 X-Roles」的红线（`StaffTokenAuthFilter`）直接冲突 |
| **传原始 `Bearer` token** ✅ | 对端用自己的 `TokenStore` 反查，得到同一个 `LoginUser` 与 `DataScopeSpec`。**权限判定始终发生在持有 TokenStore 的那一侧**，与单体形态语义完全一致 |

实现：`CallContext`（ThreadLocal 存原始 token —— `SecurityContext` 里只有解析后的
`LoginUser`，token 本身已经不在了）+ `StaffTokenAuthFilter` 写入/清理 + `RemoteCaller` 附加请求头。

`CallContextTest` 锁住两条：**token 被透传** · **请求结束不残留**。
后者防的是最危险的一类 bug —— 线程池复用下上一个请求的 token 泄露给下一个，
表现为「偶发地以别人的身份执行」，与并发和调度相关，几乎不可复现。

**ThreadLocal 的边界是有意的**：异步线程（`@Async`、事件监听、定时任务）拿不到这个值。
后台任务没有「调用方身份」，应当显式声明以什么身份运行，而不是悄悄继承某个恰好触发它的用户。

**剩余局限**：
- **后台任务无凭证** —— 对账/投递器调 `/internal` 时不带 token，应由部署层用服务账号兜底；
  依赖会话的 Port（如 `existsInScope`）不应出现在后台任务里；
- **无重试与熔断** —— 跨进程调用会失败，当前直接抛异常。

### 解开 seed 阻塞的那一步：seeder 是装配，不是业务实现

`SeedData` 一度挡住 `agent`/`loc`/`wo` 三个包的迁移。试过的思路里，
**把种子数据拆散到各域**是错的（285 行里共享着 `p()`/`REGIONS`/`VENUE_NAMES` 等常量，硬拆会大量重复），
**改 Flyway 灌入**也是错的（那会让演示数据进入所有环境，包括生产）。

正确答案是换个角度问「seeder 属于哪一层」：它依赖全局单例 + 各域实体，
本质是**跨域的启动期装配** —— 按 ADR-017「app-* 持有启动类+配置+装配」，
它本就该留在 app。5 个 seeder 全部上提到 `seed/domain/` 后，
svc 里不再有任何 seeder，`SeedData` 不必被拆散，三个包的阻塞同时解开。

**卡在「怎么拆这个依赖」时，先问「它属于哪一层」往往能绕开整个问题。**

### `agent`/`loc` 的迁移过程（已完成）

它们本属 platform 服务，但有两处**不能靠搬文件解决**的依赖：

| 阻塞 | 性质 | 正确解法 |
|---|---|---|
| `seed.SeedData` | 骨架期的内存种子数据 | **先修了更严重的问题**（见下）；包依赖本身待 `agent`/`loc` 迁移时一并清 |
| ~~`report.ReportService`~~ | ✅ **已清**：`SiteAnalysisService` 是**读模型不是 loc 的领域概念**（其实现本就委托报表域以保证口径唯一），已连同 `SiteAnalysis` DTO 迁入 `report` —— **归位而非解耦**，loc→report 依赖随之消失 |

### ⚠️ 清理 seed 依赖时发现的上线事故隐患（2026-07-30 已修）

追查 `SeedData` 的包依赖时发现：**5 个 `*Seeder` 全部没有任何环境门禁**。

它们是 `CommandLineRunner`，逻辑是「表为空则灌入」—— 意味着
**生产环境首次上线会被写入 12 个假代理商、20 个假站点、演示订单与工单**。
而且因为幂等（有数据即跳过），灌入后既不会被覆盖，也不会有任何提示。

这不是拆分问题，是上线事故。已加 `@ConditionalOnProperty(name = "sharehub.seed.enabled", havingValue = "true")`
**默认关闭**，开发环境在 `application.yml` 显式开启。已做反向对照：关掉后 seeder 确实不装配。

**这个发现的价值高于本轮的模块拆分** —— 它是追查包依赖时顺带撞见的，
说明「为什么这个包依赖那个包」这类问题值得追到底，答案常常不在依赖本身。

**svc-finance 的拆出是对 ADR-018 的结构性坐实**：它的依赖里**没有 svc-core** ——
资金侧只 join `ord_order` 共性主表、不碰任何 `ord_*_ext` 扩展表。
这不是巧合，是「新增设备类型资金域一行不改」成立的证据；做不到就说明共性列没抽对。

**包正名**：`trade.finance` → 顶层 `finance`，避免与 svc-core 的 `trade` 形成跨 jar 分裂包。
`user.cs`(17 类) 与 `dev.alarm`(16 类) 待拆 ops 时同样处理。

**先拆 gateway 是有意的**：它是设备类型与供应商增多时唯一线性膨胀的部分（ADR-018），
也是五个服务里最小的一个 —— **拿它验证拆分模式，失败代价最小，成功则其余四个是机械重复**。

验证到的两件事：
1. **Spring 跨模块装配正常** —— 组件扫描、MyBatis mapper、驱动 SPI 全部跨 jar 工作；
2. **`app` 聚合 `svc` 的形态成立** —— 这正是「换个 app 就换形态」的落点，svc 模块本身一行不改。

踩到一个坑：**`provided` 作用域不传递**，lombok 要在每个 svc 模块自行声明。

**`api` 暂为一个模块而非设计里的 5 个**：接口总共 6 个文件，分五个模块的收益抵不过 pom 维护成本。
等接口数量上来、或出现「只想依赖某一个服务的接口」的真实需求时再拆 —— 已写进该模块的 pom 描述。

**未做**：其余 4 个 svc（platform/core/ops/finance）· 6 个 `app-*` 启动模块 ·
`portal` 的 255 处按端点前缀分派。

**S2 与 ADR-014 更名（`ai.neargo.powerbank` → `ai.neargo.sharehub`）同批做** ——
两者都是大范围机械移动，分两次做等于承受两次冲突合并的痛苦。

### S3 实测结果（2026-07-30）

`split-readiness.py` 与 `arch-guard.py` 的 G3 查的**不是同一件事**：
G3 只查「注入了别的服务的 ServiceImpl/Mapper」（**纪律**），
本脚本查**任何跨服务 import**（**能不能编译**）—— 真拆 Maven 模块时，
`svc-core` 里一行 `import ...gw.entity.DevHeartbeat` 就编译不过。
**G3 报 0 不代表能拆，split-readiness 报 0 才代表能拆。**

首跑 2 处，均已修复：

| 问题 | 根因 | 修法 |
|---|---|---|
| `dev.entity.DevHeartbeat` / `HeartbeatMapper` | **包归属与表归属不一致** —— 心跳表归 device-gateway（ADR-018：南向产物），实体却放在 core 的 `dev` 包 | 迁到 `gw/` 包 |
| `MonitorService.heartbeats()` 返回 `List<DevHeartbeat>` | **Port 抽了但接口签名还在用网关实体** —— 等于 Port 白抽 | 签名改用 `api` 层的窄 DTO `HeartbeatRecord` |

第二条尤其值得记：抽 Port 时只改了实现、没改接口签名，`arch-guard` 的 G3 因为查的是注入而非签名，**报了绿**。
两个卡口查的维度不同，缺一不可。

**⚠️ 但业务层就绪 ≠ 可以拆**：`portal`（控制器层）有 **255 处引用跨 5 个服务**，
`report` 有 5 处跨 4 个服务。它们在 S4 拆 `app-*` 时按端点前缀分派 —— 这是设计使然（BFF 本就聚合多服务），
但**必须量化出来**，否则「跨服务引用 0 处」会被误读成「随时可拆」。

**S3 是唯一有真实工作量的一步**：现有代码里跨模块直连有多少，决定了它的成本。
现状估计不高 —— 全仓 0 个 XML mapper、业务逻辑全是单表、12 处多实体事务全部落在同一服务内。
但**必须先建成跟调用链的检测卡口再动手**，否则漏改的直连会在拆分时才暴露。

### G3 已清零：三个 Port 已落地（2026-07-30）

| Port | 住在 | 解决 |
|---|---|---|
| `api/platform/port/SiteQueryPort` | 实现在 `loc/port/LocalSiteQuery` | `UserFavoriteServiceImpl` 不再直连 `SiteMapper` |
| `api/gateway/port/TelemetryQueryPort` | 实现在 `gw/port/LocalTelemetryQuery` | `MonitorServiceImpl` 不再直连 `HeartbeatMapper` |
| `api/core/port/DeviceOwnershipPort` | 实现在 `dev/port/LocalDeviceOwnership` | `AgentOwnershipSync` 不再直连 `CabinetMapper` |

三条设计约束写进了接口注释：**出参用窄 DTO 不传实体**（传实体等于泄露内部模型，改一列波及所有下游）·
**只提供批量接口**（单个接口会诱导调用方写出 N+1）· **写接口要窄**（开放通用写等于把表交给别人改）。

`DeviceOwnershipPort` 还把两种相反的 scope 语义放在一起并写明差异：
`reassign*` **豁免**数据范围（级联要完整），`existsInScope` **保留**数据范围（授权闸门）。
搞反其一会造成部分级联，搞反其二会造成越权划拨。

**验证**：`mvn test` **80 通过 0 失败**（行为未变，纯解耦）。

### G2 仍有 2 处 —— 这是对的

**抽 Port 解决的是纪律三（不直连别人的表），不解决纪律二（不跨服务事务）。**
`LocalDeviceOwnership` 仍在调用方的事务里同步写 `DevCabinet`，检测器穿透接口看到了这一点，
**没有被重构骗过去** —— 这正是给检测器加「接口→实现」展开的原因：
不加的话，每次抽 Port 都会让跨服务事务从报告里「消失」。

| 违规 | 性质 | 处理 |
|---|---|---|
| `AgentAssignmentServiceImpl#assign` | 已知设计债（ADR-017 记录在案） | 改事件驱动最终一致 + 对账补偿 |
| `ConsumerAuthService#login` | **新发现** —— 同事务写 `usr_user`(core) 与 `sys_token`(platform) | **待决策，见下** |

#### `sys_token` 已解决：是分类问题，不是架构问题（ADR-019 决策一）

查证后发现 **`TokenStore` 本来就是可切换 SPI**，已有 `RedisTokenStore` /
`MysqlTokenStore` / `MemoryTokenStore` / `LocalCacheTokenStore` 四个实现，
当前开发配置是 `token-store: memory`。

所以 `sys_token` 只是 MySQL 实现的**存储细节**，不是业务表。
把它算作 platform 的业务表，会让「登录」（发生在 core）凭空跨界 ——
这个跨界是分类造成的幻象。

已在 `module-graph.py` 引入**显式的 `INFRA_TABLES` 集合**（`sys_token` +
`flyway_schema_history`），在 `module_of()` 入口处排除。入列须同时满足三条硬判据：
所有服务都读写 · 不承载业务语义 · 拆分后走共享中间件而非业务库。

**这与「给违规开豁免」有本质区别**：豁免是承认跨界但假装没事（口子一开卡口会退化成摆设），
分类是它根本不属于任何业务服务、因而不存在跨界。集合显式枚举、每条写理由、加入需评审。

**JWT 方案已否决**：现有 `StaffTokenAuthFilter` 用权限版本戳（口径 B）实现
「角色权限变更对在线员工下一请求即生效」，JWT 签发后不可变，做不到即时生效与吊销。
**为消除一个架构告警而牺牲已实现的安全属性，是本末倒置。**
