# 库存管理 · 菜单与模块规范

> 2026-10-30 · V211菜单规范：出库管理；安装选项称待安装设备。V209/V210的历史名称不作为现行规范。
>
> 本文是**库存管理模块**的菜单结构、页签归属与功能边界规范。它不是 UI 视觉规范：配色、排版、间距、布局仍以 [`设计规范-ShareHub运营台.md`](设计规范-ShareHub运营台.md) 与 [`设计规范-布局与外壳.md`](设计规范-布局与外壳.md) 为唯一真源。
>
> 背景：用户 2026-10-29 要求把库存管理从设备管理拆成独立模块，完整管理设备及其他物料（备件 / 配件、耗材 / 物料、其他整机），将来可作为独立系统。**独立系统的承载方仍以 ai-shop 库存服务为准**（[独立进销存/A ~ D](独立进销存/)）。powerbank 运营端负责统一入口与宿主侧主数据。权限码沿用 `device:inventory:*`。

---

## 一、模块边界

| | 设备管理（`/devices`） | 库存管理（`/inventory`） |
|---|---|---|
| 回答的问题 | 这台设备**装在哪、跑得怎样、坏了没** | 东西**在不在库、在哪个仓、有多少、怎么进出** |
| 管的对象 | 机柜、充电宝（上线后的生命周期） | 机柜、充电宝（在库阶段），以及所有其他物料 |
| 典型动作 | 绑定、装机、上线、监控、指令、OTA、维修、撤机、报废与遗失 | 建档、入库、质检放行、出库给商家、领用、报废出库、退供应商、调拨、盘点、对账 |
| 交界 | 已出库设备清单绑定后进入设备管理；撤机回仓生成入库单回到库存管理 | 同左 |

**判断一个功能归哪边**：只要动的是「库存账」（在库数量、所在仓、出入库单据），就归库存管理。只改设备在业务上的状态（点位、在线、故障），就归设备管理。

## 三、规则

1. **一个 URL 只属于一个 L1**：库存页签全部在 `/inventory?tab=…`。`/devices?tab=<库存页签>` 的旧链接由 `lib/inventory-routes.ts#inventoryRedirect` 转过去，其他参数（如 `no`）原样保留。`tab=inventory` 转成 `tab=transfers`。
2. **页签键 = 菜单叶子的 `tab` 参数**，三处同序：`nav.ts` 库存段、`app/inventory/page.tsx` 的 `TAB_KEYS`、`lib/inventory-routes.ts` 的 `INVENTORY_TAB_KEYS`（由 `inventory-routes.test` 与 `nav-page-tabs.test` 兜住）。
3. **菜单真源在 `iam_menu`**：改库存段必须新开迁移，并在 `nav-seed.test.ts` 的 `PATCHES` 里登记重放。
4. **后端未就绪的叶子不置 `ready`**：真实后端模式下菜单灰显「待开发」，mock 模式照常可用。
5. **组件归属**：库存页面的组件在 `components/inventory/`，设备生命周期视图留在 `components/device/`。库存组件只能经 `lib/api` 调接口，不能 import 设备页的内部函数。将来整体抽出时，按目录搬走即可。
6. **组内顺序按业务流**：主数据（先建档）→ 出入库（东西进来、出去）→ 库内作业（仓内移动与核对）→ 库存账（结果查询）→ 设置。

## 四、物料模型（对齐 ai-shop 库存服务）

| 概念 | 取值 | 说明 |
|---|---|---|
| 大类 `category` | `DEVICE` 整机设备 · `SPARE_PART` 备件 / 配件 · `CONSUMABLE` 耗材 / 物料 | 只用于分类筛选，不影响记账规则 |
| 跟踪方式 `trackingMode` | `SERIAL` 逐件（序列号）· `QUANTITY` 按数量 | 同 ai-shop `InvItem.trackingMode`；**有出入库流水后不可改** |
| 内置物料 | 机柜（`MT0001`）、充电宝（`MT0002`） | 只读。它们的账走设备流程（入库单、已出库设备清单、调拨），不进物料单据，不可归档 |
| 单据用途 | 入库：`PURCHASE` 采购 / `OPENING` 期初 / `RETURN` 退回；出库：`REQUISITION` 领用 / `SCRAP` 报废 / `RETURN_SUPPLIER` 退供应商；`TRANSFER` 调拨 | 对应 ai-shop 入库 / 出库单用途。调拨 = 一出一入在同一张单 |
| 过账 | 建单即过账 | 同处置出库。纠错走反向单据，不改历史 |

**不变式**（mock 已强制，后端实现须同口径，见 `lib/mock/db/material.ts`）：

- **M1**：余额只由单据产生。
- **M2**：数量物料出库不得超过本仓在手。逐件物料出库的序列号须在本仓；入库的序列号不得已在任何仓。
- **M3**：有流水后跟踪方式不可改；在任何仓有库存时不可归档。
- **M4**：内置物料不进物料单据。
- **M5**：用途与必填项绑定：
  - `SCRAP` 须原因码；
  - `PURCHASE` / `RETURN_SUPPLIER` 须供应商；
  - `REQUISITION` 须领用人或工单；
  - `TRANSFER` 须调入仓，且不同于调出仓；
  - 填了单价须填币种。

## 五、实现（V210，账接 ai-shop 库存服务）

用户 2026-10-29 定：物料的账**直接记在 ai-shop 库存服务**，powerbank 只存主数据与单据的宿主记录。

| 端点（`/api/ops/inventory/`） | 宿主做什么 | 库存服务侧 |
|---|---|---|
| `materials`（增改、`/archive`、`/unarchive`） | 物料档案存本地 `inv_material`；首次出入库时同步，之后改名也同步 | `PUT items/by-ref/{物料号}`（gatePolicy NONE：质检只管柜和宝） |
| `material-docs`（建、列、查） | 本地校验 M1–M5（出库前按库存服务余额预检，一次列全）；成功后存 `inv_material_doc(_line)` 与对方单号 | 入库 → `inbounds` + `post`；出库 → `outbounds`（报废带 `reasonCode`；退供应商带 `targets.SUPPLIER`，先同步供应商为外部目标）+ `post`；调拨 → `TRANSFER_OUT` + `TRANSFER_IN` 两张单 |
| `material-balances` | 按本地仓、物料映射回来；逐件物料带在库序列号 | `balances`、`serials` |
| `material-thresholds` | 本地 `inv_material_threshold`；低于下限并入告警 `LOW_STOCK`（仓管待办） | — |

- **引擎**：物料单据与物料库存只在 `inv.engine = SERVICE` 下可用，LOCAL 下返回 409 `error.inventory.material_service_only`，页面给出说明。物料档案任何引擎都能维护。
- **处置出库**：SERVICE 引擎下与本地报废同一事务，在库存服务做一张出库（`SCRAP` / `RETURN_SUPPLIER`）。库存服务拒绝时整单回滚。
- **业态档案**：powerbank 业主的档案要声明这些用途：
  - 去向 `SUPPLIER`；
  - 入库 `OPENING` / `TRANSFER_IN`；
  - 出库 `REQUISITION` / `RETURN_SUPPLIER` / `TRANSFER_OUT`。

  定义唯一在 `backend/scripts/inventory-local/onboard.sh` 的 `PROFILE`；已开过租户的用 `profile.sh <ownerId>` 更新。
- **已知限制**：调拨的出库已过账而入库失败时，库存服务里东西处于「已出未入」。会记 ERROR 并带幂等键，需人工在库存服务补入库。
- **验证**：后端 `MaterialServiceTest`（内存替身）；本机联调 `e2e.py` 对真实库存服务 44 项（含物料 8 项、SERVICE 下处置 1 项）。

### 出库管理与待安装设备

菜单叫「出库管理」，用于已出库设备的交付和安装状态管理；「出库单」仅表示库存出库业务凭证。设备的状态叫「已出库待绑定」：出库给某商家、还没绑到点位。撤机后设备留在原商家且等待重新安装时，称「留商家待安装」；实际回仓称「退库」。


## 六 现行库存术语

以[库存术语与菜单命名规范](库存术语与菜单命名规范.md)为准。现有 `/inventory?tab=issued` 是出库管理，不是出库单列表；安装选择已出库、符合交接条件的待安装设备。出库必须选择商家，筛选和提交均校验商家一致性。
