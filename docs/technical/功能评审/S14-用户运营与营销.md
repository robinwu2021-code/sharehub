## 二、跨功能问题

### 2.1 准入规则不在准入点（本阶段 3 处）

名单与分数存在、运营能改，但「能不能借 / 能不能免押」的唯一判定点 `rent()` 与免押冻结都不读它们：黑名单（P0-1）、信用分（无读取方）、会员 `depositFree`。与 S6 的「借出不认预授权」同一根：**准入逻辑散在各自的表旁边，而不是收在借出入口**。

**方案**：在 `sharehub-api` 定义 `ConsumerGatePort.check(cUserNo, intent)`（`intent = RENT / FREE_DEPOSIT / RECHARGE / LOGOFF`），返回 `{allowed, reasons[]}`；本地实现汇总黑名单、欠费、注销中、信用阈值（裁决后）、会员免押；借出、免押冻结、充值、注销申请都只调它。黑名单部分本阶段 P0（OPT-S14-02），其余随各自裁决。

### 2.2 授予类动作缺「受益人 ≠ 授予人」与额度闸（本阶段 4 处）

免单白名单（`user:risk:update`，CS）、人工调账（`user:wallet:update`）、发券（`marketing:coupon:issue`，CS）、开会员（`user:member:update`）——四个动作都是「员工给某个 C 端账号送钱或折扣」，都没有：原因必填、单次 / 累计上限、超限审批、拦截授予人自己关联的 C 端账号。S7 的人工减免、S11 的调整单已有审批的先例。

**方案**：四个动作统一走 `GrantGuard`：原因必填；按动作配置单次上限与月度累计上限（C-S14-1、C-S14-5）；超限转 `flow:approval`，审批人 ≠ 申请人；员工与 C 端账号按手机号哈希关联（`usr_identity.provider_uid` 与员工登录标识同一 `IdentifierHasher`），关联命中即拒。审计记「授予人 / 受益人 / 动作 / 金额或额度」。

### 2.3 写后不查行数（OPT-S0-29 在本阶段的 21 处）

`user` 包内 `updateById` 调用 27 处，去掉不属本阶段的开票 3（S8）、登录 1、站内信 1、改昵称 1，本阶段 21 处，全部在资金或状态路径上；资金相关 8 处：钱包 `WalletServiceImpl.java:213, 274`、券库存 `UserCouponServiceImpl.java:170, 218`、免单白名单 `FreeWhitelistServiceImpl.java:101, 112`、信用分 `CreditScoreServiceImpl.java:69`、充值单 `RechargeServiceImpl.java:121`。本阶段首批改这 8 处（OPT-S14-27），其余 13 处进 S0 台账。

### 2.4 「页面能配、计算不读」（本阶段 11 处）

见 §〇 清单。与 S6–S12 同源。**方案**：卡口 `known-unread-config-fields.txt`——凡运营端可写字段，要么有读取方的场景用例，要么登记在台账并在出参带 `enforced:false`，只准变短（OPT-S14-29）。

### 2.5 权限码与真源表漂移（本阶段 5 + 2 + 1）

`perm-ssot-align.py` ② 中本阶段 5 个：`marketing:recharge:update`、`marketing:push:update`、`marketing:ad:read`、`marketing:ad:update`、`user:risk:read`；① 中 1 个：`marketing:campaign:create`。语义颠倒 2 组：券「修改」用 `:create`、「归档」用 `:update`；充值套餐「改」用 `user:wallet:update`、「下架」用 `marketing:recharge:update`。归属不一致 1 处：`user:wallet:update` 真源表给 BD、代码只有 ADMIN。免单授予借用「拉黑」的码（P0-2）。**方案**：OPT-S14-26 一次对齐，先改真源表再改代码。

### 2.6 数据范围（只记录，随 S0）

`usr_*` 12 张、`mkt_*` 4 张、`usr_coupon`、`usr_membership`、`usr_wallet*`、`usr_recharge_*` 均未登记（台账）。今天无越权：AGENT 不持相关码，B 端端点全挂权限码。风险在**持码但按区域收敛的员工**（如区域 CS）——未登记即全放行（S0 §2.6），会看到全部市场的用户。随 OPT-S0-13 按 `region_id` 登记，C 端用户表对 AGENT 显式拒绝（OPT-S14-28）。

- 止血期：`POST /mp/user/logoff` 返回 501 `error.logoff.not_available`；`GET /mp/user/logoff` 照常（让已有申请的用户能看到并撤销）

- 运营端 `LogoffItem` 增加 `cancelledBy`、`cancelReason`、`purgedAt`

### 4.6 公告（OPT-S14-23）

- `NoticeReq.startAt / endAt` 为 ISO 8601（带时区或按业务时区解释），非法 400；出参统一 `yyyy-MM-ddTHH:mm:ssZ`
- 归档已发布公告：同时下线，出参 `status=OFFLINE`
- `publish` 对已归档 409 `error.notice.archived`

### 5.2 需复核

1. **P0-1 生产实测**：在生产运营端对一个测试账号点「拉黑」，看浏览器网络面板 `POST /internal/user/credit/blacklist` 的状态码（预期 405 或 SPA 回退），再查 `SELECT COUNT(*) FROM usr_blacklist WHERE status='ACTIVE'`。本机复现「拉黑后仍可借」：拉黑测试账号后调 `POST /mp/trade/orders/rent`，应建单成功。
2. **P0-2 现存授予**：`SELECT c_user_no, reason, quota_type, valid_to, granted_by FROM usr_free_whitelist WHERE status='ACTIVE'`，看 `UNLIMITED` 且 `valid_to` 为空的行与授予人；`SELECT COUNT(*), SUM(waived_amount) FROM ord_order WHERE free_reason IS NOT NULL`。
3. **P0-3 紧迫度**：`SELECT tpl_no, name, stock, issued, status FROM coupon_tpl WHERE status='ACTIVE' AND archived_at IS NULL`——有行即 C 端今天可领；`SELECT c_user_no, tpl_no, COUNT(*) FROM usr_coupon GROUP BY 1,2 HAVING COUNT(*) > 1` 看是否已有重复领取。
4. **P0-4 已违约数**：`SELECT COUNT(*) FROM usr_logoff WHERE status='PENDING' AND cooling_until < NOW()`。
5. **信用分**：`SELECT COUNT(*) FROM usr_credit` 对比 `usr_user` 行数；任取一行调 `POST /api/user/users/{cUserNo}/credit-score {"delta":1,"reason":"x"}`，预期 400「超出区间」。
6. **钱包一致性**：`SELECT w.c_user_no, w.balance + w.gift_balance, SUM(t.amount) FROM usr_wallet w LEFT JOIN usr_wallet_txn t ON t.wallet_no = w.wallet_no GROUP BY w.wallet_no HAVING w.balance + w.gift_balance <> COALESCE(SUM(t.amount), 0)`。
7. **与 S6 的优先级**：本文把 OPT-S6-14 的黑名单拦截部分定为 P0（OPT-S14-02），S6 原定 P1，需在汇总时统一。
8. **V152 菜单名**：「免押白名单」由菜单会话于 2026-10-28 更名（`V152:22-24`，`运营端菜单功能矩阵.md:246`），本文未改；OPT-S14-05 需与该会话对齐。功能清单 SF-CON-02 / 03 / 04、SF-SAL-12 / 13 / 14 / 15 的「差距：无」需按本文更新（本文不改其他文档）。
