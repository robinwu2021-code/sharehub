### SF-DEV-08 设备履历

**结论**：新建。评审对象是设计；核心不在表，而在**同一个事务里由同一个记录点写入**。

**证据**：无现有代码。设计依据：功能清单 SF-DEV-08（`服务端功能清单.md:512-519`）、架构设计 §八 `dev_movement_log`（`架构设计-第一阶段-运营方需求.md:407`）与 §九 `DeviceMoved`、RQ-AST-08 / MER-06 / RPT-R12 / R14、S4 收货设计里预留的 `MovementRecorder` 端口、S5 OPT-S5-03 的 `status-logs`。路径已与前端会话商定为 `GET /api/ops/devices/{deviceNo}/movements`（§4.4）。

**与 S5 `status-logs` 的分工**（已与前端会话对齐）：`status-logs` 记**状态迁移**（`from_status → to_status`，含现场标故障、现场修复）；`movements` 记**位置与归属的移动**（物理在哪、归哪个商家）。一个动作同时改两者时（撤机：`DEPLOYED → IN_STOCK` 且「点位 → 运输」），**同一事务各写一行**，两行互相带对方编号。前端的完整时间轴 = 两个端点按时间合并；R14「维修」口径 = 送修 / 修回（movements）+ 现场故障 / 修复（status-logs）。

## 二、跨功能问题

### 2.1 「单据能填、动作不读」（本仓第四次出现）

前三次是 S1 OPT-S1-25（分润规则页写的表不参与计算）及此后同型的两处。本阶段两处：

| 位置 | 能填什么 | 谁不读 | 证据 |
|---|---|---|---|
| 调拨单终点 `SITE / LOCATION` | 建单时可选站点或点位为终点 | 签收只处理终点为仓的情况：机柜仓位被写成 `NULL`、不落站点；充电宝不改 | `TransferOpsServiceImpl.java:176, 189-194` · `CabinetLifecycleServiceImpl.java:184-187` |
| 权限码 `device:inventory:stocktake` | 真源表声明、前端权限映射有、角色种子随 `device:inventory:*` 发给 OPS | 后端没有任何端点 | `功能权限清单.md:55` · `ops-web/lib/perm-map.ts:103` · `RolePerms.java:25` |

另核对了本阶段的两处「配置」，**均被计算读取**，不属此模式：运维分成系数（`agent.ops.coef.*` 由考核读，系数由 `ShareGeneratorImpl.java:184` 乘到 `OPERATE` 分润）、回仓仓库 `inv.return_warehouse`（`TransferOpsServiceImpl.java:281`）。
**规则**：单据上的每个可填字段要么有消费方、要么不出现在写入面；评审时对每个新字段问一句「谁读它」。本阶段落在 OPT-S10-05（终点收窄）与 OPT-S10-15（盘点端点）。

### 2.2 资产差异是死胡同

| 差异 | 设备停在哪 | 能否出来 |
|---|---|---|
| 调拨缺件 · 机柜 | `IN_TRANSIT`，调拨单 `DONE` | ❌ 状态机出口只有 `RECEIVE`，所属单已终结；`setItems` 要求 `IN_STOCK`，也上不了新单 |
| 调拨缺件 · 充电宝 | `IN_STOCK`，仍记调出仓 | 数得到、找不到——按设备行现算的库存会多算 |
| 调拨多件 | 原样（多在别的仓 / 站点） | 账实永久不符 |
| 撤机 / 巡检数量差 | 只有数量、没有件号 | 说不出少了哪几颗 |

**方案**：差异处置 = 一次带审批的「调整」，审批通过的同一事务改设备状态与位置并写履历（OPT-S10-14）；撤机与巡检改逐颗清点（OPT-S10-16）。这是 AST-10「差异可统计」之外的那一半：差异要能**闭环**，否则 R12 的「期末」永远对不上实物。

### 2.3 事件重投与幂等必须一起修

S0 OPT-S0-21 让进程内监听可以重投——这是对的，但本阶段两个监听器今天之所以「看起来幂等」，靠的是「失败即回滚、且永不重投」：

| 监听器 | 重投后会重复的写入 | 库层幂等键 |
|---|---|---|
| `RemovalCompletedListener` | 清点差异（`:86-88`）、回仓单（先查后插 `:239-241`） | ❌ 两者都没有 |
| `AgentSuspendedListener` | 改派（已改派的不再命中查询，天然幂等） | 不需要 |
| 新增 `DeviceMoved` 的消费方（报表） | 履历派生行 | 由 `dev_movement_log` 的业务唯一键提供 |

**规则**：OPT-S0-21 上线前，凡进程内监听写库的，先补库层幂等键（本阶段 OPT-S10-07、17）。建议在 S0 的任务说明里加这一条前置。

### 2.4 「结清」的口径应当只有一处

清退的结清门禁、S11 的应付台账、ADR-032 的「付款来源可切换」讲的是同一件事：**欠这个商家的钱是否已经两清**。今天门禁用「分润已出账 + 结算单已付 + 提现已办结」三张表拼凑，其中「结算单已付」在代码里不可达（§一 SF-OPR-07）；提现又与结算单互不关联（提现申请不校验余额，`WithdrawalServiceImpl.java:95-138`，属 S11 评审范围）。
**方案**：结清判据只读 S11 的应付余额（`PayableQueryPort.balanceOf(agentNo)`），清退不自造口径；S11 落地前按 OPT-S10-18 的过渡判据，并在 S11 评审里把「提现与应付的关系」列为前置问题。
