## 〇、阶段结论

设备域的**单体内骨架是对的**：机柜状态只经 `CabinetStateMachine`、动作按**原状态**条件更新（并发只一人赢、输的 409，`CabinetLifecycleServiceImpl.java:255-266`）；上线门禁十项（质检、勘测、装机工单、装宝比例、点位、站点、合同、在线、试借还、计费方案）**在服务端强制**，手动上线与装机完工自动上线走同一份判据（`:91-134, :138-148, :191-202`）；设备事件按 `eventId` 去重**落在库层唯一键**（`V43__sys_event_consumed.sql` `uk_event_consumed (event_no, handler)`，先插后做、同事务，`EventIdempotency.java:50-66`），单条失败不拖垮整批（`DeviceSignalServiceImpl.java:90-101`）；保护动作用「持有者 + 唯一键」表达，人工与信号各解各的（`ProtectionServiceImpl.java:39, 152-179`）。

### 2.6 卡口的两个盲区

- **实体请求体**：卡口只认 `extends BaseEntity`（`EntityRequestBodyRatchetTest.java:45-47`），没继承它的 `@TableName` 实体（本阶段 `DevOtaRollout`、`DevOtaRelease`）当请求体不会被拦。

**方案**（OPT-S5-28）：实体识别改为「有 `@TableName` 注解」；数据范围卡口增加一条——表含 `cabinet_no` / `site_no` / `agent_no` 任一列、又被 B 端读端点直接查询的，须登记或在白名单写理由。

## 四、契约草案

**草案，后端实现前可再议**；字段命名遵循 camelCase、`xxxNo`、`xxxAt`、枚举大写下划线。4.1 ~ 4.6 给运营端，4.7 是单体与设备对接服务之间的内部契约。

### 4.1 机柜写接口（OPT-S5-02、06）

| 方法 | 路径 | 权限 | 入参 | 说明 |
|---|---|---|---|---|
| POST | `/api/ops/cabinets` | `device:cabinet:create` | `CabinetCreateReq {cabinetNo, sn, vendorCode, model, slotTotal, locationNo?}` | 编号已存在 409 `error.device.cabinet_exists` |
| POST | `/api/ops/cabinets/{cabinetNo}` | `device:cabinet:update` | `CabinetUpdateReq {sn?, vendorCode?, model?, slotTotal?, locationNo?}` | 省略的字段不改；不存在 404；并发冲突 409 `error.common.state_changed` |

### 4.2 状态日志与状态词表（OPT-S5-03、04）

- `GET /api/ops/devices/{deviceNo}/status-logs?page=&size=` · `device:cabinet:read`
- 行 `CabinetStatusLog {logNo, event, fromStatus, toStatus, reason, fromLocationNo, toLocationNo, siteNo, operator, occurredAt}`
- `mark-fault`、`undeploy`、`retire` 的 `reason` 必填（已是），此后出现在日志里，不再出现在 `Cabinet.faultReason`；`faultReason` 只在 `status = FAULT` 时有值
- **待裁决后生效**：`status` 增 `WITHDRAWN`（已撤出）、`RETURNED`（退回仓库）、`DAMAGED`（损坏）、`REPAIRING`（维修中）、`LOST`（遗失）；新增动作 `POST /api/ops/devices/{no}/receive-back`、`/send-repair`、`/repair-done`、`/mark-lost`，均判 `device:cabinet:update`；`undeploy` 的目标态从 `IN_STOCK` 改为 `WITHDRAWN`
- 退役改判 `device:cabinet:retire`（先登记真源表）
- **安装时间**（2026-10-28 应运营端菜单会话 OM03-01 补入）：`Cabinet` 出参增加 `installedAt`，取 `dev_cabinet.went_live_at`，**不新加列**；由 `go-live` 动作写入，撤机时保留最后一次的值（历次安装见设备履历时间轴，S10）。存量设备的期初安装日期由期初登记写入（S4 §4.4 的 `installDate`）。

### 4.7 单体 ↔ 设备对接服务（OPT-S5-14、15、27）

均走 `X-Internal-Token`。类型放 `sharehub-api` 的 `api.gateway`，两边只引用它。

**指令**

```
POST /internal/gw/commands
  DeviceCommand {commandId, deviceNo, type, slotIndex?, params?, bizType, bizRef, operator?, timeoutSec?}
  → 200 CommandReceipt {commandId, status, acceptedAt}      // commandId 已存在：返回原回执，不重复下发
GET  /internal/gw/commands/{commandId} → CommandReceipt + {attempts, resultCode, finishedAt}
```

- `commandId` 由业务方生成，约定 `<bizRef>:<type>`（借出 `<orderNo>:EJECT`、试借还 `<trialNo>:EJECT`），≤ 64 位
- `bizType`：`RENT / TRIAL_RENT / OPS / AUTO_RETRY / OTA`；`bizRef` 是业务编号，**不含消费者个人信息**
- 弹仓类指令不自动重试；其余按类型配置重试次数与超时
- 终态以设备事件 `COMMAND_RESULT` 回推：`attrs = {commandId, result: OK | FAIL | TIMEOUT, resultCode}`

**设备事件 v1**

```
POST /internal/events/device
  DeviceEventBatch {events: DeviceEvent[≤500]}
  DeviceEvent {eventId, type, deviceNo, slotIndex?, powerbankNo?, vendorCode, vendorErrorCode?,
               occurredAt /* ISO-8601 带偏移 */, attrs /* 按 type 白名单 */}
  → IngestResult {accepted, duplicated, unmatched}
```

- `eventId` 由网关生成 UUID，与 `gw_message_log.event_id` 同值；单体按 `(eventId, handler)` 去重
- `attrs` 白名单：`COMMAND_RESULT` → `commandId / result / resultCode`；`SLOT_REPORT` → `battery / health`；`FAULT` → `component / detail`；其余类型空。白名单外的键网关丢弃并留痕——**防止厂商报文里的手机号、会员号等经 `attrs` 进入单体**
- `unmatched`（原 `unknownCode`）：未知设备或未知码，单体落 `dev_signal_unmatched`，**不消费 `eventId`**，补档后可重放

**心跳查询**：`GET /internal/gw/heartbeats?cabinetNo=&limit=` 不变，`beatAt` 改带偏移。
