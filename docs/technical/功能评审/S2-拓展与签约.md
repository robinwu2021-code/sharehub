## 〇、阶段结论

合同这条线的骨架是全仓最规整的之一：**所有状态迁移都经 `ContractStateMachine`，且按原状态条件更新、输的一方 409**（`ContractServiceImpl.java:651-663`），非法迁移在状态机抛错（`ContractStateMachine.java:29-34`）；`loc_contract` 全仓只有这一个类在写；四眼原则（不能审自己提交的、会签人不能是运营审批人）、终止审批期间合同照常生效、补充协议不发签约事件，都在服务端强制。线索转化一个事务、不能重复转化。

**问题集中在「钱从合同之外流出去」**，共 5 个 P0：

| # | 发现 | 后果 | 证据 |
|---|---|---|---|
| 1 | **改商机的「落成站点」会给伙伴再挂一条拓展分润，旧的不撤**；商机不经合同、直接建成「已签」就能写分润依据 | 改正一个填错的站点号，伙伴就在两个站点上都拿拓展佣金；没有任何审批 | `LeadServiceImpl.java:121-140, 200-244` · `SiteAgentServiceImpl.java:79-132` · `ShareGeneratorImpl.java:149-174` |
| 2 | **财务会签形同虚设**：BD 角色种子是 `location:*`，通配含 `location:contract:cosign` | 超阈值合同可由三位 BD 走完「提交 → 审批 → 会签」，财务不经手 | `RolePerms.java:94-97` · 功能权限清单 §3 第 71 行只给 FIN |
| 3 | **续签合同生效会再付一次牵线费** | 牵线费按合同号幂等，续签换了新号；代码只排除了补充协议 | `ContractServiceImpl.java:528-549, 641-643` · `ReferFeeGeneratorImpl.java:94, 110-116` |

## 二、跨功能问题

### 2.1 写后不检查影响行数（本阶段 5 处）

与 S1 §2.1 同一根因（`@Version` 冲突时 `updateById` 返回 0、不抛异常）。本阶段：合同编辑草稿（`ContractServiceImpl.java:258`）与签署（`:429`）、进件保存与审核（`VenueOnboardingServiceImpl.java:98, 131`，后者导致并发重复建场地方）、场地方保存与归档（`LocService.java:250, 360`）、线索保存（经 `AbstractCrudService.java:196`）。**合同的迁移骨架是正面样板**（`transit` 检查返回值并 409），修法照它即可。全仓收口在 OPT-S1-23；本阶段只修 OPT-S2-07、15 两处会产生错数据的。

### 2.2 更新接口遇到不存在的编号就新建

S1 P0 #3（修改商家可新建）的同形还有两处：`LocService.saveVenue`（`LocService.java:230-240`）与**通用基类** `AbstractCrudService.save`（`AbstractCrudService.java:157-166`，15 个使用者共用，线索是其一）。基类那处要在 S0 统一修（更新分支编号不存在即 404），本阶段只在 OPT-S2-02、08 里列出受影响端点。

### 2.3 审计字段取自客户端

进件的审核人来自请求体（`LocExtDtos.java:70`）。**规则**：审核人、操作人、时间一律服务端取，请求体里出现即忽略并在卡口里拦（与 S1 §2.3「状态经保存修改」同一类：服务端决定的字段不进请求体）。

### 2.4 实体请求体卡口只识别 `BaseEntity` 子类

`EntityRequestBodyRatchetTest` 用正则 `extends BaseEntity` 认实体（`EntityRequestBodyRatchetTest.java:45-47`）。`LocVenue`、`LocContract` 等直接用 `@TableName`、不继承 `BaseEntity` 的实体当请求体时漏网——`OpsController#createVenue / updateVenue` 正是如此。**方案**：卡口改为识别所有 `@TableName` 类，`LocVenue` 先入台账再迁出；与 OPT-S1-22（出参记录类当请求体）合并为一次卡口扩展。

### 2.5 数据范围

`loc_lead`、`loc_venue`、`loc_venue_onboarding` 未登记（全局放行），`loc_contract` 只登记了 `SITE`（`REGION` 主体会 fail-closed 看到空集）。真源表要求 BD 按区域收敛，但种子与 `IamSeeder` 实际给 `ALL`（真源表 §二·B #6）。**属[待裁决清单 ①](../../requirements/待裁决清单-9-25.md)**，随 S0 统一；本阶段只列出需要补的锚点列（场地方实体补 `regionId`，合同冗余 `region_id` 或经站点派生）。

### 2.6 联系方式的明文边界

线索、场地方、进件三张表的 `contact` 注释都写「掩码；明文落 pii」，代码无掩码、原样存储并原样出参。与 S1 §2.5 不同的是，这三处连「有意明文」的决定都没有。**方案**：随 `sharehub_pii` 落地统一迁移（OPT-S2-25）。

### 2.7 ADR-032 之后，原文的「合同」指哪一份（需裁决）

ADR-032 把原文「商户」改读为「商家」（`agt_agent`）。于是 RQ-MER-03/04/07 的「合同档案、分成比例、历史变更、到期提前 2 个月提醒」字面上是**平台 × 商家**的合同；而系统里的合同是**场地方 × 站点**的进场合同，商家的分成比例在 `share_rule(AGENT)` 上、没有起止日、没有合同实体（对齐文档 4.8 MER-03 已注「代理协议无合同实体」）。功能清单把 MER-03/04/07 挂在 SF-NET-05/06 上，是按作废前的映射。

| 选项 | 做法 | 代价 |
|---|---|---|
| A 进场合同即所指 | 运营方的 Hotel A 既是商家又是场地方，合同就是进场合同；商家分成仍在 `share_rule` | 不改模型；但商家分成没有起止与变更版本，RQ-MER-04「分成条款历史」只能靠审计日志（SHR-07 已指出） |
| B 新建商家合同 | 平台 × 商家合同（起止、分成比例、版本、到期提醒），`share_rule(AGENT)` 挂到合同版本上 | 规模 L，横跨 S1、S2、S11；第一阶段需求真正覆盖 |
| C 两者并存 | 进场合同照旧，另建商家合同 | 两套审批、两套到期提醒 |

**若裁决为 B 或 C，本条升为 P0**（阻塞第一阶段需求）。列为 OPT-S2-21。

## 四、给前端的契约草案

### 4.1 合同到期提醒参数（OPT-S2-22）

`GET/POST /api/platform/biz-rules` 新增 `contract` 分区（与现有分区一样按分区保存，缺省由服务端兜默认值）：

```json
"contract": {
  "leadUnit": "MONTH",
  "lead": 2,
  "escalateDays": [30, 7],
  "receivers": ["BD", "OPS"]
}
```

| 字段 | 含义 | 默认 | 校验 |
|---|---|---|---|
| `leadUnit` | 提前量单位：`MONTH`（按日历月）或 `DAY` | `MONTH` | 二选一 |
| `lead` | 提前量数值 | `2` | `MONTH` 1–12；`DAY` 1–365 |
| `escalateDays` | 升级阈值（距到期天数，降序） | `[30, 7]` | 每个值小于提前量折算的天数；去重 |
| `receivers` | 待办与推送的承接角色 | `["BD", "OPS"]` | 角色码须存在 |

- **为什么用「单位 + 数值」而不是只给天数**：运营方原文是「提前 2 个月」，示例 12-26 到期、10-26 提示，按日历月算；只给天数（60）在大小月下会差 1–2 天。
- 读方：合同汇总的「即将到期」统计与 `ContractExpiryEvaluator` 同读这组参数，不再各自写死 60；`dev_alarm_code.threshold` 对 `CONTRACT_EXPIRING` 不再生效，告警码配置页对该码隐藏阈值项。
- 权限：读 `system:biz_rule:read`，写 `system:biz_rule:update`（与其他分区一致）。
- 承接角色看到待办的前提：BD 角色补 `dashboard:todo:read`（见 OPT-S2 中「承接角色看不到待办」一条）。
