## 〇、阶段结论

本阶段的代码质量**不均匀**。文件存储是全仓写得最严谨的模块之一：服务端生成对象键、按文件头判定类型、按实际字节计大小、下载按归属对象鉴权且查不到时拒绝、个人数据文件不发链接、本地签名用常量时间比较（`FileServiceImpl.java:51-57`）。系统参数改完立即生效（每次现查，`LocalSysParam.java:13`），多副本下也不会读到旧值。

### 2.2 配置写入没有记录改前改后的值（RQ-SEC-09）

`AuditTrailInterceptor` 对所有写操作都记了「谁、何时、哪个端点、成功与否」，但请求体不入审计；改前改后的值只来自各服务自己调用 `AuditChanges.record`（`AuditTrailInterceptor.java:229-247`）。本阶段 6 类配置中只有 `biz.timezone` 调用了它（`SysParamServiceImpl.java:57-59`）。于是「谁在什么时候把职责分离改成了 OFF」「谁把运维分成系数改成了多少」「谁把哪条问题改成了自动退款」都**查不到值**。

**方案**（OPT-S15-20）：在 `AbstractCrudService.save` 的更新分支统一比对 `current` 与 `body` 中非 null 的字段，自动记入 `AuditChanges`（敏感字段按注解 `@AuditMasked` 掩码），子类无需逐个记得调用；业务规则按分区比对 JSON 字段（合并 OPT-S6-09 中「字段级审计」那一部分）。

### 2.3 基础资料的引用完整性只靠前端

银行、地区、品牌、仓库、角色码 / 员工号（工单升级对象）这些「被引用方」，在被引用时不校验是否存在、是否已归档，归档时也不检查是否仍被引用。与 S1 §2.3、S0 §二.1（「修改」能新建）同属「服务端不守边界」。方案见 OPT-S15-07；`sys_param` 中引用型的值（`inv.return_warehouse`、`wo.escalate.*`）在注册表中声明为 `REF(kind)` 类型，写入时同样校验。

### 2.4 权限码真源对齐（本阶段）

`perm-ssot-align.py` 本阶段相关的不一致共 7 项：

| 码 | 情况 | 处理 |

## 四、给前端的契约草案

### 4.1 系统参数（OPT-S15-03、04）

- `GET /api/platform/sys-params` 每行增加：`type`（`INT / DECIMAL / ENUM / ZONE / TEXT / REF`）、`min`、`max`、`options`（ENUM 的可选值）、`defaultValue`、`effectiveValue`、`sensitivity`（`NORMAL / FINANCE / COMPLIANCE`）、`editable`（当前用户是否有对应写权限）
