## 一、开工前核对（2026-10-30 实测）

### 1.1 与文档一致的事实

| 项 | 证据 |
|---|---|
| 默认引擎仍是 LOCAL | `InventoryEngineRouter`、`StockViewServiceImpl`、`MaterialServiceImpl`、`InventoryEventPuller` 四处 `textOf("inv.engine", "LOCAL")` |
| 远端流水只取最近 500 条 | `StockViewServiceImpl.REMOTE_LEDGER_WINDOW = 500` |

### 复核结论（2026-10-30）：改按对接明细的批次顺序开发

原方案把「设备写链整体接恢复日志」和「默认 SERVICE」一起放在阶段 1 先做。对照[对接明细](设备全生命周期-Web与服务对接明细.md) §9.4，明细的顺序是按节点分批：T1 契约与默认路由（F05 / F09）→ T2 收货与查询（A01–A11、B01–B06）→ T3 出库与安装（C01–C13）→ T4 调拨与盘点（B07–B14、F01–F06）→ T5 运行与退出（D、E）→ T6 切流。

**从这里起按明细顺序逐节点开发**。下面阶段 1–7 的任务内容不变，只改归属批次：恢复日志不再整体先做，而是做到哪个写节点就给哪个节点接上（入库在 A07 / A10，出库在 C02，调拨在 B08 / B09，处置在 E07 / E10）；执行异常列表与重试（F04）随 T4。缺的远端能力已整理成[宿主接口需求](库存服务-宿主接口需求-2026-10-30.md)，依赖它的节点先按现有能力做并标「待远端」。
