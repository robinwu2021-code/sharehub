> ## 为什么要有这份文档
>
> 配色对齐做了三轮才对。前两轮都失败，原因值得记下来：
>
> | 轮次 | 做了什么 | 为什么还是"不像" |
> |---|---|---|
> | 1 | 中性色脱离主色派生，改用 shadcn 中性灰 | 治好了"换肤整屏变色"，但**没对 C 端的值** |
> | 2 | 语义色 hex 逐个抄 C 端，中性色抄 `--pb-*` | 值全对了，**形状全错** |
> | 3 | 把 C 端跑起来量计算样式，对齐形状语言 | ✅ |
>
> **教训：让 C 端"软"的是形状语言（药丸、零边框、重字重、填充块分区），不是色值。**
> 只对色值可以做到每个 hex 都相同而整体观感依然是两个产品。
> 以后再有"风格不一致"的反馈，**先去量对方的计算样式**，不要从 token 文件推。

## 一、色板（token 层，`app/globals.css`）

### 1.1 主色：3 套皮肤，与 C 端 `SKINS` 同名同值

| 皮肤 | 值 | C 端对应 |
|---|---|---|
| `mono` 黑白灰（默认）| `#18181B` | `--pb-primary` 默认 |
| `blue` 时尚蓝 | `#2F6BFF` | `data-skin="blue"` |
| `purple` 科幻紫 | `#7C3AED` | `data-skin="purple"` |

**皮肤只换 `--primary`。** 中性色与语义色恒定不参与换肤——否则换肤会动摇整个界面的观感，
且 QA 面从 3 套膨胀成 3×N 套。暗色下 `mono` 的主色反相为近白，否则近黑主色在深底上不可见。

### 1.2 中性色：逐个取自 C 端 `--pb-*`

| ops-web token | 值 | C 端来源 |
|---|---|---|
| `--background` / `--card` | `#FFFFFF` | `--pb-surface` / `--pb-elev` |
| `--foreground` | `#16171D` | `--pb-ink` |
| `--muted-foreground` | `#8A8D97` | `--pb-sub` |
| `--muted` / `--secondary` | `#F2F3F6` | `--pb-faint` |
| `--accent` | `#E8EAEF` | （faint 再深一档，C 端无对应）|
| `--canvas` | `#F8F8FA` | **C 端无对应**，由 faint 混白 55% 派生 |
| `--sidebar` | `#F2F3F6` | **C 端无对应**（手机端无侧边栏）|
| `--border` | `#EEEFF3` | **C 端 border-width 全为 0**，见 §三 |

这组灰是**微冷的**（带一点蓝），不是纯中性。这与"中性色不由主色派生"不冲突：
病根是**派生**（换肤整屏变色），不是带不带色相。一组固定的冷调灰同样治病，还能两端一致。

### 1.3 语义色：5 个，四个抄 C 端 + 一个新增

| token | 浅色 | 暗色 | 说明 |
|---|---|---|---|
| `--success` | `#12B76A` | `#32D583` | = `--pb-success` |
| `--warning` | `#F79009` | `#FDB022` | = `--pb-warning` |
| `--destructive` | `#F04438` | `#F97066` | = `--pb-danger` |
| `--info` | `#2F6BFF` | `#6690FF` | **新增**：运营台大量"处理中/待审/提示"，此前只能借主色，与"可点击/主操作"语义混淆 |

暗色下语义色**提亮**（C 端不提亮）——运营台的徽章在深底上要保证可读，这是有意的偏离。

每个语义色配两个派生量，成对使用：
- `--*-tint`：徽章/提示块的**底色**（浅色 = 混白 14%，暗色 = 混卡片色 22%）
- `--*-ink`：tint 上的**文字色**（浅色 = 压暗，暗色 = 语义色原值）

> ⚠️ **不要直接把语义色当 tint 上的文字色。** `#12B76A` 落在浅绿底上只有约 2.8:1，
> 小字过不了 WCAG AA。这是 Badge 的原实现，已修。

## 二、形状语言（这才是"风格"的主体）

全部换算自 C 端组件的实测计算样式（rpx ÷ 2 = px，750 设计宽）。

| 元素 | C 端 | ops-web | 依据组件 |
|---|---|---|---|
| 卡片圆角 | 30rpx = 15px | `--radius: 14px` | `pb-card` |
| 卡片边框 | **0** | 无 | `pb-card` |
| 卡片阴影 | `0 3px 14px rgba(18,20,34,.06)` | 同 | `--pb-shadow` |
| **按钮** | **9999px 药丸**，字重 **700** | 同 | `pb-button` |
| **搜索框** | **9999px 药丸** + faint 填充 | 同（Toolbar 传 `rounded-full`）| 首页 search |
| **表单输入** | **22rpx = 11px**，faint 填充 | `Input` 默认 11px | `pb-field` |
| **徽章** | 9999px，字重 **700**，22rpx = 11px | 同 | `pb-tag` |
| **分段控件** | faint 灰槽 + 全圆，选中项白药丸 + 600 | 同 | `pb-segmented` |
| 标题 | 23px / **800** / -0.2px | `text-[17px] font-extrabold` | `.pb-h1` |
| 统计数值 | 20px / **700** | 同 | `pb-stat` |
| 卡片 tint 变体 | 语义 tint 底 + **去阴影** | `<Card tone>` | `pb-card--*` |

**搜索框是药丸、表单输入是 11px** —— 这两者 C 端刻意不同，别统一。
筛选下拉与搜索框同处工具栏一行，故也用药丸（`FilterSelect` 内置）。

## 三、唯一一处刻意不照搬：表格行分隔

**C 端全局 `border-width: 0`，一根线都不画**，分区完全靠填充块 + 阴影。

运营端不能照搬：C 端没有表格，而运营台的主体是密集表格，**去掉行分隔就读不动**。

折中：
- `--border` 压到 `#EEEFF3`（几乎只剩"带感"而非"线感"）
- 且**只用于表格行分隔**；卡片、工具栏、输入框、抽屉一律无边框，走填充块 + 阴影

若将来希望表格也彻底无线，替代方案是隔行浅灰块（`--muted`），代价是行高要放大、
单屏信息密度下降——属产品取舍，不是技术限制。

## 四、字体

| | C 端 | ops-web |
|---|---|---|
| 拉丁 | Nunito | Nunito（next/font 自托管）|
| 阿语 | Tajawal | Tajawal（next/font 自托管）|
| 中文 | Noto Sans SC | Noto Sans SC（**Google Fonts CDN**）|
| 基准 | 28rpx/1.5 = 14px | 14px / 1.5 |

中文走 CDN 而非自托管**是被迫的**：`Noto Sans SC` 在 next/font 的字体数据里只登记了
`cyrillic/latin/latin-ext/vietnamese`，**没有 `chinese-simplified`**，自托管路径取不到汉字字形。
用 `latin` 子集时 `document.fonts.check(...,'设备')` 实测为 `false`——字体加了等于没加，
且肉眼完全看不出来。已知代价：受限网络/内网部署下会静默回退到 PingFang SC / 微软雅黑。

## 五、改配色时的自检清单

1. 改的是 token 还是组件？**颜色一律改 token**，组件里不写死颜色值。
2. 新增语义色？必须同时给出 `--*-tint` 与 `--*-ink`（明暗各一组），并验证 tint 上文字 ≥ 4.5:1。
3. 动了 `--border`？确认没有把它用在卡片/输入框上——那是填充块的活。
4. 觉得"还是不像 C 端"？**先把 c-app 跑起来量计算样式**（`dist/build/h5` 起个静态服务即可），
   对比圆角、border-width、font-weight 这三项，它们比色值更决定观感。
