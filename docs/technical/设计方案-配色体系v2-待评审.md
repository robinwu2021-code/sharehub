## 零、先说清楚为什么会错

前几轮我对齐的是 c-app 的**旧版本**（本地 HEAD，3 皮肤、默认黑白灰）。
真正的现状在未合并的远程分支 `origin/feature/ops-nav-v2` 上：**4 皮肤，默认「简电青」**。

| | 我一直在对的（本地 HEAD） | C 端实际现状（ops-nav-v2） |
|---|---|---|
| 皮肤数 | 3 | **4** |
| 默认皮肤 | `mono` 黑白灰 `#18181B` | **`brand` 简电青 `#17C3C0`** |
| 品牌表达 | 无 | JD Charge 品牌青绿，**渐变 hero 卡** |

所以「配色和 C 端不一致」不是我调得不准，是**对齐了一个错误的基准**。
这也解释了「美感不足」：ops-web 现在是一套**纯中性 + 近黑主色**的方案，
C 端却是**品牌青绿 + 渐变 + 大量 tint 色块**——后者本来就更有生气。

> 教训（已写入 [设计规范](设计规范-运营端配色与形状.md)）：
> 对齐前先确认**基准在哪个分支**。`git log --all -- <path>` 比读当前工作区可靠。

## 一、C 端 v2 实测规格（这次是运行时量的）

### 1.1 四皮肤

| 皮肤 | id | 主色 | 中文名 |
|---|---|---|---|
| **简电青（默认）** | `brand` | `#17C3C0` | 取自 JD Charge 品牌青绿 |
| 黑白灰 | `mono` | `#18181B` | |
| 时尚蓝 | `blue` | `#2F6BFF` | |
| 科幻紫 | `purple` | `#7C3AED` | |

**换肤只改 `--pb-primary` 一个变量**，中性面与语义色恒定——这一条和我们现在的做法一致，不用改。

### 1.2 中性面与语义色

与我上一轮对齐的完全一致（`#16171D` ink / `#8A8D97` sub / `#F2F3F6` faint /
`#12B76A` `#F79009` `#F04438`），**这部分不需要动**。

### 1.3 新发现：三个我们完全没有的表现手法

这三点才是「美感差距」的实际来源，比色值重要得多。

**① 渐变 hero 卡**（首页 / 我的 / 订单详情票根头，三处同一配方）
```css
background: linear-gradient(135deg,
  var(--primary),
  color-mix(in srgb, var(--primary) 72%, #000 14%));
```
主色到「主色压暗 14%」的 135° 渐变。换肤时渐变自动跟着变，不需要每套皮肤各配一组。

**② 票根式虚线分隔**（订单详情）
```css
border-top: 2rpx dashed color-mix(in srgb, var(--sub) 32%, transparent);
```
不是实线，是**次要文字色 32% 透明度的虚线**——比实线柔和得多，且自动适配明暗。

**③ tint 图标底片**（列表项左侧的图标块）
主色 12% tint 做圆角方块底 + 主色图标，替代「灰底灰图标」。
`--pb-primary-tint: color-mix(in srgb, var(--pb-primary) 12%, transparent)`

## 二、ops-web 的差距诊断

按你指出的三点逐条对应：

### 2.1 「颜色本身不好看」

**根因：主色选错了。** ops-web 默认 `mono #18181B`，等于整个界面**没有品牌色**，
只有黑白灰 + 三个语义色。运营台确实该克制，但**完全无彩**会显得死板廉价。

### 2.2 「缺少层次感/精致度」

**根因：我们只有「白卡 + 极轻阴影」一种表达，C 端有四种。**

| C 端手法 | ops-web 现状 |
|---|---|
| 渐变 hero 卡 | ❌ 完全没有 |
| tint 图标底片 | ❌ 图标都是裸的 |
| 票根虚线分隔 | ❌ 只有实线 border |
| 语义 tint 卡（`<Card tone>`）| ✅ 已有，但**几乎没有页面在用** |

### 2.3 「和 C 端对不上」

已定位，即第零节的分支问题。

## 三、方案（待评审，未实施）

### 提案 A：主色改用简电青，与 C 端默认一致 ⭐

- ops-web 默认皮肤 `mono` → **`brand` 简电青 `#17C3C0`**
- 皮肤列表补齐到四套，与 C 端 id/hex/中文名完全一一对应
- **中性色与语义色不动**（已经对齐了）

**影响面**：`globals.css` 皮肤块 + `lib/stores/theme.ts` 皮肤列表，约 20 行。
组件层零改动（主色是 token）。

**需要评审的点**：运营台用青绿做主色是否合适？
青绿在**表格密集界面**里出现频率远高于 C 端（每个链接、每个主按钮、每个激活态），
可能比在手机端更「跳」。备选：ops-web 保留 mono 为默认、但把 brand 加进可选列表。

### 提案 B：引入 C 端的三个表现手法

| 手法 | ops-web 落点 | 价值 |
|---|---|---|
| **渐变 hero** | 工作台顶部 KPI 区、登录页 | 目前工作台是纯白卡片堆叠，最需要视觉锚点 |
| **tint 图标底片** | Rail 导航激活态、StatCard 图标、空态插图 | 成本极低，立刻提升精致度 |
| **票根虚线** | 抽屉内分区（详情 vs 操作）、结算单金额分隔 | 替代现在生硬的实线 |

这三项都是**新增 token + 组件变体**，不改既有组件行为。

### 提案 C：补一档「品牌渐变」token

```css
--gradient-brand: linear-gradient(135deg, var(--primary),
                  color-mix(in srgb, var(--primary) 72%, #000 14%));
--tint-icon: color-mix(in srgb, var(--primary) 12%, transparent);
--divider-dashed: 1px dashed color-mix(in srgb, var(--muted-foreground) 32%, transparent);
```
挂进 `@theme inline` 后可用 `bg-gradient-brand` / `bg-tint-icon`。

## 四、需要你拍板的三个问题

1. **主色：跟 C 端用简电青，还是运营台保留黑白灰？**
   （我倾向跟 C 端——「两端是一个产品」的价值大于「运营台要克制」，

   如果它是废弃分支，那 C 端的「现状」到底以哪个为准需要重新确认。
   我基于它做的所有对齐都建立在「它会成为正式方案」的前提上。

3. **提案 B 的三个手法做几个？**
   建议至少做 tint 图标底片（成本最低、收益最直接）。
