# 方案 · ops-web 的认证与权限（多主体）

状态：**已定**（2026-09-23，用户「继续」＝采纳各条推荐；§十 逐条记录了结论）
依据 [ADR-030](./ADR/ADR-030-账号与主体-一个账号可属多个运营主体.md) · [v4/06 认证与权限](./v4/06-认证与权限.md)
确认后并入 [开发计划-入驻与多主体账号](./开发计划-入驻与多主体账号.md)

> ops-web 同时是**运营端**和**代理门户**（[接口清单 §3.5](../api/接口清单-按端.md) 定案：代理端 = ops-web 的角色视图，不建独立前端）。
> 所以「一个人可属多个主体」这件事，前端要在**同一套代码**里表达两种 realm、两套可见性、和一个会在运行时切换的数据范围。

## 一、现状体检（实测，2026-09-23）

| # | 现状 | 文件 | 多主体下会怎样 |
|---|---|---|---|
| 1 | **权限表硬编码在前端**：`ROLE_PERMS: Record<Role, string[]>`，`can(role, code)` 查它。后端下发的 `perms` **一个字节都没读过** | [permissions.ts:6](../../ops-web/lib/permissions.ts) | **根本表达不了**。同一个人在 A 主体是属主、在 B 主体是店员，权限不同——而前端表是按 `role` 查的，查不出主体差异。**而且它现在就已经漂了，见 §1.1** |
| 2 | `agentNo` 是**单值字符串** | [auth.ts:22](../../ops-web/lib/auth.ts) | 放不下 `memberships[]` |
| 3 | `AGENT` 被当成**一个角色**塞进 `Role` 联合类型 | auth.ts:7 | realm（账号池）与 role（权限）是正交的两件事，合并后「属主 vs 店员」无处表达 |
| 4 | 发 `X-Roles` / `X-Merchant-Id` 两个头 | [http-client.ts:33](../../ops-web/lib/api/http-client.ts) | 都是客户端可控且服务端不信的遗留头；`X-Merchant-Id` 在[取消租户](./ADR/ADR-026-取消租户概念-唯一运营方.md)后已无意义 |
| 5 | `/login` 是**唯一**硬编码的免登录路由 | [app-shell.tsx:21](../../ops-web/components/layout/app-shell.tsx) | 自助注册公开页进不来 |

**一条好消息**：判权已经收口在 `useCan()` 一个 hook 里，全仓 `can()` 只有 **9 处**调用、`canModule()` **4 处**。
**换权限真源的改动面比看上去小得多。**

### 1.1 实测：前后端权限表**已经漂了 29 处**

`RolePerms.java` 的类注释原话是「**与 ops-web `lib/permissions.ts` 同源**」。
把两边逐角色对出来（括号配对解析，7 个角色两边都命中，ADMIN 1:1、BD 9:9 完全一致，解析可信）：

| 角色 | 前端码数 | 后端码数 | 仅前端 | 仅后端 |
|---|:-:|:-:|:-:|:-:|
| ADMIN | 1 | 1 | 0 | 0 |
| OPS | 27 | 20 | **8** | 1 |
| CS | 30 | 21 | **9** | 0 |
| FINANCE | 27 | 19 | **8** | 0 |
| BD | 9 | 9 | 0 | 0 |
| VIEWER | 14 | 14 | 1 | 1 |
| AGENT | 9 | 10 | 0 | 1 |
| | | | **26** | **3** |

**「同源」是一句注释，没有任何东西在拦。** 两类症状各有各的难查：

| 类型 | 数量 | 表现 | 例子 |
|---|:-:|---|---|
| 仅前端有 | **26** | 菜单/按钮渲染得出来，**点进去 403** | CS 的 `system:problem:update`；OPS 前端给了 `device:ota:*` 通配而后端只有 `device:ota:read`——OTA 发布按钮看得见、点了 403 |
| 仅后端有 | **3** | 后端允许，**界面上没有入口**，功能等于不存在 | VIEWER 的 `agent:agent:read`；AGENT 的 `workorder:wo:read` |

> ai-shop 在他们 `auth.ts` 的注释里把这件事记了下来，一字不差就是我们现在的处境：
> 「后端一直在下发，而前端此前一个字节都没读过 —— `can()` 查的是前端自己写死的角色表。
> 两套各自演化的结果是：**前端放行、后端 403**，或者**前端拦住、后端本来允许**（功能存在而没人找得到入口）。」
>
> **他们已经修完了。这一节之后的内容，主体是搬，不是设计。**

## 二、直接搬 ai-shop 的成果

> 2026-09-23 用户定：「**权限要用 ai-shop 的 ops-web 的成果。**」
> ai-shop 的 ops-web 权限机制是**已落地**状态（六角色 × 13 码复核于 2026-08-12），

### 2.1 机制层：照搬（`ops-web/lib/`）

**三条最值钱的语义**（照抄，不要自己重新推）：

| 语义 | ai-shop 的理由（原文要点） |
|---|---|
| **先查映射、后判通配** | 反过来的话超管会看到 `UNIMPLEMENTED` 的入口——而那些端点根本不存在，点下去同样 404。「超管什么都能做」说的是权限，不是「后端还没写的功能他也能用」 |
| **漏登记 = 判 false**（拒绝优先） | 默认放行会静默开口子；漏登记的表现是「按钮神秘消失」，那是最难查的一类 |
| **`canModule` 无受控码 = 返回 true** | 看板就是这样：登录后的首页人人可见。返回 false 的话**所有人登录后落到空导航** |

### 2.2 模型层：照搬（B 端权限方案的三条规则）

来自 ai-shop 的「B 端权限方案」（同级仓库 `ai/ai-shop`，`docs/technical/reference/B端权限方案.md`）§三。它们对我们的 `is_owner` / 多角色同样成立：

| 规则 | 对应我方 | 不这么做会怎样 |
|---|---|---|
| **`OWNER = "*"` 不是「拥有全部权限点」，是「不走这张表」** | `agt_account.is_owner=1` 的属主 | 反过来做（逐项列给属主）的后果是：**上一个新功能，老板被锁在外面，而他是唯一能给自己授权的人——死锁** |
| **多角色取并集，不取最小** | L2 的 `agt_account_site` 多角色 | 取交集是那种「看起来更安全」的聪明做法，但它把老板的显式意图判成了错误 |
| **空角色 = 零权限，不是「零权限 = 全放行」** | `perms: []` 判 false | 「空即无限制」是权限系统里最常见的一类漏洞 |

### 2.3 拒绝的表达：**两个码，不是一个**

ai-shop 把 403 拆成两个业务码，理由值得照抄：

| 情形 | 他们的码 | 给用户的话 |
|---|---|---|
| **不是商家**（压根不该进这个端） | `10403` | 「没有操作权限」——他该去入驻 |
| **是商家，但角色不够** | `70006` | 「你在这家店没有这个权限」——他该找店主 |

> 撞同一个码时，「权限没配对」与「数据不在范围里」在日志里长得一模一样，排查只能靠猜；
> 而且给用户的话也不一样——一个消费者误点进来看到「找店主开通」，而他根本没有店主。
>
> **我方对应**：`不是代理商` vs `是代理商但在这个主体下没有这个权限`，两个码要分开。
> 具体码值按本仓既有错误码段分配（`fail()` 约定）。

### 2.4 数据范围：照搬「三层，不是两层」+ 那条豁免教训

**认证 → 授权 → 数据范围**，第三层最容易被忽略：授权回答「能不能调这个接口」，数据范围回答「能看到哪些行」。

> ⚠️ **跨属主的查询必须显式豁免。** ai-shop 在这上面栽过两次：
> 核销的写路径（不豁免则 UPDATE 影响 0 行，**接口返回成功而订单纹丝不动**）、
> 日累计限额的读路径（不豁免则「该商家当日成交额」被改写成「**该买家**在这家店的当日成交额」，
> 限额实际成了「每买家一份」）。**两次的共同点：没有任何报错。**
>
> 我方的 `DataScopeRegistration` 已经是同一套形状，这条教训直接适用——
> 统计类、对账类、跨主体聚合的查询，写的时候就要想清楚要不要豁免。

### 2.5 后端守卫：`decisionsAreActuallyEnforced`

ai-shop 的 `BizEndpointPermTest` 四条守卫里，这一条是真正的兜底：
**登记表里定了权限的端点，代码里必须真的有 `@PreAuthorize`**。

> 「**登记表是许愿，注解才是执行。** 一张全绿但没落地的权限表，比没有表更危险——它会让人以为已经防住了。」

**我方的情况查清了，结论是「一半天然成立、一半完全没有」**：

`docs/api/contract.json` 由 [`api-extract.py`](../../backend/scripts/api-extract.py) **扫控制器源码生成**
（正则抽注解，不是人工维护）。实测 **382 个端点、324 个带权限码**；58 个无码的分布：

| 无码端点 | 数量 | 判断 |
|---|:-:|---|
| `/api/auth/*`（login · logout · me · menus · permissions） | **5** | **合理**——登录与身份自查 |
| `/mp/**` | 39 | 合理——C 端走 CONSUMER realm 的属主判定，不进 RBAC |
| `/internal/**` | 14 | 合理——进程间 |

**也就是说 `/api/**` 的 312 个端点里，无码的只有那 5 个 auth 端点，没有裸奔的运营端点。**

| ai-shop 的守卫 | 我方状态 |
|---|---|
| `everyBizEndpointHasADecision`（每个端点必须登记权限决定） | **天然近似成立**——契约是扫注解生成的，"抽到 perm" 就等于 "有注解" |
| `decisionsAreActuallyEnforced`（登记表是许愿，注解才是执行） | **同上，天然成立**——不存在"表里有、代码里没有"的缝 |
| `allCodesExist`（前端用到的码必须真的存在于后端） | ❌ **完全没有** —— 这正是 §1.1 那 26 处「仅前端有」的来源 |
| 页面用到的码必须在映射表里 | ❌ **完全没有**（连映射表都还不存在） |

**结论：后端侧的两条不用补，前端侧的两条是 D6d 的主要内容。**

> 仍值得补一份**人工登记**的「有意公开」清单（那 5 + 39 + 14 个），
> 否则将来有人漏写注解时，`contract.json` 里的表现与"有意公开"一模一样。这条排在 L2。

### 2.6 **不能搬的：主体切换器**

ai-shop 的 ops-web **没有运行时主体切换**——他们的数据域（`merchantNo` / `communityNo` / `pickupNo`）是
**登录时确定、会话内不变**的；多门店切换在他们的 **B 端**（`b-app`），不在 ops-web。

我们不一样：**代理门户在 ops-web 里**（[接口清单 §3.5](../api/接口清单-按端.md) 定案不建独立前端），
所以「运行时切主体 + 切完重算权限与数据范围 + 清缓存 + 丢弃在途响应」这一整套
**没有现成答案，是我方新增的部分**（§三 决策 4、§八 的 D6b）。

## 三、ai-shop 没覆盖的部分：五个决策

### 决策 1 · 前端权限表退役 —— **照搬 §二.1，不再自行设计**

```
真后端模式：perms ← GET /api/auth/me 的 perms[]          ← 唯一真源
mock 模式：  perms ← BACKEND_ROLE_PERMS[role] 展开        ← 仅离线开发用
```

`can(perms, code)` 签名与语义、`UI_PERM_MAP` 映射层、`UNIMPLEMENTED`、守卫、体检页**全部照 ai-shop**。
现有 `ROLE_PERMS` 改造成 `BACKEND_ROLE_PERMS`（后端角色表的前端镜像，仅供 mock 与对账），
`useCan()` 改读 store 的 `perms`——9 + 4 处调用点逐个改。

> **为什么必须现在做**：①多主体下「同一个人在不同主体权限不同」，前端表按 role 查，
> 切到 B 主体后菜单和按钮**还是 A 主体的样子**，而且不报错；
> ②**它现在就已经漂了 29 处**（§1.1）——这一步顺带把那 29 处对平。

### 决策 2 · realm 与 role 拆开

```ts
realm: "STAFF" | "AGENT" | ""    // 账号池：决定用哪套登录、看哪个门户
role:  string                     // 仅用于显示（「财务」「代理商」），不参与判权
perms: string[]                   // 判权唯一依据
```

判权只看 `perms`。`role` 留着是因为界面上要显示身份名称，**但任何 `role === "..."` 的分支都要清掉**。

### 决策 3 · `X-Operator-No` 与 `X-Roles` 是**两种性质完全不同的头**

这一条必须写进实现注释，否则实现者会以为「反正后端不信客户端头」。

| 头 | 服务端信不信 | 结论 |
|---|---|---|
| `X-Roles` · `X-Merchant-Id` | **不信**（只认 token 反查） | 遗留，**建议删**（见 §十 决定 3） |
| **`X-Operator-No`** | **信**（落在会话 `memberships` 内时采纳） | **整条多主体改造里唯一有越权面的头**；服务端必须校验，不在成员集合内就**整个丢弃、回落默认主体、不报错** |

前端也挡一层（切换前校验 `no ∈ memberships`），但**前端那层不算数**——它只是减少无效请求。

### 决策 4 · 切换主体 = 重新装配身份，不是改一个头

```
switchOperator(operatorNo):
  ① 前端校验 operatorNo ∈ memberships          （减少无效请求，不是安全措施）
  ② set currentOperatorNo；operatorGen++       （世代号，见下）
  ③ 重新拉 GET /api/auth/me + GET /api/auth/menus   → 覆盖 perms / role / dataScope
  ④ queryClient.clear()                        ← 必须
  ⑤ 当前路由在新主体下无权限 → 回首页，并提示「该页面在当前主体下不可见」
```

| 步 | 漏了会怎样 |
|---|---|
| ③ | 菜单与按钮还是上一个主体的；点进去 403，用户以为系统坏了 |
| ④ | **切过去看到的还是上一个主体的列表——页面照常打开、数据是另一家的，没有任何报错。** 这是本方案里最危险的一条 |
| ⑤ | 停在一个已经没权限的路由上，页面空白或反复 403 |

**世代号 `operatorGen`**：参与 react-query 的 `queryKey`，也用于丢弃在途响应。
只清缓存不够——切换瞬间已发出的请求带的是**旧**主体的头，回来时会写进新主体的缓存。
响应到达时比对世代号，不一致就丢弃。

### 决策 5 · 菜单可见性：perm 收敛为主，realm 兜底为辅

`nav.ts` 现在靠 `leaf.perm` + `canModule` 收敛。多主体下**再加一层 realm 过滤**：

```
可见 = can(leaf.perm) && realmAllows(leaf)
```

`realmAllows`：`AGENT` realm 只看代理门户那几个 group（经营概览 / 我的资产 / 我的服务），
`STAFF` 看其余。**这是兜底，不是主依据**——真依据仍是 perms。

> 理由：代理门户的叶与运营叶有权限码重合（如 `agent:settlement:read` 两边都用），
> 光靠 perm 收不干净，会让员工菜单里冒出「我的收益」。
> 更彻底的做法是**菜单全部由后端 `GET /api/auth/menus` 下发**（端点已存在），
> `nav.ts` 降级为路由与图标的描述——但那是更大的一步，**建议留到 L2**（见 §十 决定 4）。

## 四、store 形状

```ts
interface AuthState {
  realm: "STAFF" | "AGENT" | "";
  subjectNo: string;          // 员工 employee_no / 代理 account_no
  displayName: string;
  roleLabel: string;          // 仅显示
  perms: string[];            // ← 判权唯一依据（服务端下发）
  scoped: boolean;            // 是否受限视图（用于「你看到的是自己范围内的数据」提示）

  // —— 仅 AGENT realm ——
  memberships: { operatorNo: string; name: string; isOwner: boolean; isPrimary: boolean }[];
  currentOperatorNo: string;
  operatorGen: number;        // 切换世代号

  token: string;
}
```

**删掉**：`role: Role`（改 `roleLabel` + `perms`）· `agentNo`（改 `currentOperatorNo`）· `tenantNo`（ADR-026 后无意义）。

> ⚠️ `persist` 到 localStorage 的键是 `pb-ops-auth`。**结构变了要改 key 或写 migrate**，
> 否则老浏览器里残留的旧结构会被读成「有 token、没 perms」＝**登录态存在但什么都看不见**。

## 五、登录页

多主体之前先要解决一件事：**员工和代理用同一个登录页，怎么分账号池。**

### 推荐方案 B：登录页显式两个 tab

```
[ 员工登录 ]  [ 合作伙伴登录 ]
  邮箱+密码      手机号或邮箱+密码
```

前端传 `realm`，后端按 v4/06 §2.6「`realm` 只选账号池，不是权限」处理。

| | 方案 A：单输入框，后端两池都查 | **方案 B：显式选 realm**（推荐） |
|---|---|---|
| 用户操作 | 少一步 | 多一次点击 |
| 同一邮箱既是员工又是代理 | 要返回「选择身份」中间态，**多一条几乎不会触发但必须写的分支** | 不存在这个问题 |
| 错误信息 | 「账号或密码错误」（不能说哪个池没有，否则可枚举） | 「该手机号不是合作伙伴账号」，指向清楚 |
| 与 v4/06 现有约定 | 需要改 | **一致**（`realm` 缺省 STAFF） |

**其余不变**：入参一个 `identifier` 字段（手机号**或**邮箱，含 `@` 走邮箱），不传 `role`。
今天登录页里 `api.login(username, password, "ADMIN")` 那个写死的 `"ADMIN"` 要删。

## 六、mock 侧怎么支持多主体

否则 D4 / D5 / D6 在 `NEXT_PUBLIC_USE_MOCK=1` 下开发不了。

| 要素 | 做法 |
|---|---|

### 10.1 关于第 3 条的查证

全仓实际读取的请求头**只有两个**：`Authorization`（`AuthController:137` · `ConsumerAuthController:85`）
与 `X-Forwarded-For`（`AuditTrailInterceptor:97`）。

`X-Roles` / `X-User-Id` / `X-Merchant-Id` 在后端出现 **10 处，全部是注释**——
内容都是在说明「**不信**客户端这些头」。**没有任何一处实际读取。**

因此浏览器侧这三个头可以直接删，不需要后端配合。

> ⚠️ **一个要留意的同名陷阱**：`RemotePorts:133` 有一条已知局限——
> 跨进程调用 `/internal/**` 时，数据范围「必须由受信头透传（`X-User-Id`/`X-Roles`）」，当前未透传。
> 那是**服务端之间**的受信头，与浏览器发的同名头是两回事。
> 将来真要做跨进程透传时**建议改名**（如 `X-Internal-Actor`），
> 否则「同一个头名，一处不信、一处必须信」这件事迟早被某个人按错的那一半理解。
