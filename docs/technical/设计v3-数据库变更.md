## 一、设备类型注册表

### `md_device_type`（新增 · L0 主数据 · **全局表无 `tenant_id`**）

**类型差异用数据描述，不用 `if/else` 散在代码里** —— 这张表就是「加一种设备要改哪些东西」的清单。

| 列 | 类型 | 说明 |
|---|---|---|
| `type_code` | `VARCHAR(32)` UQ | `POWERBANK` / `EV_PILE` / `LOCKER` |
| `name_zh` `name_en` `name_ar` | `VARCHAR(64)` | 三语（i18n 规范） |
| `has_movable_item` | `TINYINT(1)` | 槽位里是否有平台资产：充电宝 1，桩/柜 0 |
| `item_table` | `VARCHAR(64)` | 物品台账表名，`has_movable_item=0` 时为 NULL |
| `order_ext_table` | `VARCHAR(64)` | 订单扩展表名，如 `ord_charge_ext` |
| `default_metering` | `VARCHAR(16)` | `MINUTE` / `KWH` / `COUNT` |
| `reservation_target` | `VARCHAR(16)` | 预约粒度：`CABINET`（任意槽位）/ `SLOT`（具体枪） |
| `supports_return_elsewhere` | `TINYINT(1)` | 是否支持异地归还：充电宝 1，其余 0 |
| `command_family` | `VARCHAR(32)` | 指令族：`POWERBANK` / `EV_PILE` / `LOCKER` |
| `status` | `VARCHAR(16)` | `ENABLED` / `DISABLED` |

**首批三行**：

```
POWERBANK  item=1 dev_powerbank  ord_rent_ext    MINUTE  CABINET  return_elsewhere=1
EV_PILE    item=0 NULL           ord_charge_ext  KWH     SLOT     return_elsewhere=0
LOCKER     item=0 NULL           ord_locker_ext  MINUTE  SLOT     return_elsewhere=0
```

**注册进 `DataScopeRegistration`？** 否 —— 全局主数据，无归属语义。

## 二、订单：共性主表 + 类型扩展表

### `ord_order`（新增 · 替代 `ord_rent`）

**成立判据（验收标准）：资金侧只 join 本表。** 分润 / 账务 / 发票 / 结算 / 报表读模型
一律不碰扩展表 —— 做不到就是共性列抽错了，回头调主表而不是往扩展表塞。

| 列 | 类型 | 说明 |
|---|---|---|
| `order_no` | `VARCHAR(36)` UQ | 前缀 `ORD`，存量单号原样迁入 |
| `device_type` | `VARCHAR(32)` | 一等维度，默认 `POWERBANK` |
| `tenant_id` | `VARCHAR(36)` | |
| `c_user_no` | `VARCHAR(36)` IX | **数据范围 `SELF` 锚点** |
| `site_no` `location_no` `cabinet_no` | `VARCHAR(36)` | 在哪 |
| `slot_index` | `INT` | 哪个槽位（充电宝=仓位，桩=枪，柜=格口） |
| `agent_no` `region_id` | `VARCHAR(36)` IX | **归属快照，转手不回写**（数据范围锚点） |
| `status` | `VARCHAR(24)` | 共性状态机，见下 |
| `sub_status` | `VARCHAR(24)` | 类型子状态（`DISPENSING`/`PREPARING`/`IDLE`），**资金侧不读** |
| `started_at` `ended_at` | `DATETIME(3)` | 业务起止 |
| `price_plan_no` | `VARCHAR(36)` | 计价方案 |
| `price_snapshot` | `JSON` | **整个 plan 的展开结构**（items+ladders+schedule 生效值），改价不影响在途单 |
| `coupon_no` `free_reason` `waived_amount` | | 减免 |
| `amount` `currency` | `DECIMAL(18,2)` / `VARCHAR(8)` | 应收 |
| `deposit_amount` `auth_no` | `DECIMAL(18,2)` / `VARCHAR(36)` | **押金/预授权（自 rent_ext 升入）**，`auth_no`→`pay_auth` |
| `source_channel` | `VARCHAR(16)` | `APP`/`MINI`/`H5`/`INTERCONNECT` |
| `partner_no` | `VARCHAR(36)` | 互联互通伙伴（§六） |
| `reservation_no` | `VARCHAR(36)` | 由预约履约而来时回链 |

**升格规则**：字段出现在 **≥2 种设备类型**即升主表。押金升入（充电宝押金/桩预授权/柜押金），
`buyout` 只有充电宝有，留扩展表。**新增第四类设备时用这条规则复核一遍主表**。

**索引**：`uk_order_no` · `idx_ord_user(tenant_id,c_user_no,created_at)` ·
`idx_ord_scope(tenant_id,agent_no,status)` · `idx_ord_cabinet(cabinet_no,status)` ·
`idx_ord_type(tenant_id,device_type,status,created_at)`（新增：按设备类型筛是运营端主查询）

**共性状态机**（资金侧只认 `SETTLED`）：

```
CREATED ──> ACTIVE ──> ENDED ──> SETTLED ──> CLOSED
   │           │          │
   └─ CANCELLED│          └─ 类型子状态 IDLE（桩：充满未拔）
               └─ 类型子状态 DISPENSING（宝：等待弹出）/ PREPARING（桩：等待插枪）
```

| 状态 | 充电宝 | 充电桩 | 储物柜 |
|---|---|---|---|
| `ACTIVE` | 已借出 | 充电中 | 占用中 |
| `ENDED` | 已归还（可异地） | 已停止 | 已取出 |

### 三张扩展表（主键即 `order_no`，1:1）

**`ord_rent_ext`**：`order_no` PK · `powerbank_no` · `return_cabinet_no` · `return_slot_index`
· `buyout`(`TINYINT`) · `duration_min`(`INT`)

**`ord_charge_ext`**：`order_no` PK · `connector_no` · `energy_kwh`(`DECIMAL(10,3)` —— 电量三位小数是行业口径)
· `start_soc` `end_soc`(`TINYINT`) · `peak_power_kw`(`DECIMAL(8,2)`)
· `stop_reason`(`FULL`/`USER`/`FAULT`/`BALANCE`/`REMOTE`) · `idle_min`(`INT`)
· `meter_start` `meter_stop`(`DECIMAL(12,3)` **表底数** —— 结算只认它，过程累计仅展示)

**`ord_locker_ext`**：`order_no` PK · `cell_index` · `access_code`(`VARCHAR(16)`，取件码)
· `overtime_min`(`INT`) · `item_note`(`VARCHAR(128)` 可空)

> 扩展表**不带** `tenant_id`/`version`/`deleted` —— 生命周期完全依附主表，
> 由主表的租户与软删覆盖。这是本项目 `@TableName(excludeProperty)` 的既有用法。

### 迁移（`ord_rent` 136 行）

1. 建 `ord_order` + 3 张 ext（Flyway 新版本号，**不改 V1..V13**）；
2. `INSERT ... SELECT` 拆列：共性列 → `ord_order`（`device_type='POWERBANK'`），
   `powerbank_no/return_cabinet_no/buyout/duration_min` → `ord_rent_ext`；
   `deposit_amount` **升入主表**；
3. `ord_rent` 改为**只读视图**（`CREATE VIEW ord_rent AS SELECT ... JOIN ...`）保留一个版本周期，
   老代码不改也能读，给切换留缓冲；
4. 资金侧四域改 join `ord_order`（列名不变，只改表名）；
5. 一个版本后 `DROP VIEW ord_rent`。

**数据范围注册必须同步改**：`DataScopeRegistration` 里 `ord_rent` 的登记
（含 `SELF→c_user_no`）迁到 `ord_order`。**漏了会导致 C 端「我的订单」直接空集**
—— `DataScopeHandler` 对未登记维度是 fail-closed 生成 `1=0`，这个坑本项目踩过。

## 三、计价：方案 → 费用项 → 阶梯

### `price_plan`（改造）

加 `device_type`（默认 `POWERBANK`）。**四个计费列
（`free_minutes`/`unit_minutes`/`unit_price`/`cap_daily`）保留但废弃**，
迁移后由 `price_plan_item` 承载；保留是为了灰度期双读比对，一个版本后删。

### `price_plan_item`（新增）

| 列 | 类型 | 说明 |
|---|---|---|
| `item_no` | `VARCHAR(36)` UQ | 前缀 `PI` |
| `plan_no` | `VARCHAR(36)` IX | 所属方案 |
| `item_type` | `VARCHAR(16)` | `TIME_FEE`/`ENERGY_FEE`/`SERVICE_FEE`/`IDLE_FEE`/`HOLD_FEE` |
| `metering` | `VARCHAR(16)` | `MINUTE`/`KWH`/`COUNT` |
| `free_qty` | `DECIMAL(12,3)` | 免费额度（分钟/度/次），`IDLE_FEE` 用它表达宽限期 |
| `unit_qty` | `DECIMAL(12,3)` | 计费步长（如每 30 分钟、每 1 度） |
| `cap_daily` `cap_total` | `DECIMAL(18,2)` | 单项封顶 |
| `rounding` | `VARCHAR(16)` | `CEIL`/`FLOOR`/`HALF_UP` —— **必须显式**，四舍五入口径是对账争议高发区 |
| `sort` | `INT` | 出账顺序（账单展示与发票行序） |

**`SERVICE_FEE` 与 `ENERGY_FEE` 分列是硬要求**：对账、发票、分润三处口径都要求电费与服务费分开
（多数市场电费不可加价、服务费才是平台收入）。

### `price_ladder`（新增）

| 列 | 说明 |
|---|---|
| `ladder_no` | 前缀 `PL` |
| `item_no` IX | 所属费用项 |
| `seq` | 阶梯序 |
| `from_qty` `to_qty` | 区间（`to_qty` NULL = 无上限） |
| `unit_price` | 该区间单价 |

单段阶梯即「无阶梯」—— **不为「简单场景」另设一条无阶梯路径**，一种表达方式减少分支。

### `price_schedule`（改造）

加 `item_no`（作用到具体费用项）+ `mode`（`MULTIPLY` 系数 / `REPLACE` 替换价）。
峰谷电价是「替换价」，节假日上浮是「系数」，两种都要。

### 计价迁移

现 `price_plan` 每行 → 一条 `TIME_FEE` item（`metering=MINUTE`，`free_qty=free_minutes`，
`unit_qty=unit_minutes`，`cap_daily` 平移）+ 一条无上限 `price_ladder`（`unit_price` 平移）。
**语义零变化**，用存量订单做**影子重算逐分比对**通过后才切换。

## 五、供应商：多值列拆表

### `gw_vendor_device_type`（新增关联表）

`gw_vendor.device_types` **不做多值列** —— db-design §1.7 明确多值拆表。

| 列 | 说明 |
|---|---|
| `vendor_code` | 供应商 |
| `device_type` | 支持的设备类型 |
| `protocol` | `VENDOR_CLOUD`(形态A) / `DIRECT`(形态B) / `OCPP16J` / `OCPP201`(形态C) |
| `command_family` | 指令族 |

UNIQUE `(vendor_code, device_type)` —— 一家供应商同一设备类型只能一种协议。

`gw_vendor_config` 加 `capability_manifest`(`JSON`)：driver 声明的 commands/events 白名单。
**白名单是供应商红线的执行手段** —— 不在白名单里的厂商能力（尤其订单/支付类 SaaS），
driver 层面就不存在。

| 列 | 说明 |

| `name` · `country` | |

### `intc_session_map`（新增）

外部会话 ↔ 本地订单双向映射。**伙伴的 session id 是他们的主键，必须双向可查**
—— 他们查我们、我们推 CDR 都要用。

`partner_no` · `external_session_id` · `order_no` · `status` ·
UNIQUE `(partner_no, external_session_id)` + UNIQUE `(order_no)`

### `intc_cdr_log`（新增 · **追加表**，无 `version`/`deleted`）

CDR 推送日志，幂等重推：`cdr_no` · `partner_no` · `order_no` · `payload`(JSON) ·
`push_status` · `retry_count` · `last_error` · UNIQUE `(partner_no, order_no)`。

### `stl_settlement`（改造）

`payee_type` 扩 `PARTNER`。伙伴按 CDR 对账 —— `recon_task` 加对账源 `INTERCONNECT`。

## 七、事务性发件箱

### `sys_outbox`（新增 · 追加表）

单体用 `ApplicationEventPublisher` 够；**拆服务后「落库」与「发消息」必须原子**，
否则订单结算了但分润事件丢了，账就永远对不上。

`event_no` · `aggregate_type` · `aggregate_id` · `event_type` · `payload`(JSON) ·
`status`(`PENDING`/`SENT`/`FAILED`) · `retry_count` · `next_retry_at` ·
IX `(status, next_retry_at)`

**单体期就要建并写入** —— 它是拆分的前置条件，不是拆分时才加。写入与业务同事务，
投递由独立轮询器完成；单体下投递器直接转 `ApplicationEventPublisher`，拆分后转 MQ。
