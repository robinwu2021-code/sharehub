## A. 该接（4 条）

### A1. 调拨单看不到调了哪些设备 —— ✅ 已接（2026-09-24）

`GET /api/ops/inventory-transfers/{transferNo}` → `InventoryTransferDetail`

出参是 `InventoryTransfer + List<TransferItem>`，而**列表那个类型没有 items**。
于是运营端的调拨单只能看到「从哪到哪、多少台」，
**点不开「这一单具体调了哪几台充电宝」** —— 而盘点对不上时要查的恰恰是这个。

落点：设备管理 › 库存调拨，**单号做成详情入口**，抽屉逐台列出编号与核对状态。
未核对的排在前面 —— 盘点差异的落点就在那几行。

### A2. 发票看不到对应哪些订单 —— ✅ 已接（2026-09-24）

`GET /api/trade/invoices/{invoiceNo}` → `InvoiceView`

出参是 `Invoice + List<String> orderNos`。前端没有发票详情抽屉，
于是「这张发票是哪几笔订单开出来的」查不到 —— 税务或客户质疑时这是第一个要答的问题。

落点：财务管理 › 发票，详情抽屉里加「对应订单」一栏（抽屉本来就有，缺的是这一栏）。

### A3. 员工级数据范围没有任何入口 —— ✅ 已接（2026-09-24）

后端半 `9af5a21`，运营端半 `5f75d6b`。

`GET /api/platform/data-scopes/{subjectType}/{subjectNo}`

后端的读写两个端点都按 `subjectType` 支持 **ROLE 与 EMPLOYEE 两级**，
而前端 `saveRoleDataScope` 把 subjectType **写死成 ROLE**，且从不读。

后果：**某个员工要比他的角色看得更窄/更宽，做不到** —— 只能为他单开一个角色。
（读那一半现在可以不接：角色的范围值已随 `RoleRowVO.scopeRefs` 出参带出来了，2026-09-24 修。）

落点：员工与权限 › 员工，加「数据范围」抽屉（复用角色那套 UI，subjectType 传 EMPLOYEE）。

**读那一半最后还是接了**，上面那句「可以不接」只对角色成立：员工列表出参不带范围信息，
而保存是整体覆盖 —— 抽屉打开时显示空值、运营点一下保存，原设置就被抹了。

**接的过程中顺出一个更要紧的**：前端下拉里的 `LOCATION` 在后端数据范围注册表里
**一张表都没登记**，而 `DataScopeHandler` 是 fail-closed 的 ——
选了它的人每一页都是空的，且没有任何报错。更糟的是那个档位的选择器给的是「站点」、
标签写「按点位」、存下去却是 `LOCATION`；而真正实现的 `SITE`（登记在 5 张表）
根本不在选项里。已改正，并加卡口 `DataScopeOptionsTest`
（前端能选的每一档，注册表里必须至少有一张表登记）。

### A4. 改了权限，用户不重登就一直用旧的 —— ✅ 已接（2026-09-24）

`GET /api/auth/me`

`perms` 目前**只在登录那一刻拿一次**并存进 localStorage。
运营改了某个角色的权限后，受影响的人**不重新登录就一直用旧权限** ——
多给的看得见、少给的照样点得动，而且两边都不报错。

⚠️ 顺带：`ops-web/lib/auth.ts` 的注释写着「判权读的是后端 `GET /api/auth/me` 下发的 perms」，
**与实际不符** —— 实际来自登录响应。注释要跟着改。（已改，`5ab212e`。）

落点：`lib/perms-sync.ts` + 挂在 `AppShell`。进应用与**标签页重新可见**时拉一次
（最小间隔 60 秒），不轮询。

**先验了前提再接**：`/me` 返回的若是登录那一刻的快照，前端再怎么拉也只是把
同一份旧权限反复写回，而且看不出任何异常。后端 `StaffTokenAuthFilter` 的口径 B
（会话戳 ≠ `PermVersion` 就按角色重建）此前**一个测试都没有** ——
现由 `PermsRefreshWithoutReloginTest` 守住三件事：`/me` 不重登即收敛、
**收权后同一个 token 被服务端拒（403）**、吊销后 `/me` 回 401 而不是 200。

据此纠正本文此前的说法：「少给的照样点得动」**不成立** —— 闸一直在服务端。
真正的损失是「多给的看不见」（后端放行、界面没入口）与「少给的按钮还在、
点下去弹无权限」。

## B. 重复 / 该删（3 条）

### B1. `GET /api/platform/iam/roles`

与前端在用的 `GET /api/platform/roles` 重复，且**直接返回实体 `IamRole`** ——
与仓库「不拿实体当出参」的方向相反（见 `known-entity-request-bodies.txt` 的同类纪律）。
前端用的是带 `permCount`/`memberCount` 的 `RoleRowVO`。**建议删**。

### B2 / B3. 菜单有三处真源

| 来源 | 现状 |
|---|---|
| `ops-web/lib/nav.ts` | **前端实际在用的 SSOT** |
| `GET /api/auth/menus` → `MenuNode` | 后端按权限过滤出的动态菜单树，**没人调** |
| `GET /api/platform/iam/menus` → `IamMenu` | 直接读 `iam_menu` 表（**生产 12 行**），**没人调** |

三份真源同时存在，日后必然对不上。**要先定哪一份是真的**：
若定前端 `nav.ts`，则后两个端点与 `iam_menu` 表该退役；
若定后端下发，则 `nav.ts` 要改成消费 `/api/auth/menus`（那是件大改动，涉及门禁与面包屑）。

另：`GET /api/auth/permissions` 返回的就是 `/me` 里那份 `perms`，**二者取一即可**。

## C. 不需要接（8 条）

这些 `GET /{id}` 详情端点的**返回类型与对应列表完全相同**（实测自 `contract.json`），
前端用列表数据渲染详情是合理的，不构成缺口：

| 端点 | 返回类型 |
|---|---|
| `GET /api/agent/accounts/{accountNo}` | `AgentAccount`（同列表） |
| `GET /api/agent/commissions/{ruleNo}` | `AgentCommission`（同列表） |
| `GET /api/ops/inspection-plans/{planNo}` | `InspectionPlan`（同列表） |
| `GET /api/ops/leads/{leadNo}` | `Lead`（同列表） |
| `GET /api/ops/sla-rules/{slaNo}` | `SlaRule`（同列表） |
| `GET /api/ops/venue-onboardings/{onboardingNo}` | `VenueOnboarding`（同列表） |
| `GET /api/trade/settlements/{settleNo}` | `SettlementView`；构成明细前端已走 `listSettlementRecords` 取到 |
| `GET /api/auth/permissions` | 与 `/me` 的 `perms` 重复（见 B3） |

> **判据**：详情端点只有在**返回比列表更多的东西**时才算缺口（A1/A2 就是这种）。
> 返回同一个类型时，再调一次只是多一次往返。
