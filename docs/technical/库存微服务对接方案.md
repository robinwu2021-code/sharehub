## 〇、一页结论

1. **对接已经落地一大半**。客户端、引擎开关、出库与签收、撤机回仓、盘点、物料单据、处置出库、存量迁移、事件拉取都有代码。按提交记录，后端 939 例、前端 1500 例通过，本机对真实库存服务联调 44 项通过。本文作者没有重跑这些测试。
2. **默认仍是本地引擎**。系统参数 `inv.engine` 缺省 `LOCAL`，生产没有库存服务实例，生产配置里也没有 `sharehub.inventory.*`。
3. **上线前有四件必须收口的事**（§七，P0）：
   - 本地事务里同步调远端，幂等键每次随机，**远端成功而本地回滚后无法恢复**，设备会卡在两边不一致的状态；
   - 没有任何对账，不一致只会留在日志和收件箱的 FAILED 行里；
   - 存量迁移按「采购入库」写，会让切换当期的采购量虚增，且没有用库存服务自带的迁移导入接口（有冲突检测与空跑）；
   - 生产设备套、凭证、备份、实例自检、预检都还没做。
4. **充电宝与 ai-shop 的约定不一致**：ai-shop 决定柜、宝都按序列号管理并用「柜包含宝」的组装关系；powerbank 目前只有柜走出库池，宝只入库、不出库，也没用组装关系（§七 G5，待业务确认）。
5. **需要联合确认的三项**：迁移走哪条路（Q-1）、充电宝组装由谁登记（Q-2）、客户端用自写还是 `inventory-client`（Q-3）。

## 一、边界与分工

库存服务只管**仓内**：入库、在仓、出库、盘点、流水。交接给商家（签收，库存服务叫「领取」）之后，库存服务不再跟踪。其余全归 ShareHub。这是 ADR-046 决定 6，也是 D 文档的口径。

| 环节 | 谁管 | 对接点 |
|---|---|---|
| 到货或回仓后的质检、放行凭证 | **ShareHub** | 质检记录号作为入库行的放行凭证（`gateRef`），库存服务只校验「有、未被别的序列号用过」，不判断内容 |
| 入库、在仓余额、盘点、流水 | 库存服务 | ShareHub 页面经后端调用 |
| 发货出库（商家、可选站点、接收人） | 库存服务 | 用途 `ISSUE`，生成出库池记录 |
| 签收 | 交接点 | 接收人签收即调「领取」，本地写 `issued_agent_no` 与履历 |
| 绑定、装机、上线、解绑、换站点、整站换商家、撤机 | **ShareHub** | 不调库存服务 |
| 撤机回仓后的再入库 | 两边 | ShareHub 复检，库存服务 `RETURN` 入库并冻结，ShareHub 解除本地关联后调「业务确认」解冻 |
| 物料（耗材、配件）与处置出库（报废、退供应商） | 库存服务记账 | ShareHub 保留本地档案与单据，成功后存对方单号 |
| 统一库存视图、库存报表 | **ShareHub** | 汇总库存服务（仓内段）与本地（仓外段） |
| 谁能做什么、数据范围 | **ShareHub** | 库存服务只记操作人，不授权 |

ai-shop 侧的关键决定（ADR-046）与 ShareHub 的关系：

| 决定 | 对 ShareHub 的含义 |
|---|---|
| 进销存是独立服务 `inventory`，名称不带 shop，代码暂在 ai-shop 的 `backend/inventory/` | 通过 HTTP 对接，不依赖 ai-shop 业务模块 |
| 同一构件，**测试一套、生产两套**：电商套只放行 `SHOP`，设备套放行 `SHAREHUB` 与充电桩 | ShareHub 生产连**设备套**，库是新库，不碰电商库 |
| 一个业主 = 一本库存账；ShareHub 的业主是运营方（ADR-026 唯一运营方，一个业主），每个仓是业主下的库位 | 一套凭证，不按商家拆账 |
| 序列号管理，柜、宝都按序列号，宝挂在柜下 | 见 §七 G5 |
| 库存只管仓内，质检、出库后位置、人员角色、运营界面归调用方 | 与 §一 表一致 |

## 二、部署与环境

| 环境 | 库存服务 | 库 | 备注 |
|---|---|---|---|
| 本机联调 | `inventory-svc-local`，端口 8086 | `inventory_test`，MySQL 9.7 | ai-shop 迁移含 MariaDB 语法，需按 `~/work/tools/ai-shop-mysql-conv` 改写；步骤见 `backend/scripts/inventory-local/README.md` |
| 测试 | 共用一套，装全部业态 | 一个库 | 用来暴露「内核里藏着业态假设」的问题 |
| 生产 | **设备套**：实例代号 `DEVICE`，端口 8087，放行 `SHAREHUB,CHARGING` | 新库 `neargo_inv_device` | 与电商套不共享任何资源；设备套停机不影响电商 |

连接与安全约定（来自 ai-shop TDD §2.3、§2.13）：

| 项 | 约定 | ShareHub 现状 |
|---|---|---|
| 地址 | 同机内网 `127.0.0.1:8087`，`/api/inventory/v1` 不经 nginx 对外 | 配置项 `sharehub.inventory.base-url`，缺省空 |
| 认证 | `Authorization: Bearer <key>:<secret>`，每个系统一把凭证，只在所属实例的库里签发，服务以凭证中的系统与业主**覆盖**请求参数 | 配置项 `app-key`、`app-secret`，缺省空，未配置时所有调用 503 |
| 操作人 | `X-Inventory-Actor`，只记审计，不授权 | 已发 `STAFF:<userNo>`，无会话时 `SYSTEM` |
| 幂等 | 所有写请求带 `Idempotency-Key`；同键同参返回原结果，同键异参 409 | 已带，但**键每次随机**（§七 G1） |
| 超时 | 未规定 | 连接 2 秒、读取 5 秒，可配 |
| 实例自检 | ShareHub 启动时比对 `/actuator/info` 的实例代号，不是 `DEVICE` 就拒绝启动（手册第 4 步） | **未实现** |

引擎开关：系统参数 `inv.engine`，`LOCAL` 或 `SERVICE`，运行时切换不必重启，V198 种入，缺省 `LOCAL`。`InventoryEngineRouter` 是 `InventoryPort` 的主实现，按开关路由到本地或远程。

## 三、接口契约

前缀 `/api/inventory/v1`。成功体是裸 JSON，失败体 `{code, message, data:{args}}`，ShareHub 翻成 `InventoryRemoteException`，再转成业务冲突 `error.inventory.remote` 抛给界面。

ShareHub 已使用的端点（`HttpInventoryApi`）：

| 能力 | 端点 | 用在 |
|---|---|---|
| 物料 | `PUT /items/by-ref/{externalRef}` | 首次出入库时把型号或本地物料同步过去 |
| 外部目标 | `PUT /external-targets/{MERCHANT\|SITE\|PERSON}/{ref}` | 每次发货前同步商家、站点（上级为商家）、接收人 |
| 仓库 | `GET /warehouses` · `POST /warehouses` | 按名称认领已有仓，没有再建 |
| 入库 | `POST /inbounds` · `POST /inbounds/{no}/post` · `POST /inbounds/{no}/business-clearance` | 到仓待检入库、回仓入库与解冻 |
| 出库 | `POST /outbounds` · `POST /outbounds/{no}/post` | 发货、处置、物料出库、迁移 |
| 出库池 | `GET /dispatch-pool?serialNo=` · `POST /dispatch-pool/claims` · `POST /dispatch-pool/claims/{no}/release` · `POST /dispatch-pool/{id}/redirect` · `/revoke` | 签收、调整、退回 |
| 查询 | `GET /balances` · `GET /serials` · `GET /ledger` · `GET /reports/period-summary` | 库存余额、在库明细、流水、期间报表 |
| 盘点 | `POST /counts` · `GET /counts/{no}` · `/scans` · `/submit` · `/approve` · `/reject` · `/post` · `/cancel` | 盘点页，经后端透传 |
| 事件 | `GET /events` · `POST /event-acks` | 每分钟拉取 |

库存服务提供、ShareHub **尚未使用**的端点：

| 端点 | 为什么值得用 |
|---|---|
| `GET /commands/{requestId}` | 按幂等键查命令结果，是 G1 恢复的现成手段 |
| `GET /dispatch-pool/claims/by-request/{requestId}` | 签收超时后按请求号查领取结果 |
| `POST /serials/{sn}/assemble` · `/disassemble` | 柜与宝的组装关系，见 G5 |
| `GET /in-transit` | 待签收汇总，可替代本地统计 |
| `GET /documents` | 统一单据列表 |
| `POST /admin/v1/owners/{ownerId}/imports?apply=` | 迁移导入，有预演、冲突检测、重跑为空的判据，见 G3 |

事件（库存服务发，至少一次投递，信封带 `eventId`、`resourceVersion`）：ShareHub 收件箱按 `event_id` 唯一去重。目前只对 `DispatchRedirected` 与 `DispatchRevoked` 做本地投影，其余事件只入箱留痕。

## 四、数据与映射

**主数据映射**，存在 `inventory_sync_state`（键值表，V198）：

| 键 | 值 | 写入时机 |
|---|---|---|
| `item:CABINET` / `item:POWERBANK` | 库存服务 `itemId`；两者都建成序列号管理、入库须带质检凭证 | 首次入库 |
| `wh:{本地仓号}` | 库存服务 `locationId`；按名称认领已有仓，没有再建 | 首次用到该仓 |
| `claim:{设备号}` | 领取单号；退回、调整时先释放用 | 签收成功 |
| `events:seq` | 事件游标 | 每轮拉取 |
| `mig:{类型}:{设备号}` | 迁移进度，`IN` 或 `OUT` | 存量迁移 |

商家、站点、接收人不落映射，**每次写之前先 upsert 成外部目标**（父先于子），保证对方一定认得。

**本地数据**：

| 对象 | 变更 | 说明 |
|---|---|---|
| `dev_cabinet` / `dev_powerbank` | `issued_agent_no`、`issued_at` 等出库池列 | 本地投影，由本地端口同事务写；与 D 草稿的 `inv_stage` 方案不同，见 §六 |
| `inventory_inbox` | `event_id` 唯一、`type`、`status` DONE 或 FAILED | 事件去重与失败留痕 |
| `inv_material`、`inv_material_doc(_line)`、`inv_material_threshold` | V210 | 物料档案、物料单据（含对方单号）、安全库存 |
| `inv_*` 旧表 | SERVICE 模式下仍保留，设备表是展示与绑定约束的依据 | 退场计划未定 |

**ID 对应**：设备序列号 = 本地设备号（柜号、宝号）；放行凭证 = 本地质检记录号；出库目标 = 商家号、站点号、内部人员号。

## 五、已实现的流程

所有写操作的顺序都是：**本地校验与投影（同事务）→ 调库存服务 → 任一步失败整笔回滚**。

| 流程 | 本地 | 库存服务 | 备注 |
|---|---|---|---|
| 到仓待检入库 | 质检通过的设备置在库 | 建 `PURCHASE` 或 `RETURN` 入库单并过账；回仓的随即「业务确认」解冻 | 放行凭证 = 质检记录号 |
| 发货出库（柜） | 写 `issued_agent_no` 等 | 按来源仓分单建 `ISSUE` 出库单并过账；**不指定接收人时以经办人为接收人并当场领取** | 与「运营代签、一步出库」的裁决一致 |
| 签收 | 写签收时间 | 调「领取」，记 `claim:{设备号}` | |
| 出库调整 | 改商家、站点、接收人 | 已领取的先释放，再 `redirect`，再按本地状态重新领取 | |
| 出库池退回仓库 | 清出库池字段，落回仓 | 先释放，再 `revoke`，由库存服务冲回**原出库仓** | 本地所选回仓仓与原仓不同时只打警告，要靠盘点或调拨纠正 |
| 撤机回仓 | 撤机完工建到仓待检单（RETURN） | 复检通过后 `RETURN` 入库并确认 | |
| 盘点 | 不落数据 | 页面经后端透传开盘、扫码、提交、复核、过账 | 提交人不能自己复核由库存服务强制 |
| 物料单据与物料库存 | 本地档案与单据 | 采购、期初、退回入库，领用、报废、退供应商出库，余额与序列号查询映射回本地仓与物料 | 仅 SERVICE 引擎可用，LOCAL 下 409 |
| 处置出库 | 报废、退供应商 | 同事务出库，拒绝则整单回滚 | |
| 库存侧直接改出库池 | `InventoryEventPuller` 把重定向、撤回拉齐到本地未绑定的设备 | 事件 | 已绑定的不跟，绑定是业务侧的事 |
| 存量迁移 | `InventoryMigration`：在仓设备入库，仓外的柜先入默认仓再 `ISSUE` 给商家 | 按「采购」入库 | 见 G3 |

联调脚本覆盖：入库、出库、出库池退回、库存服务拒绝时本地不动、事件去重、盘点、撤机回仓、统一视图与期间汇总、存量迁移、物料、处置，共 44 项。

## 六、设计与实现的差异

D 文档是 2026-10-29 早些时候的草稿，实现走了不同的路。这些差异是有意还是遗漏，需要评审时确认。

| 项 | D 草稿 | 实际实现 | 判断 |
|---|---|---|---|
| 写库存服务的方式 | 业务事务里写发件箱命令，执行器异步调用，幂等键 = 事件号，退避重试，耗尽转死信 | **本地事务里同步调用**，失败整笔回滚，键随机 | 实现更简单、界面即时反馈，但丢了恢复能力，见 G1 |
| 客户端 | 引用 `inventory-client` | 自写 `HttpInventoryApi` | `inventory-client` 尚未发布到 Nexus（ai-shop Q5），暂合理，见 G6 |
| 库存服务不可用时 | 查询提示不可用，写入排队，恢复后自动完成 | 写入直接失败 | 与同步方式一致；E2E-10 未覆盖 |
| 本地阶段表示 | 设备加 `inv_stage` 等投影列，由事件处理回写 | 本地端口同事务直接写，事件只补库存侧发生的变化 | 本地为权威展示，库存服务为账，**两本账靠对账兜底**，而对账没做 |
| 迁移 | 配合库存服务做 dry-run、切换、回滚演练 | 自写 `InventoryMigration`，试跑可重跑 | 与库存服务自带导入接口重叠，见 G3 |
| 回滚 | 切换后不重新打开本地写，避免双写 | 本地投影始终完整，把 `inv.engine` 改回 `LOCAL` 即回滚 | 比 ai-shop 手册的「回滚后要补录」简单，前提是所有动作都由 ShareHub 发起 |
| 充电宝 | 一期按数量（D Q2） | 按序列号入库；出库池只有柜 | 与 ai-shop 决定 D3 不一致，见 G5 |
| 到仓待检、质检、履历 | 新建 | 已建 | 一致 |
| 商家门户「待交付设备」、统一视图、期间报表 | 计划 | 统一视图与期间汇总已做；商家门户页签请核对 | 本文未核实门户 |

## 七、差距与风险

证据均来自代码阅读，未做运行验证。优先级按「生产切到 SERVICE 之前」判定。

### P0 · 切换前必须收口

**G1 远端成功、本地回滚后无法恢复**

- 证据：`RemoteInventoryPort` 的写方法带 `@Transactional`，并在其中调用库存服务；幂等键由 `key()` 生成，形如 `kind-` 加随机 UUID（`RemoteInventoryPort.java` 末尾）。`HttpInventoryApi` 读取超时 5 秒。
- 失败场景：
  1. `dispatch` 过账出库成功，随后「领取」被拒，异常使本地回滚；库存服务里设备已离开仓库，本地仍显示在仓，再次出库会被对方拒绝（序列号已不在库）。
  2. 多个来源仓时循环建单，前一个仓已过账，后一个仓失败，整笔回滚但前一单留在远端。
  3. 回包超时或进程崩溃：远端已提交，本地未提交，重试用新随机键，不会命中「同键重放返回原结果」。
  4. 回仓入库在过账后「业务确认」失败，设备在远端停在退货待确认冻结。
- 现成手段：库存服务有 `GET /commands/{requestId}` 与 `GET /dispatch-pool/claims/by-request/{requestId}`，ShareHub 都没用。
- 建议（任务 1）：**先落命令、再调用**。在独立事务里写一行 `inventory_command`（命令号、动作、业务引用、状态 PENDING），用命令号作幂等键调用，成功后标 DONE；本地事务回滚时命令行仍在。再加一个补偿任务，对 PENDING 命令用 `GET /commands/{requestId}` 查结果，按结果补本地或冲回远端。保留同步调用的即时反馈，不改成 D 草稿的全异步。

**G2 没有对账**

- 证据：`inv/remote/` 下没有对账任务；D 的 PB-A4（每日对账主数据）与 PB-A6（每日对账序列号、出库池与本地归属、未完成命令）都未实现。现有的失败信号只有 `inventory_inbox` 的 FAILED 行和日志。
- 影响：本地与库存服务是两本账，G1 的任何残留、库存服务界面上的直接操作、手工改库，都没有发现途径。
- 建议（任务 2）：每日任务只报不改——逐序列号比对「库存服务在库 / 在出库池」与本地「在仓 / 已出库待绑定」，核对未完成命令，差异进运营待办。同时把收件箱 FAILED 条数接入告警。

**G3 存量迁移口径与重复造轮子**

- 证据：`InventoryMigration` 以 `PURCHASE` 入库（`InventoryMigration.java:110`），放行凭证缺省 `MIG-{设备号}`（`:188`）。ai-shop 对存量的约定是 `OPENING` 用途、依据 `MIGRATION`，报表单列；并提供 `POST /admin/v1/owners/{ownerId}/imports?apply=`，一个事务内按仓、物料、外部目标、在仓设备补账，**只补不减**，有冲突整批拒绝，重跑报告为空即完成（手册第 5 步）。
- 影响：切换当期的「采购入库」被存量虚增，库存报表的「本期入（采购）」失真；自写迁移没有冲突检测。
- 建议（任务 3）：改用库存服务的导入接口；若保留自写版本，至少把用途改为 `OPENING`。需与 ai-shop 确认批次格式与放行凭证由谁出（Q-1）。

**G4 生产部署与启动检查未做**

- 证据：生产配置与 `deploy/tencent/preflight.sh` 里都没有 `sharehub.inventory.*`；代码里没有 `/actuator/info` 实例代号自检；ai-shop 侧「生产形态演练、设备套建库上线、库停与重启人工演练」也尚未执行。
- 要补的清单（任务 4）：
  - 设备套建库 `neargo_inv_device`、账号、systemd 单元、开通 `SHAREHUB` 业主、装档案、签凭证；
  - 备份：把新库加进 `deploy/tencent/backup-to-cos.sh` 的库清单（手册要求建库同一步做，漏备库的事故发生过两次）；
  - ShareHub：`sharehub.inventory.*` 进环境文件，凭证不进仓库；预检在 `inv.engine=SERVICE` 时检查三项配置与连通性；启动自检实例代号；
  - 监控：事件积压、未确认、最久未关盘点、最久退货待确认四个指标已由库存服务暴露，需接到云监控；
  - 参数 `inv.return_warehouse` 缺省 `WH001`，生产要种入真实仓，事件投影会用到它。

### P1

**G5 充电宝没有按约定接入出库池**

- 证据：`InventoryPort` 与 `RemoteInventoryPort` 不含充电宝；调用 `createOutbound` 的只有处置、物料、迁移和柜的发货；全仓没有使用 `parentSerialNo` 或组装端点。入库时宝按序列号登记（`links.itemId` 对宝也建成序列号管理）。
- ai-shop 约定（TDD §2.6，决定 D3，Q8）：柜、宝都按序列号，宝挂在柜下；入库时由宿主质检单附柜内宝清单；出库池以柜为主记录、宝为从属，随柜调整、撤回、签收、退货；扫柜码展开。
- 推断（**待确认**）：宝在库存服务里入库后，发货时没有随柜出库，库存服务里宝的账会一直留在仓里，与实际不符。
- 建议（任务 5）：先与业务确认宝在 ShareHub 的真实流转（随柜出库，还是单独补货），再按 ai-shop 的组装关系接入；若一期不管宝的仓内账，则宝不要入库存服务，避免半套数据（Q-2）。

**G6 自写客户端，没有契约保障**

- `HttpInventoryApi` 是 313 行自写客户端，Fake 与真实服务各一份；契约变化只能靠联调脚本发现。ai-shop 的 `inventory-api`、`inventory-client` 待 M8 后发布 Nexus（Q5）。
- 建议（任务 6）：发布前保留自写客户端，但把联调脚本纳入定期执行；发布后换成 `inventory-client`，Fake 仍保留给场景测试。

**G7 事件处理与监控偏薄**

- 只投影两类事件，`DispatchClaimed`、`ReturnReceived` 等只入箱；收件箱 FAILED 只写日志。建议（任务 7）FAILED 超过阈值告警，并提供「重放」入口。

**G8 库存服务不可用时的体验**

- 同步写入下，库存服务不可用 = 所有出入库不可用。5 秒读取超时较紧，大单（多柜）可能超时并触发 G1。建议（任务 8）界面明确提示「库存服务不可用」，并按单量调整超时；这也是 G1 修复后才能安全放宽的参数。
