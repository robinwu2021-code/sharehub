## 二、验证流程

每步写明：**做什么 → 期望看到什么 → 不对的话说明什么**。
「期望」是断言，不是描述 —— 看到别的就是缺陷，当场记录。

### 阶段 A · 拓展到签约（P1–P2）

| 步 | 动作 | 期望 | 不对说明 |
|:-:|---|---|---|
| A1 | 建商机 ×2，其中一个填竞品与排他期 | 列表可见；查重对同名场地二次新建**报错并说明已有谁在跟** | 查重没生效 ⇒ 同一场地多人重复拜访 |
| A2 | 商机 1 跟进 → 推进阶段 | 阶段按状态机走；跟进记录带 `fromStage`/`toStage` | 能跳级 ⇒ 状态机没在服务端强制 |
| A3 | 商机 2 标记丢单（填原因 + 竞品） | 阶段 LOST，`lostReason`/`competitorName` 落库 | 原因可空 ⇒ 丢单分析拿不到依据 |
| A4 | 商机 1 **签约转化** | 一次生成场地方 + 站点 + **合同草稿**三者，且互相关联 | 只生成一部分 ⇒ 转化不是原子的 |
| A5 | CT-A 提交 → 运营审批通过 | 状态 DRAFT → PENDING → **ACTIVE**（不触发会签） | 停在待会签 ⇒ 阈值判定错 |

## 四、怎么执行

两种方式，**建议混用**：

1. **接口脚本**（主）：一条链路一个脚本，每步带断言，失败即停并打印上下文。
   放在 scratchpad，不进仓库（它依赖生产数据的具体编号）。
2. **浏览器**（辅）：阶段 B/C/D 的**界面**要亲眼看一遍 ——
   门禁清单的「去处理」链接、摘要卡点击筛选、完工表单的必填拦截，
   这些是接口测不出来的（接口只知道 400，不知道按钮是灰的还是点了没反应）。

## 五、清理

**全程记录每一个新建对象的业务号**，写进 `scratchpad/vt0926-created.txt`，一行一个 `表名 业务号`。

```sql
-- 按记录的业务号精确删（倒序：先删引用方）
DELETE FROM wo_handle WHERE wo_no IN (...);
DELETE FROM wo_order WHERE wo_no IN (...);
DELETE FROM dev_alarm WHERE alarm_no IN (...);
DELETE FROM dev_trial_rent WHERE cabinet_no IN (...);
DELETE FROM inv_transfer_item WHERE transfer_no IN (...);
DELETE FROM inv_transfer WHERE transfer_no IN (...);
DELETE FROM dev_powerbank WHERE powerbank_no IN (...);
DELETE FROM dev_cabinet WHERE cabinet_no IN (...);
DELETE FROM loc_site_survey WHERE site_no IN (...);
DELETE FROM loc_contract WHERE contract_no IN (...);
DELETE FROM loc_location WHERE location_no IN (...);
DELETE FROM loc_site WHERE site_no IN (...);
DELETE FROM loc_venue WHERE venue_no IN (...);
DELETE FROM loc_lead WHERE lead_no IN (...);
-- 兜底核对：名称里带标记的还有没有剩
SELECT 'venue', venue_no, name FROM loc_venue WHERE name LIKE '【VT0926】%'
UNION ALL SELECT 'site', site_no, name FROM loc_site WHERE name LIKE '【VT0926】%';
```

⚠️ **分润与结算产生的行不删**：它们由出账逻辑生成、彼此勾稽，
手工删会留下对不上的账。这些行金额极小（一站一柜八宝），
留着比删干净更安全 —— 但要在清理记录里写明「哪些是验证产生的」。
