## 1. ⚠️ 先更正：对齐脚本的输出不能直接当排期依据

`backend/scripts/api-align.py` 三方比对的原始输出是：

| 类 | 脚本报 | **实测真值** | 误报率 |
|---|---:|---:|---:|
| A 前端调、后端没有 | 0 | 0 | — |
| B 字段对不上 | 24 | 见 §2.1 | 含嵌套误报 |
| **C 后端有、前端没调**（运营端） | **113** | **18** | **84%** |

**C 类 84% 是误报**，原因是脚本的路径匹配不认模板串。例如：

```ts
saveAgentAccount: (x) => client.post(x.accountNo ? `/api/agent/accounts/${x.accountNo}` : "/api/agent/accounts", x)
```

这一行同时调了两个端点，脚本两个都报成「未接线」。把 `${...}` 与 `{param}` 归一后重算，
运营端真未接线从 113 降到 **18**。

**B 类同样含误报**：脚本把前端嵌套类型的成员拍平后与后端顶层字段比。
`DashboardStats` 报缺 `gmv/orders/pendingRefunds/pendingWithdrawals` ——
实际 `gmv/orders` 在 `trend[]` 里、另两个在 `todos` 里，**一个都不缺**。
`OperationOverview` 报缺 `total` 同理（在 `geoReady` 里）。

> [实现状态总表](./实现状态总表.md) §六 写的「131 条前端未接线，当前投入产出比最高的一块」
> 正是基于这份输出。**按它排期会去做 95 条不存在的工作。**
> 修脚本因此是 P0 的第一件事，不是可选项。

而那 18 条里还有 **9 条是 `/internal/` 的服务间调用与 cron 触发**
（`ownership/*`、`cabinets/briefs`、`settlements/generate`、`price-adjustments/tick`…），
**本来就不该由前端调**。

**⇒ 运营端真正的前端未接线，只有 6 条。**

## 3. 为什么是这个顺序

**① 先修脚本与状态表**，因为它们现在指向 95 条不存在的工作。
按错的地图走，走得越快偏得越远。

**② 假数据先于缺数据。** 环比 `+8.2%` 会被当成真实经营指标去做决策；
而一个空字段至少看得出来它是空的。**错的比没有更危险。**

**③ 权限后端驱动（P2-1）先于其余接线**，因为它是唯一改变结构的一条：
权限码的真源现在在前端硬编码里，后端改了前端不知道 —— 这类分歧与今天修的
信封、词表是同一种失效。

**④ 功能深度排在接线之后**，因为它们要么依赖录入口（经纬度），
要么依赖外部件（调度器），不是纯前端工作。

## 4. 这套方案依赖的既有地基（都已就位）

| 地基 | 状态 | 本方案怎么用 |
|---|---|---|
| 模块解耦 | ✅ 跨服务引用 **0**，Maven enforcer 强制 | 新增 api 面不会引入跨域依赖 |
| 包无环 | ✅ ArchUnit 守 | 新控制器若造环当场红 |
| 信封契约 | ✅ `EnvelopeContractTest` | 新端点的出参形状自动被守 |
| 词表棘轮 | ✅ 80 条，只准变短 | 新代码不许写裸状态串 |
| 测试隔离 | ✅ 独立测试库，迁移自愈 | 新功能的集成测试可信 |
| Port 契约 | 6 个 + `AgentDirectoryPort` | 跨域读走 Port，S5 可换远程实现 |

**这就是"基于基础架构逐步补充"的确切含义**：地基已经能接住新功能，
且每一类会漂的东西都有一条会红的断言守着。
