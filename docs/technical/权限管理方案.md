## 0. 两条主线（先分清）

| 概念 | 回答的问题 | 机制 | 承载 |
|------|-----------|------|------|
| **认证 Authentication** | 你是谁 | 凭据校验 → 签发会话/Token | `neargo-auth-core`（`pb_auth` 凭据库，`realm` 分池）|
| **功能授权 Authorization** | 能做什么操作 | RBAC 权限码 `@PreAuthorize` | `iam_role/iam_permission/iam_role_permission` |
| **数据授权 Data Scope** | 能看/改哪些数据 | 归属链条件注入 SQL | `iam_data_scope` + `TenantContext` |
| **审计 Audit** | 谁在何时做了什么 | 切面留痕（WORM）| `OperateLog` → `audit_log` |

**运营端（员工/代理）= 认证 + RBAC 功能权限 + 数据权限**（细粒度）。
**C 端（消费者）= 认证 + 资源属主鉴权**（无 RBAC，只能操作"自己的"数据）。

## 1. 主体与身份域（Principal / Realm）

powerbank 有 5 类被授权主体，凭据分池存于 `pb_auth.cred_credential`（`realm` 列区分），授权模型与数据隔离键各不同：

| 主体 | 载体端 | 凭据池 `realm` | 授权模型 | 数据隔离键 |
|------|--------|---------------|---------|-----------|
| **员工 / 运维** | 运营端 Web · Ops App | `STAFF` | RBAC（功能权限码 + 数据权限）| `tenant_id` + `data_scope`（区域/站点/点位）|
| **代理商** | 代理端（uni-app / 受限 ops-web）| `AGENT` | RBAC **受限子集** + **强制 `agent_no`** | `tenant_id` + `agent_no`（硬过滤）|
| **C 端用户** | App（P0）· 小程序（P1）| `CONSUMER` | **资源属主鉴权**（无 RBAC）| `tenant_id` + `c_user_no`（`openid×tenant`）|
| **设备 / 柜机** | MQTT(EMQX) · TCP(Netty) | —（auth-core 签发设备 JWT，非账号池）| topic ACL / 首帧绑定 | `sn` 命名空间（region+tenant claim）|
| **第三方** | OpenAPI | —（`openapi_app` AppKey/Secret）| AppKey 签名 + `scope` + 限流 | `tenant_id` + `scopes` |

> 员工与代理**共用 auth-core 凭据机制**，靠 `realm` + 角色区分；C 端是独立消费者池。设备鉴权是**连接级 JWT**（每连接签发，claim 带 region/tenant），不落账号池。

## 2. 认证 Authentication

### 2.1 凭据存储（`pb_auth`，独立 KMS）
- 库 `pb_auth.cred_credential`：**仅 `neargo-auth-core` 访问**，独立 KMS（PDPL，ADR-010）。`realm` 分池：`STAFF` / `AGENT` / `CONSUMER`。
- 业务域**不落凭据**，只持 `user_id`（员工/代理，→`iam_employee.user_id` / `agt_account`）或 `c_user_no`（C 端，→`usr_user`）逻辑引用。
- 敏感明文（手机号/证件/密码 hash）不进 `pb_core`：密码 hash 在 `pb_auth`，手机号/证件在 `pb_pii`（独立 KMS，脱敏访问）。

### 2.2 各端登录方式
| 主体 | 登录方式 | 建户/绑定 |
|------|---------|----------|
| 员工/运维 | 账号 + 密码 / OTP（auth-core）| 后台开通 `iam_employee` → 绑 `user_id` |
| 代理商 | 同员工池，`realm=AGENT` | `agt_account` 开通（BD `agent:account:manage`）|
| C 端 App | 手机号 OTP / Apple / Google（`C-AC-01`）| `openid×tenant` 建 `usr_user`（`UK(tenant_id,openid)`）|
| C 端 小程序 | 微信 `code→openid` 一键 | 同上（`POST /mp/user/login`）|
| 设备 | auth-core 签发设备 JWT（clientId=sn，claim region/tenant）| `gw_device_binding`（SN↔cabinetNo）|

### 2.3 会话与 Token（复用 auth-core + common-security）
- **不透明 Token**：auth-core `TokenIssuer` 签发 → `OpaqueTokenAuthFilter` 校验 → `SessionStore`（Redis）。
- **吊销/OTP**：`RevokeService` / `OTP`（auth-core），支持登出、强制下线、验证码。
- C 端会话走 `/mp/**`（C 池）；员工/代理会话走各端 BFF（换取可信头后进 `/api/**`）。

### 2.4 边缘 → 内部的可信头（`AuthHeaders`，边缘注入、内部只读）
认证只在**边缘（BFF/网关）**做一次；内部域**信任头、不重复认证**：

```
客户端 ──登录──> BFF/边缘
   BFF: 校验会话 → 解析出 身份/角色/数据范围 → 注入可信头 ↓
   ┌────────────────────── AuthHeaders（common-security）──────────────────────┐
   │ X-Region-Id · X-User-Id · X-Merchant-Id(承载 powerbank tenant_no,ADR-007) │
   │ X-Roles(角色码,供 @PreAuthorize) · X-Store-Scope(数据范围)                 │
   └───────────────────────────────────────────────────────────────────────────┘
   → TenantContextFilter 写 TenantContext → TenantPropagationInterceptor 跨 RestClient 透传
```
> **可信头边界是安全红线**：客户端伪造的同名头在入口一律**剥离重置**（api/README §1.3）。`X-Merchant-Id` 是 commons 原名，语义承载 powerbank `tenant_no`，域内经 `PowerbankTenantLineHandler` 映射到 `tenant_id` 列（ADR-007，避免与"点位商户 venue"命名冲突）。

## 3. 路径分层鉴权（对齐 api/README §1.2）

不同路径前缀对应不同的**认证方式**，是第一道闸：

| 前缀 | 面向 | 认证方式 | 授权 |
|------|------|---------|------|
| `/api/**` | 运营端 BFF → 内部域 | 受信头（BFF 已换取 `AuthHeaders`）| **RBAC `@PreAuthorize` + 数据范围** |
| `/mp/**` | C 端 App/小程序 BFF | C 端会话（auth-core `CONSUMER` 池）| **资源属主校验**（`c_user_no`）|
| `/internal/**` | 域间 RestClient | 内网 + 受信头透传 | 调用方域信任（不对外暴露）|
| `/gw/**` | 硬件供应商南向回调 | **供应商验签**（`DeviceDriver.verify`）| 按 `vendor_code` 命名空间 |
| `/notify/**` | 支付渠道（nearpay）异步回调 | **渠道验签** | 幂等 + 引用匹配 |
| `/openapi/**` | 第三方 | **AppKey 签名 + 限流** | `openapi_app.scopes` |

## 4. 授权 —— 运营端（员工 / 代理）

### 4.1 功能权限（RBAC 权限码）
- **权限码规范**：`<模块>:<资源>:<动作>`（小写点分），通配 `<模块>:*` / `*`。完整矩阵见 [功能权限清单.md](../requirements/功能权限清单.md)（14 模块 + 平台口子），**这是前后端唯一权限码来源**。
- **角色集（单运营方内部）**：`ADMIN`(全) · `OPS`(设备/工单/库存/OTA) · `CS`(订单干预/退款申请/风控/报障) · `FINANCE`(财务/分润/结算/提现/对账) · `BD`(点位/场地方/合同/CRM) · `VIEWER`(只读) · `AGENT`(代理，见 §4.3) · 🔒`PLATFORM_ADMIN`(多租户口子，休眠)。
- **存库**（`pb_core.iam_*`）：
  - `iam_permission`（全局权限目录，`perm_code` UK）
  - `iam_role` + `iam_role_permission`（角色→权限码；内置角色**只读**，可后台维护自定义角色）
  - `iam_employee` / `iam_dept`（员工与组织）
- **两点强制（纵深防御）**：
  1. **BFF 预校验**：菜单/按钮级，`POST /internal/platform/authz/check`（+ 前端 `can('device:command:send')`，仅体验，非安全边界）。
  2. **域内 `@PreAuthorize`**：`@PreAuthorize("hasAuthority('order:refund:audit')")`，读 `X-Roles`/authorities，**每个写接口必挂**——即便 BFF 漏挡，域内仍拒。权限码常量集中在 `powerbank-common-api`。

### 4.2 数据权限（Data Scope）
功能权限之上再收敛**能操作哪些数据**，按归属链（[领域模型](./领域模型-本体与关系.md)：Venue→Site→Point→Cabinet；agent_no 归属）：

| 维度 | 语义 | 典型角色 | MVP |
|------|------|---------|-----|
| `ALL` | 全域 | ADMIN/FINANCE/VIEWER | ✓ |
| `REGION` | 按区域 | 区域运维/BD | ✓ 首期 |
| `SITE` / `LOCATION` | 按站点/点位 | OPS/BD | ✓ 首期 |
| `VENUE` | 按场地方 | 场地方对接 | ✓ 首期 |
| `AGENT` | **强制自己 `agent_no`** | AGENT | **✓ 首期必做**（ADR-012）|
| `SELF` | 自己经手 | CS（客服会话）| ✓ |

- **存库**：`iam_data_scope(role_no, scope_type, scope_ref)`。
- **落地**：`TenantContext` 承载当前用户数据范围 → **数据范围拦截器**（MyBatis-Plus，类租户 handler 机制）自动在 SQL 拼 `agent_no in (...)` / `region_id in (...)` / `site_no in (...)` 条件，**防漏过滤**。
- **`AGENT` 是红线**：代理登录后 `agent_no` 从会话强制注入，**任何查询/操作只见自己归属**的设备/点位/订单/收益，前端传入的 agent_no 一律忽略。

### 4.3 代理端（`AGENT` 角色）
- **= 运营端权限码的受限子集 + 强制 `agent_no` 数据范围**，**不新造码**（唯一新增 `finance:withdrawal:apply` 供代理自助提现）。持有：我的看板/我的设备(查)/设备报修(开工单)/我的订单(脱敏查)/我的收益分润(查)/提现申请/我的点位(查)。
- 端形态：uni-app 代理端 或 ops-web 受限视图（我的设备/订单/收益/提现/报修）。凭据 `realm=AGENT`。

## 5. 授权 —— C 端（消费者）

**核心区别：C 端无 RBAC，只有"属主鉴权"——每个人只能操作自己的数据。**

### 5.1 资源属主鉴权（服务端强制，不信前端）
- C 端会话解析出 `c_user_no` + `tenant_id`，**所有 `/mp/**` 资源访问在服务端强制加 `where c_user_no = <会话值> and tenant_id = <会话值>`**。
- 订单/钱包/券/会员/报障/发票一律按属主过滤：
  - `GET /mp/trade/orders` → 只返回本人订单；`GET /mp/trade/orders/{orderNo}` → **校验该单属主 = 当前会话**，否则 403（防横向越权 IDOR）。
  - `POST /mp/user/report`、`GET /mp/user/wallet`、`GET /mp/user/coupons` 同理。
- **不信任前端传参**：即便请求体带了 `c_user_no`/`order_no`，服务端以会话为准，做属主二次校验。

### 5.2 数据隔离（openid × tenant）
- `usr_user` `UK(tenant_id, openid)`：同一微信/手机在不同租户是不同账户，天然隔离。
- 隔离键 `tenant_id` 由 `Neargo/PowerbankTenantLineHandler` 自动注入，C 端也走同一套租户条件（MVP 恒 `MAIN`）。

### 5.3 敏感数据与脱敏（PII）
- 手机号/实名/证件在 `pb_pii`（独立 KMS，区域驻留，PDPL）；C 端接口返回一律经 `Sensitive` 脱敏（掩码），完整值不下发到端。
- 支付/免押不落渠道明文（委托 nearpay，ADR-005）。

### 5.4 隐私合规（PDPL，`C-AC-03`）
- 授权同意（登录/免押授权）、账号注销、数据导出/删除，均需可执行并留痕；ar/en 协议。注销触发凭据吊销 + PII 删除/匿名化。

## 6. 设备与第三方鉴权（补全南向/开放）

### 6.1 设备（access-gateway）
- **MQTT 型**：clientId=`sn`，auth-core 签发 JWT（claim region/tenant），EMQX **broker ACL** 限设备只能收发自己命名空间 `pb/{region}/{tenant}/device/{sn}/#`（TDD-access-gateway §3.6）。
- **TCP 型**：Netty `channelActive` 首帧鉴权 → 绑定 SN → 会话入 Redis。
- **HTTP 回调**：`/gw/vendors/{vendor}/callback` 必经 `DeviceDriver.verify` 验签，密钥 `gw_vendor_config`（KMS）。
- 设备**只认 SN、不碰业务鉴权**，越权面收敛为"设备只能上报自己 SN 的事件"。

### 6.2 第三方（OpenAPI）
- `openapi_app`（`app_key` / `app_secret` hash / `scopes` JSON / status）；`/openapi/**` 走 AppKey 签名（时间戳+nonce+签名防重放）+ `scope` 授权 + 限流。首期开放范围待定（设备状态/订单查询/对账）。

## 7. 审计 Audit

- **切面**：`neargo-common-web.OperateLog` 自动留痕，落 `pb_core.audit_log`（`append`/WORM，按 `created_at` 月分区）。
- **必审计动作**（功能权限清单 §三）：所有 `create` / `update` / `delete` / `*audit*` / `*intervene*` / `*refund*` / `command`（设备指令）+ 🔒**跨租户切换**。
- 字段：`tenant_id, user_id, action, target_type, target_no, detail JSON, ip, created_at`。
- 财务/风控类高危操作（提现审核、退款审批、拉黑、强制归还）审计**不可省**，供合规追溯。

## 8. 多租户口子（休眠，ADR-011）

- `tenant_id` 全链路隔离机制**全建**（列/handler/上下文/透传），但**管理面 MVP 不做**：单主租户 `tenant_no=MAIN`，上下文默认注入，无前台切换。
- 🔒`PLATFORM_ADMIN` + `tenant:switch`（跨租户切换）**后置 P1+**：白名单角色放行 + **强制 `OperateLog` 审计**；引入第二个隔离经营实体（如充电桩业态）时才启用。
- 平台大盘 `dashboard:platform:read`、租户开通/配额/SaaS 计费均属口子，MVP 空置。

## 9. 落地清单与责任分工

| 层 | 组件/表 | 责任 |
|----|---------|------|
| 认证 | `pb_auth.cred_credential`(realm) · auth-core `TokenIssuer/RevokeService/OTP/SessionStore` | 登录/会话/吊销 |
| 可信头 | common-security `AuthHeaders/TenantContextFilter/OpaqueTokenAuthFilter/TenantPropagationInterceptor` | 边缘注入、内部透传 |
| 功能权限 | `iam_permission/iam_role/iam_role_permission/iam_employee/iam_dept` · `@PreAuthorize` · `powerbank-common-api` 权限码常量 | 角色→码→接口 |
| 数据权限 | `iam_data_scope` · `TenantContext` · 数据范围拦截器（MyBatis-Plus）| 归属链 SQL 注入 |
| C 端属主 | `usr_user`(UK tenant×openid) · `/mp/**` 属主校验 | 横向越权防护 |
| 设备/第三方 | `gw_vendor_config`(KMS 验签) · EMQX ACL · `openapi_app` | 南向/开放鉴权 |
| 审计 | `OperateLog` → `audit_log`(WORM) | 高危留痕 |
| 端点 | `POST /internal/platform/authz/check` · `GET /api/platform/permissions` · `GET/POST /api/platform/roles` | BFF 鉴权 & 角色维护 |

**前端映射**：ops-web `lib/permissions.ts`（角色→码 + `can()`/`canModule()`）由本方案 + 功能权限清单生成；C 端无 RBAC，仅按会话渲染"我的"数据。
