## 1. 目标

一句话：**菜单是资源的一种，用户经角色拿到资源，服务端按此决定菜单与接口，两者同一份判定。**

拆成可验收的四条：

1. 一个人能看到哪些菜单，**只由他的角色持有的权限码决定**，判定发生在服务端一处；
2. 菜单项挂的权限码，**必须是后端真的在强制的那个码** —— 挂一个没人强制的码，
   等于这个菜单对谁都不可见（除超管）而**没有任何报错**；
3. 用户 → 角色 → 权限码 → 菜单，四段**都在库里**，改完不发版即生效；
4. 每一段都有一条**会红的测试**盯着，而不是靠约定。

## 2. 模型

### 2.1 三类资源，一种表达

| 资源 | 落在哪 | 今天怎么判 |
|---|---|---|
| **接口** | `@PreAuthorize("@perm.can('x:y:z')")` | 服务端，158 个码 |
| **菜单** | `iam_menu.perm` | 刚迁进库（V67），**尚未用于判定** |
| **页内按钮** | 前端 `allow('x:y:z')` | 前端，经 `UI_PERM_MAP` 翻译后比对 |

三者统一的前提是**同一套码**。目录表 `iam_permission` 就是这套码的清单 ——
它同时是角色勾选树的数据源、菜单挂码的选择器数据源。

> ⚠️ **按钮那一侧短期内统一不了**：`UI_PERM_MAP` 现有 8 条翻译，
> 存在的原因是某些界面能力**没有专属端点**（如「站点概览」映到 `location:poi:read`）。
> 这属于 SSOT 缺码，不是实现问题。菜单这一侧**可以现在就统一**——
> 实测 96 个带码的菜单叶，需要翻译的是 **0 个**。

### 2.2 授权链

```
iam_employee ──(iam_employee_role)──> iam_role ──(iam_role_perm)──> iam_permission
                                          │                              │
                                          │                              │ 引用
                                    iam_data_scope                  iam_menu.perm
                                    （正交的第四维：                      │
                                      看得到哪些行）              服务端过滤后下发
```

**数据范围（`iam_data_scope`）是正交维度**，不参与菜单可见性：
权限码决定「能不能进这个页面」，数据范围决定「进去之后看得到哪些行」。
两者混在一起谈是上一轮设计反复卡住的原因。

### 2.3 菜单授权：三种模型，选 C

| | 模型 | 后果 |
|---|---|---|
| A | 菜单可见性**完全**由 `menu.perm` 推出 | 简单、不可能分叉；但无法「有权限但不给入口」 |
| B | 菜单单独授权（`iam_role_menu`） | 能精细定制；**但会出现「有菜单没权限」（点了 403）和「有权限没入口」** |
| **C** | **以 A 为底，允许按角色显式「排除」，不允许显式「新增」** | 可定制，且**结构上不可能**出现「有菜单没权限」 |

**选 C**。可见性 = `hasPerm(menu.perm)` **且** 未被该角色排除。
B 的两种分叉正是本仓库反复踩的那一类（前端显示后端 403 / 后端允许界面没入口），
而它们**都不报错**。C 用一张排除表换来定制能力，代价是「排除」这一侧要有卡口
（排除到一个角色看不到任何菜单时应当拒绝保存）。

排除表 `iam_role_menu_deny(role_no, menu_no)` —— 命名用 deny 而不是 allow，
是为了让任何人读到表名就知道它只能减不能加。

## 3. 现状：四段链条，两段是断的

全部为 2026-09-24 生产实测：

| 环节 | 表 / 位置 | 生产数据 | 状态 |
|---|---|---|---|
| 登录 → 用户 | `AuthController.login` | — | **断**：生产只有硬编码 `admin` + 口令闸，从不读 `iam_employee` |
| 用户 → 角色 | `iam_employee_role` | **0 行** | **断**：表和同步代码都在，但员工是种子直灌的，没走过 service |
| 角色 → 权限 | `iam_role_perm` | 116 行 / 8 角色 | 通，在用 |
| 权限目录 | `iam_permission` | **57 条** | **缺 118 条**：后端强制 158，目录只有 57；另有 17 条目录里有而没人强制 |
| 菜单 → 权限 | `iam_menu` | 127 行（V67 刚灌） | 新建；**13 个叶子没有码** |
| 数据范围 | `iam_data_scope` | 1 行 | 读取刚修好（`9af5a21`），员工级此前存得进读不出 |

两个数字值得单独说：

- **目录 57 / 强制 158** —— 角色勾选树是从目录渲染的，
  也就是说**今天的管理界面连 3/4 的权限都选不出来**。
  「统一管理」在目录补齐之前无从谈起。
- **`iam_employee_role` 0 行** —— 用户到角色这一段是空的。
  在真实员工登录落地之前，「按用户动态展示菜单」里的「用户」还不存在。

## 4. 实施路径

每一步都能独立上线、独立回滚，且各配一条卡口。

### P0 · 资源目录补齐（前提）

- 从 `@PreAuthorize` 扫出 158 个码，灌进 `iam_permission`，带模块与中文名；
- 17 条「目录里有但没人强制」的逐条定性：是待建功能，还是该删；
- **卡口**：后端强制的每个码都必须在目录里。新加一个 `@perm.can('新码')`
  而忘了登记，CI 就红 —— 否则表现是「管理员在勾选树上找不到这个权限」。

### P1 · 菜单按权限过滤（服务端一处判定）

- **补齐 13 个无码叶子**。它们今天靠「跟随父模块」隐式可见，
  服务端按码过滤表达不了这条隐式规则。实测：不补则每个角色**多出 7–15 项**
  （SLA 管理、巡检计划、营销活动、客服会话、四张报表……）。
  这正是 `nav.ts` 注释里记过的旧伤：*「靠无 perm 的叶子跟随父模块，漏出了 SLA 管理 / 巡检计划 / BD 拓展 CRM」*。

  | 叶子 | 挂 |
  |---|---|
  | 工单 › SLA 管理 / 巡检计划 | `workorder:sla:update` / `workorder:inspection:update` ⚠️见 §7 |
  | 营销 › 活动 / 邀请裂变 | `marketing:campaign:read` / `marketing:referral:read` |
  | 营销 › 广告位 / 广告活动 / 投放曝光 | `marketing:ad:read` |
  | 客服 › 报障受理 / 客服会话 | `cs:ticket:read` / `cs:session:read` |
  | 报表 › 财务 / 大屏 / 自定义 / 消费者 | `report:{finance,screen,custom,consumer}:read` |

- **`portalFor` 规则挪到服务端**（3 个 section）：命中门户角色只看门户，其余角色看不到门户；
- 服务端按 `hasPerm(menu.perm)` 过滤 + 剪掉无可见叶子的 section。
  此后 `module`/`modules` 不再参与可见性，只留作路由归属；
- **卡口（本阶段最重要的一条）**：切换前后，**每个角色看到的菜单逐项相同**。
  上面那「多出 7–15 项」就是靠这个对拍测出来的 —— 没有它，
  漏出的菜单项不会有任何症状，直到某个角色点进了不该进的页面。

### P2 · 前端切数据源

- `NAV` 从编译期常量改为由 `GET /api/auth/menus` 填充，**23 个导出函数不动**；
- 删掉菜单的前端判权（服务端已判）；
- **保留** `phase` / `ready` / `soon` 的门禁 —— 它们是产品分期与构建属性，不是权限。
  `soon` 尤其不能进库：它由 `pageReady(page, useMock)` 算，取决于前端连 mock 还是真后端；
- 外壳处理首屏 loading：菜单到达前导航是空的，不能闪成「什么都没有」。

### P3 · 用户 → 角色打通

- 登录改为读 `iam_employee` + `iam_employee_role`（多角色取并集）；
- 回填现有 5 个员工的 `iam_employee_role`；
- 这一步同时解锁**员工级数据范围**：`scopeOf` 按 `userNo` 认人，
  而生产会话的 `userNo` 今天是 `admin`，匹配不到任何 `employee_no`
  （已写在 `PermissionService.scopeOf` 注释里）；
- **卡口**：同一个人挂两个角色时，权限是并集；停用员工立刻失去全部菜单。

### P4 · 统一管理界面（到这一步才兑现「不发版改菜单」）

- **角色**：权限勾选树（数据源 = 补齐后的 158 条目录）+ 该角色可见菜单预览（只读，实时算）；
- **菜单**：树的增删改 / 排序 / 显隐 / 挂码。挂码从目录里选，**挂不出不存在的码**；
- **员工**：分配角色（多选）+ 数据范围（已有抽屉，subjectType 传 EMPLOYEE）；
- **卡口**：保存菜单时校验 `perm` 在目录内；排除规则不得让某角色可见菜单为空。

### P5 · 收尾

- 删 `nav.ts` 里的硬编码菜单数据（函数留着）；
- 删重复端点：`GET /api/platform/iam/menus`（与 `/api/auth/menus` 重复）、
  `GET /api/auth/permissions`（与 `/me` 的 `perms` 重复）、
  `GET /api/platform/iam/roles` 列表（与 `/api/platform/roles` 重复且直接返实体）；
- `MenuPermissionContractTest` 从扫 `nav.ts` 改为扫迁移数据。

## 7. 待定（需要拍板）

1. **SLA 管理 / 巡检计划挂什么码**：后端只有 `:update`，没有 `:read`。
   挂 `:update` 等于「只有能改的人看得到」，而今天 VIEWER / BD 都看得到。
   三选一：后端补 `:read` 码 / 就挂 `:update`（一次真实的可见性收窄）/ 这两项暂不挂码。
2. **模型 C 的排除表要不要现在建**：不建则 P1–P3 就是纯 A 模型，够用；
   建了才有「同一角色不同人看不同菜单」的能力。
3. **17 条「目录里有但没人强制」**：逐条定性为待建功能还是删除。

## 8. 边界

- `UI_PERM_MAP` 不会消失：它服务页内按钮的 8 条翻译，根因是 SSOT 缺码；
- `phase` / `ready` / `soon` 永远留在前端，它们不是权限；
- P4 之前，加一个菜单项要写迁移（今天是改一行 TS，**更麻烦**）。
  这是 P1–P3 期间的真实代价，不应被略过不提。
