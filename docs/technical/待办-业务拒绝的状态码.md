# 待办：业务拒绝不该落 500

> 2026-09-25 建立。**自包含工单**：背景、判据、逐处清单、怎么改、怎么验，不需要读前面的对话。
>
> 起因：核 C 端闭环时发现刚上线的领券功能里「券已领完」返回的是
> HTTP 500「服务器错误」，并且在应用日志里留下一行 `ERROR 未处理异常` 带堆栈。

## 先读：为什么这类缺陷两头都疼

`GlobalExceptionHandler` 目前映射三种异常，**`IllegalStateException` 不在其中**：

| 异常 | 映射 | 出处 |
|---|---|---|
| `ServerException` | `Result.error(code, msg)`，**HTTP 200** | neargo-common-core |
| `IllegalArgumentException` | 400 | 本仓库自管 |
| `AccessDeniedException` | 403 | 本仓库自管 |
| `ResponseStatusException` | 保留其状态与 reason | 本仓库自管 |
| **其它（含 `IllegalStateException`）** | **500 + `log.error` 带栈** | 兜底 |

于是 48 处 `throw new IllegalStateException` 全部落兜底，代价是两头的：

- **调用方拿不到真原因。**「券已领完」「仅 HELD 押金可解冻」「投诉已结案」返回的
  都是同一句「服务器错误」。用户不知道该改什么，客服也问不出来；
- **ERROR 级别失去意义。** CLAUDE.md 定的口径是「ERROR = 需要人介入且不介入会持续出错」，
  而券领完不需要任何人介入。这类噪音会把真告警埋掉 —— 而
  [日志规范](../../CLAUDE.md) 里那句「噪音会让真告警被忽略」正是这个意思。

**它一直没被发现的原因**：全仓库**零个测试断言过这些路径的状态码**
（`grep 'isEqualTo(500)' → 0 处`）。没有人钉过，所以没有人红。

## 判据：哪些改、哪些不改

一刀切映射 `IllegalStateException → 409` 是**错的**，会把
`HMAC 不可用`、`会话序列化失败`、`跨服务调用失败` 变成 4xx 并停止记录堆栈 —— 比现在更糟。

分三类，**只有 A 类改**：

| | 类别 | 处数 | 判据 |
|---|---|:--:|---|
| **A** | **业务拒绝** | **22** | 调用方改个做法就能成功；不需要任何人介入；重试无用但换条件有用 |
| B | 基础设施 / 不可能发生 / 配置缺失 | 24 | 需要人介入（补配置、修数据、修环境），不介入会持续出错 |
| C | 已被控制器 `catch` 成 429/403 | 2 | 已经是对的 |

## ⚠️ C 类是最容易踩的坑（先看这条再动手）

`AuthController` 已经在两处 `catch (IllegalStateException)` 并转成 `ResponseStatusException`：

```java
// AuthController:178 —— 重发过频（OtpGate 节流）
} catch (IllegalStateException e) {
    throw new ResponseStatusException(HttpStatus.TOO_MANY_REQUESTS, e.getMessage());

// AuthController:285 —— 名下一个主体都没有
} catch (IllegalStateException e) {
    throw new ResponseStatusException(HttpStatus.FORBIDDEN, e.getMessage());
```

改了对应 service 的抛出类型，这个 catch **静默失配**，异常落到兜底 ⇒
**429 变 500、403 变 500，而且没有任何编译错误**。

所以：`user/consumer/OtpService.java:73`（发送过于频繁）与
`agent/ext/service/impl/AgentLoginServiceImpl.java:107`（没有可用运营主体）
**本次不动**。它们是「已经对了」，不是「还没改」。

> 动每一个抛出点之前重扫一次：
> `grep -rn "catch (IllegalStateException" backend --include='*.java' | grep -v /test/`
> 另一条线随时可能加新的 catch。

## 目标形状

复用已有的 `ServerException`（`ErrorCode.CONFLICT` = 409，已确认字节码里是 409），
并给 handler 补 HTTP 状态 —— **让状态码由业务码推导，而不是恒 200**：

```java
@ExceptionHandler(ServerException.class)
public ResponseEntity<Result<Void>> onServer(ServerException e) { ... }
```

**两端前端无需改动**，已确认都优先取 body 里的 message：

```
ops-web/lib/api/http-client.ts   const msg = body.message || translate(curLocale(), statusKey(r.status));
c-app/src/api/http-client.ts     reject(new Error(body?.message || `HTTP ${res.statusCode}`));
```

所以 `409 + {code:409, message:"券已领完"}` 会原样显示给用户。

## 待裁决（不在本次范围，但要有人看一眼）

**`PriceResolver:83` 未匹配到计价方案，现在是 500。** 它的消息自己写着
「**拒绝结算而非按 0 收费** —— 静默免单无法被发现」，这个判断是对的。
但调用方是**正在扫码借电宝的 C 端用户**，他看到的是「服务器错误」。

两种口径都说得通，需要产品定：

- **(a) 保持 500**：这确实是配置缺失，需要运营介入，ERROR + 告警是对的；
- **(b) 对 C 端回 409「该点位暂不可借」，同时仍打 ERROR 日志**：用户看到能理解的话，
  运维照样收到告警。代价是状态码不再区分「配置缺失」和「业务拒绝」。

倾向 (b)，但它改变的是**用户看到什么**，不是纯技术选择。

## 不在本次范围：消息的 i18n

改完之后用户第一次看到的是 `券已领完` 这句**中文** —— 比「服务器错误」好，
但在阿语/英语界面上仍是中文。

**不顺手做的原因不是懒，是它不止加几行 properties**：22 条里大多带插值
（`"仅 FROZEN 可请款，当前：" + e.getStatus()`），而

- `ServerException` 只有 `(ErrorCode, String)` 构造器，**带不了参数**（它在外部 jar 里，改不了）；
- `GlobalExceptionHandler` 调的是 `Messages.msg(e.getMessage())`，**不传 args**。

要 i18n 化得先加一个能带 `Object... args` 的项目内异常类型，那是另一个设计决定。
另外后端消息包现在只有 **6 条 key**（`backend/sharehub-common/src/main/resources/i18n/messages*.properties`），
这条线还没真正开张 —— 一起排更合适。

## 执行步骤

1. **补 handler + 状态码推导**（`GlobalExceptionHandler`）。
   验收：单元用例 3 条 —— 409 / 404 / 无法解析的码回 200。
2. **先扫 catch 再改 throw**（见上方 ⚠️）。每批开始前重扫一次。
3. **按批改 22 个抛出点**，三次提交。
4. **棘轮** `backend/known-raw-illegal-state.txt`（只准变短）+
   `BizRejectionNotRawIllegalStateTest`：扫 `**/service/impl/**` 与 `*StateMachine.java`，
   裸抛必须在台账里；台账种 B 类那几条并逐条写明「为什么它该是 500」。
5. **API 层用例** `BizRejectionStatusTest`：挑 3 个代表
   （券已领完 / 押金已解冻不能买断 / 冷静期内重复申请注销），
   断言 **HTTP 409 且 `message` 是业务原话**，不只是「不是 200」。
6. **日志核对**：全量跑完确认 `未处理异常 → 500` 的出现次数下降，剩下的都属 B 类。
