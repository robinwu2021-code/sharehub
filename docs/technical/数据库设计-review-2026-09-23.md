## 〇、总体判断

结构是好的。三条主线——**场所归属链**（站点 → 点位 → 设备）、**资金链**（分润 → 结算 → 提现 → 复式记账）、
**订单主表 + 形态扩展**——都建对了，而且扩展表用 `order_no` 作主键、费率在记录上落快照、
迁移一律 `IF NOT EXISTS`，这些是经验的痕迹，不是新手 schema。

问题集中在两类：**一个真缺陷（幂等键含可空列）**，和**一批约定漂移**（软删除、币种、枚举宽度）。
审计列原本被我列为漂移，**核对后撤销**——V10 已经统一补齐，见勘误。

| 级别 | 条数 | 概览 |
|---|:-:|---|
| 🔴 真缺陷 | 2 | 幂等键含可空列（潜伏）· 业务键无唯一索引 |
| 🟠 会在已排期的事情上绊倒 | 3 | 金额无币种 · 取价表结构不足 · 分润表撑不住责任模型 |
| 🟡 约定漂移 | 4 | 软删除双轨 · `tenant_id` 残留 · 比率精度 · 枚举宽度（**审计列已撤销**，见勘误） |
| 🔵 待办登记 | 2 | ADR 所需 DDL 12 项未建 · `EV_PILE` 改名 |

## 一、🔴 真缺陷

### 1.1 `share_record` 的幂等键含两个可空列 —— 约束形同虚设

**证据**

```
share_record.payee_no    VARCHAR(36) NULL
share_record.dimension   VARCHAR(16) NULL          -- V37 新增时就是 NULL
V37: ADD UNIQUE KEY uk_srec_order_payee (order_no, dimension, payee_no)
```

**问题**：MySQL / MariaDB 的 `UNIQUE` **不约束 NULL** —— 两行 `(OD001, NULL, NULL)` 可以共存。
而 V37 的整个存在理由是「outbox 重投是设计内的，没有唯一键重投一次就把分成记第二遍，钱会被真的多算一次」。
只要有任何一条写入路径让 `dimension` 或 `payee_no` 为空，**这道闸门对那条路径静默失效**。

**今天没出事**，因为 `ShareGeneratorImpl` 只写 VENUE / AGENT 两种、两列都有值。但：

- `share_record.payee_type` 的注释写着 `VENUE/AGENT/**PLATFORM**` —— 平台净收入行天然没有 `payee_no`，
  哪天补上这一行，它就是不设防的；
- 还有 6 处代码写 `ShareRecord`（含 `DemoOpsFinanceSeeder`），不都经过 `ShareGenerator`；
- **ADR-027 要往这个键里再加一列 `basis`** —— 又一个可空维度，问题只会放大。

**顺带一处认知偏差**：V37 的注释写「存量行用 payee_type 回填，否则唯一键会把它们全判成 (null,null) 冲突」。
恰恰相反——NULL 在唯一索引里**不冲突**，它们会全部被放行。回填是对的，理由记反了。

**建议**：`dimension` 与 `payee_no` 改 `NOT NULL`，平台行用哨兵值（`payee_no=''`）而非 NULL。
这正是 ai-shop 在 `mch_payment_merchant` 上用过的手法（`store_no` 用 `''` 表示主体级，
原话：「因为 MySQL 唯一索引不约束 NULL」）。**改之前先扫存量有没有 NULL 行。**

### 1.2 `notify_template.template_no` 没有唯一索引

**证据**：该表唯一键建在 `(tenant_id, channel, code)` 上，`template_no` 只是个普通列。

业务键不唯一意味着可以写出两条同号模板，而发送记录 `notify_log` 是按模板号回溯的。
其余 148 张表的 `xxx_no` 都有唯一键——**这一张是例外，不是风格**。

## 二、🟠 会在已排期的事情上绊倒

### 2.1 两处金额没有币种 —— 多市场时会错，且错得无声

| 表 | 金额列 | 有 currency？ |
|---|---|:-:|
| `pay_auth` | `freeze_amount` · `captured_amount` | ❌ |
| `pay_refund` | `amount` | ❌ |


`pay_order` 有 `currency`，`stl_*` / `share_record` / `ord_rent` / `usr_wallet_txn` 都有。**这两张是漏网**。
单市场（AED）时不会暴露；[ADR-028 §七](./ADR/ADR-028-收费方案的适用范围与取价优先级.md)
要做第二个市场的币种硬过滤时，「这 50 是 AED 还是 SAR」将无法回答，而退款金额算错是**直接的资金事故**。

> `price_ladder` 没有 `currency` 是**对的**——币种在 `price_plan` 上，
> 一个方案只能一种币种（OM-S3 规定「方案保存后不能改币种」）。不要给它们加。

### 2.2 `price_plan_scope` 撑不起 ADR-028 的八层取价

现状只有 `(plan_no, scope_type, scope_ref)` 三列，`scope_type` 仅 `SITE/SCENE/ALL`。
ADR-028 需要 `device_type`（修「站点规则不看设备类型」）、`level`（八层）、`priority`、生效期、
以及 `vendor_code` / `model` / `brand_no` 三个过滤列。

**更要紧的是这张表现在没有读侧**：`PriceResolver` 只读 `price_rule`，`price_plan_scope` 由
`PricePlanServiceImpl` 读写、只喂界面。这是 ai-shop 总结过的「有能力没消费方 = 假能力」。

### 2.3 分润三表撑不住 ADR-027 的责任模型

| 需要 | 现状 |
|---|---|
| `share_rule.basis` / `share_record.basis`（出资 / 拓展 / 运维 / 效果管理 / 牵线） | 无 |
| `loc_site_agent` 责任关系表 | 无 |
| `agt_agent.agent_type`（代理商 / 城市合伙人） | 无 |
| `loc_lead.owner` 接受代理商 | 只接受 `employee_no`，代理商找来的场地无法归因 |

另外 `agt_commission` 与 `share_rule` **两张表表达同一件事**（代理分润比例），
前者多了 `dimension=GMV/ORDER_COUNT` 与 `fixed_amount`，后者被 `ShareGenerator` 实际使用。
责任模型落地时应合并为一张，否则「代理商分几个点」有两个答案。

## 三、🟡 约定漂移

> 这些不会今天出事，但它们让「新表该长什么样」没有唯一答案。

### 3.0 审计列：**已经是统一的**（原判定撤销）

`V10__audit_columns.sql`（2026-07-30）已按明确口径补齐，并写下了分类规则：

| 类别 | 处理 | 张数 |
|---|---|:-:|
| 可变表 | 补 `created_by` + `updated_by` | 113 |
| **append 只增表** | **只补 `created_by`** | 17 |

append 表的理由值得保留在规范里：「账本 / 审计 / 报文 / 指令流水在设计上永不 UPDATE，
补 `updated_*` 永远是 NULL，反而让读表的人以为是漏填」。

实测结果：

| 项 | 数 |
|---|---|
| 五件套（`id`+`created_at`+`created_by`+`updated_at`+`updated_by`）齐全 | **118/149** |
| 缺 `id` | 4（`ord_rent_ext`/`ord_charge_ext`/`ord_locker_ext` 用 `order_no` 作主键，**1:1 扩展表，合理**；`sys_token`） |
| 缺 `created_at` / `created_by` | 6 / 5 |
| 缺 `updated_at` / `updated_by` | 22 / 27（其中 17 / 22 张是 append 型，**属设计豁免**） |
| 五列类型一致性 | `BIGINT` · `DATETIME(3)` · `VARCHAR(36)` **100% 一致** ✅ |

**只剩一处真不一致**：`sys_biz_rule.updated_by` 是 `VARCHAR(64)`，其余 148 张都是 `VARCHAR(36)`。

**5 张表值得复核**——它们缺 `updated_at`/`updated_by`，但看名字不像 append 型：
`agt_assignment`（划拨流水，像 append）· `ord_intervention`（干预留痕，像 append）·
`usr_consent`（同意记录，PDPL 要求可撤回 → **撤回是不是 UPDATE？**）·
`usr_coupon_issue` · `usr_credit_change`。前两张大概率对，后三张建议逐张确认。

### 3.1 其余漂移

| # | 漂移 | 实测 | 建议 |
|---|---|---|---|
| 3.1 | **软删除双轨** | **16 张**表同时有 `deleted` 和 `archived_at`（`loc_site`·`loc_venue`·`loc_location`·`dev_cabinet`·`dev_powerbank`·`agt_agent`·`price_plan`·`iam_role`·`coupon_tpl`·`md_bank`·`md_problem`·`mkt_notice` 等） | 契约禁止 `delete*`、只用 `archive*`（CLAUDE.md），`deleted` 是 MyBatis-Plus 逻辑删除留下的。**两个字段两套语义**，查询漏一个就出幽灵数据。缺 `deleted` 的 41 张 / 缺 `version` 的 40 张多为 append 表，属正常 |
| 3.2 | **`tenant_id` 120/149 张** | ADR-026 已把它降为「恒 MAIN 的历史常量」 | 覆盖不全无害（它本就不做隔离）。**要点是新表不要再加** |
| 3.3 | **比率精度不一** | 主流 `DECIMAL(5,4)`（0..1 四位小数）；`mbr_benefit.points_rate` 是 `DECIMAL(8,2)`，`sys_tax_setting.rate_percent` 是 `DECIMAL(5,2)` | 后者是「百分数」语义（5.00 = 5%），与主流的 0..1 相反。**同一系统两种比率表示法**，算税最容易弄错 |
| 3.4 | **枚举列宽度** | `VARCHAR(16)` 118 处、`(24)` 12、`(32)` 7、`(64)` 4、`(8)` 3 | 统一 `VARCHAR(16)`，超长的（如 `command_family`）单独说明 |

## 五、查过但**不是**问题（免得下次重查）

| 疑点 | 结论 |
|---|---|
| 订单扩展表 `ord_rent_ext` / `ord_charge_ext` / `ord_locker_ext` 的 `order_no` 没索引 | **误报**：它是 `PRIMARY KEY`。（我第一版脚本只扫 `KEY`，漏了主键） |
| `pay_order.order_no` 没唯一索引 | **误报**：`order_no` 是指向订单的外键，自身业务键 `pay_no` 有 `uk_pay_no` |
| `dev_cabinet.location_no` 可空 | **合理**：设备可以在仓库未上架 |
| `price_plan_item` / `price_ladder` 没有 `currency` | **合理**：币种在方案层，见 §2.1 备注 |
| `ord_rent` 没有计价快照 | **已有**：V16 加了 `price_snapshot JSON`，注释写明「展开结构而非 plan_no 引用，改价不影响在途单」。ADR-028 的命中原因可直接挂进去 |
| `gw_command_log.order_no` / `ord_reservation` 等缺索引 | **可接受**：这些表按 `command_id` / `reservation_no` 查，不按订单号扫 |

## 六、建议的动作顺序

| 序 | 做什么 | 为什么排这里 |
|:-:|---|---|
| 1 | 扫 `share_record` 存量 NULL 行 → `dimension` / `payee_no` 改 `NOT NULL` + 哨兵值 | 唯一的**真缺陷**，且 ADR-027 加 `basis` 之前必须先修，否则在坏地基上加层 |

| 6 | ADR-028 步 1 + ADR-027 步 2（L1） | 两者都动分润 / 取价，同窗口做省一次回归 |
