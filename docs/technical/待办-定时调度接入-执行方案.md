## 1. 卡在哪（实测，2026-09-25 复核仍成立）

v4/07 的结论是「不自建、用 ai-shop 的任务服务」（ADR-020/024/025）。但：

- `backend/pom.xml` 的 enforcer 禁止依赖 `ai.neargo.shop:*`（`fail=true`）；
- 放行名单里写的 `shop-job-api` / `shop-job-target` **两个坐标都不存在**
  （ai-shop 那边模块叫 `job/job-api`，`shop-job-target` 尚未收拢）；
- ai-shop 侧的 MJ1–MJ8 **自 2026-09-24 起未开工**。

⇒ 本仓**连 `JobHandler` 都写不了**，而 v4/07 的 J0 恰恰是「先写好首批任务」。
整条链堵在一个外部仓库后面。

## 2. 决策：本仓先定义零依赖的任务接口（选项 B）

| | 做法 | 结论 |
|---|---|---|
| A | 等 ai-shop 做完 MJ1–MJ8 | ✗ 时间不可控，12 个业务缺口全堵着 |
| **B** | **本仓先定义 4 个零依赖接口，业务任务照 v4/07 §4.1 的签名写；ai-shop 构件就绪后改 import** | ✅ **采纳** |
| C | 自建调度器 | ✗ 与 ADR-020/024/025 相悖 |

**为什么 B 成立**：J0 依赖的不是 ai-shop 的**调度器**，只是那几个**接口形状**。
`JobHandler` / `JobDeclaration` / `JobInvocation` / `JobResult` 都是零依赖的值类型
与单方法接口，本仓自己定义半天的事，换来 12 个业务缺口可以并行开工。

**怎么保证将来换得掉**：

1. 签名以 v4/07 §4.1 的示意为准，包名用 `ai.neargo.sharehub.common.job`；
2. 业务侧只 import 这四个类型，**不得**在 handler 里依赖本仓的注册表实现；
3. **不进** `backend/known-inprocess-schedules.txt`：那份台账记的是**会自己 tick 的东西**
   （目前只有 `OutboxDispatchScheduler`），而注册表不会 —— 它只在被调用时跑。
   混进去会稀释那份台账的含义：将来有人扫它想知道"生产上有哪些东西在自转"，
   会得到一个假阳性。占位身份写在 `JobHandler` 的类注释里，并由
   `JobRegistryTest.this_package_must_not_grow_a_scheduler` 卡着 ——
   **那条卡口拦的正是本节最可能的走偏**：有人顺手在这儿加个定时，它就能跑了，
   于是没人再去接 ai-shop，最后落成一套要废弃的第二实现，而且它会比真调度器先被信任。
   （已实测：往包里塞一个 `ScheduledExecutorService`，该用例立刻红。）
4. 替换时是纯 import 改名，若 ai-shop 的签名有出入，差异只落在这四个文件上。

> ⚠️ 顺带记一笔：`known-inprocess-schedules.txt` 的头部写着「只准变短，不准变长」，
> 但**全仓库没有任何测试在守它** —— 与本仓库其它台账（`known-*.txt` 多数配了棘轮用例）
> 不同。它现在只是一份自觉遵守的文档。要不要补卡口另说，别以为它已经有了。

> ⚠️ **不要顺手做成一个真调度器**。本仓只实现「注册表 + 手动/进程内触发」，
> cron 解析、失败重试、job_run 留痕、运营端页面**一律等 ai-shop** ——
> 那些正是 v4/07 选择不自建的理由，自己写一份等于制造要废弃的第二套。

## 3. 任务清单（逐条核过代码，与 v4/07 §五 有出入）

v4/07 §五 列了 17 个 `SHAREHUB` 任务。**逐个查过源码**后分三类 ——
这个分类直接改变工作量估算：**只有 5 个是「包一层就能跑」，11 个连业务逻辑都没有**。

### A 类 · 业务已实现，包一层即可（6 个）

| 任务 | 现成方法 | 现在靠什么触发 |
|---|---|---|
| `outbox-dispatch` | `OutboxDispatcher.dispatchDue()` | 进程内 `OutboxDispatchScheduler`(30s)，**默认关**，已在台账 |
| `price-adjust-apply` | `PriceAdjustmentServiceImpl.tick()` | 内部端点 `POST /internal/trade/price-adjustments/tick` + **列表页惰性触发**（`page()` 里调一次，「不必等调度器那一分钟」） |
| `settlement-generate` | `SettlementService.generate(period, payeeType)` | 手动 `POST /api/trade/settlements/generate` |
| `inspection-plan-run` | `InspectionPlanService.run(planNo)` | 手动 `POST /inspection-plans/{planNo}/run` —— **按单个计划**，缺「当天到期的批量扫」 |
| `push-sweep-due` | `PushService.sweepDue(now)` | 手动 `POST /api/user/push-messages/sweep-due` |
| `ownership-reconcile` | `OwnershipReconciler.redeliverPending()` | **没有任何调用方** |

> `push-sweep-due` **不在 v4/07 §五 的目录里**（它是 9-24 之后加的，目录没跟上）。
> 相关：[待办-定时推送后端](./待办-定时推送后端.md)。

### B 类 · 空

> **本文第一版把 `price-adjust-apply` 列在这里，说「预约调价到点永远不会生效」——那是错的。**
> `tick()` 早就实现了，还有内部端点和列表页的惰性触发。
> 错因是用 `grep -E "public .*\("` 列接口方法，而它的签名是
> `java.util.List<String> tick();` —— **全限定返回类型里的点号让正则没匹配上**，
> 于是整个方法在视野外，接着就据此推断「没有到点执行的路径」。
>
> **可靠的查法**（本文第二版用的）：直接在主源码里找周期性动作形状的方法名 ——
> ```
> grep -rnE "public .*\b(sweep|tick|scan|purge|expire|retry|reconcile|dispatchDue|redeliver)[A-Za-z]*\s*\(" \
>      --include="*.java" . | grep -v /target/ | grep -v /test/
> ```
> 全仓库只命中 4 个真周期方法（`dispatchDue` · `tick` · `sweepDue` · `redeliverPending`），
> 加上两个不带这类命名但有手动端点的（`generate` · `run`），正好就是上面的 A 类 6 个。
> **按接口逐个看方法容易漏，按动作形状全局搜不会。**

### C 类 · 业务逻辑也没有，调度器不是瓶颈（10 个）

| 任务 | 实测 |
|---|---|
| `order-overdue-scan` 超时未归还 | 全仓库只有一个 `overdueHours` 配置字段（`SysDtos`），**无扫描逻辑** |
| `order-pending-sweep` CREATED 超时 | 无 |
| `reservation-expire` 预约过期 | 无 |
| `preauth-expiry-scan` 预授权到期 | 无扫描方法 |
| `coupon-expire` · `membership-expire` · `free-whitelist-expire` | 无 |
| `alarm-rule-eval` 告警规则评估 | `DevAlarmRule` 在主源码里**只被自己的 CRUD 栈与控制器消费**，没有任何评估引擎 —— 规则建了就躺着 |
| `wo-sla-escalate` SLA 升级 | **规则是会用的**（`WoOpsServiceImpl` 建单时按 `activeRule(type)` 算 due、落 `WoSla` 计时行），缺的是**判超时那一半**：没有任何代码去置 `responseBreached` / `resolveBreached` / `escalatedAt` ⇒ 计时行一直写，**升级永远不发生** |
| `notify-retry` 通知重试 | 无 |
| `session-purge` 会话清理 | 无 |
| `biz-recon` 业务对账生成 | 无（`recon_task` 只有演示种子） |
| `event-consumed-purge` 事件表清理 | 无 |

> **`alarm-rule-eval` 与 `wo-sla-escalate` 值得单独点名**，但两者性质不同：
> 告警规则是**整块没做**（建了没人读）；SLA 是**做了一半**（计时行天天写、超时没人判）。
> 后者更隐蔽 —— 界面上 SLA 那一列有数字，看着像在工作。

`GATEWAY` / `PAY` 两个目标随网关与支付上线，本文不展开（见 v4/07 §5.2/§5.3）。

## 4. 执行顺序

按依赖排，不按 v4/07 的清单顺序。每步能独立验收。

| 步 | 内容 | 依赖 | 验收 |
|---|---|---|---|
| **S1** | **四个零依赖接口 + 注册表**（§2） | 无 | ✅ **已完成**（`JobHandler` / `JobDeclaration` / `JobInvocation` / `JobResult` / `JobRegistry` + `JobRegistryTest` 13 例）。声明与实现对不上则启动失败；handler 抛异常/返回 null 一律 FAILED 不外抛；「本包不许长出调度器」的卡口已实测会红 |
| **S2** | **A 类 6 个包成 JobHandler**（含给 `inspection-plan-run` 补「当天到期批量扫」的包装） | S1 | ✅ **已完成**。六个都注册并真跑通（`JobCatalogTest`）。⚠️ **不能删 `OutboxDispatchScheduler`** —— 本方案原先写「接管后删」是错的：`JobRegistry` 只是注册表、**不会自己 tick**，删了 outbox 在生产上就没有任何东西驱动，而且不报错（事件静静堆在表里）。顺序是 S5 接真调度器 → 启用任务 → 确认在跑 → 再删 |
| **S3** | **`wo-sla-breach-scan`**：补判超时。⚠️ **升级不在本步**，见下方说明 | S1 | ✅ **已完成**（`WoSlaBreachScanTest` 6 例）。没人接的单过期限 → 标记；已接单/已完工的不重复判；无 SLA 规则的不考核；幂等 |
| **S4** | **C 类其余按业务优先级排期**。建议 `alarm-rule-eval` 靠前（规则建了从来没人读） | S1 | 各任务自带 |

> **S3 的两处更正**（做的时候查出来的，原文说法不准）：
>
> 1. **「没有任何代码去置 breached」是错的**。`WoOpsServiceImpl.markBreached` 一直都在，
>    只是**事件驱动**：接单那一刻判响应超时、关单那一刻判解决超时。
>    真实缺口比原说法更有意思 —— 已经接了/关了的单能被正确标记（哪怕晚了），
>    而**一张彻底躺着没人管的单，因为永远不会发生那两个事件，标记就永远是 0**。
>    ⇒ 超时最严重的那些，恰恰是唯一不会被判定的。定时扫描补的正是这块盲区。
>
> 2. **升级（escalate）刻意不做**，任务因此叫 `wo-sla-breach-scan` 而不是 v4/07 的
>    `wo-sla-escalate` —— 叫 escalate 会让运营端出现一个名字承诺了却没做的事。
>    缺的是**通道**：`wo_sla_rule.escalate_to` 指向 role_no/employee_no，
>    但 `sharehub-svc-ops` 不依赖通知模块，发不出任何东西。
>    只写 `escalated_at` 而不通知任何人，就又是一个「界面有、不生效」。
>
> **还欠一个读侧**：`respond_breached` / `resolve_breached` / `escalated_at`
> 在运营端**一个都没被消费**（前端只认 `slaDueAt`）。往出参加字段而前端不用，
> 会让 `known-api-align-gaps.txt` 台账变长，而那是只准变短的棘轮 ——
> 所以读侧要连前端一起做，是独立的一步。在那之前这几列是「算对了但没人看」。

| **S5** | ai-shop 的 MJ1–MJ8 就绪后：换 import、接 `shop-job-target`、登记 `system=SHAREHUB`、运营端页面 | **ai-shop** | 即 v4/07 的 J1–J4 |

**S1–S4 全部不依赖 ai-shop。** S5 之前，所有任务靠手动端点 + 进程内触发，
每一条都必须在 `backend/known-inprocess-schedules.txt` 台账里显形。

## 5. 不要踩的

- **别在 handler 里写 `@Scheduled`** —— v4/08 的卡口禁止，理由是「每个定时的东西
  都必须在运营台可见可控」。本方案的进程内触发同样不可见，所以才要台账兜着。
- **别把本仓的临时注册表做成调度器**（§2 末）。
- **幂等是业务侧的责任**，不是调度器的。A 类五个方法都要确认按业务键幂等 ——
  多副本下台账里的东西会重复执行，靠的是消费端幂等，不是「不会重复」。
- **卡口只看得见「跑过的代码路径」**。S2 里 `JobCatalogTest` 触发 `inspection-plan-run`，
  第一次让 `wo_order.source='PLAN'` 在测试库里出现，`StoredValueInVocabularyTest`
  当场红了 —— 那一列的注释漏声明 PLAN 已经很久（写入校验与前端都认它，只有注释没跟上），
  但**在没人跑过巡检生成之前，数据驱动的卡口看不见它**（V93 修）。
  ⇒ 给任务写用例时让它**真跑一次**，往往能顺带照亮一段从没被执行过的路径。
- **任务的用例要 `@Transactional`**。同一条用例第一版没加，一次跑下来在共享测试库里
  生成了 4 张巡检工单，而且每天跑每天造。`test_sharehub` 是累积型共享资产。
  ⚠️ 验回滚时别被幂等键骗了：第二次跑「数字没变」可能只是因为本周期已执行过被拒，
  要先清掉幂等键制造「本该写入」的条件，再看数字变不变。
- **日切类任务的时区**：`bizDate` 与 cron 按调度器 JVM 时区算，业务口径（日结、账期）
  在任务内部按 `Asia/Dubai` 换算，不依赖调度器时区（v4/07 §6.1）。
