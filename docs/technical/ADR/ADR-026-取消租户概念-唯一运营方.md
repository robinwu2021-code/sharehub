# ADR-026 取消租户概念 —— 平台是唯一运营方，加盟商按加盟商的逻辑

状态：**已接受**（2026-09-23 用户定：「本平台只支持唯一的运营方，简化逻辑，没有租户概念」；
并确认「加盟商用平台品牌，用户无感知」）
· **作废** [ADR-011](./ADR-011-单运营方为主多租户为口子.md) 的「多租户口子」部分
· **确认并加固** [ADR-012](./ADR-012-代理商模型.md)：代理商 ≠ 租户（原否决项成为正式决策）

## 背景

ADR-011（2026-07-11）把多租户降为「休眠口子」：管理面不建，但保留 `tenant_id` 列，
理由是「抽掉将来难补，成本极低」，并把口子语义泛化成「隔离的经营实体」。

2026-09-23 对标甲方交付清单时，「商户管理」一项引出追问：加盟商到底是不是租户？
用户给出的答案是**两条都要**：平台只有一个运营方，**且产品里不存在租户这个概念**。

## 决策

### 一、产品层：租户概念取消

不存在「租户」这个对象，因此也不存在：租户开通/停用/套餐配额、SaaS 计费账单、
超管跨租户切换、平台大盘（跨租户汇总）、设备-租户归属分配、`PLATFORM_ADMIN` 角色。
文档与界面**不再出现「租户」一词**（历史 ADR 不改）。

### 二、加盟商按加盟商的逻辑（ADR-012 不变）

| | 加盟商 `agt_agent` |
|---|---|
| 是什么 | 运营方**体内**的分润伙伴：出钱买设备、包一片区域的铺设与运维 |
| 品牌 | **用平台品牌，C 端消费者无感知**（2026-09-23 确认） |
| 数据隔离 | **数据范围 `AGENT`**（强制 `agent_no` = 自己），不是行级 `tenant_id` 隔离 |
| 分润 | 参与运营方**统一分润**：`share_rule(dimension=AGENT)` → `share_record` → `settlement` → `withdrawal` |
| 入口 | ops-web 的角色视图（ADR-012 2026-09-23 补充定案），不建独立前端 |

「加盟商」「代理商」「城市合伙人」是同一实体的不同叫法，不新增主体。

### 三、代码层：`tenant_id` 保留为恒定 `MAIN` 的历史列，但它不再是「口子」

实测：`tenant_id` 出现在 **102 个 Java 文件、23 个迁移、约 259 处**，
而取值全程硬编码 `MAIN`（`SecurityUtils.currentTenant()` 的 `orElse("MAIN")`、
`AbstractCrudService.TENANT_MAIN`）—— 它**本来就没有在做任何隔离**。

**决定：不做物理移除。** 理由：
- 它已经是惰性常量，留着不产生任何行为；移除要动 102 个文件 + 23 个迁移，
  是纯粹的改动风险，换不来任何功能或性能收益 —— 那不叫简化，叫折腾；
- 真正的简化发生在产品层（少一整套管理面、少一个角色、少一个心智负担），已由 §一 完成。

**但语义变了**：ADR-011 把它称作「为将来预留的口子」，本 ADR 起它**只是历史遗留的常量列**。
新代码**不得**基于它做任何分支、不得暴露到接口出参、不得在界面上体现。
将来若真要做多实例，走**独立部署**（ADR-011 细化 #1 已指出这才是更现实的路径），不靠这一列。

## 影响

| 面 | 变化 |
|---|---|
| 权限 | 删除 `PLATFORM_ADMIN` 角色与 `tenant:*` 权限码族（[功能权限清单 §15](../../requirements/功能权限清单.md)）；角色集固定为 7 个：ADMIN/OPS/CS/FINANCE/BD/VIEWER/AGENT |
| 功能清单 | 🔒「多租户/平台」整组删除；[分级矩阵](../../requirements/功能清单-分级矩阵.md) 的多租户条目一并去掉 |
| 运营端 | 无租户切换、无平台大盘；经营看板就是唯一的全局视图 |
| C 端 | 无变化（本来就没有租户概念，`openid × MAIN` 的写法中 MAIN 不再解释为租户） |
| 数据库 | 零变更。`tenant_id` 列保留，恒 `MAIN` |

## 对「加盟商进件、收款」的连带结论

用户同日还提出「商户用来进件、收款」。结合本 ADR 的两条约束，**推断首期应走 `LEDGER`**
（平台统一收款 → 分润 → 结算单 → 提现打款），理由：

1. **「用平台品牌，用户无感知」与「加盟商自己收款」直接冲突** ——
   若走 `CHANNEL_SPLIT`，消费者的卡单/账单上出现的是加盟商的商户名（merchant descriptor），
   用户立刻就有感知了，与本 ADR 确认的品牌口径矛盾；
2. 统一分润（§二）要求资金先归集再分配，这正是 `LEDGER` 的形状；
3. [ADR-004](./ADR-004-分账双模式.md) 本就写明 `LEDGER` 是「通用兜底，MENA 首期主用」，
   且否决过「仅官方分账」（长尾商户没有特约资质）。

因此「进件」在本项目里应理解为**加盟商入驻平台的资质审核**（平台侧建档与审核流程），
而不是**支付进件**（向 PSP 报件开子商户号）。前者是运营流程，后者需要 ADR-004 改主路径。
**此推断待用户确认**，见[分级矩阵 §八 #9](../../requirements/功能清单-分级矩阵.md)。

## 备选与否决

| 方案 | 否决理由 |
|---|---|
| 激活 `tenant_id`，一个加盟商一个租户 | 与「用平台品牌、用户无感知」冲突；切断统一分润（ADR-012 原否决理由至今成立）；且唯一运营方需要跨租户全局视图，等于又要把 ADR-011 说「不建」的管理面建起来 |
| 物理移除 `tenant_id` 列与相关代码 | 动 102 个 Java 文件 + 23 个迁移换零收益；它已是惰性常量，留着不妨碍任何事 |
| 保留 ADR-011 的「口子」说法 | 「口子」会诱导后人往里加东西；明确降级为历史遗留常量，才能真正止血 |
