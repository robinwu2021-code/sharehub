# ADR-030 账号与主体 —— 一个账号可属多个运营主体

状态：**提议 · 待确认**（2026-09-23，依据用户「同时要支持一个账号多个主体，商家用手机注册后可以建立多个主体，这个和 ai-shop 应该是一致的」起草）
· 扩展 [ADR-029](./ADR-029-运营主体抽象.md)：主体是**经营单位**，账号是**登录单位**，两者 N:M
· 修订 [ADR-012](./ADR-012-代理商模型.md) 的「代理登录 = AGENT 角色 + 自己 agent_no」（单主体假设）
· 对齐 ai-shop 的 `mch_account` 成员关系模型与 `BizContext`
· §三 入驻双入口依 2026-09-23「商家可以注册，运营商也可以代建，条件相同」补写
· §2.2–2.5 依 2026-09-23「注册信息包含手机号码、邮件」重写为 `agt_principal` + `agt_account` 两张表，落实 [功能矩阵 OPS-AGT-07](../../requirements/功能清单-分级矩阵.md)

---

## 一、现状：结构上不支持

```sql
agt_account
  UNIQUE KEY uk_agt_username (tenant_id, username)   -- ← 用户名全局唯一
  KEY idx_agt_account_agent (agent_no)               -- ← agent_no 只是普通索引
```

**一个用户名只能存在一行，因此只能属于一个代理商。** 同一个人要经营两个主体，今天只能注册两个用户名——
而「这两个用户名是同一个人」这件事系统不知道。

登录侧同样是单主体假设：`POST /api/auth/login {username, password, role, agentNo}`，
`agentNo` 由**前端传入**（`AuthController:105`，缺省还兜底成硬编码 `"AG001"`）——
这既是单主体的痕迹，也是 [v4/06 §〇](../v4/06-认证与权限.md) 列的第 1 号安全问题。

---

## 二、决策：账号表就是「人 × 主体」的成员关系表

### 2.1 核心语义（这条最容易理解错，必须写死）

> **「一个账号多主体」不是一行多主体，是同一手机号的多行。**

```
自然人（手机号 13800138000）
   ├── agt_account 行 1：operator_no=AG001, is_primary=1, is_owner=1
   └── agt_account 行 2：operator_no=AG002, is_primary=0, is_owner=0
```

两行、两个 `account_no`。这正是 ai-shop 的形状（`mch_account` 唯一键 `(entity_no, login_phone)`），
他们在实体类注释里专门标注了这一点，因为**看上去像"一个账号"，实现上是"多行"**，
按直觉写成一行多主体会在鉴权、切换、授权三处同时出错。

### 2.2 表结构：**两张表**，人一张、成员关系一张

> 2026-09-23 用户补充「注册信息包含手机号码、邮件」——**这一条把本节从一张表改成了两张。**
> 理由见 §2.4：两个登录标识 + 一套凭据挂在「人」身上，不能在 N 行成员关系里重复。

```sql
agt_principal  -- 🆕 自然人（登录主体）：一个人一行
  principal_no  业务键
  phone_hash    HMAC(规范化手机号)   ← 登录查找键 · UNIQUE
  phone_mask    138****0000          ← 只用于显示，**不进任何唯一键**
  phone_enc     可逆加密明文（pb_pii 建成后迁出）
  email_hash    HMAC(lower(trim(邮箱))) ← 登录查找键 · UNIQUE
  email_mask    a***@example.com     ← 只用于显示
  email_enc     可逆加密明文
  cred_ref      凭据引用（一个人一套密码）
  status        ACTIVE / DISABLED

  UNIQUE KEY uk_agt_principal_no    (principal_no)
  UNIQUE KEY uk_agt_principal_phone (phone_hash)
  UNIQUE KEY uk_agt_principal_email (email_hash)

agt_account    -- 成员关系：人 × 主体，一个人在 N 个主体下就是 N 行
  account_no    业务键（每个成员关系一个）
  operator_no   所属运营主体（NOT NULL）
  principal_no  → agt_principal                        🆕 取代 username / login_phone 做键
  is_owner      是否主体属主（全站点全权限，不进授权表）  🆕
  is_primary    是否该人的默认主体（登录后默认进哪个）     🆕
  display_name  在该主体下的显示名                       🆕
  status        ACTIVE / DISABLED

  UNIQUE KEY uk_agt_account_no      (account_no)
  UNIQUE KEY uk_agt_account_member  (operator_no, principal_no)  🆕 取代 uk_agt_username
  KEY        idx_agt_account_pr     (principal_no, is_primary)   🆕 登录后找该人全部成员关系
```

**`uk_agt_username (tenant_id, username)` 必须删**——它是单主体限制的来源。

### 2.3 ⚠️ 掩码列**不能**做登录键（本 ADR 前一版的缺陷，已改正）

`agt_account.login_phone` **今天已经存在**（[V13](../../../backend/sharehub-app/src/main/resources/db/migration/V13__entity_column_reconcile.sql) 加的），
但它存的是**脱敏值**——列注释原文：「明文脱敏值；完整明文在 pb_pii」。

**用它做唯一键会误判**：`13800138000` 与 `13811138000` 的掩码都是 `138****8000`，
两个不同的人会撞同一个键——注册时报「该主体下已有此手机号」，**而这两个号根本不是同一个**。
反过来查找也不成立：掩码不可逆，按掩码查等于按前缀模糊匹配。

因此本 ADR 把**三种用途拆成三列**，这是加了邮箱之后更要守住的一条：

| 列 | 用途 | 进唯一键？ | 可逆？ |
|---|---|:-:|:-:|
| `*_hash` | **登录查找 · 唯一约束** | ✅ | ❌ 确定性 HMAC（带 pepper，不是裸 SHA） |
| `*_mask` | 列表与详情**显示** | ❌ **绝不** | ❌ |
| `*_enc` | 需要还原时（发短信 / 发邮件） | ❌ | ✅ 可逆加密；`pb_pii` 建成后迁出 |

> `pb_pii` 库**今天并不存在**——`V4` 里那段建库 SQL 是注释掉的。
> 所以 `*_enc` 先留在业务表，迁出路径是「搬 `_enc` 一列」，`_hash` 与 `_mask` 原地不动。

### 2.4 两个登录标识：手机号与邮箱**都能登录**，但键在「人」上

| | 手机号 | 邮箱 |
|---|---|---|
| 注册时 | **必填** | **必填**（用户 2026-09-23 定） |
| 能否登录 | ✅ | ✅ |
| OTP 通道 | ✅ 短信（自助注册防刷靠它） | 备用 |
| 通知 | 借还 / 告警类 | **审核结果 · 驳回原因 · 结算与账单**（长文、可留存） |
| 稳定性 | 高（MENA 市场的身份锚） | 低（换公司就换） |

**两个标识都全局唯一，但唯一性落在 `agt_principal` 上，不落在成员关系行上。**
改邮箱只改 `agt_principal` 一行，该人在所有主体下同时生效；
如果把邮箱冗余进 N 行成员关系，改一次要改 N 行，**漏一行就是一个还能登的旧邮箱**。

> 员工侧（`iam_employee`）本来就用邮箱登录（[v4/06 §2.6](../v4/06-认证与权限.md)），
> 代理侧加上邮箱之后两边的登录标识形状一致，登录实现可以共用同一套解析
> （输入含 `@` 走 `email_hash`，否则规范化后走 `phone_hash`）。

### 2.5 五条硬约束

| # | 约束 | 理由 / 守卫 |
|---|---|---|
| 1 | **同一个人在同一主体下至多一行** | `uk_agt_account_member (operator_no, principal_no)` |
| 2 | **同一个人至多一个 `is_primary=1`** | 应用层校验；否则登录进哪个主体不确定 |
| 3 | **`operator_no` 不得为 `PLATFORM`** | ADR-029 不变量 #3：主体是经营单位不是登录单位，平台员工走 `iam_employee` |
| 4 | **掩码列不得出现在任何唯一键或 `WHERE` 等值条件中** | §2.3；加一条结构守卫测试，否则日后有人「顺手」拿 `phone_mask` 去查 |
| 5 | **手机号与邮箱都不得为空**，且都全局唯一 | 用户 2026-09-23 定；唯一性落在 `agt_principal` |

## 三、入驻：两条入口，一条审核（2026-09-23 用户定）

> 用户原话：「**商家可以注册，运营商也可以代建，条件相同，商家注册，也需要运营商审核通过。**」

### 3.1 「条件相同」落成三个「同」

两条入口在系统里**不分叉**——它们只是同一张申请单的两个写入点：

```
商家自助注册  ──┐
（手机号 + 资料）│
                ├──▶  agt_apply 入驻申请（一张表 · 一个状态机）──▶ 运营商审核 ──▶ 激活派生
运营商代建     ──┘                                                    │
（后台录入）                                                    通过 │ 驳回 + 原因（可回填重提）
                                                                     ▼
                                              agt_agent 主体 + agt_account 属主成员关系行
```

| # | 同 | 含义 | 反面（不能这么做） |
|---|---|---|---|
| 1 | **同一张申请单、同一个状态机** | `agt_apply`，`DRAFT → SUBMITTED → REVIEWING → APPROVED / REJECTED` | 代建走一条「直接建档」的旁路，申请单里没有行 |
| 2 | **同一套资料要求与校验** | 必填项由 `operator_type`（AGENT / CITY_PARTNER）决定，**不由 `source` 决定** | 代建时放宽必填，日后补件没人记得 |
| 3 | **同一个审核动作** | 都经过 `/audit`，都写 `reviewed_by` / `reviewed_at` | 代建静默置为已通过 |

**Stripe 的同构佐证**：Stripe Connect 的两种 onboarding（平台用 API 代建账户 vs 商家走 Stripe 托管页自助填）
**核验要求完全相同**——同样取决于国家、主体类型与所申请的能力；两者的差别只在**谁负责收集信息**，
不在**要求本身**。与本节 §1「同一套资料要求」同一条道理。

### 3.2 差别只有两个字段

| | 商家自助 | 运营商代建 |
|---|---|---|
| `source` | `SELF_SERVICE` | `OPS_CREATED` |
| `submitted_by` | 申请人手机号 | 经办员工 `employee_no` |
| 审核 | 运营商审核 | **仍需审核动作**（见 §3.3） |
| 资料谁填 | 商家自己 | 运营商代录（线下签约后） |

### 3.3 代建不是「跳过审核」，是「同一人立即完成审核」

代建场景下允许一键**提交并通过**，但**状态机照走、两条留痕照写**：

```
submitted_by = E1001（经办人）
reviewed_by  = E1001（同一人，或配置要求换人）
→ 审计链完整：谁录的、谁批的、什么时候
```

| 约束 | 理由 |
|---|---|
| 一键通过需**独立权限码** `agent:apply:approve`，与 `agent:apply:create` 分开 | 否则「能录入」等于「能放行」，四眼原则无处落脚 |
| 是否允许**同一人录入并审核**，做成系统配置 | 首期人少，允许；规模化后可要求换人复核，不改代码 |
| 绝不允许**不写申请行直接建主体** | 一旦有旁路，「审核通过率」「入驻周期」这类指标全是假的；且驳回重提无处回填 |

### 3.4 审核通过 = 激活派生（一个事务）

通过那一刻**在一个事务里**派生出下游对象（形状照 ai-shop 的 `activate()`）：

| 派生 | 表 | 说明 |
|---|---|---|
| 运营主体 | `agt_agent` | `operator_type` 取申请单的；`status=ENABLED` |
| **自然人** | `agt_principal` | 按 `phone_hash` 查，**已存在则复用**（第 2 个主体的情形）；不存在才新建 |
| **属主成员关系行** | `agt_account` | `is_owner=1`；`principal_no` 指向上一行 |
| 收款账户占位 | `stl_payout_account` | ADR-029；**建占位不等于可打款**，见 §3.6 |
| 辖域 / 默认分润率 | `agt_agent_region` · `agt_agent.default_share_rate` | 审核时定，不是事后补 |
| 申请单回写 | `agt_apply.operator_no` | 申请 ↔ 主体双向可查 |

### 3.5 第二个主体：已有账号再申请，**不重建凭据**

这是本项目相对 ai-shop 的增量——ai-shop 的入驻默认申请人是新人。

同一手机号申请第 2 个主体时，激活派生只做**一件事的差别**：

| | 第 1 个主体 | 第 2 个及以后 |
|---|---|---|
| `agt_principal` | 新建一行 | **复用**（按 `phone_hash` 命中） |
| `agt_account` | 新增行，`is_primary=1` | 新增行，`is_primary=0` |
| 凭据 `cred_ref` | 新建 | **复用同一凭据**（一个人一套密码，§4.3） |
| 登录 | 登录后直接进该主体 | 登录后进原默认主体，靠 `X-Operator-No` 切过去 |

> ⚠️ 第 2 次申请时填的**邮箱若与已有 `agt_principal` 的不一致**，不能静默覆盖：
> 那是「同一个手机号 + 不同邮箱」，要么是换了邮箱（应走改邮箱流程并重新验证），
> 要么填错了。**审核时显式提示，由审核人裁决**。

> 申请单里的手机号已存在时，**不得当作重复注册报错**——它是合法的多主体申请。
> 校验的是「同一手机号在同一主体下至多一行」（`uk_agt_account_member`），不是「手机号不得重复」。

### 3.6 照抄 ai-shop 的教训：**审核通过 ≠ 能拿钱**

ai-shop 在「商家全生命周期：入驻 → 审核 → 账户 → 积分 → 出款」（同级仓库 `ai/ai-shop`，
`docs/requirements/商家全生命周期-入驻到出款-功能梳理.md` §2.1）里把这条列为**最要紧的一条**：
商家审核通过 → 能开店、能卖、订单成立、结算单生成 → 解析不到收款号 → **账单留空、钱欠着**，
而商家**一路上没收到任何提示**。他们的结论是：结算侧的兜底「保证了不出错，没保证有人知道」。

我方完全同构，且今天就是断的（[ADR-029 §5.2](./ADR-029-运营主体抽象.md)）：
`loc_venue` 没有账户列、`agt_agent.settle_account` **全仓无代码读它**、`stl_withdrawal` 没有账户列。

**因此两个判据必须分开，且入驻侧要有闸：**

| 判据 | 字段 | 回答 |
|---|---|---|
| 能不能经营 | `agt_agent.status = ENABLED` | 能铺设备、能产生分润明细 |
| **能不能拿钱** | `stl_payout_account` 完整（开户行 + IBAN + 户名 + 校验通过） | 提现能打出去 |

代理门户必须显示「**你还不能收款**」，判据是收款账户状态**而不是审核状态**。

## 四、登录与切换

### 4.1 登录：先解析成「人」，再找**全部**成员关系

```
POST /api/auth/login { realm:"AGENT", identifier, credential }
  ① identifier 含 '@' → email_hash = HMAC(lower(trim(x)))
     否则规范化（去空格/连字符，补国际区号）→ phone_hash = HMAC(x)
  ② 查 agt_principal WHERE phone_hash=? OR email_hash=?  → 拿到 principal_no + cred_ref
  ③ 校验凭据（对这个人唯一，不按主体分）
  ④ 查 agt_account WHERE principal_no=? AND status='ACTIVE'
  ⑤ 会话写入：memberships[]（全部 operator_no）+ currentOperatorNo（默认取 is_primary）
  ⑥ 返回 { token, operators:[{operatorNo, name, isOwner}], current }
```

> **入参叫 `identifier` 而不是 `phone`**：手机号与邮箱走同一个字段、同一个端点。
> 分两个字段或两个端点，前端就要先判断用户输的是什么——那个判断迟早和后端的不一致。
> ⚠️ **①的规范化必须与注册时写入 hash 用的规范化是同一个函数**，否则「注册能成、登录查不到」，
> 且这种错只在带空格 / 带连字符 / 带国际区号的输入上出现，测试很容易漏。

> ⚠️ **`limit 1` 必须带确定排序**：`ORDER BY is_primary DESC, id ASC`。
> ai-shop 踩过——不给排序的 `limit 1` 在多主体时**随机挑一个**，而「今天进的是 A、明天是 B」这种故障没人能复现。

### 4.2 切换：请求头 `X-Operator-No`，缺省用 `is_primary`

采用 ai-shop 的请求头方案而非会话级切换，理由是**浏览器多标签页**：
ops-web 是 SPA，会话级「当前主体」会让一个标签页的切换影响另一个。
请求头按请求生效，两个标签页可以各看一个主体。

**越权闸（必须照抄）**：`X-Operator-No` 是客户端可控的头，
反查出的 `operator_no` **必须落在该会话的 `memberships` 集合里**；
不在就**整个丢掉、回落默认主体**，不报错——
ai-shop 的类注释写明这是整条多主体改造里**唯一有越权面的地方**。

### 4.3 凭据挂「人」，不挂成员关系

一个人一套密码，不是每个主体一套。改密码改一处，所有成员关系一起生效。

**`cred_ref` 落在 `agt_principal` 上**（§2.2）——原先「留在 `agt_account` 每行重复」的选项
在加了邮箱之后已不成立：两个登录标识 + 一套凭据同时冗余进 N 行，改一次要改 N 行，
**漏一行就是一个还能登的旧凭据 / 旧邮箱**。这条把 §七 原待确认 2 结掉了。

## 五、授权：三层不能混

这是本 ADR 最容易出错的地方——**三个看起来都是「谁能碰哪个站点」的东西，含义完全不同**：

| 层 | 表 | 回答 | 例子 |
|---|---|---|---|
| **① 主体对站点的责任** | `loc_site_operator`（ADR-027） | 这个**主体**在这个站点做了什么、凭什么分钱 | AG001 在 S001 出资 + 运维 |
| **② 账号对站点的授权** | `agt_account_site`（本 ADR，**L2**） | 这个**人**能管主体名下的哪几个站点 | 店长李四只管 S001、S002 |
| **③ 数据范围** | `iam_data_scope` + 拦截器 | SQL 层能查出哪些行 | `WHERE operator_no IN (...)` |

**①** 是分钱依据，**②** 是人员授权，**③** 是执行手段。混起来的后果：
把 ① 当授权用，会让「出资方」自动获得运维操作权；把 ② 当分钱依据用，会让换个店长就改变分润。

### 5.1 属主走旁路

`is_owner=1` 的账号 = 该主体名下**全部站点**，**不进 `agt_account_site` 表**。
ai-shop 的理由值得抄：「给店员按主体展开的话，加一个店员等于把所有门店都交出去」——
属主与店员的「全部站点」口径必须不同：属主按主体展开（含他明天新建的站点），店员按授权行展开。

### 5.2 L1 先不做 ②

首期代理账号都是属主（老板本人）。`agt_account_site` 的表结构在本 ADR 定下，**L2 再建**。

## 六、数据范围如何收敛

会话里有 `currentOperatorNo`，数据范围维度 `AGENT` 的锚点值就取它（而非今天的「会话里那个唯一的 agentNo」）。

| 项 | 变化 |
|---|---|
| `DataScopeRegistration` 注册表 | **不变**（仍是 `AGENT → agent_no`） |
| 锚点取值 | 从 `LoginUser.agentNo()` 改为 `currentOperatorNo`（按请求头解析后的） |
| `agent_cannot_see_platform_direct_rows` | **照样通过** |
| 新增守卫 | 切到 B 主体后，看不到 A 主体的任何数据 |

> **`operatorNo` 是解析的入参，不是解析完再套上去。** ai-shop 原话：
> 「先解析主体再换门店，在多证照下会静默错：进 B 主体的店但 `merchantNo` 还停在 A，页面照常打开、数据是另一家的。」
> 我方对应：身份解析必须**先**读 `X-Operator-No`，再据它装配权限与数据范围。

## 八、否决的方案

| 方案 | 否决理由 |
|---|---|
| 一行账号 + `operator_nos` JSON 数组 | 撤销单个主体成员关系要读-改-写，并发下互相覆盖且不报错（同 ADR-027 对责任行的判断） |
| 会话级「当前主体」 | 多标签页互相干扰；ops-web 是 SPA，这个场景一定会出现 |
| 每个主体一套密码 | 同一个人记 N 套密码；改密要改 N 处，漏一处就是一个还能登的旧密码 |
| 用 `username` 而非手机号做登录键 | 用户名没有天然唯一的现实对应物，跨主体撞名无解；手机号本身是身份 |
| 用 `login_phone`（掩码列）做唯一键 | 掩码不可逆且会撞：`13800138000` 与 `13811138000` 掩码相同，两个不同的人会被判为重复（§2.3） |
| 手机号与邮箱各一个登录端点 / 各一个入参字段 | 前端要先判断用户输的是什么，那个判断迟早和后端不一致；合成 `identifier` 一个字段（§4.1） |
| 邮箱冗余进每行 `agt_account` | 改一次要改 N 行，漏一行就是一个还能登的旧邮箱（§2.4） |
| 把 `loc_site_operator` 当账号授权用 | 责任是分钱依据，授权是人员管理。合用会让「出资方」自动获得运维操作权 |
| 代建走「直接建档」旁路，不写申请单 | 审核通过率 / 入驻周期等指标全失真；驳回重提无处回填（§3.3） |
| 自助注册免审核、先用后审 | 用户 2026-09-23 明确「商家注册，也需要运营商审核通过」；且代理商一旦有主体就能领设备、进分润链 |
| 按 `source` 分两套资料要求 | 代建放宽必填，补件日后没人记得；Stripe 两种 onboarding 核验要求相同即此理（§3.1） |
