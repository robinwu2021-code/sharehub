# ADR-018 多设备类型与多供应商 —— 抽象边界与服务数调整

状态：**已决**（2026-07-30，用户定调）
· 修正 [ADR-014](./ADR-014-平台更名ShareHub与设备类型抽象.md) 的「零骨架改动」结论
· 扩展 [ADR-003](./ADR-003-硬件接入driver插件化.md) 的驱动 SPI
· 把 [ADR-017](./ADR-017-单体与微服务双形态部署.md) 的 4 服务调整为 **5 服务**

## 背景

用户要求：平台将来要承载**充电桩等各种共享设备**、对接**不同供应商**；服务数可增可减，
但**「业务抽象与易治理」是第一原则，「尽量少」是第二原则**。

ADR-014 已定「加 `device_type` + 一套驱动，**零骨架改动**」。**这个结论是错的**，
实测 `ord_rent` 的列就能推翻：

| 列 | 充电宝语义 | 充电桩 |
|---|---|---|
| `powerbank_no` | 借走的那个实物 | **没有实物被借走** |
| `return_cabinet_no` | 异地归还到哪台柜机 | **没有归还这回事** |
| `deposit_amount` · `buyout` | 押金、丢失买断 | 不适用 |
| `duration_min` | 按时长计费 | 主要按**电量 kWh** |
| — | — | 缺 `connector_no`(枪) · `energy_kwh` · `start/end_soc` · `peak_power_kw` |

**柜机=容器、仓位=货位这层确实设备无关**（ADR-014 这半句对），
但**订单生命周期与计费口径是设备特有的**，而订单恰恰是整个系统的中枢。
不处理这一层就加设备类型，结果是 `ord_rent` 变成一张越来越宽、大半列为 NULL 的表。

## 决策

### 一、三个抽象层次，各自的正确切法

| 抽象 | 是什么 | **不是什么** |
|---|---|---|
| **设备类型** | 数据维度 + 订单模型分化 + `device.<type>` 模块 | ~~服务边界~~ |
| **供应商** | 驱动插件（SPI 实现） | ~~服务边界~~ |
| **南向接入** | **服务边界** | — |

**原则：按「变化的原因」拆服务，不按「业务名词」拆。**
设备类型多了，变的是订单扩展表和一个 device 模块；供应商多了，变的是驱动实现。
这两者都不该让服务数量跟着涨 —— 按设备类型拆服务意味着订单/计价/结算/分润全套复制 N 份，
是灾难。而南向接入**变化的原因与业务完全不同**，所以它是边界（见三）。

### 二、订单模型：共性主表 + 类型扩展表

```
ord_order        共性主表：order_no · device_type · c_user_no · site_no · location_no
                 · cabinet_no · status · amount · currency · started_at · ended_at
                 · price_plan_no · coupon_no · agent_no · tenant_id
   ├─ ord_rent_ext     充电宝：powerbank_no · return_cabinet_no · deposit_amount
   │                          · buyout · duration_min
   └─ ord_charge_ext   充电桩：connector_no · energy_kwh · start_soc · end_soc
                              · peak_power_kw · stop_reason
```

**这个切法成立的唯一判据：资金侧只认共性主表。**
分润 `share_record.order_no`、账务 `acct_ledger.order_no`、发票 `fin_invoice_item.order_no`、
结算 —— 全部只 join `ord_order`。**新增一种设备类型，资金域一行代码不改。**
做不到这一点，就说明共性列没抽对，应该回头调整而不是往扩展表里塞。

**状态机同理，共性骨架 + 类型语义**：

```
CREATED → ACTIVE → ENDED → SETTLED → CLOSED
```

| 状态 | 充电宝 | 充电桩 |
|---|---|---|
| `ACTIVE` | 已借出，用户持有中 | 充电中 |
| `ENDED` | 已归还（可能异地） | 已停止（拔枪/充满/主动停止） |

分期分状态的判断（如充电宝的 `DISPENSING` 等待弹出、充电桩的 `PREPARING` 等待插枪）
落在**类型子状态**，不污染共性骨架。资金侧只认 `SETTLED`。

**迁移**：`ord_rent` → `ord_order` + `ord_rent_ext`，`device_type` 默认 `POWERBANK` 向后兼容。
存量 136 条订单可无损迁移（纯拆列，不改语义）。

### 三、服务数 4 → 5：南向接入独立为 `device-gateway`

**理由是治理，不是性能**：

| 维度 | 南向接入 | 业务服务 |
|---|---|---|
| 变更频率 | 每接一个新供应商就改一次 | 按业务节奏 |
| 故障域 | 某厂商长连接风暴 / 协议异常 | 不该被前者拖垮 |
| 技术栈 | Netty / MQTT / TCP 长连接 | HTTP + 事务 |
| 团队 | 硬件对接，独立工种 | 业务开发 |

**它是设备类型与供应商增多时唯一会线性膨胀的部分 —— 把膨胀关进一个进程里，**
这正是「易治理优先」的含义：不是让服务更少，是让**变化被隔离**。

**代价极小，实测**：拆出去只增加 **3 条**真实跨服务依赖，且全是**日志侧记录外部标识**
（`gw_command_log.cabinet_no` / `.order_no`、`dev_ota_task.cabinet_no`）——
写日志时记个 ID，不需要同步查对方实体。

**不增加网络跳数**：调厂商云 API 或经长连接下发本来就是跨进程，
把它收敛到一个服务里只是换了个落点。

调整后的五服务：

| 服务 | 表 | 职责 |
|---|---|---|
| `platform` | 41 | 底座与运营配置面 |
| `core` | 56 | 借还/充电主链路：消费者 · 券 · 计价 · **订单** · 支付 · 设备资产 · 库存 |
| **`device-gateway`** | 9 | **南向：厂商目录 · 驱动 · 绑定 · 心跳 · 指令与报文 · 固件下发** |
| `ops` | 14 | 告警 · 工单 · 客服 |
| `finance` | 12 | 账务 · 分润 · 结算 · 发票 · 对账 |

固件（OTA）随网关走 —— 它的下发通道、灰度节奏、失败重试都与驱动同源。

### 四、驱动 SPI 按设备类型分族

ADR-003 的 SPI 方向正确，但**它的指令集与事件集是充电宝专用的**
（`EJECT_ANY` / `SLOT_REPORT` / `RENT_CONFIRMED` / `RETURNED`），充电桩一个都用不上。

改为**通用集 + 类型族**：

| 层 | 指令 | 事件 |
|---|---|---|
| **通用**（所有设备） | `REBOOT` · `LOCATE` · `QUERY_STATUS` · `OTA_PUSH` | `ONLINE` · `OFFLINE` · `HEARTBEAT` · `FAULT` · `OTA_RESULT` |
| **充电宝族** | `EJECT_ANY` · `EJECT_SLOT` · `LOCK` / `UNLOCK` | `SLOT_REPORT` · `EJECT_OK` · `ITEM_INSERTED`（事件是**物理事实**不是业务语义 —— 归还判定归 core，见总纲 §1.5 红线） |
| **充电桩族** | `START_CHARGE` · `STOP_CHARGE` · `SET_CURRENT` · `UNLOCK_CONNECTOR` | `METER_VALUE` · `TX_START` · `TX_STOP` · `CONNECTOR_STATUS` |

驱动声明自己支持的 `(deviceType, protocol)`；平台按柜机的 `vendor_code + device_type` 路由。

**充电桩族直接对齐 OCPP 1.6J / 2.0.1**，不自创协议模型 —— 这是行业标准，
绝大多数桩企的云或桩端原生支持，自创等于给每一家都做一次适配。
充电宝没有对应标准（各家私有协议），维持 ADR-003 的自定义抽象。

`gw_vendor` 增加 `device_types` 多值列：一个供应商可能同时供柜机与充电桩。

### 五、设备资产：容器/槽位保持共用

`dev_cabinet`（容器）与 `dev_slot`（槽位）**保持设备无关**，加 `device_type` 维度：
- 充电宝：容器=柜机，槽位=仓位，槽位里**有实物**（`powerbank_no`）
- 充电桩：容器=充电桩体，槽位=**枪/连接器**，槽位里**没有实物**

`dev_powerbank` 是**充电宝特有**的资产台账（可移动物品），充电桩没有对应表 ——
这正是「容器/槽位共用、物品按类型分化」的体现。将来的储物柜同样没有可移动物品。

## 影响

**正面**：新增设备类型的工作量收敛为四件事 —— 加一张 `ord_<type>_ext` · 加一个 `device.<type>` 模块
· 加一族指令/事件 · 加驱动实现。**资金域、场地域、代理域、工单域完全不动。**

**成本**：`ord_rent` 必须拆表（一次性迁移）；驱动 SPI 要重构成分族结构。
**这两件事越晚做越贵** —— 现在只有 136 条订单和一套充电宝驱动。

**风险**：共性主表的列若抽错，会在接第二种设备时暴露，届时改动波及资金侧。
缓解：以「资金侧只认主表」为验收标准，接充电桩前先用它反推一遍列是否够。
