# ADR-002 多租户隔离方案

状态：已接受（2026-07-11）

## 背景
SaaS 多品牌是 P0 地基。需在隔离强度、成本、跨租户平台报表之间权衡。

## 决策
**单库行级隔离（tenant_id）起步，预留按租户垂直分库升级（ShardingSphere 路由）。**

机制（**直接复用 ai-neargo `neargo-common-security` + `neargo-common-data`，不重造**）：
1. BFF/网关从 JWT 解析 tenantId → `AuthHeaders`(X-Tenant-Id/X-Region-Id/X-User-Id) → `TenantContextFilter` 写入 `TenantContext`。
2. `NeargoTenantLineHandler`（MyBatis-Plus 租户插件）自动注入 `tenant_id` 条件；实体继承 `BaseEntity`（自带 tenantId/regionId）。
3. `TenantPropagationInterceptor` 跨 RestClient 透传租户头；事件属性携带 tenantId。
4. 平台超管角色白名单放行跨租户查询，`OperateLog` 强制审计。
5. 租户级配置（支付 sub_mchid、计费模板、品牌、启用供应商/渠道）集中于 platform 域配置中心。

## 备选与否决
- 按租户分库：隔离强但一期运维成本高 → 保留为大租户升级路径。
- 分 schema：MySQL 下管理复杂、收益有限 → 否决。

## 影响
所有业务表必须含 `tenant_id`；code review 检查项；跨租户操作必须显式声明并审计。
