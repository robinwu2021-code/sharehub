# ADR-032 第一阶段以商家为结算单元 · 外部会计系统（Zoho Books）架构预留、暂不编码

状态：**已决**（2026-10-28，用户定）
· 起因：[运营方原始需求-与现有需求对齐](../../requirements/运营方原始需求-与现有需求对齐.md) §二 术语映射、§三 K2 / K3
· 收窄 [ADR-029](./ADR-029-运营主体抽象.md) 的结算受益方：第一阶段只有「商家」一支
· 不改 [ADR-004](./ADR-004-分账双模式.md) 的双模式机制，只定第一阶段的结算对象
· 落地方案：[架构设计-第一阶段-运营方需求](../架构设计-第一阶段-运营方需求.md)

用户原话：
1. 「目前第一阶段以**商家为结算单元**，**商家对应商户，商户是渠道方的定义**」
2. 「**zoho 暂时不做，在架构上考虑，编码上暂时不处理**」

---

## 一、结算单元 = 商家

### 1.1 三个词各指什么

| 词 | 指什么 | 在系统里 | 谁的定义 |
|---|---|---|---|
| **商家** | 与平台结算的经营方。运营方原始需求里的「Merchant / 商户」（如 Hotel A）在本系统一律称商家 | 运营主体 `agt_agent`（ADR-029 的 Operator），经自助注册或运营代建、审核后产生 | 本平台 |
| **商户** | 商家在**支付渠道**侧的收款身份：子商户号、进件状态、结算账户 | `pay_merchant`（ADR-029 §5.2 规划，未建），按 `商家 × 渠道 × 市场` 1:N | 支付渠道 |
| 场地方 | 提供物理场地的一方 | `loc_venue`，保留为场所档案 | 本平台 |

一句话：**商家是我们的概念，商户是渠道的概念；一个商家可以在不同渠道、不同市场各有一个商户。**
这与 ADR-029「`merchant` 只用于支付语境」一致，本 ADR 只是给经营方补上了业务名称。

### 1.2 第一阶段的结算链路只有商家一支

```
订单结算 ─▶ 分润记录(按商家) ─▶ 结算单(商家 × 账期) ─▶ 应付台账(商家) ─▶ 付款
                                                                    │
                                     第一阶段：本系统登记付款 ◀──────┤
                                     会计系统接入后：从会计系统读回 ◀─┘（§二）
```

| 项 | 第一阶段 |
|---|---|
| 结算受益方 `payee_type` | 只用**商家**（代码现值 `AGENT`，即运营主体） |
| 场地方 `VENUE` | 不作为独立结算对象；场地档案、进场合同照常维护，分成如何承担见 §三 待确认 1 |
| 报表、发票提取、应付 | 原始需求里所有「按商户」的口径，一律按**商家**实现 |
| 收款号解析 | 商家 → 商户（按渠道、市场）；商户未建时按 ADR-004 的 LEDGER 模式由平台代收 |

### 1.3 为什么不新建「商家」表

商家就是 ADR-029 的运营主体，已有入驻申请、审核、账号、数据范围（`AGENT`）整套机制。
新建一张表会让同一个经营方有两条记录。**只统一叫法，不动模型**：
界面与文档用「商家」，代码列名维持 `agent_no`，随 ADR-021 的 S1 改名窗口一并改为 `operator_no`。

## 二、外部会计系统：架构预留，不编码

### 2.1 第一阶段做什么、不做什么

| 做（架构与文档） | 不做（代码） |
|---|---|
| 在架构文档的契约规划里登记 `AccountingPort`，定义要同步的业务事件 | 不写任何 Zoho 客户端、映射、同步任务 |
| 规定资金类事件必须带会计同步所需的全部字段（金额、币种、税额、业务键、发生时间） | 不建 `acct_ext_*` 表 |
| 规定应付台账的「已付」来源可切换：本系统登记 / 外部读回 | 不做付款读回 |
| 内部复式账 `acct_ledger` 保持为第一阶段的账务记录来源 | 不降级内部账 |

### 2.2 预留的三处接缝

接缝的意思是：将来接入时**只加实现、不改业务代码**。

| 接缝 | 第一阶段的形态 | 接入时 |
|---|---|---|
| ① 资金事件 | 订单结算、发票开具、退款、结算单确认、付款登记都经 `sys_outbox` 发出（订单结算已有，其余随各自功能落地时补） | 新增一个消费者，把事件同步到会计系统 |
| ② 会计端口 `AccountingPort` | **只在契约规划中登记**，不建代码 | 建接口 + `ZohoAccountingPort` |
| ③ 付款来源 `PayoutSource` | 应付台账落地时按「来源可切换」建，唯一实现是本系统付款登记 | 加读回实现，按配置切换；同一笔付款按外部单号幂等 |

②③ 都不含任何 Zoho 代码。③ 是应付台账本身需要的抽象，不是为 Zoho 额外写的。

### 2.3 为什么现在就要预留

原始需求的验收 AC-06（从会计系统同步付款后自动更新未结应付）与 RQ-ZOH-08（会计系统是记录来源）
都会反向约束**应付台账的数据模型**和**事件字段**。
这两样如果现在不按「来源可切换」设计，接入时要改的是资金域的表结构，而不是加一个适配器。

## 三、待确认

| # | 问题 | 第一阶段的默认做法 |
|---|---|---|
| 1 | 场地方的分成第一阶段由谁承担：商家线下自付，还是商家与场地方是同一主体 | 不由平台结算；进场合同中的分成比例仅作记录 |
| 2 | 商家收款走平台代收后结算（LEDGER），还是渠道分账直达商户（SPLIT） | 沿用 ADR-004 第一阶段的 LEDGER；SPLIT 待商户进件能力就绪 |
| 3 | 接入会计系统时，内部账是否降级为运营子账 | 届时裁决；预留接缝不预设答案 |

## 四、影响

| 面 | 变化 |
|---|---|
| 需求 | 对齐文档 K2、K3 由「待裁决」改为「已决」；原文「商户」统一读作「商家」 |
| 代码 | 本 ADR 本身**不要求改代码**；落地项见架构文档的第一阶段清单 |
| 已有能力 | 场地方分润（`share_rule(VENUE)`、保底补足）第一阶段不进入结算单，代码保留 |
