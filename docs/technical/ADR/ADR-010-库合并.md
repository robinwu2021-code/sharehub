# ADR-010 数据库合并（3 库）

状态：已接受（2026-07-11）

## 背景
初版按 neargo「一域一库」拆了 8 个库（pb_platform/ops/trade/user/user_pii/gateway/auth_b/auth_c）。powerbank 是**模块化单体**部署（app-modulith + access-gateway 两进程），库过碎、运维与事务成本高。用户要求合并。

## 决策
合并为 **3 个库**（按合规边界，而非按域）：
1. **`pb_core`** —— 全部业务域：platform / ops / trade / user / gateway。域用**子域前缀**区分（`iam_`/`dev_`/`loc_`/`wo_`/`ord_`/`pay_`/`acct_`/`usr_`/`gw_`…），表名库内唯一。app-modulith 与 access-gateway 两进程共享（gateway 仅用 `gw_*`）。
2. **`pb_pii`** —— 个人数据（`pii_*`），**独立 KMS + 区域驻留**（PDPL 硬要求，ADR-009）。
3. **`pb_auth`** —— 登录凭据（auth-core `cred_*`，`realm` 列区分员工/消费者池，取代 neargo 双库），**独立 KMS，仅 auth-core 访问**。

## 关键理由
- **trade 可并入 core**：支付/收单委托 nearpay（ADR-005），powerbank 无资金 vault，「资金轨 CBUAE」压力在 nearpay 侧；powerbank trade 仅持订单/计费/账务记账/nearpay 引用，属业务数据。
- **pii / auth 不能并入 core**：PDPL 双轨合规 + 独立 KMS + auth 访问隔离（ADR-009）是硬边界，合并会违规。

## 影响
- 域边界仍在逻辑层：子域前缀保留、跨域**逻辑引用不建物理 FK**，规模化后可按前缀无痛拆库（纯 schema 迁移，零改名）。
- 单库内可用本地事务，简化「创单+记账+outbox」一致性（原跨库需分布式事务）。
- 更激进可将 pii+auth 合为 `pb_secure`（2 库），但削弱访问边界，暂不采纳。

## 备选与否决
- 保持 8 库（neargo 一域一库）→ 否决：单体部署下过碎。
- 全部合 1 库 → 否决：违反 PDPL/auth 合规隔离。
