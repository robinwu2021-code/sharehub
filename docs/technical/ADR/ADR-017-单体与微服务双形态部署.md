# ADR-017 一套代码，两种部署 —— 单体与不超过 4 个服务

状态：**已决**（2026-07-30，用户定调）· **取代 [ADR-016](./ADR-016-目标架构为微服务与服务边界.md) 的 10 服务划分**
· 服务数已由 [ADR-018](./ADR-018-多设备类型与多供应商的抽象边界.md) 调整为 **5 个**（南向接入独立）

> 本文的**双形态机制**（Maven 结构 · 接口层 · 装配开关 · 四条纪律）全部有效。
> 仅「4 个服务」这一处被 ADR-018 修订为 5 个：`device-gateway` 独立出来，
> 理由是治理（变更频率/故障域/技术栈/团队），实测只增加 3 条日志侧跨服务边。

## 背景

ADR-016 定了 10 个微服务 + 3 BFF + 1 网关。用户 2026-07-30 提出两条新约束：

1. **同一套代码要同时支持单体部署与微服务部署**；
2. **微服务数量最多 4 个**。

10 个服务对一个尚未上线、单运营方的系统是过度设计：14 个进程意味着 14 套配置、
14 条发布流水线、以及大量本可以是方法调用的网络调用。而「先单体、将来再拆」如果不在
**今天**就把边界立住，到时候拆不动 —— 这正是绝大多数「以后再拆」失败的原因。

## 决策

### 一、默认单体，边界按微服务的标准维护

**部署默认是单体**（一个进程、一个库）。微服务形态随时可切，但**不默认启用**。

代码按 [业务模块分层](../业务模块分层.md) 的 32 模块 / 6 层组织，**模块边界按跨进程的标准维护**
—— 即使现在是同进程，也不许跨模块 JOIN、不许跨模块共享事务、不许绕过接口直接调实现。
这几条纪律是单体与微服务之间唯一的差别所在：守住了，切换只是打包方式；守不住，就是重写。

### 二、四个服务的边界

划分依据不是「边最少」，而是「**同步主链路必须在同一进程内**」。

| 服务 | 模块 | 表 | 职责 |
|---|---|---|---|
| **platform** | 租户 · 认证授权 · 审计 · 主数据 · 数据字典 · 系统参数 · 通知 · 开放平台 · 支付渠道 · 厂商目录 · 组织架构 · 代理商 · 场地拓展 · 场地与点位 · 资产归属 | 43 | 底座与运营配置面。写少读多，变更慢 |
| **core** | 消费者 · 权益与营销 · 计价 · 订单 · 支付 · 设备资产 · 固件 · 设备接入 · 库存 | 63 | **借还主链路全在这里**：扫码 → 查机柜 → 选充电宝 → 弹仓 → 建单 → 收款 |
| **ops** | 告警 · 工单 · 客服 | 14 | 异常发现与人工处置。异步、可延迟，与主链路解耦 |
| **finance** | 账务 · 分润 · 结算提现 · 发票 · 对账 | 12 | 钱怎么记/分/结/核。**全部由订单完成事件驱动**，无同步调用 |

**为什么 core 这么大**：因为借出这一笔要在一个事务里同时动订单、充电宝占用、支付预授权、
券核销。把它们拆开就得上分布式事务或 Saga —— 用系统里最热的链路去换「服务更小」，
是拿可用性换整洁。core 大是有意的。

**16 条真实跨服务依赖，没有一条在同步主链路上**（另有 18 条是目录型引用，见下）：

| 类型 | 例子 | 跨进程后怎么办 |
|---|---|---|
| 资金域读订单 | `share_record.order_no` · `acct_ledger.order_no` · `fin_invoice_item.order_no` | 订单完成**事件**携带所需字段，finance 落自己的库 |
| 运行域读资源 | `wo_order.cabinet_no` · `cs_ticket.order_no` · `dev_alarm.cabinet_no` | **只读查询**，走 API；工单/告警建单时**快照**冗余机柜名等展示字段 |
| 业务域读场地 | `ord_rent.location_no` · `dev_cabinet.site_no` · `price_rule.site_no` | 场地是慢变数据，**本地缓存 + 变更事件失效** |
| 投诉转工单 | `ord_complaint.wo_no` | **异步命令**，失败进重试队列 |

目录型依赖（`region_id` / `vendor_code` / `channel_code` 等 18 条）**不计入拆分成本**：
它们指向慢变只读的目录数据，各服务本地缓存 + 订阅变更事件即可，不需要同步调用。

### 三、怎么做到一套代码两种部署

**1. Maven 结构**

```
powerbank-common/          公共：Result · 分页 · 异常 · 受信头 · 数据范围
powerbank-svc-platform/    ┐
powerbank-svc-core/        │ 业务实现（jar，不可独立启动）
powerbank-svc-ops/         │
powerbank-svc-finance/     ┘
powerbank-api-platform/    ┐ 跨服务接口（只有接口 + DTO，无实现）
powerbank-api-core/        │ 被别的服务依赖，**绝不反向依赖实现**
powerbank-api-ops/         │
powerbank-api-finance/     ┘
powerbank-app-mono/        单体：依赖全部 4 个 svc
powerbank-app-platform/    ┐
powerbank-app-core/        │ 微服务：各依赖 1 个 svc + 别人的 api
powerbank-app-ops/         │
powerbank-app-finance/     ┘
```

**2. 跨服务调用：业务代码不知道自己在哪种形态**

调用方只依赖 `*-api` 的接口。实现有两套，靠**本地实现在不在 classpath 上**自动选：

```java
// powerbank-api-core：只有接口
public interface DeviceQueryPort {
    CabinetView cabinet(String cabinetNo);
}

// powerbank-svc-core：本地实现，单体与 core 服务里都存在
@Service
class LocalDeviceQuery implements DeviceQueryPort { ... }

// powerbank-api-core：远程实现，仅当本地实现不存在时装配
@ConditionalOnMissingBean(DeviceQueryPort.class)
@Service
class RemoteDeviceQuery implements DeviceQueryPort {
    // HTTP 调 core 服务
}
```

单体里 `LocalDeviceQuery` 在 classpath 上 → 用它，是一次方法调用；
拆开后 ops 服务里没有 core 的实现 → 自动装 `RemoteDeviceQuery`，变成一次 HTTP。
**业务代码一个字都不改。**

**3. 数据库**

单体一个 `pb_core`；拆开后每个服务只连自己那部分表（先分 schema，再分实例）。
表的归属已在 [业务模块分层](../业务模块分层.md) 里定死，132 张表全部有主。

**4. 事件**

单体用 Spring 的 `ApplicationEventPublisher`（同进程、事务后触发）；
拆开后同一个事件类改由消息中间件投递。**发布方与订阅方的代码不变**，换的是传输。
前提是事件必须**自带消费方需要的全部字段**，不能让消费方回调查询 —— 那等于把同步调用藏在事件里。

**5. 报表**

报表是唯一跨域 JOIN 的地方（`ord_rent ⋈ loc_site`、`dev_cabinet ⋈ loc_site`，全在 `ReportMappers`）。
单体下直接 JOIN；拆开后报表走**独立读模型**（订阅各服务事件落一份宽表），不跨服务 JOIN。
**在此之前，跨域 JOIN 只许出现在 `ReportMappers`，不许扩散到业务代码。**

### 四、现在就要守的四条纪律

拆不动的系统不是拆的时候拆不动，是平时就没守住。这四条**从今天起适用于单体**：

1. **不跨模块 JOIN** —— 例外只有 `ReportMappers`，且必须走独立读模型演进；
2. **不跨服务事务** —— 一个 `@Transactional` 里只许写同一个服务的表；
3. **只经 `*-api` 接口调用** —— 不许 `@Autowired` 别的服务的 `ServiceImpl`；
4. **写操作幂等** —— 已有 `Idempotency-Key`、业务键 UNIQUE、`source_ref` UNIQUE、
   `pay_event_log(ref_no,event_type)`，拆开后重试会变多，这些是前提不是优化。

前三条**可以机器校验**（见「验证」）。

## 现状与阻塞

拆分可行性已实测，不是估计：

| 项 | 实测 | 结论 |
|---|---|---|
| 跨域 JOIN | 全仓 0 个 XML mapper，仅 2 个文件有 `@Select`，跨域 JOIN **只在 `ReportMappers`** | ✅ 业务逻辑全是单表，可拆 |
| 多实体事务 | 12 处触及 ≥2 实体，**按本 ADR 的四服务划分全部落在同一服务内** | ✅ 事务边界与切分独立吻合 |
| 循环依赖 | 模块图 **0 环** | ✅ |
| 表归属 | 132 张**全部有主，0 落单** | ✅ |

**三处必须先解决的**：

1. **划拨级联跨了服务边界** —— `AgentAssignmentServiceImpl.assign`（`@Transactional`）
   经 `AgentOwnershipSync.apply()` 在同一事务里写 `agt_assignment`+`loc_site`+`loc_location`(platform)
   与 `dev_cabinet`(core)。划拨是低频运营动作、不在主链路，改为**事件驱动最终一致**
   （划拨落单发事件 → 各服务回写自己的 `agent_no`）+ 对账补偿。
   ⚠️ 自动扫描发现不了这类问题（它不跟调用链，只看方法体），**所以「0 处跨界事务」这个结论不可信**
   —— 这一处就是跟着已知线索人工找到的。拆分前必须做一次跟调用链的完整核查。
2. **`gw_command_log.order_no`** —— 让 ops/设备接入 反向依赖 core 的订单。
   弹仓指令也可能由工单或运维触发，应改为通用 `biz_type` + `biz_ref`。
3. **5 个跨域重名业务键**（`account_no` `invoice_no` `plan_no` `refund_no` `rule_no`）——
   拆开后同名列指向不同服务的不同实体，是排错灾难。按 [db-design §1.4.1] 的冲突登记办法收敛。

## 取舍

**为什么不直接上 4 个微服务**：单运营方、未上线、团队规模小。4 个进程的运维成本现在换不来收益。
但边界现在不立，将来立不起来。

**为什么不是 ADR-016 的 10 个**：10 个服务里有 7 个的模块数 ≤3，拆出来只是把方法调用变成 HTTP。
本 ADR 的 4 个每个都有独立的伸缩理由：platform 读多写少可多副本、core 是主链路要单独扩容、
ops 可延迟、finance 是批处理。

**代价**：`*-api` 接口层与两套实现是**实打实的额外代码**，单体形态下它是纯开销。
接受这个开销换的是「拆分随时可做」，而不是「拆分要重写」。

**什么时候真的拆**：出现下列任一信号 —— core 的扩容需求与其他部分明显不同 ·
finance 的批处理开始影响主链路响应 · 合规要求资金数据独立部署 · 团队大到发布互相阻塞。
**在信号出现前不拆。**
