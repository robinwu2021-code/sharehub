# ADR-015 权限模块化与打包方式 —— 基础设施走脚手架(starter)、IAM 管理走业务模块、都不独立服务

状态：草稿（待确认）· 2026-07-12

## 背景

权限能力当前全部在 `backend/powerbank-app` 单模块内（`auth/*` 基础设施 + `platform/iam/*` 管理 + 各域 `@PreAuthorize` 消费）。用户要**动态管理角色/权限**，且要求「权限、角色的管理要**独立的业务模块**」，问：用**独立 jar / 独立服务 / 脚手架引入**？

## 关键前提：先把三类东西分开（性质不同 → 打包不同）

把"权限"当一坨会得出错误结论。它其实是三层，各自性质与最优打包不同：

| 层 | 内容（现有类）| 性质 | 有业务表? | 最优打包 |
|----|--------------|------|:--------:|---------|
| **① 权限基础设施** | `TokenStore` SPI+4实现 · 双 Filter · `SecurityUtils`/`StaffContext`/`ConsumerContext` · `PermChecker(@perm)` · `DataScope*`(拦截器/注册表/上下文) · `LoginUser`/`Realm`/`ScopeDim`/`PermVersion` · `SecurityConfig` | 横切、无状态、跨项目可复用 | 否 | **脚手架 starter jar** |
| **② IAM 业务域** | `iam_role/permission/role_perm/employee_role/menu/data_scope` + `PermissionService`/`MenuService`/`IamAdminController`/`IamSeeder`/`AuthController` | 有表、有配置 API、有审计 = 业务 | 是 | **业务模块 jar（进 monolith）** |
| **③ 消费方** | `trade`/`ops`/`user`… 用 `@perm` + `SecurityUtils` + 注册数据权限表 | 业务 | 是 | 依赖 ① |

## 三方案评估

### 方案 A · 独立服务（microservice）❌ 现在不做
- **违背 [ADR-001](./ADR-001-技术栈与服务粒度.md)**（modulith-default，按信号裂解，非上来就拆）。
- **否决点 = 数据权限**：`DataScopeHandler` 是**进程内拦截业务 SQL** 的 MyBatis 拦截器，必须与业务 Mapper **同进程**。拆成 IAM 服务后，AGENT/区域过滤**无法远程执行**——每个业务服务仍得内嵌 ① 的 infra jar，拆了并不省，反添分布式复杂度。
- 其它代价：每请求鉴权多一次网络跳（或复杂的本地缓存+失效广播）；分布式会话一致性；运维/部署翻倍。
- 结论：授权 + 数据权限 = **库（贴业务进程）**，不是服务。仅"认证签发/校验"与"IAM 配置管理 API"理论可远期服务化（见末节），但 MVP 不值当。

### 方案 B · 独立 jar（库）✅ 分两层
- **B1 = 基础设施 starter**（即方案 C 的形态）；**B2 = IAM 业务模块 jar**（进 monolith）。
- 契合 modulith；infra 可多 app 复用；边界清晰；未来"搬迁不重写"可无痛拆服务。

### 方案 C · 脚手架（spring-boot-starter）✅ 仅适用 ① 基础设施
- 就是 B1：把 ① 做成 `spring-boot-starter` + `@AutoConfiguration`，业务项目**引依赖即用、零样板**。
- **不适用 ② IAM 管理**（有表有业务、有配置数据，不是纯脚手架）。

## 决策

**① 基础设施 → 脚手架 starter jar；② IAM 管理 → 独立业务模块 jar（装进 app-modulith）；都不做独立服务（现在）。**

三件产物：
1. **`powerbank-security-starter`**（基础设施 starter）：`@AutoConfiguration` 自动装配 TokenStore/双 Filter/SecurityUtils 系/`@perm`/DataScope 系/SecurityConfig。业务模块**引依赖即获**「认证 + 功能鉴权 + 数据权限」能力，无样板。**类比现有 `neargo-common-security`/`neargo-auth-core`**（它们本就是 infra jar）。
2. **`powerbank-iam`**（业务模块 jar，回应用户"独立业务模块"）：角色/权限/菜单/数据范围**管理域**（表 + Service + `/api/platform/iam/*` 后台 API + 种子 + 登录/menus/permissions）。依赖 ①，与 `trade`/`ops`/`user` **平级**装进 app-modulith。
3. **各业务模块**依赖 ①（用 `@perm`/`SecurityUtils`/注册数据权限表）；运行期与 ② **同进程**（monolith 直调）拿 perms/menus。

## 为什么这样分（理由）

- **与既定架构一致**：ADR-001 modulith + [ADR-006](./ADR-006-复用neargo基础框架与依赖方式.md) 复用 neargo commons 作 L1 jar —— "infra 作 starter jar"是**已确立模式的延续**，不是新范式。
- **数据权限的物理约束**：enforcement 必须贴业务进程 → ① 只能是库。这条**直接否决了独立服务**。
- **IAM 是有状态业务域**（表/配置/审计）→ 独立**业务模块**，但不必是服务。
- **复用与解耦**：多 app（powerbank / 未来 neargo 家族）共享 ① starter；② 的 `iam_*` 表与业务同库（`pb_core`），同 monolith 直调，无跨库/跨服务事务。

## 迁移路径（从现状单模块，搬迁不重写）

| 阶段 | 动作 | 时机 |
|------|------|------|
| **P0 ✅ 已实施（2026-07-12）** | 边界做实：`auth`=纯 infra（**零 iam/业务依赖**，DIP 接口 `PrincipalRefresher` 解耦口径 B 的 `PermissionService`）、`platform.iam`=IAM 业务模块（`AuthController`/`RolePerms` 已移入，仅依赖 infra）；两包 `package-info` 声明模块边界；grep 验证依赖方向 + 29 测试全绿 | ✅ 完成 |
| P1 | 抽 `powerbank-security-starter`：移 `auth/*` infra + `config/{SecurityConfig,TokenStoreConfig,MybatisPlusConfig 数据权限段}` → `@AutoConfiguration` + `AutoConfiguration.imports` | 出现第二个消费方 / 想强制复用纪律时 |
| P2 | 抽 `powerbank-iam`：移 `platform/iam/*` + `AuthController` + `RolePerms`(种子)；app-modulith 聚合 | 与 P1 同期或稍后 |
| P3 | infra starter **上推 neargo commons 私仓**（与 auth-core 并列），neargo 家族共享 | 跨 app 复用成真时 |

> **YAGNI 提示**：powerbank 目前是**唯一** app 且是 monolith，P1/P2 现在抽模块**收益有限、平添工程复杂度**。务实路径：**现在先满足"IAM 独立业务模块"= 干净的包/子模块边界**（甚至一个 Maven module `powerbank-iam` 但仍单可部署），把 infra 抽 starter **推迟到第二个 app 或 monolith 裂解**时。因为包边界已干净，届时抽取=搬包+加 pom，业务代码不改。

## 何时才考虑独立"身份服务"（触发信号）

- 多个**独立部署**的应用需共享同一账号/角色/SSO（非同 monolith）；
- 合规/团队要求 IAM 独立部署与审计。

届时形态：IAM 配置管理 + 认证签发 → 独立**身份服务**（REST/OIDC 下发 token + perms/menus + **数据范围规则**），但 **`DataScopeHandler` enforcement 仍以 infra starter 内嵌各业务进程**——即「**中心配置 + 分布执行**」，而非把授权整体搬到服务。这再次印证：**认证可服务化，数据权限强制不可**。

## 影响

- 工程从单模块 →（未来）多模块：`parent` + `security-starter`(infra) + `iam`(business) + 业务域 + `app-modulith` 聚合。
- starter 需 `@AutoConfiguration` + `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` + `@ConditionalOnMissingBean`（让业务可覆盖默认，如自定义 TokenStore）。
- 版本：starter/iam 随 powerbank；上推 neargo 后随 commons 私仓版本。

## 待确认

1. **infra starter 归属**：powerbank 自有 `powerbank-security-starter`，还是直接增强 `neargo-common-security`（需与 neargo 协调发版）？（建议先自有，稳定后上推。）
2. **抽取时机**：现在就拆多模块，还是**先保持单模块 + 干净包边界，待第二消费方/裂解时再抽**（YAGNI，推荐）？
3. **IAM 表归属**：`iam_*` 随 ② 业务模块（`pb_core`），不随 ① infra（infra 无业务表）——确认。
