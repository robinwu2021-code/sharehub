# ADR-011 单运营方为主，多租户为预留口子

状态：已接受（2026-07-11 用户澄清）

## 背景
前期文档把「SaaS 多租户招商」当作一等目标，两级后台（平台超管 / 租户后台）、租户开通、SaaS 计费等占了不少 P0。用户澄清：**powerbank 本质是单一运营方自营** —— 有一个大租户就是平台运营方自己，核心运营逻辑围绕这一个租户。多租户只是为将来扩容预留的口子，不是 MVP 重心。

## 决策
1. **MVP = 单主租户自营**：存在一个 `tenant_no = MAIN`（运营方自己），所有运营在其下进行；上下文默认注入主租户，前台无租户切换。
2. **隔离机制照建（口子的"数据面"）**：`tenant_id` 全链路、`NeargoTenantLineHandler`、`TenantContext` 全部保留。理由：抽掉将来难补，且成本极低（一个列 + 一个插件）。
3. **平台层管理能力后置为 P1+（口子的"管理面"）**：租户开通/停用/套餐配额、SaaS 计费账单、平台超管跨租户切换、平台大盘、设备-租户归属分配等 —— **MVP 不做**，招商引入第二个租户时才启用。
4. **运营重心 = 主租户的日常经营套件**：设备/订单/工单/财务/点位/用户/员工权限 —— 这些围绕单一运营方全量做 P0。

## 影响
- 运营端两级后台在 MVP **收敛为一套运营后台**（主租户视角）；平台超管层是空壳/后置。ops-web 的 `PLATFORM_ADMIN` 角色与 `/tenants` 模块降为口子（保留但非 MVP 重点）。
- 功能矩阵中「平台」层功能点整体降级（见各功能细化的重标）。
- 架构零改动：多租户设计（ADR-002）仍成立，只是运营语义上先跑一个租户。
- C端品牌/共用小程序（ADR-005）语义简化：MVP 就是主运营方一个品牌。

## 细化（2026-07-11 追加）
1. **多租户是休眠口子，可能永不启用**：AI 时代更可能是**每个租户一套独立部署的系统**（各自实例），而非共享一套多租户平台。故多租户**管理面（§15）不建、文档最小化体现**，仅保留 `tenant_id` 数据列这个最低成本的口子。
2. **口子语义泛化为"隔离的经营实体"**：若真启用，最现实的场景不是"招别的运营商"，而是**同一运营商跑多个业态实体**（充电宝 / 充电桩 / … 各算一个 tenant，数据各自独立）。`tenant_id` 因此不绑定"品牌运营方"含义，泛指一个隔离经营单元（业态 / 未来运营方 / 独立部署 皆可）。
3. **业态可扩展性（前瞻，非 MVP）**：当前设备/订单模型是**充电宝专用**（机柜/仓位/充电宝）；充电桩(EV 等)是不同的设备/会话模型，属**未来业态**，届时可用 `tenant_id`（各业态一租户）或独立部署承载，MVP 不建，但设备抽象尽量不写死"仅充电宝"。

## 备选与否决
- 抽掉多租户、纯单租户建模 → 否决：口子成本极低（一列+一插件），将来难补。
- 维持多租户招商为 P0 / 建管理面 → 否决：与运营重心不符，且 AI 时代可能改走独立部署，不值当。
