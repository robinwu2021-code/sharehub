## 一、运营主体 Operator —— 谁在经营

> 出钱、铺设、运维、拿分润的那个主体。

```
                  Operator 运营主体
          （operator_no · operator_type · 名称 · 联系人 · 状态）
                          │
      ┌───────────────────┼───────────────────┐
  PLATFORM            AGENT             CITY_PARTNER
  平台自营             代理商              城市合伙人
  恒一行，不可停用     出资 + 运维        出资+拓展+运维+效果管理
```

**`代理商` 不是一个主体类型的名字，它是运营主体的一种。** 平台自营是另一种。

**主体向下分出两条并列的 1:N**（[领域模型 §2.4.1](../领域模型-本体与关系.md)）：
`主体 → 商户`（通道 × 市场 × scope）与 `主体 → 站点`（主责）。
**不是「主体 → 商户 → 站点」的三级树**——站点与商户之间没有边，收款号在站点上按 scope 解析。
向上则是 N:M：一个手机号可属多个主体（[ADR-030](./ADR-030-账号与主体-一个账号可属多个运营主体.md)）。

### 1.1 这个抽象消掉的四个副作用

今天没有这个概念，「平台自营」只能用**没有主体**表示——6 张表的 `agent_no` 可空，`NULL` 就是平台：

| # | 副作用 | 后果 |
|---|---|---|
| 1 | NULL 进不了唯一键 | `share_record` 幂等键 `(order_no, dimension, payee_no)` 失效（MySQL 的 UNIQUE 不约束 NULL） |
| 2 | 平台收入记不进分润表 | 直营站点的收入在 `share_record` 里**没有行**，对账时平台侧是个洞 |
| 3 | `GROUP BY` 丢平台行 | 「按运营主体统计 GMV」要 `COALESCE` 才不少算 |
| 4 | 责任表无法表达直营 | ADR-027 的责任行，直营站点的 `OPERATE` 挂给谁？ |

**四个同一个根因：把「平台」这个主体排除在主体之外。**

## 二、商户 Merchant —— 为收款而加，挂在主体上

> **主体先是运营主体，商户只是挂在它上面的收款能力。**

```
Operator 运营主体
  └─ Merchant 商户（1 : N）
       通道 × 市场 × 进件状态 × 子商户号 × 结算账户
```

### 2.1 为什么必须分开：这个词坑过人

ai-shop 的「全域命名基准」（同级仓库 `ai/ai-shop`，`docs/technical/reference/全域命名基准.md`）第 1 条：

> **`merchant` 一词只用于支付语境（收款商户号），经营实体一律叫 `entity`。**

写这条的代价是一整轮返工——他们把「商户」读成了「一张营业执照的经营实体」，据此提了一套三层模型还打算新建表，事后在文档里公开更正。
**本 ADR 采用同一条铁律：「商户」只在支付语境出现，经营实体一律叫「运营主体」。**

### 2.2 一个主体多个商户（1:N）

ai-shop 的 `mch_payment_merchant` 唯一键是 `(entity_no, pay_channel, store_no)`——
同一主体在不同通道、不同门店可以有不同收款号。我们多市场（AED / SAR）时同理。

**没有商户的主体照样是主体**（还没进件的新代理商），**有多个商户的主体也不矛盾**。
这正是「主体不强调收款」的实际含义：收款是能力，不是身份。

### 2.3 Stripe 的同构验证

Stripe Connect **Accounts v2 把固定账户类型改成了可组合的角色配置**（Merchant / Customer / Recipient），
一个 Account 可同时持有多个。也就是说「能不能收款」是挂在主体上的**能力**，不是主体的**类型**——与 §二 同构。

## 三、场地 Venue —— 独立概念，与运营主体关联

> 场地方提供物理场地，按进场合同拿分成。**不经营、不出资、不运维。**

```
Venue 场地方 ──提供场地──▶ Site 站点 ◀──经营── Operator 运营主体
        └──签──▶ Contract 进场合同（分成率/进场费/期限）
```

站点上两个归属**正交**，不能压成一条所有权链：`operator_no`（谁在经营，拿分润）· `venue_no`（谁的地盘，拿进场分成）。

### 3.1 场地方需要的不是「商户」，是「收款账户」

这是本 ADR 最要紧的一条区分：

| | 收单（收消费者的钱） | 打款（接收结算） |
|---|---|---|
| **运营主体** | ✅ 需要**商户**（进件 / 通道 / 子商户号） | ✅ 需要收款账户 |
| **场地方** | ❌ **从不收消费者的钱** | ✅ 需要收款账户 |

场地方永远不与消费者发生支付关系——它只是周期性地被打款。
所以给场地方配「商户」是错的；它需要的是**银行收款账户**（`md_bank` + IBAN + 户名）。

**Stripe 恰好也是这么分的**：`merchant` 配置 = 能收款，`recipient` 配置 = 能接收转账与打款，两者独立。
大多数 marketplace 的连接账户只配 `recipient`——对应我们的场地方。

### 3.2 Payee 仍是两支，但机制不同

```
Payee 分润受益方（payee_type + payee_no）
  ├── OPERATOR  运营主体 ── 费率来源：分润规则 + 责任 basis（ADR-027）
  └── VENUE     场地方   ── 费率来源：进场合同
```

两者都是受益方、共享 `share_record → stl_settlement → stl_withdrawal → acct_account` 整条链；
差别只在**费率从哪来**与**收款机制**（商户 vs 纯打款账户）。

### 3.3 为什么场地方不并进主体（本轮否决 Party 合并）

Party Model、SAP Business Partner 都主张「一个实体多个角色」，理由是同一家公司可能既是客户又是供应商，
拆两张表会出现两条重复记录。**这条在通用 ERP 成立，在本项目按用户裁决不采用**：

- 场地方与运营主体的属性交集只有「名称 / 联系人 / 收款账户」，**其余完全不同**
  （代理商有辖域、分润率、责任；场地方有行业、进场合同）；
- 并表会让「运营主体」这个词失去判据——一个不经营的东西凭什么叫运营主体；
- 「商场自投自营」的情形仍可表达：该商场作为 Venue 提供场地，同时**另行登记**为 Operator 经营自己的站点。
  两条记录指向同一家公司，**代价是这层关联不在系统里** —— 见 §七 待确认 3。

## 四、三个概念的职责边界（一句话各一条）

| 概念 | 回答什么 | 不回答什么 |
|---|---|---|
| **运营主体 Operator** | 谁在经营这个站点、谁拿分润 | 钱怎么收（→ 商户）、场地是谁的（→ 场地方） |
| **商户 Merchant** | 消费者的钱从哪个通道进、进谁的子商户号 | 谁在经营（→ 主体） |
| **场地 Venue** | 场地是谁的、按什么合同分成 | 谁在经营（→ 主体） |

### 5.1 两步走：概念正确性与迁移时机解耦

| | **A · 现在（L1）** | **B · S1 改名窗口** |
|---|---|---|
| 做法 | `agt_agent` 升格为运营主体表，加 `operator_type` 与 `PLATFORM` 哨兵行；6 个可空列去 NULL | 列名 `agent_no → operator_no`，表 `agt_agent → org_operator` |

| 对象 | 表 | 说明 | 级 |

## 六、不变量

| # | 不变量 | 守卫 |
|---|---|---|
| 1 | 每个站点**恰好一个**运营主体，不允许为空 | DDL `NOT NULL` |
| 2 | `PLATFORM` 主体**恒有且仅有一行**，不可停用 / 归档 / 删除 | 应用层校验 + 守卫测试 |
| 3 | 平台**不得有代理账号**（运营主体是经营单位，不是登录单位；平台员工走 `iam_employee`） | 应用层校验 |
| 4 | 数据范围行为不变：代理商看不到直营数据 | 现有 `agent_cannot_see_platform_direct_rows` **照样通过** |
| 5 | 运营主体与场地方**两个正交归属**，不得合并 | [领域模型 §2.2](../领域模型-本体与关系.md) |
| 6 | **「商户」只在支付语境出现**；经营实体一律叫运营主体 | 命名守卫（同 ADR-021 的命名卡口） |
| 7 | 场地方**不得挂商户**，只挂收款账户 | 应用层校验 |
| 8 | **`loc_site.operator_no` 必须在该站点责任行中出现且持有 `OPERATE`** | 应用层校验 + 守卫测试（[领域模型 §2.4.2](../领域模型-本体与关系.md)）|
| 9 | 站点**不得**有 `pay_merchant_no` 外键；收款号只按 scope 解析 | 命名/结构守卫（§5.2 · V51） |

## 七、否决的方案

| 方案 | 否决理由 |
|---|---|
| 场地方并入主体（Party Model / SAP 式合并） | 用户 2026-09-23 裁决「场地不算主体」。属性交集只有三项，并表会让「运营主体」失去判据 |
| 主体直接带收款字段（不分商户） | 违反「主体不强调收款」；且一个主体多通道多市场时放不下 |
| 给场地方也配商户 | 场地方从不收消费者的钱，配商户是错的抽象（§3.1） |
| 保持 NULL + 查询里 `COALESCE` | 把问题推给每个查询，漏一处静默少算；唯一键仍用不了 |
| 平台自营单独建「直营站点」表 | 直营与代理经营的站点在其它所有维度同构，拆表让每个查询变 UNION |
| 直接上 B、不走过渡 | 四个副作用要多等一个大窗口；而 A→B 迁移成本几乎为零 |
