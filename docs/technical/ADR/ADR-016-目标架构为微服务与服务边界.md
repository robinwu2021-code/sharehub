# ADR-016 目标架构为微服务 —— 服务边界与接口契约

状态：**已被取代**（2026-07-30）→ [ADR-017 一套代码，两种部署](./ADR-017-单体与微服务双形态部署.md)

> ⚠️ **本文的 10 服务划分已作废**。用户同日追加两条约束：一套代码要同时支持单体与微服务部署、
> 微服务数量不超过 4 个。ADR-017 重新划分为 **4 个服务（platform / core / ops / finance）**，
> 划分依据从「按域切分」改为「**同步主链路必须在同一进程内**」。
>
> 本文仍有价值的部分：服务间接口契约的写法、演进路径 P0→P5 的节奏判断。
> 已作废的部分：服务数量与具体边界。

## 背景

[ADR-001](./ADR-001-技术栈与服务粒度.md) 定的是「**粗粒度域 + modulith 起步，按信号裂解**」——
即不预设最终形态，等出现扩缩容/发布节奏/合规边界的压力信号再拆。

2026-07-30 用户明确要求「**架构图按照微服务设计，定义边界以及对应的接口**」。
这把目标形态从「按信号演化」变成了「**已定为微服务，现在就把边界与接口定下来**」。

两者的实质差别不在最终形态（ADR-001 也允许拆到微服务），而在**什么时候定契约**：

| | ADR-001 | 本 ADR |
|---|---|---|
| 目标形态 | 开放（可能一直是单体） | **明确为微服务** |
| 边界定义时机 | 裂解时再定 | **现在就定** |
| 当前部署 | 单体 | 单体（**不变**） |

## 决策

### 1. 目标架构 = **10 个业务服务 + 3 个 BFF + 1 个南向网关**

服务目录、数据归属、拆分依据见 [架构-微服务边界与接口.md](../架构-微服务边界与接口.md)。

### 2. **当前仍是单体部署，但代码必须按目标边界组织**

这是本 ADR 最实际的约束。具体到日常开发：

- 跨域调用**写成接口调用的形状**（域间经 `/internal` 契约或 `DomainEventPublisher`），
  不图省事直接调另一个域的 Service 内部方法；
- **绝不跨域 join 表**。需要别的域的数据 → 走接口取，或在本域存读模型副本；
- 一张表只有一个域写。冗余列（如 `agent_no`）只能由**权威域**的事件驱动更新。

> 这三条不是为了将来好看，是为了「拆分 = 搬迁不重写」。**任何一次跨域 join 都是给未来埋雷**，
> 这是 code review 要盯的第一条。

### 3. 拆分顺序沿用 ADR-001 的信号驱动

`access-gateway`（长连接）→ `payment`+`finance`（合规边界）→ `trade`（峰值扩缩容）→
`device`+`workorder`（写入量）→ 其余按需。`platform-config` 与 `identity` 是全域依赖，最后拆或永不拆。

### 4. 明确**不拆**的三处（避免 nano-service）

| 曾考虑拆出 | 不拆的理由 |
|---|---|
| `alarm` 独立服务 | 告警的唯一下游是工单，且「告警→自动开单」要求幂等 + 同事务语义。拆开这个闭环变成跨服务 saga，收益为零 |
| `support`(客服) 独立服务 | 报障受理是薄分流器，规则来自字典，出口是工单/退款，自身几乎无数据无逻辑 |
| `pricing` 独立服务 | 计费引擎是**纯函数**，被订单在同一请求内高频调用。拆出去等于给每次算价加一次网络往返 |

## 后果

### 正面
- 边界与接口先定，避免「先写成一团再想怎么拆」；
- 归属/幂等/事件契约在单体阶段就被强制，拆分风险大幅下降。

### 负面 / 代价
- **约束了日常写法**：不能跨域 join、不能直调别域内部方法 —— 短期比单体自由写法慢；
- **已实现功能受影响**：行级数据范围依赖 `agent_no` 在五张表上的冗余，拆分后这五张表分属四个服务，
  当前 `AgentOwnershipSync` 的本地事务级联必须改为 `OwnershipChanged` 事件驱动。
  详见 [架构-微服务边界与接口 §四](../架构-微服务边界与接口.md)——**这是本次口径变更最实际的技术债**；
- 拆分后必须先有链路追踪，否则排障成本指数上升。

### 与 ADR-015 的关系
[ADR-015](./ADR-015-权限模块化与打包方式.md) 否决「IAM 独立服务」的核心理由是
**`DataScopeHandler` 是进程内 MyBatis 拦截器，必须与业务 Mapper 同进程**。该理由在本 ADR 下依然成立：
本 ADR 的 `identity` 服务只提供**权限集与数据范围规格**（`GET /internal/identity/data-scope/{no}`），
**过滤动作仍在各业务服务本地执行**。两个 ADR 不冲突。

## 待确认
1. 消息中间件选型（`DomainEventPublisher` 目前是 Logging 实现）与事件 schema 演进策略。
2. BFF 是三个还是合并（代理端接口面几乎是运营端子集，可否靠数据范围区分）。
3. 划拨后归属可见性允许秒级延迟（事件驱动）还是要求立即（同步查权威域）。
