# ADR-025 直接复用 ai-shop 在跑的支付与任务服务；两服务改造为多系统多平台；框架暂缓

状态：**已决**（2026-09-23，用户定）
· 修订 [ADR-020](./ADR-020-单体优先-支付与协议对接独立部署.md) 待确认 2（实例「各自一套」→ **共用一套**）
· 延续 [ADR-024](./ADR-024-共用服务暂由ai-shop托管-组件并入框架.md)（支付与任务是共用服务、代码留 ai-shop）
· 暂停 [v4/13](../v4/13-neargo-framework独立仓库.md) 的框架落地

用户原话：「pay 和 job 基本直接用 ai-shop 现成的服务，要求 pay 和 job 支持多系统、多平台；pay 和 job 的代码已经整理为统一的 `/pay` 和 `/job` 下包含各自的全部代码；framework 暂时先不建，等本地全部处理好并测试通过再建」。

## 背景（2026-09-23 实测）

| 项 | 现状 |
|---|---|
| 代码位置 | ai-shop 已把两个服务各自收拢：`backend/pay/{pay-channel,pay-domain,pay-svc}` + 聚合 pom；`backend/job/{shop-job-api,-store,-core,shop-job}` + 聚合 pom（提交 `9ee65416`） |
| 部署 | 两个服务**已在生产跑**：`ai-shop-pay.service`（:8083）· `ai-shop-job.service`；与 ShareHub 在**同一台腾讯云机器**上，内网直通 |
| job 多目标 | **已有**：`targets: {PLATFORM: url}` 映射 + `job_definition.target` 列；但**没有「系统」维度**，`job_name` 全局唯一，运营端直读 job 库、无系统过滤 |
| job 令牌 | 所有目标**共用一把** `shop.job.worker.token` |
| pay 多市场 | **已有**：`sys_market`（市场 / 币种 / 精度 / 时区）· `sys_pay_channel_market`（通道 ↔ 市场） |
| pay 通道凭据 | 在**配置项**里（`shop.pay.wechat.mchid/appid/private-key…`），一个进程只能持有一套商户凭据 |
| **pay 的库** | **今天连的是 ai-shop 主库 `ai_shop`**，且 Flyway 由主应用统一跑（`pay-svc` 自己关闭 Flyway）；「独立进程」已做、「独立库」未做 |
| pay 业务耦合 | `stl_payment` 直接带 `order_no` / `sub_order_no` / `after_sale_no` / `entity_no` 等电商字段；另有 41 处对 ai-shop 业务口的反向引用 |

## 决策

| # | 决定 |
|---|---|
| 1 | **ShareHub 不部署自己的支付与任务实例**，直接接入已在跑的 `ai-shop-pay` 与 `ai-shop-job`（同机内网） |
| 2 | 两个服务**改造为多系统**：数据、配置、接口、运营权限都带 `system` 维度；首批两个系统 `SHOP`（ai-shop）· `SHAREHUB` |
| 3 | **多平台**：支付复用已有的 `market` 维度（一个系统可有多市场多币种），通道凭据按 `(system, market, channel)` 存**库**、不再放配置项；任务的 `targets` 按系统分组（一个系统多个目标进程） |
| 4 | **硬前提**：支付服务必须**先有自己的库**。今天它连主库 `ai_shop`，不先分库，ShareHub 的支付数据会落进 ai-shop 的业务库 —— 这一步不做，多系统不许上线 |
| 5 | **框架（`neargo-framework`）暂缓**：本地目录**冻结**（不提交、不建远端、不发布、不做 2.x 重排），ShareHub 的父 POM 维持现状；等支付与任务的多系统改造在本地跑通且测试通过，再启动框架 |
| 6 | **留退路**：`system` 维度到位后，任何时候可以按市场 / 法域拆成两套实例，只改配置里的地址，代码与数据模型不动 |

## 为什么共用实例（而不是各自一套）

| 理由 | 说明 |
|---|---|
| 服务已在跑 | 两个服务是 ai-shop 的在产资产，ShareHub 另起一套等于把同一份代码的运维成本翻倍（两套配置、两套升级、两套监控、两套凭据轮换） |
| 同机内网 | 两个系统在同一台腾讯云机器上，调用不过公网、不经 nginx |
| 多系统本来就该做 | 将来还会有第三个系统。把「系统」做成一等维度，比每次新系统都复制一套实例更省 |
| 可退可分 | 拆分的成本在**有没有 system 维度**，不在实例个数。先把维度做出来，拆分随时可做 |

## 风险与对策

| 风险 | 对策 |
|---|---|
| **爆炸半径**：一个支付服务挂了两个系统都不能付款 | 内部接口版本化 + 向后兼容；发版灰度（先重启一个实例）；ShareHub 侧对支付调用**全部走 `PaymentPort`**，支付不可用时借还降级为「先借后付」或拒绝新单，不拖垮主流程 |
| **数据驻留**：将来 UAE PDPL 要求本地化时，两系统的数据在同一个库 | `system` 列使「按系统整库搬迁」成为一次 `WHERE system='SHAREHUB'` 的导出；触发条件（法务要求本地化）出现即按决定 6 拆实例 |
| **越权**：一个系统读到另一个系统的数据或凭据 | 每系统一把内部令牌；过滤器把令牌解析成 `system` 并**强制覆盖**请求里的值；DAO 层按 `system` 过滤（不信任调用方传参）；验收用「拿 SHAREHUB 令牌查 SHOP 数据 → 404」的测试守 |
| **运营串台**：ShareHub 运营看到 / 触发 ai-shop 的任务 | 运营端任务接口按登录人所属系统过滤；ShareHub 的运营台只能取到 `system=SHAREHUB` |
| **版本耦合**：一边要改契约，另一边还没准备好 | 内部接口只加不改；需要破坏性变更时先并行提供新路径，两系统都切完再下线旧的 |
| **单号相撞**：两系统各自生成的商户单号可能重复 | `out_trade_no` 带系统前缀；唯一键含 `system` |

## 否决

| 方案 | 理由 |
|---|---|
| ShareHub 各自部署一套支付与任务实例（ADR-020 原推荐） | 用户明确要求直接用现成服务；同机同网下另起一套只增加运维成本 |
| 不做 `system` 维度，用 target 名字前缀（如 `SHAREHUB_APP`）区分 | `job_name` 全局唯一会跨系统相撞；运营端无法按系统隔离；支付侧更不可行（凭据、对账、结算都要按系统分） |
| 支付继续连 ai-shop 主库 | ShareHub 的支付与用户数据落进 ai-shop 业务库，越权与合规风险都不可接受 |
| 先建框架、再改两个服务 | 用户要求先把本地跑通；框架重排会与两个服务的改造抢同一批人和同一批测试 |

## 后果

- ADR-020 的「实例各自一套（推荐）」作废，改为**共用一套 + 可拆**；[02 §一](../v4/02-服务与模块.md) 的进程表随之调整：ShareHub 侧不再有 `sharehub-pay` / `sharehub-job` 两个自有进程，改为「接入 ai-shop 的两个服务」；
- ShareHub 不再需要 `sharehub_pay` / `sharehub_job` 两个库（数据在共用服务的库里，按 `system` 隔离）；
- 需要 ai-shop 做的改造清单见 [v4/15 多系统多平台改造需求](../v4/15-多系统多平台改造需求.md)，由 ai-shop 统一改；
- 框架相关的 v4/10–13 与[框架 design/01](../../../../neargo-framework/docs/design/01-分层粒度与多ORM.md) 全部标记**暂缓**，方案保留不作废；本地 `/Users/robin/work/ai/neargo-framework` 原样冻结（已验证可构建，随时可继续）；
- ShareHub 侧不阻塞的工作照常推进：安全止血、卡口与测试地基、实体请求体、目录重排、包归位、命名通用化、跨进程地基（[v4/14](../v4/14-执行任务清单.md)）。
