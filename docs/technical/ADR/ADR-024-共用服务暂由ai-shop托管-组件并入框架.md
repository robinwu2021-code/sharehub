# ADR-024 支付与任务为共用服务、暂由 ai-shop 托管；其余能力作为组件并入框架

状态：**已决**（2026-09-23，用户定）· **后续**：[ADR-025](./ADR-025-直接复用ai-shop在跑的支付与任务服务-多系统改造.md) 进一步定下「两个服务的**实例**也共用一套、改造为多系统」，本 ADR 的「代码留 ai-shop」不变
· 修订 [ADR-020](./ADR-020-单体优先-支付与协议对接独立部署.md) 待确认 1（共享 pay 放哪）与 3a（任务代码放哪）
· 修订 [ADR-022](./ADR-022-共享构件发布到自建Nexus.md) 的发布源
· 取消 [v4/13](../v4/13-neargo-framework独立仓库.md) 推荐的 `neargo-components` 仓库

用户原话：「channel 应该集成到 pay 中，wechat 应该也包含在内，pay 和 job 作为独立的服务，暂时先放到 ai-shop 项目中，如果需要改，协调 ai-shop 项目统一改；其他的可以考虑统一封装到 framework，作为组件部分」。

## 背景

- 此前方案把 ai-shop 里可共用的东西统称「能力组件」，计划抽到新仓库 `neargo-components`。其中混了两类性质不同的东西：
  **服务**（自己的进程、自己的库、部署即生效：支付、任务调度）与**库**（嵌在调用方进程里、随调用方升级生效：通知通道、媒体存储）。
- 实测 ai-shop（2026-09-23）：
  - `pay/pay-svc` 是独立进程（`PayApplication`，自有库，只开放 `/internal` 与 `/callback`）；生产目前跑「形态 A · 内嵌」，`shop-app` 直接依赖 `pay-channel` + `pay-domain`；
  - `shop-job` 是独立调度器（`JobApplication`，自有库）；`shop-job-core` 同时被 `shop-app` 内嵌；
  - 微信能力分散在三处：微信支付与进件在 `pay-channel`；小程序登录、手机号、小程序码、发货信息录入在 `shop-channel`；订阅消息在 `shop-notify`；
  - `shop-notify` 只有通道适配器（阿里云短信、SMTP、FCM、APNs、个推 + Stub），无表、无进程；模板与发送日志在 `shop-core/message/notify`（业务）；
  - 媒体（`shop-channel/media` + `shop-store-mybatis/media`）是库，带表 `sys_media_asset`，清理任务以 `JobHandler` 注册。

## 决策

| # | 决定 |
|---|---|
| 1 | **支付、任务是共用服务**，不是组件，不进框架 |
| 2 | 两个服务**暂时留在 ai-shop 仓库**，坐标沿用 ai-shop 的（`ai.neargo.shop:pay-*` · `ai.neargo.shop:shop-job-*`）；本项目需要的任何改动**提给 ai-shop，由 ai-shop 统一改**，本项目不 fork、不复制 |
| 3 | **通道归入支付服务**：所有支付通道（微信支付、支付宝、待接的 AE 通道）与进件都在支付服务内，不单独对外 |
| 4 | **微信能力全部归入支付服务**：小程序登录（code2Session）、手机号、小程序码、发货信息录入、订阅消息的实现，与微信支付放在一起；对外经支付服务的内部接口与客户端提供 |
| 5 | **其余可共用的能力作为「组件」并入 `neargo-framework`**（目录 `components/`）：现阶段为 `neargo-notify`（通知通道）与 `neargo-media`（媒体存储）；以后满足入选判据的（如 `neargo-md`）照此加入 |
| 6 | ~~实例各自部署~~ → **已被 [ADR-025](./ADR-025-直接复用ai-shop在跑的支付与任务服务-多系统改造.md) 修订**：两个服务**共用 ai-shop 在跑的实例**，按 `system` 维度隔离；拆分随时可做 |

## 理由

| 决定 | 理由 |
|---|---|
| 服务不进框架 | 服务有自己的进程、库、迁移与部署配置；版本语义是「网络接口兼容、部署即生效」，与框架库的「Java 接口兼容、调用方升级才生效」不同，放在一条版本线里会互相拖累 |
| 暂留 ai-shop | 两个服务只有 ai-shop 在生产跑；现在搬仓会打断 ai-shop 的在途工作（支付双形态切换）。坐标与包名跟放在哪个仓库无关，以后要搬，本项目只改依赖坐标 |
| 微信并入支付 | ① 微信的 `access_token` 同一时刻只能由一方持有并刷新，多个进程各自获取会互相顶掉 —— 必须集中在一个服务；② 小程序登录拿到的 openid 是微信支付下单的必需参数；③ 发货信息录入是微信小程序支付的合规要求；④ appid / 密钥 / 商户号与 API v3 密钥集中在一个进程，泄露面最小 |
| 组件并入框架 | 通知通道、媒体存储是嵌入产品的库，发布节奏与框架一致；与框架同仓、同版本、同一个 BOM，产品只管一个版本号 |

## 后果

- **本项目依赖 ai-shop 发布的少量构件**：只许依赖服务的客户端与契约 —— `pay-client`、`shop-job-api`、`shop-job-target`；其余 `ai.neargo.shop:*` 一律禁止（enforcer 白名单，[v4/12 §5.6](../v4/12-代码库与工程结构.md)）。
- **需要 ai-shop 做的改动**（本项目提需求、ai-shop 排期）：

  | # | 改动 | 本项目为什么需要 |
  |---|---|---|
  | 1 | 把 `shop-app/payclient`（22 个类）整理为独立模块 `pay-client`，不依赖 `shop-*` | 本项目只经它调用支付服务 |
  | 2 | 收款 API 与回调入口移进 `pay-svc`（现在 11 个远程 Port 是「调用即抛」的桩） | 本项目只用独立形态 |
  | 3 | 41 处对 ai-shop 业务口的反向引用（`MerchantQueryPort` 27 · `SettleSourcePort` 14）泛化为 `bizType + bizNo`，或可按实例关闭 | 本项目的实例没有 ai-shop 的商户数据 |
  | 4 | 预授权族（冻结 / 请款 / 撤销）与首个 AE 通道 | 免押借还必需；本项目在阿联酋 |
  | 5 | 微信能力并入支付服务并开放内部接口（登录、手机号、小程序码、发货信息、订阅消息） | 本项目小程序（P1） |
  | 6 | 目标侧小类（`shop-base/job` 的 `JobHandlerRegistry` 等）收成 `shop-job-target`；配置前缀可配 | 本项目的 app 与网关是任务目标 |
  | 8 | **两个服务改造为多系统多平台**（ADR-025，详见 [v4/15](../v4/15-多系统多平台改造需求.md)） | 两个产品共用同一套实例的前提 |
  | 7 | ai-shop 的 CI 把上述客户端 / 契约构件发布到 Nexus | 本项目要依赖它们（可执行 jar 由 ai-shop 自己部署，本项目不再另起实例，ADR-025） |

- **组件与服务之间不许反向依赖**：框架里的组件不能依赖 ai-shop 的构件。所以
  - `neargo-media` 只提供扫描 / 对账 / 清理的服务方法，产品自己把它们登记成任务（一个几行的 `JobHandler`）；
  - `neargo-notify` 保留订阅消息的接口与 Stub，真正的微信实现由产品接到支付服务。
- 仓库数减为：`neargo-framework`（框架 + 组件）· ai-neargo · ai-shop（产品 + 两个共用服务）· 本项目。

## 否决

| 方案 | 理由 |
|---|---|
| 另建 `neargo-components` 放支付 / 任务 / 通知 / 媒体 / 微信 | 把服务和库混在一类；服务还没有稳定到可以离开 ai-shop |
| 支付 / 任务并入 `neargo-framework` | 服务的进程、库、发版语义与框架库不同（见理由） |
| 微信能力做成独立的库、各产品进程各自调用微信 | `access_token` 会被多个进程互相顶掉；密钥散落 |
| 本项目先复制一份支付 / 任务代码自己改 | 违背 ADR-020「两个项目用一个模块」 |
