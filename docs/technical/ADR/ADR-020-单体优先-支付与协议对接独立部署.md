## 决策

### 一、默认部署 = 1 个业务单体 + 2 个独立服务 + 1 个调度器

| 部署单元 | 包含 | 独立的理由 |
|---|---|---|
| **`sharehub-app`** 业务单体 | platform · core · ops · finance 全部业务模块 + 嵌入式认证 + portal（`/api` `/mp` `/internal`） | —（默认形态） |
| **`pay-svc`**（ShareHub 实例） | **共享的 ai-shop pay 模块**：通道适配 · 支付流水 · 退款 · 回调 · 对账 · 提现打款 | 见决策二 |
| **`sharehub-gateway`** 协议对接服务 | 厂商目录运行时 · 传输适配 · 接入内核 · 驱动插件 · 指令 / 报文日志 · OTA 下发 | ADR-018 已论证（变化原因 / 故障域 / 技术栈 / 工种） |
| **`sharehub-job`** 调度器 | **共享的 ai-shop 任务服务**：到点回调各进程的任务端点，本身不执行业务 | 见决策六 |

ADR-017 的双形态机制（`*-api` 接口 + 本地 / 远程两套实现、classpath 决定形态）**保留**，
但**只有 pay 与 gateway 默认走远程**。ops / finance / platform 的拆分信号仍按 ADR-017 执行，**信号出现前不拆**。

### 二、支付：共享 ai-shop pay 模块 —— 一份代码，两项目各自部署

**不重做。** ai-shop 的 `pay/`（`pay-channel` / `pay-domain` / `pay-svc`）已有通道 SPI（`PayGateway`）、
微信 / 支付宝 / Stub 适配器、回调验签（验签 → 回查 → 落库）、幂等、四轴对账、提现、独立进程与独立数据源。
ShareHub 把它当作**共享模块**使用，自己只写两样东西：

1. **适配层**：`PaymentPort`（ShareHub 业务侧已有的接口：pay / preAuth / capture / release / refund / query）
   的远程实现 `RemotePaymentPort`，调 pay-svc 的内部 API；
2. **支付编排**：何时冻结、冻结多少、何时请款 / 撤销 —— 留在 core 的订单状态机里。

**「共享」的含义分两层，本 ADR 的选择**：

| 层 | 选择 | 理由 |
|---|---|---|
| 代码 | **一份**（两项目依赖同一组构件） | 用户要求 9；通道对接、验签、对账是最贵也最容易出错的部分，维护两份是纯浪费 |
| 部署实例 | **各自一套**（ShareHub 起自己的 pay-svc + `sharehub_pay` 库） | 两项目的签约主体、商户号、市场（CN / MENA）、数据驻留（PDPL 要求 MENA 用户数据留在区域内）都不同；一个实例服务两者要给每张表、每个 API、每个回调加应用维度，风险与工作量都更大 |

**共享前必须做的三件事**（实测 ai-shop 现状得出，不是估计）：

| # | 现状 | 要做什么 |
|---|---|---|
| 1 | `pay-channel` / `pay-domain` 依赖 `shop-base` + `shop-store-mybatis`（ai-shop 内核）；包名 `ai.neargo.shop.pay` | **暂留 ai-shop**（[ADR-024](./ADR-024-共用服务暂由ai-shop托管-组件并入框架.md)，2026-09-23 用户定：pay 与 job 作为独立服务暂放 ai-shop，需要改动由 ai-shop 统一改）；内部依赖不必改，对外只发布不依赖 `shop-*` 的 `pay-client`；两项目按坐标依赖（同 ADR-006 的方式） |
| 2 | pay 对 ai-shop 业务口有 **41 处反向引用**（`MerchantQueryPort` 27 · `SettleSourcePort` 14，ai-shop 自己有棘轮在管） | 泛化为以 `bizType + bizNo` 表达的 SPI（收款主体、结算来源），**两项目各自实现**；ShareHub 不用的结算能力不装配 |
| 3 | 回调入口 `/pay/callback/{channel}` 在 `shop-core`；独立形态的 pay-svc 目前只暴露费率 / 结算发票端点 | 回调与收款 API 移进 pay-svc —— 这也是 ai-shop 自己 ADR-021「切产物」阶段的目标，两边一起受益 |

**ShareHub 需要、共享模块目前没有的**（补进共享模块，而不是 ShareHub 自己写）：

- **预授权族**（`preAuth` / `capture` / `release`）—— 免押的前提；作为 `PayGateway` 的可选能力接口，不支持的通道不实现；
- **阿联酋通道**：ai-shop 多区域通道方案已预置 N-Genius / Tap / PayTabs（AE · AED），**尚未实现**，首个 AE 适配器由 ShareHub 需求驱动落地；
- 币种：pay 已有按通道取币种的机制（默认 CNY 兜底），AED 走同一机制。

**ShareHub 不用的**：积分（`pts_*`）、电商商户分账 / 补贴、商户结算单 —— 这些是电商模型。
ShareHub 的分润与结算规则（场地 / 代理分成）**仍在 ShareHub finance**，只把「打款」交给 pay。

**与 ADR-005 / nearpay 的关系**：「委托 nearpay API」被本决策取代。neargo 规划中的 nearpay（聚合支付平台）
若将来落地，作为共享 pay 模块的**一个通道适配器**接入，业务侧零改动。

**修正 ADR-017 对 core 的一条论证**：ADR-017 说「借出要在一个事务里同时动订单 + 占用 + 支付预授权」。
实际上**预授权从来不在本地事务里** —— 它是对 PSP 的外部调用，可能走 3DS、可能异步回调。
订单状态机本来就必须处理「授权中」与「弹仓失败 → 撤销预授权」的补偿。
支付改为跨进程后，**新增的只是一跳内网 HTTP，补偿路径本已存在**。
订单 + 占用 + 券核销仍在 core 一个事务里，这部分论证不变。

### 三、协议对接服务：逻辑上一个服务，物理上三种形态

对业务单体只暴露三样契约：`DeviceCommandPort`（下指令）· `DeviceEvent`（收事件）· `TelemetryQueryPort`（查在线态）。
在此之下服务内部可以按需演进，**业务侧看不到差别**：

| 形态 | 驱动怎么装 | 何时用 |
|---|---|---|
| ① 单进程（默认） | 驱动 = Maven 子模块，编进 jar | 现在 |
| ② 插件化 | 驱动 jar 放 `plugins/`，独立类加载，manifest 注册 | 厂商多到「每接一家就要发一次版」成为负担 |
| ③ 多进程 | 按**传输**拆（如 OCPP / TCP 长连接节点），共用内核库、`sharehub_gw` 与 `/internal/gw` 契约 | 长连接数或某厂商故障开始拖累其他厂商 |

**按传输拆，不按厂商拆**（ADR-003 已否决按厂商拆服务）。

### 四、认证：neargo 底座 + ai-shop 会话方案，嵌入式，不独立部署

两者**分工明确、不重叠**：

| 能力 | 来源 | ShareHub 现状 |
|---|---|---|
| RBAC 权限码 `@perm.can()`、通配匹配、`PermissionResolver` SPI | **neargo** `neargo-common-security`（rbac 包） | ✅ 已接（U1 上推） |
| 数据权限引擎 `DataScopeHandler` + 注册表 | **neargo** `neargo-common-data`（scope 包） | ✅ 已接（U2 上推） |
| 租户上下文、受信头、跨服务透传 | **neargo** `neargo-common-security` | 部分使用 |
| OTP、凭据、密码 | **neargo** `neargo-auth-core` | ShareHub 自有 `OtpService`，待对齐 |
| 会话：Realm 前缀路由、不透明令牌、哈希存储、软撤销、`SessionProfile` 按池装配、堆内缓存 + 撤销轮询 | **ai-shop** 方案（`shop-auth-store` + `shop-base-auth`） | ShareHub 有 `TokenStore` SPI 四实现，**缺**前缀路由 / 哈希 / 分池 |
| 登录策略按 `grantType` 分发 | 两边同构 | ✅ ShareHub 已有 5 个（比 ai-shop 多 Google） |

**`shop-auth-store` 建议与 pay 同样下沉共享**：它本来就与产品无关
（包名 `ai.neargo.auth.store`，只依赖 spring-jdbc + ehcache，刻意不引 shop-base / MyBatis）。
下沉为 neargo 的 `neargo-auth-store` 后两项目用同一份会话持久层；Realm 集合与过滤器链各自定义
（ai-shop：CONSUMER / MERCHANT / OPERATOR；ShareHub：CONSUMER / STAFF / AGENT）。

**令牌约定**（照 ai-shop）：每个 Realm 一个前缀（`ctk_` 消费者 / `stk_` 员工 / `atk_` 代理），前缀不符直接 401、不查库；
不透明令牌，库里只存 SHA-256，软撤销；权限**不存进会话**，每次请求现算；改权限后以库内版本号 + 撤销轮询通知各实例，**多实例 5 秒内生效**（取代今天只在单进程内有效的 `PermVersion`）。

**不独立部署的理由**：只有 `sharehub-app` 接受终端用户令牌，pay-svc 与 gateway 只接受服务凭证。
认证独立成进程只会让每个请求多一跳；ai-shop 也是嵌入式。**信号**：出现第二个产品要共用账号（SSO）时，
同一套代码加一个内省端点单独部署即可。

**服务间凭证分两类**（与[设计v3-工程骨架](../设计v3-工程骨架.md)「传 token 不传身份声明」不冲突）：

| 调用 | 凭证 | 理由 |
|---|---|---|
| 业务服务 ↔ 业务服务（将来拆分后） | 透传用户 Bearer（v3 已定，不变） | 对端要做权限 / 数据范围判定 |
| 业务单体 → pay-svc / gateway | **服务凭证 `X-Internal-Token`**（每个调用方一把，可轮换；同 ai-shop `InternalClient`） | pay / gateway 不做用户级鉴权；后台任务本就没有用户令牌 |

### 五、会话存储：库为权威 + 堆内缓存，Redis 可选

修订 ADR-019 决策一中的「生产配 `token-store: redis`」，**分类结论不变**（会话表是基础设施）：

- 权威存储 = `sharehub_auth` 的会话表（每个 Realm 一张），缓存 = 堆内，**缓存时长与踢人延迟分开调**（同 ai-shop `SessionProfile`）；
- ai-shop 线上就是这个形态（生产无 Redis），少一个必须高可用的中间件；
- `RedisTokenStore` 保留，副本数或 QPS 上来后可切，业务零改动。

**当前风险**：线上 `token-store: memory`，多副本会互相不认令牌。`sharehub-app` 扩到 2 个副本前**必须**先切到库实现。

### 六、定时任务：共享 ai-shop 任务服务，ShareHub 部署自己的调度器

**不自建。** ShareHub 后端今天没有任何定时调度（实测无 `@Scheduled` / Quartz / XXL），而 ai-shop 的任务服务
（`shop-job-api` / `-store` / `-core` + 独立进程 `shop-job`）本来就与业务无关：包名已是 `ai.neargo.job.*`，api 零依赖，有测试守着「不引任何业务模块」。

- **代码共享**：任务服务留在 ai-shop（[ADR-024](./ADR-024-共用服务暂由ai-shop托管-组件并入框架.md)），由 ai-shop 把散在 `shop-base` / `shop-app` 的目标侧小类收成 `shop-job-target` 并发布；
- **实例各自**：ShareHub 部署 `sharehub-job` + `sharehub_job` 库（时区、区域不同；ai-shop 调度器的 `job_name` 全局唯一、只有一把令牌，共用需先补缺口）；
- **一个调度器、三个目标**：`SHAREHUB`（sharehub-app）· `GATEWAY` · `PAY` —— 用上 ai-shop 已设计的多目标机制；
- **业务只写 `JobHandler` + `JobDeclaration`**，执行锁用 ShedLock（锁名 = 任务名），**禁止 `@Scheduled`**（卡口）；
- 任务目录、接线与 ai-shop 踩过的坑见 [v4/07](../v4/07-定时任务.md)。

## 否决的方案

| 方案 | 否决理由 |
|---|---|
| ShareHub 自建支付服务（本 ADR 初稿） | 用户要求 9：不重做；通道对接与对账重复建设 |
| ShareHub 直接依赖 ai-shop 现有构件（`ai.neargo.shop:pay-*`） | 会把 `shop-base`（含电商 SPI）整个带进 ShareHub；ShareHub 的发布被 ai-shop 内核版本绑住。**可作为抽离完成前的过渡**，不作目标 |
| 两项目共用**一个调度器实例** | ai-shop 调度器 `job_name` 全局唯一、单令牌、运营端不分目标；时区与区域也不同 |
| 两项目共用**一个 pay-svc 实例** | 主体 / 商户号 / 市场 / 数据驻留都不同；需给全部表与 API 加应用维度。出现「同一主体、同一区域」的第三个项目时再议 |
| 支付留在 core（维持 ADR-017） | 违反用户要求 1；「金额不能改写」的边界在同一个库里立不住 |
| 认证独立部署 | 只有一个进程接受终端用户令牌，独立出去只多一跳 |
| 协议对接按厂商拆多个服务 | 每接一家多一个进程；ADR-003 已否决 |
| 服务间事件直接上 Kafka | 只有 4 个进程、事件量小；Outbox + 内网 HTTP 推送够用，`DomainEventBus` 接口不变，量上来再换 |

## 后果

**正面**：支付不重复建设，ai-shop 已踩过的坑（回调回查、幂等、对账轴、独立数据源）直接继承；
ShareHub 补的预授权与 AE 通道反过来让 ai-shop 的多区域路线受益。设备接入被隔进独立进程；业务单体保持方法调用 + 本地事务。

**代价**：
- **跨仓协作**：抽离与去耦要改 ai-shop 仓库，需与 ai-shop 的并行会话协调；共享模块的任何改动须两项目契约测试都过；
- 借出链路多两跳内网调用（app → pay-svc、app → gateway），**必须有跨进程链路追踪**；
- 支付跨进程后，「弹仓失败 → 撤销预授权」靠事件 + 对账兜底，不能再指望本地回滚。
