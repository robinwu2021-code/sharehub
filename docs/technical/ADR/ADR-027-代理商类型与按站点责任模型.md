# ADR-027 代理商类型与按站点责任模型 —— 一个代理商在不同站点可以承担不同责任

状态：**已接受**（2026-09-23 用户定：「代理商需要，可以增加一个城市合伙人，其他的都按照系统配置进行」）
· 修订 [ADR-012](./ADR-012-代理商模型.md)：保留「体内伙伴、用运营商品牌、统一分润」三条，**放宽「一个站点一个代理商一种角色」**
· 依赖 [ADR-026](./ADR-026-取消租户概念-唯一运营方.md)（唯一运营方）· [ADR-004](./ADR-004-分账双模式.md)（LEDGER 首期）
· 参照 ai-shop 的 `mch_store_role` 多行授权与「资金三维度分开」两条判据

## 背景

用户 2026-09-23：**场地往往是代理商搞定的**——包含商务谈判，甚至整个效果管理过程都由代理商负责；
**也有代理商只负责协调关系**。问：准确的名字是「合伙人」还是别的？要更细化的方案。

现状实测，模型把「代理商」当成一种固定角色，四处写死：

| 假设 | 落点 | 与现实的差距 |
|---|---|---|
| 一个站点只有一个代理商、一种角色 | `loc_site.agent_no` 单列 | 同一站点可能是 A 出资、B 牵线 |
| 代理商分成是一个比例，不问为什么分 | `share_rule(AGENT, agent_no).rate` · `agt_commission.rate` | 出资、拓展、运维、牵线的钱是四回事 |
| 找场地是运营商员工的事 | `loc_lead.owner` **只接受 `employee_no`** | 代理商找来的场地无法归因 |
| 谁出资 = 谁经营 | `dev_cabinet.agent_no`「随站点」 | 运营商出设备、伙伴只运维的模式表达不了 |

分润生成（`ShareGeneratorImpl`）对 AGENT 只做一件事：按订单快照的 `agentNo` 查一条规则、写一条记录。
**责任不同却拿同一个比例**，或者**两个伙伴各有责任却只能记一个**——这是结构问题，不是配置问题。

## 决策

### 一、命名：保留「代理商」，加一个「城市合伙人」，其余不造名字

用户 2026-09-23 定案。**不做「代理商 → 合作伙伴」的全局改名**——原提案里那一整轮文案与前缀迁移取消。

| 登记类型 `agent_type` | 名字 | 典型责任 | 谁建 |
|---|---|---|---|
| `PLATFORM` | **平台自营** | 运营商自己经营的站点（[ADR-029](./ADR-029-运营主体抽象.md) 扩充，恒一行、不可停用） | — |
| `AGENT`（默认） | **代理商** | 出资 + 运维，按约定分润 | 运营商 |
| `CITY_PARTNER` | **城市合伙人** | 出资 + 拓展 + 运维 + 效果管理，包一片区域全责 | 运营商 |

**只有这两个名字。** 其余差异——只运维不出资、只牵线不谈判、只出资不管事——**一律不新造名词，由系统配置表达**：
建档时选类型带出默认责任，再按站点调整责任行（§二、§三）。

这条决定的三个后果：

1. `agt_` 表前缀、`agent_no` 业务键、`agent:*` 权限码、`/api/agent/**` 路径**全部不动**，原 §分级第 3 步的 `agt_ → ptn_` 改名取消；
2. 运营端菜单「代理商管理」保留原名，只在档案里多一个「类型」字段；
3. 「城市合伙人」不是第二个实体，是 `agt_agent` 上的一个枚举值 —— 分润、结算、提现、门户全部复用同一套（Payee 泛化不变）。

> **为什么不把「渠道介绍人」也做成类型**：它与代理商的差别不在主体属性，而在**某个站点上做了什么**。
> 做成类型就会出现「这个人在 A 站是介绍人、在 B 站是代理商」无处安放的矛盾；做成责任配置则天然成立。

### 二、责任是原子的，合作模式只是预设

五项**原子责任**，一个伙伴在一个站点上承担其中若干项：

| 责任 | 代码 | 做什么 | 拿什么钱 |
|---|---|---|---|
| 出资 | `INVEST` | 买设备 | 资产收益（按 GMV 比例，持续） |
| 拓展 | `DEVELOP` | 找场地、商务谈判、签进场合同 | 拓展佣金（持续小比例，或签约一次性） |
| 运维 | `OPERATE` | 装机、补货、维修、接工单 | 运维分成（按 GMV 比例，持续） |
| 效果管理 | `MANAGE` | 持续经营优化：点位调整、坪效、活动 | 经营分成（可与 OPERATE 合并计酬，见待确认 #3） |
| 牵线 | `REFER` | 只介绍关系，不谈判 | 介绍费（一次性，或持续极小比例） |

约束：`REFER` 与 `DEVELOP` **互斥**（牵线是拓展的弱形式，一个站点上同一人只能算其一）。

**登记类型 = 责任集合 + 默认费率的预设**，存为数据（`md_agent_type`，两行：`AGENT` / `CITY_PARTNER`），
运营建档时选一个，系统展开成责任行；之后可逐站点改。
日常操作只需「这是个城市合伙人」一步，同时又保留「他在那个站点只是牵线」的精确性 —— **后者不需要一个新名字**。

### 三、责任挂在「伙伴 × 站点」上，不挂在伙伴上

新增关系表：

```
loc_site_agent                 -- 命名跟随既有 agt_ / agent_no 体系（§一：不改名）
  site_no        站点
  agent_no       代理商 / 城市合伙人
  role           INVEST / DEVELOP / OPERATE / MANAGE / REFER
  rule_no        该责任对应的分润规则（可空 = 用登记类型的默认费率）
  effective_from / effective_to
  uk (site_no, agent_no, role)
```

**一行一责任**，不用 JSON 数组列——ai-shop 的教训：撤销单个角色变成读-改-写，两人同时改会互相覆盖，
而覆盖的后果是**有人多拿了权限或多分了钱，且不报错**；多行方案里撤销就是删一行。

`loc_site.agent_no` **保留**，语义收窄为**主经营方** = 承担 `OPERATE` 的那个伙伴。它仍是数据范围与工单派单的锚点，
不需要改任何现有查询。只有 `REFER` 的站点，`agent_no` 为空（= 直营运维）。

### 四、钱：分润规则加「依据」，一笔订单可给同一伙伴多条记录

| 表 | 改动 |
|---|---|
| `share_rule` | 加 `basis`（INVEST / DEVELOP / OPERATE / MANAGE / REFER）；`(dimension=AGENT, payee_no, basis)` 唯一 |
| `share_record` | 加 `basis`；唯一键 `uk_srec_order_payee` → `(order_no, payee_no, basis)` |
| `ShareGeneratorImpl` | AGENT 分支从「查一条」改为：读该站点的 `loc_site_agent` 行 → 每行按 `basis` 查规则 → 每行写一条记录 |
| 结算 / 提现 / 账务 | **不动**。`Payee` 泛化（领域模型 §3.3）成立：`basis` 是记录上的一列，汇总时按受益方合并 |

一次性介绍费（`REFER`）不走逐单分润，走**事件触发**：`ContractSigned` 或首单结算时生成一条 `share_record(basis=REFER, order_no=合同号)`。
触发点见待确认 #2。

**资金三维度**（ai-shop 判据）在本模型里：`site_no` 说这笔钱哪个站点挣的（统计）· `payee_no + basis` 说给谁、凭什么（合规）· 收款账户说打到哪（结算）。

### 五、拓展归因：商机能记到伙伴头上

`loc_lead.owner`（只接受 `employee_no`）→ `owner_type (STAFF | AGENT) + owner_no`。
商机 `SIGNED` 且 owner 是代理商时，自动写一行 `loc_site_agent(role=DEVELOP)`；
若这单只是牵线（运营方自己谈的合同），建档时改成 `REFER`。拓展佣金的依据就是这一行，不靠人记。

### 六、责任决定看到什么、能做什么

| 责任 | 数据范围 | 门户里多出什么 |
|---|---|---|
| `OPERATE` / `MANAGE` | 该站点进入自己的范围（设备 / 订单 / 工单 / 收益） | 现有门户 7 叶 |
| `DEVELOP` | 自己的商机与合同可见 | 🆕「我的商机」（BD CRM 的伙伴视图） |
| `INVEST` | 该站点的设备与收益可见，工单只读 | — |
| `REFER` | **只见自己的介绍费记录**，站点本身不可见 | 「我的收益」里的一类 |

数据范围仍以 `loc_site.agent_no`（主经营方）为锚：`OPERATE` 就是主经营方；其他责任的可见性由 `loc_site_agent` 派生，
这需要 `DataScopeRegistration` 增加一条按关系表解析的维度——**先补覆盖测试再加**（ai-shop 的两条性质）。

## 分级与落地顺序

| 步 | 内容 | 级 | 为什么 |
|---|---|:-:|---|
| **1** | `agt_agent` 加 `agent_type`（`AGENT` / `CITY_PARTNER`）；`md_agent_type` 登记两种类型与默认责任、默认费率；档案页加「类型」字段 | **L0** | 只加一列 + 一张字典表，**无改名、无文案迁移** |
| **2** | `loc_site_agent` 责任表 + `share_rule/share_record.basis` + `ShareGenerator` 按责任行生成 + `loc_lead.owner_type` | **L1** | 「同一伙伴在不同站点责任不同」「一个站点两个伙伴」在开站一个月内就会出现（介绍人先于城市合伙人出现是常态） |
| **3** | 门户「我的商机」；数据范围按关系表派生 | L1 | `agt_` → `ptn_` 改名**已取消**（§一） |

第 1 步不改任何表结构以外的逻辑；第 2 步是真改动，但**结算 / 提现 / 账务三块不动**——这是 Payee 泛化的红利。

## 否决的方案

| 方案 | 否决理由 |
|---|---|
| 只在 `agt_agent` 加一个「类型」枚举**就算完** | 类型解决「他大体是哪种人」，解决不了「他在这个站点做了什么」。两者都要：类型定默认，责任行定实际 |
| 全局改名「代理商 → 合作伙伴」 | 2026-09-23 否决：收益是措辞更准，代价是表前缀 / 业务键 / 权限码 / 路径 / 文案全量迁移。**不值得** |
| 每种合作模式一张表 / 一个实体（合伙人表、介绍人表） | 责任是可组合的，实体化会出现「既出资又只牵线」的矛盾对象；Payee 泛化也会碎掉 |
| 责任存 JSON 数组列 | 见 §三，并发撤销静默覆盖 |
| 保持一个代理商一个比例，靠人工调比例体现责任差异 | 比例背后的依据不可追溯，结算争议时说不清「这 8% 里几个点是运维几个点是出资」 |

## 后果

- 正面：一个站点上「谁出钱、谁找的、谁在维护、谁牵的线」四件事各有其位，各拿各的钱，结算单能逐项说清；伙伴模式变了不返工
- 代价：`ShareGenerator` 一次改写（含幂等键变更 → 需迁移已有 `share_record` 补 `basis=OPERATE`）；数据范围多一条维度。**无改名代价**（§一）
- 不变：结算 / 提现 / 账务 / 门户主体结构 / `loc_site.agent_no` 的锚点作用

## 待确认

1. ~~命名~~ **已定（2026-09-23）**：保留「代理商」，加「城市合伙人」，其余由系统配置表达；不做全局改名。
2. **介绍费怎么触发**：签合同一次性、首单结算一次性、还是持续极小比例？（决定 `REFER` 走事件还是走逐单）
3. **效果管理 `MANAGE` 与运维 `OPERATE` 是否分开计酬**：分开更精确，但首批伙伴多半两件都做，合并叫「经营」更省事
4. **一个站点多代理商**是否 L1 就要（「A 出资、B 运维」或「A 牵线、B 经营」的场景是否近期会出现）
5. ~~`agt_` → `ptn_` 改名~~ **已取消**（§一）
