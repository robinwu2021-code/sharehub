# ADR-028 收费方案的适用范围与取价优先级 —— 一笔订单到底按哪个方案收钱

状态：**提议 · 待确认**（2026-09-23，依据用户同日描述起草）
· 落实 [运营管理-功能清单 OM-S3 决策 D3](../../requirements/features/运营管理-功能清单.md)：只保留「适用范围」一种机制
· 依赖 [ADR-021](./ADR-021-通用设备命名与使用形态.md)（设备类型登记）· [ADR-027](./ADR-027-代理商类型与按站点责任模型.md)（伙伴与站点的关系）
· 与 [领域模型 §2.5](../领域模型-本体与关系.md) 互为表里

## 背景

用户 2026-09-23：一个站点多台设备；不同站点、**不同品牌的设备**、不同收费方案；大商场、机场里甚至**不同代理商、不同站点、不同收费方案**。

这本质是一个**取价问题**：订单落在一台设备上，系统要从所有可能适用的方案里**选出恰好一个**。
今天的取价键只有 `(deviceType, siteNo, sceneType)`，用户点名的维度一个都不在里面。实测还有三处缺陷：

| # | 缺陷 | 证据 | 后果 |
|---|---|---|---|
| 1 | **站点规则不看设备类型** | `PriceResolver.matchPlanNo` ① 层只比 `site_no`；`price_rule` 没有 `device_type` 列 | 站点同时有充电宝和按摩椅时，站点规则会拿充电宝方案给按摩椅计价。今天只有一种设备所以没炸，**L2 按摩椅前必爆** |
| 2 | **「适用范围」写了没人读** | `price_plan_scope` 由 `PricePlanServiceImpl` 读写供界面展示；`PriceResolver` 只读 `price_rule` | 运营在方案上勾了「适用站点」，取价引擎不认；真正生效的是另一个菜单「差异化定价」。两套机制表达同一件事（OM-S3 D3 已指出） |
| 3 | **时段倍率配置了不生效** | `ChargeChain.charge(gross, multiplier, …)` 接受倍率，但**没有任何调用方从 `price_schedule` 算出倍率传进来**；`PricingScheduleService` 未注入订单流程 | 「活动 / 时段价」菜单能存能改，订单一分钱都不多收。又一个「有能力没消费方」 |

另有一个结构性空缺：`md_region` 没有市场 / 国家列，`loc_site.region_id → md_region` 推不出币种。
方案带 `currency`，站点却没有可推导的币种，多市场时无法做「币种必须相符」的硬过滤。

## 决策

### 一、只有一种机制：`price_plan_scope`；`price_rule` 退役

把「差异化定价」（`price_rule`：站点 / 场景 → 方案）并入「适用范围」（`price_plan_scope`），
取价引擎改读后者，前者迁移后删除。OM-S3 的 D3 已经这么定了，本 ADR 只是把它落到取价引擎上。

`price_plan_scope` 扩展为：

```
price_plan_scope
  plan_no
  device_type     必填 —— 修缺陷 1
  level           DEVICE / LOCATION / SITE / VENUE / AGENT / SCENE / REGION / ALL
  ref             对应层的业务号；ALL 为 '*'
  vendor_code     可空 —— 设备品牌（厂商）过滤
  model           可空 —— 设备型号过滤
  brand_no        可空 —— 消费者品牌过滤（随 ADR-026 §五 品牌落地）
  priority        同一层同一范围的并列裁决
  effective_from / effective_to
  uk (device_type, level, ref, vendor_code, model, brand_no)   —— 同一范围只能有一个启用中的方案
```

### 二、取价优先级：越具体越优先，层内按过滤条件数，再按 priority

| 序 | 层 `level` | 引用 | 典型用途 |
|:-:|---|---|---|
| 1 | `DEVICE` | `device_no` | 单台特价（一台快充柜比同站其它柜贵） |
| 2 | `LOCATION` | `location_no` | **大商场 / 机场分区**：贵宾厅一个价、美食广场一个价，不必为此拆站点 |
| 3 | `SITE` | `site_no` | 站点专属（今天的「站点专属规则」） |
| 4 | `VENUE` | `venue_no` | **场地方统一价**：机场要求旗下所有站点同价，通常写在进场合同里 |
| 5 | `AGENT` | `agent_no` | **伙伴级价**：一个合作伙伴名下所有站点一个价 |
| 6 | `SCENE` | `scene_type` | 按场景（商场 / 医院 / 机场）—— 今天的 ② 层 |
| 7 | `REGION` | `region_id` | 按区域（城市级定价） |
| 8 | `ALL` | `*` | 该设备类型的默认方案 —— 今天的 ③ 层 |

**裁决顺序**：① 只看 `device_type` 相符且币种相符的行（硬过滤）→ ② 取命中层序最小的 → ③ 同层内，`vendor_code` / `model` / `brand_no` 命中数多的优先 → ④ 仍并列按 `priority` 降序 → ⑤ 仍并列取最新。
**一个都没命中 → 抛异常**，沿用现有「绝不静默免单」纪律。

为什么 `VENUE` 在 `AGENT` 之上：场地方的价格约束来自**合同**，是对外承诺；伙伴定价是内部安排。机场说「全场 5 块」时，伙伴不能在机场里自己定 8 块。
为什么 `LOCATION` 在 `SITE` 之上但 `DEVICE` 又在最上：粒度越细越是有意为之的例外，例外优先于常规。

### 三、设备品牌 / 型号 / 消费者品牌 是过滤条件，不是层

「不同品牌的设备」不构成一个层——它与场所层级正交（快充柜可能出现在任何站点）。
建模为**范围行上的可选过滤**：「本站点 × 厂商 X」比「本站点」更具体，同层内胜出。
不给它单独一层，是避免出现「站点级方案 vs 厂商级方案谁赢」这种没有业务答案的排序问题。

### 四、叠加层在方案之后，不参与选方案

| 叠加 | 落点 | 在哪一步 | 现状 |
|---|---|---|---|
| 时段 / 节假日倍率 | `price_schedule` | 方案选定后、封顶之前（`ChargeChain` 位置 ③） | **修缺陷 3**：由取价流程按订单**开始时刻**算出倍率传入，并写进快照 |
| 预约调价 | `price_adjustment` | 到时改方案字段，随快照进新订单 | 已实现（V40） |
| 会员权益 / 优惠券 | 计价引擎 | 毛额之后 | 已实现 |

时段倍率按**开始时刻**取值并快照，不按每一分钟分段——分段计价的争议成本远高于它带来的精度。SESSION 型套餐同理。

### 五、命中原因进快照

`ord_order.price_snapshot` 增加 `hit: {level, ref, filters, planNo, multiplier}`。
OM-S3 试算器要显示「命中的方案和命中原因」，结算争议时也要能回答「为什么这单按这个价」——都从快照读，不回头重算。

### 六、谁能定价（治理）

| 层 | 谁建 | 说明 |
|---|---|---|
| `ALL` / `REGION` / `SCENE` / `VENUE` | 运营商 | `VENUE` 级建议由进场合同带出（合同里的价格约束 → 自动生成范围行） |
| `AGENT` / `SITE` / `LOCATION` / `DEVICE` | 运营商 | 首期全部由运营商建 |
| 伙伴自助定价 | 合作伙伴（承担 `MANAGE` 责任者，ADR-027） | **L2**：在运营商设定的每种设备类型上下限内，为自己名下站点建 `AGENT` / `SITE` 级行 |

### 七、币种硬过滤需要补链

`md_region` 加 `market_code` → `md_market_country`（币种 / 时区）。取价时 `plan.currency` 必须等于站点所在市场币种，否则该行不进候选。
单市场（AED）时恒真；这是为第二个国家预留的，**不是 L0**。

## 分级与落地顺序

| 步 | 内容 | 级 | 为什么 |
|---|---|:-:|---|
| **1** | `price_plan_scope` 加 `device_type` / `level` / `priority` / 生效期；`price_rule` 数据迁入（SITE / SCENE 行）；`PriceResolver` 改读 scope 并按 §二 裁决；命中原因入快照；**时段倍率接入订单流程** | **L1** | 修三处缺陷；`VENUE` 与 `AGENT` 级在第一批站点就会遇到（机场统一价、伙伴要自己的价） |
| 2 | 退役 `price_rule` / `PricingDiffService` / ops-web 「差异化定价」tab（并入 OM-S3 ④ 适用范围） | L1 | 随第 1 步 |
| 3 | `LOCATION` / `DEVICE` 级；`vendor_code` / `model` / `brand_no` 过滤 | L2 | 大商场分区、设备品牌差价，规模化后出现 |
| 4 | `md_region.market_code` + 币种硬过滤；伙伴自助定价与上下限 | L2 / L3 | 多市场；伙伴自治 |

**L0 不动**：今天只有一种设备、一个市场、方案按站点或场景区分，现有四层取价够用。
但第 1 步必须在 **L2 按摩椅之前**完成，否则缺陷 1 会把按摩椅按充电宝价收。

## 否决的方案

| 方案 | 否决理由 |
|---|---|
| 给伙伴 / 场地方 / 厂商各加一张「专属方案表」 | 取价要跨 N 张表比优先级，规则散在代码里；一张范围表 + 一个层序枚举把优先级变成数据 |
| 设备品牌单独一层 | 与场所层级正交，「站点级 vs 厂商级谁赢」没有业务答案（见 §三） |
| 方案挂「所属运营商 / 伙伴」隔离（简电云做法） | 那是多运营商的隔离手段；我方唯一运营商（ADR-026），伙伴级差价只是一个范围层，不是隔离边界 |
| 时段倍率按分钟分段计价 | 精度收益小，争议成本大；开始时刻快照可解释可复算 |
| 拆站点来表达商场分区 | 站点是归属与分成单元（ADR-013），为定价拆站点会连带拆合同与分润 |

## 后果

- 正面：所有「哪个方案适用」的问题都变成一张表里的一行；优先级是数据不是代码；试算与结算同源；三处「配置了不生效」的缺陷一并消除
- 代价：`PriceResolver` 一次重写（两个调用方：下单快照 `RentOrderServiceImpl`、C 端价格展示 `MpNearbyController`）；一次数据迁移；一个 ops-web tab 并入另一页
- 不变：`price_plan` / `price_plan_item` / `price_ladder` 结构；订单快照纪律；「不静默免单」

## 待确认

1. 层序中 **`VENUE` 高于 `AGENT`** 是否符合商务现实（机场统一价压过伙伴自定价）
2. 时段倍率按**订单开始时刻**取值是否可接受（跨时段的长单不分段）
3. `VENUE` 级方案是否由**进场合同**自动带出（合同加「价格约束」字段），还是运营手工建
4. 伙伴自助定价放 L2 还是 L3；上下限按设备类型设还是按市场设
5. `LOCATION` 级是否 L2 就要（首批是否有机场 / 大商场需要分区定价）
