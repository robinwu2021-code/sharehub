## 2. 决定顺序的三条原则

**① 依赖向下、整理向上。** 五层的依赖是
`实体 → mapper → service → (api/Port) → controller`。
从下往上整理，每层动的时候上层还没重写，返工最少。**反过来会返工两遍**：
先统一 DTO 再改实体名，DTO 全部作废。

**② 与领域模型对账在最前，因为它决定"有没有这个对象"。**
对不上的有三种：实体多了（表已废）、实体少了（`md_brand` 等九个待建对象）、
名字与本体不一致。这三种若不先裁定，后面每一层都会照着错的对象建一遍。

**③ 未拍板的 ADR 圈出来，不要先整理。**
ADR-027（伙伴 × 站点责任）与 ADR-028（取价优先级 + `price_rule` 退役）
会**增删对象**。在它们确认前整理 `agent` / `price` / `share` 三个域，等于给将要作废的结构写代码。

## 3. 整理顺序（七步）

### L0 · 对账：实体 ↔ 领域模型（**先做，且只做对账不改代码**）

产出一张 `docs/technical/实体-领域对象对账表.md`：140 个实体 × 领域模型对象清单，逐条标
`一致` / `实体多余` / `对象待建` / `命名不一致`。

**为什么单独成步**：这一步的产出是**决策输入**，不是代码。裁定完才知道后面六步的工作量。
边对账边改会让"发现差异"和"决定怎么改"混在一起，最后谁也说不清某个类为什么改成了那样。

**判据**：对账表覆盖 140 个实体与领域模型全部对象，每条有裁定；差异条目关联到负责的 ADR。

**✅ 已完成（2026-09-23）**：[实体-领域对象对账表](./实体-领域对象对账表.md)。
结论两条：**① 实体层吻合度 89%（136/152 三方一致），L1 工作量小于预估**；
**② 真正的欠账在状态词表 —— DDL 里 55 个词表、模型写明 12 个、Java 业务状态 enum 0 个**。
交出三条待裁定（`dev_alert` v1 死表未退役 · 两张零引用表 · `agt_assignment` 未登记）。

### L1.5 · 词表收敛：状态 / 类型的字面量收进 enum（**L0 新增的一步**）

L0 对账发现：业务状态**没有任何单一真源** —— DDL 注释里 **55 个**不同词表，
领域模型为 **12 个**对象写明词表，而 Java 里业务状态 enum 是 **0**。
`"ACTIVE"` 散落 49 处 / 30 个文件，`"ENABLED"` 22 处，全是裸串。

**这一步不是整洁度问题，它已经造成了一个无症状缺陷**：
`AlarmServiceImpl` 自动开工单时查 `status IN ('OPEN','ACK')`，但 `ACK` 是事件名、
落库状态是 `ACKED` —— 已受理的告警**永远开不出工单**，不报错、不留日志。
详见[对账表 §3.2](./实体-领域对象对账表.md)。

| 做什么 | 说明 |
|---|---|
| 每个对象一个 `enum`，**值仍以 String 落库** | 不动 MyBatis 类型处理器，实体字段暂保持 `String`；只收敛**字面量来源** |
| 以领域模型的「状态 / 生命周期」列为准，与 DDL 注释逐条对齐 | 打架的（`OPEN/ACK/RESOLVED` vs `OPEN/ACKED/CLOSED` vs `OPEN/HANDLED`…）在这一步裁定，不留到状态机 |
| 拼写分叉一并处理 | 已知 `ACK`/`ACKED`、`CANCELLED`/`CANCELED` |
| 加卡口：扫描 service 层裸状态字面量，台账化、只减不增 | 同三本 `known-*.txt` 的做法 —— **没有卡口，收敛完下个月又会长出来** |

**为什么排在这里**：状态词表是 **L3 状态机的输入**。拿裸字符串写完状态机再回头收敛，
等于把状态机写两遍（原则①）。排在 L1 之后是因为改名裁定会影响个别 enum 的归属域。

**判据**：12 个对象各有 enum；裸状态字面量台账建立且基线记录在案；
`AlarmServiceImpl` 那条缺陷随本步修掉并补一条会红的测试。

#### ✅ 卡口已建（2026-09-23）

`known-bare-status-literals.txt` + `BareStatusLiteralRatchetTest`，**实测基线 122 条 / 62 个类 / 60 个取值**
（此前"49 处 ACTIVE"只是按值计数，这才是按用法锚定的真实工作量）：

| 域 | 条 | | 域 | 条 |
|---|---:|---|---|---:|
| platform | 23 | | cs | 7 |
| trade | 19 | | loc | 6 |
| user | 19 | | wo | 5 |
| dev | 13 | | agent | 4 |
| finance | 9 | | common · alarm | 3 · 3 |
| seed | 8 | | operation · gw | 2 · 1 |

**锚在用法上，不扫所有大写字符串**：`^[A-Z_]+$` 会把权限码、表名、事件名全扫进来。
只认状态值真正流过的五个口子（`setXxx("L")` · `"L".equals(getXxx())` ·
`getXxx().equals("L")` · `.eq(X::getXxx,"L")` · `.in(X::getXxx,…)`），
字段名以 Status / Type / Level / Action / Mode 结尾。实测**注释误报 0 条**。

> 说服力在于：告警那个缺陷正是 `.in(DevAlarm::getStatus, List.of("OPEN","ACK"))`
> —— 这条卡口若早存在，它在写下的当天就会红。

**五类字段一次定全**：以后再往锚点加类别会让台账变长，而台账的全部意义是「只准变短」。
一个能被放宽的棘轮不是棘轮。

反向对照三条全部验过：新增一条裸字面量 → 红；把扫描路径改坏 → `isNotEmpty` 抓住
（而不是"0 违规"绿过，arch-guard 假绿过一次）；台账留陈旧条目 → 红。

**收敛顺序**：先做未被 ADR 圈住的域（`dev` 13 · `cs` 7 · `wo` 5 · `alarm` 3 · `gw` 1），
`agent` / `price` / `share` / `loc` 等 ADR-027/028/029 拍板。

### L2 · Mapper 层：形态统一为**每域一个** `XxxMappers`

122 个 Mapper 里 114 个是单实体式。v4/09 定的是**每域一个聚合 Mapper**（照 ai-shop）。

**为什么在 service 之前**：service 注入的是 Mapper。先统一 Mapper，service 只改一次注入；
反过来 service 整理完再合并 Mapper，每个 service 要再动一次。

**判据**：每个业务域一个 `XxxMappers`；arch-guard G3 不新增豁免；棘轮台账不变长。

---

### L3 · Service 层：接口 + `Command` 内嵌，实现落 `service/impl/`

| 做什么 | 说明 |
|---|---|
| 接口与实现分离到 `service/` + `service/impl/`（现已基本成立，补齐例外） | |
| 入参统一为接口内嵌的 `Command`（v4/09 的 Req/Command/VO 三分） | 这一步**顺带完成 B3 未做的那一半**：39 个实体请求体改成 Command 后，`known-entity-request-bodies.txt` 才能真正清零 |
| 状态迁移收进 `StateTransitions` | 领域模型 §2.4 的不变式在这里落成代码。**状态值取自 L1.5 的 enum，不再写裸串** |

**判据**：`known-entity-request-bodies.txt` 显著变短；状态机测试覆盖领域模型列出的不变式。

---

### L4 · api 层：把 5 处跨域直连改成 Port

现在只有 6 个 Port，而 arch-guard 记录了 5 处"只读跨界"豁免 + 13 处 G3 豁免。
按领域模型 §四（依赖关系）逐条判定：**哪些是真正的跨域依赖**（建 Port），
**哪些只是报表式只读**（留在 app 层编排，已豁免）。

**为什么在 service 之后**：Port 的签名应当由 service 的 Command/VO 决定，
先定 Port 再回头改 service，Port 会被改两遍。

**判据**：`known-arch-exemptions.txt` 变短；svc 之间零直接注入。

---

### L5 · Controller 层：32 个下沉到各域 `api/{ops,mp,internal}`

这就是 **B5 包归位**。放最后的理由：它是**纯搬迁**，动的文件最多、冲突面最大，
而前四步会改变控制器调用的每一个签名 —— 先搬只会搬完再改一遍。

同时处理：`Req` 内嵌到控制器；`/internal/*` 的历史业务端点按 v4/04 §三改名到
`/api/platform/...`（B7 给服务凭证留的前缀白名单随之收紧）。

**判据**：`app/portal/` 清空（只剩跨域编排）；`known-fat-controllers` 下降；两个前端实机回归。

---

### L6 · 目录重排（B4）与命名通用化（B6）

`foundation/ contracts/ domains/ gateway/ apps/ support/`（v4/12 §4.2）+ ADR-021 的通用设备改名。
放最后是因为它们**跨所有模块移动文件**，与任何并行工作都冲突。

## 5. 三个风险

| 风险 | 对策 |
|---|---|
| **并行会话冲突**：另一会话仍在改实体与 seed | L1/L2 按域切分，每域一次提交；动手前 `git status -- <域路径>` 确认无在途改动 |
| 大步骤中途被打断，代码停在半迁移状态 | 每步**按域**收口，一个域整理完就绿一次；不做"全量改到一半" |
| 整理过程中卡口被绕过 | 每步结束跑 arch-guard `--strict` + enforcer + 全量测试；三本棘轮台账**只准变短** |
