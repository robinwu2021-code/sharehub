> 状态：**已实现并实测**（2026-07-12）· 本文与 `backend/powerbank-app` 代码**逐一对齐**，是运营端权限的落地权威。

> 三处 SSOT：**权限码**=[功能权限清单.md](../requirements/功能权限清单.md)；**角色→码**=后端 `auth/RolePerms.java` ⇔ 前端 `ops-web/lib/permissions.ts`（同源镜像）。
> 代码根：`backend/powerbank-app/src/main/java/ai/neargo/powerbank/`（下文类名均相对此）。

## 0. 范围与三层模型

**运营端 = 员工/运维/代理（realm ∈ {STAFF, AGENT}）**，走 `/api/**` 与 `/internal/**`。C 端（`/mp/**`, realm=CONSUMER）**分链、分过滤器、分上下文**，只共用基座（见 §1、§3）。

| 层 | 回答 | 机制（代码） |
|----|------|-------------|
| **认证** Authn | 你是谁 | `StaffTokenAuthFilter` + `SessionStore`（Bearer→LoginUser） |
| **功能授权** Authz | 能做什么操作 | `@PreAuthorize("@perm.can('码')")` → `PermChecker` → `StaffContext.hasPerm` |
| **数据授权** Data Scope | 能看/改哪些数据 | `DataScopeHandler`（MyBatis-Plus 拦截器）+ `DataScopeTableRegistry` |

> **业务/权限分离（架构红线）**：业务代码**只经 `SecurityUtils`/`StaffContext` 读身份**，绝不直接 `SecurityContextHolder`；功能权限只在 Controller 层 `@PreAuthorize`，Service 不判权限。

## 1. Spring Security 拓扑（`config/SecurityConfig`）

两条 `SecurityFilterChain` 按 `@Order` + `securityMatcher` 分链；运营端是**默认兜底链**：

```
@Order(1) consumerChain  securityMatcher("/mp/**")   → ConsumerTokenAuthFilter（C端，另文）
@Order(2) opsChain       （无 matcher，兜底）          → StaffTokenAuthFilter   ★运营端
```

opsChain 关键配置（`SecurityConfig.opsChain`）：
- `sessionCreationPolicy(STATELESS)`、`csrf.disable()`（Bearer 非 Cookie，无 CSRF 面）、`cors(...)`（dev 允许 ops-web 源）。
- `authorizeHttpRequests`：
  - `permitAll`：`OPTIONS /**`、`/api/auth/login`、`/api/auth/logout`、`/actuator/**`、`/notify/**`。
  - `anyRequest().authenticated()`：其余 `/api/**`、`/internal/**` 需认证。
- `addFilterBefore(new StaffTokenAuthFilter(store), UsernamePasswordAuthenticationFilter.class)`。
- `exceptionHandling`：`authenticationEntryPoint`→401、`accessDeniedHandler`→403，均写 `{"code","msg","data":null}` JSON（**不跳登录页**）。
- 类级 `@EnableMethodSecurity` 开启 `@PreAuthorize`。

> **MVP 与设计的差异（对齐说明）**：[TDD-认证鉴权.md](./TDD-认证鉴权.md) 描述了 5 链拓扑（internal/openapi/consumer/ops）与「拆分后 `RequestHeaderAuthenticationFilter` pre-auth」两形态。**当前落地是模块化单体的 2 链 MVP**：ops-web/C 端**直连 app-modulith 自认证**（`StaffTokenAuthFilter` 反查 token），`/internal`/`/gw`/`/openapi` 暂并入两链的 permitAll/authenticated，未拆独立链、未接 pre-auth 与 AppKey——列为后续（§10）。

## 2. 封装的 Filter：`auth/StaffTokenAuthFilter`

`OncePerRequestFilter`，每请求一次：

```
Authorization: Bearer <token>
  → SessionStore.get(token) : LoginUser
  → 若 u != null 且 u.realm() != CONSUMER：
        authorities = u.perms() 映射 SimpleGrantedAuthority
        principal   = u（LoginUser 本体，非 username 串）
        SecurityContext.setAuthentication(UsernamePasswordAuthenticationToken(u, null, authorities))
  → 无/无效/ C端 token：不设认证 → 后续 authenticated() 触发 entryPoint 401
```

**安全红线**：ops-web 是静态 SPA，其 `http-client.ts` 会自填 `X-Roles`/`X-User-Id`/`X-Merchant-Id`。**本过滤器只认 token 反查的 `LoginUser.perms()`，完全忽略客户端可信头**——`X-Roles` 仅前端自用回显，绝不参与后端鉴权。C 端会话（realm=CONSUMER）在此不放行（交给 consumerChain）。

## 3. 封装的 Utils（业务/权限分离的接缝）

### 3.1 主体模型 `auth/LoginUser`（运营端 + C 端共用 principal）
`record LoginUser(Realm realm, String userNo, String username, String role, List<String> perms, String tenantId, String agentNo, DataScope dataScope)`
- `hasPerm(code)`：通配判定，**与前端 `lib/permissions.ts` 的 `match()` 完全一致**——`p.equals(code) || (p.endsWith("*") && code.startsWith(p 去尾))`。支持 `*` / `device:*`（模块）/ `device:cabinet:*`（资源级）。

### 3.2 共享基座 `auth/SecurityUtils`（realm 无关，薄）
| 方法 | 返回 |
|------|------|
| `currentUser()` | `Optional<LoginUser>`（principal 是 LoginUser 才有） |
| `requireUser()` | `LoginUser`（无则 `AccessDeniedException`） |
| `userNo()/tenantId()/realm()` | 通用身份 |

### 3.3 运营端门面 `auth/StaffContext`（与 C 端 `ConsumerContext` 分离）
| 方法 | 用途 |
|------|------|
| `require()` | 当前 STAFF/AGENT 主体，非运营端→拒 |
| `hasPerm(code)` | 功能权限（委托 `LoginUser.hasPerm`） |
| `isAgent()` / `agentNo()` | 代理判定 / 代理号（数据范围硬过滤用） |
| `dataScope()` | 当前有效数据范围（供拦截器/业务） |

### 3.4 SpEL 校验器 `auth/PermChecker`（`@perm`）
`@Component("perm")`，`boolean can(String code)` → `StaffContext.hasPerm(code)`。**用法：`@PreAuthorize("@perm.can('order:refund:audit')")`**（见 §4）。

### 3.5 会话存储 `auth/SessionStore`（内存 MVP，取代旧 `StaffTokenStore`）
`token → LoginUser`；`issue(LoginUser)`（token 前缀按 realm：`stk_`/`atk_`/`ctk_`）、`get`、`revoke`。生产换 auth-core `RedisSessionStore`。

> **用法约定（业务侧）**：取代理号 `StaffContext.agentNo()`、取当前人 `SecurityUtils.userNo()`、判权限交给 `@PreAuthorize`。**任何业务/Service 不得 import `SecurityContextHolder`**。

## 4. 功能授权（RBAC）

### 4.1 权限码与角色
- **权限码** `<模块>:<资源>:<动作>`，通配 `<模块>:*` / 资源级 `<模块>:<资源>:*` / 超管 `*`——SSOT=[功能权限清单.md](../requirements/功能权限清单.md)。
- **角色集**：`ADMIN`(`*`) · `OPS` · `CS` · `FINANCE` · `BD` · `VIEWER` · `AGENT`。角色→码硬编码于 `auth/RolePerms.java`，**与前端 `ops-web/lib/permissions.ts` 逐字同源**（改一处须改两处；后续落 `iam_role_permission` 表统一）。

### 4.2 通配语义（含 bug 修复记录）
`LoginUser.hasPerm` 采用「精确 或 pattern 去尾前缀」匹配。**修复记录**：早期后端只取首段模块（`device:` → `device:*`），导致 `device:cabinet:*` 这类**资源级通配匹配不上**，与前端 `can()`（`code.startsWith(pattern.slice(0,-1))`）不一致 → OPS 等在后端被误 403。现已镜像前端，前后端 RBAC 一致（实测 OPS 下发指令 200）。

### 4.3 已挂鉴权的写接口（纵深防御第二道，权威列表）
| 方法 · 路径 | 权限码 | 位置 |
|------------|--------|------|
| `POST /api/ops/cabinets/{no}/commands` | `device:command:send` | `ops/OpsController` |
| `POST /api/ops/work-orders/{woNo}/dispatch` | `workorder:wo:dispatch` | `ops/OpsController` |
| `POST /api/ops/sites`（增改） | `location:poi:create` | `ops/OpsController` |
| `POST /api/ops/locations`（增改） | `location:poi:create` | `ops/OpsController` |
| `POST /api/trade/orders/{no}/intervene` | `order:intervene:execute` | `trade/TradeController` |
| `POST /api/trade/withdrawals/{no}/audit` | `finance:withdrawal:audit` | `trade/TradeController` |
| `POST /internal/user/credit/blacklist` | `user:risk:update` | `user/UserController` |
| `POST /api/agent/agents`（代理增改，含 `/{agentNo}`） | `agent:agent:update` | `agent/AgentController` |
| `POST /internal/gw/vendors/{code}/config` | `device:vendor:config` | `gateway/VendorController` |

> **纵深防御**：前端 `can()/canModule()` 控菜单/按钮（体验层，可绕过）；**后端 `@PreAuthorize` 是安全边界**。二者读同一套码，但后端只信 token 反查权限。新增写接口**必挂** `@PreAuthorize`。

### 4.4 一个坑（已处置）
`@PreAuthorize` 在 **AOP 层**抛 `AccessDeniedException`，**不经** Security 的 `accessDeniedHandler`，会被 `GlobalExceptionHandler` 兜底当 500 → 已在其加 `@ExceptionHandler(AccessDeniedException)→403`。另：`@PreAuthorize` 在**参数反序列化之后**执行，坏 body（`int` 字段传 null）先 500 不到鉴权（非安全问题，方法体未执行）。

## 5. 数据授权（Data Scope）

### 5.1 模型（`auth/DataScope`、`auth/ScopeDim`）
`DataScope{boolean all, List<ScopeRule(ScopeDim dim, Set<String> refs)>}`；维度全集 `ALL/REGION/SITE/LOCATION/VENUE/AGENT/SELF`。

### 5.2 解析（`auth/DataScopeResolver`，登录时）
- `ADMIN`（含 `*`）→ `ALL`；
- `AGENT` → `DataScope.agent(agentNo)`（**强制自己 agent_no，ADR-012 红线**）；
- 其余 STAFF → 暂 `ALL`（`REGION/SITE` 待接 `iam_data_scope(subject_type=ROLE/EMPLOYEE)` 数据源，见 [db-design](./db-design.md)）。

### 5.3 注册表（`auth/DataScopeTableRegistry`）
表→（维度→锚点列）。**未注册表 = 全局放行**。MVP 仅：`loc_site`（`AGENT→agent_no`、`REGION→region_id`、`SITE→site_no`）。`ord_rent`/`wo_order` 已有 `agent_no` 列但**尚未注册**（§10）。

### 5.4 注入器（`auth/DataScopeHandler` — MyBatis-Plus `MultiDataPermissionHandler`）
- 读 `SecurityUtils.currentUser().dataScope()`；`null`/`ALL`/豁免/未注册表 → **返回 `null`**（无附加条件）。
- 命中：按各维度锚点建 `col IN (refs)` 多条 OR；一条不命中 → `1=0`（拒绝，防越权）。条件用 `CCJSqlParserUtil.parseCondExpression` 构造（规避 jsqlparser 版本 API 差异）。
- **关键契约（含 bug 修复）**：`MultiDataPermissionHandler` **只能返回「追加段」或 null，MP 自行 AND 进原 WHERE**。早期误返回原 `where`/`AndExpression(where,cond)` → MP 二次 AND → WHERE 重复、占位符翻倍（`No value specified for parameter`），打挂**所有带参查询**（曾是并行会话的 Phase-0 阻塞）。已修。

### 5.5 豁免（`auth/DataScopeContext`）
`executeWithoutScope(Supplier/Runnable)`：无登录人的**后台任务/事件消费/域间调用**必须包裹，否则拦截器按空范围查空。

### 5.6 拦截器顺序（`config/MybatisPlusConfig`）
`DataPermissionInterceptor(dataScopeHandler)` → `PaginationInnerInterceptor` → `OptimisticLockerInnerInterceptor`（数据权限**先于**分页，MP 建议）。

### 5.7 实测
AGENT(AG002) `GET /api/ops/sites` 仅返回自己 2 个站点（其余 agentNo 全滤除），ADMIN 见全 15；`?keyword=` 组合查询 scope 仍生效。

## 6. 登录与会话（`auth/AuthController`）

| 端点 | 说明 |
|------|------|
| `POST /api/auth/login` | MVP 入参 `{username, role, agentNo?}`，**无密码校验（演示）**：校验 role→定 realm→`RolePerms.of(role)`→`DataScopeResolver.resolve`→组装 `LoginUser`→`SessionStore.issue`→返 `{token, role, perms}`。生产换 auth-core：pb_auth 凭据 + OTP/密码 + realm。 |
| `GET /api/auth/me` | 经 `SecurityUtils.currentUser()` 回显身份/权限。 |
| `POST /api/auth/logout` | `SessionStore.revoke`。 |

ops-web 登录改调 `/api/auth/login` 换真 token，`http-client` 携 `Authorization: Bearer`。

## 7. 端到端时序（一次受保护写请求）

```
ops-web ──Bearer token──▶ opsChain
  StaffTokenAuthFilter: token→SessionStore→LoginUser→SecurityContext(principal=LoginUser, authorities=perms)  [忽略客户端 X-Roles]
  DispatcherServlet ▶ @PreAuthorize("@perm.can('workorder:wo:dispatch')") ▶ PermChecker→StaffContext.hasPerm  ── 无权→AccessDenied→403 Result
  Controller ▶ Service：读身份仅 StaffContext.agentNo()/SecurityUtils.userNo()（不碰 SecurityContext）
  Mapper 查询 ▶ DataScopeHandler：AGENT→WHERE 追加 agent_no IN(...)   ── 只见自己数据
  ▶ Result{code:0,...}
```

## 10. 局限与后续

> **动态可配置化的详细落地步骤**（硬编码→运行时配角色/权限码/菜单/数据范围）见 [运营端权限-动态配置实现步骤.md](./运营端权限-动态配置实现步骤.md)。下列 1–4 项在该文展开为可照做的步骤。

1. **数据范围注册面**：仅 `loc_site`；下一步注册 `dev_cabinet`/`ord_rent`/`wo_order`（核实实际表含 `agent_no` 列），让 AGENT 也只见自己设备/订单/工单。
2. **REGION/SITE 维度**：`DataScopeResolver` 暂对非 AGENT 返 ALL；接 `iam_data_scope(subject_type=ROLE/EMPLOYEE)` 后出区域/站点 refs（角色级+员工级并集）。
3. **会话**：`SessionStore` 内存 → auth-core `RedisSessionStore`；登录接 pb_auth 真凭据（密码/OTP）。
4. **角色→码**：`RolePerms` 硬编码 → `iam_role_permission` 落库 + 缓存，前后端同源改为生成。
5. **拓扑**：`/internal`（域间 pre-auth 信任头）、`/openapi`（AppKey 签名）拆独立链（对齐 TDD-认证鉴权 §2 的 5 链目标）。
6. **审计**：`OperateLog`→`audit_log`（WORM）切面尚未挂（高危写操作留痕）。
