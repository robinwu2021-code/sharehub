## 一、本轮设计变化（相对上一版）

用户 2026-09-23 两次补充：「商家可以注册，运营商也可以代建，条件相同」→「注册信息包含手机号码、邮件」。
第二条看似只是加一个字段，**实际把账号模型从一张表改成了两张**：

| # | 变化 | 触发原因 |
|---|---|---|
| 1 | 新建 `agt_principal`（自然人 / 登录主体），`agt_account` 改挂 `principal_no` | 两个登录标识 + 一套凭据不能在 N 行成员关系上冗余；改邮箱要改 N 行，漏一行就是一个还能登的旧邮箱 |
| 2 | **登录键用 `*_hash` 而不是现有的 `login_phone`** | `agt_account.login_phone` 存的是**掩码**（V13 列注释原文「明文脱敏值」）。`13800138000` 与 `13811138000` 掩码相同——**用它做唯一键，两个不同的人会被判为重复** |
| 3 | 登录入参合成 `identifier` 一个字段 | 手机号与邮箱同一个端点；分两个字段，前端要先判断用户输的是什么，那个判断迟早和后端不一致 |
| 4 | ADR-030 原「待确认 2：凭据归属」结案 | 加了邮箱之后，`agt_principal` 从「更正确但多一张表」变成必需 |

**三列分工（加了邮箱之后更要守住）**：`*_hash` 做键与查找 · `*_mask` 只显示 · `*_enc` 需要还原时用。

## 二、D0 · 硬前置：真实登录链路不存在

这是全计划最重要的一条，**必须先看清楚再排期**。

```java
// AuthController:78 —— 今天的全部登录逻辑
if (gateConfigured) { if (!"admin".equals(username) || !adminPassword.equals(in.password())) 401; role = adminRole; }
else if (devMode.isEnabled()) { role = 前端传的 role; }   // 免密，角色前端自选
else 401;
```

| 事实 | 证据 |
|---|---|
| `agt_account` **根本不在登录链路里** | 全仓 `loginPhone` 只出现在实体与 DTO 各一处，**无任何业务代码读它** |
| 没有凭据校验 | `sharehub_auth.cred` 未建；口令是配置项 `sharehub.admin.password` |
| `agentNo` 由**前端传入**，缺省兜底硬编码 `"AG001"` | `AuthController:105` |

这三条是 [v4/06 §〇](./v4/06-认证与权限.md) 的第 1 号安全问题，**本计划不重复解决它**。
含义很直接：

> **D3（多主体登录）与 D6（主体切换）的验收，取决于 D0 是否已做。**
> D0 未做时，D3 可以先把 `agt_principal`、规范化 + HMAC、成员关系查询、越权闸都写好并单测覆盖，
> 但端到端「用手机号登录并切主体」跑不通。**排期时不要把 D3 当成能独立演示的一批。**

#### 三个实测才发现的问题

| # | 问题 | 处置 |
|---|---|---|
| 1 | **`CHAR(64)` 会让 `agt_apply` 建不出来** | MariaDB 12.2.2 报 `ERROR 1901`：`CASE` 的两分支类型不同（`CHAR` vs `VARCHAR`）时结果字符集要做合并，而生成列要求表达式结果确定。**两分支同为 `VARCHAR` 才通过**。hash 列统一改 `VARCHAR(64)`，并在 V48 末尾写了注释防止有人改回去 |
| 2 | **存量掩码不可逆，任何自动回填都只能填错** | 给每条存量账号派生占位 `agt_principal`（`PR-LEGACY-{account_no}`，hash 由 account_no 派生，**永远不会被真实登录命中**）并置 `DISABLED`。宁可让人工补资料后再启用，也不要产生「能登录但身份不明」的行 |
| 3 | **pepper 尚未拍板**（§7.1 #3），但它卡在最前面一批 | 按可逆的默认落地：配置项 `sharehub.security.identity-pepper`（启动 fail-fast），表加 `hash_ver TINYINT DEFAULT 1`。**轮换路径 = 用 `*_enc` 全表重算后统一切版，唯一键不动**——这也是 `*_enc` 必须可逆的原因。若最终选别的方案，改的是配置与重算脚本，不动表结构 |

**两个坑**：

1. **回填走人工，不写进脚本。** 掩码不可逆，从 `138****8000` 推不回明文。
   上线前先跑 `SELECT COUNT(*) FROM agt_account WHERE deleted=0;` —— 很可能接近 0（它不在登录链路里），
   那就不需要回填，直接 `NOT NULL`。
2. **`login_phone` 列留着不动**，只当显示用；**不要**拿它回填 `phone_hash`。

### D3 · 后端 · 自然人与多主体登录（4 天）— **依赖 D0**

| | |
|---|---|
| 新增 | `agent/ext/entity/AgtPrincipal.java` · `mapper/AgtPrincipalMapper.java`<br>`common/identity/IdentifierNormalizer.java`（规范化）· `IdentifierHasher.java`（HMAC + pepper） |
| 修改 | `platform/iam/AuthController.java` · 数据范围锚点取值 · `LoginUser` 加 `memberships` 与 `currentOperatorNo` |

**四条实现约束**：

1. **规范化必须只有一个实现**，注册与登录共用。两处各写一遍 = 注册能成、登录查不到，且只在带空格 / 连字符 / 国际区号的输入上出现。
2. **`limit 1` 必须带 `ORDER BY is_primary DESC, id ASC`**。无序 `limit 1` 在多主体下随机挑一个，「今天进 A 明天进 B」无法复现。
3. **`X-Operator-No` 越权闸**：解析出的主体必须落在会话 `memberships` 内；不在就**整个丢弃、回落默认，不报错**。这是整条改造里唯一有越权面的地方。
4. **`operatorNo` 是解析的入参，不是解析完再套上去**：先读请求头定主体，再据它装配权限与数据范围。

**必加的守卫测试**：切到 B 主体后看不到 A 主体的任何数据 · 伪造 `X-Operator-No` 回落默认 · 掩码列不出现在任何唯一键或等值查询里。

#### 一个真缺陷：端点判权码的**粒度**错了

「站点概览」这个只读看板，端点判的是 `location:poi:read` —— 一个覆盖 **4 个端点、3 个菜单叶**的宽码。
而功能权限清单第 67 行本来就为它定了专属码 `location:overview:read`（给 OPS/FIN/BD/VIEW），
**后端却没有任何端点用过它**。

于是形成一个闭环的错：前端拿一个没人判的码渲染入口，后端拿另一个更宽的码判访问。
财务看得到「站点概览」却打不开（没有 `poi:read`）；而给财务补 `poi:read`
又会连带解锁「站点管理」「点位管理」两个它不该有的入口。
**改判专属码，两头都正了** —— 这不是对齐两份表，是让码的粒度与功能一致。

> **文档里的「没有 X」比「有 X」更值得复核** —— 前者会让人去新建，而新建的东西一旦上线就难撤。

#### B2 为什么现在不做（2026-09-23 对齐结论）

读完另一会话刚落地的 `loc_site_agent`（V52 + A2 系列）后，B2 有两个前置没解：

1. **已经有一个哨兵，但在另一层**：`CabinetQueryPort.DIRECT_OPERATED = "__NONE__"` 是
   **查询参数**层的（传它 = 只看直营），存储层仍是 `agent_no IS NULL`。
   B2 会再引入一个**存储层**哨兵 `PLATFORM` —— 同一个概念两个表示、分属两层。
   语义其实不同（`__NONE__` = 不属于任何代理；`PLATFORM` = 属于平台这个主体），
   但读代码的人很难第一眼分清。
2. **A2 系列正建立在「`agent_no` 为空 = 直营」之上，且还有两批没做**
   （A2-3 商机归因、A2-4 REFER 签约事件）。他们 V52 的注释明写
   「只有 REFER 的站点 `agent_no` 为空（= 直营运维）」—— B2 会改掉这个前提，
   此刻动手会让那两批返工。

**结论**：等 A2 落定 + 哨兵分层有结论再排。在那之前 `loc_site.agent_no`
的空值语义由 A2 那边定义。详见 [ADR-029 §八待确认 1](./ADR/ADR-029-运营主体抽象.md)。

**B3 已全部完成**（`002d19b` 收尾）：场地方档案列表加了「收款账户」列 ——
有默认账户显示掩码，没有则标「未设置 · 去补录」并链到财务那边的管理页。
那一页**不做账户增删改**：两处各造一套 CRUD 的结果一定是「在哪个入口改的」
决定别人看不看得见。
