## 〇、设计原则（用户定调，按优先级排列）

1. **业务抽象与易治理第一，服务数量少第二** —— 不是让服务更少，是让**变化被隔离**；
2. **按「变化的原因」拆，不按业务名词拆** —— 设备类型是数据维度，供应商是驱动插件，
   只有「变化原因与业务不同」的南向接入才是服务边界；
3. **微服务不刻意多也不刻意合并**，当前定为 5 个（见 §四）；
4. **一套代码两种部署**：接口抽成独立包，整体可打包为单体，配置切换（见 §五）；
5. **每条边界必须可被机器校验**，否则等于没有边界（见 §六）。

## 一、业务抽象层

### 1.1 设备类型：容器 / 槽位 / 物品 三分法

一切共享设备都装进同一个模型，差别只在「槽位里有没有可移动物品」。
**首批登记三类**（用户拍板储物柜一同考虑）：`POWERBANK` · `EV_PILE` · `LOCKER`。
储物柜的价值不只是第三个类型 —— **它是对共性抽象的第一次真实检验**，已当场修正一处（押金，见 1.2）：

| 概念 | 表 | 充电宝 | 充电桩 | 储物柜（将来） |
|---|---|---|---|---|
| **容器** | `dev_cabinet` + `device_type` | 柜机 | 充电桩体 | 柜体 |
| **槽位** | `dev_slot` + `device_type` | 仓位 | **枪/连接器** | 格口 |
| **物品** | `dev_powerbank`（类型特有表） | 充电宝（可移动） | **无** | **无**（存的是用户自己的东西，不是平台资产） |

- 容器/槽位**永远设备无关** —— 站点归属、数据范围、告警、工单、库存全部只挂容器/槽位，
  所以这些域在新增设备类型时**零改动**；
- 「物品」按类型建表：有可移动物品的类型（充电宝）才有物品台账；充电桩的"资产"就是容器+槽位本身；
- 新增设备类型登记进 **`md_device_type`**（L0 主数据，规划新表）：
  `type_code`(POWERBANK/EV_PILE/LOCKER…) · `has_movable_item` · `default_metering` ·
  `order_ext_table` · `reservation_target`(CABINET/SLOT)。
  **类型的差异用数据描述，不用 if/else 散在代码里** —— 这张表就是「加一种设备要改哪些东西」的清单。

### 1.2 订单：共性主表 + 类型扩展表（定案）

```
ord_order          共性主表（资金侧唯一入口）
 ├─ ord_rent_ext        充电宝扩展
 └─ ord_charge_ext      充电桩扩展
```

**`ord_order`（共性列，来自现 `ord_rent` 中设备无关的部分）**：

| 列 | 说明 |
|---|---|
| `order_no` | 业务键，前缀不变（§1.4.1 注册表） |
| `device_type` | 一等维度，默认 `POWERBANK` 向后兼容 |
| `c_user_no` · `site_no` · `location_no` · `cabinet_no` · `slot_index` | 谁、在哪、哪台、哪个槽位 |
| `agent_no` · `region_id` | 归属快照（数据范围锚点，转手不回写） |
| `status` | 共性状态机（见下） |
| `started_at` · `ended_at` | 业务起止 |
| `price_plan_no` · `coupon_no` · `free_reason` · `waived_amount` | 计价快照与减免 |
| `amount` · `currency` | 应收 |
| `deposit_amount` · `auth_no` | **押金/预授权（自 rent_ext 升入主表）**：充电宝押金、充电桩预授权、储物柜押金 —— 三类中两类以上需要的字段属于共性。`auth_no` 关联 `pay_auth` |
| `source_channel` · `partner_no` | 订单来源：`APP/MINI/H5/INTERCONNECT`；互联互通单带伙伴编号（§1.6） |
| `reservation_no` | 由预约履约而来时回链（可空） |

**升格规则（由储物柜检验得出）**：一个字段出现在 **≥2 种设备类型**，就升入主表；只属一类才留扩展表。
押金原在 `ord_rent_ext` —— 储物柜也要押金、充电桩要预授权，故升入主表。`buyout`（丢失买断）只有充电宝有，留在扩展表。

**`ord_rent_ext`**：`powerbank_no` · `return_cabinet_no` · `return_slot_index` · `buyout` · `duration_min`
**`ord_charge_ext`**：`connector_no` · `energy_kwh` · `start_soc` · `end_soc` · `peak_power_kw` · `stop_reason`(FULL/USER/FAULT/BALANCE) · `idle_min`(充满后占位分钟)
**`ord_locker_ext`**：`cell_index`(格口) · `access_code`(取件码) · `overtime_min`(超期占用) · `item_note`(存物备注，可空)
— 储物柜没有击穿计价设计：主计费就是 `TIME_FEE` + 超期用 `IDLE_FEE`，五类费用项无需新增，**这正是抽象成立的证据**。

**成立判据（验收标准，不是愿望）**：分润 `share_record`、账务 `acct_ledger`、发票 `fin_invoice_item`、
结算、报表读模型 —— **只 join `ord_order`**。新增设备类型时资金域一行不改；做不到就是共性列抽错了，
回头调主表而不是往扩展表塞。

**共性状态机**（类型语义放子状态，资金侧只认 `SETTLED`）：

```
CREATED → ACTIVE → ENDED → SETTLED → CLOSED
            │        │
   充电宝: DISPENSING(等待弹出) 是 CREATED→ACTIVE 的类型子状态
   充电桩: PREPARING(等待插枪) 同上；ENDED 后可有 IDLE(占位中) 子状态，占位费在 SETTLED 前并入账单
```

**迁移方案**（执行时机待放行，与 ADR-014 更名可同批）：
1. 建 `ord_order` + 两张 ext（Flyway 新版本号，遵守「不改 V1..V13」纪律）；
2. 存量 136 条 `ord_rent` 拆列迁入（`device_type='POWERBANK'`），`ord_rent` 保留为只读视图一个版本周期；
3. 资金侧四域改 join `ord_order`（列名不变，改表名）；
4. `RentOrderService` 更名 `OrderService`，充电宝特有逻辑下沉 `device/powerbank`。

### 1.3 预约与占位（新决策：充电桩要）

现 `ord_reservation` 结构已大半通用（BORROW/RETURN、`hold_fee`、`PENDING/FULFILLED/EXPIRED/CANCELLED`），
**泛化而非另建**：

| 改动 | 说明 |
|---|---|
| 加 `device_type` | 默认 POWERBANK |
| 加 `target_ref` | 预约的具体标的：充电宝=柜机（任意仓位），充电桩=**具体枪** `connector_no` —— 粒度差异由 `md_device_type.reservation_target` 声明 |
| `type` 语义扩展 | 充电桩只有 BORROW（占枪）；储物柜 BORROW=预留格口，无 RETURN 预约 |
| 履约回链 | `FULFILLED` 时写 `ord_order.reservation_no`，`hold_fee` 作为账单抵扣项进计价（见 1.4） |

**充电桩预约的特有规则**（写入 TDD 时落地）：
- 预约成功 → 枪置 `RESERVED`（OCPP `ReserveNow`），过期自动释放（OCPP `CancelReservation`）；
- 到场插枪 → 预约履约 → 订单 `CREATED`；预约费转入订单抵扣；
- 过期未到 → `EXPIRED`，`hold_fee` 按计价项「预约违约」收取或退还（运营可配，`sys_biz_rule`）；
- **超时占位费与预约费是两回事**：前者是充满后不挪车（`ord_charge_ext.idle_min` × 占位费率），
  后者是占枪未用 —— 两者都是计价的「费用项」，不是订单模型的特例。

### 1.4 计价引擎：计量维度 + 费用项 + 阶梯 + 分时（新决策：一起设计）

现 `price_plan` 把时长计费写死在列上（`free_minutes/unit_minutes/unit_price/cap_daily`），
充电桩装不进去。重构为**方案 → 费用项 → 阶梯**三级，分时复用现有 `price_schedule`：

```
price_plan            方案头：plan_no · device_type · name · scope · currency · status
 └─ price_plan_item   费用项：item_type · metering · free_qty · cap_daily · cap_total
     └─ price_ladder  阶梯：seq · from_qty · to_qty · unit_price
price_schedule        分时段（峰/平/谷），作用到指定费用项的单价系数或替换价
price_rule            适用规则（站点/场景/维度匹配，四层取价链不变）
```

**费用项类型 `item_type` × 计量维度 `metering`**：

| item_type | metering | 充电宝 | 充电桩 |
|---|---|---|---|
| `TIME_FEE` 时长费 | MINUTE | ✅ 主计费（现 price_plan 平移为一个 item） | 可选（慢充按时补充） |
| `ENERGY_FEE` 电费 | **KWH** | — | ✅ 主计费，**必须阶梯 + 分时** |
| `SERVICE_FEE` 服务费 | KWH / MINUTE | — | ✅ 行业惯例电费与服务费**分列**（对账、发票、分润口径都要求分开） |
| `IDLE_FEE` 占位费 | MINUTE | — | ✅ 充满后计，`free_qty` 为宽限期 |
| `HOLD_FEE` 预约费 | 次 | 可选 | ✅ 履约转抵扣 / 违约收取 |

**四层取价链不变**（快照 plan → 券在封顶后抵扣 → 免费单先算后减免），只是「算一个数」
变成「逐费用项算完求和」。**订单快照的是整个 plan 的展开结构**（items+ladders+schedule 生效值），
不是 plan_no 一个引用 —— 改价不影响在途订单，这条现有纪律延续。

**充电桩是过程计费**：`METER_VALUE` 事件流实时累计 kWh 与金额（C 端展示「已充 X 度 / 预计 Y 元」），
`TX_STOP` 定稿。**过程累计值仅展示，结算只认 TX_STOP 的表底数** —— 表底对不上走对账差异（`recon_diff`）。

**兼容迁移**：现 `price_plan` 的四个列平移为一条 `TIME_FEE` item + 单段阶梯，语义零变化；
`price_plan` 保留 `device_type` 默认 POWERBANK。

### 1.5 供应商接入：三种形态 × 能力声明

「对接不同供应商的系统」在实践里是三种完全不同的形态，**驱动 SPI 必须显式区分**：

| 形态 | 对接对象 | 协议 | 典型 | driver 要实现 |
|---|---|---|---|---|
| **A 厂商云** | 供应商的开放平台 | HTTPS API + Webhook | 充电宝主流厂商 | `invoke()` / `parseWebhook()`（验签、SN 映射归 driver） |
| **B 设备直连** | 设备本体 | TCP / MQTT 私有协议 | 部分柜机 | `encode()` / `decode()`（长连接会话在 device-gateway） |
| **C 行业标准** | 桩本体或桩企云 | **OCPP 1.6J / 2.0.1**（WebSocket） | 充电桩 | OCPP 适配器**一次实现**，各桩企只配差异参数 |

**驱动能力声明（manifest）**，注册进 `gw_vendor`：

```
{ vendorCode, deviceTypes: [POWERBANK|EV_PILE|…], form: A|B|C,
  commands: [...], events: [...], auth: {...} }
```

- 平台按 `(vendor_code, device_type)` 路由指令；`gw_vendor.device_types` 多值列（§1.7 拆表规范）；
- 指令/事件三层：**通用集**（REBOOT/LOCATE/ONLINE/OFFLINE/FAULT/OTA）+ **充电宝族**（EJECT/SLOT_REPORT/RETURNED）
  + **充电桩族**（START/STOP_CHARGE · METER_VALUE · TX_START/STOP · CONNECTOR_STATUS，语义对齐 OCPP，不自创）
  + **储物柜族**（OPEN_CELL · QUERY_CELLS ／ CELL_OPENED · CELL_CLOSED · OVERTIME）——
    最小的一族，无计量、无实物，正好作为「新增一族要写多少东西」的下界样本；
- **新增供应商 = 写一个 driver + 后台注册 manifest，业务与网关框架零改动**（ADR-003 承诺，分族后依然成立）；
- 反方向的「把我们开放给别人」走 `openapi_app`（开放平台模块），与南向互不混用。

**供应商边界红线（2026-07-30 用户定界）：供应商只做设备管理，资金与支付全在本平台。**

| 能力 | 归属 | 说明 |
|---|---|---|
| 设备控制 · 遥测 · 固件 | 供应商侧（经 API/协议互通） | driver 的全部工作面 |
| 订单 · 计价 · 支付 · 结算 · 分润 | **本平台，无例外** | 供应商对交易资金**零接触** |

三条推论，逐条落到设计：

1. **厂商云的订单/支付类 SaaS 能力一律不用**。充电宝厂商开放平台普遍带「租借下单/代收款」
   接口 —— 只调设备类 API（弹出/查仓/状态），订单永远由 core 建。manifest 的 `commands/events`
   白名单就是执行手段：不在白名单里的厂商能力，driver 层面就不存在；
2. **设备事件一律是物理事实，不是业务语义**。充电宝族事件更名：
   `RENT_CONFIRMED` → `EJECT_OK`（仓门弹出成功）、`RETURNED` → `ITEM_INSERTED`（有宝插回）。
   「这算不算某个订单的归还」由 core 判定 —— 换柜归还、误插回、非订单宝插回都是 core 的业务规则，
   设备只报告它看见了什么。**命名带业务语义，边界迟早被写穿**；
3. **供应商的资金关系只有设备采购/租赁（应付账）**，与交易分润无关，线下或应付模块处理，
   不进 `share_record`/`stl_settlement`。与 §1.6 伙伴（**交易资金对手方**）恰成对照：
   **供应商在设备侧，伙伴在资金侧，两者不会是同一个抽象**。

附带的数据边界：指令与报文**不携带消费者个人信息**（PDPL）——设备只需要「弹哪个仓」，
不需要知道是谁在借。SN↔业务编号映射留在 driver/网关内。

### 1.6 北向互联互通（新决策：在范围内）

充电桩生态里平台是 **CPO**（桩的运营者）；第三方聚合/出行平台（eMSP）要能**在他们的 App 里
启动我们的桩**。这是一个**北向 B2B 接入面**，与南向设备接入完全是两回事，不进 device-gateway：

| | 南向 device-gateway | 北向 互联互通 |
|---|---|---|
| 对端 | 设备/厂商云 | 聚合平台/出行平台（伙伴） |
| 方向 | 我们控制设备 | **伙伴调我们**下单 |
| 协议 | OCPP / 私有 | **OCPI 2.2.1**（国际）/ 中电联标准（国内），按市场配 |
| 资金关系 | **无**（供应商只做设备管理，红线见 §1.5） | **伙伴是结算对手方**：我们向伙伴收费或分成 |

**模块「互联互通 interconnect」**（L5 对外服务面，规划表 `intc_*`）：

| 表 | 内容 |
|---|---|
| `intc_partner` | 伙伴档案 · 凭证 · 协议类型(OCPI/中电联) · 结算方式 |
| `intc_session_map` | 外部会话 ↔ `order_no` 映射（伙伴的 session id 是他们的主键，必须双向可查） |
| `intc_cdr_log` | CDR（账单明细）推送日志，幂等重推 |

**协议面对齐 OCPI 模块**：Locations（桩/枪目录发布）· Tariffs（价格发布，来自计价引擎的展开结构）·
Commands（远程启停 → 经 core 订单 API 建单，`source_channel=INTERCONNECT`）· Sessions（过程状态回推）·
CDRs（结算账单推送）。中电联标准作第二适配器，**协议差异收在 interconnect 内，core 不感知**。

**资金闭环**：互联互通单照常走 分润/账务（资金侧只认 `ord_order`，来源渠道无关 —— 这正是主表判据的红利）；
**新增的是伙伴结算**：`stl_settlement.payee_type` 扩展 `PARTNER`，按 CDR 对账（`recon_task` 加伙伴对账源）。

**部署归属**：模块先随 `platform` 部署（伙伴量小，纯协议适配无状态）；
它与 device-gateway 同构 —— **伙伴多了会线性膨胀** —— 故登记为**第 6 个服务的首选增长点**，
拆分信号：伙伴数 >3 或某伙伴调用量影响配置面。

## 二、模块设计

### 2.1 分层与模块（32 模块 6 层，机器校验）

以 [业务模块分层](./业务模块分层.md)（`module-graph.py` 生成）为准，此处不重复清单。三条硬约束：
**每张表必须归位（132/132）· 每条依赖可追到具体列 · 分层不许反向依赖**。

本轮规划的新表归属（建表时同步登记进脚本 `MODULES`）：

| 新表 | 模块 | 层 |
|---|---|---|
| `md_device_type` | 主数据 | L0 |
| `ord_order` / `ord_rent_ext` / `ord_charge_ext` | 订单 | L3 |
| `price_plan_item` / `price_ladder` | 计价 | L3 |
| `ord_locker_ext` | 订单 | L3 |
| `intc_partner` / `intc_session_map` / `intc_cdr_log` | 互联互通（新模块） | L5 |

### 2.2 模块内部结构约定

```
<module>/
  entity/  mapper/  service/ + service/impl/     # 数据与业务
  dto/                                            # 出入参（镜像前端 types）
  api/                                            # 【跨服务被调面】只放接口+DTO → 编译进 *-api 包
```

- 模块间调用**只许经对方 `api/`**；`service/impl` 是模块私有；
- 设备类型特有逻辑收进 `device/<type>/`（ADR-014 M3），如 `device/powerbank/`、`device/evpile/`；
- 事件类放发布方模块的 `api/event/`，**事件自带消费方所需全部字段**（否则等于把同步调用藏进事件）。

### 2.3 已知欠账（不解决则边界是纸糊的）

1. 3 个旧骨架控制器跨模块（`OpsController`/`TradeController`/`UserController`）——按目标模块拆；
2. 20 个 `/api/**` 端点无功能权限码（任何已登录员工可读账务分录/员工名册/审计日志）；
3. `gw_command_log.order_no` 反向依赖 → 改 `biz_type + biz_ref`；
4. 5 个跨域重名业务键（`account_no`/`invoice_no`/`plan_no`/`refund_no`/`rule_no`）→ 按 db-design §1.4.1 收敛；
5. 划拨级联跨界事务（`AgentOwnershipSync`）→ 事件驱动最终一致 + 对账补偿。

## 三、整体架构（5 服务 + 3 BFF + 南向）

```
 运营端 ops-web      C端 c-app       代理端(待建)
      │                │                │
   ops-bff          mp-bff         agent-bff          ← 薄壳：鉴权/受信头/形状裁剪，无业务
      └────────────────┼────────────────┘
              ┌────────┴─────────┬──────────┬────────────┐
          platform            core         ops        finance
        底座+运营配置      主链路(订单/支付/  告警/工单/客服   账务/分润/
        41 表             计价/消费者/设备   14 表        结算/发票/对账
                          资产/库存) 56 表                12 表
              └─────────事件总线（单体=Spring Event / 微服务=MQ）─────────┘
                                   │
                            device-gateway  9 表
                     厂商目录 · 驱动(A/B/C 三形态) · 绑定 · 心跳

                                   │
                 厂商云 API ⇄ Webhook │ TCP/MQTT 直连 │ OCPP WebSocket
```

**主数据流**（跨服务边全部为异步事件或只读查询，实测主链路跨服务边 = 0）：

| 链路 | 路径 | 形态 |
|---|---|---|
| 借出/充电 | mp-bff → core（订单+计价+支付+设备占用，**单事务**）→ device-gateway 下发指令 | 指令下发是**天然异步**（设备本来就要回执） |
| 设备事件 | device-gateway 归一化 → 事件 → core（履约/结算）· ops（告警） | 事件 |
| 资金 | core「订单已结算」事件 → finance 记账/分润/开票 | 事件 |
| 运维 | ops 读 core/platform 的资源快照 + 只读 API | 只读 |
| 报表 | 订阅各服务事件落宽表（读模型）；单体期直接 JOIN，仅限 `ReportMappers` | 读模型 |

## 四、服务边界（为什么是这 5 个，不多不少）

| 服务 | 独立的理由（变化的原因） | 不再拆的理由 |
|---|---|---|
| `platform` | 运营配置面，读多写少，变更按运营节奏 | 内部模块（组织/代理/场地）变化原因相同 |
| `core` | **同步主链路**：借出一笔要单事务动订单+占用+预授权+券 | 拆开=分布式事务，拿最热链路换整洁 |
| `device-gateway` | **供应商与设备类型增多时唯一线性膨胀**；长连接技术栈；故障域隔离 | — |
| `ops` | 异步可延迟，处置节奏与主链路无关 | 告警/工单/客服共享处置上下文 |
| `finance` | 批处理节奏；合规上可能要求独立部署 | 账务/分润/结算共享记账一致性 |

**不设的服务**：按设备类型拆（订单/计价/结算复制 N 份，灾难）· 按供应商拆（ADR-003 已否决）·
独立「用户服务」「计价服务」（与 core 同一变化原因，拆出来只是方法调用变 HTTP）。

**将来允许的增长点**（出现信号再拆）：**`interconnect`（首选** —— 与 device-gateway 同构的北向膨胀点，信号：伙伴数 >3，见 §1.6）· `report`（读模型独立）· `notify`（触达量大后）。
增长上限心智：**7 个**。超过就要回答「哪两个变化原因真的不同」。

## 五、双形态部署（细化 ADR-017）

### 5.1 Maven 结构（接口独立成包）

```
sharehub-common                      Result/分页/异常/受信头/数据范围/事件总线抽象
sharehub-api-{platform,core,gateway,ops,finance}    ← 只有 接口+DTO+事件类，无实现
sharehub-svc-{platform,core,gateway,ops,finance}    ← 实现 jar，不可独立启动
sharehub-app-mono                    聚合 5 个 svc → 单体（默认交付物）
sharehub-app-{platform,core,gateway,ops,finance}    ← 各含 1 个 svc + 他人 api → 微服务交付物
```

依赖规则（enforcer 卡死）：`svc-X` 只许依赖 `common` + 任意 `api-*`；**`api-*` 不许依赖任何 `svc-*`**；
`app-*` 不含业务代码。

### 5.2 配置切换（业务代码不知道自己在哪种形态）

```yaml
sharehub:
  deploy:
    mode: mono            # mono | micro
    remotes:              # micro 时生效；mono 下整段忽略
      core: http://svc-core:8080
      platform: http://svc-platform:8080
```

- 跨服务调用只依赖 `api-*` 接口；`svc-*` 提供本地实现，`api-*` 附带
  `@ConditionalOnMissingBean` 的 HTTP 实现 —— **classpath 决定形态，配置只补充地址**；
- 事件：`common` 定义 `DomainEventBus` 接口；mono 绑 `ApplicationEventPublisher`（事务提交后投递），
  micro 绑 MQ + **transactional outbox**（`sys_outbox` 表，规划）保证「落库与发事件」原子；
  发布/订阅代码两种形态下零差异；
- BFF 与网关路由：mono 下 nginx 全量转单体；micro 下按前缀路由表分发（`/api/trade→core` 等），
  路由表跟随 `api/contract.json` 生成，不手维护。

### 5.3 数据库演进

| 阶段 | 形态 | 说明 |
|---|---|---|
| 现在 | 单库 `pb_core` | 132 表全部有主（脚本校验），跨模块 JOIN 仅 `ReportMappers` |
| 拆分时 | **先分 schema** `pb_{platform,core,gw,ops,fin}` | 归属清单即 `module-graph.py` 的 `services` 输出；连接串按服务切 |
| 需要时 | 再分实例 | 只有出现独立扩容/合规信号才做 |
| 并行 | `pb_pii` / `pb_auth` | 个人信息与凭证隔离（PDPL），与形态无关，上线前必须拆 |

### 5.4 部署矩阵

| 场景 | 交付物 | 进程 | 库 |
|---|---|---|---|
| 开发/演示/小客户私有化 | `app-mono` | 1 | 1 |
| 生产（默认起步） | `app-mono` ×N 副本 | N | 1（读写分离可选） |
| 信号出现后 | 5 个 `app-*` | ≥5 | 分 schema |
| 混合（允许） | 如 `app-gateway` 先拆、其余仍 mono | 2 | gateway 表先分出 |

**混合形态是双形态机制的直接推论**：任何一个服务都可以单独先拆，不要求一次全拆。
最可能先拆的就是 `device-gateway`（接第二家供应商风暴一次就够了）。

## 七、演进路线（每步可独立交付，前后不互锁）
