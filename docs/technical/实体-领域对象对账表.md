### 3.2 它已经造成了一个真缺陷

[`AlarmServiceImpl.java:156`](../../backend/sharehub-svc-ops/src/main/java/ai/neargo/sharehub/alarm/service/impl/AlarmServiceImpl.java#L156) —— 自动开工单：

```java
.in(DevAlarm::getStatus, java.util.List.of("OPEN", "ACK"));
```

但 `"ACK"` 是**事件名**，不是状态。状态机 `AlarmStateMachine` 里 `"ACK"` 是 event、
落库的状态是 `ACKED`；DDL 注释写 `OPEN/ACKED/CLOSED`；seed 写的也是 `ACKED`。
**没有任何一行数据的 status 会等于 `"ACK"`。**

⇒ **已受理（`ACKED`）的告警永远不会被自动开工单**，只有 `OPEN` 的会。
没有报错、没有日志、测试也不会红 —— 少的那部分工单不会自己喊疼。

这正是裸字面量的代价：`ACK` 与 `ACKED` 差一个字母，编译器无从分辨。
（同类拼写分叉还有 `CANCELLED`（代码 3 处 + DDL）vs `CANCELED`（DDL 2 处）。）

**✅ 已修**（2026-09-23）：`"ACK"` → `AlarmStateMachine.ACKED`，值只从状态机常量取。
配 `AlarmStatusVocabularyTest`，**改前只有 ACKED 那条断言红、OPEN/CLOSED 都绿**
（反向对照证明缺陷真实存在，且断言打在点上）。测试同时钉住 CLOSED **不该**开单 ——
只断言 ACKED 会被"把条件放开到查全表"的错误修法蒙混过去。

### 3.3 55 个词表已经互相打架

同一类语义，四套不同词表并存：

| 词表 | 用在 |
|---|---|
| `OPEN/ACK/RESOLVED` | v1 告警（已废） |
| `OPEN/ACKED/CLOSED` | v2 告警 |
| `OPEN/PROCESSING/CLOSED` | 工单 |
| `OPEN/HANDLED` · `OPEN/HANDLING/RESOLVED/IGNORED` | 对账差错处置 |

这不是"不好看"。它的具体代价是三条：

1. **拼错不报错**，安静写进库，直到某张报表少一类数据才被发现（3.2 就是实例）；
2. **状态机没有闭包** —— 现在无法回答"这个对象的合法状态有哪些"，除非通读全部 service；
3. **模型改了词表，代码不会红** —— 文档与实现从此各说各话。

### 4.1 退役为什么只改名不 DROP

本机 `pb_core` 实测 `dev_alert` **0 行、无外键、无视图引用**，代码只有 3 处注释提到它。
但**别的环境的行数在这里无法确认**，所以 V45 只 `RENAME`：数据原样保留、随时可改回来，
而它已从活跃 schema 消失。DROP 留给确认过各环境行数之后的单独一次迁移。

V8 里那段 `dev_alert → dev_alarm` 的数据搬运**仍不执行** —— 列映射需人工复核，
未经复核的搬运比不搬更糟：它会把错的值变成"正式数据"。

### 4.2 顺带修掉的第三处词表分叉

领域模型 §2.2 写 `agt_assignment(action=ASSIGN/RECLAIM)`，而 DDL 注释与
`AgentAssignmentServiceImpl` 的白名单都是 **`ASSIGN/REVOKE`**。文档里的 `RECLAIM`
**从未被任何代码写入过**。已改。

连同 §3.2 的 `ACK`/`ACKED` 与 `CANCELLED`/`CANCELED`，**三处分叉全部出在"没有单一真源"这一个根因上**。

**依赖向下、整理向上；反过来会返工两遍。**
