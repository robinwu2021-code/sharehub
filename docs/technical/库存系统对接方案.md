## 一、分工

| | powerbank（宿主，业务系统） | ai-shop 库存服务（账本） |
|---|---|---|
| 管什么 | 设备生命周期（质检、绑定、上线、维修、撤机）；商家、站点、人员；运营界面与权限 | 在库数量与序列号、出入库单据、出库池（发货 → 签收 / 撤回 / 退回）、盘点、流水、期间汇总 |
| 账 | 本地设备表是**业务状态**；切到独立进销存后，**库存账以库存服务为准** | 唯一的库存账 |
| 身份 | 人的权限只在 powerbank 判定 | 只认系统凭证（`SHAREHUB` 业主），不认人 |
| 界面 | 全部在 ops-web | 无（不直接面向运营） |

**一句话**：powerbank 做业务和界面，库存服务记账；两边通过 powerbank 后端的 `InventoryApi` 客户端对接，ops-web 不直接调库存服务。

### 2.2 powerbank 后端

| 配置 | 说明 |
|---|---|
| `sharehub.inventory.base-url` | 库存服务地址，如 `http://127.0.0.1:8088` |
| `sharehub.inventory.app-key` / `app-secret` | `SHAREHUB` 业主的系统凭证。**不入仓库**：本机放 `~/.local/etc/inventory-sharehub-cred.json`（权限 600），由启动脚本读入 |
| `sharehub.inventory.connect-timeout` / `read-timeout` | 默认 2s / 5s |
| 系统参数 `inv.engine` | `LOCAL`（默认，本地设备表）/ `SERVICE`（独立进销存）。运营端「库存管理 › 库存设置」可改 |

三项凭证配齐、`inv.engine = SERVICE` 时才真正调库存服务。缺凭证时，任何走库存服务的动作都返回 409 `error.inventory.not_configured`。

`GET /api/ops/inventory/engine` 返回 `engine`、`configured`、寻址方式 `endpointMode`（STATIC / DISCOVERY），SERVICE 下还会现探一次连通性：`reachable`，不可达时附 `failure` 错误码。运营端「库存管理 › 库存设置」页顶显示，30 秒重探一次。

## 三、开通（一次性）

用库存服务的管理端（`/api/inventory/admin/v1/owners`，头 `X-Inventory-Admin-Token` 与 `X-Inventory-Actor`）完成三件事。脚本在 `backend/scripts/inventory-local/`：

1. **开业主**：`systemCode = SHAREHUB`、`externalRef = powerbank-<环境>`。（`onboard.sh`）
2. **业态档案**：定义唯一在 `onboard.sh` 的 `PROFILE`。已开过业主的只更新档案：`profile.sh <ownerId>`。
3. **发凭证**：返回 `appKey / appSecret`，写进凭证文件，不打印、不入仓库。

当前档案（version 2）：

| 项 | 取值 | 谁在用 |
|---|---|---|
| 能力 | `SERIAL`、`DISPATCH_POOL` | 柜 / 宝按序列号管理；出库进出库池 |
| 去向类型 | `MERCHANT`、`SITE`（上级 MERCHANT）、`PERSON`、`SUPPLIER` | 出库给商家；退供应商 |
| 入库用途 | `PURCHASE`、`RETURN`、`CORRECTION`、`OPENING`、`TRANSFER_IN` | 到仓待检入库、撤机回仓、期初、物料 / 设备调拨入 |
| 出库用途 | `ISSUE`（须 MERCHANT + PERSON，可选 SITE，进出库池）、`SCRAP`、`REQUISITION`、`RETURN_SUPPLIER`（须 SUPPLIER）、`TRANSFER_OUT` | 出库给商家；报废；物料领用；退供应商；物料 / 设备调拨出 |
| 放行凭证 | `QC` | 柜 / 宝入库必须带质检记录号 |
| 盘点复核 | 必须复核、复核人 ≠ 提交人 | 盘点 |

> 8088 实例与 8086 联调实例同用 `inventory_test`，`SHAREHUB` 业主（`OWN202610290849200000872`）、档案 v2 与凭证都已就绪，powerbank 的凭证在 8088 上已验证可用。

## 四、调用约定

| 约定 | 内容 |
|---|---|
| 鉴权 | `Authorization: Bearer <appKey>:<appSecret>`；业主由凭证决定 |
| 操作人 | `X-Inventory-Actor: STAFF:<工号>`，后台任务为 `SYSTEM`（库存服务记入审计与事件信封） |
| 幂等 | 写请求带 `Idempotency-Key`（≤ 64 字符）：同键同参返回原结果，同键异参冲突。物料单据 / 处置出库的键由本地单号派生（如 `md-out-<单号>`），失败后可原样重试 |
| 错误 | 库存服务返回 `{code, message, data.args}`。宿主经 `InventoryCalls` 统一转成 409 `error.inventory.remote`，并带上对方码与参数；**本地事务同时回滚** |
| 超时 | 连接 2s、读 5s，超时按失败处理（本地回滚） |
| 客户端 | `InventoryApi`（接口）/ `HttpInventoryApi`（HTTP）/ 测试用 `InventoryFake`（内存，按库存服务规则强制） |

## 五、主数据映射

映射存在 powerbank 的 `inventory_sync_state` 表（键值），由 `InventoryLinks` 维护：首次用到时按名称认领或新建，之后直接读。

| 键 | 值 | 说明 |
|---|---|---|
| `wh:<本地仓号>` | 库存服务 `locationId` | 先按仓名认领已有仓，没有再 `POST /warehouses` |
| `item:CABINET` / `item:POWERBANK` | `itemId` | 柜、宝：序列号管理，入库须 `QC` 放行凭证 |
| `mat:<物料号>` | `itemId` | 物料（V210）：`PUT /items/by-ref/<物料号>`，gatePolicy `NONE`；跟踪方式与单位按物料档案 |
| `claim:<设备号>` | 领取单号 | 出库池签收后记下，释放时用 |
| `count:<本地盘点号>` | 库存服务盘点号 | |
| `mig:<类型>:<设备号>` | `IN` / `OUT` / `SKIP` | 存量迁移进度 |
| `xfer:<调拨单号>` | 调出单号 | 设备调拨发货时在库存服务调出后记下；签收时没有它 = 发货时还是 LOCAL 引擎，不同步 |
| `events:seq` | 已确认的事件游标 | |

去向（外部目标）用 `PUT /external-targets/<类型>/<编号>` 同步，出库前保证存在：商家、站点（带上级商家）、接收人、供应商。

## 六、业务动作对照

| powerbank 动作（运营端位置） | 库存服务调用 | 规则要点 |
|---|---|---|
| 入库单 · 质检合格入库（库存管理 › 入库单） | `POST /inbounds`（`PURCHASE`；撤机回仓为 `RETURN`）→ `/post`；回仓再 `/business-clearance` | 序列号行带 `gateRef = 质检记录号`；凭证一次性 |
| 期初建账入库 | 同上，`gateRef = OPEN-<设备号>` | 存量免检，与迁移的 `MIG-` 同口径 |
| 出库给商家（库存管理 › 出库单） | `POST /outbounds`（`ISSUE`，targets MERCHANT / SITE / PERSON）→ `/post`；不指定接收人时当场 `POST /dispatch-pool/claims` | 进出库池 |
| 接收人签收 / 释放 | `POST /dispatch-pool/claims`、`/claims/<号>/release` | |
| 出库调整 / 撤回 / 退回仓库 | `POST /dispatch-pool/<id>/redirect`、`/revoke`；退回走 `RETURN` 入库 | 只有待签收的能调整、撤回 |
| 处置出库 · 报废 / 退供应商（库存管理 › 处置出库） | `POST /outbounds`（`SCRAP` + `reasonCode`；`RETURN_SUPPLIER` + `targets.SUPPLIER`）→ `/post` | 与本地报废同事务，库存服务拒绝即整单回滚（V210） |
| 库存调拨 · 仓到仓（库存管理 › 库存调拨） | 发货 `POST /outbounds`（`TRANSFER_OUT`）→ `/post`；签收 `POST /inbounds`（`TRANSFER_IN`，只含实收的件）→ `/post` | `gateRef = XFER-<调拨单号>-<设备号>`；少收的留在已调出，与本地资产差异同口径；撤机回仓不走这里；调出方 / 目的不是仓的一侧不记；切引擎前发出的单签收时不同步，以盘点纠正 |
| 物料单据（库存管理 › 物料单据） | 入库 → `/inbounds`（`PURCHASE` / `OPENING` / `RETURN`）；出库 → `/outbounds`（`REQUISITION` / `SCRAP` / `RETURN_SUPPLIER`，数量行 + 序列号）；调拨 → `TRANSFER_OUT` + `TRANSFER_IN` | 出库前按 `balances` / `serials` 预检，一次列全（V210） |
| 物料库存 | `GET /balances`、`GET /serials` | 按 `wh:` / `mat:` 映射回本地仓与物料 |
| 盘点（库存管理 › 盘点） | `POST /counts` → `/scans` → `/submit` → `/approve` 或 `/reject` → `/post` / `/cancel` | 复核人 ≠ 提交人；只在 SERVICE 引擎 |
| 库存流水 | `GET /ledger` | |
| 期间汇总 / 库存报表 | `GET /reports/period-summary` | LOCAL 引擎下由本地履历倒推 |
| 存量迁移（仓库页「迁移到独立进销存」） | 在仓 → `PURCHASE` 入库（gateRef = 最近质检号或 `MIG-`）；在商家出库池 → 入库后 `ISSUE` 出库并签收 | 分批、可重跑、逐台独立 |

**不走库存服务的**：绑定 / 解绑、装机、上线、撤机、换站点、整站换商家等。它们只改业务状态，库存服务签收后不再跟踪。

## 七、事件（库存服务 → powerbank）

- **拉取**：任务 `inventory-event-pull` 每分钟一次，`GET /events?afterSeq=<游标>&limit=<条数>`，处理完 `POST /event-acks`。只在 SERVICE 引擎下运行。手动触发：`POST /internal/job/inventory-event-pull/trigger`。
- **去重**：事件按 `event_id` 落 `inventory_inbox`，至少一次投递下重复事件只处理一次；投影失败记 `FAILED` 和 ERROR 日志，等人工核对。
- **投影**：`DispatchRedirected` / `DispatchRevoked` 回写本地设备的出库商家、站点、接收人（处理在库存服务侧直接改出库池的情况）。

## 八、上线步骤（LOCAL → SERVICE）

1. **库存服务就绪**：`/actuator/health` 为 UP，`/actuator/info` 的允许系统含 `SHAREHUB`。
2. **开通**：开业主、写档案、发凭证（第三节）。环境已开过的只跑 `profile.sh` 更新档案。
3. **配置 powerbank**：`sharehub.inventory.base-url / app-key / app-secret`，重启后端；`GET /api/ops/inventory/engine` 返回 `configured=true`。
4. **试跑迁移**（仓库页「迁移到独立进销存」）：看待入库 / 待出库 / 跳过清单；跳过原因逐条处理（多是「在到仓待检」，入库后再迁）。
5. **执行迁移**：分批（每批 ≤ 200 台），失败的按错误码处理后重跑，重跑不重复。
6. **切引擎**：库存设置 › 库存引擎 = `SERVICE`。
7. **核对**：库存余额与库存服务 `balances` 一致；出库池、在途、期间汇总抽查；跑一遍联调脚本。
8. **回滚**：库存引擎改回 `LOCAL` 即可，本地设备表一直在维护。切换期间库存服务里产生的账，回滚后不会自动反写。

## 九、一致性与故障处理

| 场景 | 处理 |
|---|---|
| 库存服务拒绝（4xx 业务错误） | 本地整单回滚，界面显示对方错误码；按码处理后重试 |
| 超时 / 网络错误 | 同上。同一幂等键重试安全；跨请求的重复操作由本地状态机拦截 |
| 物料调拨出库已过账、入库失败 | 库存服务里东西「已出未入」；记 ERROR（含单号与幂等键 `md-in-<单号>`），在库存服务按原键补入库 |
| 出库池找不到记录（`error.inventory.dispatch_missing`） | 本地与库存服务出库池不一致：查 `inventory_inbox` 是否有失败投影，在库存服务核对后修正本地 |
| 已领取但本地无领取单号（`error.inventory.claim_unknown`） | 在库存服务侧释放 |
| 事件投影失败（`inventory_inbox.FAILED`） | ERROR 日志带 eventId；人工核对后重放 |
| 盘点进行中 | 库存服务冻结该仓相关过账，宿主侧动作会收到冲突，盘点过账后再做 |

## 十二、业务系统怎么调库存服务（统一服务封装）

### 12.1 三层封装

```
业务代码（入库单、出库单、处置、物料、盘点、报表、迁移、事件任务）
   │  只依赖下面两个接口之一
   ├─ InventoryPort ……… 库存「业务动作」：inbound / dispatch / claim / redirect / returnToWarehouse
   │     LocalInventoryPort（改本地设备表） ┐ InventoryEngineRouter 按系统参数 inv.engine 选
   │     RemoteInventoryPort（本地 + 库存服务）┘
   └─ InventoryApi …………… 库存服务 v1 契约的强类型客户端（29 个方法，见 12.2）——「统一的库存服务」
         HttpInventoryApi（HTTP 实现）
            └─ InventoryEndpoint ……… 寻址：本次调用打哪个地址
                  StaticInventoryEndpoint（默认，sharehub.inventory.base-url）
                  ＜服务发现实现＞（Nacos / Consul / k8s，可选模块提供，见 12.4）
```

- **业务代码不知道库存服务在哪、走什么协议**：只调 `InventoryPort` / `InventoryApi`。
- **换寻址**（固定地址 → Nacos）只换 `InventoryEndpoint` 的实现，HTTP 客户端与业务代码一行不动。
- **换协议**（HTTP → Dubbo / gRPC）就再写一个 `InventoryApi` 实现。契约（方法、入参出参、错误码）不变，`InventoryFake` 照样能测。
- 鉴权、操作人、幂等键、错误转换都在 `HttpInventoryApi` 一处，业务代码不碰 HTTP 细节。

### 12.2 需要库存服务提供的接口清单（`/api/inventory/v1`）

| 分组 | 库存服务接口 | `InventoryApi` 方法 | 用途 |
|---|---|---|---|
| 主数据 | `PUT /items/by-ref/{ref}` | `upsertItem` | 柜、宝、物料登记为库存物料 |
| | `PUT /external-targets/{type}/{ref}` | `upsertTarget` | 商家、站点、接收人、供应商 |
| | `GET /warehouses`、`POST /warehouses` | `warehouses`、`createWarehouse` | 本地仓认领 / 新建 |
| 入库 | `POST /inbounds`、`POST /inbounds/{no}/post` | `createInbound`、`postInbound` | 采购、期初、退回、调拨入 |
| | `POST /inbounds/{no}/business-clearance` | `businessClearance` | 退货入库后解冻 |
| 出库 | `POST /outbounds`、`POST /outbounds/{no}/post` | `createOutbound`、`postOutbound` | 发货、报废、领用、退供应商、调拨出 |
| 出库池 | `GET /dispatch-pool?serialNo=` | `dispatchesBySerial` | 查一台设备的出库池记录 |
| | `POST /dispatch-pool/claims`、`/claims/{no}/release` | `claim`、`releaseClaim` | 签收 / 释放 |
| | `POST /dispatch-pool/{id}/redirect`、`/revoke` | `redirect`、`revoke` | 出库调整 / 撤回 |

管理端（`/api/inventory/admin/v1/owners`：开业主、档案、凭证）**不在业务调用里**，只在开通与运维时用（第三节脚本）。

### 12.4 接入服务发现（Nacos 等）

现在默认是固定地址（v4 §8.1：不引服务发现中间件）。要接 Nacos 时：

1. **库存服务侧**：服务名注册到 Nacos，如 `inventory-svc`。
2. **powerbank 侧**：新建可选模块（如 `sharehub-integration-discovery`），依赖 Spring Cloud Alibaba Nacos Discovery，提供一个 `InventoryEndpoint` Bean。默认的 `StaticInventoryEndpoint` 因 `@ConditionalOnMissingBean` 自动退让：

   ```java
   @Bean
   InventoryEndpoint discoveryInventoryEndpoint(DiscoveryClient discovery,
                                                @Value("${sharehub.inventory.service-id}") String serviceId) {
       return new InventoryEndpoint() {
           private final AtomicInteger next = new AtomicInteger();
           public String mode() { return "DISCOVERY"; }
           public boolean configured() { return !discovery.getInstances(serviceId).isEmpty(); }
           public String baseUrl() {
               List<ServiceInstance> xs = discovery.getInstances(serviceId);
               if (xs.isEmpty()) throw new InventoryRemoteException(503, "inventory.unreachable", List.of(serviceId), "无可用实例", null);
               return xs.get(Math.floorMod(next.getAndIncrement(), xs.size())).getUri().toString();
           }
       };
   }
   ```

3. **配置**：`sharehub.inventory.service-id=inventory-svc` 取代 `base-url`。凭证（`app-key / app-secret`）、幂等键、错误转换不变。
4. **不变的**：业务代码、`HttpInventoryApi`、`InventoryFake` 与所有测试。

要用 Spring Cloud LoadBalancer、Consul、k8s Service DNS 时同理：只换 `InventoryEndpoint`。k8s Service DNS 甚至不用换，`base-url` 直接写服务名即可。

## 十三、运营端页面怎么调库存服务

### 13.1 结论：继续由 powerbank 后端中转（portal 层控制器），不直连、不加网关进程

运营端（ops-web）**只调 powerbank 的 `/api/ops/**`**，由 powerbank 的控制器（`InventoryController`、`DevicePoolController`、`ReportController` 等）转到 `InventoryPort` / `InventoryApi`，现在就是这么做的。

| 方案 | 做法 | 结论 |
|---|---|---|
| **A. powerbank 控制器中转**（现状） | ops-web → `/api/ops/inventory/**` → 本地服务 → `InventoryApi` → 库存服务 | **采用** |
| B. API 网关统一鉴权、透传 | ops-web → 网关（如 Spring Cloud Gateway）→ 库存服务 | 不采用 |
| C. 浏览器直连库存服务 | ops-web 直接带凭证调 8088 | 不采用 |

### 13.2 为什么不用网关透传（B）

1. **权限判不了**：库存服务只认系统凭证、不认人。员工的功能权限（`device:inventory:*`）和数据范围（商家只看自己的站点设备）在 powerbank 里。网关要判这些，就得把 RBAC 与业务数据搬过去，等于再造一个 powerbank。
2. **编号对不上**：运营端用本地仓号、物料号、设备号、商家号；库存服务用 `locationId`、`itemId`、`dispatchId`。映射在 powerbank 的 `inventory_sync_state` 里，网关做不了。
3. **动作是组合的**：一次「出库给商家」要先同步商家 / 站点 / 接收人，再出库、过账、按需签收，同时改本地设备状态，并保证同一事务、库存服务拒绝即回滚。这是业务编排，不是转发。
4. **凭证不能出后端**：`app-secret` 只在 powerbank 后端；透传就得让网关持有它，并把用户令牌换成系统凭证。
5. **契约要一致**：运营端约定统一的 `Result{code,message,data}`、camelCase、`xxxNo`、三语错误文案，库存服务的错误模型不同，中转层负责转换。
6. **架构已定**：技术架构方案 v4 §3.3 不建独立网关或 BFF 进程，portal 层就是 BFF；ops-web 只用既有 6 个前缀。

网关以后可以放在 nginx 这一层做 TLS、限流、按前缀分流，但它不替代 powerbank 的控制器。

### 13.3 新增库存功能时的做法

1. 在 `InventoryApi` 加方法；`HttpInventoryApi` 和 `InventoryFake` 各实现一次（对应 12.2 加一行）。
2. 在本地服务里编排：权限、数据范围、编号映射、本地状态、同事务回滚。
3. 在 `InventoryController`（`/api/ops/inventory/**`）暴露给运营端，判 `device:inventory:*` 权限码（对应 12.3 加一行）。
4. ops-web 走 `lib/api` 的契约，经漂移卡口与后端对齐。

### 13.4 库存服务自己的「运营端口」能不能保留

可以保留，但**不给 ShareHub 运营端用**：

| 库存服务接口 | 谁用 | 怎么保护 |
|---|---|---|
| `/api/inventory/v1/**`（业务接口） | 只有 powerbank 后端 | 系统凭证；内网或 `/etc/hosts` 名访问，不对公网 |
| `/api/inventory/admin/v1/**`（管理端） | 平台管理员开通、改档案、发凭证、对账 | 管理令牌；只在运维网络可达 |
| ai-shop 商家端 / 运营端控制器（在 shop-app，不在独立服务） | ai-shop 自己的界面 | 商城登录体系；与 ShareHub 无关 |

以后如果要给仓管一个「库存服务原生控制台」，应作为独立应用部署在内网，有自己的登录，**不要嵌进 ops-web**：一个页面背后两套权限，迟早有人看到不该看的数据。
