## 先读：为什么这类漂移看不见

菜单/按钮可见性走 `can(perms, code)`（ops-web），接口鉴权走 `@PreAuthorize`（后端），
**两边各查各的码，没有任何东西要求它们一致**。表现只有两种，都不报错：

- **看得见点不开** —— 界面码有、接口码没有 → 403
- **能用但找不到** —— 接口放行、界面把按钮藏了（本批 5 条多属此类）

现在有卡口盯着了（`check-perm-parity` + `perm-ssot-align.py` + `MenuPermissionContractTest`），
但**修不修、怎么修仍要人判断**。

## T-1 `agent:settlement:read` —— 待产品裁决（**勿擅自动**）

已登记在 [`backend/known-menu-perm-mismatch.txt`](../../backend/known-menu-perm-mismatch.txt)，
那里写明了原委：「我的结算」与「代理收益结算」挂 `agent:settlement:read`，
而 `/api/trade/settlements` 挂 `finance:settlement:read`，AGENT 不持有后者。

权限清单 §末 第 2 条给了二选一：

- **(a)** 把 `agent:settlement:read` 挂到结算端点的代理视图（新增一个代理作用域端点）
- **(b)** 让 AGENT 持 `finance:settlement:read`，靠 ADR-012 的数据范围限定到自己 `agent_no`

(b) 更省，但**它给外部伙伴角色发了一个 `finance:*` 的码** —— 这是产品/安全决定，不是技术选择。

**需要谁定**：产品 + 安全。定完再动，别只改一半。

## T-2 `pricing:adjustment:create` / `:cancel` —— 需三处原子改（**勿只改一处**）

同族的 `pricing:adjustment:read` 已在 `known-menu-perm-mismatch.txt` 里，写明：

> 权限清单声明 `pricing:adjustment:read`/`:create`/`:cancel`（FIN ✓），
> 而端点挂的是 `pricing:rule:read` / `:config`，且**零个角色持有 adjustment 码**
> （ADMIN 是 `*` 通配所以只有 ADMIN 看得见这个菜单）。

**完整修法要同时改三处**：端点码 + `RolePerms.java` 授予 + 菜单码保持不变。

⚠️ **只改端点码 = 谁都调不了**（没人持有该码）。这是本批唯一一条真的会把功能改坏的。

**动哪些文件**
- 端点：搜 `pricing:rule:config` 的 `@PreAuthorize`
- 授予：`backend/.../platform/iam/RolePerms.java` 的 `FINANCE` 列表
  （注意：FIN 已有 `pricing:*` 通配 —— **先确认通配是否已覆盖**，覆盖了就不用加，
  2026-09-24 有人在别处因为用字面 grep 漏看通配而误判过）

**验收**：FIN 能调预约调价的建/撤；菜单入口仍在；`npm run check:drift` 绿。

## T-3 `device:ota:publish` —— 端点形状与真源表粒度对不上

**真源表**：`| OTA 查 / 发布 / 回滚 | device:ota:read / :publish / :rollback | OPS ✓ | … | VIEW ✓(查) |`

**后端现状**（`DeviceController`）：

| 端点 | 现挂 | 清单该给 |
|---|---|---|
| `GET /api/ops/ota-releases` | `device:ota:manage` | `:read` |
| `POST /api/ops/ota-releases` | `device:ota:manage` | `:publish` |
| `POST /api/ops/ota-rollouts` | `device:ota:manage` | `:publish` |
| `POST /api/ops/ota-rollouts/{no}` | `device:ota:manage` | **`:publish` 还是 `:rollback`？** |
| `GET /api/ops/ota-rollouts/{no}/tasks` | `device:ota:read` | ✓ 已对 |

**卡在哪**：`updateOtaRollout` 的注释是「更新投放（灰度比例调整、**回滚 `status=ROLLBACK`**）」——
**一个端点同时干发布和回滚**，而清单要拆成两个码。改注解解决不了，要么拆端点、要么接受偏离。

**两条路**
- **(a) 拆端点**：把回滚独立成 `POST /ota-rollouts/{no}/rollback`，两个端点各挂各的码。更贴清单，改动大。
- **(b) 不拆**：该端点统一判 `:publish`，并在 `known-perm-ssot-gaps.txt` 登记
  「`device:ota:rollback` 声明未强制」并注明原因。

**⚠️ 还有一个独立的访问面变化**：`GET /ota-releases` 改判 `:read` 后，清单说 VIEW 有「查」，
但 `RolePerms.java` 的 `VIEWER` **一个 `device:ota` 码都没有**。要真给 VIEW 看，
得同时给 VIEWER 加 `device:ota:read` —— **那是真的放宽访问面**，不是命名对齐，要单独确认。

**验收**：OPS 能发布与回滚；若给了 VIEW，VIEWER 能查、不能发布；`check:drift` 绿。

## T-4 `system:region:update` —— 粒度是产品决定

**现状**：后端把地区维护挂在 `system:dict:update` 下
（`POST /api/platform/regions` 与 `/{regionId}`），而界面用 `system:region:update` 判权。
真源表里**也没有** `system:region:update` 这个码（只有 `system:region:read`）。

**两条路**
- **(a) 界面映射到 `system:dict:update`**（改 `ops-web/lib/perm-map.ts` 一行）。
  立刻生效、不动后端。代价：接受「地区归字典管」——有字典编辑权的人也能改地区库。
- **(b) 后端给地区单独加闸** `system:region:update`，并补进真源表 + `RolePerms` 授予。
  粒度更对，但是三处改动（同 T-2 的坑：只改端点码 = 谁都调不了）。

**当前状态是「谁都改不了」**（除 ADMIN），所以 (a) 至少让界面与后端一致。
粒度问题可以单独排期。

**需要谁定**：产品（地区库该由谁维护）。

## T-5 前端既有不一致：员工「新增」按钮判错码（**不紧急，但会咬人**）

`ops-web/app/employees/page.tsx:343-344` 的 `canEditDept` / `canEditEmp` 都用
`org:employee:update` 判权，而**新增端点 `POST /api/platform/employees` 要的是 `:create`**。

现在两码都只有 ADMIN 持有，所以看不出来。**一旦把 `:update` 授予某个角色，
该角色会看见「新增」按钮、点下去 403** —— 正是本文开头说的「看得见点不开」。

**怎么改**：新增按钮改判 `org:employee:create`，编辑按钮保持 `:update`。

**什么时候改**：员工权限真正下放给非 ADMIN 角色时，一并做。现在改等于替一个
还没发生的授权做决定。
