# 经营链条方案 · 从运营方到分账

> 2026-09-23 · 把 [领域模型](./领域模型-本体与关系.md) 这条主干**落到库与菜单上**：
> 运营方 → 代理商 → 品牌 → 设备类型 → 站点 → 计费方案 → 调价 → 分成。
>
> **本文只做三件事**：①每一环说清「它是什么、靠什么表达」；②对着**实测库**标出差距；
> ③把差距翻译成菜单动作。不重复领域模型已经讲清的本体定义。
>
> 实测基准：本机 `pb_core`（与生产同源，迁移到 V44）。

---

## 零、一句话串起来

```
运营方（唯一，隐含单例）
  ├─ 拥有 品牌 ──────────────▶ 站点以某个品牌对 C 端呈现
  ├─ 招募 代理商 ─出资/运维──▶ 站点（agent_no，可划拨可收回）
  └─ 登记 设备类型 ──────────▶ 设备（放在站点的点位上）
                                  │
场地方 ─提供场地 + 签进场合同──▶ 站点
                                  │
                        一笔订单落在一台设备上
                                  │
                    计费方案（按适用范围选中恰好一个）
                          × 调价（到点改价、到期改回）
                                  │
                        分成：场地方按合同 · 代理商按规则
                                  │
                    分润明细 → 结算单 → 提现
```

**两个贯穿全链的原则**（领域模型 §2.2 / §2.3，本文不再重复论证）：

- **站点上是两个正交归属**：`venue_no`（谁的地盘，拿进场分成）与 `agent_no`（谁出的钱和人，拿代理分润）。两者都是**关联**，不是所有权。
- **单据落快照**：订单上的归属与费率、分润上的比例与来源，都在成单那一刻定格。用今天的归属去推历史订单的结算方，是财务事故。

## 一、逐环：定义 · 库 · 差距

### 1. 运营方 Operator

| | |
|---|---|
| 是什么 | 唯一的平台拥有者。**不是一张表**，是隐含单例（ADR-026 取消租户概念） |
| 库 | 无。各表的 `tenant_id` 恒为 `MAIN`，是历史常量不是概念 |
| 差距 | **无**。产品层已经不存在「租户」，不需要任何菜单 |

> 唯一要守住的是：不要因为看到 `tenant_id` 就以为还能多租户。它不做任何隔离。

### 2. 代理商 Agent

| | |
|---|---|
| 是什么 | 运营方**体内**的分润伙伴：出钱买设备、包一片区域铺设与运维。用运营方品牌，C 端无感知 |
| 库 | `agt_agent`（档案）· `agt_account`（登录）· `agt_agent_region`（辖域）· `agt_assignment`（划拨留痕） |
| 现状 | 档案 / 账号 / 划拨 / 分润配置 / 绩效五页齐，数据范围 `AGENT` 生效 |

**差距 A1 —— 没有「类型」**：ADR-027 定了两个名字（`AGENT` 代理商 / `CITY_PARTNER` 城市合伙人），
而 `agt_agent` **没有 `agent_type` 列**（实测）。今天所有伙伴在系统里长得一模一样。

**差距 A2 —— 一个站点只能有一个伙伴、一种责任**：`loc_site.agent_no` 是单列，
`loc_site_partner` 表**不存在**（实测）。现实里「A 出资、B 牵线」表达不了，
而出资、拓展、运维、牵线的钱本来就是四回事。

**已修（2026-09-23）**：`agt_agent.share_rate` 影子列。实体字段 `shareRate` 按驼峰推导成
`share_rate`，而真列是 V1 就有的 `default_share_rate` —— 曾据此补过一列，
结果新值写进影子列、真列恒 0，界面显示正常而读真列的地方全拿到 0。
V44 已搬回数据并删列，实体改用 `@TableField("default_share_rate")` 指回真列。

### 3. 品牌 Brand

| | |
|---|---|
| 是什么 | 运营方对 C 端呈现的经营身份：名称 / Logo / App / 客服 / 协议。一个运营方可有多个。**代理商不得拥有**（硬约束） |
| 库 | **不存在**：`md_brand` 表没有，`loc_site.brand_no` 列也没有（实测） |
| 差距 | **整条未落地** —— 这是本链条上唯一一个「连表都还没有」的环 |

**为什么它不是可选项**：站点是「以哪个品牌运营」的，而品牌决定 C 端看到的名字、协议主体、客服入口。
没有它，多品牌经营时**归因是糊的**：订单属于哪个品牌、分成算在哪个品牌账上、C 端协议该显示谁 —— 都答不了。

**为什么现在不做也能跑**：今天只有一个品牌，缺省即唯一，所以没人撞到。
**它会在第二个品牌出现的当天爆**，而那一天通常没有预告。

### 4. 设备类型 DeviceType

| | |
|---|---|
| 是什么 | 设备的种类登记：使用形态（借还 / 会话）、计量、指令族、扩展表（ADR-021） |
| 库 | `md_device_type` **齐全**：`has_movable_item` / `item_table` / `order_ext_table` / `default_metering` / `reservation_target` / `supports_return_elsewhere` / `command_family` |
| 现状 | 登记表在，`DeviceTypeModule` SPI 在。新增一种设备 = 登记一行 + 写一个实现 |

**差距 D1 —— 取价不看设备类型**：`price_rule` **没有 `device_type` 列**（实测）。
站点同时有充电宝和按摩椅时，站点规则会拿充电宝方案给按摩椅计价。
今天只有一种设备所以没炸，**上第二种设备之前必爆**。

### 5. 站点 Site

| | |
|---|---|
| 是什么 | 一个物理经营场所。**归属与分成的单元**：场地方是谁、代理商是谁、在哪个区域、以哪个品牌运营 |
| 库 | `loc_site`（含 `venue_no` / `agent_no` / `region_id` / `lng` / `lat` / `pause_reason`）· `loc_location` · `loc_contract` |
| 现状 | 建档 / 编辑 / 归档 / 暂停恢复营业 / 点位 / 合同 / 经纬度全通；站点详情八页签 |

**差距 S1 —— 缺 `brand_no`**：见第 3 环。
**差距 S2 —— 区域推不出市场与币种**：`md_region` 没有市场 / 国家列，
于是「站点的币种」无法推导，多市场时做不了「方案币种必须与站点相符」的硬过滤。

### 6. 计费方案 PricePlan

| | |
|---|---|
| 是什么 | 免费时长 / 单价 / 阶梯 / 封顶 / 买断。一笔订单必须从所有可能适用的方案里**选出恰好一个** |
| 库 | `price_plan` · `price_plan_item` · `price_ladder` · `price_plan_scope` · `price_rule` · `price_schedule` |
| 现状 | 方案 CRUD、启停、试算、命中站点在运营端可用；取价引擎按 `(deviceType, siteNo, sceneType)` 选方案 |

**差距 P1 —— 两套机制表达同一件事**：
`price_plan_scope`（适用范围）实测只有 `scope_type` / `scope_ref` 两列，**且取价引擎不读它**；
真正生效的是另一个菜单「差异化定价」背后的 `price_rule`。
运营在方案上勾了「适用站点」，引擎不认 —— 配置了不生效，比没有这个功能更糟。

**差距 P2 —— 适用范围维度不够**：用户点名的「不同品牌的设备、不同代理商、不同站点」
在 `price_plan_scope` 里一个都表达不了。ADR-028 定的目标形状是：

```
price_plan_scope(plan_no, device_type, level, ref, vendor_code, model, brand_no,
                 priority, effective_from, effective_to)
level: DEVICE > LOCATION > SITE > VENUE > AGENT > SCENE > REGION > ALL
uk (device_type, level, ref, vendor_code, model, brand_no)   同一范围只能有一个启用中的方案
```

**差距 P3 —— 时段倍率配置了不生效**：`ChargeChain.charge(gross, multiplier, …)` 收倍率，
但**没有任何调用方**从 `price_schedule` 算出倍率传进来。菜单能存能改，订单一分钱不多收。

### 7. 调价 PriceAdjustment

| | |
|---|---|
| 是什么 | 到点自动改价、到期自动改回（节假日上调、活动期降价） |
| 库 | `price_adjustment`（V40）：`patch` / `before_snapshot` / `effective_at` / `revert_at` / 状态机 |
| 现状 | **本环已完整**（2026-09-23 上线）：新建 / 撤销 / 提前恢复 / 重试；执行器由系统 cron 每分钟调，列表打开也会顺带执行 |

两条已经钉进用例的规矩：**恢复靠生效那刻的快照**；**恢复前先核对**方案是否仍是调价写进去的值，
被人手工改过就置 FAILED 不恢复 —— 悄悄覆盖别人的改动比不恢复更难查。

### 8. 分成 Sharing

| | |
|---|---|
| 是什么 | 一笔订单结算后，按约定把钱分给场地方与代理商 |
| 库 | `loc_contract`（场地方费率）· `share_rule`（代理费率）· `share_record`（逐单明细，含 `rate` / `source_no` 快照）· `stl_settlement` · `stl_withdrawal` · `acct_*` |
| 现状 | **链路已打通**（2026-09-23）：`OrderSettledEvent` → `ShareGenerator`；V37 幂等键防重投记两遍 |

**口径已定（D2）**：场地方以**进场合同**为准（按站点签、签过字的那份），无生效合同才回落分润规则；
代理商只看 `share_rule(AGENT, agentNo)`。费率来源写进 `share_record.source_no`，
排错时「这笔为什么是 20%」当场能答。

**差距 F1 —— 分成不分责任**：接第 2 环的 A2。今天一个代理商在一个站点只能拿一个比例，
而出资、拓展、运维、牵线本该各算各的。ADR-027 的目标是按 `loc_site_partner(site_no, partner_no, role)`
**分条生成**分润记录。

## 二、差距汇总与优先级

判据：**「今天就错」＞「上第二种设备/品牌就错」＞「结构不够但今天不错」**。

| # | 差距 | 性质 | 什么时候会咬人 | 建议 |
|---|---|---|---|---|
| **P1** | 适用范围写了没人读，两套机制并存 | **今天就错**：配了不生效 | 已经在发生 | **最先做**。取价引擎改读 `price_plan_scope`，`price_rule` 迁移后退役 |
| **P3** | 时段倍率不生效 | **今天就错**：能存不收钱 | 已经在发生 | 与 P1 同批，倍率接进 `ChargeChain` |
| **D1** | 取价不看设备类型 | 上第二种设备就错 | L2 按摩椅 | 与 P1 同批（`price_plan_scope.device_type` 必填） |
| **P2** | 适用范围缺品牌 / 厂商 / 型号 / 代理维度 | 结构不够 | 多品牌或多厂商混投时 | 随 P1 一次做到位，事后补等于再迁一次 |
| **B1** | 品牌整条未落地（无表无列） | 结构缺失 | 第二个品牌出现当天 | 建 `md_brand` + `loc_site.brand_no`，**先建表再谈菜单** |
| **A1** | 代理商没有类型 | 结构不够 | 有城市合伙人时 | 一列枚举 + 档案上一个字段，成本极低 |
| **A2/F1** | 站点上只能一个伙伴一种责任 | 结构不够 | 「A 出资 B 牵线」出现时 | `loc_site_partner` + 分润按责任分条，**改动最大，放在 P1 之后** |
| **S2** | 区域推不出市场与币种 | 结构不够 | 第二个市场开城时 | `md_region` 补市场列 |

## 三、菜单该怎么动

原则：**先有模型与库，再谈菜单**。以下每条都标注它依赖哪个差距 —— 差距没填，菜单加了也是空壳。

### 3.1 现有菜单里改的（不新增入口）

| 菜单 | 动作 | 依赖 |
|---|---|---|
| 计费定价 › **计费模板** | 「适用范围」从展示字段变成**真正生效**的配置：设备类型（必填）+ 层级 + 厂商 / 型号 / 品牌过滤 | P1 · P2 · D1 |
| 计费定价 › **差异化定价** | **整页下线**，内容并入「计费模板」的适用范围 | P1 |
| 计费定价 › **活动/时段价** | 保留，但要让它真的影响金额；页面上补「这条倍率影响哪些方案」 | P3 |
| 代理商管理 › **代理商档案** | 档案加「类型」字段（代理商 / 城市合伙人），列表加类型列与筛选 | A1 |
| 站点与点位 › **站点管理**（及运营管理 › 站点管理） | 站点详情加「品牌」字段；「合作伙伴」页签列出本站点的伙伴 × 责任 | B1 · A2 |
| 财务管理 › **分润规则** | 规则维度从「分成方」扩到「分成方 × 责任」 | F1 |
| 财务管理 › **分润明细** | 明细列出「按什么责任分的」 | F1 |

### 3.2 需要新增的入口（**只有一个**）

| 菜单 | 位置 | 理由 |
|---|---|---|
| **品牌管理** | 系统设置 › 基础字典（与「银行管理」「问题管理」同级） | 品牌是运营方的一等对象，但**低频维护**（一个运营方通常一两个品牌），放基础字典而不是单开一级菜单 |

**刻意不新增的**：

| 想加的 | 为什么不加 |
|---|---|
| 「城市合伙人」独立菜单 | 它不是第二个实体，是 `agt_agent` 上的一个枚举值。分润、结算、提现、门户全部复用同一套。单开菜单会让人以为是两套数据 |
| 「设备类型管理」 | `md_device_type` 是**开发期登记**（新增一种设备要同时写一个 SPI 实现），不是运营可配的东西。给它一个菜单，等于邀请运营去点一个点了会坏的按钮 |
| 「合作伙伴责任」独立菜单 | 责任是**站点上的一行**，属于站点详情的一个页签。单开菜单就要先选站点，多一次跳转换不来任何信息 |
| 「运营方设置」 | 运营方是隐含单例，没有可管理的属性。真要配的（品牌、税率、市场）都已各有归属 |

### 3.3 落地顺序

```
第一步（今天就错的）        P1 + P3 + D1 + P2 一批做
        └ 取价引擎改读 price_plan_scope（带 device_type / 厂商 / 型号 / 品牌 / 有效期）
        └ price_rule 数据迁移 → 退役 → 「差异化定价」菜单下线
        └ 时段倍率接进 ChargeChain
第二步（结构缺失）          B1 品牌建表 + 站点挂品牌 + 系统设置加「品牌管理」
        └ 注意：品牌要先于「适用范围的 brand_no 真正可用」，否则那一维是空的
第三步（结构不够）          A1 代理商类型（一列 + 一个字段）
第四步（改动最大）          A2 / F1 站点合作伙伴 × 责任 + 分润按责任分条
第五步（第二个市场再说）    S2 区域补市场与币种
```

> **为什么品牌排在第二而不是第一**：它今天不错，但它是 `price_plan_scope.brand_no`
> 这一维的前提。第一步把维度留好、第二步把数据填上，比反过来少迁一次。

## 四、这份方案没有回答的

| 问题 | 为什么留着 |
|---|---|
| 一个站点能不能同时挂两个品牌 | 领域模型 §2.4 倾向「一站一品牌」硬约束（避免归因歧义），但未定案。**做品牌表时必须先定** —— 它决定 `brand_no` 是站点上的一列还是一张关系表 |
| 责任类型的完整清单 | ADR-027 给了出资 / 拓展 / 运维 / 效果管理 / 牵线五种，但没定各自的分润口径（固定比例？按贡献？）。**分润按责任分条之前必须定** |
| 平台净收入要不要单独记一条分润 | 今天不记（`1 - 各方合计` 隐含）。多品牌 / 多责任之后，对账时可能需要显式记录 |
