# 前端接入指引 · 动态菜单 / 权限（ops-web）

> 状态：契约已冻结 · 后端已实现并测过（2026-07-13）· 面向 ops-web 前端同学，可自助接入。
> 关联：[运营端权限-动态配置实现步骤.md](./运营端权限-动态配置实现步骤.md) · [运营端权限方案.md](./运营端权限方案.md)。
> **接入时机：不急（见 §1 YAGNI）。当前请勿改导航组件——按 §3「只加不改 + 静态兜底 + 开关灰度」低冲突接入。**

---

## 1. 先判断要不要现在做（YAGNI）

- 现在的 `lib/nav.ts`（静态菜单）+ `lib/permissions.ts`（`ROLE_PERMS`）**镜像后端 RolePerms，工作正常**。
- 动态化的**唯一增量价值** = 后台建**自定义角色**/改菜单后，**不发版即生效**。
- 因此：**只有当真的开始用自定义角色时才需要接入**。近期不建自定义角色 → 保持静态即可，别加负担。

---

## 2. 后端契约（已冻结，可直接对着写/mock）

响应统一包 `{code,msg,data}`（`0`=成功）；ops-web 的 `client.get/post` 会自动拆包返回 `data`。

### 2.1 登录（已有，形状不变）
`POST /api/auth/login  { username, role, agentNo? }`
```jsonc
{ "code":0,"msg":"ok","data":{
  "token":"stk_xxx","username":"boss","role":"ADMIN","agentNo":"",
  "perms":["dashboard:overview:read","device:cabinet:*", "..."]   // 也可直接用这个，省一次请求
}}
```

### 2.2 当前登录人权限码（前端 `can()` 用）
`GET /api/auth/permissions`  （需带 `Authorization: Bearer`）
```jsonc
{ "code":0,"msg":"ok","data":["dashboard:overview:read","device:cabinet:*","location:poi:read", "..."] }
```

### 2.3 当前登录人可见菜单树（已按权限过滤，前端直接渲染）
`GET /api/auth/menus`
```jsonc
{ "code":0,"msg":"ok","data":[
  { "menuNo":"M_dashboard","parentNo":null,"name":"经营看板","nameAr":null,
    "type":"MENU","path":"/","icon":"LayoutDashboard","sort":1,"perm":"dashboard:overview:read","children":[] },
  { "menuNo":"M_device","parentNo":null,"name":"设备管理","nameAr":null,
    "type":"MENU","path":"/devices","icon":"Server","sort":2,"perm":"device:cabinet:read","children":[] }
]}
```
字段：`type` ∈ `DIR`/`MENU`；`icon` = lucide 图标**名**（复用现有 name→组件映射）；`children` 递归；后端**已过滤**——前端**无需再按权限筛**，拿到就渲染。

## 3. 接入方式（低冲突：只加不改 + 静态兜底 + 开关灰度）

> 目标：**不重写** `rail`/`secondary-nav`/`nav.ts`，只切"数据源"，且默认走静态、开关打开才走后端。

### 3.1 契约层（新增，不动现有方法）
```ts
// lib/api/contract.ts
export interface MenuNode { menuNo:string; parentNo:string|null; name:string; nameAr:string|null;
  type:"DIR"|"MENU"; path:string|null; icon:string|null; sort:number; perm:string|null; children:MenuNode[]; }
export interface Api {
  // ...现有...
  getPermissions(): Promise<string[]>;
  getMenus(): Promise<MenuNode[]>;
}
// lib/api/http.ts
getPermissions: () => client.get<string[]>("/api/auth/permissions"),
getMenus:       () => client.get<MenuNode[]>("/api/auth/menus"),
// lib/api/mock.ts —— 用现有 nav.ts 生成一棵 mock 树 + 角色 perms，联调不依赖后端
```

### 3.2 状态（登录后拉取，存 store）
```ts
// lib/auth.ts —— 加字段，不改现有
perms: string[];  menus: MenuNode[];
// 登录成功后（api.login 已返回 perms，可直接用；或再拉 getMenus）：
set({ perms: resp.perms, menus: await api.getMenus() });
```

### 3.3 鉴权（`can()` 优先读拉取的 perms，回退静态）
```ts
// lib/permissions.ts
export function can(code:string, dynamicPerms?:string[]): boolean {
  const perms = dynamicPerms ?? ROLE_PERMS[currentRole()] ?? [];   // 有动态用动态，否则回退
  return perms.some(p => p===code || (p.endsWith("*") && code.startsWith(p.slice(0,-1))));
}
```
> 通配语义与后端 `Permissions.matches` **完全一致**（`*` / `device:*` / `device:cabinet:*`），务必保持。

### 3.4 渲染（rail/secondary-nav 换数据源，不改结构）
```ts
// 一个 hook：开关开且拉到 → 用后端菜单；否则回退静态 NAV
const menus = useDynamicNav() ? store.menus : NAV;
```
`rail`/`secondary-nav` 照旧遍历 `menus` 渲染（字段对齐：`path`/`name`/`icon`/`children`）。

### 3.5 开关灰度
`.env`：`NEXT_PUBLIC_DYNAMIC_NAV=0`（默认静态）→ 稳定后置 `1`。可先合"暗代码"，不影响当前功能。

## 4. 验证
- `NEXT_PUBLIC_USE_MOCK=1`：mock 树/perms 直接渲染，纯前端可测。
- 接后端（`USE_MOCK=0` + 后端起）：登录不同角色 → 菜单/按钮随后端增减；后台改自定义角色权限 → 该用户下次登录（或刷新）菜单/按钮即变。
- 保留 `nav.test.ts`：静态兜底路径不回归。
