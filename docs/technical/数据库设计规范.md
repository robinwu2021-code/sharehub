# 数据库设计规范

> 状态：**提议 · 待确认**（2026-09-23）· 参照 [ai-shop](../../../ai-shop) 的 `BaseEntity` / `db-design.md §一` / `全域命名基准.md`，按本项目差异调整
> 配套：[数据库设计 Review](./数据库设计-review-2026-09-23.md)（现状体检）· [领域模型 v2](./领域模型-本体与关系.md)（对象与关系）
>
> **这份文档的目标不是好看，是让「新表该长什么样」只有一个答案。**
> 所以每条规则都配了**判据**（为什么）和**守卫**（谁来拦）。没有守卫的规则会漂移——
> ai-shop 的教训：他们有成文规范但**没有一条闸门检查新表是否带齐标准列**，
> 结果 188 张表里 25 张各有各的样子，最后只能靠人逐张比对。

## 一、标准列（每张表都有）

### 1.1 精确 DDL —— 照抄这一块

位置固定：**业务列之后、索引之前**。

```sql
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  <业务列……>
  tenant_id   VARCHAR(36)  NOT NULL DEFAULT 'MAIN' COMMENT '历史遗留常量，恒 MAIN（ADR-026），新代码不得据此分支',
  created_at  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3)          COMMENT '创建时间(UTC)',
  created_by  VARCHAR(36)       NULL                                     COMMENT '创建人业务键；无登录态写 SYSTEM',
  updated_at  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3) COMMENT '更新时间(UTC)，DB 自动维护',
  updated_by  VARCHAR(36)       NULL                                     COMMENT '更新人业务键',
  version     BIGINT       NOT NULL DEFAULT 0                            COMMENT '乐观锁',
  deleted     TINYINT(1)   NOT NULL DEFAULT 0                            COMMENT '逻辑删除 0/1',
  PRIMARY KEY (id),
  UNIQUE KEY uk_<table>_no (<biz>_no),
  KEY idx_<table>_<语义> (<列>)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='<中文表名>';
```

现状符合度：**五件套齐全 118/149，五列类型 100% 一致**。这份规范主要是**把已有事实写下来并守住**，不是推倒重来。

### 1.2 逐列判据

| 列 | 约定 | 判据 |
|---|---|---|
| `id` | `BIGINT UNSIGNED AUTO_INCREMENT`，**不对外、不进 URL、不进响应** | 对外用业务键 `xxx_no`。ai-shop 原话：「一旦 `id` 出现在 URL 里，分库或数据迁移就再也做不了」 |
| `<biz>_no` | `VARCHAR(36)`，**必须有 UNIQUE** | 对外稳定标识；由 `IdGenerator` 生成 |
| `tenant_id` | `VARCHAR(36) DEFAULT 'MAIN'` | ADR-026 已降为历史常量。**新表建议不再添加**（见 §六 待确认 2） |
| `created_at` / `updated_at` | **`DATETIME(3)`**，存 UTC，`updated_at` 带 `ON UPDATE` | 见 §1.4 |
| `created_by` / `updated_by` | `VARCHAR(36)`，可空但运行时恒不为空 | 见 §1.3 |
| `version` | `BIGINT DEFAULT 0` + `@Version` | 乐观锁；append 表豁免 |
| `deleted` | `TINYINT(1) DEFAULT 0` | 逻辑删除；与 `archived_at` **语义正交**，见 §1.5 |

### 1.3 创建人 / 更新人：存什么、谁写

**存业务键字符串，不存 id。** 取值来自 `SecurityUtils.userNo()`：

| 上下文 | `created_by` 实际值 |
|---|---|
| 运营端 | `employee_no` |
| 代理端 | `account_no` |
| C 端 | `c_user_no` |
| 定时任务 / 迁移 / 设备事件 | 字面量 `SYSTEM` |

写 `SYSTEM` 而非 NULL 的理由（`AuditMetaObjectHandler` 类注释原话）：
「NULL 无法区分『系统写的』与『漏填了』」。

> ⚠️ **一列承载三个号段**是我们与 ai-shop 共有的妥协（他们在 `LoginUser` 里明文承认「靠号段恰好不撞」）。
> 我们的业务键前缀不同（`E*` / `AC*` / `CU*`），结构上不会撞，但**没有测试钉住这一点**。
> 建议补一条断言：三类业务键的首字母集合互不相交。

### 1.4 时间类型：**`DATETIME(3)`，不用 `TIMESTAMP`**

| 维度 | `DATETIME(3)`（本规范） | `TIMESTAMP(3)` |
|---|---|---|
| 自动更新 | ✅ `ON UPDATE CURRENT_TIMESTAMP(3)`，**已全库生效** | ✅ 同样支持 |
| 值是否依赖会话时区 | **否**，存字面值 | **是**，按 `time_zone` 转换存取 |
| 上限 | 9999 年 | **2038-01-19** |
| ai-shop 怎么做 | `DATETIME`（无精度），**全库零个 `TIMESTAMP` 列** | — |

**三条理由**：

1. **「自动更新」不需要换类型就已经有了**——现状 149 张表都是 `ON UPDATE CURRENT_TIMESTAMP(3)`；
2. **会话时区依赖正是本项目刚踩过的坑**。决策 D5 原文：「我部署时在 systemd 里写了
   `-Duser.timezone=Asia/Shanghai`，**这是我的失误**。预约调价按时间点执行，时区错了会在错误的时间改价」。
   用 `DATETIME` + 应用写 UTC，「库里存 UTC」是确定的；换 `TIMESTAMP` 后它变成「取决于谁连的库」——
   DBA、BI 工具、迁移脚本任何一个用本地时区连上来，读写都偏移且不报错；
3. **2038 上限**：`updated_at` 总是「现在」，所以到 2038 年才炸，但那天是全库一起炸。

**配套强制**：JVM 启动参数写死 `-Duser.timezone=UTC`，JDBC 连接串 `serverTimezone=UTC`，并加启动自检。
（ai-shop 这一条**没有被任何配置或闸门固定**，是他们的已知缺口，我们不要照抄这个缺口。）

> 若最终仍决定改用 `TIMESTAMP`：**两列必须一起改**（`created_at` 留 `DATETIME`、`updated_at` 改 `TIMESTAMP`
> 会让同一行两列跨两种时区语义，比较两者即出错），用 `TIMESTAMP(3)` 保毫秒，并把上面的时区强制提为 P0。

### 1.5 `deleted` 与 `archived_at` 并存：不是重复，是正交

| 列 | 语义 | 谁触发 |
|---|---|---|
| `deleted` | 逻辑删除，**行从所有查询消失** | MyBatis-Plus 全局逻辑删除 |
| `archived_at` | **归档**：从默认列表消失、数据保留、可取消归档 | 业务动作 `archive` / `unarchive` |

契约禁止 `delete*`，对外只暴露 `archive*`（CLAUDE.md）。现有 16 张表两列并存是**设计如此**，不是缺陷。

**但有一条必须成文**（ai-shop 的实战判例）：**唯一键与逻辑删除冲突时，三选一并写进表注释**——
① 该操作改走物理删除（如「取消收藏」，否则 `deleted=1` 的行仍占着唯一键，再次收藏会撞键）；
② 把 `deleted` 放进唯一键；③ 该表行只改不删、唯一键不含 `deleted`。

## 二、豁免：append 只增表

### 2.1 规则

| 类别 | 必须有 | 豁免 |
|---|---|---|
| **可变表** | 五件套 + `version` + `deleted` | — |
| **append 只增表** | `id` · `created_at` · `created_by` | **`updated_at` · `updated_by` · `version` · `deleted`** |

判据（`V10__audit_columns.sql` 原文）：「账本 / 审计 / 报文 / 指令流水 / 状态时间线在设计上永不 UPDATE
（`acct_ledger` 记错只能红冲、`iam_audit_log` 是 WORM），补 `updated_*` 永远是 NULL，
**反而让读表的人以为是漏填**」。

### 2.2 用类型系统兜住，而不是靠人记得

这是 ai-shop 进销存域最值得照搬的一条设计：**两个基类**。

```
BaseEntity           id · tenantId · createdAt · createdBy · version · deleted
  └─ MutableEntity   + updatedAt · updatedBy        ← 可变表继承这个
```

ai-shop 原话：「分成两个基类不是为了少写两行，是**让『这张表能不能改』在类型上就能看出来**：
继承 `InvEntity` 的实体没有 `setUpdatedAt`，于是『给流水写一次 update』这件事**在编译期就不成立**。」

我方现状是**一个** `BaseEntity` 带全部七列，append 表的实体也继承它——
于是「这张表能不能改」只存在于人的记忆里。建议按上面拆成两层。

### 2.3 当前 append 表清单（17 张，随 §2.2 改造逐张确认）

`acct_ledger` · `iam_audit_log` · `gw_message_log` · `gw_command_log` · `ord_event_log` ·
`notify_log` · `pay_event_log` · `dev_heartbeat` · `dev_alarm_notice` · `cs_message` ·
`loc_lead_follow` · `loc_site_lifecycle_log` · `usr_credit_change` · `ad_impression` ·
`sys_event_consumed` · `wo_dispatch` · `wo_handle`

**5 张需要逐张复核**（缺 `updated_*` 但不像纯 append）：
`agt_assignment` · `ord_intervention` · `usr_consent`（PDPL 撤回是不是 UPDATE？）· `usr_coupon_issue` · `usr_credit_change`。

### 3.2 命名原则（照搬 ai-shop 的五条，按本项目调整）

1. **一域一前缀**，跨域引用只经业务键，不跨域 JOIN 实体表；
2. **名字要能独立回答「这张表是什么」**，不依赖上下文；
3. **同名不同义的键禁止存在**——如 `agent_no` 只能指代理商，不能在别处指别的；
4. 关系表 = `两端实体 + 关系词`（如 `loc_site_agent`）；字典表 = `md_ + 名词`；
5. **禁用词 `merchant` / 商户**——三个语境三个意思（领域模型 §1.0）。
   ai-shop 因 `merchant` 二义性**返工过一整轮**，这是有代价的教训。

### 3.3 未归域检测

`tenant` / `tenant_config` 两张无前缀表是历史遗留。**新表一律带前缀**；
守卫（§五）把「前缀不在上表」列为失败项——一张没有域的表，谁改它、谁为口径负责都不清楚。

## 四、其余口径

| 项 | 约定 | 与 ai-shop 的差异 |
|---|---|---|
| **金额** | `DECIMAL(18,2)` + **必须有同表 `currency VARCHAR(8)`** | ai-shop 用 `BIGINT` 分 + `_minor` 后缀。**我们不改**：`DECIMAL` 同样精确（不是浮点），40 个金额列全改代价大、收益为零 |
| **比率** | `DECIMAL(5,4)`，**0..1 语义**（0.1500 = 15%） | ai-shop 用 `INT` 万分比。我们不改，但要**清掉两处百分数写法**：`sys_tax_setting.rate_percent`、`mbr_benefit.points_rate` |
| **枚举** | `VARCHAR(16)`，值 `UPPER_SNAKE_CASE`，**枚举值必须写进列 COMMENT**，格式 `值1 中文 / 值2 中文` | 一致。COMMENT 不是装饰——它是三端枚举对账脚本的输入 |
| **业务键** | `VARCHAR(36)`，必须 UNIQUE | ai-shop 用 `VARCHAR(64)` |
| **索引命名** | `uk_<table>[_<语义>]` / `idx_<table>_<语义>` | 采用 ai-shop 的**新式**（带完整表名）。旧式只带语义，跨表撞名 |
| **索引判据** | **每个索引要能追回一种真实查询**，写进表注释或 `db-design` | 一致 |
| **外键** | **不建 DB 外键**，完整性由应用层 + 唯一键保证 | 一致 |
| **JSON 列** | 仅用于快照与不需检索的结构（如 `price_snapshot`） | 一致 |
| **迁移** | 一律 `IF [NOT] EXISTS`；**已应用的迁移是冻结的**，改一个字符都会 checksum mismatch | 一致 |

## 五、守卫（没有它，上面全是建议）

**ai-shop 没有这道闸，明确建议我们补。** 建 `SchemaConventionTest`，扫 `db/migration/*.sql`：

| # | 断言 | 失败示例 |
|---|---|---|
| 1 | 每张表有 `id`（或明确的业务键主键）+ `created_at` + `created_by` | 新表漏列 |
| 2 | 非 append 表还须有 `updated_at` + `updated_by` + `version` + `deleted` | — |
| 3 | append 表必须登记进 `APPEND_ONLY` 白名单并写理由，**白名单只许缩短**（棘轮） | 随手豁免 |
| 4 | 五列类型一致：`BIGINT` / `DATETIME(3)` / `VARCHAR(36)` | `sys_biz_rule.updated_by VARCHAR(64)` |
| 5 | 表前缀 ∈ §3.1 映射表 | 未归域 |
| 6 | 业务键 `xxx_no` 有 UNIQUE | `notify_template.template_no` |
| 7 | 有金额列必有 `currency` | `pay_auth` · `pay_refund` |
| 8 | 唯一键**不含可空列** | `uk_srec_order_payee` ← **当前真缺陷** |
| 9 | 索引名匹配 `uk_*` / `idx_*` | — |

**解析器只许有一份。** ai-shop 的教训：同一套 DDL 解析逻辑在三个脚本里各写一遍，
「于是同一类 bug 中了三次，每次都是**静默出错**：① 字典序排文件（V15 排在 V2 前）② 不认 `DROP TABLE` ③ 不认 `MODIFY COLUMN`。修一处等于漏两处。」

> 这条我们已经亲身验证过：本次 review 初版正是栽在**①字典序排文件**上（`V10` 排到 `V2` 前），
> 导致统计全错。解析器务必集中一处并配自测。

## 六、当前差距与动作

### 6.1 P0：`updated_by` 从插入那刻起就没变过（**活缺陷**）

`AuditMetaObjectHandler.updateFill` 用的是 `strictUpdateFill`：

```java
strictUpdateFill(metaObject, "updatedAt", LocalDateTime.class, LocalDateTime.now());
strictUpdateFill(metaObject, "updatedBy", String.class, currentActor());
```

反编译 MyBatis-Plus 3.5.16 的 `strictFillStrategy` 确认：
`getValue(fieldName)` → **`ifnonnull` 直接返回**，即**只在字段为 null 时才填**。

而更新走的都是「先查出实体 → 改几个字段 → `updateById`」，查出来的 `updatedBy` 一定有值 → **永远跳过**。

| 列 | 是否受影响 | 原因 |
|---|:-:|---|
| `updated_at` | ❌ 不受影响 | DDL 上的 `ON UPDATE CURRENT_TIMESTAMP(3)` 由数据库兜住 |
| **`updated_by`** | ✅ **受影响** | **没有任何 DB 侧兜底，148 张表的「谁改的」永远显示创建人** |

**修法**（照 ai-shop，他们踩过同一个坑并留了守卫测试）：

```java
setFieldValByName("updatedAt", LocalDateTime.now(), metaObject);
setFieldValByName("updatedBy", currentActor(), metaObject);
```

并补测试：①已有值也要被覆盖 ②没有这两个字段的实体（append 表）不能抛异常。

### 6.2 动作顺序

| 序 | 动作 | 级 |
|:-:|---|:-:|
| 1 | 修 `updateFill` + 守卫测试（§6.1） | **P0** |
| 2 | 修 `uk_srec_order_payee` 含可空列（review §1.1） | **P0** |
| 3 | `notify_template.template_no` 补 UNIQUE；`pay_auth`/`pay_refund` 补 `currency`；`sys_biz_rule.updated_by` 改 36 | P1 |

## 七、待确认

1. **时间类型**：维持 `DATETIME(3)`（本规范建议，理由见 §1.4），还是改 `TIMESTAMP(3)`？
   改的话两列一起改 + 时区强制提 P0。
2. **`tenant_id`**：新表是否还加？建议**不加**（ADR-026 已取消租户概念），但 117 张存量保留不动。
3. **金额单位**：维持 `DECIMAL(18,2)`（建议），还是照 ai-shop 改 `BIGINT` 分？后者要改 40 列 + 全部计价/结算代码。
4. **§2.3 那 5 张表**是不是 append 型，需逐张定。
5. **迁移编号缺 V12**：是从未存在，还是曾应用后被删？后者会让已有库 `validate` 失败。
