## 一、口径

每个对象判四态。判据是**能不能从菜单走到一个能看见它的界面**，不是「有没有表」「有没有接口」。

| 记号 | 含义 |
|---|---|
| ✅ | 有**专属菜单叶子** |
| ◐ | 有界面但**无独立入口**——嵌在别的对象的详情/抽屉/字段里（正常，但要知道它在哪） |
| ❌ | 运营端**零入口**（缺口） |
| — | **不该有**：技术设施 / C 端私有 / 隐含单例 |

## 二、总账

| | |
|---|---:|
| 领域对象（扣掉 §1.0 的 7 条术语裁定行与已取消的租户） | **88** |
| ✅ 专属菜单 | 58 |
| ◐ 嵌入式 | 15 |
| ❌ 零入口 | **7** |
| — 不适用 | 8 |

> **核验深度不一样，标出来**：❌ 的 7 条与 ◐ 的 15 条是**逐条查过代码**的（见各条的文件行号）；
> ✅ 的 58 是**余数**——由 110 个叶子逐个反查到对象后剩下的，没有再逐条打开页面确认其完整度。
> 即本文回答「点不点得进去」，不回答「进去之后功能全不全」（那是
> [逐菜单待办清单](./前端静态实现-逐菜单待办清单.md) 的事）。

菜单侧反查：110 个叶子**没有一个**挂不上领域对象（无「孤儿菜单」）。
缺口是**单向**的 —— 模型有、界面无，没有反向的界面有、模型无。

## 三、七个缺口

排在前面的三条是**合规与可审计**类：它们不是"少个页面"，是**已经在发生的业务无人可管**。

### 3.1 注销申请 Logoff —— C 端能提交，运营端看不见

`usr_logoff` 有 PENDING 与冷静期；C 端 [`MpUserController:156`](../../backend/sharehub-app/src/main/java/ai/neargo/sharehub/portal/core/MpUserController.java#L156) `POST /mp/user/logoff` 已开放。
运营端零入口 ⇒ **冷静期内没有任何人能看到待注销队列**，也没有撤销入口。
`UserLogoffService` 的注释写明「冷静期已过此时数据可能已开始清除」——
这意味着误操作的用户只能等数据被清掉。PDPL 语境下这是要能举证的一环。

### 3.2 同意记录 Consent —— 表在模型里，**后端零 Java 引用**

`usr_consent`（明示同意 / 撤回）在领域模型 §1.6 登记，但全后端搜不到一处引用，运营端也无入口。
即"合规要求可查可撤回"这件事目前**两端都没有实现**，只有一行模型定义。
⇒ 这条不是前端缺页，是**整条没做**，登记位置应是需求侧而非本文。

### 3.3 会话令牌 Token —— 有存储，无「踢人」

`sys_token` + `RedisTokenStore`/`MysqlTokenStore` 已就绪，模型定义写明"可撤销可踢人"。
运营端没有会话列表、没有强制下线。员工离职走 `iam_employee` 停用，
但**已签发的令牌不会因此失效**（除非停用逻辑里显式撤销，现未见）。

### 3.4 订单事件 OrderEvent —— **写进去了，没人读得到**

这一条最值得单拿出来：

- `ord_event_log` 有表，`OrdEventLog` 有实体，`OrderEventLogService.timeline(orderNo)` **已实现**；
- Refund / Deposit / OrderException / Complaint **四个 service 都在往里写**；
- `timeline()` 的**调用方是 0 个**，没有任何 Controller 暴露它；
- 运营端订单详情的 `<Timeline>` 渲染的是**干预历史**（`ord_intervention`），不是状态流转。

⇒ 订单的每一次状态迁移都留了痕，而**留的痕谁也看不到**。
排障时"这单怎么走到 EXCEPTION 的"只能靠翻日志。
这是 §3 里唯一**补一个读侧端点 + 详情页一个 Field 就能闭合**的，成本最低、价值最直接。

### 3.5 设备类型 DeviceType —— ADR-021 的预留，尚未接入

`md_device_type` ⏸ 全代码零引用（[对账表 §2.1.2](./实体-领域对象对账表.md)）。
运营端只在 `lib/types/pricing.ts` 里作为**计价适用范围的一个维度**出现，没有管理面。
设备类型抽象是 ADR-014 / ADR-021 的核心，迁移放行前不必补入口；
但**它现在是"表建了没人用"**，不是"做了没挂菜单"，两者处置不同。

### 3.6 自然人 Principal —— 表待建，入口随之待建

`agt_principal` 待建（ADR-030）。运营端「代理账号管理」管的是 `agt_account`
（人 × 主体的成员关系行），**不是登录主体本身**。
⇒ 一个人在 N 个主体下有 N 行账号，但"这个人"没有一处可查，
改手机号 / 停用这个人要逐行改。ADR-030 落地时需同时补这个入口，否则模型分了两层、界面还是一层。

### 3.7 C 端发票 / 抬头 UsrInvoice —— 申请提交后无人受理

`usr_invoice` · `usr_invoice_title`，C 端可提交开票申请（本会话刚把
`InvoiceApplyReq` 转成 DTO 的那个端点）。运营端「发票」叶子管的是 `fin_invoice`
——**给场地方/代理商开的结算发票**，与 C 端开票是两个对象。
⇒ 消费者提交的开票申请落库后没有受理界面。

## 四、15 个嵌入式对象（◐）——在哪，记一下

不是缺口，但"找不到在哪"本身会让人以为没做，所以登记位置。

| 对象 | 实际在哪 |
|---|---|
| 运营主体 Operator | 「代理商档案」（现寄居 `agt_agent`，ADR-029 独立后需拆） |
| 代理辖域 AgentRegion | 代理商档案详情 |
| 数据范围 DataScope | 角色权限 / 员工详情 |
| 凭据 Credential | 无管理面（仅登录流程用） |
| 槽位 Slot | 设备详情 · 实时监控 |
| 设备影子 DeviceShadow | 实时监控 |
| 订单事件 OrderEvent | **→ 见 §3.4，实为 ❌** |
| 干预 Intervention | 订单详情「干预历史」 |
| 支付单 Payment | 财务页 · 对账 |
| 信用 Credit | 「风控用户」 |
| 广告主 Advertiser | 营销页（广告活动内选择，无档案管理） |
| 广告创意 Creative | 营销页（广告活动内） |
| 收藏/消息/通知偏好/推送令牌 | — C 端私有，运营端不应有 |
| 菜单 Menu | — 由 `nav.ts` 生成 `iam_menu` 种子，v4/06 才下发 |
| 发件箱 Outbox | — 技术设施 |

其中 **广告主 Advertiser** 值得单记：`ad_advertiser` 是独立表、L3 对象，
现在只能在广告活动里选，没有档案页 —— 广告主的联系人、结算口径、历史投放都无处落。
L3 启动时这是第一件要补的。

## 五、结论与建议顺序

1. **§3.4 订单事件**：补读侧端点 + 详情页时间线。半天，收益立刻。
2. **§3.1 注销申请**：补运营端待办队列 + 撤销。合规必需。
3. **§3.3 会话令牌**：员工停用时撤销其令牌（后端一行）+ 会话列表（可后置）。
4. **§3.7 C 端开票受理**：与 §3.1 同一个「C 端提交、运营端受理」的模式，可一起做。
5. §3.2 / §3.5 / §3.6 随各自的 ADR 放行，不单独排期。

> 第 1–4 条有个共同形状：**C 端或后端已经在产生数据，运营端没有对应的消费面**。
> 这类缺口不会报错、不会红、用户也不会投诉（他们不知道本该有），
> 只有拿模型逐对象扫一遍才会露出来 —— 这就是本文存在的理由。
