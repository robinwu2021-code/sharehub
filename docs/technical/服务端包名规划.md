├── operator     商家管理      ┐
├── network      网点管理      ├ sharehub-svc-platform
├── system       系统管理      ┘
├── device       设备管理      ┐
├── sales        销售管理      ├ sharehub-svc-core
├── consumer     用户管理      ┘
├── ops          运维管理        sharehub-svc-ops

├── gateway      设备对接服务    sharehub-svc-gateway（独立进程 sharehub-app-gateway）

|---|---:|
| 不动 | 80 |
| 同一 Maven 模块内改包 | 898 |
| 换 Maven 模块 | 121 |
| 留在单体跨域编排层 | 15 |
| 需先拆分的类 | 6 |

## 一、命名规则

| # | 规则 | 例 | 理由 |
|---|---|---|---|
| 1 | 第一级是**业务模块**，与架构图的 11 个模块一一对应；另有 5 个部件：`auth` `gateway` `api` `common` 与单体装配 | `operator` `sales` `invoice` | 打开代码目录就能对上架构图 |
| 2 | 第二级是**域**，一个域拥有一组表（一个或几个表前缀） | `sales.order` 拥有 `ord_*` | 表归属可被 `module-graph.py` 校验 |
| 3 | 第三级是**层**，固定词表（§三） | `entity` `service.impl` `api.b` | 架构测试按层写规则 |
| 4 | **用完整英文单词**，不用缩写；业界通用缩写只保留 `iam` | `device` 不用 `dev`；`workorder` 不用 `wo` | 新人不用猜 |
| 5 | **包名不带服务组、不带 Maven 模块名** | 不写 `core.sales.order` | 服务边界将来会动，包名不跟着动（v4/09） |
| 6 | **「merchant / 商户」只用于支付渠道**；经营方叫商家，包名用 `operator` | `operator.merchant` = 商家在渠道侧的商户 | ADR-029 · ADR-032 |
| 7 | **改包不改表名、不改 URL** | `loc_*` 表仍叫 `loc_*` | 包移动是纯重构；表与接口另有改名窗口（ADR-021 S1） |
| 8 | 分润包叫 `profit`，不叫 `share` | `settlement.profit` | 避免与平台代号 ShareHub 混淆（v4/09） |

## 三、层级子包

### 3.1 固定词表

| 子包 | 放什么 | 约束（v4/09 §四，进架构测试） |
|---|---|---|
| `api.b` | **B 端**控制器：`/api/**`，服务运营台与商家视图 | 只做鉴权、校验、形状裁剪；不依赖 Mapper；不写 `@Transactional` |
| `api.c` | **C 端**控制器：`/mp/**`，服务 App / 小程序 / H5 | 同上；身份只经 `ConsumerContext` |
| `api.internal` | 内部端点：`/internal/**`，契约 Port 的服务端 | 不套 `Result` 信封 |
| `service` | 服务接口、命令 record、状态机 | 接口名 `XxxService` |
| `service.impl` | 服务实现 | 实现名 `XxxServiceImpl` |
| `entity` | 实体，一表一类 | 不出现在请求体与响应里 |
| `mapper` | MyBatis Mapper | 只被本域 `service.impl` 引用 |
| `dto` | VO 与请求、响应对象 | `XxxVO.of(entity)` 是唯一转换出口 |
| `port` | 本域对 `sharehub-api` Port 的实现、事件监听 | Port 接口本身只在 `sharehub-api` |
| `event` | 本域的 Outbox 消费者 | 按 `eventId` 幂等 |
| `job` | 定时任务 `JobHandler` | 禁止 `@Scheduled` |
| 域特有 | 如 `sales.price.engine`、`ops.alarm.eval`、`gateway.driver.spi` | 只在确有一组同类类时建 |

**枚举、状态机等跨层共用的小类型**放在域根包，例如 `sales.order.OrderStatus`。

### 3.2 控制器放哪：随域，或留在单体编排层

```
控制器只依赖本域的实现类，其他域都经 sharehub-api 的 Port？
        │
     是 ┴─▶ 放进域内：<模块>.<域>.api.{b|c|internal}      ← 默认；拆服务时随域一起走
        │
     否 ──▶ 放在单体：portal.{b|c|internal}                ← 跨域编排，如找柜卡片、C 端订单投影
```

代码清单 §三 列出了今天不满足条件的 15 个类与原因。处理方式二选一：把对他域实现类的直接引用改成经 Port，然后随域迁入；或确认它本来就是跨域装配，留在 `portal`。

## 五、迁移步骤

**总原则**：每一步行为不变；URL 不变、表名不变；一次只动一个 Maven 模块；用 IDE 重构移包，改完 grep 确认落点；
每步结束重跑 `gen-code-inventory.py`，清单里的「改包 / 迁模块」只减不增；提交只用显式路径。

按**现所在的 Maven 模块**分步，各步类数取自代码清单，合计 1019 个（即「改包」898 + 「迁模块」121）。

| 步 | 内容 | 要动的类 | 前置 |
|---|---|---:|---|
| **P0** | 新代码立即按目标包写（§四）；把本文规则写进架构测试 | — | 本文确认 |
| **P1** | 拆分 6 个跨域旧骨架控制器；编排层 15 个类中能改为经 Port 的先改 | 21（计入 P5） | — |
| **P2** | `sharehub-svc-platform`：`agent → operator`、`loc → network`、`platform.* → system.*`；佣金迁财务、B 端登录与凭据池迁认证 | 278 | P1 |
| **P3** | `sharehub-svc-core`：`dev/inv → device`、`trade → sales`、`user → consumer / sales`；C 端登录迁认证、C 端开票迁发票、OTA 迁设备对接服务、`PaymentPort` 移入契约 | 365 | P1 |
| **P4** | `sharehub-svc-ops` 与 `sharehub-svc-finance`：运维三域改名；财务平铺包按表前缀拆成 `finance` / `settlement` / `invoice` | 196 | P1 |
| **P5** | `sharehub-app` · `sharehub-common` · `sharehub-api`：新建 `sharehub-auth`、`sharehub-svc-report` 并迁入；控制器从单体迁入各域；契约按业务模块重新分包 | 155 | P2–P4 |
| **P6** | `sharehub-svc-gateway`：`gw → gateway` 按域分包 | 25 | — |

P2、P3、P4、P6 互不依赖，可以多人并行，各管一个 Maven 模块。P5 之后单体里只剩装配与跨域编排。
P3 中的 OTA 迁移若与 v4 S5（OTA 移入网关）排期不同，可单独推迟，不影响其余改包。

与 v4/09 重构步骤的关系：P1–P4 即 v4/09 的 C3「包归位」，P5–P6 即 C6「模块抽取」；C4 命名通用化（`cabinet → device` 等表与列改名）仍按 ADR-021 S1 单独进行，不与本迁移混在同一批。

2. 商家管理的包名用 `operator`（与 ADR-029 的「运营主体」一致），不用 `merchant`；
3. C 端开票申请（`usr_invoice*`）从交易组迁入发票模块，属于跨 Maven 模块迁移；
4. 迁移排期：建议 P1 与第一阶段第一批新功能同一迭代，P2–P4 在其后集中做一次。
