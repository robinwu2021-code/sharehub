# 方案 · 场地管理优化（编号 / 行业 / 地址）

> 2026-09-26。已实现，迁移 `V121`。三件事的共同点是
> **界面上能填、填了不算数或者没人拦** —— 这一类毛病不报错，所以能活很久。

---

## 〇、三处现状

| | 现状 | 后果 |
|---|---|---|
| **编号** | 表单上有个可编辑的「编号」框，占位写着「新增自动生成」 | 后端 `createVenue` 第一行就是 `body.setVenueNo(null)` —— 打进去的值**被静默丢弃**。API 是安全的，但这个字段看着能用、其实不生效 |
| **行业** | 纯文本框 | 生产 5 行里三行是错的：Emaar Malls（商业地产）填「零售」、Majid Al Futtaim 填「航空」、DXB Airports 填「地产」 |
| **地址** | `loc_venue` **根本没有地址列**；`loc_lead.address` 有地址、没坐标 | 签约转化传的是 `SiteReq(..., address, null, null, ...)`：**转化出来的站点有地址、没落点** —— 地图上看不见它，C 端「找附近」按坐标排也排不到它，而这件事不报错 |

自由文本的问题不是「填错了」，是**填错了没人拦，也没人看得出来**。
而这一列将来要用来按行业看坪效、按行业定价、按行业分派 BD。

## 一、编号方案

### 定下来的

| 项 | 取值 |
|---|---|
| 格式 | `VEN` + 顺序号，**宽度 3 位**（`VEN305`、`VEN306`…） |
| 为什么是 3 位 | 与现有种子 `VEN300~304` 同形。超过 999 自然进位成 `VEN1000`，不截断 |
| 取号 | `MAX(CAST(SUBSTRING(venue_no, 4) AS UNSIGNED)) + 1` |
| 表单 | **删掉编号字段**，不是置灰。编辑时编号在抽屉标题里显示 |

### 为什么换掉 ULID

原先是 `IdGenerator.next("VEN")`，出来的是 `VENMUI9X6VY1M3XM5DQ`（19 位）。
场地方编号是**人要读、要念、要在合同和对账单上核对**的东西。

而这个仓库里走 `AbstractCrudService` 的实体（员工、部门…）本来就是顺序号 ——
今天生产建的是 `E1006` / `E1007`。**同一套系统里两种编号形态，没有理由。**

### 为什么不用字典序取最大

位宽不一致时字典序会取错。实测（提现单）：库里同时有 `WD9002`(4 位) 与 `WD009003`(6 位)，
字典序下 `'WD9002' > 'WD009003'`，取到 9002 → 下一个算成 `WD009003` → 撞已存在行报
`Duplicate entry`。所以按**数字序**取 `MAX`。

### 已知取舍：并发下会撞唯一键

两个人同一瞬间建档，`MAX+1` 会算出同一个号，其中一个撞 `uk_venue_no` 失败。
场地方一天建几个，这个代价可以接受；要绝对安全得上号段表，不值得。
**员工号走的也是这条路**，行为一致。

### 明确不做

- **不给存量场地方重新编号**。编号已经被合同、站点、结算引用了。
- **不动另外 22 个用 `IdGenerator` 的服务**（合同号 `CTMUI4...`、工单号、告警号…）。
  那是全站业务键，牵一发动全身，与本次无关。想统一得单独立项。

## 二、行业词表

13 档，码是大写下划线（全仓约定），中文名在 `VENUE_INDUSTRY_LABEL` 一处定义：

```
SHOPPING_MALL 购物中心   COMMERCIAL_RE 商业地产   AIRPORT 机场与航空
TRANSPORT_HUB 交通枢纽   F_AND_B 餐饮            HOTEL 酒店与住宿
MEDICAL 医疗            EDUCATION 教育           OFFICE 办公
ENTERTAINMENT 娱乐      RETAIL 零售              SCENIC 景区与文旅
OTHER 其它
```

**留 `OTHER` 兜底**：没有兜底时运营会被逼着乱选一个，那比「其它」更难查。
**空值放行**：行业不是必填，「还没问清楚」是合法状态。

### 与站点「场景类型」是两个轴，没有合并

- 行业说的是**这家公司做什么**（Emaar 是商业地产）
- 场景说的是**这个点位在什么地方**（它名下那个点位在商场里）

取值高度重叠，但地产集团运营商场时二者恰恰不同 —— 合并会表达不了这种情况。

### 为什么不用可配字典（`dict_item`）

放进字典运营就不用发版能增减，听着更好。但：
生产 `dict_item` **是空的**、这套机制没被任何页面真用过，
且词表变成运行时数据之后**跨端词表卡口就查不了它**
（`StatusVocabularyAcrossEndsTest` 比的是两端的具名类型）。
先按 `sceneType` 已有的形态做，要改成可配是另一个决定 —— 它改变的是谁拥有这份分类。

### 存量归一

按字面映射，**不替业务猜**：

```
零售 → RETAIL     航空 → AIRPORT     地产 → COMMERCIAL_RE     餐饮 → F_AND_B
```

DXB Airports 映射成「商业地产」看着就是错的，但**那是它本来就填错了**。
现在有了下拉，改它是一次点击的事。词表外的一律归 `OTHER` ——
留一个词表外的值，`StoredValueInVocabularyTest` 当场红，而且下拉也选不中它
（显示空白，一保存就被改成别的值）。

`loc_venue_onboarding.industry` 同一套词表：进件通过后会**原样建档成场地方**，
两边词表不同的话失配发生在审批通过那一刻 —— 那时申请人已经走了。

## 三、地址与坐标

### 加在哪

| 表 | 加了什么 |
|---|---|
| `loc_venue` | `address` / `lng` / `lat`（此前一列都没有） |
| `loc_lead` | `lng` / `lat`（`address` 早就有） |

两个表单都改用 `type: "address"`（`AddressPicker`，站点页早就在用）——
地址与经纬度**必须一致**，分开手填时两者对不上没人拦得住。
没配地图密钥时它自动降级成「地址手填 + 两个坐标小输入框」，建档这件事不被地图挡住。

### 真正值钱的是商机那一头

`LeadOpsServiceImpl.convert` 现在把商机的坐标一起带进新建站点：

```java
// 改前
new SiteReq(..., firstNonBlank(r.address(), lead.getAddress()), null, null, ...)
// 改后
new SiteReq(..., firstNonBlank(r.address(), lead.getAddress()), lead.getLng(), lead.getLat(), ...)
```

改前那两个 `null` 意味着：**每一个由签约转化建出来的站点，在地图上都没有落点**。

### 一处已知的、没在本次解决的不一致

商机**没选点**时：mock 退到区域中心，真后端退到 `null`。
这个差异是既有的（mock 一直用区域中心），意味着「商机没填地址」这条路
在 mock 里看不出问题、切后端才发现站点没落点。
顺带：前端 `Site.lat/lng` 的类型是**必填 number**，而后端确实会回 null ——
类型在这一点上是错的。两件事都超出本次范围，记在这里。

## 四、验收

| 断言 | 在哪 |
|---|---|
| 编号是 `VEN` + 顺序号，客户端传什么都不算数 | `VenueNumberingAndIndustryTest` |
| 词表外的行业当场 400，且不留半行 | 同上 |
| 库里现存的行业值全在**枚举**里（与按列注释比的那条不重复） | 同上 |
| 商机坐标带进转化出来的站点 | 同上（后端）+ `venue-industry.test.ts`（mock） |
| 行业词表两端同值 | `venue-industry.test.ts` |

负对照都验过：取号退回 ULID → 红；行业校验拆掉 → 红；坐标不带过去 → 红。

> ⚠️ 写用例时撞到一条**假绿**并换掉了：原本写的是「编辑商机时坐标不会被抹掉」，
> 而 `updateLead` 用 `Object.assign(cur, {…})`、真后端是 MyBatis-Plus 的 NOT_NULL 策略 ——
> 两层都是「只改传了的」，那个隐患在这条路上根本不成立，断言恒绿。
> 换成了「新建时坐标真的落下来」，拆掉实现会红。
