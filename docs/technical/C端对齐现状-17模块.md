## 零、先说结论：卡口已经绿了，而绿的含义比看起来窄

`api-align.py`（挂在 `ops-web` 的 `check:drift` 下）当前对 C 端的判定：

| 类别 | 数量 | 说明 |
|---|---|---|
| A 前端在调、后端没有（运行期 404） | **0** | 零容忍，确实是 0 |
| B 字段对不上（运行期 undefined） | **0**（全仓 2 条都在运营端且是有意的） | 9-25 那批逐字段对完了 |
| C 后端有、c-app 未调 | **4** | 全是开票（`/mp/user/invoice{s,-titles}`），等市场口径 |

后端 `/mp` 端点 **42** 个，c-app 调 **38** 个。**路径层与字段层的对齐已经做完。**

**但卡口只比三件事**：路径在不在、出参字段名对不对、类型有没有声明。
它**不比**：

1. **请求体里的枚举值** —— c-app 登录页发 `grantType:"password"`，而后端曾**没有这个策略**。
   路径与形状都对、卡口全绿，用户却吃 400。**2026-09-26 已修**（`PasswordStrategy`），
   但这一类的盲区依旧存在：卡口不比取值域。
2. **能力开关** —— **2026-09-26 已收口**：`GET /mp/auth/methods` 下发按国家的开关
   （需求 OPS-SYS-07，`sys_login_setting` 自 V5 就有、此前没有任何一处读它），
   端上按它显隐三个入口，`ConsumerAuthService` 服务端强制。剩改邮箱仍是 400（`pb_pii` 未建）。
3. **依赖的桩** —— `PaymentPort` 只有 `StubPaymentPort` 一个实现，**一律模拟成功**。
   形状完全正确，钱一分没动。

## 二、⚠️ 桩支付：一个要在接短信通道之前处理的次序问题（已处置）

`StubPaymentPort` 的类注释写得很清楚：「一律模拟成功」「不校验余额」，
换真实现时新增 `NearpayPaymentPort` 加 `@Primary` 即可，注入点一行不改。设计是干净的。

问题在**它没有开关**：它是无条件的 `@Service`，任何环境都生效，而
`RechargeServiceImpl` 的逻辑本身是对的 —— 它检查 `PAID` 之后才 `wallets.credit(...)`：

```
payments.pay(...) → StubPaymentPort 恒返 PAID → wallets.credit(...) 真加余额
```

所以**任何跑这套构建的环境里，登录后的用户都能免费充值**（同理：免押冻结是假的、
买断与租金结算都记为已付）。

现在够不到，唯一原因是 **C 端登录不了**（万能码后门 9-23 已关、短信通道未接）。
而「接短信通道」正是当前待办的下一步 —— **接通的同一天，免费充值就变成可达的。**

### 已处置（2026-09-27）

原本的建议是给桩加 `@ConditionalOnProperty`、不显式开启就没有 bean。**没有那样做**，
因为桩现在是唯一的 `PaymentPort` 实现 —— 那等于**所有环境都起不来**，包括正在跑的演示环境。

改成把闸做在「会把钱变成可花余额」的那一条路上：

- `PaymentPort.simulated()`（default false，桩覆写 true）—— 让上层能问出「这是模拟的吗」。
  此前问不出来：桩的返回形状与真实通道**完全一样**，「已支付」就是「已支付」。
- `RechargeServiceImpl` 在 `simulated() && !devMode` 时**拒绝充值**，方法第一句，
  早于任何参数校验与 mapper（有用例钉住这个顺序）。
- `StubPaymentPort` 启动打 WARN 横幅，照 `DevMode` 的做法。

**为什么只拦充值**：借还/押金/买断是「把应收记成已付」——平台少收钱，
不是给用户凭空发一笔能花的余额。两者严重性不同，处置也该不同。
（C 端余额**没有提现出口**，所以损失有界于站内消费，但仍是真实损失。）

⚠️ 副作用：演示环境（dev-mode 关）从此**充值会失败**。这是有意的 —— 它此前发的是假钱。
借还全链路照旧可演。

接入真实通道后（新增 `NearpayPaymentPort` 并 `@Primary`）这道闸自动失效，不需要回来改。

## 三、卡口看不见的三类，怎么补

| 请求体枚举值 | `grantType:"password"` | 只比字段名，不比取值域 | 后端把支持的 grantType 列进契约、脚本比对；或短期先在 c-app 隐掉密码页签 |

## 五、接真后端还差什么

c-app 的开关仍是 mock（`.env` 的 `VITE_USE_MOCK=1`，`src/api/index.ts` 是唯一切换点）。
切过去要按顺序做三件：

1. **桩支付 fail-closed**（§二）—— 否则接通登录即开免费充值
2. `.env.local` 置 `VITE_USE_MOCK=0` + `VITE_API_BASE`
3. 按 §一的 🔴/🟡 逐条实测 —— 尤其模块 1 的密码三入口、模块 12 的报障附件

**不建议先切开关再逐条查**：mock 与真后端的差异现在只剩语义层（桩、能力开关、枚举值），
而这三类切过去都**不报错**，只是行为不对 —— 正是最难发现的那种。
