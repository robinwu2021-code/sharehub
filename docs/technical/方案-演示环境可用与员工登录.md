# 方案 · 让生产环境真正可用

> **状态：待放行**。2026-09-26 拟。两件互相独立的事，可分别放行：
> **A 补齐种子数据**（48 台柜子一颗宝都没有、全部离线停借）·
> **B 员工登录**（只有 `admin` 能登录，双人复核的流程全部走不通）。

---

## 〇、为什么这两件事卡住了整个环境

2026-09-26 生产业务流程验证暴露的：

| 现状 | 后果 |
|---|---|
| `dev_powerbank` **0 行**，48 台柜子无宝 | 站点「无宝可借」，C 端借不到；上线门禁的装宝比例永远不过 |
| 48 台柜子心跳停在 **9-23** | 按业务定义全部离线 → 41 台被挂 82 条 `STOP_RENT` |
| 只有 `admin` 能登录 | 合同审批链（不能自批自）、财务会签（不能与审批人同人）**全部走不通**，任何合同进不了 ACTIVE |

前两条让环境「看起来有数据但用不了」，第三条让**流程类功能无法验证也无法演示**。

## A · 补齐种子数据

### A0 先说清楚：保护不用手动删

41 台柜子上的 82 条 `STOP_RENT` 是**告警持有**的，条件恢复后会自己解除
（实测链路：条件消失 → 记 `recovered_at` → 防抖 10 分钟 → 告警关闭 `SELF_HEALED` → 保护解除）。
**手动删是错的**：判定每分钟都在跑，删了下一分钟又挂上。
把设备变回「在线且有宝」，保护会自己退场。

### A1 灌充电宝

| 项 | 取值 | 为什么 |
|---|---|---|
| 数量 | 每柜 **总仓位的 60%**（8 仓 → 5 颗）；全库 48 台合计 **250 颗**（实测仓位总数算得） | 上线门禁要求装宝比例落在 **50%–80%**；装满反而不让上线（满柜没有空位可还宝，实测撞到过） |
| 状态 | `IN_CABINET` | 在柜可借 |
| 电量 | 60–100 随机 | 低于 60 的宝不计入可借（与告警判定同口径） |
| 循环 | 10–400 | 不要超 500 —— 那是老化阈值，会被 `powerbank-aging` 标成 AGED 并停借 |
| SN | `PBSN{柜号}{仓位}` | 可识别、可回溯，不与将来真设备撞 |

同时把 `dev_cabinet.available_count` 回写为实际在柜数 —— 告警判定读的是这一列。

### A2 心跳：必须是**持续**的

这是最容易做错的一步。**发一次心跳没用**：在线判定是「最近心跳在 3 分钟内」，
发完 3 分钟后又变离线，保护再次挂上。

做法：一个只在演示环境安装的模拟器。

```
deploy/tencent/cron/powerbank-demo-heartbeat     # 每分钟给种子柜发心跳
deploy/tencent/demo/heartbeat.sh                 # 实现（读 X-Internal-Token，批量发）
```

三条硬约束：

1. **只发给种子柜**（`cabinet_no LIKE 'CAB1%'`，实测当前 48 台全部落在这个号段），
   真设备接入后它们有自己的心跳，模拟器不能盖掉 —— 否则真设备掉线了你也看不出来。
   ⚠️ 真设备的柜号**必须避开 `CAB1` 前缀**，否则会被模拟器一起刷心跳。
   这一条要写进设备接入的准备清单。
2. **文件名带 `demo`**，且脚本头部写明「演示环境专用，接入真设备前必须删除」。
3. **不进 `powerbank-jobs`**：那份清单由 `JobCronCoverageTest` 按任务声明生成，
   塞一个不存在的任务进去会让卡口红。

> ⚠️ **为什么不改在线判定窗口**（把 3 分钟调大）：那个窗口是真实业务语义 ——
> 设备掉线 3 分钟就该停借。为了演示把它调成 30 天，等于把这条闸关掉，
> 而将来没人记得调回来。**宁可让演示环境多一个模拟器，也不要改业务口径**。

### A3 验收标准

```bash
# 1. 装宝比例落在门禁要求内
curl -s .../api/ops/devices/CAB1001/go-live-gate | grep LOAD     # 期望 ✓

# 2. 保护自行退场（心跳跑满 10 分钟防抖后）
select count(*) from dev_protection where action='STOP_RENT' and released_at is null;  # 期望 0

# 3. 告警自愈
select status, close_reason from dev_alarm where alarm_code='SITE_UNRENTABLE';         # 期望 CLOSED / SELF_HEALED
```

### A4 代价与风险

| 风险 | 处理 |
|---|---|
| 模拟器被带到真实环境 | 文件名带 `demo`、脚本头警告、独立 cron 文件（一条命令即可卸） |
| 真设备接入后模拟器盖住真心跳 | 只发 `CAB1%` 号段；真设备用别的号段 |
| 灌的宝与将来真宝撞号 | SN 前缀 `PBSN`，业务号由服务端取号 |

## B · 员工登录（凭据底座 B2）

### B0 现状：地基齐了，没接线

V114（`0646488`）已经建好：

- `cred_credential` 表：`realm` / `subject_no` / `algo` / `hash` / `must_change` /
  `failed_count` / `locked_until` / `pwd_changed_at` / `status` —— **锁定与强制改密的字段都在**
- `iam_employee.cred_ref` 列（指向凭据）、`phone_hash` / `email_hash`（登录标识）
- `PasswordEncoder`（BCrypt）—— 但**没有任何调用方**
- `StaffIdentityBackfillJob`（回填身份哈希）

而登录（`AuthController#login`）今天只有三条路：
**① 配了 admin 口令 → 只认 `admin` 一个用户名；② dev-mode 免密；③ fail-closed 拒绝。**
凭据表一行都没有，表 0 行。

### B1 要补的三件事

| # | 内容 | 端点 | 权限 |
|:-:|---|---|---|
| 1 | **管理员给员工建号 / 重置密码** | `POST /api/platform/employees/{employeeNo}/credential` | `org:employee:update` |
| 2 | **本人改密** | `POST /api/auth/password` | 登录态 |
| 3 | **登录认凭据表** | 改造 `AuthController#login` | — |

生产现有 **5 名 ACTIVE 员工**（E1001 OPS / E1002 OPS / E1003 CS / E1004 FINANCE / E1005 ADMIN），
建完号正好覆盖合同审批链需要的三个角色。

**建号返回一次性初始密码**（服务端生成，不接受调用方指定），并置 `must_change=1`；
响应里只回一次，不落日志、不二次可查 —— 能再查出来的初始密码等于没有初始密码。

### B2 登录改造的顺序（这一步最容易把所有人锁在门外）

```
1. 查 cred_credential（realm=STAFF, subject_no=输入的登录名）
   ├─ 命中且 status=ACTIVE 且未锁定 → 验 hash
   │   ├─ 通过 → 发 token；must_change=1 时在响应里带标记，前端强制跳改密
   │   └─ 失败 → failed_count+1；达阈值置 locked_until（建议 5 次 / 15 分钟）
   └─ 未命中 → **回落到现有的 admin 口令闸**（保持今天的行为）
2. dev-mode 与 fail-closed 分支原样保留
```

**回落是关键**：凭据表为空时系统的行为必须与今天**完全一致**，
否则上线那一刻所有人都进不来 —— 而这类故障只能靠改配置或改库来自救。

### B3 验收标准（每条都要有用例）

| 断言 | 为什么 |
|---|---|
| 凭据表为空时，`admin` + 原口令照常登录 | 回落没断 —— 这条最重要 |
| 给 E1001 建号后，它能用新密码登录且角色是 OPS | 角色来自员工档案而不是请求 |
| 首次登录带 `mustChange` 标记 | 初始密码必须改 |
| 连错 5 次 → 锁定，锁定期内即使密码对也拒 | 防爆破；**锁定期内密码对也要拒**，否则锁形同虚设 |
| 改密后旧密码立刻失效 | |
| 建号响应里的初始密码不出现在任何日志 | 日志会被很多人看到 |
| **离职员工（status≠ACTIVE）登录被拒** | 与 `DisabledEmployeeSessionTest` 同一条线 |

### B4 做完之后才能验的事

- **合同审批链完整走通**：E1001（OPS）提交 → E1005（ADMIN）审批 → E1004（FINANCE）会签 → 生效
- 「不能审批自己提交的」「会签人不能是审批人」这两道闸**在真实多账号下**的行为
- 按角色的菜单与按钮可见性（今天只能用超管看，所有东西都是亮的）

### B5 风险

| 风险 | 处理 |
|---|---|
| 改登录把所有人锁在门外 | 凭据未命中时**回落**到今天的行为；上线前在测试库跑一遍「凭据表为空」的回归 |
| 初始密码泄露 | 只回一次、不落日志；`must_change=1` 强制改 |
| 锁定被用来拒绝服务（恶意锁别人账号） | 按 `(subject_no)` 锁而不是按 IP；锁定期短（15 分钟）；管理员可重置 |
| BCrypt 成本参数过高拖慢登录 | 沿用 `CredentialConfig` 里已定的 cost，不在本批调 |

## 建议的次序

**先 A 后 B**，两件都不阻塞对方，但 A 的收益立刻可见（环境能演示了），B 的改动面更大。

| | 内容 | 影响面 | 可回滚性 |
|---|---|---|---|
| A | 灌宝 + 心跳模拟器 | 只加数据与一个独立 cron | 删 cron + 删带标记的数据 |
| B | 建号 / 改密 / 登录改造 | **动登录链路** | 代码可回滚；凭据数据保留无害 |

A 做完，41 台柜子的停借保护会自行退场、C 端能借到宝、上线门禁能过。
B 做完，合同审批与会签才第一次能在真实多账号下跑通。

### 开始前需要确认

1. **A 的心跳模拟器**：同意「只发 `CAB1%` 号段 + 文件名带 demo + 不进 powerbank-jobs」这三条约束吗？
2. **B 的登录改造**：同意「凭据未命中回落到现有 admin 口令闸」这个兜底策略吗？
   （它意味着 admin 那条路会长期留着，直到所有人都有了凭据）
3. B 是否要**一并做前端**（改密页、建号入口），还是先只做后端接口。
