# 03 · 站点状态机（与门店生命周期合并）

> 定调：[运营核心流程](../../requirements/运营核心流程.md) §十.2。矩阵：S-SITE-01 / 02 / 03（L0）、S-EXIT-01…03（L1 留位）。
> 模块：`sharehub-svc-platform` · 包 `ai.neargo.sharehub.loc` · Controller 仍在 `sharehub-app/portal/platform/OpsController`（站点相关端点，本次不搬家）

---

## 一、现状与改动面

| 现状 | 改为 |
|---|---|
| `loc_site.status` 只有 `ACTIVE/PAUSED`；`saveSite` 仍接受任意 status | 五态状态机；**编辑接口不再收 status** |
| `loc_site_lifecycle` 另有一套阶段、自由跳转 | 停止写入；门店生命周期页改为只读漏斗（由商机阶段 + 站点状态 + 状态日志计算） |
| `pauseSite/resumeSite` 无事务、无日志；「恢复」无前置 | 走状态机、写状态日志、恢复前查合同 |
| 没有运维责任人 | 代理运维**复用已有的 `loc_site_agent.role=OPERATE`**（ADR-027 责任模型）；平台自营站点在 `loc_site` 加 `ops_employee_no`。二者合成「运维责任人」，是自动派单的依据 |
| 首台设备上线后站点状态靠人改 | 设备上线事件驱动 PREPARING → ACTIVE，每小时对账兜底 |
| `SiteBrief`（跨模块）没有状态 | 追加 `status` 等字段 —— 借出校验与告警判定要用 |

## 二、库表（迁移 M3）

```sql
SET NAMES utf8mb4;
-- M3：站点状态与门店生命周期合并（2026-09-25 定）。存量 ACTIVE/PAUSED 值与含义不变。
ALTER TABLE loc_site
  MODIFY COLUMN status VARCHAR(16) NOT NULL DEFAULT 'PREPARING'
    COMMENT 'PREPARING 筹备中 / ACTIVE 营业中 / PAUSED 暂停营业 / WITHDRAWING 撤场中 / CLOSED 已关闭',
  -- 代理运维责任人不在这里：用 loc_site_agent(role=OPERATE)，避免同一事实两处存
  ADD COLUMN IF NOT EXISTS ops_employee_no     VARCHAR(36)  NULL COMMENT '平台员工运维责任人（站点无生效 OPERATE 伙伴时使用）',
  ADD COLUMN IF NOT EXISTS first_live_at       DATETIME(3)  NULL COMMENT '首台设备上线时刻',
  ADD COLUMN IF NOT EXISTS pause_until         DATE         NULL COMMENT '预计恢复日（暂停时填）',
  ADD COLUMN IF NOT EXISTS withdraw_reason     VARCHAR(512) NULL COMMENT '撤场原因（L1）',
  ADD COLUMN IF NOT EXISTS withdraw_planned_at DATE         NULL COMMENT '计划撤场日（L1）',
  ADD COLUMN IF NOT EXISTS withdraw_started_at DATETIME(3)  NULL,
  ADD COLUMN IF NOT EXISTS closed_at           DATETIME(3)  NULL,
  ADD KEY IF NOT EXISTS idx_site_status (status);

-- 站点状态日志（追加型）。取代 loc_site_lifecycle_log 的写入；旧表保留只读作历史。
-- 为什么不复用旧表：旧表 from_stage/to_stage 的列注释是阶段词表，混写状态值会让存量词表卡口红。
CREATE TABLE IF NOT EXISTS loc_site_status_log (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  site_no      VARCHAR(36)  NOT NULL,
  event        VARCHAR(16)  NOT NULL COMMENT 'CREATE 建档 / GO_LIVE 首台上线 / PAUSE 暂停 / RESUME 恢复 / WITHDRAW 发起撤场 / CLOSE 关闭',
  from_status  VARCHAR(16)      NULL COMMENT 'PREPARING / ACTIVE / PAUSED / WITHDRAWING / CLOSED',
  to_status    VARCHAR(16)  NOT NULL COMMENT 'PREPARING / ACTIVE / PAUSED / WITHDRAWING / CLOSED',
  operator     VARCHAR(36)  NOT NULL COMMENT '员工号；系统触发为 SYSTEM',
  reason       VARCHAR(512)     NULL,
  created_at   DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  created_by   VARCHAR(36)      NULL,
  PRIMARY KEY (id),
  KEY idx_site_status_log (site_no, id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='站点状态迁移日志（追加）';
```

- `loc_site_status_log` 有 `site_no` → `DataScopeRegistration` 登记 `Map.of("SITE","site_no")`（代理维度恒空：此表只给运营端生命周期页用）。
- `loc_site_lifecycle` / `_log` 两表**不删**，停止写入；`SiteLifecycleServiceImpl.changeStage` 与其端点删除（见 §五）。

## 四、服务

新接口 `SiteService`（`loc.service`），把 `LocService` 里站点的写方法迁入；`LocService` 保留读与点位、场地方方法。

```java
public interface SiteService {
    Site create(SiteReq r);                                // → PREPARING，写日志 CREATE
    Site update(String siteNo, SiteReq r);                 // 属性；不改状态、不改 agentNo
    Site pause(String siteNo, String reason, LocalDate pauseUntil);
    Site resume(String siteNo);
    Site withdraw(String siteNo, String reason, LocalDate plannedAt);   // L1
    Site close(String siteNo, String note);
    Checklist openingChecklist(String siteNo);
    Checklist closeGate(String siteNo);
    List<SiteStatusLogItem> statusLogs(String siteNo);
    SiteSummary summary();
    /** 系统：设备上线事件与对账共用。已是非 PREPARING 则什么都不做（幂等）。 */
    boolean goLiveIfPreparing(String siteNo, LocalDateTime at, String cause);
    SiteTickResult tick();

```

### 4.1 迁移骨架

与合同同形（02 §4.1）：带范围读 → `sm.next` → **按原状态条件更新**（并发只一人赢，失败 409）→ 写 `loc_site_status_log`。所有写方法 `@Transactional`。

### 4.2 各动作

| 动作 | 前置（409） | 附带 |
|---|---|---|
| `create` | 场地方存在；`opsEmployeeNo` 若填须为在职员工（员工目录端口） | 状态 PREPARING |
| `update` | 同上 | `AuditChanges.record` 记责任人、营业时间变化 |
| `pause` | 原因非空；`pauseUntil ≥ today`（若填） | `paused_at=now`、`pause_reason` |
| `resume` | 站点有 ACTIVE 合同（否则 409「站点无生效合同，不能恢复营业」） | 清 `pause_reason/pause_until` |
| `withdraw`（L1） | 原因、计划日 | 停借由借出校验读状态生效；为每台已布放机柜开 `REMOVE` 工单（经 `WorkOrderCommandPort`，见 06） |
| `close` | `closeGate` 全通过 | `closed_at=now`；CLOSED 后才允许归档 |
| `archive`（现有） | 追加前置：状态必须 CLOSED | — |

### 4.3 `openingChecklist`（开业清单，筹备中站点展示）

| key | 通过条件 | 数据来源 | fixHref |
|---|---|---|---|
| `CONTRACT` | 有 ACTIVE 合同 | 本模块合同表 | `/venues?tab=contracts&siteNo=` |
| `LOCATION` | ≥ 1 个未归档点位 | 本模块 | 站点详情点位页签 |
| `OPS_OWNER` | 有生效中的 `OPERATE` 伙伴且代理 ENABLED，**或** `ops_employee_no` 为在职员工 | `loc_site_agent` + `AgentDirectoryPort` + 员工目录 | 站点详情 › 合作伙伴 / 站点编辑 |
| `OPEN_HOURS` | 营业时间已设 | 本模块 | 站点编辑 |
| `DEVICE_LIVE` | ≥ 1 台机柜 DEPLOYED | `CabinetQueryPort.countBySites(…, {DEPLOYED})` | `/devices?siteNo=` |

最后一项通过即由事件自动转营业，**清单本身没有「开业」按钮**。

### 4.4 `closeGate`

| key | 通过条件 | 来源 |
|---|---|---|
| `NO_DEVICE` | 站点下非 RETIRED、未归档的机柜数 = 0 | `CabinetQueryPort.countBySites(…, {IN_STOCK, IN_TRANSIT, DEPLOYED, FAULT})` |
| `NO_OPEN_WO` | 未完结工单数 = 0 | `WorkOrderQueryPort.openCountBySites` |
| `NO_IN_FLIGHT_ORDER` | 进行中订单（`DISPENSING/IN_USE`）= 0 | `OrderQueryPort.inFlightCountBySites` |

未通过项的 `detail` 写明数量（「还有 2 台设备」），前端据此列出并跳转。

### 4.5 设备上线 → 站点营业

```java
// loc/port/SiteGoLiveListener.java
@EventListener @Transactional(propagation = REQUIRES_NEW)
public void on(CabinetWentLiveEvent e) {
    DataScopeContext.executeWithoutScope(() -> sites.goLiveIfPreparing(e.siteNo(), e.at(), "cabinet " + e.cabinetNo()));
}
```

`goLiveIfPreparing`：条件更新 `WHERE site_no=? AND status='PREPARING'`，影响 1 行才写日志 `GO_LIVE` 与 `first_live_at` —— **天然幂等**，重复事件无副作用。

**兜底**（Outbox 进程内重投缺陷修好之前必需）：`tick()` 扫 `status=PREPARING` 的站点，批量查 `countBySites(…, {DEPLOYED})>0` 的，逐个 `goLiveIfPreparing(…, cause="reconcile")`。

### 4.6 `tick()`（`POST /internal/loc/sites/tick`，每小时）

1. 上节的 PREPARING 对账；
2. `PAUSED` 且 `pause_until < today` 的站点 → **只提醒不自动恢复**（L1：生成待办给运维责任人；恢复营业涉及场地实际情况，必须人确认）。

## 六、门店生命周期只读漏斗

`LifecycleRow(kind, no, name, phase, phaseSince, daysInPhase, owner)`，`kind ∈ {LEAD, SITE}`：

- 签约前：来自 `loc_lead`（阶段 = 商机阶段，`phaseSince` = 最近一次阶段变更的跟进时间）；已签约且已关联站点的商机**不再出现**（由站点接续）；
- 签约后：来自 `loc_site`（阶段 = 站点状态，`phaseSince` = `loc_site_status_log` 中进入当前状态的时刻；无日志的存量站点取 `updated_at`）；
- 漏斗汇总 `GET /api/ops/site-lifecycles/funnel` → 每阶段数量与平均停留天数。

## 七、存量归一（迁移 M8 的站点部分）

| 条件 | 处理 |
|---|---|
| `loc_site.status=ACTIVE` | 不变（即使暂无设备：不回退已营业的站点） |
| `status=PAUSED` | 不变 |
| 生命周期阶段 `CHURNED` 且站点 ACTIVE/PAUSED | **不自动改**；迁移头部注释给出清单查询，由运营逐个发起撤场 |
| 生命周期阶段 `CLOSED` 且站点下无机柜 | → `CLOSED`，写日志 `CLOSE`，`operator='MIGRATION'` |
| 运维责任人为空的存量站点 | 不回填；在站点概览「缺运维责任人」摘要里显形，并由告警 `SITE_OWNER_MISSING`（L1）持续提醒 |

## 八、借出侧的读取（与 04 衔接）

`RentOrderServiceImpl.rent` 通过 `SiteQueryPort.briefsByNos` 取 `status`，**只有 `ACTIVE` 可借**；
`PAUSED / WITHDRAWING / CLOSED / PREPARING` 一律 409「该站点暂停服务，可就近归还」。归还不查站点状态（保还）。
