## 零、一句话结论

**路径与字段层已经对完，缺的是「流程的后半段」。**
借出能下单，但「等弹出」是 `setTimeout` 假的；使用中能看订单，但费用不会走；
归还能结算，但**请款失败之后端上没有任何补缴入口**（`api.pay` 全仓零调用）。
所有列表都只有第一页。三件事合起来的形状是：**顺利路径都通，异常路径全断**。

## 三、优化方案

### P0 · 异常路径（用户会白等或吃错，且都在主流程上）

> **B1 进度（2026-09-27）**：§3.1 §3.2 §3.4 的**端上那一半已落地并实测**（见每条末尾的「已做」）；
> §3.3 未做（缺后端字段，见下）。动手时发现一件本文此前说错的事，先更正：
>
> **「等弹出是假的」「使用中不计时」两条，根因不只在端上，后端同样没有这两件事。**
> `RentOrderServiceImpl.rent()` 第 234 行 `e.setStatus("IN_USE")`（注释写着「免押预授权 +
> 弹仓为骨架，直接置借用中」）—— **订单从不经过 DISPENSING，也不等设备回执**；
> `enrich()` 返回的 `durationMin`/`feeAmount` 是库里存的那两列，而它们**只在归还那一刻写入**，
> 进行中的单恒为 0。
>
> 所以端上若只是「轮询到 IN_USE 就成功」，在真后端上第一轮必然成功 —— 那是一个
> **写没写都一样绿**的改动。已做的是：端上不再自己编结果（以服务端状态为准、有超时有失败出口），
> mock 层按目标状态机走（DISPENSING → 回执 → IN_USE）好让这段逻辑可验；
> 而「真的等柜机」要等后端补完下面三件。

**⬜ 后端待办（B1 的另一半，未动 —— `RentOrderServiceImpl.java` 当时有另一会话在改）**

| # | 做什么 | 备注 |
|---|---|---|
| a | `rent()` 落单为 `DISPENSING`，发 `EJECT` 指令，由设备回执（`EJECT_OK`）迁到 `IN_USE` | 状态机与 `cancelUndelivered(orderNo)` **都已存在**，后者正是「DISPENSING 才能撤」的那条；现在无人走到它 |
| b | 出宝超时任务：到点调 `cancelUndelivered` 并释放预授权 | 目前只有告警处置链路（`TradeFixers`）会调，且注释写明「接入前只撤单不动钱」 |
| ~~c~~ | ~~进行中订单的实时试算~~ | **已做**（`a0e167e`）：`RentOrderService.estimateNow` 按与结算逐项相同的计价链试算，出参 `estimatedFee`/`estimatedDurationMin`/`capped`，只给单条投影（列表不带，N+1）；用例 `ConsumerLiveFeeTest` 钉住「试算 = 立即归还后的实付」，负对照已验 |


**1. 借出「等弹出」是假的 —— 不轮询、不超时、不兜底（C-RT-04/05）**

[confirm.vue:87](../../c-app/src/pages/order/confirm.vue:87) 是 `setTimeout(() => stage = "success", 1000)`：
**下单返回即宣布成功**，与柜机是否真的弹出无关。而 `DeviceEvent RENT_CONFIRMED`
才是弹出的唯一事实来源。后果分两种，都比报错难查：宝没出来而界面说成功（用户空手走人、
订单在计费）；或者弹出确实失败了，而**预授权没有被撤销**——清单要求的「失败自动解冻」一行都没有。

这不是漏了想法，是漏了接线：`shared/constants.ts` 里
`POLL_INTERVAL_MS`（[:21](../../c-app/src/shared/constants.ts:21)）与
`DISPENSE_TIMEOUT_MS`（[:23](../../c-app/src/shared/constants.ts:23)，注释直接写着
「超过触发解冻/关单兜底，C端功能清单 C-RT-04」）**全仓零引用**——常量定了，轮询没写。

**已做**（端上那一半）：下单后按 `POLL_INTERVAL_MS` 轮 `getOrder`，`IN_USE` 才进成功页；
`EXCEPTION`/`CLOSED` 或超过 `DISPENSE_TIMEOUT_MS` 进**失败页**（换柜 / 带单号报障 / 查看订单三个出口）。
两个死常量现在有人用了。失败页的文案**不承诺「授权已释放」** —— 后端那条路（`cancelUndelivered`）
的注释写着「接入前只撤单不动钱」，承诺一件没做的事比不说更糟。
mock 层给了 `CAB-TIMEOUT` 这个**永不回执的柜机号**做负对照，否则失败页在 mock 下永远走不到。

**2. 使用中订单是静止的（C-US-01/03）**

[detail.vue:22](../../c-app/src/pages/order/detail.vue:22) 只在 `onLoad` 拉一次。
「实时计时计费」在界面上表现为一个不动的数字——用户唯一的判断方式是反复退出重进。
且整页**没有归还指引**（C-US-03：就近可还网点、空仓提示），而这是使用中最高频的需求。

**已做**：时长**在端上按 `rentStartAt` 现算**（`elapsedMin`，秒针 1s，`onHide` 停表），
不再显示那个恒为 0 的 `durationMin`；**不编造费用** —— 计费口径全在服务端，
端上乘个单价得到的是「差一点」的数字，而用户会拿它去对账单，所以进行中的头部改为显示走字的时长，
配一句「费用在归还时按结算规则计算」。订单状态每 `ORDER_REFRESH_MS` 回查一次（归还由柜机侧触发，
端上收不到推送，这一页要自己变成结算展示）。首页那张常驻卡同病同治（此前写着「0 分钟 · AED 0.00」，
读起来像这次免费）。「找可还网点」已加，跳 `home?returnable=1`。

⚠️ `rentStartAt` 是**不带 Z 的 UTC**（`LocalDateTime.now(ZoneOffset.UTC).toString()`），
按本地时区解会少算 4（迪拜）/ 8（上海）小时，刚借的单显示成负数 —— `parseUtc` 显式按 UTC 解。
（2026-09-27 更正：此前这里写「`timeline[].at` 跟着服务器时区走、与 `rentStartAt` 不是一个口径」——
查实是错的：两者同经 `OrderSupport.now()` = `LocalDateTime.now(ZoneOffset.UTC)` 写入，同为不带 Z 的 UTC。
时间线差 8 小时的真因是端上按本地时区解析，已改为 `utcTimeOf`。另一种口径确实存在，但在钱包流水等
走 `AuditMetaObjectHandler` 的 `createdAt`：那是 `LocalDateTime.now()`，跟着 JVM 时区。）

**3. 支付只有下单那一刀 —— 无收银台、无重试、无欠费补缴（C-PAY-01/05 · C-BL-04）**

`ports/payment.ts` 的 `pay()` 与 `api.pay()` **全仓无人调用**（只有 `preAuthFreeDeposit` 被用）。
意味着：归还请款失败挂账后，端上**没有任何补缴入口**；而 C-BL-04 的规则是
「欠费拦下次借出」——于是用户被拦住，却在 App 里找不到能付钱的地方，只能找客服。
这是一条闭死的环。

**未做，而且比「缺个字段」更深一层（2026-09-27 查证）**：**结算从不请款。**
`returnOrderAt` 算完钱就 `SETTLE` 并发结算事件，全仓**没有任何一处**在归还时
`payments.pay(...)` 或 `capture(...)`（唯一的租借支付入口是 `POST /mp/trade/pay`，
而端上从没调过）。押金同理 —— `rent()` 只写 `deposit_amount` 这一列，不收钱。

于是「欠费」这个状态**在数据上还不成立**：`pay_order` 里每一张已结算订单都没有支付记录，
照实算的话全部历史订单都是欠费。现在加 `paidAmount`/`unpaidAmount` 出参，结果是
订单列表整页挂满「欠费」标记 —— 那不是修好了 C-BL-04，是把一个骨架缺口摊到用户脸上。

顺带一个要在上线前拍板的次序问题：`OrderSettledEvent` → `ShareGenerator`
**照「应收」生成了分润明细**，而那笔钱从没收过。桩支付阶段无所谓，接真通道时
「先收钱还是先分账」必须有个说法。

正确顺序：① 归还结算时按免押预授权 `capture`（ADR-005：capture ≤ 预授权额，超额走补付），
失败才挂账；② 那之后「欠费」才有意义，再补 `paidAmount`/`unpaidAmount` 出参与端上入口
（端点与入参都是现成的：`POST /mp/trade/pay {orderNo, scene}`，金额由服务端从订单取）。
①是支付语义的决策（capture 自预授权 / 扣钱包余额 / 两者兼有），不该顺手做掉。

（以下是原来的记述，仍然成立：）`ConsumerOrderVO` 没有任何「已付/欠费」的表达
（只有 `feeAmount`），端上无从知道一张已结算的单到底付没付 —— 画个「立即支付」按钮
要么对所有结算单都画（多数人已经付过），要么全靠猜。
先补出参（`paidAmount` / `payStatus`，由 `pay_order` 派生），再接端上的入口：
订单详情出「立即支付」→ `pay({scene:"RENT", orderNo})`，首页与借出确认页在有欠费时前置提示。
端点与入参都是现成的（`POST /mp/trade/pay {orderNo, scene}`，金额由服务端从订单取）。

**4. 借出前没有登录门禁**

[home.vue:62 `onScan`](../../c-app/src/pages/home/index.vue:62) 与 `borrow()` 都不看 `isLoggedIn`，
游客一路点到确认页，`submit()` 时 401 → `installSessionGuard` **reLaunch 到登录页**，
借出意图（`cabinetNo`、选好的券与免押方式）全部丢失，登录完落回首页要从扫码重来。
清单 C-RT-02 写的是「未登录先登录」。

**已做**：`shared/auth-gate.ts` 的 `ensureLoggedIn(redirect)` 前置在 `onScan`/`borrow`（确认页再兜一道），
登录成功按 `redirect` **`redirectTo`** 回原页（不是 navigateTo —— 否则返回键会退回一个已经登录的登录页）。
⚠️ 回跳参数要**反复解码**：门禁编一次、uni 的 H5 路由写进 hash 时又编一次，
只解一次得到的是 `%2Fpages%2F…`，`redirectTo` 不报错、只是跳不过去，而「跳不过去」
和「没写回跳」长得一模一样。

**5. 报障附件是摆设（C-CS-01）**

[feedback.vue:41](../../c-app/src/pages/order/feedback.vue:41) 能选 3 张图，提交时一张也不发——
后端无字段、无上传端点。这类「看起来记录了」的控件比没有更糟：用户以为拍了照就说明清楚了，
于是描述写得更短，客服两头都拿不到信息。
**二选一，不要留现状**：接一个上传端点 + `ReportReq.attachments`；或先摘掉选择器，
在描述框提示「请文字描述故障仓位号」。

### P2 · 结构与工程

**12. 会员顺序已经对，登记依赖即可**：先 C-MB-02（权益进计价链），再开 C-MB-01 购买。
现在的「即将上线」是正确选择，不要为了补齐清单而提前开购买。

**13. Capacitor 壳 vs uni 原生构建（影响 C-RT-01）**：`capacitor.config.ts` 的
`webDir: dist/build/h5` 说明 APK 装的是 H5 产物，WebView 里 `uni.scanCode` 这类原生插件不生效——
**扫码在当前 APK 上点不动**，而扫码是借出的唯一入口。三条路：改用 uni-app 原生 App 构建；
