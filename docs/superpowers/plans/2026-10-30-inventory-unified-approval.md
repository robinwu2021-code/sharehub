# 库存统一审批接入执行计划

> 继续执行既有库存方案；用户已明确授权继续实现，并要求需要审核的库存业务统一依赖审核模块。使用 executing-plans 与 TDD 在当前分支续做，不另建本地审批引擎。

**Goal:** 先闭合盘点提交→OpsKit统一审批→库存服务调整执行→结果回写，并为后续库存审批沿用相同模块边界。
**Architecture:** OpsKit决定审核人、待办、审核结论及历史；宿主仅存盘点业务关联、冻结版本、原提交人、送审轮次与执行恢复状态。库存服务继续拥有盘点实盘及调整凭证。复用ApprovalRequestedEvent、Outbox、验签webhook、ApprovalOutcomeHandler。
**Tech Stack:** Java21 / Spring / MyBatis / Flyway / Next.js / Vitest。
**Spec:** 原执行顺序S02、DEV-32及DEV-13；用户本轮关于统一审核模块的指令优先。

## 设计与取舍

用户已选择统一审批。沿用OpsKit，取消库存页面直接批准／驳回；不复用资金ApprovalGate建立另一张待审列表。提交只送审，批准后技术性调用库存approve/post；审批通过但执行失败明确显示，并可受控重试，不重复审批或重复调整。

V220兼容新增inv_count_review，仅保存业务联接／恢复元数据，不保存审批步骤或库存余额。流程inventory_count_audit使用独立device:inventory:audit权限，selfApproval=false；宿主回写仍校验审批单、原提交人和内容版本。仓管默认仅录入，OPS／ADMIN沿用既有权限可审核；不向仓管默认授审核权。流程定义随部署文件发布，未配置OpsKit时提交明确拒绝，不退回本地审批。

已提交后禁止本地扫码、作废、直接审核及未经授权过账。审批撤回／驳回由统一模块办理后恢复可编辑。审批单号未回填时的提前回调返回冲突等待重投，旧轮次回调不得推进新轮次。数据库先持久化发送意图，再修改远端；请求／审批／执行重试使用稳定键，并通过远端实际状态和contentVersion核对恢复。真实外部幂等保留期及UAT保持条件验收。

## 预检
