## 二、备份怎么做

- 每天 03:30 跑一次，避开 ai-shop 03:20 的备份。
- `mysqldump --single-transaction` 取一致性快照，不锁表、业务照常写；然后 gzip，上传 COS（`hxmall-backup-1301656997/db/powerbank/`）。
- 本机只留最近 3 天的备份；COS 由桶的生命周期规则管理：30 天后转低频存储，90 天后归档，365 天后删除。
- **失败即报错**：以下任一情况都以非 0 退出，cron 会把输出寄出：
  - 备份文件不是完整的 gzip；
  - 文件末尾没有 `Dump completed` 标记（例如磁盘满导致写了半截）；
  - 上传失败。
- 口令与上传命令放在 `/data/app/powerbank/ops/backup.env`（权限 600），不写进 cron 文件，也不进仓库。

**备份账号权限**：需要 SELECT、SHOW VIEW、TRIGGER、LOCK TABLES。如果库是 MySQL 8 及以上，另需 RELOAD 或 FLUSH_TABLES；MariaDB 不需要。

> ⚠️ **待确认**：部署 README 写现网用的是与 ai-shop 共用的 **MySQL 9.7**（端口 3307），上线检查清单写的是 **MariaDB**。两者的备份账号权限不同，请以现网 `SELECT VERSION()` 的结果为准，并修正写错的那份文档。

## 三、恢复演练怎么做（每月第一个工作日）

```bash
# 1. 取最新一份备份（本机 3 天内的，或从 COS 下载）
ls -t /data/backup/powerbank/db/pb_core-*.sql.gz | head -1
# 2. 恢复到演练库并核对（库名必须以 restore_drill_ 或 test_ 开头，脚本拒绝其它库名，防止误覆盖生产）
set -a; . /data/app/powerbank/ops/backup.env; set +a
/data/app/powerbank/ops/restore-drill.sh <备份文件> restore_drill_202611
# 3. 演练完删掉演练库
```

脚本核对三件事，任一不过就退出码非 0：
1. 迁移历史里没有失败的记录，并打印最高版本号，供与发布记录对照。
2. 关键表都在：订单、用户、商家、分润、结算单、系统参数、员工。
3. 系统参数表和员工表不为空，也就是基础数据确实恢复了。

把输出（恢复用时、最高版本、各表行数）记进下面的演练记录表。**恢复用时**就是真出事故时要等的时间。

开发机演练中发现并修好了两处脚本问题：
- MySQL 9 的 `mysqldump` 默认写 GTID 信息，恢复到同一实例时报错。已改为客户端支持时关掉 `--set-gtid-purged`。
- `set -o pipefail` 下，`mysqldump --help | grep -q` 会被误判为失败，导致上面那个选项没加上。已改为先取全文再匹配。

## 五、恢复到生产（真出事故时）

先在演练库里确认这份备份是好的（第三节），再停应用：`systemctl stop powerbank`。然后：
1. 把当前库改名留底，不要直接删。
2. 把备份恢复到 `pb_core`。
3. 启动应用。Flyway 会校验迁移历史；如果备份比当前代码旧，启动时会补跑缺的迁移。
4. 走一遍上线检查清单的冒烟测试。

**备份时点之后产生的订单与付款会丢失**，需要用支付通道的流水补录，所以事后必须对一次账。
