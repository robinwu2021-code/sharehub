## 一、一页结论：5 个端只有 2 个接入面

| 端 | 形态 | 接入面 | 端点数 | 专属后端？ |
|---|---|---|---:|---|
| **运营端** ops-web | Web（Next.js） | `/api/**`（6 前缀） | 312 | 是，占后端 85% |
| **加盟商 / 代理商** | **ops-web 的角色视图**（§3.5 定案，不建独立前端） | `/api/**` 同一批端点 | 复用（6 个门户叶） | **否** —— 靠 Realm + 数据范围收敛 |
| **C 端 App**（Android 套壳） | uni-app → H5 → Capacitor | `/mp/**` | 38 | 是 |
| **C 端 H5** | uni-app → H5（**唯一上线产物**） | `/mp/**` **同一批** | 38 | 否 |
| **C 端小程序**（微信） | uni-app → mp-weixin（**未打包过**） | `/mp/**` **同一批** + 2 个 | 38 + 2 | 否 |

> 「加盟商」「代理商」「城市合伙人」是**同一实体**的不同叫法（`agt_agent`，不新增主体）。
> **「商户 / 场地方」是另一个主体**（`loc_venue`，出场地、按进场合同拿分成），**不登录运营端、没有账号**，不在本文的「端」里。
> 看竞品对照时注意：简电云语境下的「商户」映射的是我们的场地方，不是代理商。

**两句话**：

1. **C 端三壳（App / H5 / 小程序）是同一份 uni-app 代码条件编译出来的三个产物，调同一套 `/mp/**`。**
   差异只在登录方式和端能力，落到接口上只多 2 个小程序专用端点（`/mp/auth/methods`、`/mp/user/phone/wx`），
   不存在「小程序的一套 API」。
2. **加盟商没有、也不该有自己的一套 API。** 代理商是运营方体内的受限外部伙伴（[ADR-012](../technical/ADR/ADR-012-代理商模型.md)），
   走 `AGENT` Realm（令牌前缀 `atk_`）进 `/api/**`，看到什么由**功能权限 + 数据范围**决定，不由路径决定。
   现有 `/api/agent/**` 那 17 个端点是**运营人员管理代理商**用的，不是代理商自己用的（见 §三）。

**端点总账**（contract.json 实测）：

| 接入面 | 端点 | 谁调 |
|---|---:|---|
| `/api/**` | **312** | ops-web（含代理门户） |
| `/mp/**` | **38** | c-app 三壳 |
| `/internal/**` | **18** | 进程之间（⚠️ 其中 4 个被 ops-web 从浏览器直调，见 §五） |
| 合计 | **368** | |

规划中新增但尚未落地的接入面：`/gw/**`（厂商 Webhook）、`/ocpp/**`（充电桩）、`/pay/callback/**`（支付通道）、
`/openapi/**`（第三方，预留）—— 见 [v4/04 §一](../technical/v4/04-接口.md)。它们都不面向人，不在本文的「端」里。

## 三、加盟商 / 代理商（Agent）

### 3.1 先分清两类接口

| | 谁在用 | 路径 | 状态 |
|---|---|---|---|
| **A. 管代理商** | 运营方的员工（招商、财务） | `/api/agent/**` 17 个 | ✅ 已实现 |
| **B. 代理商自己用** | 代理商账号 | **不是新路径**，是 A 之外的运营端端点 + `AGENT` 数据范围 | ⚠️ 门户已搭，后端收敛未做 |

这是最容易搞混的一点：`/api/agent` 这个前缀的意思是「代理商这个**业务域**」，不是「代理商这个**端**」。
17 个端点的权限码全部是运营侧的（`agent:account:manage` · `agent:scope:assign` · `agent:share:config`），代理商自己没有这些码。

### 3.4 代理门户的五个缺口（实测）

| # | 缺口 | 证据 | 影响 |
|---|---|---|---|

### 3.5 代理端形态：**ops-web 的角色视图**（2026-09-23 定案）

**代理不是一个"端"，是 ops-web 的一个角色视图。** 不建独立前端、不建 `agent-bff`、不建独立小程序。
已回填 [ADR-012](../technical/ADR/ADR-012-代理商模型.md)（原文留的两条路择一）、
[运营端功能清单 §二](../requirements/运营端功能清单.md)、`PDF对齐-系统优化方案.md` 待确认第 2 条。

理由：**接口面零增量** —— §3.3 那 6 叶背后全是既有 `/api/**` 端点，独立工程的成本 100% 落在前端与打包上。
要移动端就把这 6 个页面做响应式。

**落到工程上的三条约束**：

1. **不新增路径前缀** —— 代理看到什么由「功能权限 + 数据范围」决定，不由路径决定。
   不要因为「这是代理的接口」就去开 `/api/agent/my-*`。
2. **菜单由后端下发** —— 今天是前端 `portalFor: ["AGENT"]` 硬编码（[nav.ts:124](../../ops-web/lib/nav.ts:124)），
   [v4/06](../technical/v4/06-认证与权限.md) 规划改为 `iam_function.realm='AGENT'` 单独一棵树，由 `/api/auth/menus` 下发。
3. **开放前必须先补 §3.4 的 G3** —— 数据范围没收敛，角色视图就是个摆设：菜单裁剪住了入口，接口还是返回全量。

> 仍然未定的是**门店端**（场地方 `loc_venue`）。它与代理端不是一回事：代理商有 `agt_account` 账号表和 `AGENT` Realm，
> 场地方今天**没有任何账号体系**，要先决定给不给登录，再谈形态。

### 4.3 三壳的差异：只有 2 个端点，其余都在端内

这是本文最要紧的一张表 —— **「小程序要不要另做一套 API」的答案在这里**：

| 差异点 | App | H5 | 小程序 | 接口层面 |
|---|---|---|---|---|
| **登录方式** | `PHONE_OTP` · `PASSWORD` · `APPLE`(iOS) · `GOOGLE`(Android) | `PHONE_OTP` · `PASSWORD` | `WX_MINI` 静默 | **同一个** `POST /mp/auth/login`，靠 `grantType` 分发 |

> ⚠️ **枚举口径现在是两套，写代码前先确认在哪一侧**：
> 代码里实际跑的是**小写**（`phone_otp` · `password` · `apple` · `google` · `wechat_miniapp` · `wechat_oauth`，
> 见 `c-app/src/api/contract.ts:31` 与后端 5 个 `ConsumerLoginStrategy`）；
> 上表的**大写 + 改名**（`WX_MINI` 等）**只存在于 v4 规划文档**，代码里一处都没有。迁移挂在 [v4/06](../technical/v4/06-认证与权限.md) 的 A6 项。
| **可用方式的下发** | 按国家配 | 同 | 同 | 🆕 `GET /mp/auth/methods?platform=&country=` —— 唯一因多壳而生的端点 |
| **绑手机号** | 验证码 | 验证码 | `getPhoneNumber` | `POST /mp/user/phone/bind`（通用）· 🆕 `POST /mp/user/phone/wx`（**小程序专用**） |
| **支付拉起** | 卡 / Apple Pay / Google Pay | 卡 | 微信支付 | 同一个 `POST /mp/trade/payments`，出参 `cashier.channel` 不同 |
| **401 处理** | 跳登录页 | 跳登录页 | **先静默登录重试一次**，失败再跳 | 端内逻辑，无端点差异（[v4/06 §4.3](../technical/v4/06-认证与权限.md)） |
| **版本更新** | 检查并提示 | 不适用 | 微信自管 | 同一个 `GET /mp/app/version`，H5/小程序不调 |
| **扫码 / 定位** | 原生权限 | 浏览器 API | 微信 API | 端能力，走 `src/ports/`，无端点差异 |

**所以：小程序 = 三壳共用的 38 个 + 2 个（`auth/methods` 与 `phone/wx`），没有第二套 API。**

因载体而生的端点一共只有 3 个，且**两个还没实现**：

| 端点 | 状态 |
|---|---|
| `GET /mp/app/version?platform=` | ✅ 后端已实现（`platform ∈ IOS/ANDROID/H5`），**c-app 完全没调** |
| `GET /mp/auth/methods?platform=&country=` | ⬜ 只在 v4 文档里。支撑表 `sys_login_setting` 存在，但**没有微信/小程序开关列** |

小程序这条线的真实成熟度：**一个未被引用的端侧函数**（`ports/auth.ts` 的 `acquireLogin`，登录页绕过了它）

## 六、要新起一个端时，先问这三个问题

1. **它的使用者是不是已有 Realm？** 员工 / 代理 → `/api/**`；消费者 → `/mp/**`。
   三个 Realm（`stk_` / `atk_` / `ctk_`）已覆盖全部人类使用者，**新端不等于新 Realm，更不等于新前缀**。
2. **差异是"看到的数据不同"还是"能做的事不同"？**
   前者用数据范围（代理商就是这一类），后者用功能权限。两者都不需要新端点。
3. **真正需要新端点的，只有端能力差异。**
   对照 §4.3：三个壳跑下来，因端而生的端点一共 2 个。这是一个有用的标尺 ——
   如果某个新端提出要几十个专属端点，多半是把「数据范围」当成了「新 API」。
