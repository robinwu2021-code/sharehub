## 新增前缀：`/ocpi/2.2.1/**`

现有前缀有 `/api`(运营) `/mp`(C端) `/internal`(服务间) `/gw`(南向) `/notify`(第三方回调) `/openapi`(我们开放给客户)。
**互联互通需要第七个前缀**，理由是它与既有六个都不同：

| 前缀 | 谁调 | 认证 | 协议自由度 |
|---|---|---|---|
| `/openapi` | 我们的客户（B端） | 我们定义的 AppKey | **我们定** |
| `/gw` | 设备/厂商云 | 驱动验签 | 我们定 |
| **`/ocpi`** | **行业伙伴（eMSP）** | **OCPI Token A/B/C 三段式** | **对方定（国际标准）** |

**路径与出入参形状由 OCPI 规范决定，不套用本项目的 `Result<T>` 信封**
—— 这是唯一豁免统一响应契约的前缀。套自己的信封等于让每个伙伴为我们做特殊适配，
与「对齐行业标准，不自创」的决策自相矛盾。

`ApiResponseWrapper` 需按包排除 `interconnect.northbound`。

## 一、设备类型（运营端）

| 方法 | 路径 | 权限码 | 说明 |
|---|---|---|---|
| GET | `/api/platform/device-types` | `system:device_type:read` | 列表 |
| GET | `/api/platform/device-types/{typeCode}` | `system:device_type:read` | 详情 |
| POST | `/api/platform/device-types/{typeCode}` | `system:device_type:update` | upsert（自然键，须显式给键） |

**只有三个端点，且无删除** —— 类型被订单/设备引用，删除会产生孤儿。停用走 `status`。

**出参 `DeviceType`**：`typeCode` · `nameZh/En/Ar` · `hasMovableItem` · `itemTable` ·
`orderExtTable` · `defaultMetering` · `reservationTarget` · `supportsReturnElsewhere` ·
`commandFamily` · `status`

## 二、计价：费用项与阶梯

| 方法 | 路径 | 权限码 |
|---|---|---|
| GET | `/api/trade/price-plans/{planNo}/items` | `pricing:plan:read` |
| POST | `/api/trade/price-plans/{planNo}/items` | `pricing:plan:update` |
| POST | `/api/trade/price-plans/{planNo}/items/{itemNo}` | `pricing:plan:update` |
| DELETE | `/api/trade/price-plans/{planNo}/items/{itemNo}` | `pricing:plan:update` |
| GET | `/api/trade/price-items/{itemNo}/ladders` | `pricing:plan:read` |
| PUT | `/api/trade/price-items/{itemNo}/ladders` | `pricing:plan:update` |
| POST | `/api/trade/price-plans/{planNo}/preview` | `pricing:plan:read` |

**阶梯用 `PUT` 整组覆盖而非逐条 CRUD**：阶梯必须连续无缝隙无重叠，
逐条增删会产生中间非法态。整组提交 → 服务端一次性校验区间闭合。

**`/preview` 是试算端点**（入参：`deviceType` + 计量值如 `{minutes:90}` 或 `{kwh:23.5, idleMin:10}`，
出参：逐费用项明细 + 合计）。运营改价前能看到效果，
**它同时是「影子重算」迁移校验的接口** —— 用它跑存量订单比对新旧账单。

**入参 `PriceItemReq`**：`itemType` · `metering` · `freeQty` · `unitQty` ·
`capDaily` · `capTotal` · `rounding` · `sort`

## 三、预约（泛化）

| 方法 | 路径 | 权限码 | 端 |
|---|---|---|---|
| GET | `/api/ops/reservations` | `order:reservation:read` | 运营 |
| POST | `/api/ops/reservations/{no}/cancel` | `order:reservation:cancel` | 运营（客服代取消） |
| POST | `/mp/reservations` | 属主 | C端 下单预约 |
| GET | `/mp/reservations` | 属主 | C端 我的预约 |
| POST | `/mp/reservations/{no}/cancel` | 属主 | C端 取消 |

**入参 `ReservationReq`**：`deviceType` · `siteNo` · `cabinetNo` · `targetRef`（桩=枪号，宝=空）
· `reservedFrom` · `reservedTo`

**`targetRef` 的粒度由 `md_device_type.reservation_target` 决定，服务端校验**：
桩必须给具体枪（`SLOT`），充电宝给柜机即可（`CABINET`）。前端传错直接 400 —— 
**不做「智能兼容」**，粒度错了说明调用方理解错了业务。

## 四、C 端：充电与储物柜

### 充电桩 `/mp/charge/**`

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/mp/charge/start` | 启动充电（入参 `cabinetNo` + `connectorNo`；返回 `orderNo`） |
| POST | `/mp/charge/{orderNo}/stop` | 主动停止 |
| GET | `/mp/charge/{orderNo}/live` | **过程态**：已充 kWh / 当前功率 / 预估金额 / SOC |

**`/live` 的数据只作展示，不作结算依据** —— 结算认 `TX_STOP` 的表底数（`meter_stop`）。
出参须带 `estimated: true` 标记，前端展示「预估」而非「金额」，
避免用户按过程值预期最终账单。

### 储物柜 `/mp/locker/**`

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/mp/locker/store` | 存物（分配格口，返回 `accessCode`） |
| POST | `/mp/locker/{orderNo}/open` | 开格取物（校验属主 + 取件码） |

### 通用

`GET /mp/orders` 加 `deviceType` 筛选；`GET /mp/orders/{no}` 出参按类型附带对应 ext 段。

## 五、南向 `/gw`（设备事件回调）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/gw/{vendorCode}/events` | 统一事件入口（driver 解析后归一化） |
| POST | `/gw/{vendorCode}/ocpp` | OCPP WebSocket 升级入口 |
| POST | `/gw/{vendorCode}/meter-values` | 计量上报（高频，独立端点便于限流） |
| POST | `/gw/{vendorCode}/tx-stop` | 交易结束（带表底数，**结算依据**） |

**事件命名一律是物理事实**：`EJECT_OK` / `ITEM_INSERTED` / `TX_START` / `TX_STOP` /
`CELL_OPENED` —— 不是 `RENT_CONFIRMED` / `RETURNED`。
「这算不算某订单的归还」由 core 判定；换柜归还、误插回、非订单宝插回都是 core 的业务规则。

**指令与报文不携带消费者个人信息**（PDPL）—— 设备只需要知道「弹哪个仓」。

## 六、北向 `/ocpi/2.2.1`（互联互通）

伙伴调我们。**路径与形状遵循 OCPI 规范**，下表为我们作为 CPO 需实现的模块：

| 模块 | 方法 | 路径 | 说明 |
|---|---|---|---|
| Versions | GET | `/ocpi/versions` · `/ocpi/2.2.1` | 版本协商（握手入口） |
| Credentials | GET/POST/PUT/DELETE | `/ocpi/2.2.1/credentials` | Token 三段式交换 |
| Locations | GET | `/ocpi/2.2.1/locations[/{id}]` | 发布站点/桩/枪目录 |
| Tariffs | GET | `/ocpi/2.2.1/tariffs` | 发布价格（**由计价引擎的展开结构转换**） |
| Sessions | GET | `/ocpi/2.2.1/sessions` | 过程状态 |
| CDRs | GET | `/ocpi/2.2.1/cdrs` | 账单明细 |
| Commands | POST | `/ocpi/2.2.1/commands/{START_SESSION\|STOP_SESSION}` | **伙伴远程启停** |

**`Commands` 是唯一的写入口**，它内部调 core 的订单 API 建单
（`sourceChannel=INTERCONNECT` + `partnerNo`），**不绕过订单域直接控设备**。
绕过会让互联互通单不进分润、不进对账 —— 资金侧只认 `ord_order` 的红利就没了。

### 运营端伙伴管理

| 方法 | 路径 | 权限码 |
|---|---|---|
| GET | `/api/platform/interconnect/partners` | `system:partner:read` |
| POST | `/api/platform/interconnect/partners[/{no}]` | `system:partner:update` |
| POST | `/api/platform/interconnect/partners/{no}/handshake` | `system:partner:update` |
| GET | `/api/platform/interconnect/cdr-logs` | `system:partner:read` |
| POST | `/api/platform/interconnect/cdr-logs/{no}/resend` | `system:partner:update` |

**凭证只回掩码**（与 `pay_channel` 同规），明文进 KMS。

## 七、改造既有端点（14 处）

| 端点 | 改造 |
|---|---|
| `GET /api/trade/orders` | 加 `deviceType` 筛选；出参加 `deviceType`/`subStatus`；**表名 `ord_rent`→`ord_order`** |
| `GET /api/trade/orders/{no}` | 出参按类型附 ext 段（`rentExt`/`chargeExt`/`lockerExt`） |
| `GET /api/ops/cabinets` | 加 `deviceType` 筛选，出参加 `deviceType` |
| `GET /api/ops/cabinets/{no}` | 槽位出参加 `slotKind`/`connectorStd`/`powerKw` |
| `GET /api/trade/price-plans` | 加 `deviceType` 筛选；出参 `items` 摘要 |
| `POST /api/ops/cabinets/{no}/commands` | 指令按 `commandFamily` 校验（发桩不认识的指令 → 400） |
| 分润/账务/发票/结算 4 组列表 | **join 表名改 `ord_order`，出入参不变** —— 这正是共性主表的价值 |
| `GET /internal/gw/vendors` | 出参加 `deviceTypes` + `protocol` |

**兼容策略**：`ord_rent` 保留只读视图一个版本周期，上述端点可分批切换，不必一次全改。
