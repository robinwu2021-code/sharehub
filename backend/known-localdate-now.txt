# 直调 LocalDate.now() 台账 —— 只准变短，且**每次变化都要改数字**（在 review 里显形）。
#
# 由 BizDateFromBizClockTest 卡住：格式 `类名 处数`，按类**精确相等**比对。
# 精确相等而不是「不超过」：同一个类里删一处又加一处会互相抵消，那样棘轮就是摆设。
#
# ───────────────────────────────────────────────────────────────
# 为什么直调是错的
#
# LocalDate.now() 取的是**服务器 JVM 时区**。生产实测跑在 Asia/Shanghai
# (-Duser.timezone=Asia/Shanghai)，而业务在阿联酋（sharehub.biz-zone=Asia/Dubai）。
# 于是每天有 4 小时 —— 迪拜 20:00 到午夜，正是租借高峰 —— 它比业务「今天」早一天。
#
# 已经造成过的后果（2026-09-27 查出）：
#   · 有效期到 9-30 的券，迪拜 9-30 20:00 起判为过期 —— 用户看得见、又说不出所以然的损失
#   · 合同签署撞上「日期不能晚于今天」，10 条用例同时红
#
# 这类缺陷**每天自己好一次**：过了那 4 小时再跑就全绿。于是它看起来像偶发抖动，
# 最坏的情况是有人为了「修」它去放宽服务端校验 —— 那是把真约束拆掉，
# 换来一个永远不会红的测试。
#
# 业务日期一律走 BizClock#today()。什么算业务日期：会被人在业务日历上核对的东西
# （合同生效/终止日、券有效期、免费额度的自然月、结算归属期间）。
# ───────────────────────────────────────────────────────────────
