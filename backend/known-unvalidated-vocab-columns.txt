# 词表列的写入侧**待核实**台账 —— 只准变短。
#
# 由 VocabularyWriteCoverageTest 卡住。格式：每行 `表.列`，一行一个**尚未核实**的列。
#
# ───────────────────────────────────────────────────────────────
# 这台账要解决的是「没有任何东西说这一列的入口还没接」
#
# 事后卡口 StoredValueInVocabularyTest 比对**库里已存的值**与列注释，
# 但脏数据必须**先落库**才会被它发现 —— 而那时该查的是当初写它的那次请求，
# 现场早没了。2026-09-27 一天之内串错三次（V82 告警等级 / V84 对账差异 /
# V85 活动类型与拉黑原因），三次的写入方都绕开了校验。
#
# 最值钱的一条实证：share_rule.mode / share_record.mode 曾有 17 行 RATE（V66 归一），
# 写它们的是 ShareServiceImpl.saveRule —— 而 ShareMode.of() **那时已经存在、只是这里没调**。
# 词表有定义、校验有实现、中间那一步没接上，三者都不报错。
#
# ───────────────────────────────────────────────────────────────
# 怎么把一行从这里去掉
#
# 1. 写入口调对应枚举的 of()（**用 ofNullable 口径**：传了才校验 ——
#    保存端点创建与编辑共用，编辑只传要改的字段，没传的 null 表示「不改」。
#    第一版用 of() 的后果是「改个活动名字都会被拒」：改的是值的合法性，
#    却顺手改了字段是否必填，而后者从来不是这道题）；
# 2. 往 VocabularyRejectedOnWriteTest 里**加一格**（POST 词表外的值必须 400，
#    并带正对照 —— 只验拒绝不验放行，会把「一律拒」也判成通过）；
# 3. 从本文件删掉那一行。
#
# ⚠️ **新增词表列时必须当场表态**：要么接上校验，要么把它加进本文件并说明为什么先不接。
# 卡口会拦住「悄悄多出一列没人管的词表列」—— 那正是这三次串错的共同形状。
#
# ───────────────────────────────────────────────────────────────
# ⚠️ 这个数字是「**待核实**」不是「**有缺陷**」—— 两者差别很大
#
# 建账时我先用「VocabularyRejectedOnWriteTest 覆盖了哪几列」去推，当场就错了：
# AlarmCodeServiceImpl 实际逐个 of() 校验了 8 列（level / domain / subjectType /
# evalType / disposition / mergeScope / recoverRule / basePriority），
# 而那条卡口只验过 level —— 于是另外 7 列被我误记成「没接」。
#
# 分清两件事：
#   (a) **写入口调了校验** —— 真正的保护；
#   (b) **有端点用例证明它会拒** —— 证明。
# 台账记的是「(a) 尚未有人核实」。一行被移出，要么是读代码确认了 (a)，
# 要么是补了 (b)（更好：(b) 顺带证明了 (a)，且以后改坏会红）。
#
# 也不能反过来按「代码里出现过 of()」自动判 —— 按字段名匹配两个方向都不准
# （AlarmNo / SiteNo 之类根本不是词表校验），而**判不准的卡口比没有更糟**：
# 它会让人以为「绿了就是接上了」。所以覆盖与否由人写，机器只管账对不对得上。
#
# 口径：与 StoredValueInVocabularyTest **共用同一份判据**（VocabularyColumns）——
# 注释里凑得出两个及以上大写取值，且列名不是 _no / _ref / _hash / tenant_id
# （按本仓库约定不可能是枚举），且库里存的值像枚举（≤25 种、个个大写形）。
#
# 建账当天分叉过一次：只抄了「注释里有没有词表」那半条，漏了「存的值像不像枚举」，
# 于是 agt_principal.phone_hash（注释写着 HMAC-SHA256）这类列被记了进来。
# 判据抽成 VocabularyColumns 之后两条卡口不可能再分叉。
#
# 与事后卡口唯一的分歧是**空列**：库里还没有任何取值时形状判不出来。
# 事后卡口跳过它（没有数据就没有脏数据），本台账**保留**它 ——
# 新建的空表恰恰是最该当场表态的，跳过等于说「新表的状态列不用接校验」。
# 当前 279 列里有 90 列是这种情况。
#
# ⚠️ 已知漏网 8 列：按取值形状判成了非枚举，其中 6 个确实是自由文本
# （sys_app_version.version_id / sys_outbox.aggregate_id / iam_dept.path /
# wo_order.wo_created_at / share_record.period / price_schedule.period），
# iam_role.code 是可扩展的角色码（191 种）不算固定枚举，
# 而 wo_sla_rule.priority **是真枚举**，只因词表里有个 `*` 哨兵值（「类型默认」）
# 不合大写形而掉了出去。它是这份判据目前唯一的假阴性，记在这里以免被当成不存在。
#
# 2026-09-28 建账：词表列 279，已核实 22，待核实 257。
# 同日核实第一批（钱那一侧）：已核实 27，待核实 252。（fin_invoice.status 接上校验；
# 四个 payee_type 查明不来自请求体 —— 常量/派生/已有白名单，见 COVERED 旁的说明。）
# 同日第二批（实体请求体可写的那 18 个）：**已核实 44，待核实 235**。
# 挑这一批不是凭印象，是拿 known-entity-writable-fields.txt 跟本清单求交集 ——
# 那些列前端直接写得进去、中间**没有任何 setXxx 拦着**，风险最高。
# 18 个里 7 个真没接（已接上并各带端点格）、8 个原来就有校验（建账时没人核，属于虚高）、
# 2 个服务端全权。剩 1 个 usr_invoice_title.vat_trn **不是词表列**（税号是自由文本），
# 只因那张表是空的、判据看不到取值而留在这里 —— 表一有数据它会自动掉出去。
#
# ⚠️ 这一批最值钱的发现与词表无关：usr_invoice_title 判税号必填写的是
# "COMPANY".equals(type)，而 type 不校验 —— 传小写 company **既不报错也不要税号**，
# 抬头存下来了，按它开出去的发票是废的。归一大小写才是真正的修复。
#
# 同日第三批（订单域 + 设备 OTA）：**已核实 59，待核实 220**。
# OTA 四列新接上校验（原先只在空的时候补默认值）；ord_deposit.last_dun_channel 接上；
# 其余 10 列读代码核实为「原本就有白名单」或「服务端常量/状态机」。
#
# ⚠️ 第三批的方法论教训：**只 grep `setXxx(` 那一行会得出错的结论**。
# ord_complaint.resolution 的 setter 是 `e.setResolution(req.resolution())`，
# 看着是请求体直达，而白名单 RESOLUTIONS.contains(...) 就在它上面几行。
# 自动分类只能排优先级，判定必须读方法。
#
# 同日第四批（告警域 + 设备域 29 列）：**已核实 88，待核实 191**。
# 告警域几乎全是「服务端全权」——引擎内部用枚举 .name() 写、人工关闭走 AlarmCloseReason.of()、
# 通知渠道抄自已覆盖的 dev_alarm_rule.channel、时间线 event 是 private writeLog 的字面量。
# 两处真缺口已接：dev_powerbank.health（参与可借判定，原先原样落库）、
# dev_alarm_route.wo_type（原先**只在 disposition=WORK_ORDER 时才校验** ——
# 换个处置方式就能把词表外的值存进去，等哪天改回 WORK_ORDER 开单时才炸）。
#
# ⚠️ 这一批撞出两个与词表无关、但严重得多的缺陷，都已修（见实现状态总表 §六 ⑭）：
# 告警路由**改第二次就 500**（软删的行占着唯一索引）· **连续建第二只充电宝必定 500**（取号每次给同一个号）。
#
# 同日第五批（合同域 + 工单域 24 列）：**已核实 112，待核实 167**。
# 两处真缺口已接：loc_contract.settle_period（写错 = 保底永远不补差，
# AdjustmentServiceImpl 判 !"MONTH".equalsIgnoreCase 就跳过、只 log.warn）、
# wo_order.audit_result（它驱动「FAIL 不许关单」那道闸，原先却不校验 ——
# 传小写 fail 那道闸拦不住，且最后报的是「关单原因必填」，指向错的字段）。
#
# ⚠️ 第五批反方向证了一次「只 grep setXxx 会判错」：wo_order 有七列
# **一个 setXxx 都搜不到**，差点被当成死列 —— 它们是用 UpdateWrapper.set("列名", ...)
# 按列名写的。实体 setter 与 UpdateWrapper 列名是两条写入路径，查一条不够。
#
# 同日第六批（钱那一侧剩下的 21 列）：**已核实 134，待核实 146**。
# 这一批**一个真缺口都没查出来** —— finance 域的守法很统一：要么枚举 .name()、
# 要么方法开头的白名单（ACTION_RESULT / PAY_CHANNELS / DEBIT-CREDIT 的 else-throw），
# 而白名单**离 setter 有十几行远**，只看 setter 那一行会连着误判三次（本轮就撞了三次）。
#
# ⚠️ pay_auth / pay_order / pay_refund 的 status 带**前提**：它们落的是 PaymentPort
# 返回的 r.status()，是**支付驱动**给的，不是请求体。当前 StubPaymentPort 返的就是
# 本仓枚举名，所以成立；接 nearpay 之后那个 Port 实现必须把渠道方状态映射成本仓词表，
# 原样透传就要把这三行挪回台账。与 stl_withdrawal.approval_state 同类。
#
# ⚠️ 两个 `period` 列（stl_adjustment / agt_ops_assessment）不是词表列 ——
# 装的是 YYYY-MM。它们留在这儿的原因和 usr_invoice_title.vat_trn 一样：
# 表是空的，取值判据看不到值。表一有数据就会自动掉出去。
# pay_channel.channel_code 同理是**可扩展的自然键**（STRIPE/TABBY/NEARPAY…）不是固定枚举。
#
# ⚠️ 三个「没有任何写入路径」的表/列**故意留在台账上**：
# ord_exception（create 零调用方）· ord_reservation（只有 page/cancel，一处 insert 都没有）
# · dev_ota_task（只读）。这里「没人写」不等于安全，等于这个功能没有生产者 ——
